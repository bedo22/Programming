The Rhythm — How Developers Think When Building a Feature

Tutorials teach syntax. Almost none teach the thinking process that precedes the code. Here it is: three threads — Model, View, Flow — cycled as a loop, and the one upfront decision that catches traps while they cost minutes, not days. Anchored to How Developers Think.

Where this fits

The Ecosystem is done — you know the language, the platform, state, the camps, and React's revolution. The Practice movement begins: how developers actually think when building a feature (this lesson), a contrasting path in Angular (L8), and where React is heading (L9).

1. Three threads, not a sequence

When a senior developer sits down to build a feature, they do not follow a waterfall — "first the HTML, then the CSS, then the JavaScript." Instead they hold three intertwined threads and cycle through them, each pass deeper than the last:

  • Model — the data structures and state shape. What the app knows.
  • View — the structure and layout, the visual hierarchy. What the user sees.
  • Flow — the events, the data movement, the logic. What happens.

The crucial word is cycle. You don't finish the Model and never return. You sketch a little data, build a little view, wire a little flow, then go back to the Model with what you learned. Each round is deeper. This is a rhythm, not an algorithm.

2. The loop, not the waterfall

You cycle through the threads in rounds, each one a deeper pass. A common shape: Round 1 — Skeleton (the thinnest end-to-end slice that works at all: one piece of data, one element, one event). Round 2 — Make it real (real data, real layout, real interactions). Round 3 — Polish (edge cases, accessibility, performance). You don't move to the next round by a rule — you move when you feel the friction: when the current round starts to creak, that's the signal to deepen.

This is not a new idea. The reference doc traces it back through decades of the same insight: Boehm's spiral model (1986), iterative and incremental development, Kent Beck's Extreme Programming (1999), the Agile Manifesto (2001), and Eric Ries's Lean Startup MVP (2011). All of them say the same thing in different words: build in narrowing spirals, let feedback tell you when to go deeper. The frontend loop is that idea applied to a single feature.

3. The one upfront decision: sketch the data shape

Before any of the cycling, there is one decision that catches more bugs than any other: sketch the data shape first. The reference doc gives a concrete sequence:

  • Nouns — what are the things in this feature? (a todo, a cart, a product, a user…)
  • Fields — what fields does each noun have, and what are their types?
  • Collection — what holds the nouns? (an array, a Map, a Set…)
  • Operations — what does the user do to the data? (add, remove, filter, toggle…)
  • Where state lives — which component holds which piece?
  • What's derived — what can be computed from the rest, and therefore should not be stored as state?

Here's the payoff. If your data shape distinguishes "loading" from "loaded but the results are empty," you avoid the classic trap of flashing "no results found" while the fetch is still in flight. You saw the trap before writing a line of code — while it cost minutes, not days. That is what sketching the data shape buys you.

The win

  
You now hold the thinking process that precedes the code: three threads — Model, View, Flow — cycled as a loop, each round deeper, moving on when you feel the friction. And the one upfront decision that pays off most: sketch the data shape first — nouns, fields, collection, operations, where state lives, what's derived. That habit catches traps like "loading vs empty" while they cost minutes, not days. The loop has a lineage — spiral model, Agile, Lean Startup — but on a single feature it's simply how seniors avoid staring at a blank file.
