Problem-Solving — Pólya's Four Phases

You know the atoms, the ecosystem, the practice, and the system. But there's a layer you've been using without knowing its name — the thinking skill that sits between finding the problem (Design Thinking) and building the feature (The Rhythm). Here it is: a four-phase rhythm from 1945 that you already intuited in your HackerRank comments. Anchored to Problem-Solving.

Where this fits

The technical spine is complete — atoms (L1–3), ecosystem (L4–6), practice (L7–9), system (L10–11). Before going upstream to the human layer (L16–17), we pause to name the connective tissue: the thinking skill you use to solve any problem, whether it's a HackerRank challenge or a React feature. This is the Bridge movement — 4 lessons that deepen your thinking before you go upstream.

The three layers of thinking. This is the reframe that makes everything click:

  • Layer 1 — Design Thinking (reference): "What problem should I solve?" — desirability, feasibility, viability. Upstream of code.
  • Layer 2 — Problem-Solving (this lesson): "How do I solve this problem?" — understand, plan, execute, review. The missing middle.
  • Layer 3 — The Rhythm (reference, L7): "How do I build this feature?" — Model → View → Flow. The implementation loop.

You've had Layer 1 (coming in L17) and Layer 3 (L7). Layer 2 was never named — you intuited it, but didn't have the vocabulary. This lesson names it.

1. The mathematician who mapped thinking (1945)

In 1945, a Hungarian mathematician named George Pólya published How to Solve It — a book that has sold over a million copies, been translated into 15+ languages, and is still in print 80 years later. Pólya didn't invent problem-solving; he named what good problem-solvers already did. His contribution was a four-phase checklist — a rhythm you cycle through for every problem, from a homework exercise to a competitive programming challenge.

The four phases are deceptively simple:

  • Phase 1 — Understand the problem. What is the unknown? What are the data? What is the condition? Can you restate it in your own words?
  • Phase 2 — Devise a plan. Have you seen this before? Can you solve a part? Can you work backwards? Can you use a concrete example?
  • Phase 3 — Carry out the plan. Execute each step, checking each step as you go.
  • Phase 4 — Look back. Can you check the result? Can you derive it differently? Can you use the method elsewhere? What did you learn?

That's it. Four phases. No magic. The power is in the discipline of actually doing all four — especially the last one, which everyone skips.

2. You already use this — your HackerRank comment proves it

Remember this comment you wrote for a word-frequency counter challenge?

Input: a string of text to analyze
Operation: count the number of times each word appears
Output: an object with each word (lowercased) as a key
Algorithm:
  1- create an empty object to hold the word frequencies
  2- split the input string into an array of words
  3- iterate through the array of words
    a- for each word, convert to lowercase and remove punctuation
    b- if the word is not already a key, add it with a value of 1
    c- if the word is already a key, increment its value by 1
  4- return the object containing the word frequencies

You did Phase 1 (Input / Operation / Output — that's restating the problem in your own words) and Phase 2 (the numbered algorithm — that's the plan). You'd do Phase 3 when you wrote the JavaScript. What you skipped was Phase 4 — the look-back: what if the string is empty? What about numbers? What about contractions like "don't"? What pattern does this teach you? (Answer: "count occurrences → hash map" — a pattern you'll see again and again.)

You were two-thirds of Pólya without knowing his name. That's the value of learning the framework: it names what you already do, and it shows you what you're missing.

3. A rhythm, not an algorithm — and why that matters

Here's the key insight that resolves your original question ("is it a rhythm or an algorithm?"): it's both, at different levels.

  • At the meta-level, Pólya's four phases are a rhythm — a repeatable cycle you go through for every problem. You cycle through them, you go back to "understand" when your plan reveals a gap, you revise your plan when execution fails. It's iterative, like The Rhythm (L7).
  • At the object-level, each individual problem's solution (your numbered steps for word counting) is an algorithm — a specific, finite sequence of steps that solves that problem.

So: problem-solving is a rhythm (Pólya's phases) that produces an algorithm (the specific solution). The rhythm is the process; the algorithm is the product.

This also explains why the frontend loop (L7) is called "Rhythm, Not Algorithm" — you can't write down a fixed sequence of steps for "build a feature." But for a HackerRank challenge, you can write down a fixed sequence. The difference is the problem type, not the thinker.

4. Well-defined vs wicked — why HackerRank gets an algorithm but features get a rhythm

PropertyWell-defined problemWicked problem
ExamplesHackerRank, LeetCode, math proofsUI features, product decisions, architecture
InputClearly specifiedEvolving, ambiguous
OutputClearly specifiedSubjective, contested
SuccessObjective (tests pass)Subjective (users like it?)
StoppingClear (all tests pass)No true stop — only better or worse
Output typeAn algorithmA rhythm

Both use Pólya's four phases at the meta-level. But well-defined problems converge to a fixed algorithm (you can write down the exact steps), while wicked problems require a rhythm (the steps change as you learn). Your HackerRank challenge is well-defined — it gets an algorithm. Your React feature is wicked — it gets the Model→View→Flow rhythm (L7). Same thinker, same four phases, different output type.
