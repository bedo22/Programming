Solution Evaluation — Big O, Quality Attributes, and Trade-offs

You solved the problem. But is the solution good? This lesson teaches the evaluation skill: the parameters (what you measure), the measures (Big O), the trade-offs (when parameters conflict), and the judgment (which parameters matter when). Traced through a real brute-force solution and its upgrade. Anchored to CS & SE.

Where this fits

Lesson 16 named the umbrella discipline (CS & SE). This lesson teaches the skill at its core: solution evaluation — the deepening of Pólya's Phase 4 (Look back). This is the last Bridge lesson; next, we go upstream to the human layer (L18: UI/UX, L19: Design Thinking, L20: Income/Markets).

1. The four layers of evaluation

After you solve a problem (Pólya's Phase 3), you evaluate the solution (Phase 4). That evaluation has four layers:

  • The parameters — what you measure: time complexity, space complexity, correctness, readability, maintainability. The formal name is quality attributes (ISO 25010 defines 8).
  • The measures — how you quantify: Big O notation for time and space. O(n) means "linear growth." O(n²) means "quadratic growth."
  • The trade-offs — when parameters conflict: faster often means more memory; more readable often means less optimized. The Pareto front is the set of solutions where you can't improve one without degrading another.
  • The judgment — which parameters matter for your context, and when to stop optimizing. HackerRank: time/space. Production: maintainability. Interview: clarity + correctness.

2. Big O — the complexity classes you need to know

Big ONameExampleAt n=1000
O(1)ConstantHash map lookup1 operation
O(log n)LogarithmicBinary search~10 operations
O(n)LinearSingle pass; your word counter1,000
O(n log n)LinearithmicMerge sort, quick sort~10,000
O(n²)QuadraticNested loops1,000,000
O(2ⁿ)ExponentialNaive FibonacciUniverse ends

How to analyze: count the loops. One loop over n = O(n). Nested loop = O(n²). Halving each iteration = O(log n). The highest-order term dominates — O(n² + n + 5) is just O(n²). On HackerRank, the time limit is ~10⁸ operations. If your solution is O(n²) and n = 10⁵, that's 10¹⁰ — too slow. You need O(n log n) or better.

3. Trade-offs — the engineering reality

You cannot maximize all parameters simultaneously. The standard trade-offs:

  • Time vs space — precompute and cache (faster, more memory) vs compute on the fly (slower, less memory).
  • Readability vs performance — bit manipulation is fast but unreadable; clear code is readable but potentially slower.
  • Simplicity vs flexibility — hardcoded is simple but rigid; configurable is flexible but complex. (YAGNI says: start simple.)

The engineering skill is making trade-offs explicit — naming what you're sacrificing and why. "I'm trading O(1) space for O(n) time here, because the input can be 10⁵ and the O(n²) approach would time out."

4. Judgment — which parameters matter when

ContextPrimaryDeprioritize
HackerRankTime, space, correctnessReadability, maintainability
Production frontendMaintainability, readability, usabilityMicro-optimization
InterviewCorrectness, clarity, communicationOptimal Big O (working O(n²) > broken O(n))

Knuth's principle: "Premature optimization is the root of all evil" (1974). It doesn't say "don't optimize" — it says don't optimize before you know it matters. Measure first. Is it on the critical path? Have you profiled it? Will optimization hurt maintainability? This is the same judgment as The Rhythm's "feel the friction" (L15) — build simple first, optimize where it creaks.

5. Worked example — evaluating a brute-force solution

Problem: "Find the first non-repeating character in a string."

Brute force (O(n²)): For each character, count its occurrences in the whole string. Correct, readable, but nested loop = O(n²). At n=10⁵, that's 10¹⁰ — too slow for HackerRank.

Upgrade (O(n)): Count all characters once in a hash map, then scan once for the first count of 1. Two single passes = O(n). The trade-off: we traded O(1) space for O(n) space — the hash map uses extra memory. Time vs space.

The judgment: On HackerRank (n up to 10⁵), the upgrade is mandatory — O(n²) will time out. In production (n < 100), the brute force is fine — 10,000 operations is instant, and it uses no extra memory. In an interview, start with brute force, then say: "This is O(n²), which works for small n. For large n, I'd use a hash map for O(n)." The evaluation skill IS the interview signal.

The win

  
You now hold the evaluation skill — the judgment that ties together parameters (what you measure), measures (Big O), trade-offs (when they conflict), and context (which parameters matter when). The key insights: Big O tells you how your solution scales (O(n²) at n=10⁵ is 10¹⁰ — too slow). Trade-offs are inevitable (time vs space, readability vs performance) — the skill is making them explicit. Knuth's principle — don't optimize before you know it matters. And the deepest one: the same two solutions get different answers depending on context — HackerRank needs the optimal algorithm; production often needs the simplest one. The evaluation skill IS the interview signal, and it's the skill AI can't replace — because AI doesn't know your context.
