Problem-Solving — Paradigms + Debugging

Pólya's phases tell you when. CT tells you what. Heuristics tell you how. This lesson gives you the tools (six algorithm paradigms) and the application (debugging as inverted problem-solving, plus the "Look back" phase everyone skips). Anchored to Problem-Solving.

Where this fits

Lesson 13 gave you the lens (computational thinking), the moves (heuristics), and the monitor (metacognition). This lesson gives you the paradigms — the fundamental approaches to designing an algorithm — and the application: debugging (the same four phases, inverted) and the "Look back" phase that builds long-term skill. This is the final problem-solving lesson; next, we deepen the rhythm (L15).

1. The tools — six algorithm design paradigms

During Phase 2 (Devise a plan), after you've decomposed and recognized patterns, you need to choose a paradigm — a fundamental approach to designing the algorithm. There is no single optimal algorithm for all problems; there are paradigms, each fitting a different class of problem. Recognizing which paradigm a problem calls for is itself a pattern-recognition skill built through practice.

ParadigmWhen to use itExample
Brute forceAlways start here if the input is small. Get it correct first, optimize later.Find all pairs that sum to N (nested loop)
GreedyWhen local optimum = global optimum. Prove it works before trusting it.Minimum coin change (certain systems)
Divide & conquerWhen sub-problems are independent (solving one doesn't depend on another).Merge sort, binary search
Dynamic programmingWhen sub-problems overlap (the same sub-problem appears multiple times).Fibonacci, knapsack, edit distance
BacktrackingWhen you need to explore all possibilities but can prune early.N-Queens, Sudoku solver
Hash tableWhen you need fast lookup, counting, or deduplication. Often the upgrade from brute force O(n²) → O(n).Your word-frequency counter, two-sum

The critical distinction — D&C vs DP: Divide & Conquer is for independent sub-problems (merge sort: each half is sorted independently). Dynamic Programming is for overlapping sub-problems (Fibonacci: fib(5) needs fib(4) and fib(3), but fib(4) also needs fib(3) — so you store fib(3) rather than recomputing). If the sub-problems don't overlap, use D&C. If they do, use DP. This single distinction is one of the most tested in interviews and competitions.

Your HackerRank word-frequency counter uses the hash table paradigm — you intuitively recognized that counting occurrences is a hash-map problem, not a brute-force "search the array each time" problem. The skill to build: solve enough problems that you start recognizing the paradigm from the problem statement, before you even plan the steps.

2. Debugging — the same four phases, inverted

Debugging is problem-solving. The problem is simply: "Why doesn't this code do what I expect?" It follows Pólya's four phases, but the direction is inverted — you start from the symptom (the wrong output) and work backwards to the cause. Recognizing debugging as problem-solving (not a separate ad-hoc activity) is what separates systematic debuggers from people who randomly change things and hope.

  • Rubber duck debugging (Hunt & Thomas, 1999) — explain your code, line by line, to an inanimate object. The act of explaining forces you to articulate your assumptions — and the bug is almost always in an assumption you didn't realize you were making. This is Phase 1 (Understand) applied to your own code.
  • Hypothesis-driven debugging — the scientific method: Observe → Hypothesize → Predict → Test → Conclude. Don't change code until you've confirmed the cause. The anti-pattern is changing code without a hypothesis — "let me try removing this line" — which is guessing, not debugging.
  • Binary search debugging — when a bug is somewhere in a large codebase, apply divide & conquer: put a checkpoint in the middle. Is the state correct there? If yes, the bug is in the second half. If no, it's in the first half. The same algorithm paradigm applied to the debugging process itself.

3. The "Look back" phase — what everyone skips

Phase 4 (Look back) is the phase that builds the most long-term skill and is the most consistently skipped. After a solution passes, the temptation is to move on immediately. Resist it. The minutes you spend here compound into the pattern recognition that makes future problems faster.

Three things to do during Look back:

  • Check edge cases. Empty input, single element, all-same, maximum size, boundary values, null/undefined. For your word-frequency counter: what if the string is empty? ("".split(" ") gives [""] not [] — a bug.) What about numbers? Contractions like "don't"?
  • Ask "can I derive it differently?" Is there a simpler approach? A more efficient one? A more general one? For word-frequency: could you use reduce instead of a for loop? Could you make it a reusable countOccurrences(tokens) function?
  • File the pattern. What category does this problem belong to? What signal in the problem statement told you the approach? For word-frequency: "count occurrences" → hash map paradigm. Filed under: hash-map / frequency-counting. Next time you see "count how many times each character appears," you'll recognize it instantly.

This is how pattern recognition is built — not by reading about patterns, but by filing them after solving. Each filed pattern is one more entry in your mental lookup table. After 50 problems, you'll recognize categories from the problem statement. After 200, from the first sentence.
