The Class→Hooks Revolution — React's Biggest Mental-Model Shift

For its first five years, React components were classes: this, bind, lifecycle methods. Then in 2018 the team introduced hooks and made functions the default. The counterintuitive part: functions already existed — they just couldn't hold state. Anchored to the paradigm-shift reference.

Where this fits

This is the Ecosystem finale. It leans directly on Lesson 3 — the class→hooks story is, at bottom, the story of where state lives. It also sets up the frontier (Lesson 9), where the compiler finishes what hooks started. See the plan.

1. React's first model: classes

When React shipped in 2013, a component was a class. It extended React.Component, held its state in this.state, mutated it with this.setState, and ran side effects in lifecycle methods with names like componentDidMount, componentDidUpdate, and componentWillUnmount. To pass a handler safely you had to bind(this) in the constructor — a ceremony every React dev memorized.

This worked. Facebook ran on it. But over five years of maintaining tens of thousands of components, the React team watched the same three pains repeat at scale.

2. The three problems, and the counterintuitive catch

The React team's own 2018 post, Introducing Hooks, named three problems they'd watched repeat across tens of thousands of components:

  • Hard to reuse stateful logic. To share behavior (say, "subscribe to a friend's online status"), you wrapped components in layers of higher-order components and render props — "wrapper hell" in the DevTools tree.
  • Giant, hard-to-follow components. One component's unrelated concerns (fetching, subscriptions, timers) were split across componentDidMount, componentDidUpdate, and componentWillUnmount — the same concern scattered across three methods.
  • Classes confuse people and machines. this, bind, super(), and constructor were a tax every learner paid; they were also hard for tools to optimize.

Here's the counterintuitive catch that most summaries skip: React already had function components before hooks — and they were not enough. Early function components were stateless: they could return JSX from props, but they couldn't hold state or run side effects. So for anything real, you still needed a class. Functions alone weren't the answer — functions lacked the powers that made them usable for real components.

3. Hooks: giving functions the missing powers

Hooks (2018) are the missing piece. useState lets a function hold state across renders; useEffect lets it run side effects and clean them up. Now a function component could do everything a class could — and the three problems dissolved:

  • Reuse → custom hooks. Extract stateful logic into a function that calls hooks; any component calls it. No wrappers, no nesting.
  • Giant components → one effect per concern. Setup and cleanup for one concern live together in one useEffect; unrelated concerns get separate effects.
  • No this. The function's locals (including the setter from useState) are ordinary variables. No this to lose, no bind.

And recall Lesson 3: state is just a variable that persists and matters across events. With hooks, the variable didn't change kind — it just moved. In a class, state lived in this.state (the instance). With hooks, state lives in a React-owned slot, indexed by the order you called useState. Same variable, different owner. The component asks React to remember; React holds the real cell.

The deepest reason. Function components capture the rendered values — each render has its own box for props and state, and a handler closes over that box, which doesn't change. Classes read this.props, which React mutates on every render. So a delayed handler (say, an alert 3 seconds after a click) shows the right person with functions and the wrong person with classes. You can't fix it by binding — binding pins this, but the bug is that this mutates. The fix is to capture, which is exactly what closures do. This is why the shift was deeper than "functions are tidier."

The win

  
You now hold React's biggest shift: classes (2013, this/bind/lifecycles) gave way to functions + hooks (2018) because hooks gave functions the two powers they lacked — useState (state) and useEffect (effects) — dissolving wrapper hell, giant components, and this. The counterintuitive key: functions already existed; they just couldn't hold state until hooks. And the deepest reason is that functions capture rendered values (correct) while this mutates (buggy). Per Lesson 3, state just moved from the class instance to a React-owned slot — same variable, different owner. Classes remain in the spec, but no one teaches them first anymore.
