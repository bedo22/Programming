The Contract — How Systems Speak Without Speaking

An API is a contract — a promise that lets services and clients evolve independently. Its defining trait is high reversal cost: these decisions are expensive to change later. The styles (REST, GraphQL, gRPC) are tools, not religions. Anchored to API Design.

1. What an API actually is

Most tutorials teach "how to call an API." API design starts somewhere else: what contract lets both sides move without breaking each other? An API is a contract — a stable, evolvable boundary between independent deployables (a server and a browser, two services, a mobile app and a backend). It produces decisions, not code: what are the resources? What does each call promise? How does the API say "no" in a way the client can act on? How do we add, change, and remove things without breaking existing clients?

Here is the defining characteristic: these decisions are expensive to change later. Wire-format changes need coordinated deployments. Interface changes need consumer migrations. Both are multi-week efforts in any real system. That high reversal cost is what makes API design a distinct discipline — not just "writing an endpoint," but deciding the promises that endpoint makes.

2. Two layers of the same contract

The reference doc splits an API contract into two layers — both are API design, and neither is complete without the other:

  • Interface contract (macro) — what the consumer sees: resources, operations, versioning, authentication, rate limits, error envelope, pagination strategy, idempotency semantics. The promises.
  • Wire contract (micro) — what the bytes say: serialization format, schema evolution rules, field-level nullability, enum extensibility, timestamp formats, transport (HTTP/1.1, HTTP/2, gRPC, WebSocket). What makes the promises verifiable.

Both matter. A beautiful interface contract with a broken wire contract is unverifiable; a perfect wire contract with an incoherent interface is unusable. The interface sets the promises; the wire makes them real.

3. Styles are tools, not religions — and bad contracts leak downstream

"REST vs GraphQL vs gRPC" is not a religion. Each won a different era by fitting a different constraint:

  • REST (Roy Fielding's dissertation, 2000) — resources + HTTP verbs + stateless. Won the public-API era because it's simple, cacheable, and works with a curl command.
  • GraphQL (Facebook, 2015) — client-specified queries, one endpoint. Won the mobile era because it solved over-fetching and under-fetching on slow connections.
  • gRPC (Google, 2015) — HTTP/2 + Protocol Buffers, contract-first codegen. Won the internal-microservices era because it's fast, typed, and streaming-built-in.

The core idea — a stable boundary between independent deployables — never changed. What changed was the dominant constraint, and the style that fit it. That's the same "extend vs invent" pattern from Lesson 4, applied to contracts.

And here's the cost of getting it wrong: a bad contract doesn't stay at the boundary. It forces "paper-over code" downstream — loading states that shouldn't exist, retries that patch over flaky semantics, type assertions that paper over schema drift, toast storms for errors the client can't programmatically handle. That friction is exactly what Lesson 7's developer loop absorbs. The contract is upstream of the UI; design it there.

The win

  
You now hold the contract layer: an API is a contract — a promise that lets both sides move independently — and its defining trait is high reversal cost (these decisions are expensive to change later). It has two layers: interface (the promises the consumer sees) and wire (the bytes that make them verifiable). The styles — REST, GraphQL, gRPC — are tools for different constraints, not a religion; the stable-boundary idea never changed while the winning style did. And the cost of a bad contract doesn't stay at the boundary — it forces paper-over code downstream in the UI, which is exactly what the developer loop (Lesson 7) then has to absorb.
