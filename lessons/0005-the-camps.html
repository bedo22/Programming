The Camps — How Real Products Ship UI

Knowing the atoms, you might assume "frontend" means one thing — a React single-page app. It doesn't. Real products ship UI in different camps, each optimizing for something different. Knowing the camp tells you where the JS lives. Anchored to Frontend Camps Survey.

Where this fits

Lesson 4 showed JS running across stacks. But on the frontend stack specifically, not everyone builds the same way. This lesson is a map of the camps you'll actually meet at work — not a tutorial in any one of them. Next, Lesson 6 dives into React's own internal revolution. See the plan.

1. Frontend is not one thing

If your only exposure is a Vite + React tutorial, you'd think "frontend" is a single-page app: a mostly-empty HTML page that downloads a big JavaScript bundle and renders everything in the browser. That is one camp. It is not the only one.

At work you will open repositories that look nothing like that. Some are WordPress themes that render HTML on the server and use jQuery for a carousel. Some are Astro sites that ship almost no JavaScript. Some are Next.js apps where the server renders part of the UI and the browser renders the rest. These are not lesser or greater — they are different camps, each optimized for a different constraint. The reference doc calls them centers of gravity, not exclusive clubs.

2. The five camps

The reference doc maps roughly five camps. What distinguishes them is the unit of work and the JS load strategy — where the JavaScript lives, and how much of it ships to the user.

  • CMS / classic server — the server owns the document (PHP, Rails, Django). JS is optional sugar for forms and widgets. The page is real HTML on every request.
  • HTML-first — server HTML plus small interactive "islands." Ship almost no framework. (Astro is the flagship.) The document is the product; JS is a garnish.
  • SPA (single-page app) — a client app shell. A large initial JS bundle downloads, then the browser owns the UI and re-renders on navigation without round-trips. (Classic Vite + React.)
  • Meta-framework — route + data + UI together, split between server and browser. The framework decides what ships where. (Next.js, Nuxt.)
  • WASM / systems UI — a compiled module does the heavy logic; JS is glue. (Figma-ish, games, heavy visualization.)

3. The thing that confuses everyone: camps overlap

Here is the part that breaks the tidy mental model. These camps are not exclusive boxes. A Next.js app is a meta-framework, yet on some routes it behaves exactly like an SPA. A WordPress site can host a React admin SPA inside it. An Astro site (HTML-first) can embed a React island that is, locally, an SPA.

So treat the labels as centers of gravity, not walls. You don't ask "is this camp A or camp B?" — you ask "what is the dominant pattern here, and where does the JS actually live?" That question tells you which mental model applies, how much ships, and whether your React intuition holds as-is or needs adjusting.

The win

  
You now hold a map of how real products ship UI: five camps — CMS, HTML-first, SPA, meta-framework, WASM — distinguished most by where the JS lives and how much ships. The crucial nuance: camps overlap; they're centers of gravity, not walls. At work, you don't ask "which camp is this exclusively?" — you ask "what's the dominant pattern, and where does the JS actually live?" That recognition keeps you from forcing one mental model onto every codebase.
