The Platform Layer — What the Browser Actually Is

The browser doesn't paint a canvas. It builds in-memory trees from your HTML and CSS, merges them, and runs an algorithm — the cascade — to decide which style wins. This is the substrate every framework runs on. Anchored to HTML & CSS.

Where this fits

Lesson 1 showed why JavaScript exists. But JS doesn't paint pixels — it manipulates something. This lesson is that something: the platform layer (HTML & CSS). Together with the language and the concept of state (Lesson 3), these are the atoms the whole ecosystem is built from. See the plan for the full arc.

1. A page is a tree, not a canvas

The browser receives your HTML as text. Its first job is to parse that text into the DOM — the Document Object Model, a tree of nodes (elements, attributes, text). When you call document.querySelector('article'), you get back a node in that tree. MDN is blunt that the document is a structured text file and the browser's default look comes from stylesheets the browser ships — separate from the HTML itself.

The reframing that matters: the page is not a flat canvas you draw on. It is a living tree of nodes the browser holds in memory. That tree is the structure JavaScript sees, mutates, and re-reads. Everything else in frontend is built on top of this tree.

2. The second tree, and the algorithm that resolves it

CSS is separate from HTML. The browser parses your CSS rules into a second in-memory tree: the CSSOM (CSS Object Model). Now two trees exist — the DOM (structure) and the CSSOM (styles).

When two CSS rules target the same element, something must pick the winner. That algorithm is the cascade. It resolves, in order: origin (user-agent / user / author styles), importance (!important), specificity, source order, scope proximity, and cascade layers. It is deterministic and inspectable in DevTools — not a guess and not a mystery. "Cascading" is literally the C in CSS.

3. The merge: the render tree

The browser now merges the DOM and the CSSOM into a third structure: the render tree. Each visible node is paired with its computed style and becomes a box (content, padding, border, margin). Layout solves the boxes' geometry; paint fills the pixels; composite assembles the layers. The reference doc sums it up: three trees, one source — the HTML you write.

There is also a parallel tree worth knowing: the accessibility tree, derived from the DOM and filtered for semantics. A <button> becomes a role="button" node; a <div onclick> becomes a generic node with no role. Screen readers traverse this tree, not the DOM. Semantic HTML isn't a checklist — it's how the page becomes accessible by default.

4. Why this is the substrate

So what does JavaScript actually do? It manipulates the DOM and the CSSOM — it never paints pixels directly. You change a node or a style; the browser re-cascades, lays out, and paints for you. Every framework you'll meet — React, Angular, Vue, Astro — is a different abstraction over this same substrate. The substrate doesn't change; only the abstraction's leakiness does.

This is why a layout shift, a specificity war, or a dark-mode breakage is a platform problem, not a framework problem. You skipped the layer. Knowing the trees and the cascade is what lets you read any frontend, in any camp, without panic.

The win

  
You now hold the platform model: HTML parses to the DOM, CSS to the CSSOM, they merge into the render tree of boxes, and the cascade is the deterministic algorithm that picks the winning style. A parallel accessibility tree is what screen readers actually read. JavaScript manipulates the trees; the platform does the rendering. Every framework abstracts this exact substrate — so when a layout breaks, you now know which layer to blame.
