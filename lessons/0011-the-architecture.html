The Architecture — What Code Alone Can't Handle

1. "The real programming is in system design"

System design is the disciplined activity of structuring a software solution across trust, consistency, and scaling boundaries. It translates a validated problem ("what to build") into a structural answer ("how it fits together"). It produces decisions, not code — and those decisions determine:

  • Decomposition — what are the independently deployable, failure-isolated units? (services, functions, modules)
  • Data ownership — which unit is the source of truth for each piece of state?
  • Consistency models — what guarantees does the system make about reads and writes?
  • Failure domains — what fails independently, and how does the system degrade?
  • Capacity & scaling — where are the bottlenecks, and how do we add capacity?

And just like API design (Lesson 10), the defining trait is high reversal cost: service boundaries and data ownership are expensive to change later. Variable names and function extraction are cheap; moving a service boundary is not. That cost difference is what makes this a distinct discipline from the component loop of Lesson 7.

2. Two scales, one discipline

System design operates at two scales simultaneously — both are system design, and neither is complete alone:

  • Architectural (macro) — how many services? What communicates with what? Where does data live? How do we scale? What fails and how do we survive it? Artifacts: service topology, data-flow diagrams, capacity estimates.
  • Component (micro) — who owns this data? What is the API contract? Where is the trust boundary? What consistency model? Artifacts: OpenAPI specs, bounded context maps, data ownership matrices.

The architectural layer sets the constraints; the component layer makes them executable. Notice the connection to Lesson 10: system design decides the boundaries and data ownership; API design materializes those boundaries as callable contracts. One decides where the seams are; the other defines how they speak.

3. Monolith vs services — a trade-off, not a religion

Here is the reframe that saves you from cargo-culting. "Microservices vs monolith" is not a question with one right answer. It's a trade-off driven by team boundaries, domain complexity, and scale:

  • A URL shortener — one team, one simple domain (shorten, resolve, count clicks), 10B reads/day. A CRUD monolith with a Redis cache is the right answer. Splitting it into services would add operational complexity for no benefit.
  • A multi-team order system — place order → reserve inventory → charge payment → confirm shipping, each owned by a different team, any step can fail and must compensate. Here an event-driven saga across services is right: each team owns its service, failures are isolated, and compensation (refund, cancel reservation) is explicit.

The reference doc has both worked examples with capacity estimates and architecture diagrams. The lesson: don't pick a style because it's trending. Pick it because the problem's team boundaries, domain complexity, and scale demand it. A monolith isn't a failure; it's the right answer when the domain is simple and the team is small.

The win

  
You now hold the architecture layer: system design is structuring a solution across trust, consistency, and scaling boundaries — decomposition, data ownership, consistency, failure domains, capacity. Its defining trait (like API design) is high reversal cost: service boundaries are expensive to change. It operates at two scales — architectural (services, events, scaling) and component (bounded contexts, contracts, trust boundaries). And the big reframe: monolith vs microservices is a trade-off, not a religion — a URL shortener is a CRUD monolith; a multi-team order system is an event-driven saga. Pick the style the problem's team boundaries, domain complexity, and scale demand. System design decides where the seams are; API design (Lesson 10) defines how they speak.
