The Software Development Process — From Waterfall to Agile

You know how to build a feature (The Rhythm, L7) and how to think about problems (Problem-Solving, L12–14). But how does a team decide what to build, when to build it, and how to ship it? That's the macro-process — the SDLC and the methodologies that navigate it. Here's the 55-year history, the Agile Manifesto, and the key insight: a sprint is the project-scale process; The Rhythm is the feature-scale process within it. Anchored to Software Development Process.

Where this fits

The Bridge movement has taught you the meta-skills: problem-solving (L12–14), the rhythm deepened (L15), CS & SE (L16), solution evaluation (L17). This lesson adds the process layer — the project-scale counterpart to The Rhythm. The next lesson (L19) covers Scrum/Kanban in detail and the AI/Agent frontier.

1. The SDLC — six phases, every methodology

Every methodology — Waterfall, Agile, Spiral, DevOps — navigates the same six phases: Requirements → Design → Implementation → Testing → Deployment → Maintenance. The SDLC describes what happens; the methodology describes how you navigate those phases. Waterfall does them once, sequentially. Agile does them every sprint, iteratively. The phases don't change; the navigation does.

2. The 55-year history — why Agile replaced Waterfall

YearEventWhat it contributed
1970Waterfall (Royce)Sequential: finish all requirements, then all design, then all code. Royce actually warned against single-pass — people skipped his warning.
1986Spiral (Boehm)First formal "loop": Plan → Risk Analysis → Engineering → Evaluation, each cycle deeper. The ancestor of iterative development.
1999XP (Beck)"Make it work, make it right, make it fast." TDD, pair programming, CI. The engineering practices.
2001Agile Manifesto17 developers at Snowbird, Utah. 4 values + 12 principles. Not a framework — a philosophy. Scrum, Kanban, XP implement it.
2009DevOpsAutomated deployment via CI/CD. "Deploy 50 times a day" becomes possible.

The pattern: each methodology was a response to a failure of the previous one. Waterfall failed because requirements change. Spiral made change explicit. Agile embraced it. DevOps automated the deployment bottleneck. The recurring theme: humans are bad at predicting what software should do, so processes that embrace change beat processes that resist it.

3. The Agile Manifesto — 4 values

Value (left is valued more)Over (right still has value)
Individuals and interactionsProcesses and tools
Working softwareComprehensive documentation
Customer collaborationContract negotiation
Responding to changeFollowing a plan

The crucial nuance: the right side is not wrong — the Manifesto says "while there is value in the items on the right, we value the items on the left more." Plans matter; responding to change matters more. This is a reprioritization, not a rejection.

Principle 10 — "simplicity, the art of maximizing the amount of work not done" — is YAGNI (L16) in manifesto form. Principle 12 — "reflect and adjust" — is metacognition (L13) at the team level. The Manifesto's principles connect directly to everything you've already learned.

4. The macro/micro connection — how this relates to The Rhythm

The key structural insight: The Rhythm (L7) is the micro-process (one feature, minutes to hours). This doc is the macro-process (one project, weeks to months). A Scrum sprint contains multiple features, each built with the Model→View→Flow rhythm. Sprint planning decides what to build; The Rhythm decides how to build each one. The sprint review inspects the results (Pólya's Phase 4 at the team level). The retrospective inspects the process (metacognition at the team level).

They're the same pattern at different scales: Boehm's spiral (1986) named the iterative pattern; XP (1999) operationalized it in code; Agile (2001) institutionalized it at the sprint scale; The Rhythm (L7) applies it at the feature scale. Learn the macro once, and it explains the micro; learn the micro once, and it makes the macro concrete.
