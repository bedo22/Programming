Ignoring display artifacts and reviewing substance only.

## Overall verdict

This is a **strong orientation doc**. Its core purpose — helping a developer open an unfamiliar frontend repo and recognize which “camp” it belongs to — is well served by the current structure.

Its strongest parts:

- The camp map: CMS/classic, HTML-first/islands, SPA, meta-frameworks, signals world, WASM.
- The “centers of gravity, not exclusive clubs” framing.
- The mental models table comparing how practitioners in each camp reason.
- The transfer-trap warning for React developers entering signals frameworks.
- The migration paths table.
- The ecosystem/tooling catalog.

However, compared with the rest of the shelf, it is still **less complete as a practical field manual**. It tells the reader what camps exist, but it does not yet fully teach:

1. how to identify the camp from a real repository,
2. how to choose a camp for a new product,
3. how rendering, state, routing, and data differ across camps,
4. what the camp-specific failure modes are,
5. how camps overlap and hybridize,
6. how each camp affects SEO, accessibility, performance, security, and deployment,
7. how to read a camp-specific codebase step by step.

So: **very good conceptual survey, but not yet complete as a practical recognition-and-decision reference**.

# 1. What the document does especially well

## 1.1 The camp framing is excellent

The table at the top:

| Camp | Unit of work | Default runtime | JS load strategy |
|---|---|---|---|
| CMS/classic | Page/template | Server | Optional progressive enhancement |
| HTML-first | Document + islands | Server HTML | Ship almost no framework |
| SPA | Client app shell | Browser | Large initial JS |
| Meta-framework | Route + data + UI | Server/browser split | Framework decides |
| WASM/systems UI | Compiled module | Browser/edge | JS as glue |

is one of the best parts of the doc.

It gives the reader immediate orientation without forcing a religious framework debate.

Keep this.

---

## 1.2 The “centers of gravity” warning is important

The doc correctly says:

> These camps overlap. Treat the labels as centers of gravity, not exclusive clubs.

This is essential because real codebases are often hybrids:

- WordPress with a React admin SPA,
- Astro with React islands,
- Next.js App Router with client-heavy routes,
- Angular with signals but legacy zone.js,
- React SPA with a WASM hot path.

This framing should remain central.

---

## 1.3 The mental models table is the best section

The table comparing:

- CMS/classic,
- HTML-first/islands,
- SPA React,
- meta-framework RSC,
- signals,
- WASM,

is excellent.

It correctly identifies that the hardest part of reading another camp is not syntax, but the mental model:

- CMS: page = template + data,
- islands: static document + precision holes,
- SPA React: UI = f(state), re-render + diff,
- RSC: server functions + client React,
- signals: reactive graph, not component re-run,
- WASM: compiled module + JS glue.

This is the highest-value part of the doc.

---

## 1.4 The transfer-trap warning is very useful

The warning:

> Bringing React’s re-render model to signals frameworks causes over-subscription. Bringing signals’ dirty-flag model to React causes missing memoization.

is exactly the kind of cross-camp insight the doc should contain.

This should be expanded, not removed.

---

## 1.5 The migration paths table is strong

The migration table is one of the most practical sections:

- CMS → HTML-first islands,
- HTML-first → meta-framework,
- SPA → meta-framework,
- Angular → React/Next,
- signals library → React.

This is useful because teams rarely stay in one camp forever.

> **How to identify the camp from a repository**

### First files to check

| Check | What it tells you |

## 3.3 Add a camp selection framework

The doc says “not to pick a religion,” but teams still need to choose.

Add:

> **Choosing a camp — constraint-based selection**

| Constraint | Favored camp |
|---|---|
| Content-heavy, editorial workflow, SEO | CMS/classic or HTML-first |
| Marketing site with a few interactive widgets | HTML-first islands |
| Authenticated app behind login, high interactivity | SPA or meta-framework |
| Public + app pages in one codebase | Meta-framework |
| Server-owned data, SEO, streaming, RSC | Meta-framework, especially Next.js |
| Extremely low JS budget | HTML-first/islands |
| Existing Angular/Vue/Svelte team | Signals/world camp matching team skill |
| Heavy compute in browser | WASM hybrid inside SPA/meta-framework |
| Simple internal tool | SPA or meta-framework depending on data needs |
| Team primarily knows React | SPA or meta-framework React path |

Add:

> Do not choose a camp because it is fashionable. Choose it based on content-to-interactivity ratio, SEO needs, performance budget, team skill, data ownership, and deployment constraints.

This turns the survey into a decision tool.

## 3.4 Add rendering and hydration strategy table

The camps differ most in how HTML and JS arrive.

Add:

| Strategy | Camp association | JS shipped | Interactivity model | Main risk |
|---|---|---:|---|---|
| Server-rendered full page | CMS/classic | Minimal | Round-trip or small enhancement | Page reload friction |
| Static HTML + islands | HTML-first | Very low | Islands hydrate selectively | Island sprawl |
| CSR/SPA | SPA | High | Client owns UI after load | First paint/SEO/bundle size |
| SSR | Meta-framework | Medium | Server renders, client hydrates | Hydration cost/mismatches |

| Streaming/RSC | Meta-framework | Targeted | Server components + client islands | Boundary/cache complexity |

| WASM module | WASM hybrid | Binary module + JS glue | Compiled logic, JS DOM glue | Toolchain/memory complexity |

This is essential for understanding camp differences.

## 3.7 Add camp-specific failure modes

The doc has transfer traps, but it needs explicit failure modes per camp.

Add:

| Camp | Failure mode | What happens | Fix |
|---|---|---|---|
| CMS/classic | jQuery soup | Scattered DOM scripts, no clear state | Introduce islands or small components |
| CMS/classic | Headless without plan | CMS API exists but frontend has no rendering strategy | Choose rendering camp deliberately |
| HTML-first | Island sprawl | Too many islands recreate a poorly designed SPA | Consolidate islands, define hydration budget |
| HTML-first | HTMX complexity leak | Server-rendered fragments become stateful and hard to trace | Keep server state explicit, use progressive enhancement carefully |
| SPA | Bundle bloat | First load slow, SEO weak | Code-split, defer, or move public pages to meta-framework/islands |
| SPA | State duplication | Server data duplicated in global store | Separate server cache from UI state |
| Meta-framework | Abstraction leak | Developers do not understand server/client boundary | Teach RSC/loader boundaries, add lint/review rules |
| Meta-framework | Cache confusion | Stale or over-cached pages | Make caching explicit, document revalidation |
| Signals | React transfer trap | Developer expects component re-render semantics | Learn camp-native reactivity model |
| Signals | Effect overuse | Derived state duplicated in effects | Prefer computed/derived signals |
| WASM | Toolchain tax | Simple feature becomes build/toolchain problem | Use WASM only for hot paths, keep UI in JS |
| WASM | Memory/debugging pain | Crash or performance issue hard to trace | Keep JS/WASM boundary narrow and observable |

This would significantly improve practical completeness.

```md
- Content-heavy public site → CMS or HTML-first.
- Interactive authenticated product → SPA or meta-framework.
- Public + app in one codebase → meta-framework.
- Minimal JS budget → HTML-first/islands.
- Heavy compute in browser → WASM hybrid.
- Team skill and hiring often decide between otherwise valid options.
```

## 7.4 Signals reading snippet

```md
In signals code, do not ask “why did this component re-render?”
Ask:

- Which signal changed?
- Which computed value derived from it?
- Which effect or binding subscribed?
- Did I accidentally read a signal where I should have derived?
```

## 7.5 Hybrid snippet

```md
When a repo seems confusing, check whether it is a hybrid:

- CMS content + React admin SPA
- Astro marketing pages + Next.js app pages
- React SPA + WASM compute module
- Server-rendered pages + HTMX fragments

Identify the primary camp first, then the embedded secondary camp.
```

# 9. Bottom line

This document is already one of the most useful orientation docs in the shelf. Its camp taxonomy, mental models table, and migration paths are strong.

To become complete, it needs to move from **“what camps exist”** to **“how to recognize, choose, read, and migrate between camps in practice.”**

The highest-leverage improvements are:

> repository identification, camp selection framework, rendering/state/routing tables, camp-specific failure modes, hybrid patterns, and a worked example.

## Final recommendation

**Strong draft, publishable as an orientation map, but should be expanded before being treated as a complete practical field manual.**

The doc’s core thesis is correct:

> Camps are centers of gravity, not religions. The skill is recognizing which mental model a codebase expects.

With the additions above, it becomes a much stronger tool for reading real frontend code at work.
