## Overall verdict

This is a **strong, well-scoped doc** that fills a genuine gap on the shelf: the SQL query language itself, positioned between schema design (Data Modeling) and the request loop (Backend Engineering). The SELECT anatomy with execution order, NULL handling rules, JOIN taxonomy, window functions, UPSERT pattern, and the PostgreSQL feature showcase are all well-executed and practically useful.

However, the doc is **incomplete as a SQL reference**. It teaches reading and querying well but is thin on writing DDL, data types, constraints, views, stored procedures, transactions in depth, indexing from the SQL side, security, monitoring, and real-world query patterns. It also skips several PostgreSQL features that are commonly encountered in production code.

# 1. What the document does especially well

## 1.1 The execution order insight

The written-order-vs-execution-order distinction is the single most important SQL mental model, and the doc nails it:

```
WRITTEN: SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
EXECUTES: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

The note "Most SQL bugs are order bugs: a `WHERE` that should be a `HAVING`, an alias used where it does not exist yet" is exactly the insight that saves hours of debugging.

## 1.2 NULL handling rules

The three rules (`IS NULL`, `IS NOT NULL`, `IS DISTINCT FROM`) plus `COALESCE`, `NULLIF`, and the `COUNT(*)` vs `COUNT(col)` distinction are precisely the rules that trip up every SQL learner. Well-placed.

## 1.3 JOIN taxonomy with "when to use"

The table mapping each JOIN type to its mental model ("intersection," "every customer and their orders if any," "rarely used — flip and use LEFT") is practical and correct.

## 1.4 Window functions as "aggregation without folding"

The one-sentence distinction — "Aggregates fold rows into one result per group. Window functions compute an aggregate-style value but keep every row" — is the clearest explanation of why window functions exist.

## 1.5 UPSERT as the idempotent write

Connecting `INSERT ... ON CONFLICT` to the API Design doc's idempotency keys is excellent cross-referencing. The "get-or-create" pattern is a real-world staple.

## 1.6 The worked example with EXPLAIN

Showing the composite index turning a Seq Scan into a 0.05ms point read is concrete and convincing. The expand-contract migration example for `delivery_window` is practical.

## 1.7 The MySQL comparison table

The feature-by-feature comparison (UPSERT syntax, JSON, arrays, full-text, window functions, RLS) is exactly what a freelancer working with WordPress needs.

# 2. High-priority completeness gaps

## 2.1 Missing: Data types section

The doc never teaches PostgreSQL data types. This is a fundamental gap. A learner reading the worked example sees `bigserial`, `text`, `jsonb`, `timestamptz`, `integer` but never learns what these are or when to choose them.

Add a section:

| Type category | PostgreSQL types | When to use | Common mistakes |
|---|---|---|---|
| Integers | `smallint`, `integer`, `bigint`, `serial`, `bigserial`, `identity` | IDs, counts, quantities | Using `serial` (legacy) instead of `GENERATED ALWAYS AS IDENTITY` |
| Decimals | `numeric(p,s)`, `real`, `double precision` | Money: `numeric(19,4)`. Never `float` for money | `float` rounding errors in financial calculations |
| Text | `text`, `varchar(n)`, `char(n)` | `text` for almost everything. `varchar(n)` only when length is a business constraint | `varchar(255)` cargo-culted everywhere |
| Boolean | `boolean` | Flags, toggles | Storing booleans as `int` 0/1 |
| Date/Time | `timestamp`, `timestamptz`, `date`, `time`, `interval` | Always `timestamptz` for anything involving time zones | Using `timestamp` (no tz) for user-facing times |
| UUID | `uuid` | Distributed IDs, public-facing identifiers | Using `uuid` as primary key for hot tables (index fragmentation) |
| JSON | `json`, `jsonb` | `jsonb` almost always. `json` only if you need exact text preservation | Using `json` when `jsonb` is better |
| Arrays | `text[]`, `integer[]`, etc. | Tags, simple lists | Using arrays when a junction table is better |
| Enums | `CREATE TYPE ... AS ENUM` | Small, stable sets of values | Using enums for values that change often |
| Bytea | `bytea` | Binary data (images, files) | Storing large files in DB instead of object storage |

## 2.2 Missing: Constraints section

The doc mentions constraints in passing but never teaches them systematically.

Add:

| Constraint | Syntax | What it enforces | When to use |
|---|---|---|---|
| `NOT NULL` | `column_name type NOT NULL` | Value must exist | Almost always. NULL should be deliberate |
| `UNIQUE` | `UNIQUE (col)` or `CONSTRAINT name UNIQUE (col)` | No duplicates | Natural keys, email addresses |
| `PRIMARY KEY` | `PRIMARY KEY` or `CONSTRAINT name PRIMARY KEY (col)` | Unique + NOT NULL. Identifies the row | Always. Every table needs a PK |
| `FOREIGN KEY` | `REFERENCES table(col)` | Referential integrity | Always for relationships |
| `CHECK` | `CHECK (condition)` | Arbitrary boolean condition | Business rules: `CHECK (price >= 0)` |
| `EXCLUSION` | `EXCLUDE USING gist (...)` | No two rows can satisfy condition simultaneously | Overlapping time ranges, seat booking |

Also teach `ON DELETE` behaviors:

| Behavior | What happens when parent is deleted | When to use |
|---|---|---|
| `CASCADE` | Child rows deleted too | Strong ownership (order → order_items) |
| `SET NULL` | FK set to NULL | Optional reference (post → author, author deleted) |
| `RESTRICT` | Delete blocked if children exist | Weak reference, must handle explicitly |
| `NO ACTION` | Same as RESTRICT but checked at end of statement | Rarely different from RESTRICT |
| `SET DEFAULT` | FK set to default value | Rarely used |

## 2.3 Missing: Views and Materialized Views

Not covered at all. These are fundamental.

Add:

**Views** — a named query, computed on every access:

```sql
CREATE VIEW active_orders AS
SELECT id, customer_id, total, created_at
FROM orders
WHERE status != 'cancelled';
```

- Use for: simplifying complex queries, hiding implementation details, access control
- Cost: recomputed every time you query the view
- Cannot be indexed directly

**Materialized Views** — a named query, result stored on disk:

```sql
CREATE MATERIALIZED VIEW order_summary AS
SELECT customer_id, COUNT(*) as order_count, SUM(total) as lifetime_value
FROM orders
GROUP BY customer_id;

-- Must be refreshed manually or on schedule:
REFRESH MATERIALIZED VIEW order_summary;
REFRESH MATERIALIZED VIEW CONCURRENTLY order_summary;  -- doesn't block reads
```

- Use for: expensive aggregations queried frequently, dashboards, reports
- Cost: stale data until refreshed; refresh takes time
- Can be indexed
- Need a refresh strategy (cron, event-driven, `pg_cron`)

**Decision framework:**

| Need | Use |
|---|---|
| Simplify a complex query, always fresh | View |
| Cache an expensive aggregation, can tolerate staleness | Materialized View |
| Store base facts | Table |

## 2.4 Missing: Indexes from the SQL perspective

The doc mentions indexes in the performance section but doesn't teach `CREATE INDEX` or index selection.

Add:

```sql
-- B-Tree (default): equality, range, ORDER BY
CREATE INDEX idx_orders_customer ON orders (customer_id);

-- Composite: multi-column queries
CREATE INDEX idx_orders_customer_created ON orders (customer_id, created_at DESC);

-- Partial: hot subset only
CREATE INDEX idx_orders_active ON orders (status) WHERE status = 'active';

-- GIN: JSONB containment, full-text, arrays
CREATE INDEX idx_events_meta ON events USING GIN (meta);

-- Unique
CREATE UNIQUE INDEX idx_shipments_tracking ON shipments (tracking_number);

-- Covering (index-only scan)
CREATE INDEX idx_orders_total ON orders (customer_id) INCLUDE (total, status);

-- Expression index
CREATE INDEX idx_users_lower_email ON users (LOWER(email));
```

**When to add an index:**
- Column appears in `WHERE`, `JOIN ON`, `ORDER BY`, or `GROUP BY`
- Table has >10k rows (indexes on tiny tables are overhead)
- `EXPLAIN` shows Seq Scan on a filtered query
- Foreign keys are almost always worth indexing

**When NOT to add an index:**
- Column has very low cardinality (boolean flag on a 100M row table)
- Table is write-heavy and rarely queried on that column
- Table is tiny (<1k rows)

## 2.5 Missing: Transactions in depth

The doc covers `BEGIN/COMMIT/ROLLBACK` but skips isolation levels, locking, and savepoints.

Add:

**Isolation levels:**

| Level | What it prevents | What it allows | PostgreSQL default |
|---|---|---|---|
| `READ COMMITTED` | Dirty reads | Non-repeatable reads, phantom reads | ✅ Yes |
| `REPEATABLE READ` | Dirty reads, non-repeatable reads | Phantom reads | |
| `SERIALIZABLE` | Dirty reads, non-repeatable reads, phantom reads | Serialization errors (must retry) | |

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- your transaction
COMMIT;
```

**Row locking:**

```sql
-- Lock specific rows for update (prevents other transactions from modifying them)
SELECT * FROM orders WHERE id = 42 FOR UPDATE;

-- Lock but don't wait if already locked
SELECT * FROM orders WHERE id = 42 FOR UPDATE NOWAIT;

-- Lock but skip locked rows (useful for job queues)
SELECT * FROM jobs WHERE status = 'pending' FOR UPDATE SKIP LOCKED LIMIT 1;
```

**Savepoints:**

```sql
BEGIN;
INSERT INTO orders (customer_id, total) VALUES (1, 100);
SAVEPOINT after_order;
INSERT INTO order_items (order_id, product_id, qty) VALUES (1, 5, 2);
-- if this fails:
ROLLBACK TO SAVEPOINT after_order;
-- order still exists, item insert rolled back
COMMIT;
```

**Advisory locks (application-level locking):**

```sql
-- Session-level lock (released when connection closes)
SELECT pg_advisory_lock(12345);
-- do work
SELECT pg_advisory_unlock(12345);

-- Transaction-level lock (released on COMMIT/ROLLBACK)
SELECT pg_advisory_xact_lock(12345);
```

## 2.6 Missing: Prepared statements / Parameterized queries

Mentioned in failure modes but never taught. This is critical for security and performance.

Add:

```sql
-- BAD: SQL injection vulnerability
SELECT * FROM users WHERE email = 'user@example.com' OR 1=1; --'; DROP TABLE users; --

-- GOOD: Parameterized query (in application code)
-- Node.js with node-postgres:
const result = await client.query(
  'SELECT * FROM users WHERE email = $1',
  ['user@example.com']
);

-- PostgreSQL prepared statements (server-side):
PREPARE get_user (text) AS SELECT * FROM users WHERE email = $1;
EXECUTE get_user('user@example.com');
DEALLOCATE get_user;
```

**Why parameterized queries matter:**
- Prevent SQL injection (security)
- Allow query plan caching (performance)
- Handle type casting correctly (correctness)

## 2.7 Missing: Recursive CTEs with examples

Mentioned in the CTE section but no example. This is needed for hierarchical data.

Add:

```sql
-- Organization hierarchy: find all reports under a manager
WITH RECURSIVE reports AS (
  -- Base case: the manager
  SELECT id, name, manager_id, 0 AS depth
  FROM employees
  WHERE id = 1

  UNION ALL

  -- Recursive case: direct reports of current level
  SELECT e.id, e.name, e.manager_id, r.depth + 1
  FROM employees e
  JOIN reports r ON e.manager_id = r.id
)
SELECT * FROM reports ORDER BY depth, name;
```

**Common uses:**
- Org charts / tree structures
- Bill of materials
- Comment threads
- Category hierarchies
- Graph traversal (shortest path with weights)

## 2.8 Missing: Real-world query patterns

Add a "Query Recipes" section:

**Keyset pagination (the OFFSET killer, already mentioned but expand):**

```sql
-- Page 1
SELECT * FROM events ORDER BY created_at DESC, id DESC LIMIT 20;

-- Page 2 (using last row's values from page 1)
SELECT * FROM events
WHERE (created_at, id) < ('2026-01-15 10:30:00', 98765)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

**Soft delete pattern:**

```sql
-- Add deleted_at column
ALTER TABLE orders ADD COLUMN deleted_at timestamptz;

-- "Delete" = set timestamp
UPDATE orders SET deleted_at = now() WHERE id = 42;

-- Query only "live" rows
SELECT * FROM orders WHERE deleted_at IS NULL;

-- Partial index for live rows only
CREATE INDEX idx_orders_live ON orders (customer_id) WHERE deleted_at IS NULL;
```

**Queue table (job queue):**

```sql
CREATE TABLE job_queue (
  id bigserial PRIMARY KEY,
  type text NOT NULL,
  payload jsonb NOT NULL,
  status text NOT NULL DEFAULT 'pending',
  attempts integer NOT NULL DEFAULT 0,
  max_attempts integer NOT NULL DEFAULT 3,
  locked_at timestamptz,
  locked_by text,
  created_at timestamptz NOT NULL DEFAULT now(),
  completed_at timestamptz
);

-- Worker picks up a job (SKIP LOCKED prevents contention)
UPDATE job_queue
SET status = 'processing', locked_at = now(), locked_by = 'worker-1'
WHERE id = (
  SELECT id FROM job_queue
  WHERE status = 'pending' AND attempts < max_attempts
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;
```

**Temporal / audit trail:**

```sql
CREATE TABLE price_history (
  id bigserial PRIMARY KEY,
  product_id bigint NOT NULL REFERENCES products(id),
  price numeric(19,4) NOT NULL,
  valid_from timestamptz NOT NULL DEFAULT now(),
  valid_to timestamptz NOT NULL DEFAULT 'infinity',
  EXCLUDE USING gist (
    product_id WITH =,
    tstzrange(valid_from, valid_to) WITH &&
  )
);

-- Current price for a product
SELECT price FROM price_history
WHERE product_id = 42 AND valid_from <= now() AND valid_to > now();
```

## 2.9 Missing: PostgreSQL monitoring and diagnostics

Add:

```sql
-- What's running right now?
SELECT pid, now() - pg_stat_activity.query_start AS duration,
       query, state, wait_event_type, wait_event
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC;

-- Kill a stuck query
SELECT pg_cancel_backend(pid);   -- graceful
SELECT pg_terminate_backend(pid); -- forceful

-- Top 10 slowest queries (requires pg_stat_statements extension)
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Table bloat / dead tuples
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup::numeric / GREATEST(n_live_tup, 1) * 100, 2) AS dead_pct,
       last_vacuum, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- Index usage
SELECT indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;  -- low scan count = candidate for removal

-- Lock contention
SELECT blocked_locks.pid AS blocked_pid,
       blocking_locks.pid AS blocking_pid,
       blocked_activity.query AS blocked_query,
       blocking_activity.query AS blocking_query
FROM pg_locks blocked_locks
JOIN pg_locks blocking_locks ON blocked_locks.locktype = blocking_locks.locktype
  AND blocked_locks.relation = blocking_locks.relation
  AND blocked_locks.pid != blocking_locks.pid
JOIN pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

## 3.2 Expand the JOIN section

Add `LATERAL` joins:

```sql
-- For each customer, get their 3 most recent orders
SELECT c.id, c.name, recent_orders.*
FROM customers c
CROSS JOIN LATERAL (
  SELECT id, total, created_at
  FROM orders o
  WHERE o.customer_id = c.id
  ORDER BY created_at DESC
  LIMIT 3
) recent_orders;
```

Add `NATURAL JOIN` warning:

```sql
-- AVOID: NATURAL JOIN matches on ALL same-named columns. Fragile.
SELECT * FROM orders NATURAL JOIN customers;  -- DON'T
SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id;  -- DO
```

## 3.3 Expand the subquery section

Add EXISTS vs IN vs JOIN decision framework:

| Pattern | Use when | Performance |
|---|---|---|
| `EXISTS (SELECT 1 ...)` | "Does a related row exist?" Short-circuits on first match | Usually fastest for existence checks |
| `IN (SELECT ...)` | "Is this value in a small set?" | Materializes the subquery result |
| `JOIN` | "I need columns from both sides" | Best when you need data from both tables |
| `NOT IN (SELECT ...)` | "Not in set" — careful with NULLs! | If subquery returns NULL, NOT IN returns no rows |
| `NOT EXISTS (SELECT 1 ...)` | "No related row exists" — NULL-safe | Preferred over NOT IN |

## 3.4 Expand the window functions section

Add frame clauses:

```sql
-- Running total over entire partition (default)
SUM(amount) OVER (ORDER BY date)

-- Moving average over last 3 rows
AVG(amount) OVER (ORDER BY date ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)

-- Rank within a sliding window
SUM(amount) OVER (ORDER BY date RANGE BETWEEN interval '7 days' PRECEDING AND CURRENT ROW)
```

Add `NTH_VALUE`, `PERCENT_RANK`, `CUME_DIST`:

```sql
SELECT
  name, salary,
  NTH_VALUE(name, 2) OVER (ORDER BY salary DESC) AS second_highest_earner,
  PERCENT_RANK() OVER (ORDER BY salary) AS salary_percentile,
  CUME_DIST() OVER (ORDER BY salary) AS cumulative_distribution
FROM employees;
```

## 3.5 Expand the transactions section

Add deadlock example and prevention:

```sql
-- Deadlock scenario:
-- Transaction A: UPDATE accounts SET balance = balance - 100 WHERE id = 1;
--                UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- Transaction B: UPDATE accounts SET balance = balance - 50 WHERE id = 2;
--                UPDATE accounts SET balance = balance + 50 WHERE id = 1;
-- If A locks id=1 and B locks id=2, both wait forever.

-- Prevention: always lock rows in the same order (e.g., by id)
UPDATE accounts SET balance = balance - 100 WHERE id = LEAST(1, 2);
UPDATE accounts SET balance = balance + 100 WHERE id = GREATEST(1, 2);
```

## 3.9 Add a "SQL anti-patterns" section beyond failure modes

| Anti-pattern | What it looks like | Fix |
|---|---|---|
| `SELECT *` in production | Fetches all columns, breaks covering indexes | Name columns explicitly |
| `NOT IN` with nullable subquery | Returns empty result if subquery has NULL | Use `NOT EXISTS` instead |
| `LIKE '%term%'` on large table | Full table scan, can't use B-Tree index | Use `pg_trgm` GIN index or full-text search |
| `OFFSET` for deep pagination | Scans and discards rows | Use keyset/cursor pagination |
| `float` for money | Rounding errors | Use `numeric(19,4)` |
| `varchar(255)` everywhere | Cargo-culted, no business meaning | Use `text` unless length is a constraint |
| Storing comma-separated lists | `tags = 'a,b,c'` in a text column | Use array column or junction table |
| UUID as PK for hot tables | Index fragmentation on random inserts | Use `bigserial` or UUIDv7 for hot paths |
| `DELETE` without `WHERE` | Wipes entire table | Always include `WHERE`. Use transactions |
| `UPDATE` without `WHERE` | Updates every row | Always include `WHERE`. Use transactions |
| N+1 queries in ORM | 1 query for list + N queries for details | Eager load / JOIN / batch |
| Implicit type cast in WHERE | `WHERE text_col = 123` skips index | Cast the parameter, not the column |

# 5. Structural improvements

## 5.1 Add a "DDL: Creating and altering tables" section

The doc teaches querying but not schema creation. Even though Data Modeling owns schema design, the SQL syntax for DDL belongs here:

```sql
CREATE TABLE shipments (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tracking_number text NOT NULL UNIQUE,
  customer_id bigint NOT NULL REFERENCES customers(id),
  status text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'in_transit', 'delivered', 'exception')),
  weight_kg numeric(10,2),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

-- Add a column (non-breaking, additive)
ALTER TABLE shipments ADD COLUMN delivery_window jsonb;

-- Add a constraint
ALTER TABLE shipments ADD CONSTRAINT chk_weight CHECK (weight_kg > 0);

-- Create an index
CREATE INDEX idx_shipments_customer ON shipments (customer_id);

-- Rename a column (breaking change — expand-contract)
ALTER TABLE shipments RENAME COLUMN status TO shipment_status;

-- Drop a column (breaking change — contract phase only)
ALTER TABLE shipments DROP COLUMN legacy_field;
```

# 6. Worked example improvements

The existing worked example is good. Add these queries:

**Window function: running total per customer:**

```sql
SELECT
  s.customer_id,
  s.tracking_number,
  s.created_at,
  SUM(s.total) OVER (
    PARTITION BY s.customer_id
    ORDER BY s.created_at
  ) AS running_total
FROM shipments s
WHERE s.created_at >= now() - interval '30 days'
ORDER BY s.customer_id, s.created_at;
```

**Recursive CTE: shipment event timeline as a tree:**

```sql
WITH RECURSIVE timeline AS (
  SELECT id, shipment_id, type, happened_at, payload,
         1 AS depth
  FROM shipment_events
  WHERE shipment_id = $1 AND type = 'CREATED'

  UNION ALL

  SELECT e.id, e.shipment_id, e.type, e.happened_at, e.payload,
         t.depth + 1
  FROM shipment_events e
  JOIN timeline t ON e.shipment_id = t.shipment_id
    AND e.happened_at > t.happened_at
    AND e.id != t.id
  WHERE t.depth < 20
)
SELECT * FROM timeline ORDER BY happened_at;
```

**EXISTS vs JOIN for "customers with at least one shipment":**

```sql
-- EXISTS: stops at first match, usually faster
SELECT c.id, c.name
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM shipments s WHERE s.customer_id = c.id
);

-- JOIN: returns duplicates if customer has multiple shipments
SELECT DISTINCT c.id, c.name
FROM customers c
JOIN shipments s ON s.customer_id = c.id;
```

# 8. Bottom line

This doc is a **strong foundation** for the SQL query language. The SELECT anatomy, execution order, NULL rules, JOIN taxonomy, window functions, and UPSERT pattern are all well-taught. The PostgreSQL feature showcase and MySQL comparison are practical. The worked example is concrete.

The main gaps are on the **writing side** (DDL, constraints, data types), the **operational side** (transactions in depth, monitoring, backup, configuration), and the **pattern side** (real-world query recipes, anti-patterns, indexes from the SQL perspective).

The doc teaches you to **read and query** a database well. It needs expansion to teach you to **write, maintain, and operate** one.

## Final recommendation

**Strong draft, publishable as a query-language reference. Needs expansion for a complete SQL + PostgreSQL reference.**

The highest-leverage additions are:

> Data types, constraints, views/materialized views, indexes from SQL side, transactions in depth, parameterized queries, recursive CTE examples, and real-world query patterns.
