## Quick review

**The Rhythm document is conceptually strong, but it currently overlaps too much with the Software Development Process doc, and it also touches several topics that may belong in the upcoming Problem-Solving doc.**

Its best content is the **feature-scale frontend loop**:

- Model → View → Flow
- Skeleton → Deepen → Polish
- sketching the data shape
- “feel the friction”
- derived state
- thinnest end-to-end slice
- frontend-specific failure modes
- React/Server Components/AI impact

That is the part this document should own.

The weaker part is that it spends a lot of space on:

- Waterfall
- Spiral
- IID
- Agile
- XP
- Lean
- SDLC vs methodology vs workflow
- Pólya/metacognition/wicked problems
- general history of iterative development

Those are useful, but many of them are already covered or should be covered by other docs.

# 3. Completeness gaps in The Rhythm doc

These are the main things I would add to make it more complete as a frontend implementation doc.

---

## 3.1 Add a clearer scope statement

The doc should explicitly say what it assumes.

### Suggested addition

> This doc assumes the problem has already been discovered, the solution approach is roughly known, and the team process provides the work item. It does not cover problem discovery, project management, or system-scale architecture except where they directly affect building one frontend feature.

This prevents overlap with:

- Design Thinking
- Software Development Process
- System Design
- Problem-Solving

---

## 3.2 Expand Round 0 into a proper inputs checklist

The current Round 0 questions are good but too thin.

Add:

### Round 0 checklist

- What is the user trying to do?
- What is explicitly out of scope?
- What are the main UI states?
- What data comes from the server?
- What data is client-only?
- What is the API contract?
- What errors can happen?
- What breakpoints/devices matter?
- What accessibility requirements matter?
- What does “done” mean for this feature?

This makes the doc much more practical.

---

## 3.3 Add a frontend state taxonomy

This is one of the biggest missing pieces.

Frontend state is not just “state.” It has different kinds:

| State type | Examples | Where it usually lives |
|---|---|---|
| UI state | modal open, hover, draft input | Component state |
| Server data | products, user profile, orders | Query/cache layer or server component |
| Client cache | normalized server data | Store/query cache |
| Form state | fields, errors, dirty state | Form component or form library |
| URL state | route, filters, page number | Router/search params |
| Local persistence | theme, sidebar preference | localStorage/sessionStorage |
| Derived state | filtered list, active count | Computed at render |

This would greatly improve the Model thread.

---

## 3.4 Add an async UI states matrix

The search box example mentions:

```ts
status: "idle" | "loading" | "done" | "error"
```

But this should become a general principle.

Add a table:

| State | Meaning | UI needed |
|---|---|---|
| Idle | Nothing happened yet | Initial UI |
| Loading | Request in flight | Spinner/skeleton |
| Success | Data arrived | Main UI |
| Empty | Success but no data | Empty state |
| Error | Request failed | Error state/retry |
| Stale | Old data visible while refreshing | Subtle loading indicator |
| Partial | Some data loaded | Progressive UI |
| Optimistic | UI assumes success before server confirms | Undo/rollback handling |

This is a major completeness improvement.

---

## 3.5 Add guidance on server state vs client state

The doc talks about Model, but it should distinguish:

- data owned by the server
- data cached on the client
- data owned by the UI
- data derived from other state

This is especially important with:

- React Query/SWR
- Redux/Zustand
- React Server Components
- Next.js

### Suggested principle

> Do not treat server data as ordinary client state. Server data has fetching, caching, invalidation, staleness, and synchronization concerns. UI state does not.

---

## 3.6 Add component state ownership guidance

The todo example sketches where state lives, which is excellent. Make that a formal step.

Add a small table:

| Question | Why it matters |
|---|---|
| Which component owns the source of truth? | Prevents duplicate state |
| Which components receive it as props? | Clarifies data flow |
| Which components only send events upward? | Keeps child components simple |
| Is any state global? | Avoids premature global stores |
| Is any state URL-based? | Makes feature shareable/bookmarkable |
| Is any state derived? | Prevents synchronization bugs |

This would strengthen the Model → View connection.

---

## 3.7 Add form-specific guidance

The current examples are:

- todo list
- cart
- search box

But forms are one of the most common frontend features.

Add a short form example or checklist:

### Form state checklist

- field values
- validation errors
- touched/dirty state
- submitting state
- submit success
- submit error
- disabled state
- optimistic submission?
- server validation errors
- confirmation/cancel behavior

This would make the doc much more complete.

---

## 3.8 Make accessibility a required part of Round 2/3

Accessibility is currently mentioned briefly. It should be explicit.

### Round 2 accessibility checklist

- semantic HTML first
- labels for inputs
- keyboard access
- visible focus
- correct heading order
- alt text where needed
- aria only when HTML is insufficient
- sufficient contrast
- motion reduced where appropriate

This prevents accessibility being treated as optional polish.

---

## 3.9 Make responsive design part of the View thread

The doc says “responsive” in Round 2 but does not develop it.

Add:

### Responsive checklist

- mobile first?
- breakpoints
- touch targets
- overflow behavior
- text wrapping
- image sizing
- navigation collapse
- container width behavior

This is important for real frontend features.

---

## 3.10 Add performance guidance, but keep it tied to judgment

The doc already warns against premature optimization. Good.

Add a small performance checklist for Round 3:

| Performance issue | Signal | Possible response |
|---|---|---|
| Slow list rendering | large list, jank | virtualize/window |
| Expensive computation | slow interaction | memoize or move off main thread |
| Too many re-renders | profiler shows waste | component split/memoization |
| Large initial load | slow first render | lazy load/code split |
| Image-heavy page | slow paint | optimize/lazy load images |
| Network waterfall | sequential requests | parallelize/prefetch |

This keeps performance practical without turning into a performance doc.

---

## 3.11 Add a frontend Definition of Done

This would improve completeness and connect well with the process doc without duplicating it.

### Suggested frontend Definition of Done

A feature is done when:

- happy path works
- loading state handled
- error state handled
- empty state handled
- disabled/duplicate submission handled
- keyboard access works
- target breakpoints work
- no obvious console errors
- derived state is not duplicated
- API contract assumptions are verified
- accessibility basics pass
- tests/checks required by the team pass

This is feature-scale, not process-scale.

# 4. Content improvements inside the existing structure

## 4.1 Clarify “Model”

“Model” can confuse readers because of MVC/backend associations.

Add:

> Here, Model means the frontend’s working data shape: the state, props, and data structures the UI uses while running. It is not necessarily the backend domain model.

---

## 4.2 Soften “Derived state is never stored”

This is mostly right, but “never” is too absolute.

Better:

> Derived state should not be stored as a separate source of truth. If performance requires caching, use memoization or an explicit cache, not a second state variable.

That is more precise.

---

## 4.3 Add race conditions and async ordering

Frontend features often fail because of async timing.

Add to Round 3:

- what happens if requests finish out of order?
- what happens if the user navigates away?
- what happens if the component unmounts?
- what happens if the user clicks twice?
- what happens if the server response differs from the optimistic update?

This is a real-world completeness gap.

---

## 4.4 Add “states before pixels”

This could become a memorable principle:

> Before styling the happy path, list the states the feature can be in.

This would complement “sketch the data shape first.”

---

## 4.5 Add a component API step

Before implementation, sketch the component contract:

```tsx
<ProductCard
  product={product}
  onAdd={handleAdd}
/>
```

Questions:

- what props does it receive?
- what events does it emit?
- is it controlled or uncontrolled?
- does it fetch its own data?
- is it reusable or screen-specific?
- does it have children/slots?

This would strengthen the View thread.

# 5. Failure modes to add

The current failure modes are good. I would add these frontend-specific ones:

| Failure mode | What happens | Fix |
|---|---|---|
| Missing async states | Feature only handles success | List idle/loading/success/error/empty states first |
| Server data treated as local state | Stale data, sync bugs | Use query/cache semantics or server state boundaries |
| Premature global store | Everything goes into Redux/Zustand too early | Keep local until sharing pain is real |
| Prop drilling ignored | Props pass through many layers | Reconsider state ownership or component composition |
| Desktop-only thinking | Mobile breaks late | Check breakpoints early |
| Accessibility as afterthought | Keyboard/focus fail at the end | Use semantic HTML and keyboard checks in Round 2 |
| Happy-path styling first | Beautiful UI with no error/empty states | Style states, not just screens |
| Ignoring API contract pain | Loading/error code becomes messy | Coordinate with API Design, handle errors explicitly |
| Overusing memoization | Code becomes complex prematurely | Measure first |
| AI skeleton accepted blindly | Wrong data shape/state boundaries | Human must validate against sketch |
