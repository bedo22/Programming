## Overall verdict

This is a **solid, well-structured doc** that covers the open source ecosystem comprehensively. The license taxonomy, governance models, contributor journey, and business models sections are well-executed. The "review attention as currency" mental model is particularly sharp.

However, the doc has significant gaps in the **practical "how" layer**. It tells you what open source is and what the journey looks like, but doesn't teach the skills you need to actually walk the journey: finding a project, reading an unfamiliar codebase, setting up a dev environment, writing a good issue, understanding license compatibility, or evaluating project health. These are the skills that separate "I want to contribute" from "I made my first PR."

# 1. What the document does well

## 1.1 The definition section is precise

The four-way distinction (open source, free software, no license, public domain) is exactly right. The "no license = all rights reserved" trap is the most common misunderstanding and the doc calls it out directly. The "free of charge ≠ free software" distinction is also correct and important.

## 1.2 The constraint inversion pattern is consistent

The five inversions (trade secret → open source, single maintainer → community, code → community, voluntary → funded, human-written → AI-assisted) follow the same pattern as every other doc on the shelf. This consistency is a strength.

## 1.3 The license taxonomy is well-structured

The two families (permissive, copyleft) with four subtypes (permissive, strong copyleft, weak copyleft, network copyleft) are correctly organized. The "what it means for you as a contributor" and "what it means for you as a consumer" columns are practical. The AGPL "SAAS loophole" explanation is correct and important.

## 1.4 The "review attention as currency" mental model is sharp

This is the best mental model in the doc. It explains why:
- Small PRs get reviewed faster than large ones
- Well-written PR descriptions get reviewed faster than vague ones
- Contributors who help review others' PRs get their own reviewed faster
- Maintainers who don't review eventually lose contributors

This is the economic model of open source, and the doc names it correctly.

## 1.5 The business models section is practical

The five models (open core, hosted/SaaS, support, sponsorship, dual licensing) with "how it works" explanations are correct. The "the code is free; the work around it is not" framing is the right insight.

### Finding your first project

| Signal | What it tells you | Where to look |
|---|---|---|
| `good first issue` label | Maintainer explicitly welcomes newcomers | GitHub issue search: `label:"good first issue"` |

### Red flags to avoid

| Red flag | Why it matters |
|---|---|

The key insight: **your first PR should be small, well-defined, and explicitly welcomed.** A `good first issue` with clear reproduction steps is better than a vague feature request.

## 2.2 Missing: Reading an unfamiliar open source codebase

The doc says "Read the conventions before writing code" but doesn't teach HOW to read an unfamiliar codebase. This is a skill in itself.

Add a section:

### Reading an open source codebase (the 30-minute method)

| Step | Time | What to look at | What you learn |
|---|---|---|---|
| 1. Read the README | 5 min | What does it do? Who uses it? What problem does it solve? | The project's purpose and audience |
| 2. Read CONTRIBUTING.md | 5 min | How to set up, run tests, submit PRs, code style | The contribution workflow and norms |
| 3. Read the directory structure | 5 min | What are the top-level directories? What does each contain? | The architecture at a glance |
| 4. Read the entry point | 5 min | `main`, `index`, `app` — where does execution start? | The control flow entry point |
| 5. Find the issue you want to fix | 5 min | Read the issue, the linked code, the test that fails | The specific code you'll touch |

### The "follow the data" technique

Once you've found the issue, trace the data flow:

1. **Where does the input enter?** (API endpoint, CLI flag, config file)
2. **Where does it get transformed?** (functions, classes, middleware)
3. **Where does the output go?** (response, file, database)
4. **Where is the bug?** (the step where the data goes wrong)

This is the same "trace the data" technique from [Backend Engineering](./backend-engineering.html) and [Testing & Debugging](./software-testing-and-debugging.html). The difference is that you're reading someone else's code for the first time.

### What to skip on first read

| Skip | Why |
|---|---|
| Generated code (build artifacts, compiled output) | It's not the source of truth |
| Test fixtures (unless they're the bug) | They're test data, not production logic |
| Vendor/dependency code | It's someone else's problem |
| Config files (unless they're the bug) | They're environment-specific |
| Documentation (unless it's wrong) | Read the code, not the docs, when they disagree |

## 2.3 Missing: Setting up a dev environment

Contributing to open source requires setting up someone else's project locally. This is often the hardest part for newcomers.

Add a section:

### Setting up an open source project locally

| Step | What to do | Common pitfalls |
|---|---|---|
| 1. Fork the repo | Click "Fork" on GitHub | Don't clone the original; fork first |
| 2. Clone your fork | `git clone https://github.com/YOUR-USERNAME/project` | Don't clone the original repo |
| 3. Add upstream remote | `git remote add upstream https://github.com/ORIGINAL/project` | You need this to sync with the original |
| 4. Install dependencies | `npm install` / `pip install -e .` / `cargo build` | Read CONTRIBUTING.md for the exact command |
| 5. Run the tests | `npm test` / `pytest` / `cargo test` | If tests fail before your change, report it as an issue first |
| 6. Run the linter | `npm run lint` / `ruff check .` / `cargo clippy` | Fix lint errors before your change, not after |
| 7. Create a branch | `git checkout -b fix/issue-123` | Don't work on `main`; create a feature branch |

### The "it works on my machine" problem

Open source projects run on many environments. If the tests pass on your machine but fail in CI:

1. Check the CI logs for the specific failure
2. Check if it's an environment issue (OS, Node version, dependency version)
3. Check if it's a timing issue (flaky test)
4. If you can't reproduce it locally, say so in the PR

## 2.4 Missing: Writing a good issue

The contributor journey mentions claiming an issue but doesn't teach how to write a good bug report or feature request.

Add a section:

### Writing a good bug report

| Section | What to include | Why it matters |
|---|---|---|
| Title | One sentence: what's broken and where | Maintainer triages by title |
| Description | What you expected vs what happened | Maintainer needs the gap |
| Reproduction steps | Exact steps to trigger the bug | Maintainer needs to reproduce it |
| Environment | OS, version, browser, dependency versions | Many bugs are environment-specific |
| Error message | The exact error, including stack trace | Maintainer needs the specific failure |
| Screenshots/logs | If applicable | Visual evidence speeds diagnosis |
| Minimal reproduction | The smallest code that triggers the bug | Maintainer can debug without your full setup |

### The minimal reproduction principle

The single most valuable thing you can include in a bug report is a **minimal reproduction**: the smallest piece of code that triggers the bug. This lets the maintainer debug without setting up your entire environment.

| Bad | Good |
|---|---|
| "The app crashes when I click the button" | "Here's a 10-line code snippet that crashes when `handleClick` is called with a null argument" |
| "The API returns 500" | "Here's the exact request body that triggers the 500, and the stack trace from the server logs" |

### Writing a good feature request

| Section | What to include | Why it matters |
|---|---|---|
| Problem statement | What problem does this solve? | Maintainer needs the "why" |
| Current workaround | How do people solve this today? | Shows the pain is real |
| Proposed solution | What should the API/behavior look like? | Gives the maintainer a starting point |
| Alternatives considered | What other approaches did you consider? | Shows you've thought about trade-offs |
| Breaking changes | Does this break existing behavior? | Maintainer needs to assess impact |

## 2.5 Missing: License compatibility

When can you combine code from different licenses? This is a common question the doc doesn't answer.

Add a section:

### License compatibility matrix

| You're using… | You can combine with… | You cannot combine with… |
|---|---|---|
| MIT | MIT, BSD, Apache, GPL, AGPL | Nothing (MIT is compatible with everything) |
| Apache 2.0 | MIT, BSD, Apache, GPL 3.0+ | GPL 2.0 (patent clause conflict) |
| GPL 3.0 | MIT, BSD, Apache, GPL 3.0, AGPL | GPL 2.0-only (incompatible) |
| AGPL | MIT, BSD, Apache, GPL 3.0, AGPL | Anything you don't want to open-source |
| Proprietary | MIT, BSD, Apache | GPL, AGPL (copyleft would infect your code) |

### The copyleft infection rule

The key rule: **if you combine GPL code with your code, the combined work must be GPL.** This is the "copyleft infection" that makes GPL incompatible with proprietary software.

| Scenario | Result |
|---|---|
| You use an MIT library in your proprietary app | Fine. MIT is permissive. |
| You use a GPL library in your proprietary app | Your app must become GPL. This is usually unacceptable. |
| You use an AGPL library in your SaaS | Your SaaS must offer source to users. This is usually unacceptable. |
| You use an LGPL library in your proprietary app | Fine. LGPL allows linking without infection. |

### The practical rule

**Read the license before you depend on it.** If you're building proprietary software, avoid GPL and AGPL dependencies. If you're building open source, MIT and Apache are the safest choices for maximum compatibility.

## 2.6 Missing: Evaluating project health

How do you know if a project is worth contributing to? How do you know if it will still be alive in a year?

Add a section:

### Project health signals

| Signal | Healthy | Unhealthy | What it tells you |
|---|---|---|---|
| Commit frequency | Weekly+ | Monthly or less | Is the project actively developed? |
| Issue response time | < 1 week | > 1 month | Is the maintainer responsive? |
| PR merge rate | > 50% | < 20% | Are contributions actually landing? |
| Contributor count | > 5 | 1-2 | Is there a bus factor risk? |
| Release frequency | Regular | Irregular or none | Is the project shipping? |
| CI status | Green | Red or none | Are quality gates enforced? |
| Dependency freshness | Up to date | Years out of date | Is the project maintaining dependencies? |
| Documentation | Clear and current | Missing or stale | Does the project care about onboarding? |

### The bus factor

The **bus factor** is the number of contributors who would need to be hit by a bus before the project becomes unmaintainable. A bus factor of 1 means a single maintainer holds all the knowledge. If they leave, the project dies.

| Bus factor | Risk | What to do |
|---|---|---|
| 1 | Critical: one person holds all knowledge | Contribute to build redundancy, or avoid the project |
| 2-3 | Moderate: a few people hold knowledge | Contribute to build redundancy |
| 4+ | Low: knowledge is distributed | Safe to depend on |

## 2.7 Missing: Legal risks

What happens if you accidentally include proprietary code in an open source contribution? What about patents? Trademarks?

Add a section:

### Legal risks in open source contributions

| Risk | What it means | How to avoid it |
|---|---|---|
| Proprietary code in your PR | You copied code from a proprietary source | Only contribute code you wrote or have rights to |
| Patent infringement | Your code implements a patented technique | Check for known patents; avoid novel techniques without legal review |
| Trademark issues | You use a project's name/logo without permission | Follow the project's trademark policy |
| CLA vs DCO | The project requires you to sign a contributor agreement | Read the CLA/DCO before contributing |
| License violation | You combine incompatible licenses | Check the compatibility matrix above |

### The "I wrote it at work" problem

If you wrote the code as part of your job, your employer may own the copyright. Check your employment contract before contributing code you wrote at work.

| Scenario | Who owns the code? | Can you contribute it? |
|---|---|---|
| You wrote it on personal time, personal equipment | You | Yes |
| You wrote it at work, on work equipment | Your employer | Check your contract; usually no |
| You wrote it at work, but it's unrelated to your job | Depends on contract | Check your contract; varies by jurisdiction |

## 2.8 Missing: Open source security (supply chain)

The [Security & Threat Modeling](./security-and-threat-modeling.html) doc covers supply chain security, but open-source-specific security deserves mention here.

Add a section:

### Open source supply chain risks

| Risk | What it means | Example |
|---|---|---|
| Dependency confusion | Attacker publishes a package with the same name as your internal package | `lodash` vs `lodash-internal` |
| Typosquatting | Attacker publishes a package with a misspelled name | `lodash` vs `l0dash` |
| Malicious maintainer | A maintainer account is compromised | The `event-stream` incident (2018) |
| Vulnerable dependency | A dependency has a known vulnerability | Log4Shell (2021) |
| Abandoned dependency | A dependency is no longer maintained | You inherit the maintenance burden |

### The dependency audit habit

Before adding a new dependency:

1. Check the maintainer (who are they? how active?)
2. Check the download count (is it widely used?)
3. Check the issue tracker (are issues responded to?)
4. Check the license (is it compatible with your project?)
5. Check for known vulnerabilities (`npm audit`, `pip audit`, `cargo audit`)

# 7. Bottom line

This doc is **strong on theory and weak on practice**. It tells you what open source is, how it works, and what the journey looks like. But it doesn't teach you the skills you need to actually walk the journey: finding a project, reading a codebase, setting up a dev environment, writing a good issue, understanding license compatibility, or evaluating project health.

The fix is to add a **practical skills layer** that collects all the "how to" skills in one place. This would make the doc not just a reference but a **field manual** — something you can use the day you decide to make your first PR.

The highest-leverage improvements are:

> Finding a project, reading a codebase, setting up a dev environment, writing a good issue, license compatibility, project health, legal risks, and supply chain security.
