# 1. What the doc does especially well

## 1.1 The "substrate" positioning is correct and necessary

No other doc on the shelf teaches the terminal or what a container is. The curriculum assumes you can run commands, read a log, and picture a deployment target — and never once shows you how. This doc closes that gap. The positioning paragraph is honest about what it is and isn't:

> "Web engineers do not administrate this layer; they operate it — enough to unblock themselves, run their code, and understand the deployment targets their systems design chooses."

That sentence alone justifies the doc's existence. Keep it.

## 1.2 The "safely ignore" table is a structural innovation

Most "intro to DevOps" content tries to teach everything. This doc explicitly says what you don't need:

> "If the task is keeping infrastructure alive as a job, it belongs to SREs and Platform Engineers — and the cloud does most of it for you anyway."

This is the correct boundary for a web engineering curriculum. The "safely ignore" column in the Definition table is as important as the "what this doc is" column. It prevents the doc from becoming a sysadmin course.

## 1.3 The Docker mental model is the single most important concept

The image-vs-container distinction is the one thing that, once understood, makes everything else about Docker click:

> "An image is the blueprint (a recipe: base OS + runtime + your code + config), built once and versioned; a container is a running process created from that image, started as many times as you like."

And the "container is not a VM" explanation is correct and well-framed:

> "VMs virtualize hardware; containers virtualize the OS."

The recipe/meal analogy is simple and effective. Keep it.

## 1.4 The three cloud eras connect to the rest of the shelf

The IaaS → PaaS → Serverless progression isn't just a history lesson. It connects directly to Backend Engineering's statelessness contract:

> "The next request may hit a different, cold-started container — so sessions and caches cannot live in local memory."

And to System Design's edge/data-gravity discussion:

> "Reading a database in us-east-1 from a user in Tokyo pays a physics penalty — the speed of light — which is why CDNs and edge compute push work to where the users are."

These connections make the doc feel like part of a coherent curriculum rather than an isolated reference.

## 1.5 The ghost port worked example is the exact scenario the audience faces

The `EADDRINUSE` example is perfect. It's the most common local-development bug, and the four-command fix is memorable:

```
lsof -i :3000 → kill -9 <PID> → npm run dev
```

The generalization at the end — "read the error → find the evidence → act on exactly what the evidence names → verify" — connects to the Testing & Debugging doc's evidence-first philosophy. Good.

# 2. Completeness gaps — organized by priority

## Priority 1: Shell fundamentals (the biggest gap)

The doc jumps straight to commands without explaining the shell itself. A learner who has never used a terminal needs these concepts before `pwd` makes sense:

### 2.1a What is a shell vs a terminal?

The doc uses "terminal" throughout but never distinguishes:
- **Terminal** — the window/emulator (iTerm2, Windows Terminal, GNOME Terminal)
- **Shell** — the program that interprets commands (bash, zsh, fish)
- **Command line** — the interface where you type

This matters because:
- macOS defaults to zsh (since Catalina), Linux often defaults to bash
- Shell config files differ: `~/.bashrc` vs `~/.zshrc`
- The learner will eventually need to edit their shell config (add to PATH, set aliases)

A two-sentence explanation at the top of the terminal section would suffice.

### 2.1b Tab completion and command history

These are the two features that make the terminal faster than a GUI, and they're never mentioned:
- **Tab completion** — type `git ch` and press Tab to complete to `git checkout`. Press Tab twice to see all options.
- **Command history** — Up/Down arrows to navigate past commands. `Ctrl+R` to search history.

Without these, the terminal feels slower than clicking. With them, it's dramatically faster. This is the "aha" moment that makes the terminal stick.

### 2.1c Absolute vs relative paths

The doc uses `cd ..` and `cd ~` but never explains:
- **Absolute path** — starts from root: `/home/user/projects/my-app`
- **Relative path** — starts from where you are: `./src/index.js`, `../shared/utils.js`
- **`~`** — shorthand for your home directory
- **`.`** — current directory, **`..`** — parent directory

This is foundational. Without it, the learner can't understand why `cd projects` works from home but not from `/tmp`.

### 2.1d Output redirection

The pipes section covers `|` but not the other redirection operators:
- `>` — write output to a file (overwrite)
- `>>` — append output to a file
- `2>` — redirect errors (stderr) separately from output (stdout)
- `2>&1` — combine errors and output

These come up constantly:
```bash
npm run build > build.log 2>&1    # capture all output to a file
echo "DATABASE_URL=..." >> .env   # append to .env
```

### 2.1e Wildcards/globbing

- `*.js` — all JavaScript files
- `src/**/*.ts` — all TypeScript files in src and subdirectories
- `rm *.log` — delete all log files

This is used daily and never mentioned.

### 2.1f Combining commands

- `&&` — run second command only if first succeeds: `npm install && npm run dev`
- `||` — run second command only if first fails
- `;` — run both regardless

The `&&` pattern is extremely common in scripts and CI pipelines.

### 2.1g Aliases

```bash
alias gs='git status'
alias gco='git checkout'
alias npmd='npm run dev'
```

Not essential for the survival kit, but worth a one-line mention since the learner will see aliases in other people's configs and wonder what they are.

### Suggested fix

Add a short "Shell fundamentals" subsection before the survival kit tables. It doesn't need to be long — six or seven short paragraphs covering the items above. The key is that the learner understands the *environment* they're typing commands into, not just the commands themselves.

## Priority 2: Docker compose and the Dockerfile mental model

### 2.2a Docker compose is mentioned but not explained

The doc says:

> "The one command you'll actually run daily: `docker compose up`"

But it never explains what `docker compose` is, what a `docker-compose.yml` file looks like, or why you'd use it instead of `docker run`. For the target audience, this is the most common Docker interaction — spinning up a local Postgres/Redis for development.

A minimal explanation would cover:
- `docker-compose.yml` is a YAML file that describes multiple containers and how they connect
- `docker compose up` starts all the containers described in the file
- `docker compose down` stops and removes them
- The file typically describes: your app container, a database container, a cache container, and the network connecting them

A 10-line example `docker-compose.yml` would make this concrete:

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: dev
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7
    ports:
      - "6379:6379"

volumes:
  pgdata:
```

The learner doesn't need to write this from scratch. They need to be able to *read* it when they clone a repo that has one.

### 2.2b The Dockerfile mental model

The doc says "if you can read a simple Dockerfile and run compose, you have the literacy this shelf requires." But it never shows what a Dockerfile looks like or explains the four key instructions:

- `FROM` — the base image (what you're building on top of)
- `COPY` — copy files from your machine into the image
- `RUN` — execute a command during the build (install dependencies)
- `CMD` — the command that runs when the container starts

A 6-line example would suffice:

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
CMD ["npm", "start"]
```

The mental model: a Dockerfile is a recipe. Each line is a step. The result is an image. You run the image to get a container.

### 2.2c Port mapping and volume mounts

Two Docker concepts that come up constantly in development:

**Port mapping** (`-p 3000:3000`):
- The container has its own network namespace
- `-p 3000:3000` maps port 3000 on your machine to port 3000 in the container
- Without this, you can't access the container's web server from your browser

**Volume mounts** (`-v ./src:/app/src`):
- By default, changes inside a container are lost when it stops
- `-v` mounts a directory from your machine into the container
- This is how you develop inside a container: your local files are live-synced

These are the two flags the learner will see in every `docker run` command and every `docker-compose.yml` file.

### 2.2d The "it works on my machine" problem

The doc mentions that containers solve this but doesn't explain *how*. The mental model:

> Without Docker: your app depends on a specific Node version, specific OS libraries, specific environment variables. Your coworker's machine has different versions. The server has different versions. "It works on my machine" means "my machine happens to have the right combination."
>
> With Docker: the image contains the exact Node version, the exact OS libraries, the exact environment. Everyone runs the same image. "It works on my machine" becomes "it works in this image," and the image is the same everywhere.

This is the *why* that makes the *what* (images, containers, Dockerfiles) make sense.

## Priority 3: The "where does my code run?" mental model

The doc covers local terminal, Docker, and cloud, but never explicitly connects them into a single mental model. The learner needs to understand the full path:

```
Your laptop (terminal)
  → Dev server (localhost:3000)
    → Staging (staging.example.com)
      → Production (example.com)
```

And for each step:
- **Where is the code?** (your machine, a server, a container, a CDN)
- **How do you interact with it?** (terminal, browser, SSH, dashboard)
- **What can go wrong?** (port conflict, missing env var, wrong Node version, network timeout)
- **How do you debug it?** (read logs, check processes, curl the endpoint, check the dashboard)

This could be a simple table:

| Environment | Where it runs | How you access it | Common issues | Debug with |
|---|---|---|---|---|
| Local dev | Your laptop | `npm run dev`, browser | Port conflict, missing `.env` | `lsof`, `cat .env`, browser console |
| Docker dev | Container on your laptop | `docker compose up`, browser | Port mapping, volume sync | `docker logs`, `docker exec` |
| Staging | Cloud server/container | Browser, SSH | Wrong env vars, missing secrets | SSH + `tail -f`, curl |
| Production | Cloud server/container/CDN | Browser, monitoring dashboard | Everything above + traffic | Logs, metrics, traces |

This table connects the terminal section, the Docker section, and the cloud section into one coherent picture.

## Priority 4: Common ports table

The doc mentions port 3000 in the worked example but never explains what ports are or lists the common ones. A learner who sees "port 5432" in a docker-compose file has no idea what that is.

| Port | Service | What it is |
|---|---|---|
| 80 | HTTP | Unencrypted web traffic |
| 443 | HTTPS | Encrypted web traffic |
| 3000 | Dev server (convention) | React/Next.js/Express dev server |
| 5432 | PostgreSQL | Default Postgres port |
| 3306 | MySQL | Default MySQL port |
| 6379 | Redis | Default Redis port |
| 27017 | MongoDB | Default MongoDB port |
| 22 | SSH | Remote login |
| 8080 | HTTP alternate | Common for proxied web servers |

And a one-sentence explanation:

> A port is a number that identifies a specific service on a machine. A machine can run many services simultaneously — the web server on 3000, the database on 5432, the cache on 6379 — and the port number is how the OS routes traffic to the right one. When two services try to use the same port, you get `EADDRINUSE`.

## Priority 5: SSH keys and the concept of "remote"

The doc mentions `ssh user@host` but doesn't explain:
- **What SSH is** — a secure tunnel to a remote machine. You type commands on your laptop; they execute on the server.
- **SSH keys** — a public/private key pair that lets you log in without a password. Your private key stays on your laptop; your public key goes on the server.
- **`~/.ssh/config`** — a file that lets you define shortcuts: `ssh prod` instead of `ssh deploy@203.0.113.42 -p 2222`.
- **The concept of "remote"** — when you're SSH'd into a server, you're typing commands on that server. `ls` shows the server's files, not yours. `exit` brings you back.

This matters because:
- The learner will eventually need to SSH into a client's server (Freelance Web Practice)
- They'll need to set up SSH keys for GitHub/GitLab
- They'll see `~/.ssh/` referenced in docs and need to know what it is

A short subsection (4-5 sentences) would suffice. The depth can stay in the Security doc.

## Priority 7: A second worked example

The ghost port example is good but narrow. A second example that covers a different part of the substrate would help. Suggestions:

### Option A: "I just cloned a repo and need to run it"

```bash
git clone https://github.com/team/project.git
cd project
cat README.md          # read the setup instructions
cat package.json       # check the Node version and scripts
npm install            # install dependencies
cp .env.example .env   # create the environment file
npm run dev            # start the dev server
# → Error: connect ECONNREFUSED 127.0.0.1:5432
# The database isn't running. Check docker-compose.yml:
docker compose up -d   # start the database
npm run dev            # try again
```

This covers: git, reading files, npm, env vars, Docker compose, and the common "database isn't running" error. It's the exact workflow the learner will follow on their first day at a job.

### Option B: "I need to check if my API is working"

```bash
curl -I https://api.example.com/health
# HTTP/2 200
curl -s https://api.example.com/api/users | head -20
# [{"id":1,"name":"Alice"},{"id":2,"name":"Bob"}...]
```

This covers: curl, reading HTTP responses, piping to `head`, and the mental model of "the terminal is how you test APIs without a browser."

Either example would complement the ghost port example well. Option A is probably more valuable for the target audience.

## Priority 8: Minor survival-kit additions

A few items that belong in the survival kit but are missing:

### 2.8a `head` and `tail`

```bash
head -20 server.log     # first 20 lines
tail -f server.log      # last lines, follow new output (live log reading)
```

`tail -f` is the single most common debugging command in server work. It's how you watch logs in real time. It should be in the survival kit.

### 2.8b `find`

```bash
find . -name "*.env"           # find all .env files
find . -name "*.js" -path "*/src/*"  # find JS files in src/
```

Comes up when you need to find a file and don't know where it is. Less common than `grep` but still survival-kit level.

### 2.8c `which` / `where`

```bash
which node    # /usr/local/bin/node
which npm     # /usr/local/bin/npm
```

Answers "where is this command installed?" — essential for debugging PATH issues.

### 2.8d `man` and `--help`

```bash
man lsof      # full manual page
lsof --help   # quick usage summary
```

The learner needs to know how to look up commands they don't know. `man` and `--help` are the terminal's built-in documentation.

# 7. Bottom line

This is a **well-conceived doc with the right scope and the right boundaries**. The "substrate" positioning is correct, the "safely ignore" table is a structural innovation, and the Docker/K8s/cloud sections are correctly scoped for a web engineering audience.

The main gap is that the doc assumes the learner already knows how a shell works. The survival kit teaches *commands* but not the *environment* those commands run in. Adding a short "Shell fundamentals" section — covering paths, tab completion, redirection, wildcards, and the terminal-vs-shell distinction — would close this gap without bloating the doc.

The second gap is Docker compose. The doc says `docker compose up` is "the one command you'll actually run daily" but never explains what compose is or what the YAML file looks like. Since this is the most common Docker interaction for a web developer, it deserves a brief explanation with a minimal example.

The third gap is the "where does my code run?" mental model. The doc covers local, Docker, and cloud separately but never connects them into a single picture. A simple table showing the path from laptop to production would tie the whole doc together.

## Final recommendation

**Strong draft, publishable with the Priority 1 additions.** The doc's scope is correct, its boundaries are well-drawn, and its content is accurate. The improvements are about filling genuine gaps in the survival kit, not about expanding the scope. The "safely ignore" table is the doc's best feature — protect it.

The highest-leverage improvements are:

> Shell fundamentals (paths, tab completion, redirection), Docker compose explanation, common ports table, `tail -f`, and a "where does my code run?" table.
