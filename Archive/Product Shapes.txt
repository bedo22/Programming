Ignoring display artifacts and reviewing substance only.

## Overall verdict

This is a **strong triage-layer doc**. Its core idea — identify the shape before choosing the stack — is excellent and fills a real gap between the discipline docs and real client briefs. The dominant-constraint framing, death-mode thinking, nesting rules, and per-shape link maps are all valuable.

However, the doc is not yet complete as a full reference. It needs more depth in several areas:

1. It lacks the shelf-standard sections: history, intersection/duplication table, underlying theory, mental models.
2. It mixes **product archetypes** with **engagement/project shapes** without naming the difference.
3. It needs shape lifecycle/migration paths between shapes.
4. It needs shape-specific implications: data model, API contract, security, testing, hosting, maintenance, metrics.
5. It needs more hybrid patterns and at least one more worked example.
6. The AI-era section is good but should address AI products as a shape, not only AI-assisted building.

So: **strong draft, publishable as a triage map, but not yet complete as a full reference**.

# 1. What the document does especially well

## 1.1 The core triage idea is excellent

The central rule:

> Identify the shape before choosing the stack.

is the right lesson. Most failed projects fail because someone chose a stack before understanding the dominant constraint. This doc prevents that mistake.

## 1.2 Dominant constraint per shape is the right lens

Each shape has one constraint that kills the project if mishandled:

- landing page: load speed and conversion,
- dashboard: data density and permissions,
- SaaS: tenant isolation and billing,
- booking: time math and conflicts,
- migration: SEO/data preservation,
- WordPress/CMS: client editability.

This is the most useful part of the doc.

## 1.3 Death-mode thinking is excellent

Asking “how does this shape die?” is a great risk model. It turns abstract architecture into concrete failure prevention.

Examples:

- landing page dies slow/untracked,
- SaaS dies from tenant leak/billing bug,
- e-commerce dies from double-charge/lost order,
- migration dies from SEO drop/data loss.

This is a strong mental model.

## 1.4 Nesting rules are useful

The rule “when shapes nest, the outer constraint dominates” is a good heuristic. The examples are helpful.

## 1.5 Per-shape link maps are valuable

Routing each shape to the owning discipline docs is exactly what a shelf-level triage doc should do.

## 2.2 Missing: product shapes vs engagement shapes

This is an important conceptual gap.

The taxonomy mixes two kinds of shapes:

### Product archetypes

These describe what the product is:

- landing page,
- dashboard/admin panel,
- SaaS,
- CRUD/internal tool,
- e-commerce,
- content site,
- booking/scheduling,
- portfolio.

### Engagement/project shapes

These describe the kind of work being requested:

- API integration/automation,
- WordPress/CMS customization,
- migration/redesign,
- performance optimization.

This is not wrong, but the doc should name the distinction.

Add:

> Some shapes describe the product being built. Others describe the engagement being requested. Both need triage, but they have different scoping questions. Product shapes ask “what must exist?” Engagement shapes ask “what must be changed safely?”

This prevents confusion and improves scoping.

## 2.11 Missing: second worked example

The clinic example is good, but one more example would strengthen the doc.

Suggested example: “A bakery wants to sell cakes online and post weekly menus.”

Triage:

- “Sell cakes online” → e-commerce shape.
- “Post weekly menus” → content/CMS shape.
- Nested shape: e-commerce + content.
- Dominant constraint: checkout reliability and inventory.
- Death mode: lost order or double-charge.
- Owning docs: Payments & Commerce, WordPress/CMS or Shopify, UI/UX, API Design.
- Scope: store first, menu content second, payment integration, order emails, admin editing.

This shows how money shapes dominate content shapes.
