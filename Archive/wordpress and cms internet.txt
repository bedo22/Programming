Ignoring display artifacts and reviewing substance only.

## Overall verdict

This is a **strong and genuinely useful doc**. It fills a real gap in the shelf: the rest of the shelf teaches custom product engineering, but most paid web work lives in the CMS internet. The doc correctly treats WordPress not as “legacy PHP” but as a serious ecosystem with its own architecture, economics, failure modes, and client realities.

Its strongest parts:

- The positioning: “the other 60% of the web.”
- The explanation of why WordPress won.
- The mechanics: request lifecycle, template hierarchy, the Loop, CPTs, taxonomies, hooks.
- The headless WordPress section.
- The managed/no-code landscape.
- The decision matrix.
- The freelancer reality: “a website I can edit myself.”
- The worked example.
- The failure modes.

However, for completeness, it still needs more depth in several practical areas:

1. WordPress security and maintenance playbook.
2. Performance playbook.

## 3.1 Add a WordPress security and maintenance playbook

The doc mentions security briefly, but WordPress deserves a dedicated operational section because security is one of its biggest real-world concerns.

Add:

> **WordPress security and maintenance playbook**

| Area | Baseline practice |
|---|---|
| Updates | Core, theme, and plugin updates on a fixed schedule |
| PHP version | Run supported PHP, not end-of-life PHP |
| Passwords | Unique admin passwords, no shared accounts |
| 2FA | Required for admins/editors |
| Login hardening | Limit login attempts, rename/disable unnecessary login surfaces |
| File editing | Disable plugin/theme file editor in production |
| XML-RPC | Disable if unused |
| REST API | Audit permission callbacks; do not expose private data |
| Backups | Off-site backups, tested restores |
| Staging | Never test updates on production first |
| Malware scanning | Periodic scan and file integrity monitoring |
| Nulled plugins/themes | Never use; they are a common malware vector |
| Roles | Least privilege; client gets only what they need |
| wp-config | Salts, secure keys, environment-aware credentials |

Add a maintenance cadence:

| Cadence | Task |
|---|---|
| Weekly | Check updates, backups, uptime |
| Monthly | Plugin audit, security scan, performance check |
| Quarterly | Restore test, dependency audit, content/model review |
| Yearly | Hosting review, PHP upgrade plan, replatform check |

This would make the doc much more complete for real client work.

## 3.2 Add a performance playbook

> **WordPress performance playbook**

| Layer | Practice |
|---|---|
| Hosting | Use managed WordPress or right-sized VPS; avoid overloaded shared hosting |

| Page cache | Full-page caching for anonymous traffic |

## 3.4 Add a WordPress development workflow section

The doc explains how WordPress works, but not how an engineer should develop and deploy WordPress professionally.

Add:

> **WordPress development workflow**

| Concern | Professional practice |
|---|---|
| Local development | Local by Flywheel, wp-env, Docker, or Bedrock |
| Version control | Theme/plugin code in Git; database not in Git |
| Configuration | Environment-specific `wp-config` values; no secrets in repo |
| Content model | ACF JSON or custom post type definitions in code |
| Blocks | `block.json`, `@wordpress/scripts`, theme.json |
| Database changes | Migrations or scripted updates where needed |
| Deployment | Build/deploy theme and plugins; sync content carefully |
| Environments | Local → staging → production |
| CLI | WP-CLI for imports, search-replace, updates, cache flush |

Add:

> WordPress content and code have different lifecycles. Code should be versioned and deployed. Content should be migrated, imported, or synced deliberately. Treating the database like code is a common source of pain.

## 3.5 Add content modeling decision guidance

The doc covers CPTs, taxonomies, and meta, but it should help readers choose between content modeling tools.

Add:

> **Content modeling choices in WordPress**

| Need | Best default |
|---|---|
| Editorial content with layout flexibility | Blocks / Gutenberg |
| Structured fields for a CPT | ACF / Meta Box / Pods |
| Repeated content type | Custom post type |
| Classification | Taxonomy |
| Site-wide settings | Options page / `wp_options` |
| Reusable layout chunks | Block patterns / template parts |
| Global design settings | theme.json |
| Complex relational data | Custom tables or external service |

Add warning:

> Post meta is flexible but not relationally strong. Heavy meta queries can become slow. If the data is central to the product and queried often, consider custom tables or a separate service.

This is important for engineers who try to make WordPress do too much.

## 3.6 Add a headless decision tree

The headless section is good, but it should be more decision-oriented.

Add:

> **When to use headless WordPress**

Use headless WordPress when:

- there is a frontend team,
- the content powers multiple surfaces,
- the frontend needs custom interactivity,
- the stack is React/Next/Astro/Svelte,
- performance and DX matter,
- editorial workflow can be adapted.

Do not use headless WordPress when:

- there is no frontend team,
- the site is mostly content pages,
- the client needs simple editing and preview,
- budget is small,
- SEO plugins and page builders are expected to work normally,
- the site needs many WordPress plugins that assume theme rendering.

Add:

> Headless WordPress is not automatically better. It trades editing simplicity and plugin compatibility for frontend freedom. The trade must be deliberate.

# 10. Bottom line

This is a **very strong doc** and one of the most strategically important additions to the shelf. It correctly maps the CMS internet, explains why WordPress matters, and connects the platform to freelance reality.

But to become complete, it needs to move from **orientation** to **operational reference**:

- security,
- performance,
- maintenance,
- development workflow,
- content modeling,
- migration mechanics,
- client requirements,
- platform comparison,
- testing,
- cost/lock-in.

## Final recommendation

**Strong draft, publishable as an orientation doc, but not yet complete as a practical CMS engineering reference.**

The highest-leverage improvements are:

> security/maintenance playbook, performance playbook, plugin evaluation, development workflow, content modeling decisions, headless limitations, migration mechanics, and client handoff checklist.
