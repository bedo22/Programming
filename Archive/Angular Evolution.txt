This is a **strong companion doc**. It does an excellent job explaining Angular’s three eras:

1. AngularJS dirty-checking,
2. Angular 2+ classes + zone.js,

Its strongest contribution is the central thesis:

> Angular and React moved in the same direction — narrower reactivity — but through different mechanisms. React narrowed developer bookkeeping with hooks and compiler; Angular narrowed framework watching with Signals.

## 3.6 Add migration paths

This is a major missing piece.

The doc says AngularJS → Angular 2+ had “0% migration path,” but it should explain the actual migration options.

Add:

> **Migration paths**

| From → To | Trigger | Strategy | Risks |
|---|---|---|---|
| AngularJS → Angular 2+ | Digest performance, old architecture, no TS | Rewrite, strangler fig, or hybrid `ngUpgrade` | Big-bang failure, duplicated code, routing mismatch |
| AngularJS → modern Angular via hybrid | Need incremental migration | Use `UpgradeModule`, route-by-route extraction | Two frameworks running, bundle size, mental overhead |
| NgModules → standalone | Boilerplate, modern DX | Convert declarations to standalone, use `provideRouter`, `provideHttpClient` | Incomplete migration, mixed module/standalone confusion |
| zone.js → zoneless | Runtime cost, debugging complexity | Adopt Signals, remove zone-dependent patterns | Missing async triggers, stale UI if state not signal-based |
| RxJS-heavy state → Signals | Simpler synchronous state | Move UI state to signals; keep streams in RxJS | Mixing models without clear boundary |
| OnPush optimization → Signals | Manual change detection discipline | Replace manual `markForCheck` with signal-driven bindings | Overusing effects instead of computed |

Add:

> Angular’s eras are physically visible in code, but migrations should usually be incremental. The hardest migration is AngularJS to Angular because the mental model, template syntax, dependency injection, routing, and build system all changed.

## 3.7 Add Signals vs RxJS guidance

This is essential for reading real Angular code.

Add:

> **Signals vs RxJS — when to use which**

| Concern | Prefer Signals | Prefer RxJS |
|---|---|---|
| Synchronous UI state | Yes | Usually no |
| Derived state | `computed()` | `map`/`combineLatest` only if already stream-based |
| Form state | Signals or typed forms | Complex async validation streams |
| HTTP requests | `httpResource()`/signals where available | `HttpClient` + RxJS operators |
| Event streams | Simple events can use outputs | Complex event composition |
| Cancellation | Depends on resource/API | RxJS strong |
| Debounce/throttle/switch | Not native to signals | RxJS strong |
| Long-lived subscriptions | Be careful | Good with lifecycle cleanup |
| Component state | Signals | Avoid if simpler signals suffice |

Add:

> Signals are not a replacement for RxJS. Signals are best for synchronous reactive state. RxJS is best for asynchronous stream composition. Modern Angular code often needs both, with a clear boundary between them.

This is one of the most useful practical additions you can make.

### AngularJS

```js
angular.module('app', [])
  .controller('CounterCtrl', function($scope) {
    $scope.count = 0;
    $scope.increment = function() {
      $scope.count++;
    };
  });
```

### Angular 2+

```ts
@Component({
  selector: 'app-counter',
  template: `
    <p>Count: {{ count }}</p>
    <button (click)="increment()">+</button>
  `
})
export class CounterComponent {
  count = 0;

  increment() {
    this.count++;
  }
}
```

### Modern Angular

```ts
@Component({
  selector: 'app-counter',
  standalone: true,
  template: `
    <p>Count: {{ count() }}</p>
    <button (click)="increment()">+</button>
  `
})
export class CounterComponent {
  count = signal(0);

  increment() {
    this.count.update(c => c + 1);
  }
}
```

items = signal<Item[]>([]);
