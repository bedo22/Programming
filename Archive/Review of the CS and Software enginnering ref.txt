# 3. Correctness issues and claims that need nuance

These are not necessarily fatal errors, but if you want the document to be precise, they should be adjusted.

## 3.1 Factual/precision corrections

| Location | Current claim | Issue | Suggested fix |
|---|---|---|---|
| §1b, Knuth 1968 | “He coined the term ‘analysis of algorithms’.” | Knuth strongly established/popularized the field, but “coined” may be too strong. | Say: “He established/popularized the formal analysis of algorithms.” |
| §1b, NATO 1968 | “The conference named ‘software engineering’ as a discipline.” | The conference is widely credited with formalizing the term, but the phrase existed around it. | Say: “The conference formalized/legitimized software engineering as a discipline.” |
| §1b, AWS 2006 | “the first generally available infrastructure-as-a-service” | AWS was foundational and transformative, but “first” is historically debatable. Utility computing and earlier services existed. | Say: “one of the first widely adopted public IaaS platforms” or “the platform that made cloud computing mainstream.” |
| §1b, Git stat | “By 2022, ~94% of developers reported Git as their primary VCS.” | Exact statistic needs a citation. | Either cite the survey/source or soften to “the overwhelming majority of developers.” |
| §1b, Log4Shell | “embedded in ~93% of enterprise cloud environments” | This sounds like a vendor report and needs citation/nuance. Also “embedded” vs “vulnerable” matters. | Say: “affected a very large proportion of enterprise environments” and cite source, or remove exact percentage. |
| §1b, Transformer | “Every modern large language model … is a Transformer descendant.” | Most mainstream LLMs are Transformer-based, but “every” is too absolute. | Say: “Nearly all mainstream modern LLMs are Transformer-based.” |
| §1b, Docker | “Containers solved the ‘works on my machine’ problem.” | Containers greatly reduce environment drift but do not fully solve all environment differences. | Say: “Containers largely solved/reduced the ‘works on my machine’ problem.” |
| §5, Big O table | “O(1): Hash map lookup” | Hash map lookup is **average-case/amortized** O(1), not guaranteed worst-case O(1). Poor hashing/collisions can degrade performance. | Add footnote: “Average-case/amortized for hash tables with a good hash function.” |
| §5, HackerRank time limit | “time limit is typically 1–2 seconds, roughly 10⁸ operations.” | This is a useful heuristic but machine/language dependent. | Add: “as a rough heuristic; actual limits depend on language, hardware, and operation cost.” |
| §9, hash-map solution | Space complexity: O(n) | If the alphabet is fixed/small, space can be treated as O(1) bounded by alphabet size. For arbitrary strings, O(n) is acceptable, but nuance matters. | Say: “O(n) in the general case; O(1) if the character alphabet is fixed and small.” |
| §9, JavaScript example | `for (const ch of str)` | In JavaScript, this iterates by code points/code units depending on environment/string iteration semantics. It can mishandle surrogate pairs/grapheme clusters in production text. | Add note: “For Unicode-correct production code, consider `Intl.Segmenter` or explicit code-point handling.” |
| §10 | “The first four rows are CS … The last five are SE.” | Readability is arguably more SE/human-factor than pure CS. | Say: “The first three rows are primarily CS; readability bridges CS and SE.” |

# 4. Major completeness gaps

The document is strong as an **evaluation philosophy**, but if it claims to be the **umbrella for CS & SE**, it misses several major areas.

You do not necessarily need to cover all of them deeply, but you should either:

1. add short sections,
2. cross-link them explicitly, or
3. state that they are out of scope.

## 4.1 Missing: Requirements and validation

The document talks about quality attributes, but not deeply about **figuring out what to build**.

Missing topics:

- requirements elicitation
- user stories / use cases
- acceptance criteria
- functional vs non-functional requirements
- validation vs verification
- “building the right thing” vs “building the thing right”

### Why this matters

Software engineering is not only about evaluating solutions. It also includes discovering the correct problem.

### Suggested addition

Add a short subsection:

> **Requirements and Validation**  
> Before evaluating a solution, you must evaluate the problem. Requirements engineering asks: what are we building, for whom, and why? Validation asks whether we built the right thing; verification asks whether we built it correctly.
