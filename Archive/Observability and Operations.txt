# 1. What the document does exceptionally well

## 1.1 The definition is precise and well-bounded

> "Observability & operations is the discipline of knowing whether the live system is healthy, finding the fault when it isn't, and returning it to health without losing what the failure taught you."

This is a three-part definition that covers the entire operational lifecycle: watch (observability), find (localization), fix (mitigation), learn (postmortem). It also correctly distinguishes observability from monitoring: "monitoring is the subset that checks known answers; observability is the ability to ask questions you did not think to ask." This is the Charity Majors framing, correctly attributed.

The three-judgment table (what deserves a target, what deserves an alert, what deserves a postmortem) is an excellent way to define the discipline's unique contribution. Each judgment is explicitly owned here and not elsewhere.

- A clear time range

The progression from "paging" → "monitoring" → "log centralization" → "distributed tracing" → "metrics 2.0" → "SRE formalized" → "OpenTelemetry" → "AI era" is clean and each step is justified.

# 2. Factual error to correct

## 2.1 The error-budget arithmetic has a math error

The doc states:

> "A 10-minute incident burns ~23% of the month's budget; three of those and the budget is gone."

Let me verify: 99.9% over 30 days = 0.1% × 43,200 minutes = 43.2 minutes of error budget. A 10-minute incident = 10/43.2 ≈ 23.1% of the budget. Three such incidents = 3 × 23.1% ≈ 69.4% of the budget. That is not "gone." The statement should be:

> "A 10-minute incident burns ~23% of the month's budget; **four** of those and the budget is nearly gone (92%)."

Or alternatively:

> "A 10-minute incident burns ~23% of the month's budget; **two** of those and you've burned nearly half."

The current statement is inaccurate and should be corrected.

# 3. Completeness gaps — practices this doc should own but doesn't cover

These are all practices that belong to this doc and are not covered by any other doc on the shelf. I've verified each against the shelf's ownership table.

## 3.1 Missing: On-call design / rotation patterns

The doc mentions on-call extensively (alert fatigue, roles, authority, the pager) but doesn't cover the design of on-call rotations themselves. This is a core operational practice that belongs here.

**What to add:**

| Aspect | What to cover |
|---|---|
| Rotation schedules | Primary/secondary rotation, rotation length (1 week vs 2 weeks), handoff procedures |
| Escalation paths | Primary → secondary → engineering manager → VP; time-based escalation (page not ack'd in 5 minutes → escalate) |
| Shadow on-call | Training new on-call engineers by pairing them with experienced ones; the shadow observes and learns without carrying the pager |
| On-call compensation | Time off in lieu, on-call stipend, on-call as a promotion criterion; the cultural signal of "we value your sleep" |
| On-call load targets | Pages per week targets (e.g., < 2 pages/week per engineer); if exceeded, the team invests in reducing alert volume |
| Handoff procedures | Written handoff at rotation change: ongoing incidents, known issues, upcoming changes, pending action items |
| On-call tooling | PagerDuty/Opsgenie/Incident.io configuration: escalation policies, schedules, overrides, maintenance windows |

This is a genuine gap. No other doc on the shelf covers on-call design. The doc mentions on-call in the mental models ("an alert is a contract with a human"), the alert design section ("page a human for SEV-1/2 only"), and the incident response section ("on-call has authority"), but it doesn't cover the design of the rotation itself.

## 3.2 Missing: Capacity planning / load testing operations

The doc covers SLOs and alerts but doesn't cover the operational practice of capacity planning: load testing before launch, capacity modeling, headroom planning, autoscaling tuning. System Design covers capacity estimation at the architecture level (Little's Law, Amdahl's Law), but the operational practice of running load tests, interpreting results, and adjusting capacity is not covered here.

**What to add:**

| Aspect | What to cover |
|---|---|
| Load testing before launch | Run load tests at 2× expected peak before launch; verify SLOs hold under load |
| Capacity modeling | Use Little's Law (L = λW) to model queue depth; use Amdahl's Law to identify the serial bottleneck |
| Headroom planning | Maintain 30–40% headroom at steady state; autoscaling triggers at 70% utilization |
| Autoscaling tuning | Scale-up threshold, scale-down threshold, cooldown period, min/max replicas |
| Load test interpretation | Identify the knee of the latency-throughput curve; the knee is where queueing starts |
| Capacity review cadence | Monthly capacity review: compare actual load to forecast; adjust headroom |

This is a genuine gap. System Design covers the theory (Little's Law, Amdahl's Law) but not the operational practice of running load tests and adjusting capacity.

## 3.3 Missing: Deployment operations / release management

The doc covers incidents, SLOs, and alerts but doesn't cover the operational side of deployments: canary analysis, progressive rollouts, rollback procedures, deploy freezes, release trains. The CI/CD doc owns the pipeline mechanics (build, test, deploy), but the operational judgment around deployments (when to deploy, how to read canary metrics, when to abort) is an operational practice.

**What to add:**

| Aspect | What to cover |
|---|---|
| Canary analysis | Deploy to 1–5% of traffic first; compare error rate, latency, and SLO burn against baseline; abort if SLO burn exceeds threshold |
| Progressive rollouts | 1% → 5% → 25% → 50% → 100%; hold at each stage for a bake period; monitor SLOs at each stage |
| Rollback procedures | Rollback-first: if canary fails, roll back immediately; don't forward-fix during an incident |
| Deploy freezes | Freeze deploys during SEV-1/2 incidents, during peak traffic windows, and during major events (Black Friday, product launches) |
| Release trains | Fixed release cadence (e.g., weekly) vs continuous deployment; the trade-off between speed and coordination |
| Deploy-readiness checklist | All tests pass, canary is green, runbook is updated, on-call is aware, rollback is tested |

This is a genuine gap. The CI/CD doc owns the pipeline mechanics, but the operational judgment around deployments belongs here.

## 3.4 Missing: Chaos engineering as a practice

The doc mentions "Drills convert runbooks from fiction to procedure" in the mental models and "Have the runbooks been executed in a drill this quarter?" in the checklist. But chaos engineering as a discipline (GameDay exercises, fault injection, steady-state hypothesis) is not covered. The ecosystem table lists "Chaos Engineering / Reliability Testing" tools (Chaos Mesh, Litmus, Gremlin, Steadybit, AWS Fault Injection Simulator).

**What to add:**

| Aspect | What to cover |
|---|---|
| Steady-state hypothesis | Define the expected behavior before the experiment (e.g., "p99 latency < 300ms, error rate < 0.1%") |
| Fault injection | Kill a pod, introduce latency, drop packets, exhaust disk, corrupt a cache entry |
| GameDay exercises | Scheduled, team-wide chaos experiments; everyone participates; the goal is to find weaknesses before they become incidents |
| Blast radius control | Start with the smallest possible blast radius; expand only if the system handles it |
| Automation | Automate chaos experiments in CI; run them on a schedule; treat them as tests |
| Chaos engineering maturity | Level 0: no chaos → Level 1: manual GameDays → Level 2: automated fault injection → Level 3: continuous chaos in production |

This is a genuine gap. The doc mentions drills but doesn't explain the practice of chaos engineering.

## 3.5 Missing: Operational readiness reviews

The doc covers postmortems (after failure) but doesn't cover operational readiness reviews (before launch): production readiness checklists, launch reviews, go/no-go criteria.

**What to add:**

| Aspect | What to cover |
|---|---|
| Production readiness checklist | Observability (SLOs, alerts, dashboards, traces), runbooks, on-call rotation, capacity, rollback plan, security review |
| Launch review | Go/no-go decision based on readiness checklist; the launch captain signs off |
| Operational acceptance criteria | SLOs are defined and measurable, alerts are configured and tested, runbooks are written and drilled, on-call is staffed |
| Pre-launch load test | Run load test at 2× expected peak; verify SLOs hold |
| Post-launch monitoring | Watch SLOs for the first 24–48 hours after launch; the launch captain is on-call |

This is a genuine gap. No other doc on the shelf covers operational readiness reviews.

## 3.6 Missing: Observability cost management

The doc mentions "Cost per query" and "Retention vs. cost curve" in the ecosystem table but doesn't cover the operational practice of managing observability costs: sampling strategies, retention policies, cardinality management, log volume control.

**What to add:**

| Aspect | What to cover |
|---|---|
| Sampling strategies | Head-based sampling (sample at ingestion) vs tail-based sampling (sample after the trace is complete, keep errors and slow traces) |
| Retention policies | Hot storage (7 days, fast queries) → warm storage (30 days, slower queries) → cold storage (1 year, archive) |
| Cardinality management | High-cardinality labels (user_id, request_id) explode metric storage; use exemplars instead of labels for high-cardinality data |
| Log volume control | Structured logging reduces volume; log levels (DEBUG, INFO, WARN, ERROR) control verbosity; log sampling for high-volume services |
| Cost attribution | Attribute observability costs to teams/services; the team that emits the telemetry pays for it |
| Cost review cadence | Monthly observability cost review: compare actual cost to budget; identify top cost drivers; reduce or eliminate |

This is a genuine gap. Observability cost management is a real operational concern that operators deal with daily.

## 3.7 Missing: Operational maturity model

The doc covers individual practices (SLOs, alerts, incidents, postmortems, runbooks) but doesn't present a maturity model that shows how an organization progresses through these practices.

**What to add:**

| Level | Name | Characteristics |
|---|---|---|
| Level 0 | No observability | No metrics, no logs, no traces; incidents are discovered by users; no postmortems |
| Level 1 | Basic monitoring | Host-level metrics (CPU, memory, disk); dashboards exist but are not actionable; no SLOs |
| Level 2 | SLOs defined | SLOs are defined for key journeys; error budgets exist; alerts are tied to SLOs |
| Level 3 | Error budgets enforced | Error budgets are consumed publicly; feature work is gated by budget; postmortems produce action items |
| Level 4 | Proactive reliability | Chaos engineering is practiced; load tests run before launch; operational readiness reviews are standard |
| Level 5 | Self-healing | Automated rollback, automated scaling, automated failover; incidents are rare and short |

This is a genuine gap. A maturity model helps readers understand where they are and what to do next.

## 3.8 Missing: Shift-left for operations

The doc mentions "Observability ships with the service" as a principle but doesn't cover the practice of embedding operational concerns earlier in the development lifecycle.

**What to add:**

| Aspect | What to cover |
|---|---|
| Operational acceptance criteria in design reviews | Every design review includes an operational section: SLOs, alerts, runbooks, on-call |
| Observability requirements in user stories | Every user story includes observability requirements: what metrics to emit, what alerts to configure, what runbook to write |
| SLO targets set before code is written | The SLO target is set during design review, not after the code is written |
| Operational review gate in CI | CI fails if the service has no SLOs, no alerts, no runbooks |
| Operational debt tracked in the backlog | Missing runbooks, stale alerts, untested backups are tracked as operational debt in the backlog |

This is a genuine gap. The principle "Observability ships with the service" is stated but the practice of embedding operational concerns earlier is not covered.

## 3.9 Missing: Operational debt / toil

The doc covers "alert debt" implicitly (alert fatigue, alerts without runbooks) but doesn't name the broader concept of operational debt: accumulated toil, missing runbooks, stale alerts, untested backups, unpracticed failovers.

**What to add:**

| Aspect | What to cover |
|---|---|
| Operational debt defined | Accumulated work that makes operations harder: missing runbooks, stale alerts, untested backups, unpracticed failovers, manual processes that should be automated |
| Toil defined (from SRE) | Manual, repetitive, automatable work that scales linearly with service growth; the goal is to reduce toil to < 50% of on-call time |
| Operational debt inventory | A list of all operational debt items, each with an owner and a ticket; reviewed monthly |
| Operational debt budget | A percentage of each sprint is allocated to reducing operational debt (e.g., 20%) |
| Toil tracking | Track toil hours per week per engineer; if toil exceeds 50%, the team invests in automation |

This is a genuine gap. The concept of operational debt/toil is central to SRE practice and is not covered by any other doc on the shelf.

## 3.10 Missing: Operational team metrics

The doc covers SLOs for the service but doesn't cover metrics for the operations team itself.
