# 1. What the document does well

## 1.1 The three-pipe model is the right foundation

The core insight — every CLI is a transformation on three streams (`stdin`, `stdout`, `stderr`) plus an exit code — is exactly the right mental model. The distinction between `stdout` (data channel, machine-readable) and `stderr` (human channel, narrative) is the single most important design decision in CLI design, and the document nails it.

The exit code as "the CLI's contract with its caller" is also correct. This is what makes CLIs composable in shell scripts and CI pipelines.

## 1.2 The architecture spine is practical

The `entry → parse → route → config → act → output → exit` spine is the right shape. It's general enough to apply to any CLI (from a one-file script to Claude Code) and specific enough to be actionable. The code example with Commander is well-chosen.

## 1.3 The AI-agent CLI section is timely and accurate

The "REPL-with-tools" framing is correct. The five subsystems (tool calling, permission system, streaming, context management, session persistence) are the right decomposition. The insight that "the permission boundary is the security surface" is the key architectural insight for agent CLIs.

## 1.4 The "reading a CLI codebase" section is the most practical

The walk-the-spine approach (bin → router → handlers → tests) is exactly how you'd actually read a CLI codebase. The tip about testing by running the router with fixture args and asserting on stdout and exit code is the right testing philosophy.

## 1.5 The worked example is well-structured

The task-list CLI example demonstrates the architecture spine in action, from skeleton to interactive mode to publishing. The progression from argument-based to interactive prompts is a good teaching arc.

# 2. Missing sections and topics

## 2.1 Error handling conventions (missing entirely)

The worked example shows `stderr` + `exit(1)`, but there's no dedicated section on error handling in CLIs. This is a significant gap because error handling is one of the most important aspects of CLI design.

**What to add:**

**Error classification:**

| Error type | Exit code | Example | User action |
|---|---|---|---|
| Success | `0` | Command completed normally | None |
| General error | `1` | Something went wrong | Check stderr, fix input |
| Usage error | `2` | Invalid arguments | Fix command syntax |
| Permission denied | `126` | File not executable | Check permissions |
| Command not found | `127` | Binary not in PATH | Check installation |
| Fatal signal | `128 + N` | Killed by signal N | Check signal source |

**Error message design for terminals:**

- One-line summary to `stderr` for machine parsing.
- Multi-line details to `stderr` for human reading.
- Never put error messages on `stdout` (breaks pipes).
- Include a "what to do next" hint in the error message.
- Use color for errors (red) but degrade gracefully when piped.

**Exit code conventions:**

```bash
# Good: specific exit codes
exit 0    # success
exit 1    # general error
exit 2    # usage error (wrong arguments)
exit 3    # config error
exit 4    # network error
exit 5    # permission denied

# Bad: everything is exit 1
exit 1    # what went wrong? no idea
```

## 2.2 Signal handling (missing entirely)

Signal handling is crucial for CLI apps, especially long-running ones. The document doesn't mention it at all.

**What to add:**

| Signal | When it fires | What to do |
|---|---|---|
| `SIGINT` (Ctrl+C) | User wants to stop | Clean up, flush output, exit gracefully |
| `SIGTERM` | System wants to stop (kill, shutdown) | Same as SIGINT |
| `SIGHUP` | Terminal disconnected | Reload config or exit |
| `SIGPIPE` | Writing to a closed pipe | Handle gracefully, don't crash |

**In Node.js:**

```javascript
process.on('SIGINT', () => {
  console.error('\nInterrupted. Cleaning up...');
  // flush buffers, close connections, save state
  process.exit(0);
});

process.on('SIGTERM', () => {
  // graceful shutdown
  process.exit(0);
});
```

**Why this matters:** A CLI that doesn't handle `SIGINT` leaves temp files, open connections, and corrupted state. A CLI that handles it well feels professional.

## 2.4 Testing CLI applications (missing entirely)

The "reading a CLI codebase" section mentions testing but doesn't cover how to test CLI apps. This is a significant gap.

**What to add:**

**Testing strategies:**

| Test type | What to test | How |
|---|---|---|
| Unit tests | Individual command handlers | Import handler, call with fixture args, assert output |
| Integration tests | Full CLI invocation | Spawn subprocess, capture stdout/stderr/exit code |
| Snapshot tests | Output format stability | Snapshot stdout, compare across runs |
| E2E tests | Real file system operations | Use temp directories, verify file state |

**Example integration test:**

```javascript
import { execFileSync } from 'child_process';

test('todo add writes to file', () => {
  const result = execFileSync('node', ['bin/todo.js', 'add', 'Buy milk'], {
    env: { ...process.env, HOME: tmpDir },
    encoding: 'utf8',
  });
  expect(result).toContain('Added');
  expect(fs.readFileSync(path.join(tmpDir, '.todo.json'), 'utf8'))
    .toContain('Buy milk');
});
```

**Testing philosophy:** Test the contract (stdout, stderr, exit code, file side effects), not the implementation. This is the same philosophy as the "reading a CLI codebase" section.

## 2.5 Security considerations (missing entirely)

CLIs have unique security concerns that the document doesn't cover.

**What to add:**

| Concern | Risk | Mitigation |
|---|---|---|
| Command injection | User input passed to `exec()` | Use `execFile()` with argument array, never string concatenation |
| Path traversal | User input used in file paths | Validate and sanitize paths, use `path.resolve()` |
| Secrets in env vars | Secrets leaked in logs or error messages | Never log env vars, use secret managers |
| File permissions | Config files readable by all users | Set `chmod 600` on config files with secrets |
| Argument parsing | Malformed arguments cause crashes | Validate all arguments, fail gracefully |

**Command injection example:**

```javascript
// Bad: command injection
exec(`rm -rf ${userInput}`);

// Good: safe argument passing
execFile('rm', ['-rf', userInput]);
```

# 3. Expansions to existing sections

## 3.1 Expand the mental models section

The current mental models table is good but could be expanded with more specific examples of how to reason about terminal apps vs web apps.

**Add:**

| Frame | What it does | Web equivalent |
|---|---|---|
| "Three pipes, one exit code" | Every CLI is a stream transformation | HTTP request/response |
| "Programs compose" | Your CLI is a component in someone else's pipeline | Microservice in a service mesh |
| "TTY or not" | Interactive features only exist when a TTY is present | Browser vs headless mode |
| "The terminal is a conversation" | TUIs draw, respond, and redraw | React component lifecycle |
| "Config is a ladder" | Flags override env vars override config files | Environment variables override defaults |
| "Agent CLIs are REPLs with tools" | The newest form is a read–tool-call–stream loop | Chat interface with function calling |

**Key difference from web:** In web development, the browser is the runtime and the DOM is the output. In CLI development, the terminal is the runtime and the pipes are the output. This means:
- No event loop for user interaction (except TUIs).
- No DOM to manipulate (only text output).
- No CSS to style (only ANSI codes).
- No browser APIs (only Node.js APIs).

const MAX_CONTEXT_TOKENS = 100000;

function manageContext(messages) {
  let tokens = countTokens(messages);

    // Remove oldest messages, keep system prompt

}
