Ignoring display/extraction artifacts and reviewing substance only.

## Overall verdict

This is one of the strongest conceptual docs in the shelf. Its core narrative — **classes → stateless functions → hooks → compiler-era React** — is excellent, and it correctly identifies the real reasons React moved away from class components:

- hard reuse of stateful logic,
- lifecycle scattering,
- `this` confusion,
- mutable instance model conflicting with React’s snapshot-per-render model.

The sections on **closures vs `this`**, **stale closures**, **storage models**, and the **lifecycle-to-hooks translation table** are especially strong.

However, the doc is **not fully complete as a modern React mental-model reference**. It is excellent on the historical paradigm shift, but lighter on the practical modern React surface that a reader will encounter at work in 2026:

- React 18 concurrent features,
- React 19 Actions/hooks,
- Context,
- Suspense and `use`,
- transitions,
- forms,
- reconciliation and keys,
- component identity/remounting,
- derived state anti-patterns,
- effects vs event handlers,
- Strict Mode,
- batching,
- hydration,
- migration recipe,
- failure modes,
- summary checklist.

It also has a significant **duplication risk**: it says the state prequel lives in another doc, but then includes a long state-history section anyway. That should be trimmed or explicitly summarized.

# 1. What the document does especially well

## 1.1 The class-to-hooks rationale is excellent

The doc correctly explains React’s three official problems with classes:

1. Hard to reuse stateful logic.
2. Complex components become hard to understand.
3. Classes confuse both people and machines.

This is the right framing. It avoids the shallow explanation — “functional programming is better” — and correctly says:

> Function components existed before hooks, but they were not enough. Hooks made functions first-class by giving them state and effects.

That is the key insight of the doc.

---

## 1.2 The capture-vs-mutate comparison is one of the best sections

The “Follow button” example comparing function components and class components is excellent.

It correctly shows:

- function components capture rendered values,
- class components read mutable `this.props`,
- closures are not the bug,
- `this` mutability is the bug.

This is a deep and important mental model.

---

## 1.3 The stale closure explanation is strong

The interval counter example is a classic, and the doc handles it well:

- empty deps freeze the closure,
- the dependency array must be honest,
- functional updaters can remove dependencies,
- stale closures are usually dependency lies, not closure failures.

This is exactly the right lesson.

---

## 1.4 The lifecycle-to-hooks translation table is useful

Mapping:

- `componentDidMount` → `useEffect(..., [])`,
- `componentDidUpdate` → `useEffect(..., [deps])`,
- `componentWillUnmount` → effect cleanup,
- instance fields → `useRef`,
- `shouldComponentUpdate` → `memo`/compiler,

is practical and useful for reading older code.

Keep this.

---

## 1.5 The storage models section is valuable

The distinction between:

- state,
- refs,
- local variables,

is one of the most useful mental models for React developers.

The idea that hooks split class-era storage into cleaner categories is well expressed.

# 2. Duplication boundaries

This doc mostly handles duplication well, but there are a few important boundary issues.

## 2.1 The state prequel section is duplicated

The document says:

> That prequel now lives in its own reference doc — What Is “State”? — A Prequel to Programming in React.

But then it still contains a long section:

> 2. What is “state”? A prequel — before we can talk about React’s choices

with extensive history:

- automata theory,
- MVC,
- web statelessness,
- jQuery,
- Backbone/Angular/Ember,
- React classes,
- Flux/Redux,
- hooks,
- signals,
- RSC.

If `what-is-state-prequel.html` owns that material, this section should be drastically reduced.

### Recommendation

Replace §2 with a short bridge:

> State is a normal variable whose value persists across events. The full history of where state lived — MVC models, DOM state, jQuery closures, Backbone/Angular models, React instance state, Flux/Redux stores, hook slots, and RSC data — belongs in the State Prequel doc. This doc assumes that basic idea and focuses on how React’s component model changed the ownership and storage of state.

Then keep only the minimum needed for the class-to-hooks story.

---

## 2.2 OOP section overlaps with JavaScript language doc

The OOP section is good, but some of it belongs in `javascript-the-language.html`:

- prototype vs class mechanics,
- `new`,
- `this`,
- inheritance,
- JavaScript class syntax.

This doc should keep only the **UI-specific OOP story**:

- why object-oriented components felt natural for UI,
- why instance state and lifecycle methods were appealing,
- why inheritance and mutable `this` became painful for React.

Trim the general OOP theory and link to the JavaScript language doc.

---

## 2.3 Compiler/RSC/Signals/Future should stay in React 2024+

The doc already does this mostly correctly by saying:

> The full post-hooks story lives in React 2024 and beyond.

Keep that boundary.

This doc should mention the compiler and RSC only where they affect the hooks mental model:

- compiler automates memoization,
- RSC means hooks only apply to client components,
- server components do not use hooks,
- `use` and Actions change data/mutation patterns.

Do not re-explain the React Foundation, CVEs, Preact, or signals in depth here.

# 3. High-priority completeness gaps

These are the most important additions.

## 3.1 Add a modern hooks catalog

The doc talks about `useState`, `useEffect`, and `useRef`, but it does not give a full map of the modern hooks surface.

Add a section:

> **The modern hooks catalog**

Suggested table:

| Hook | Purpose | Mental model |
|---|---|---|
| `useState` | Local reactive state | A persistent slot that triggers re-render |
| `useReducer` | Complex state transitions | State machine for component state |
| `useContext` | Read context value | Environment dependency injected into component |
| `useRef` | Mutable box that does not trigger render | Stable storage across renders |
| `useEffect` | Synchronize with external systems | Setup/cleanup after render |
| `useLayoutEffect` | Synchronize with DOM before paint | Rare; use for measurement/layout |
| `useInsertionEffect` | Insert styles before layout effects | Mostly for CSS-in-JS libraries |
| `useMemo` | Cache computed value | Derived expensive value cache |
| `useCallback` | Cache function identity | Stable callback for memoized children |
| `useTransition` | Mark non-urgent updates | Keep UI responsive during heavy updates |
| `useDeferredValue` | Defer expensive rendering | Show stale-but-fast UI while new UI prepares |
| `useId` | Stable unique ID | Accessibility IDs that survive SSR |
| `useSyncExternalStore` | Subscribe to external store | Prevent tearing in concurrent rendering |
| `useDebugValue` | Debug custom hook in DevTools | Library/hook author tool |
| `useActionState` | State for form actions | Pending/error/data for async mutations |
| `useFormStatus` | Form submission status | Pending state inside form fields |
| `useOptimistic` | Optimistic UI state | Temporary state while action completes |
| `use` | Read promise/context in render | Suspense-aware resource reading |
| `useEffectEvent` | Stable event logic inside effects | Separate events from effect synchronization |

This would make the doc much more useful for reading real-world React code.

## 3.2 Add React version milestones

The doc has eras, but it should explicitly map major React versions to mental-model changes.

Add:

| React version | What changed mentally |
|---|---|
| React 0.13–15 | Class components become normal; function components are stateless |
| React 16.8 | Hooks make function components first-class |
| React 17 | Gradual upgrade strategy; new JSX transform; no major mental model change |
| React 18 | Concurrent rendering, automatic batching, transitions, Suspense improvements, `useId`, `useSyncExternalStore` |
| React 19 | Actions, form hooks, `use`, ref-as-prop, Activity, resource loading, document metadata |

This helps readers know which era a codebase belongs to.

## 3.3 Add Context mental model

The doc mentions `useContext`, but does not explain context.

Add:

> **Context — environment values, not state**

Include:

| Question | Guidance |
|---|---|
| What is context for? | Values needed by many components without prop drilling |
| What should go in context? | Theme, locale, current user, router, services |
| What should not go in context? | Frequently changing state that many components consume |
| What happens when context changes? | All consumers re-render |
| How to reduce re-renders? | Split contexts, memoize value, move consumers down |

Add:

> Context is not a global store by default. It is a dependency-injection mechanism for React subtrees. If context changes often, it can become a performance bottleneck.

## 3.4 Add reconciliation, keys, and component identity

This is a major missing piece.

The doc explains per-render boxes, but not how React decides whether state persists between renders.

Add:

> **Component identity — why state survives or resets**

Include:

- React compares the new element tree with the previous one.
- Same component type in same position → state preserved.
- Different component type → state reset.
- Different `key` → state reset.
- Changing position in a list can reset state if identity changes.

Example:

```jsx
<UserForm user={user} />
```

If this becomes:

```jsx
<UserForm key={user.id} user={user} />
```

then changing `user.id` resets the form state.

Add:

> Keys are not just list performance hints. They are identity markers. They tell React whether this component is the same thing as before.

This is essential for understanding forms, lists, tabs, modals, and navigation state.

---

## 3.5 Add derived state guidance

This is one of the most common real-world React bugs.

Add:

> **Do not store derived state**

Bad pattern:

```jsx
const [items, setItems] = useState([]);
const [activeCount, setActiveCount] = useState(0);

useEffect(() => {
  setActiveCount(items.filter(i => i.active).length);
}, [items]);
```

Better:

```jsx
const activeCount = items.filter(i => i.active).length;
```

Add:

> If a value can be computed from props, state, or context during render, compute it. Do not duplicate it into state. Do not synchronize it with an effect unless it comes from an external system.

This should be a named principle.

---

## 3.6 Add effects vs event handlers

The doc explains effects, but it should separate effects from event handlers.

Add:

| Concern | Event handler | Effect |
|---|---|---|
| Trigger | User interaction or explicit call | Render commit / dependency change |
| Purpose | Respond to an action | Synchronize with external system |
| Cleanup | Usually not needed | Often needed |
| Runs when | Event occurs | After render, when deps change |
| Example | Button click, form submit | Subscription, timer, document title, network sync |

Add:

> Effects are not “code that runs when something happens.” They are synchronization with something outside React. If the logic is a direct response to a user event, it usually belongs in an event handler, not an effect.

This prevents many overused `useEffect` patterns.

---

## 3.7 Add data fetching patterns

The doc should cover data fetching because it is a common source of effect misuse.

Add:

### Options for data fetching

| Approach | Use when |
|---|---|
| Framework/router data loading | Next.js, React Router, Remix, Astro |
| React Server Components | Server-owned data, no client fetch needed |
| Query library | Client cache, retries, background refetching |
| `use` + Suspense | Promise-based rendering where supported |
| `useEffect` | Simple client-only cases, with care |

If using `useEffect`, add checklist:

- loading/error/data state,
- abort or ignore flag,
- race-condition protection,
- cleanup on unmount,
- dependency honesty.

Example:

```jsx
useEffect(() => {
  let ignore = false;

  fetchUser(id).then(data => {
    if (!ignore) setUser(data);
  });

  return () => {
    ignore = true;
  };
}, [id]);
```

Add:

> A fetch inside `useEffect` is not wrong by default, but it is often not the best tool. Prefer framework data loading, server components, or query libraries when available.

## 3.8 Add Suspense and `use`

Suspense is missing entirely. That is a significant gap for modern React.

Add:

> **Suspense — declarative loading boundaries**

Include:

```jsx
<Suspense fallback={<Spinner />}>
  <ProfilePage userId={id} />
</Suspense>
```

Explain:

- Suspense lets components wait for something,
- fallback shows while waiting,
- works with lazy components,
- works with supported data sources,
- pairs with `use` in React 19.

Add:

```jsx
const user = use(userPromise);
```

Explain:

- `use` reads a promise during render,
- it can suspend the component,
- it can also read context,
- unlike most hooks, it can be called conditionally, but only during render.

This belongs in the hooks mental model doc because it changes how components read resources.

## 3.9 Add transitions and concurrent rendering

The doc mentions the compiler era but not React 18 concurrency.

Add:

> **Concurrent rendering — updates can be interruptible**

Include:

- React 18 introduced concurrent features,
- some updates can be interrupted,
- urgent updates keep UI responsive,
- non-urgent updates can be deferred.

Add hooks:

```jsx
const [isPending, startTransition] = useTransition();

startTransition(() => {
  setSearchResults(results);
});
```

And:

```jsx
const deferredQuery = useDeferredValue(query);
```

Guidance:

| Hook | Use for |
|---|---|
| `useTransition` | Mark state updates as non-urgent |
| `useDeferredValue` | Defer expensive derived rendering |

Add:

> Concurrent React does not mean parallel rendering by default. It means React can prepare and prioritize updates more flexibly.

## 3.10 Add forms and Actions

Forms are a major practical gap.

Add:

> **Forms in the hooks era**

### Controlled components

```jsx
const [name, setName] = useState("");

<input value={name} onChange={e => setName(e.target.value)} />
```

### Uncontrolled components

```jsx
const inputRef = useRef(null);

<input ref={inputRef} defaultValue="" />
```

### React 19 Actions

```jsx
<form action={updateProfile}>
  <input name="name" />
  <SubmitButton />
</form>
```

Add form hooks:

| Hook | Purpose |
|---|---|
| `useActionState` | Manage action result: pending, error, data |
| `useFormStatus` | Know whether enclosing form is submitting |
| `useOptimistic` | Show optimistic state while action completes |

Add:

> Actions make mutations part of the component model. They integrate forms, pending states, optimistic UI, and server mutations more naturally than manual `onSubmit` handlers.

This is important for 2026 React code.

## 3.11 Add state design guidance

The doc explains where values live, but not how to design component state.

Add:

> **Where should state live?**

| Situation | Recommendation |
|---|---|
| Used by one component | Local state |
| Used by parent and child | Lift to nearest common owner |
| Used by many distant components | Context or state library |
| Server-owned data | Server component, framework cache, or query library |
| Shareable/bookmarkable state | URL/search params |
| Temporary UI state | Local state or ref |
| Complex transitions | `useReducer` |

Add:

> State should live as close as possible to where it is used, and as high as necessary for sharing. Do not lift state until lifting is required.

This connects well with The Rhythm without duplicating it.

## 3.12 Add `useReducer` guidance

The doc mentions `useReducer`, but should explain when to use it.

Add:

| Use `useState` when | Use `useReducer` when |
|---|---|
| State is simple | State has multiple related fields |
| Updates are independent | Updates are transitions |
| Logic is local | Logic benefits from named actions |
| Few state variables | State machine behavior is useful |

Example:

```jsx
const [state, dispatch] = useReducer(reducer, initialState);
```

Add:

> `useReducer` is not only for large apps. It is useful whenever state transitions need to be explicit, testable, and readable.

## 3.13 Add memoization guidance pre- and post-compiler

The doc says the compiler removes much manual memoization, but readers still encounter `useMemo`, `useCallback`, and `React.memo` in older code.

Add:

| Tool | What it caches | Use when |
|---|---|---|
| `useMemo` | Computed value | Expensive derivation with stable deps |
| `useCallback` | Function identity | Passing callbacks to memoized children |
| `React.memo` | Component render | Child re-renders often with same props |

Add:

> Memoization is not free. It adds dependency tracking, memory, and complexity. Use it when measurement or compiler guidance shows it helps.

Then connect to compiler:

> The React Compiler reduces the need for manual memoization, but it does not remove the need to understand these tools. Old code still contains them, and incorrect memoization still causes bugs.

## 3.14 Add refs in more depth

The doc treats refs as mutable boxes, but should cover practical ref use.

Add:

| Ref use | Example |
|---|---|
| DOM access | Focus, scroll, measurement |
| Stable storage | Timer ID, previous value |
| Latest value escape hatch | Reading current value inside stable callback |
| Callback refs | Cleanup or dynamic attachment |
| `forwardRef` / ref-as-prop | Passing refs to child components |

Add:

> Do not use refs to store state that affects rendering. If changing the value should update the UI, use state. If the value is for imperative access or non-rendering bookkeeping, use a ref.

Mention React 19:

> In React 19, function components can receive `ref` as a prop in many cases, reducing the need for `forwardRef`.

## 3.15 Add Strict Mode and double invocation

This is missing and very important for debugging.

Add:

> **Strict Mode**

In development, Strict Mode:

- double-invokes component renders,
- double-invokes certain initializers,
- mounts, unmounts, and remounts effects to expose missing cleanup.

Add:

> If an effect breaks in Strict Mode, the effect was probably missing cleanup or was not idempotent. Strict Mode does not create the bug; it reveals it.

This is essential for modern React debugging.

---

## 3.16 Add batching and state update semantics

Add:

> React batches state updates.

Include:

- multiple `setState` calls in one event usually produce one render,
- React 18 extended automatic batching to promises, timeouts, and native events,
- functional updaters avoid stale state:

```jsx
setCount(c => c + 1);
```

Add:

> Do not assume `count + 1` inside multiple updates sees the latest value. Use updater functions when the next state depends on the previous state.

## 3.17 Add hydration mental model

The doc does not cover SSR/hydration.

Add:

> **Hydration — server HTML meets client state**

Include:

- server renders initial HTML,
- client attaches event handlers,
- initial state should match server output,
- browser-only values should not be read during first render.

Bad:

```jsx
const [width, setWidth] = useState(window.innerWidth);
```

Better:

```jsx
const [width, setWidth] = useState(0);

useEffect(() => {
  setWidth(window.innerWidth);
}, []);
```

Add:

> Hydration mismatches happen when the client’s first render does not match the server-rendered HTML. Keep first render deterministic.

This is important for Next.js and RSC-era React.

## 3.18 Add legacy React patterns for reading older code

The doc mentions classes, but older code has more patterns.

Add a legacy patterns section:

| Pattern | What it is | Modern equivalent |
|---|---|---|
| `React.createClass` | Pre-ES6 class factory | Function component or ES6 class |
| Autobinding methods | `createClass` bound methods automatically | Bind manually, arrow class fields, or hooks |
| Mixins | Shared logic objects | Custom hooks |
| HOCs | Wrapper components | Custom hooks, composition |

## 3.19 Add a class-to-function migration recipe

The lifecycle translation table is good, but a step-by-step recipe would be better.

Add:

> **Migration recipe: class component → function component**

```text
1. Identify state fields.
2. Convert each state field to useState or combine into useReducer.
3. Convert props access to function arguments.
4. Convert lifecycle methods:
   - componentDidMount → useEffect(..., [])
   - componentDidUpdate → useEffect(..., [deps])
   - componentWillUnmount → effect cleanup
5. Convert instance fields to useRef.
6. Convert contextType to useContext.
7. Remove this and bind usage.
8. Replace setState with state setters or dispatch.
9. Move event handlers into plain functions.
10. Add dependency arrays and cleanup.
11. Test behavior, especially mount/unmount and updates.
```

Add warning:

> Do not mechanically translate every lifecycle method into one effect. Sometimes multiple lifecycle methods become one effect; sometimes one lifecycle method becomes no effect at all because the value can be derived during render.

## 3.20 Add failure modes section

The doc has classic bugs, but should expand into a full failure modes section.

| Failure mode | What happens | Fix |
|---|---|---|
| Effect as event handler | Logic runs on mount/update when it should run on user action | Move to event handler |
| Derived state stored in state | Two sources of truth drift apart | Compute during render |
| Syncing props to state unnecessarily | Component ignores prop updates | Use props directly or reset with key |
| Missing effect cleanup | Subscriptions/timers leak | Return cleanup |
| Dishonest dependency array | Stale closures or infinite loops | Fix deps or restructure |
| Object/array identity causing re-renders | Memoization fails, effects re-run | Stabilize value or move creation |
| Missing keys in lists | State attached to wrong item | Use stable IDs |
| Index as key for reorderable lists | State follows wrong row | Use item ID |
| Context overuse | Many components re-render on frequent changes | Split context or use state library |
| Premature memoization | Complexity without benefit | Measure or let compiler handle |
| Using hooks conditionally | Hook order breaks | Move hooks to top level |
| Reading browser APIs during render | SSR/hydration failure | Move to effect |
| Fetching in effect without race protection | Old response overwrites new one | Use abort/ignore flag |
| Updating state during render | Render loop or impure component | Derive instead or move to event/effect |

## 3.21 Add principles section

Add shelf-standard principles.

| Principle | Meaning |
|---|---|
| UI is a function of state | Render describes the view from current state |
| Each render is a snapshot | Props and state values are captured for that render |
| State is owned | Every piece of state has one component owner |
| Props flow down, events flow up | One-way data flow |
| Render should be pure | No side effects, no mutation, no external writes during render |
| Effects synchronize | Effects connect React to external systems |
| Derived state is computed, not stored | Avoid duplicating truth |
| Keys define identity | Keys preserve or reset state |
| Refs are for non-rendering storage | Do not use refs for UI state |
| Compiler automates memoization, not correctness | Rules of React still matter |

# 4. Factual and precision improvements

These are mostly small but important.

| Location | Issue | Suggested fix |
|---|---|---|
| Era 1 | “React shipped in 2013 with one component model: classes” | React initially used `React.createClass`; ES6 class components came later with React 0.13 |
| Era table | “Class only, 2013–2015” | Say “createClass era → ES6 class era” |
| Era 2 | Function components could not read context | Nuance: they could access context via legacy APIs or consumers, but not ergonomically; `useContext` made it natural |
| Classes section | “Classes don’t minify well” | Keep but soften; the React team cited this, but it is not the main reason today |
| Hooks section | “useEffect schedules side-effect work after the DOM has been painted” | Clarify: passive effects usually run after paint; `useLayoutEffect` runs before paint |
| Storage models | Local variables “die at end of this render” | Good, but clarify closures can keep them alive if captured |
| Rules of hooks | “React identifies hook state by call order” | Correct; can add that hooks are stored on the component fiber |
| React 19 | Only mentions `useEffectEvent` and `Activity` via companion doc | Add Actions, `useActionState`, `useFormStatus`, `useOptimistic`, `use`, ref-as-prop |
| Current state | “As of 2025” | Update to current shelf timeframe, likely 2026 |
| Context | If saying function components could not access context pre-hooks | Clarify legacy context/Consumer existed |
| `use` | If mentioned, note it can be called conditionally but only during render | Avoid implying normal hook rules apply identically |
| Compiler | Do not imply compiler fixes all performance or correctness issues | Say it automates memoization while Rules of React still apply |

# 6. Concrete snippets you can add

## 6.1 Modern hooks snippet

```md
Hooks are not just useState and useEffect.
Modern React uses hooks for state, context, refs, synchronization,
performance, transitions, forms, and resource reading.

When reading React at work, identify which hook category you are looking at:
state, synchronization, caching, identity, concurrency, or mutation.
```

## 6.2 Derived state snippet

```md
If a value can be computed from existing props or state during render,
compute it.

Do not store derived values in state.
Do not synchronize derived values with effects.
Derived state is one of the most common sources of React bugs.
```

## 6.3 Effects vs events snippet

```md
Event handlers respond to user actions.
Effects synchronize with external systems.

If the logic should happen because the user clicked something,
it probably belongs in an event handler.

If the logic should stay in sync with something outside React —
a subscription, timer, document title, network resource, or DOM measurement —
it probably belongs in an effect.
```

## 6.4 Keys snippet

```md
Keys are identity.

Same component type + same key + same position = React preserves state.
Different key or different component type = React resets state.

If a form unexpectedly resets, check component identity before checking the state logic.
```

## 6.5 Migration snippet

```md
Do not translate lifecycle methods mechanically.

Ask:
- What state does this class hold?
- What external systems does it synchronize with?
- What derived values can be computed during render?
- What cleanup must run on unmount?
- What instance fields are really refs?

Then rebuild the behavior as a function component with hooks.
```
