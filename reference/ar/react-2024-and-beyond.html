مرجع · نظام React البيئي — تطورات ما بعد الخطافات

React 2024 وما بعدها — المترجم، RSC، المؤسسة

ما تغيّر في React بعدما استقر نموذج الخطافات: تحوّل React 19 نحو المنصة، ومترجم React v1.0، ومكونات الخادم (RSC) التي تقسم التصيير عبر حاسبين، ومؤسسة React تحت Linux Foundation، ودرس الأمن في RSC (ديسمبر 2025)، ولماذا لم تتبنَّ React الإشارات، وPreact كفرع هيكلي، وعصر الأطر والتوجيه. قصة التحوّل من الكلاسات إلى الدوال اكتملت؛ هذه الوثيقة تغطي ما حدث بعد ذلك.

اللغة: العربية · English

العلاقة مع وثيقة التحوّل النموذجي الأساسية

تنتهي وثيقة التحوّل من الكلاسات إلى الخطافات عند عصر المترجم (§12) وتحيلك إلى هنا لتفاصيل 2024+. كل ما في هذه الوثيقة يبني على النموذج الذهني للخطافات من تلك الوثيقة — مكونات العميل ما زالت تلتقط القيم عند كل تصيير، وuseState ما زال يعمل تمامًا كما هو موصوف هناك. الجديد: React 19 جعل ميزات المنصة حقيقية، والمترجم مستقر، وRSC تقسم المعالجة، وأصبحت React محكومةً من قِبل مؤسسة.

0. كيف تستخدم هذه الوثيقة

ترتيب القراءة: class-to-hooks ← هذا الدليل ← frontend-camps-survey (خريطة المعسكرات) ← nextjs-deep-dive (الإطار الأكثر احتمالًا في مسار عملك مع React). ويمكن قراءتها مستقلة: يشرح كل قسم تحوّلًا واحدًا من تحوّلات ما بعد الخطافات — ما هو، وما تغيّر في الكود، وأين يقع الحد الفاصل مع وثيقة التحوّل النموذجي.

النطاق. يغطي هذا الدليل ما تغيّر في React بعدما استقر نموذج الخطافات: إصدار المنصة (React 19)، والمترجم، ومكونات الخادم، والحوكمة، والأمن، وعصر الأطر، والنتائج على النظام البيئي. يفترض أنك تفهم بالفعل الخطافات من وثيقة class-to-hooks ولا يعيد تدريسها. لا يعلّم أساسيات React، ولا يقارن جميع معسكرات الواجهات الأمامية (frontend-camps-survey)، ولا يتعمق في دواخل Next.js (nextjs-deep-dive).

1. React 19 — التغيّر نحو المنصة

حوّل React 19 (ديسمبر 2024) عشرة أنماط مجتمعية إلى ميزات أصلية في المنصة. هذا هو الإصدار الذي يعتمد عليه المترجم وRSC، وهو المعيار الذي تُقاس به فحوصات «2024 وما بعدها» في هذا الدليل. النموذج الذهني من class-to-hooks لم يتغيّر — ما تغيّر هو أن كثيرًا مما كان النظام البيئي يبنيه بالمكتبات أصبح الآن جزءًا من React نفسها.

الميزةماذا تغيّر عند قراءة الكود
Actions (إجراءات النماذج/الانتقالات)انتقالات الحالة اللاتزامنية وإرسال النماذج سلوك React من الدرجة الأولى (§2)
useActionStateحالة لإجراء لاتزامني: قيد الانتظار، خطأ، نتيجة
useFormStatusحالة الانتظار لإرسال نموذج، تُقرأ من مكوّن فرعي
useOptimisticواجهة تفاؤلية مع تراجع تلقائي عند الفشل
use()قراءة وعد أو سياق أثناء التصيير تحت Suspense
Server Actionsتعديلات على الخادم موصولة بالنماذج والانتقالات (§2، §5)

بيانات تعريفية للمستندرفع <title>/<meta>/<link> أصلية بلا مدير Head خارجي
أولوية أوراق الأنماط + النصوص اللاتزامنيةترتيب الأنماط والنصوص يصبح تصريحيًا
تحميل الموارد المسبقمساعدات preload/preinit للخطوط والنصوص والأنماط

قراءة كود عصر 19: حين ترى useActionState + <form action={asyncFn}> + useOptimistic, فالشكل هو «عدّل، اعرض المتوقع، طابق». هذا يغني عن رقصة «إرسال + setLoading + setError» اليدوية. أنماط class-to-hooks §1 ما زالت سارية — هذا ترتيب جديد لنفس قواعد الحالة، لا نموذج حالة جديدًا.

2. الإجراءات والنماذج — عودة التحسّن التدريجي

جعل React 19 إرسال النماذج أمرًا معنيًا به في React. يمكن للنموذج أن يأخذ دالة action بدلًا من (أو إلى جانب) onSubmit:

function ProfileForm() {
 const [state, action, pending] = useActionState(updateProfile, null);
 return (
 <form action={action}>
 <input name="name" />
 {pending ? "Saving…" : <SaveButton />}
 {state?.error >&& <p className="error">{state.error}</p>}
 </form>
 );
}

دليل القراءة:

  • Action — دالة اللاتزامنية التي تُنفّذ التعديل. حين يبدأ إجراء، يؤجل React التحديث تلقائيًا إلى أولوية انتقال (واجهة غير حاصرة).
  • useFormStatus — عنصر تحكم فرعي يسأل «هل نموذجي المنتظر قيد الإرسال؟» دون رفع الحالة.
  • useActionState — اقتران «هذه الدالة» بـ«أحدث نتيجتها + علم الانتظار». الوسيط الأول هو الحالة السابقة (يتيح إعادة الإرسال بنفس الصيغة).
  • useOptimistic — اعرض القيمة المتوقعة فورًا؛ يتراجع React تلقائيًا إلى القيمة المعتمدة من الخادم عندما يستقر الإجراء.
  • Server Action — إجراء مُعلَّم بـ "use server" يُنفّذ على الخادم. نموذج + إجراء خادم = تحسّن تدريجي حديث.

إجراءات الخادم هي نقاط نهاية. كون الدالة «على الخادم» لا يجعلها آمنة. إجراءات الخادم نقاط نهاية HTTP عامة: تحقق من كل وسيط، وأذن للمستدعي، وقيّد المعدل للعمليات الحساسة، وعامل القيم المرتَّدة كغير موثوقة. بيانات النموذج مدخلات مستخدم — لا تفترض الأنواع أبدًا عند الحدود الفاصلة (§4).

3. مترجم React مستقر (أكتوبر 2025) وشحن افتراضي (2026)

صدر مترجم React v1.0 يوم 7 أكتوبر 2025 — أول إصدار مستقر بعد نحو عقد من البحث (بدأت تجارب الفريق المرتبطة بـ Prepack في 2017). المترجم إضافة Babel تحوّل كودك إلى تمثيل متوسط عالي المستوى (IR)، يجري تحليل تدفق البيانات والقابلية للتعديل، ويدرج الحفظ التلقائي (memoization) حيث يفيد — بما في ذلك أماكن لا يستطيع useMemo أن يذهب إليها قانونيًا، مثل بعد عبارة return مبكرة.

ما تغيّر في 2025–2026: التطبيقات الجديدة تبدأ اليوم والمترجم مفعّل افتراضيًا. فعّله Expo SDK 54+ في القوالب الجديدة، وتضمّه قوالب create-* في Vite و Next.js كخيار اقتنائي. والمترجم مصدر قواعد اللينت في eslint-plugin-react-hooks (تجميعات recommended/recommended-latest) — حتى الفرق التي لم تتبنَّ المترجم تحصل على تحقّقه. هذه القواعد تضبط قواعد React وتُظهر أخطاء خفية (set-state أثناء التصيير، set-state في التأثير، وصول ref غير آمن أثناء التصيير).

بالنسبة لك عند قراءة كود عملك: useMemo وuseCallback وReact.memo تصبح منافذ للنجاة لا القاعدة. الكود الجديد المكتوب تحت المترجم يمكن أن يكون النسخة البسيطة من «الرؤية الأصلية لمكوّن الدالة» في الوثيقة الرئيسة — دالة عادية بالخطافات بلا حفظ يدوي — لأن المترجم يعيد الاستفادة. الكود الحالي يستمر في العمل؛ لست مضطرًا لإزالة الحفظ الموجود عند التبني.

قواعد التبني والترقية (الجزء الذي يهمّ الممارس):

  • لا تثبّت المترجم على نطاق SemVer. يوصي الفريق بـ --save-exact (مثلًا 1.0.0 لا ^1.0.0) وترقية يدوية مع اختبار شامل.
  • فعّل قواعد اللينت أولًا. المترجم صحيح فقط بقدر صحة الكود الذي يدخله؛ قواعد اللينت تخبرك متى يكسر الكود قواعد React قبل أن يحوّره المترجم.
  • اختبر تبعيات المؤثران بعد التفعيل. يمكن للحفظ المولّد أن يغيّر أي المؤثران تشتعل عندما ينتهك الكود قواعد React بهدوء. اقرأ سجل التغييرات وشغّل كامل المجموعة — عامل ترقية المترجم كترقية رئيسية لـ React.

4. مكونات الخادم تقسم التصيير عبر معالجتَين

قوس class→hooks كان عن كيف يدير المكوّن حالته داخل معالج واحد. RSC تجيب عن سؤال مختلف: في أي معالٍج يعمل المكوّن — متصفحك أم الخادم؟ وقد صاغ دان أبراموف الفكرة بوضوح في The Two Reacts (يناير 2024):

  • مكونات العميل: UI = f(state). الحالة تعيش في المتصفح، والكود يعمل في المتصفح، والتفاعلات فورية. مكوّن Counter من وثيقة التحوّل النموذجي يعيش هنا.
  • مكونات الخادم: UI = f(data). البيانات تعيش على الخادم، والكود يعمل على الخادم (عند الطلب أو عند البناء)، ويتلقى المتصفح حمولة الواجهة المُسلسلة بالإضافة إلى كود مكونات العميل التي يحتاجها فقط — لا البيانات الخام، ولا اعتماديات الخادم، ولا الحزمة كلها. PostPreview يقرأ الملفات عبر fs.readFile عند البناء ويرسل فقط الناتج المعروض للعميل.

الصيغة المجمّعة هي UI = f(data, state). يتداخل النوعان: يستطيع مكوّن خادم أن يعرض مكوّن عميل (مزودًا بخصائص قابلة للتَسلسل)، ويمكن لـمكوّن العميل أن يستقبل محتوى معروضًا من الخادم عبر children. ما لا يستطيعه مكوّن عميل هو تمرير دوال أو قيم غير قابلة للتَسلسل إلى مكوّن خادم — الخصائص العابرة للحدود يجب أن تكون قابلة للتَسلسل. التمديد الذهني صغير: كل شيء من وثيقة التحوّل النموذجي ينطبق على مكونات العميل؛ ومكونات الخادم دوال أقرب إلى البيانات — بلا useState/useEffect لأنها لا تُعاد تصعيدها بالطريقة نفسها التي تعيدها بها مكونات العميل (تعمل عند كل طلب أو كل إعادة تحقق).

RSC ليست نموذجًا جديدًا يستبدل الخطافات — بل هي نموذج «دالة + خطافات» الذي يقرر أين تعمل كل دالة. اقرأ «مكوّن العميل» ككل ما في وثيقة التحوّل النموذجي؛ و«مكوّن خادم» كمجموعة جزئية صارمة (بلا خطافات، بلا أحداث، بلا window) تحقق حجم حزمة صفريًا ووصولًا مباشرًا لواجهات برمجة حصرية للخادم.

4.1 قواعد الحدود الفاصلة في RSC

هذه هي القواعد التي تعرف بها الحدّ الفاصل. كل ما في هذا الدليل عن المترجم (§3) ما زال ينطبق على مكونات العميل؛ وهذه تنطبق على الخادم مقابل العميل:

القاعدةالمعنى
لا تستخدم مكونات الخادم الخطافاتلا useState ولا useEffect ولا useReducer ولا useContext…
لا تستخدم مكونات الخادم واجهات برمجة المتصفحلا window ولا localStorage ولا document…
يمكن أن تكون مكونات الخادم لازمنيةيمكنها انتظار الوصول للبيانات مباشرة (fetch، قاعدة بيانات، نظام ملفات)
يمكن لمكونات الخادم أن تعرض مكوناتَ عميلالخادم يركّب تفاعل العميل — يمرر داخله خصائص قابلة للتَسلسل
يمكن لمكونات العميل استقبال children معروض من الخادممنفذ التكوين: الخادم يلفّ الجزء العميل
لا تمرّر مكونات العميل دوالًا إلى مكونات الخادمالخصائص الداخلة إلى مكونات الخادم يجب أن تكون قابلة للتَسلسل (لا يمكن الخادم تنفيذ بيانات العميل)
السياق Context خاص بالعميلالمزوّدون والمستهلكون في شجرة العميل؛ لا تقرأ مكونات الخادم سياق العميل
يجب ألاّ يرسل كود الخادم أسرارًاملفات الخادم لا تصل إلى العميل — لكن البيانات المتسربة عبر ناتج الخادم ما زالت تهم (§5)

4.2 أين تضع الحدود الفاصلة للعميل

افترض مكونات الخادم لعرض البيانات؛ ادفع العميل نحو أوراق التفاعل. انقل مكوّنًا إلى العميل فقط عندما يحتاج: حالة، أو استدعاءات أثر، أو معالج أحداث، أو واجهات برمجة متصفح، أو سياقًا.

4.3 التخزين المؤقت وإعادة التحقق — النموذج الذهني

أصعب أخطاء RSC ليست أخطاء عرض تقريبًا — بل أخطاء تخزين مؤقت: بيانات قديمة، أو محتوى مخصًّص مخزّن أكثر من اللازم، أو بيانات تبدو حديثة رغم أنها عُرضت من تخزين خاطئ. عند قراءة كود تغذيه RSC، اسأل أيّ تخزين هو المعني:

طبقة التخزينالسؤال الذي تجيب عنه
تذكّر الطلب (Request memoization)هل يُدمج هذا الـ fetch ضمن مسار تصيير واحد؟
تخزين الموجّه (Router cache)هل يخزّن الإطار واجهة معروضة من الخادم على العميل عبر التنقلات؟
تخزين HTTPهل هذه الاستجابة قابلة للتخزين لدى المتصفح/CDNs الآن؟
تخزين البيانات (Data cache)هل تُثبّت البيانات المجلَبة عبر الطلبات؟
إعادة التحقق (Revalidation)متى تصبح البيانات المخزّنة بالية، ومن يفرض التحديث؟
التخصيص (Personalization)هل يُشارك المحتوى الخاص بالمستخدم على التخزين بالخطأ؟

تفاصيل الإطار (تخزين Next.js) تعيش في Next.js deep dive؛ أمّا من زاوية React فاعرف فقط: بيانات الخادم يملكها إطار العمل عبر التخزين، وواجهة تفاعلية لا تعتمد بصمت على نضارة ذلك التخزين.

4.4 إدارة الحالة بعد RSC

غيّر RSC أين تنتمي الحالة. نموذج «كل شيء في مخزن عميل عام» نموذج سابق لعصر البيانات المملوكة للخادم:

نوع الحالةأين تنتمي
بيانات مُجلَبة من الخادممكونات الخادم / تخزين بيانات الإطار — ليست مخزن عميل
حالة العنوانالموجّه / عناصر بحث search params
حالة واجهة محليةClient useState / useReducer
حالة تفاعلية مشتركةContext أو Zustand أو Redux Toolkit أو Jotai
حالة التعديل (انتظار/تفاؤل/خطأ)Actions + useActionState + useOptimistic (§2)

القاعدة: إذا كانت البيانات ملكًا للخادم ولقراءة فقط، أبْقِها على الخادم. حالة العميل للـالتفاعل — لا نسخة ظلّ من بيانات الخادم. عصر «جلِب إلى Redux عند التحميل» انتهى؛ المترجم يحفظ القيم، والخادم يملك البيانات، وحالة العميل تتقلص إلى ما هو تفاعل.

4.5 معالجة الأخطاء وحدود الأخطاء

حدود الأخطاء (Error Boundaries) خاصة بالعميل — لا يمكن أن تكون مكونات خادم. مكوّن خادم جذري لشجرة فاشلة لا يملك مقابل error.tsx لكل الشجرة، وحدود الأخطاء المتداخلة تلفّ الأشجار العميلة. الشكل العملي في عصر الأطر: ملف خطأ على مستوى الطريق (Next.js error.tsx أو عناصر الخطأ في React Router) هو اللاقطة الواعية بالخادم؛ أمّا حدود المكونات فتخص الأوراق. يجب أن تُتسلسل الأخطاء كنصوص عبر الحد الفاصل — لا تشارك أبدًا كيانات حية أو دوال (§4.1).

4.6 الدفق Streaming والتصيير المسبق الجزئي PPR

تصيير الخادم يمكن أن يشحن تدريجيًا. الدفق (Suspense على الخادم) يرسل القشرة أولًا ثم محتوى كل مكوّن معلّق حين ينتهي؛ والتصيير المسبق الجزئي PPR (أكتوبر 2023) يعيد القشرة الثابتة عند البناء ويدفق الأجزاء الديناميكية فقط لكل طلب. عند قراءة كود، شكل «قشرة + Suspense حول منطقة واحدة» يعني عادةً أن الجزء البطيء الخاص بالمستخدم معزول كي يشحن الجزء الثابت الأكبر فورًا — نموذج Suspense نفسه لكن محسوب مسبقًا.

5. الحدّ الفاصل الأمني: غيّر RSC معنى «حدّ الثقة» (ديسمبر 2025 – يناير 2026)

أعطت دوال الخادم وبروتوكول RSC للمهاجمين سطحًا هجوميًا جديدًا. في ديسمبر 2025 رصد ثغرة حرجة (CVSS 10.0) تسمح بتشغيل أوامر عن بُعد عبر بروتوكول RSC. شُحنت الإصلاحات، ثم وجد الباحثون تبعاتها — DoS عالي الخطورة (CVE-2025-55184)، وكشف كود مصدري متوسط الخطورة (CVE-2025-55183)، وDoS إضافية في يناير 2026 (CVE-2026-23864).

قائمة الفحص العملية للإنتاج:

  1. عامل كل دالة خادم كنقطة نهاية عامة. تعمل بامتيازات خادمك وأسراره. تحقق من كل وسيط وصادق عليه؛ لا تقبل عذر «إنها داخلية — عميلي فقط يستهلها». بروتوكول RSC العام يصل إليها مباشرة.
  2. لا تضع أسرارًا في كود مصدر دالة الخادم. سلّب CVE-2025-55183 كودًا مصدريًا عبر وسائط مُسلسلة كسلاسل نصية. process.env.SECRET جيد، أما const key = "sk_live_..." فلا. متغيرات بيئية، مدير أسرار.
  3. تحقق عند الحدود الفاصلة بغضّ النظر عن الأنواع. فحص TypeScript ينتهي عند حدود الخادم. تحقق من النمط (schema) من كل وسيط دالة خادم (zod/typebox/valibot) — الأنواع تُمحى وقت البناء والحمولات بلا نوع.
  4. ثبّت تبعيات React واقرأ مدوّنة الأمان. أُصلحت ثغرات ديسمبر 2025 في أسطر 19.x المتأثرة أكثر من مرة — كان أول تصحيح ناقصًا. هذه الآن ممارسة اعتيادية للثغرات الحرجة في أي ماركة؛ وخصص لها ميزانية.
  5. عامل إصدارات الأمان في الأطر كتحديثات نظام تشغيل. تبنّت Next.js إيقاعًا أمنيًا شهريًا رسميًا بإشعار مسبق — جدولها ولا تتركها تتأخر.

6. مؤسسة React (فبراير 2026): لم تَعُد Meta المالك الوحيد

في 24 فبراير 2026، أطلِقت مؤسسة React تحت Linux Foundation. لم تعد React وReact Native وJSX ملكًا لشركة Meta — بل أصبحت ملكًا للمؤسسة، تديرها لجنة تضمّ ثمانية أعضاء مؤسسين بلاتينيين: Amazon، وCallstack، وExpo، وHuawei، وMeta، وMicrosoft، وSoftware Mansion، وVercel. ويتولى Seth Webster دور المدير التنفيذي.

لماذا يهم هذا عند قراءة الكود: مَن يموّل React يشكّل ما يُولَيه أولوية. قادت حاجات شركة واحدة (Meta) خارطة طريق React 16–18 — قيود شريط الأخبار أنجبتَ التصيير المتزامن و Suspense. ثمانية أعضاء — عمالقة سحابة (Amazon, Microsoft) ولاعبو جوال (Expo, Software Mansion) ومستضيف (Vercel) — يوافقون على جملة أولويات أوسع. توقّع إلحاحًا أقل لشركة واحدة وأكثر تنسيقًا للنظام البيئي: واجهات برمجة مستقرة للشركات المضيفة، أبرم عقود ترقية أوضح للمؤسّسات، وإيقاعًا أبطأ وأكثر تدبرًا للإصدارات.

تظل الحوكمة الفنية مستقلة عن المجلس — يحدد المساهمون الاتجاه الفني ويتولى المجلس إدارة الأصول والبنية التحتية. ويحسم مجلس قيادي مؤقت البنية طويلة الأمد، ويستمر تنظيم مؤتمر React Conf.

7. React 19.2 وعصر الأطر والتوجيه

شحن React 19.2 (1 أكتوبر 2025) ثلاث ميزات تغيّر كود يومك: <Activity /> (يحفظ حالة جزء مخفي — يحلّ مشكلة «ابتعدت عن الصفحة وخسرت نموذجي») وuseEffectEvent (الحل الموثّق لأنماط «مصفوفة التبعيات تكذب لأنني أريد أحدث الخاصية في المعالج» من §11 في وثيقة التحوّل النموذجي) وReact Performance Tracks (تراكبات أدوات المطوّر تظهر ما أُعاد التصيير ولماذا).

في الوقت نفسه، تحوّلت توصية React للمشاريع الجديدة: وضعَ Create React App في حالة غروب (14 فبراير 2025) وأعلن بوضوح أن تطبيقات React الجديدة يجب أن تستخدم إطارًا. انتهى عصر «مجرد تطبيق Vite React» كبداية افتراضية. النمط أنه «الصعود في المكدس»: نموذج المكونات استقر، والطبقة التالية هي إطار العمل — التوجيه، جلب البيانات، عملية تقسيم الكود، تصيير الخادم، والتخزين.

8. سؤال الإشارات — ولماذا لم تتبنَّها React

بحلول 2026، وحّد كل إطار تفاعلي رئيسي آخر على الإشارات كأساس وحيد جديد للتفاعلية: Angular (v17+)، وVue 3.5+، وSvelte 5 (runes)، وSolid، وPreact، وحتى Ember. الإشارة خلية تفاعلية فائقة الدقة — عندما تتغيّر قيمتها لا يتحدّث إلا الذي اشترك الدوم فيه لا المكوّن بأكمله. الطرح: تحديثات أسرع ونموذج أبسط — حالة كقيمة مع مشتركين، بدلًا من «أعد تنفيذ المكوّن».

إجابة React ما زالت «لا» — للأسباب التي دوّنها دان أبراموف في 2019: الإشارات أساسها يكسر التركيب (اشتراك خطاف واحد بالإشارات يتعارض مع آخر) وتجعل التصحيح أصعب (تدفق البيانات عبر اشتراكات خفية بدل الخصائص الصريحة). مراهنة React هي أن المترجم يسد فجوة الأداء دون تغيير النموذج الذهني: تكتب دوال وخصائص، يتتبع المترجم الاعتماديات، ويعاد تصيير ما تغيّر فقط. ولكي نكون دقيقين: المترجم يقلل إعادة التصيير غير اللازمة عبر الحفظ — إنه ليس اشتراكًا دقيقًا على مستوى DOM. الاثنان يحلّان المشكلة نفسها بـ آليات مختلفة؛ وفرق النموذج الذهني (خصائص صريحة مقابل اشتراكات خفية) هو كل مغزى رفض React.

عند قراءة كود في العمل: إن لامست Angular (signal()) أو Vue (ref()) أو Svelte ($state) أو Solid (createSignal) أو Preact (signal())، تبدو مثل useState لكن تتصرف خلاف ذلك — المكوّن لا يُقدّم مرة أخرى؛ بل يُحدَّث مثل اشتراك الإشارة. لا تترجم 1:1 بين النموذجين؛ اقرأ وثائق كل إطار.

9. Preact — الفرع الهيكلي الذي طرح سؤال «ماذا لو كانت React 3.5 كيلوبايت؟»

ظهرت Preact في 2015. إنها تنفيذ منفصل لنفس نموذج المكوّنات — نفس JSX، نفس الخطافات (في النهاية)، نفس النموذج الذهني — لكن قاعدة كود مختلفة الأهداف. السرد الرئيسي الأصلي (ما زال على صفحة أهدافها):

  • الحجم: مجرد 3–4 كيلوبايت min+gzip مقابل نحو 40 كيلوبايت في ReactDOM. كان هذا مفيدًا فعلًا في 2015–2016 حين كان بيانات الجوال بطيئة.
  • الأداء: يتجاوز نظام أحداث React الاصطناعي وبقية ضريبة التجريد؛ يستخدم addEventListener المتصفح مباشرة.
  • الوضوح: قاعدة الكود كاملة قابلة للقراءة في بضع ساعات. React ليست كذلك.

9.1 لماذا لم تُضمَّم Preact في React?

ثلاثة أسباب، هي نفسها التي تبقّي Preact منفصلة في 2026:

  1. أهداف مختلفة عن قصد. تحسّن React نموذجًا متعدد المنصات (ويب، Native، VR، ألياف، تصيير متزامن، Suspense، RSC). غير-أهداف Preact تستبعد نظام الأحداث الاصطناعي، وإرهاق PropTypes، ودعم IE8 القديم. «Preact ليست إعادة تنفيذ لـ React… وإلا لكان الأوفق تقديم تحسينات إلى مشروع React نفسه».
  2. أحادي المنصّة مقابل متعدد المنصّات. يستهدف React منصّات تصيير متعددة (مثل React Native، وتقسيم معالجة RSC). أما Preact فصريحة بأنها للويب فقط وتتبع مواصفات DOM بدقة (class بدل className، onInput بدل onChange، دعم أصيل لـ Custom Elements).
  3. التوافق حلّ عبر الأدوات. طبقة preact/compat طبقة الحتمية رقيقة — وجّه المُجمّع إلى preact/compat وستعمل أكثر مكتبات React. يمتص النظام البيئي Preact عبر التوافقية، لا عبر الاندماج.

9.2 لماذا تزداد Preact أهميةً في 2026

  • أطر الجزر (Islands). يدعم Astro Preact كموّرد جزر من الدرجة الأولى — JS قليل للجزر التفاعلية في صفحات ثابتة غالبًا. إذا أضفت 5 كيلو بايت إلى صفحة تسويقية، تلجأ إلى المكتبة بحجم 3.5 لا 35 كيلوبايت.
  • بيئات محصورة/بسيطة. و Web views في التطبيقات الأصلية، وشاشات العرض، وهواتف منخفضة الموارد، وSPAs طرفية حيث يظهر كل كيلو في Core Web Vitals.

تبنّت Preact الإشارات مبكرّا (سبتمبر 2022، Introducing Signals) كإضافة رسمية — دليل على أن على أن رفض React «لا» هو قرارٌ إداري/تصميمي (§8) لا استحالة تقنية.

9.3 قراءة Preact في العمل

الاختلافات التي ستعثر عليها هي بالضبط في صفحة الاختلافات عندها: أسماء سمات DOM أصلية (class وfor و stroke-width) و onInput بدل onChange (إلا مع preact/compat)، ويمكن لمكونات الفئة أن تستقبل وسيطات render(props, state)، والأحداث لا تنتشر عبر البوابات (portals). كل شيء آخر — إغلاق، الخطافات، مصفوفات التبعيات، دورة الحياة — يأتي تباعًا من وثيقة التّحوّل النموذجي.

9.4 هل ستستبدل Preact React؟

لا. الانقسام مستقر لأنه بنيوي لا شكلي: React هي الافتراض متعدد المنصّات الغني بالتحريض والمؤسسة؛ Preact هي الفرع المقتصر على الويب، الأعلى قربًا من مواصفات الويب، وحجمه الصغير. يغلق المترجم الفجوة في إعادة التصيير من أبعاد Preact، لكن لن تتدهور حزمة React إلى حجم Preact — الضريبة متعددة المنصات و RSC قرار مقصود. ومواصفة إدارتها مؤسسة بجانب تنفيذ أصغر يحتفظ به المجتمع — إن كان أكثر استدامة من شركة واحدة تملك الاثنين.

ما تغيّر في React بعد الخطافات: ميزات React 19، والإجراءات/النماذج، المترجم، RSC (الحدود، التخزين، الحالة، الأخطاء، الدفق)، والحدود الفاصلة الأمنية، حوكمة المؤسسة، عصر الأطر، الإشارات، Preact، والأدوات العملية (الترحيل، أنماط الفشل، المبادئ، النظام البيئي، المستقبل، قائمة الفحص). ليس النموذج الذهني class→hooks (class-to-hooks)، ولا خريطة كاملة لمعسكرات frontend (camps)، ولا دواخل Next.js (nextjs)، ولا هندسة النظم أو TypeScript (system-design، across-stacks).
