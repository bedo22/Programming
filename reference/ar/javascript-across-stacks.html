جافاسكريبت عبر المنصات: أين تعمل JS، ومن يحاربها

كيف تبدو JS من منظور الواجهة الأمامية، الخلفية، الجوّال، المدمج، والذكاء الاصطناعي — ما يستخدمه كل واحد من JS، ما لا يناسب JS، واللغات التي كتبت لملء تلك الفجوة (TypeScript، .NET/C#، Java/Spring Boot، Kotlin، Dart، Rust، Python). لكل منافس: جدول تموضع بفقرة واحدة عن النظرية التي تبرر إنشاء لغة جديدة بدلاً من تمديد لغة موجودة. وثيقة شقيقة لـ javascript-the-language.

مرجع: المصطلحات — مفردات مشتركة عبر جميع وثائق المراجع.

النمط. عبر كل المنظورات، تظهر قاعدة واحدة من البيانات: لغة جديدة تربح عندما يتغير القيد المهيمن ويراهن تصميم اللغة القديمة ضد القيد الجديد. JS ربحت المتصفح لأن القيد كان حجم التحميل 1995 + غراء برمجة نصية. TypeScript ربحت أدوات JS لأن القيد تغير لصيانة الفرق الكبيرة. Go ربحت الخدمات الشبكية لأن القيد تغير للتزامن أولاً. Rust ربحت الأنظمة لأن القيد تغير لأمان الذاكرة بدون GC. Java مدت بناء جملة C++ لكن ربحت على رهان JVM (اكتب مرة، شغّل في أي مكان). القاعدة: مدد عندما القيد غير متغير، اخترع عندما ينقلب.

منظور الواجهة الأمامية

ما تستخدمه الواجهة الأمامية من JS: اللغة + DOM + fetch + Canvas/WebGL + تفاعل WASM. ما JS-اللغة لا تستطيع فعله على الواجهة الأمامية: الحساب الثقيل، الخيوط، قواعد كود كبيرة آمنة النوعياً. Recap الـ ٥ معسكرات أمامية (رابط لـ camps-survey). لا منافس حقيقي على مستوى اللغة في الواجهة الأمامية (المتصفح يشغل JS + WASM فقط)؛ المنافسون هم أوقات تشغيل بديلة (WASM) ولغات تُترجم لـ JS (TS، PureScript، Elm، ReasonML).

تحول TypeScript (المنافس الذي نجا)

TS ليس منظوراً منفصلاً — هو التطور الداخلي للمنظور الأمامي. لكنه يستحق قسمه الخاص لأنه المنافس الوحيد الذي لم يحارب JS من الخارج؛ بل استبدلها من الداخل. النظرية: تمديد JS بالأنواع التدريجية، لا كتابة لغة جديدة. لماذا فاز TS حيث خسر Dart و CoffeeScript (لا خطوة تجميع منفصلة وقت التشغيل، لا بناء جملة منفصل للكود القيمي، فقط أنواع). إصدار ٢٠١٢، رهان Angular 2 (٢٠١٤)، دعم Babel 7 + TS (٢٠١٨)، نقطة تحول ٢٠٢٠ "TS كافتراضي". جدول تموضع: TS مقابل JS — ما يحسّن كل منهما. قاعدة "TS تتبخر عند التجميع" — وقت التشغيل، JS هو ما يعمل.

كتابة JS معنونة — نظام الأنواع عملياً

جادل تحول TypeScript في لماذا يوجد TypeScript. هذا القسم في كيف يعمل كنظام قواعد: طبقة ثابتة تفحص الأنواع قبل أن يعمل المحرك أبداً، ثم تمحى إلى JS عادي. ثلاث أفكار هي الوظيفة كلها.

الفكرةماذا تعنيالمزلق الذي تمنعه
الأنواع تمحى، لا تُفرض في زمن التشغيل tsc يفحص الأنواع، يزيلها، ويصدر JS نقي. لا يوجد فحص زمن تشغيل بنمط instanceof للواجهات. نظام الأنواع عقد زمن ترجمة مع فريق التطوير، لا أكثر. افتراض أن النوع يضمن أمان زمن التشغيل. لا يضمنه — يضمن أن المترجم فحص مواضع الاستدعاء. بيانات زمن التشغيل (حمولات API، إدخال المستخدم) غير معنونة مهما علّقت.
الشكل فوق الاسم TS بنيوي لا اسمي. كائنان بنفس الحقول هما نفس النوع مهما أُعلنا. interface وtype يحددان شكلاً؛ أي قيمة تطابقه تُقبل. كتابة نمط "مصنع" أو طقوس لمطابقة الأنواع حين تكفي التوافقية البنيوية الصرفة. بطّية JS محفوظة، لكن تُفحص مبكراً.
الترميز أصغر أولاً، والاستدلال يوسّع يمكنك ترك TS يستدل على معظم الأنواع (التصريحات نادراً ما تحتاج واحداً). أضف ترميزاً عند الحدود: معاملات الدوال، أنواع الإرجاع، أشكال API. علّم حيث يلتقي العقد بالعالم غير المعنون. الإفراط في الترميز في كل مكان (سلطة الأنواع)، أو عدم الترميز إطلاقاً (يفقد الحارس). الانضباط: استدل داخلياً، علّم عند الأطراف.

بوابة الوضع الصارم: tsc --strict هو الوضع الوحيد الذي يستحق الاستخدام. يشغّل الفحوص التي تمنع الأخطاء الكلاسيكية — any الضمني، افتراضات التأكيد غير الخالية، عدم وجود فهرسة ضمنية للخصائص. دون strict، يتدهور TS بصمت نحو JS عادي وتضيع قيمته غالباً.

حد زمن التشغيل — أين تتوقف الأنواع

الحدلماذا يهم
الواجهات، الأسماء المستعارة للأنواع، العُمومات، الترميزتمحى 100% — لا تظهر في المخرج أبداً. كلفة زمن تشغيل صفرية.
Enums وأسماء النطاقاتتصدر كائنات زمن تشغيل حقيقية — إنها كود، ليست أنواعاً. فضّل كائن const + اتحادات as const؛ آمنة مع tree-shaking.
ترميز الكلاسات / خصائص الوسائطأنواع منظمة لكن المصدر يعمل كـ JS عادي.
المزينات، emitDecoratorMetadata (تجريبي)تضيف بيانات وصفية لزمن التشغيل — تجنبها إلا في إطار يطلبها (Nest/Angular القديمان مثلاً).

قصة تضييق الأنواع: الاتحاد لا يكون صالحاً في زمن التشغيل حتى تضيّقه. typeof وin وفحوص الاتحاد المميز (if (x.kind === 'a')) تضيّق. قيمة TS هي أن التضييق مُفحص نوعياً وأنت تمضي — اكتب الفحص، والمترجم يضمن الفرع.

type Result =
  | { status: "ok";   data: string[] }
  | { status: "err"; error: string };

function handle(r: Result): number {
  if (r.status === "ok") return r.data.length; // narrows to the ok branch
  return r.error.length;                        // narrows to the err branch
}

ما ليس عليه هذا القسم: ليس درساً كاملاً في TS. إنه اللغة — لبناء المنطق حسب نموذج المشروع، تدرب على الترميز مع أي JS في هذه السلسلة. لأدوات البناء (tsc، tsconfig، JSX أم لا) انظر javascript-the-language أنماط الفشل الأدوات؛ قواعد نظام الأنواع أعلاه هي الجزء الذي يهم دائماً.

TypeScript في الإنتاج — القيمة والمزالق

القيمة: عدم تطابق الأشكال يُكتشف قبل زمن التشغيل، وإعادة البناء دون خوف (الأنواع تعلّم كل موضع استدعاء يكسر التغيير)، وواجهات برمجية موثقة ذاتياً، وذكاء المحرر (الانتقال إلى التعريف، إيجاد المراجع، إعادة تسمية آمنة). كله مجاني في زمن التشغيل لأن الترميز يمحى. القيمة تتراكم مع حجم الفريق — كلما كبرت القاعدة، زاد ما يفعله المترجم.

منظور الخلفية

ما تستخدمه الخلفية من JS: Node.js — حلقة الأحداث + npm + fs/net/http الوحدات. أحادية المسار، I/O غير حاصر، عملية واحدة تتعامل مع آلاف الاتصالات. نفس الحلقة من المتصفح، مزروعة في الخادم.

لهذا النقل تاريخ ميلاد: ابتكر Ryan Dahl العقدة Node وكشفها في 2009 (JSConf أوروبا) — اللحظة التي توقف فيها «لغة واحدة عبر المتصفح والخادم» عن كونها طموحًا وصارت بيئةً تُثبَّت. كل ادعاء cross-stack في هذا المستند هو تِبعة لذلك الحدث.

ما لا يناسب: العمل المكثف CPU (يسد الحلقة)، خيوط حقيقية (خيوط عاملة موجودة لكن ثقيلة)، صندوق حماية ذاكرة (عزلات V8 ليست JVM-grade)، عقود من أدوات الخلفية المؤسسية (JMX، JPA، Spring، تشخيصات .NET)، تجمع المواهب الذي يعرف Java/C# من الجامعة.

زمن تشغيل Node — كيف تتصرف JS فعلاً على خادم

وضّع منظور الخلفية Node مقابل لغات الخلفية الأخرى؛ هذا القسم الفرعي عن زمن التشغيل نفسه — الآليات التي تجعل JS على الخادم تتصرف كما تتصرف. الأطر تأتي وتذهب، لكن هذه الآليات هي الثوابت.

حلقة أحداث الخادم — المراحل وقاعدة المهام الدقيقة

المتصفح وNode يتشاركان عائلة حلقة الأحداث نفسها، لكن الخادم بلا إطار عرض يفرض على الحلقة التنازل بين المعالجات — الحلقة المسدودة تسد كل طلب. الحلقة تعمل بمراحل بترتيب ثابت: المؤقتات (setTimeout/setInterval) ← المعلّقة (معالجات الإدخال/الإخراج المؤجلة) ← الاستقصاء (انتظر الإدخال/الإخراج، شغّل معظم المعالجات) ← الفحص (setImmediate) ← الإغلاق (المقابض المغلقة). بين كل مرحلة — وبعد كل معالج — طابور المهام الدقيقة يُفرَّغ أولاً: queueMicrotask وكل استمرارية Promise.then.

setImmediate(() => console.log("check phase"));
setTimeout(() => console.log("timer phase"), 0);
Promise.resolve().then(() => console.log("microtask"));

// actual order: microtask → timer phase → check phase
// microtasks always jump the queue once the current callback yields

القاعدة التي تهم كود الخادم: استمرارية Promise — حتى التي لم تكتبها — تعمل بين أي معالجين للمستخدم. لذا حالة كل طلب يجب ألا تعتمد أبداً على «الشيء التالي في ملفي يعمل تالياً»؛ الجدولة متداخلة. لهذا حلقة CPU طويلة (for (;;) {}) تجوّع الطلب والكامل أيضاً.

التدفقات — الذاكرة المحدودة هي الفكرة كلها

التدفق مجموعة تُعالج قطعة قطعة، فتبقى الذاكرة محدودة مهما كان الحجم الكلي. fs.createReadStream وطلبات/استجابات HTTP وgzip كلها تدفقات. لماذا يهم على الخادم: المقاربة الساذجة — «اقرأ الجسم كله في سلسلة/مصفوفة ثم أرسل» — تسقفك عند الذاكرة العشوائية وتجعل كل طلب يكلف بما يتناسب مع حمولته الكاملة. المقاربة الاحترافية توجّه: readable.pipe(writable)، حيث الضغط الخلفي يوقف المصدر حين يكون المصب بطيئاً، فتنزيل 2 جيجابايت واستجابة 2 كيلوبايت يستخدمان الذاكرة المحدودة نفسها.

// bounded memory: stream file → HTTP response, backpressure managed by pipe
const src = createReadStream(REPORT_FILE);
src.pipe(res);

النمط المضاد الذي يجب نسيانه: «خزّن الكل ثم اكتب». إذا لجأت إلى readFileSync/resp.arrayBuffer() لمعالجة حمولة لن تبحث فيها إلى الخلف، فأنت تتخلى عن ضمان الذاكرة الثابتة المجاني الذي وُجدت التدفقات لتمنحه.

V8 وlibuv — الثنائي تحت الغطاء

Node هي V8 (محرك JS: تحليل ← كود مُجمَّع JIT عبر TurboFan/Ignition، أكوام مُجمَّعة قمامةً) زائد libuv (مكتبة C تقدم حلقة الأحداث ومراحل المؤقتات وتجمع خيوط صغير لنظام التشغيل للعمل الحاجب مثل fs وDNS والتشفير). النموذج الذهني الذي يفسر تقريباً كل «لماذا فعلت Node هذا؟»:

  • الإدخال/الإخراج غير المتزامن لا يستخدم الخيوط. الحالة الافتراضية: يبدأ استدعاء النظام، تنتظر الحلقة، ويشتعل المعالج حين تكون النتيجة جاهزة.
  • العمل الحاجب ما زال يستخدم الخيوط. fs/التشفير/DNS تعمل على تجمع افتراضي من os.cpus().length (≥4) خيوط. استنزفه فتبدأ الطلبات في الاصطفاف.
  • JS النقي المرتبط بوحدة المعالجة (تحليل، حلقات تجزئة، JSON لكائنات ضخمة، ترميز الصور) يتجاوز libuv كلياً — يعمل على الخيط الرئيسي ويسد الحلقة، نقطة.

المخرج هو worker_threads — عزل V8 ثانٍ بكومة وحلقة أحداث خاصتين به، يتواصل بتمرير الرسائل (لا ذاكرة مشتركة بأعراق بيانات). أطلق واحداً لكل مهمة CPU ثقيلة. ملاحظتان قاسيتان: كل عامل يحمل كلفة V8 خاصة تبلغ ~30–60 ميجابايت، والعمال لا يشاركون حالة الذاكرة داخل العملية — كل ما يحتاجه الطرفان يُنسخ أو يُخزّن خارجياً.

النماذج الذهنية — كيف يعمل التفكير عبر الأكوام فعلاً

حين ينتقل المطورون بين الأكوام (واجهة أمامية، خلفية، جوّال، مدمج، ذكاء اصطناعي) لا يتعلمون صيغة جديدة فقط — يبدلون نماذج ذهنية. لكل كومة تجريد أولي يحدد ما يعنيه «سهل» و«صعب». نمط الكود نفسه الاصطلاحي في كومة هو نمط مضاد في أخرى.

الكومةالتجريد الأوليماذا تعني «الحالة»ماذا يعني «الأداء»ماذا يعني «الصحيح»
الواجهة الأمامية (المتصفح) شجرة DOM + حلقة أحداث تعيش في المستند؛ التحويرات تشعل إعادة الطلاء زمن العرض، الاهتزاز، حجم الحزمة، الكمون المدرَك نتيجة واحدة عبر المتصفحات؛ دلالات وصول صحيحة
الخلفية (Node) طلب/استجابة + إدخال/إخراج غير متزامن لكل طلب أو مشتركة عبر قاعدة البيانات/التخزين المؤقت؛ التحويرات تمر عبر حدود صريحة الإنتاجية، كمون p99، الذاكرة تحت الحمل التطابق (idempotency)، انتشار أخطاء صحيح، لا تسرب موارد
الجوّال (RN/أصلي) جسر واجهة أصلية + جهاز مقيد هجين: مخزن في جهة JS + مرآة واجهة أصلية ميزانية الإطار (16ms)، ضغط الذاكرة، البدء البارد تجربة واحدة دون اتصال، لا إيماءات مكسورة، لا اهتزاز
المدمج (MCU) سجلات العتاد + حلقة مقاطعة حالة عامة، غالباً بلا كومة؛ كل شيء مخزن مؤقت ثابت البايتات، الدورات، الواط؛ لا توقفات GC مسموحة توقيت حتمي؛ لا تفوّت مقاطعة؛ لا تتعطل أبداً
الذكاء الاصطناعي / البيانات متوترات + رسم حسابي أوزان النموذج؛ «حالة» العملية الجارية هي تاريخ الحساب FLOPs، عرض نطاق الذاكرة، استغلال GPU إعادة إنتاج رقمية؛ الإجابة صحيحة تقريباً بخطأ محدود

التحول: أصعب جزء في العمل متعدد اللغات ليس الصيغة — بل ملاحظة أي نموذج ذهني يراوح مكانه. مطور خلفية يقرأ كود واجهة سيعامل DOM كحالة؛ مطور واجهة يقرأ كود خلفية سيعامل الطلبات كأنها لحظية؛ مطور مدمج سيفزع من جمع القمامة. لا أحد منهم مخطئ — إنهم يحملون النموذج الصحيح لكومة مختلفة. المهارة هي المهارة الفوقية في تبديل النماذج عند الدخول.

الحافة الخاصة بـ JS: لأن JS تعيش في أكوام كثيرة، نفس الصيغة (await، Promise.all، معالج حدث) يجب أن تعمل في كل منها. لهذا بقيت اللغة صغيرة لكن مرنة — كل كومة تعيد استخدام البدائيات نفسها. الثمن أن كود JS في البرية غالباً يبدو متشابهاً عبر الأكوام لكنه يعني أشياء مختلفة حسب النموذج في رأس المطور.

منظور الذكاء الاصطناعي / علم البيانات

ما يستخدمه AI من JS: تقريباً لا شيء في طبقة النموذج (PyTorch/JAX/CUDA ليست في JS). كل شيء في طبقة التطبيق: Next.js + Vercel AI SDK + fetch لـ APIs النماذج، LangChain.js، Transformers.js (WASM)، TensorFlow.js (WebGL/WASM). JS مركبة توصيل للنماذج المدربة في مكان آخر.

خريطة الرافعة (Leverage Map) — أين تتركز كتلة ممارسة cross-stack

تسعة عشر قسمًا على ست حزم ليست متساوية الحمل. المستويات الثلاثة أدناه مشتقة من سجلات النسب الموثقة لهذا المستند نفسه — إعلان TypeScript 2012 في مايكروسوفت، وظهور Node 2009 في JSConf، والفصل الثاني Deno 2018، ومحرك JerryScript لصنف IoT — إضافة إلى جدولَي الاختيار والهجرة، لا من الانطباعات. القاعدة العاملة: المستوى الأول ينتقل معك إلى كل حزمة تدخلها؛ والمستوى الثاني يدخل حين تظهر حزمته؛ والمستوى الثالث عمقٌ لحين تصبح حزمةٌ دارك.

منظور "الآخر": Edge، Serverless، أدوات البناء

حيث JS الافتراضي بالكامل لأن المضيف JS: Cloudflare Workers، Vercel Edge Functions، Deno Deploy، Bun، esbuild/rolldown/Vite (مكتوبة Go/Rust لكن تدفع نظام JS البيئي). وقت تشغيل Edge اختار JS لأن V8 موجود بالفعل، صندوق حماية الأمان موجود بالفعل، والبدء البارد أهم من الأداء المستقر.

منافس: WASM على الحافة. Cloudflare تدعم مكونات WASM؛ Fastly Compute@Edge واصف WASM أولاً. لكن WASM ما زال يحتاج غراء JS لـ DOM/HTTP في المتصفح، والحافة تتقارب على نفس APIs (WinterCG). هنا JS لا منافس حقيقي للغة — WASM شريك، كما في المتصفح.

اختيار كومة

النمط (نمط انقلاب القيود) يفسر الفائزين بعد وقوع الأمر؛ هذه نسخة التطلع — كيف تختار كومة اليوم. نفس القاعدة، مطبقة أولاً: حدد القيد المسيطر، ثم اللغة التي يطابق رهان تصميمها. «أي لغة أفضل؟» سؤال خاطئ. «أي قيد يهيمن، ومن راهن عليه؟» هو السؤال الذي يجيب.

العكس صحيح أيضاً: عندما لا ينعكس القيد، التمديد يربح. Java مدت بناء جملة C++ لكن راهنت على JVM. C# مدت بناء جملة Java لكن راهنت على CLR. TypeScript تمد بناء جملة JS لكن تتبخر. Kotlin تمد هدف بايت كود JVM لكن تستبدل اللغة. رهان المنصة هو ما يتغير؛ البناء جملة قابلة للتفاوض.

قيد JS الأصلي: لغة برمجية نصية لـ Netscape Navigator 2.0، محمّلة عبر مودم 28k، مكتوبة في 10 أيام. ذلك القيد ذهب. القيود الجديدة (فرق كبيرة، جوّال، حافة، توصيل AI) كل منها ولّد استجابته — TS، RN/Flutter، Workers، Vercel AI SDK. لا أحد استبدل JS لأن لا أحد قلب قيد المتصفح. المتصفح لا يزال يشغل JS فقط (و WASM). ما دام هذا صحيحاً، JS تبقى في المركز والمنافسون يديرون حولها.

مفردات البحث — ما اسم هذه الأشياء

لا يمكنك البحث عن مشكلة لا تعرف اسمها. مصطلحات الفن التي تستخدمها هذه الوثيقة، وكل واحدة منها مفتاح بحث عامل:

  • التنضيج التدريجي / التنضيد البنيوي — خاصيتا التصميم الأساسيتان لـ TS. ابحث "TypeScript structural typing".
  • محو الأنواع — لماذا تختفي الأنواع عند التشغيل. ابحث "TypeScript type erasure runtime".
  • الضغط العكسي (Backpressure) — التدفقات توقف مصدرها حين يكون المصرّف بطيئاً. ابحث "Node stream backpressure".
  • BFF (خلفية من أجل الواجهة) — طبقة JS أمام نواة الخلفية. ابحث "backend for frontend pattern".
  • شجرة الخنق (Strangler fig) — هجرة تدريجية حول نواة قديمة. ابحث "strangler fig migration".
  • GIL — قفل بايثون العام؛ جدار الأداء في مسار الذكاء الاصطناعي. ابحث "Python GIL explained".
  • FFI — واجهة الدوال الأجنبية؛ كيف تستدعي اللغات بعضها أصلياً. ابحث "FFI napi-rs".
  • إشراف BEAM — نموذج تحمّل الأخطاء في Erlang/Elixir. ابحث "BEAM let it crash supervision".
  • WinterCG — جهد توحيد واجهات أوقات التشغيل الطرفية. ابحث "WinterCG runtime keys".
  • CRDT — نوع البيانات المنسوخ بلا تعارض وراء التحرير التعاوني. ابحث "CRDT vs OT collaborative editing".
