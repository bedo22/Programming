بناء أدوات سطر الأوامر وتطبيقات الطرفية

لمن: المطوّر الذي يستخدم الطرفية يوميًا ويريد أن يبني من أجلها — محللات الوسائط، والموجهات التفاعلية، ومؤشرات التقدم، وأدوات CLI الوكلاء الذكية التي تعيد تشكيل هذا الشكل.

اللغة: العربية · English

أين يقع هذا الدليل. وثيقة الركيزة الطرفية والنشر (Terminal & Deployment Substrate) تعلّمك أن تستخدم الطرفية — التنقل، والأنابيب، وSSH، والتصحيح. هذه الوثيقة تعلّمك أن تبني من أجلها. الفرق حدّ منصة: لا DOM، ولا واجهات برمجة متصفح، وTTY بدل البكسلات، وتدفقات بدل الأحداث. أنت تعرف كيف تستخدم الطرفية وكيف تبني خوادم ويب بـ Node؛ هذا هو الوسط المفقود — Node في عملية طرفية.

كيف تستخدم هذه الوثيقة

ترتيب القراءة: اقرأ قسم التعريف (ما هي أداة CLI وما ليست إياه — المفردات مهمة)، ثم قسم البنية لترى الشكل الذي تتشاركه كل أداة CLI، ثم قسم الإدخال/الإخراج الطرفي لآليات المنصة. قسم أدوات CLI الوكلاء الذكية هو المردود إن كنت تستخدم هذه الأدوات يوميًا. وحين تكون أداة CLI حقيقية أمامك، فإن قسم قراءة قاعدة كود CLI هو الخريطة. روابط متقاطعة:

  • استخدام الطرفية (الشرط المسبق): الركيزة الطرفية والنشر.
  • بيئة التشغيل (Node والتدفقات وحلقة الأحداث): جافاسكريبت عبر المكدسات §٣ب — كيف تتصرف JS فعلاً على خادم/أداة CLI.
  • الخوادم (منصة الأشقاء): هندسة الخلفية.
  • المساهمة في أداة CLI بعد أن تعرف كيف تقرأ واحدة: المصدر المفتوح.
  • مرجع: المصطلحات.

إن أردت يومًا بناء أداة لأتمتة سير عملك — أو تساءلت كيف تعمل Claude Code وCodex فعلاً — فهذه هي الخريطة. بنية واحدة، ونموذج منصة واحد، والآليات المحددة للصيغ التفاعلية وصيغ الوكلاء الذكية.

التعريف — ما هي أداة CLI وما ليست إياه

تطبيق سطر الأوامر برنامج واجهته هي الطرفية: يقرأ الوسائط والإدخال القياسي، ويكتب إلى المخرجات القياسية والخطأ القياسي، ويخرج برمز حالة. للعائلة مفردات تستحق الضبط الدقيق:

المصطلحما هومثال
CLIبرنامج تُدار به الوسائط والخيارات والإدخال القياسي؛ ينفّذ أمرًا ويخرجgit status, npm install
TUIواجهة تفاعلية كاملة الشاشة مرسومة في الطرفية (مفاتيح، لوحات، إعادة رسم)htop, lazygit
REPLحلقة القراءة–التقييم–الطباعة: جلسة تفاعلية مستمرةnode وحدها، صدفة قاعدة بيانات، أداة وكيل
GUIبكسلات ونوافذ — الطرفية مجرد مضيفVS Code، أي تطبيق سطح مكتب

الطرفية كمنصة: لعملية الطرفية ثلاثة أنابيب (stdin، stdout، stderr)، وبيئة، ووسائط، ورمز إرجاع. وعندما تكون موصولة بطرفية، يكون لها أيضًا TTY — الجهاز الذي يوصّل ضغطات مفاتيحك ويفهم رموز الهروب للألوان وحركة المؤشر. كل ما هو تفاعلي في الطرفية هو محادثة مع ذلك الـTTY.

لماذا تهيمن TypeScript/Node على أدوات CLI الحديثة: توفر Node process.argv وprocess.stdin/stdout/stderr ونموذج التدفقات مدمجًا؛ ويمنحك نظام npm البيئي كل طبقة تسهيل؛ والأدوات (tsup، esbuild) تُجمِّع في ملف واحد قابل للتوزيع. أدوات CLI الوكلاء الذكية المهيمنة — Claude Code وCodex وAider وContinue — مبنية كلها بهذه الطريقة، ولهذا هذا الدليل متمركز حول Node.

التاريخ — من الأوامر الدفعية إلى حلقات الوكلاء

أداة CLI أقدم من الواجهة الرسومية وطالتها عمرًا. أسست يونكس (سبعينيات القرن العشرين) الشكل — أدوات صغيرة، وأنابيب، ونصًا صريحًا — وفلسفة «افعل شيئًا واحدًا جيدًا» التي ما زالت تحكم تصميم CLI. دفع عصر الواجهات الرسومية الطرفية إلى الهامش، لكن المطوّرين أبقوها كأداة القوة. ثورتان حديثتان أعادتا تشكيل الصيغة: النظام البيئي لأدوات CLI في Node.js (محللات الوسائط، والموجهات، وInk) جعل بناء أدوات CLI مصقولة رخيصًا، وأداة CLI الوكيل الذكية (2023–) حوّلت الطرفية إلى واجهة تفويض العمل — REPL يستدعي الأدوات، ويبث الرموز، ويطلب الإذن. لم تمت أداة CLI؛ أصبحت المنصة لأحدث نوع من البرمجيات.

النظرية الأساسية — نموذج الأنابيب الثلاثة

كل أداة CLI تحويلٌ على ثلاثة تدفقات، ويكاد كل قرار تصميمي يتبع من ذلك:

  • stdin هو قناة الإدخال. تأتي الوسائط والخيارات من سطر الأوامر؛ ويمكن أيضًا أن تُدفق البيانات عبر الأنبوب. أداة CLI جيدة البناء تقرأ البيانات من أيٍّ من الاثنين — «تعمل مع ملف أو أنبوب» خاصية تصميمية، لا مصادفة.
  • stdout هو قناة البيانات. وهو للمخرجات القابلة للبرمجة — ما ستستهلكه أداة أخرى. إذا كان آلة قد تحلّله، أبقِه نظيفًا: نصًا صريحًا أو JSON، بلا ضجيج تقدم، وبلا ألوان عند التوصيل بأنبوب.
  • stderr هو قناة الإنسان. الأخطاء والتحذيرات والسجلات والتقدم. هو منفصل كي يبقى تمرير stdout نظيفًا — ولهذا «السجلات تذهب إلى stderr» قاعدة، لا اختيار أسلوب.
  • رمز الخروج هو العقد. 0 يعني النجاح؛ والرمز غير الصفري هو إشارة الخطأ القابلة للقراءة آليًا، طريقة CLI في إرجاع قيمة منطقية إلى مستدعيها.

يتبع الانضباط مباشرة: قرر ما هو بيانات (stdout) وما هو سرد (stderr) قبل أن تكتب سطرًا واحدًا، وستبقى أداة CLI قابلة للتركيب مع كل شيء آخر في الطرفية.

البنية — الشكل الذي تتشاركه كل أداة CLI

من سكربت صغير إلى Claude Code، يظهر الهيكل العظمي نفسه:

  1. نقطة الدخول. سطر shebang (#!/usr/bin/env node) إضافةً إلى حقل bin في package.json يربطان اسم أمر بملف JS. وظيفة ذلك الملف الوحيدة هي استدعاء الموجّه.
  2. تحليل الوسائط. Commander أو Yargs أو oclif أو clipanion يحوّلون process.argv إلى خيارات مهيكلة. هذا يتكفل بالخيارات (--format json)، والوسائط الموضعية، و--help مجانًا.
  3. توجيه الأوامر. يوزع المحلل إلى معالج أمر فرعي — git add وgit commit مساران مختلفان، لا برنامج واحد. يستقبل كل معالج الخيارات المحللة.
  4. الإعداد. سُلَّم الإعداد: الخيارات ← متغيرات البيئة ← ملف الإعداد ← القيم الافتراضية. اقرأ فقط بقدر ما يحتاجه الأمر.
  5. التنفيذ والمخرجات. يؤدي المعالج عمله، ويكتب البيانات إلى stdout والسرد إلى stderr، ويعيد رمز خروج. تُلتقط الأخطاء في المستوى الأعلى ليخرج البرنامج بنظافة برمز غير صفري.
#!/usr/bin/env node
// package.json "bin": { "todo": "./bin/todo.js" }
import { Command } from "commander";
const program = new Command();
program
  .name("todo")
  .description("A tiny task list")
  .argument("<action>", "add | list | done | delete")
  .option("--json", "machine-readable output")
  .action(async (action, opts) => {
    try {
      const result = await handle(action, opts);   // route
      process.stdout.write(format(result, opts));  // data → stdout
    } catch (err) {
      process.stderr.write(String(err));           // narrative → stderr
      process.exit(1);                              // failure code
    }
  });
program.parse();

رموز الخروج مفردات صغيرة، لا قيمة منطقية واحدة. تتحكم في 0 و1؛ وتتحكم الصدفة في بضعة أخرى يمكن لأداة CLI أن ترثها أو تعيّنها:

الرمزالمعنىمن يعيّنه
0النجاحأداة CLI الخاصة بك، عمدًا
1خطأ عامأداة CLI الخاصة بك — الافتراضي لـ«شيء فشل»
2خطأ استخدام (وسائط سيئة)محلل الوسائط لديك (يفعلها Commander)
126 / 127غير قابل للتنفيذ / الأمر غير موجودالصدفة، عند إطلاق عمليات فرعية
128 + Nقُتل بالإشارة Nنظام التشغيل، عندما تنهي إشارةٌ العملية

رسائل الخطأ تتبع انضباط الأنابيب نفسه للمخرجات: سطر واحد إلى stderr يسمّي الفشل وتلميح «ماذا تفعل بعد ذلك» («Error: no such file — run "todo add" first»). لا تكتب أخطاء إلى stdout أبدًا، وأبقِ السطر الواحد مستقرًا — السكربت الذي يفحص «هل فشل؟» يبحث في رمز الخروج، أما الإنسان الذي يصطدم بخطأ فيريد الإجراء التالي، لا تتبع الاستدعاءات.

النمط — دخول ← تحليل ← توجيه ← إعداد ← تنفيذ ← مخرجات ← خروج — هو نفسه لملف أداة واحدة أو أداة CLI كبيرة. قراءة أداة CLI حقيقية تعني تتبع هذا العمود الفقري.

القاعدة الواحدة التي تربطها كلها: كل أثر تفاعلي (لون، مؤشر دوران، موجه، TUI) يعمل عبر TTY ويجب تخطيه أو خفضه عندما يكون isTTY خاطئًا. أداة CLI ترمّز الألوان حرفيًا تكسر الأنابيب والسجلات. المكتبات أعلاه كلها تتعامل مع هذا — ولهذا تستخدمها بدلاً من كتابة رموز الهروب يدويًا.

الإشارات — طريقة نظام التشغيل في مقاطعتك. ثلاث تهم مؤلفي CLI: SIGINT (Ctrl+C — المستخدم يريد التوقف)، SIGTERM (kill/الإيقاف — النظام يريد التوقف)، وSIGPIPE (قارئ مخرجاتك أغلق الأنبوب — الطرف المصب مات، فتوقف عن الكتابة). الأوليان هما خطاف الإيقاف اللطيف: فرّغ المخازن المؤقتة، وأغلق الملفات/الاتصالات، واحفظ الحالة، ثم اخرج. الثالث هو الذي يقتل الأدوات الساذجة بصمت — أداة CLI تكتب إلى أنبوب مغلق تحصل على إشارة أنبوب مكسور، والسلوك الاحترافي هو التوقف بنظافة لا الانهيار بضجيج.

process.on("SIGINT", () => {
  process.stderr.write("\nInterrupted — saving state...\n");
  saveState();                 // flush, close, persist
  process.exit(0);             // deliberate, not a crash
});

التكامل مع الصدفة — ما تدين به أداة CLI لمضيفها. عرفانان يفصلان الأداة عن المواطن: الإكمال (دع الصدفة تقترح خياراتك وأوامرك الفرعية — يولّد Commander وoclif سكربت الإكمال لـ bash/zsh/fish، فشحن todo completion لا يكلف شيئًا) والقيم الافتراضية الصديقة للأنابيب (حين لا يكون stdout طرفية، أخرج نصًا صريحًا أو JSON لا نثرًا ملونًا — بوابة isTTY تغطي هذا أصلًا). النصف الخاص بالمستخدم — إكمال التبويب، والتاريخ، والأسماء المستعارة — يعيش في الركيزة الطرفية والنشر؛ وظيفتك هي جانب التوليد.

سطح الأمان الخاص بأدوات CLI. أداة CLI آمنة بقدر أمان طريقة استدعائها وتخزينها: فضّل execFile/spawn بمصفوفة وسائط على exec بدمج سلاسل (لا تبني أمر صدفة من إدخال مستخدم أبدًا)؛ لا تسجّل متغيرات البيئة أو الأسرار أبدًا؛ وامنح ملفات الإعداد التي تحمل أسرارًا chmod 600 (قراءة/كتابة للمالك فقط). نموذج التهديدات الكامل — ما يمكن للمهاجم الوصول إليه فعلاً عبر أداتك — في الأمن ونمذجة التهديدات؛ هذه العادات الثلاث هي شريحة CLI منه.

كيف تعمل أدوات CLI الوكلاء الذكية — صيغة REPL مع أدوات

Claude Code وCodex وAider وContinue تتشارك بنية تمدّد الشكل الكلاسيكي لأداة CLI بحلقة وكيل. كل أداة CLI ذكية هي، في العمق، REPL حيث تستطيع خطوة «التقييم» استدعاء الأدوات:

LOOP:
  read   → get the user's next instruction (typed or streamed)
  plan   → the model decides what to do, possibly calling tools
  tool   → execute a tool call (read file, run command, edit code)
  stream → stream the model's response tokens to the TTY
  permit → ask the user before destructive or expensive actions
  repeat → persist history, then loop

حد الأذونات هو سطح الأمان. كل ما لا يفعله إنسان بلا تفكير — حذف ملفات، تثبيت حزم، تشغيل أوامر عشوائية، إنفاق مال — يجب أن يسأل عنه الوكيل. هذا أهم قرار معماري في الصيغة كلها، والأكثر استحقاقًا للقراءة بعناية في قاعدة كود حقيقية. التنفيذ سُلَّم بسيط: أدوات مصنّفة بالمخاطر، والحد مرسوم بين «اسمح تلقائيًا» و«اسأل دائمًا».

قراءة قاعدة كود أداة CLI — عين المساهم

لقراءة أي أداة CLI بسرعة، امشِ على عمودها الفقري: bin/ (الدخول) ← src/commands/ أو الموجّه (التوجيه) ← src/utils/lib (العمل الحقيقي) ← الاختبارات. بالتحديد:

  1. ابدأ بحقل bin في package.json لتجد ملف الدخول، ثم إعداد محلل الوسائط — ذلك يسمّي كل أمر وخيار تدعمه الأداة.
  2. تتبّع أمرًا واحدًا من النهاية إلى النهاية من معالج مساره حتى المخرجات — هذا يعلّمك عادات المخرجات في المشروع (أين تُكتب stdout/stderr، وكيف تخرج الأخطاء).
  3. جد نقاط التفاعل — فحوصات TTY، والموجهات، واستخدام مؤشرات الدوران — لترى أين تكون الأداة «تفاعلية» وأين لا تكون.
  4. لإضافة أمر أو خيار: سجّله في المحلل، واكتب المعالج، وأضف اختبارًا. اتبع ملف الأمر القائم كقالب — النمط يُكرَّر، لا يُختلق.
  5. الاختبارات سلوك أولاً: معظم مجموعات اختبار CLI تشغّل الثنائي (أو موجّهه) بوسائط تجريبية وتؤكد على stdout ورمز الخروج والملفات المكتوبة. اختبر بنفس الطريقة التي ستُستخدم بها ميزتك.

لأداة CLI وكيل ذكية، أضف المشي نفسه لكن من أجل الحلقة: جد أين تُوزَّع طلبات استدعاء الأدوات النموذجية، وأين يقع فحص الأذونات، وأين سيُسجَّل عندها أداة جديدة. خط التماس التوسعة عادة صغير وحسن التسمية — الأدوات هي الميزة، فتُبقى سهلة الإضافة. العملية الاجتماعية الكاملة لتحويل قراءة إلى مساهمة مدمجة في المصدر المفتوح.

مثال عملي — أداة CLI لقائمة مهام، من الصفر إلى النشر

Goal: a "todo" CLI with add / list / done / delete, colored output,
      then an interactive mode, then publish it.

1 · Skeleton (parse + route + exit):
     bin/todo.js with the Commander setup from the Architecture
     section — a single  argument and handlers that return.

2 · Add real behavior (data → stdout, narrative → stderr):
     storage = a JSON file in ~/.todo.json
     add "Buy milk"      → append, write file, "Added" to stderr
     list                → print the items to stdout (clean, no color)
     done 1              → mark item 1 done, write file
     delete 1            → remove item 1
     errors (missing file, bad id) → message to stderr, exit 1.

3 · Add color, but TTY-gated:
     list --json  → plain JSON on stdout (for pipelines)
     list         → colored when process.stdout.isTTY, plain otherwise
     (this is the "three pipes" principle in practice)

4 · Add an interactive mode:
     todo add         → an @clack/prompts text input instead of an arg
     todo done        → a select prompt listing open items
     still TTY-gated — a piped "done" keeps the argument path.

5 · Add tests (behavior-first):
     run the router with fixture args; assert stdout content and
     exit code; use a temp HOME so the JSON file doesn't touch yours.

6 · Publish:
     npm publish → now "npx todo add Buy milk" works for anyone.
     Cross-platform check: file path via path.join, not string concat.

الهيكل العظمي نفسه، مكبّرًا بـ TUI (Ink) وحلقة وكيل (استدعاء أدوات + أذونات)، هو Claude Code. أداة CLI لقائمة المهام ليست نسخة لعبة من تلك البنية — إنها البنية نفسها عند الحد الأدنى من الحجم.

المستقبل — الطرفية كواجهة الوكلاء

أعادت أداة CLI الوكيل الذكية الاعتبار للطرفية، والاتجاه يتضاعف: حلقات الوكلاء تصبح الطريقة الافتراضية التي يفوض بها المطورون العمل، وأداة CLI هي الواجهة الطبيعية لأنها قابلة للبرمجة النصية، والفحص، والتركيب. ثلاثة تحولات تتبع. أولًا، نظام الأذونات يصبح المنتج — كلما اكتسب الوكلاء قوة أكبر، صارت جودة حد الاسمح/اسأل/ارفض هي ما يثق به المستخدمون. ثانيًا، يجب أن تكون أدوات CLI قابلة للقراءة من الوكلاء — الأدوات التي تُخرج بيانات مهيكلة (JSON على stdout، وأخطاء نظيفة) هي التي يستطيع الوكلاء وخطوط الأنابيب استخدامها، وهذا هو الانضباط نفسه الذي تعلّمه هذه الوثيقة. ثالثًا، يصبح بناء واحدة أيسر وصولًا — الذكاء الاصطناعي نفسه الذي جعل أدوات CLI الوكلاء شائعة يمكنه أن يهيكل أداة CLI من موجه، ما يخفض حاجز الدخول ويرفع السقف: الحِرفة الآن في البنية وحد الأمان، لا في الكتابة.

الملخص — قائمة التحقق الذهنية الكاملة

اطبع هذه. إنها الوثيقة كلها في اثني عشر سطرًا:

#السطر
1كل أداة CLI ثلاثة أنابيب + رمز خروج: البيانات ← stdout، السرد ← stderr، 0 = النجاح.
2البنية دائمًا دخول ← تحليل ← توجيه ← إعداد ← تنفيذ ← مخرجات ← خروج.
3رموز الخروج مفردات: 0 نجاح، 1 عام، 2 استخدام؛ الأخطاء إلى stderr، لا stdout أبدًا.
4تعامل مع الإشارات: SIGINT/SIGTERM تفرّغ وتخرج بنظافة؛ SIGPIPE يعني توقف عن الكتابة، لا تنهار.
5الميزات التفاعلية تعيش على TTY — اكشفه (isTTY) واخفض الأداء بدونه بلطف.
6استخدم المكتبات للألوان والموجهات ومؤشرات الدوران؛ لا تكتب رموز الهروب يدويًا أبدًا.
7الإعداد سُلَّم: الخيارات تلغي متغيرات البيئة التي تلغي ملف الإعداد الذي يلغي القيم الافتراضية.
8شحّن الإكمال؛ عامل الصدفة كمضيفك، لا فكرة لاحقة.
9الأمان: execFile على exec، ولا تسجّل الأسرار أبدًا، وchmod 600 للإعدادات التي تحملها.
10عبر المنصات: path.join، os.EOL، مصفوفات وسائط لا سلاسل صدفة.
11أدوات CLI الوكلاء الذكية REPLs بأدوات: اقرأ ← خطط ← استدعِ أداة ← بثّ ← اسمح ← كرّر.
12حد الأذونات هو سطح الأمان لأي أداة CLI وكيل.

المصادر الأولية

  1. Raymond, Eric — The Art of Unix Programming — «قاعدة الصمت» وفلسفة التصميم التي ينحدر منها نموذج الأنابيب الثلاثة في هذه الوثيقة.
  2. توثيق Node.js — process (argv, stdin/stdout/stderr, exit) — البدائيات المنصاتية التي تُبنى عليها كل أداة CLI.
  3. توثيق Node.js — Streams — نموذج الإدخال/الإخراج للطرفية.
  4. Commander.js — التوثيق — مكتبة تحليل الوسائط المهيمنة، وتعرض نمط التحليل ← التوجيه عمليًا.
  5. Ink — React للطرفية — نموذج TUI فوق تدفقات Node.

اسأل معلمك

ثلاث متابعات لتعميق هذا:

  • «امشِ معي عبر قاعدة كود أداة CLI وكيل ذكية (Claude Code أو ما يشابهها) من مدخل bin إلى حلقة استدعاء الأدوات — أين يقع حد الأذونات تحديدًا؟»
  • «خذ أداة CLI لقائمة المهام في المثال العملي وأرني ما الذي يتغير عند إضافة TUI بـ Ink، أو حلقة وكيل باستدعاء أدوات.»
  • «أي من مهاراتي الحالية ينتقل إلى بناء أداة CLI، وما أصغر أداة حقيقية يجب أن أبنيها أولًا لأثبت النمط؟»
