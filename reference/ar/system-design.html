التصميم المعماري — كيف تتعامل المعمارية بما لا يستطيع الكود وحدَه

انضباط تقرير كيف يتلاءم الحل على النطاق الواسع — من الخدمات وتدفقات البيانات إلى حدود المكونات وعقود واجهات البرمجة. وثائق شقيقة: التفكير التصميمي (طبقة المنتج السابقة)، كيف يفكر المطورون (حلقة التنفيذ التالية)، تصميم API (طبقة العقد التي تجعل الحدود قابلة للاستدعاء)، تصميم واجهات المستخدم وتجربة المستخدم والويب (طبقة العرض التي تجعل الحالة مقروءة)، HTML و CSS (ركيزة المنصة التي تعمل عليها استراتيجية العرض)، JavaScript عبر المكدسات (عواقب مستوى اللغة).

لمن هذه الوثيقة: مهندسون قراراتهم يجب أن تعيش أطول من ميزة واحدة — من يختار حدود الخدمات، أو ملكية البيانات، أو نماذج الاتساق، أو استراتيجية التوسع. قرارات هنا مكلفة التراجع؛ اقرأها قبل أن تبدأ حلقة المكوّنات.

لماذا هذا المستند منفصل

"البرمجة الحقيقية في التصميم المعماري." هذا المستند يلتقط ما يعنيه ذلك. التصميم المعماري ليس اكتشاف منتج التفكير التصميمي، ولا حلقة مكونات المطور. إنه الطبقة المعمارية التي تترجم مشكلة معتمدة إلى حل منظم — معرّفة الخدمات، ملكية البيانات، حدود الاتساق، أنماط الفشل، والدرزات حيث تلتقي المكونات. تعمل على مستويين في وقت واحد: معماري (كلي: الخدمات، الأحداث، التوسع) ومكوني (دقيق: سياقات محددة، عقود واجهات برمجة، حدود الثقة). كلاهما تصميم معماري؛ لا يكتمل أحدهما دون الآخر.

كيف تستخدم هذا المستند

ترتيب القراءة: مستقل. روابط تقاطعية:

  • أعلى إلى التفكير التصميمي — التصميم المعماري يستلم مشكلة معتمدة ("ماذا نبني") ويقرر النهج الهيكلي ("كيف يتلاءم").
  • أسفل إلى كيف يفكر المطورون عند بناء ميزة واجهة أمامية — التصميم المعماري يحدد حدود المكونات وعقود البيانات التي تنفذ حلقة المطور داخلها.
  • شقيق لـ تصميم API — التصميم المعماري يقرر حدود الخدمات وملكية البيانات؛ تصميم API يمثّل تلك الحدود كعقود قابلة للاستدعاء.
  • شقيق لـ تصميم واجهات المستخدم وتجربة المستخدم والويب — التصميم المعماري يقيد استراتيجية العرض وميزانيات زمن الاستجابة؛ تصميم UI/UX يقرر كيف ترتبط حالات السلك بحالات الإنسان.

التعريف — ما التصميم المعماري هو وما ليس

ما هو

التصميم المعماري هو النشاط المنضبط لـ هيكلة حل برمجي عبر حدود الثقة والاتساق والتوسع. ينتج قرارات — لا كود — تحدد:

  • التفكيك — ما الوحدات القابلة للنشر والتوسع والعزل المستقلة؟ (خدمات، دوال، وحدات)
  • ملكية البيانات — أي وحدة هي مصدر الحقيقة لكل قطعة حالة؟
  • عقود الاتصال — كيف تتبادل الوحدات المعلومات؟ (RPC متزامن، أحداث غير متزامنة، مخططات الرسائل)
  • نماذج الاتساق — ما الضمانات التي يقدمها النظام حول القراءات والكتابات؟ (قوي، نهائي، سببي، قراءة كتاباتك)
  • مجالات الفشل — ما الذي يفشل بشكل مستقل؟ كيف يتدهور النظام؟ (قواطع دوائر، إعادة محاولات، بدائل، ملاحم)
  • السعة والتوسع — ما أشكال الحمل؟ أين الاختناقات؟ كيف نضيف سعة؟

هذه القرارات مكلفة التغيير لاحقًا. هذه الميزة المميزة: قرارات التصميم المعماري لها تكلفة عكس عالية. قرارات حلقة المكونات (أسماء المتغيرات، استخلاص دوال) رخيصة التغيير. قرارات التصميم المعماري (حدود الخدمة، ملكية البيانات) ليست كذلك.

التطور — النماذج عبر عدسة واحدة

أنتج قيد كل حقبة تصميمها المعماري. عندما انقلب القيد، انقلبت رهانات التصميم معه — نفس النمط الموثق في جافاسكريبت عبر المكدسات.

الحقبةالقيد الأساسيالتصميم المعماري الذي أنتجتهلماذا تحدى
أحادي (Monolith) (سبعينيات–تسعينيات) تكلفة العتاد، بساطة النشر عملية واحدة، قاعدة بيانات مشتركة، كود نمطي توسع الفريق: تعارضات الدمج، تنسيق النشر، مجال فشل وحيد
طبقي / N-tier (تسعينيات–ألفينيات) فصل الاهتمامات، إعادة الاستخدام طبقات العرض / الأعمال / البيانات الطبقات صارت متسللة؛ التغييرات تعبر كل الطبقات؛ قاعدة البيانات صارت الاختناق
عميل/خادم (تسعينيات) عميل سمين مقابل عميل رقيق عميل ذكي (VB، PowerBuilder) أو خادم ذكي (ويب ١.٠) الويب فاز: صفر تثبيت، تسليم شامل. العميل صار المتصفح.
SOA (ألفينيات) تكامل المؤسسة، إعادة الاستخدام خدمات خشنة، ESB، WS-*، نموذج بيانات قانوني ESB صار عنق زجاجة؛ العقود ثقيلة؛ الحوكمة المركزية أبطأت الفرق
خدمات مصغرة (Microservices) (٢٠١٠–) استقلالية الفريق، نشر مستقل، دقة التوسع خدمات دقيقة، بيانات لا مركزية، بوابة API، مراقبة تعقيد النظام الموزع: التصحيح، الاتساق، العبء التشغيلي
بدون خادم / دوال (Serverless) (٢٠١٥–) العبء التشغيلي، وقت بدء بارد، تكلفة الخمول دالة = وحدة، وقت تشغيل مُدار، دفع لكل استدعاء تثبيت البائع، تصحيح التتبع الموزع، أحمال العمل ذات الحالة محرجة
مُدفوع بالأحداث / CQRS (٢٠١٧–) عدم تناظر توسع القراءة/الكتابة، قابلية التدقيق، استعلامات زمنية سجل الأحداث = مصدر الحقيقة، الإسقاطات = نماذج قراءة نموذج عقلي الاتساق النهائي؛ تطور مخطط الأحداث؛ تعقيد إعادة التشغيل
الحافة / دوال ذات حالة (٢٠٢٢–) زمن الوصول، جاذبية البيانات، التخصيص على النطاق الواسع الحوسبة تنتقل للبيانات (كائنات دائمة، Cloudflare KV، Vercel KV) الاتساق عبر الحواف؛ نموذج عقلي جديد (ليس منطقة، ليس مصدر)

القوس: يتغير القيد → رهان التصميم القديم يتعارض → رهان جديد ينقلب. أحادي انقلب إلى خدمات مصغرة (استقلالية النشر > تكلفة العتاد). SOA انقلب إلى خدمات مصغرة (استقلالية الفريق > إعادة الاستخدام). الخدمات المصغرة تنقلب إلى حافة/دوال ذات حالة (زمن الوصول > بساطة التشغيل). كل انقلاب يترك طبقة إرث لا تزال تعمل لقيدها.

النظرية الكامنة — ما يجعل النظام "مصممًا" لا "مجمّعًا"

يستقر التصميم المعماري على حفنة من النتائج المثبتة. كل واحدة تفرض قرارًا؛ لا يمكنك "التفاف" حولها.

النظريات أعلاه هي الحواجز الواقية. النماذج العقلية هي كيف تتنقل بداخلها. كل نموذج يضغط النظريات لسياق قرار محدد:

عزل مجال الفشل نطاق الانفجار = ما يسقط عند فشل هذا المكون. قلص نطاق الانفجار، ثم قلص التكرار. حجم الخدمات؛ اختيار متزامن مقابل غير متزامن؛ موضع قاطع الدائرة؛ حجم الحاجز. مصير مشترك: قاعدة بيانات واحدة لكل الخدمات؛ طابور واحد؛ خط نشر واحد.
ميزانية زمن وصول لكل قفزة SLO من النهاية للنهاية (مثال: p99 <٢٠٠مس) → اطرح الشبكة، المصادقة، قاعدة البيانات → المتبقي = ميزانية الخدمة. كل قفصة تأخذ شريحة. تصميم API؛ اختيار RPC مقابل REST؛ تقرير ما إذا كانت المكالمة "سريعة بما يكفي". قياس النهاية للنهاية فقط؛ التمني أن تكون سريعة.
خنق (Strangler Fig) للهجرة لا قطع كبير أبداً. وجّه الحركة تدريجياً: وكيل → خدمة جديدة → اقطع. النظام القديم يتقلص، الجديد ينمو. أحادي → خدمات مصغرة؛ REST → GraphQL؛ v1 → v2؛ محلي → سحابي. قطع كبير؛ أعلام ميزة دون تحويل حركة المرور.
تصميم موجه بالمراقبة لا يمكنك تشغيل ما لا يمكنك رؤيته. صمم للتتبع، المقاييس، السجلات قبل كتابة الكود. لوحة القيادة هي المواصفة. تصميم خدمة جديدة؛ تعريف SLO؛ عناصر إجراء مراجعة الحادث. إضافة التسجيل بعد الإطلاق؛ "سنسلك لاحقاً."
التكلفة كقيد معمار فاتورة السحابة = تغذية راجعة للمعمار. نقل البيانات، الموارد الخاملة، الإفراط في التخصيص = روائح تصميم. اختيار بدون خادم مقابل حاويات؛ موضع البيانات؛ سياسات الاحتفاظ؛ تخزين متدرج. "السحابة لا نهائية"؛ المالية تراجع الفاتورة ربع سنوي.

تخطيط السعة — كيفية تقدير الحمل والتخزين وزمن الاستجابة

تخطيط السعة ليس تنبؤاً مثالياً. إنه اختيار معمارية تنجو من عدم اليقين — الانضباط الذي يحوّل أرقام حسابات الظهر في مثال مختصر الروابط إلى عملية قابلة للتكرار.

عملية تخطيط السعة

  1. حدّد العمليات الأساسية (الحفنة القليلة من الطلبات التي تحمل 90% من الحركة).
  2. قدّر الحجم اليومي لكل عملية من واقع الأعمال، لا من الأماني.
  3. حوّله إلى متوسط QPS/TPS (اقسم على 86,400 ثانية).
  4. طبّق مضاعِف الذروة (عادة 5–10× المتوسط؛ أكثر للتجزئة والشبكات الاجتماعية).
  5. قدّر أحجام الحمولة للطلبات والاستجابات.
  6. اسقط نمو التخزين: الصفوف/يوم × حجم الصف × فترة الاحتفاظ.
  7. قدّر البيانات الساخنة التي يجب أن تعيش في الذاكرة لزمن استجابة مقبول.
  8. قدّر عرض النطاق (الطلبات × حجم الحمولة) لتكلفة الإخراج وموضع CDN.
  9. سجّل نسبة القراءة/الكتابة — هي التي تقرر معمارية الكاش مقابل قاعدة البيانات الأساسية.
  10. اصرح بمتطلبات زمن الاستجابة (p50, p95, p99) لكل رحلة مستخدم.
  11. أضف الموسمية وسلوك الاندفاعات (الجمعة السوداء، نهاية الشهر، حملات التسويق).
  12. أضف مساحة الأمان — خطط حول ~70% استغلالاً للأنظمة ذات الحالة؛ منحنى زمن الاستجابة يصير عمودياً قبل 100%.

إرشادات زمن الاستجابة

  • استخدم المئينات، لا المتوسطات — المتوسط يخفي الـ1% من الطلبات التي تستغرق 10× أطول.
  • p50 هو التجربة النمطية؛ p95/p99 هما ألم الذيل الذي ينتج شكاوى المستخدمين وحرق ميزانية الأخطاء.
  • زمن الاستجابة ينمو بشكل غير خطي قرب التشبع (الطوابير تبدأ بعد ~70% استغلالاً).
  • اختبر الحمل قبل افتراض التوسع الخطي — سقف الإنتاجية يُكتشف، لا يُفترض.

القاعدة: إذا لم يتسع نموذج السعة لصفحة واحدة، فالمعمارية أعقد من أن تُفهم تحت الحمل. النموذج أداة دعم قرار، لا جدولاً بيانات لذاته.

  • مخاطر التبديل: الدماغ المنقسم (قائدان يقبلان الكتابة) هو نمط الفشل الذي يفسد الحالة — ولهذا يوجد النصاب والسياج (fencing).

تطور المخطط

  • التوسع ثم الانكماش — أضف العمود/الجدول الجديد بينما يعمل الكود القديم؛ هاجر القراء؛ احذف الحقل القديم. لا تتحور في مكانها أبداً.
  • فضل التغييرات المتوافقة مع الخلف (حقول إضافية، قيم افتراضية قابلة للصفر) — المستهلكون القدامى يبقون يعملون.
  • كتابة مزدوجة للترحيلات — اكتب للتمثيلين القديم والجديد حتى نقطة التحويل.
  • تعبئة الخلف تعمل كوظائف خلفية ذات نقاط تحقق؛ تفشل في المنتصف ويجب أن تستأنف.
  • الترحيلات المباشرة (pgroll, gh-ost) تتفوق على ترحيلات التوقف لأي نظام دائم التشغيل.
  • عرّف الاحتفاظ مسبقاً — نمو التخزين قرار سعة وتكلفة (تخطيط السعة، صف التكلفة).
  • عامل تغييرات البيانات غير القابلة للعكس (حذف، إعادة كتابة) كأبواب باتجاه واحد تتطلب ADR.

معمارية التخزين المؤقت — أين تخزّن، ماذا تخزّن، وكيف تُبطل

أنماط فشل الكاش

  • تدافع الكاش / القطيع الهادر — انتهت الصلاحية، فكل طلب يعيد الحساب ضد قاعدة البيانات. الحل: TTL مشتتة، دمج الطلبات، تحديث مسبق.
  • المفاتيح الساخنة — مفتاح واحد يمتص حصة غير متناسبة. الحل: تكرار أو تخزين محلي للمفتاح الساخن.
  • قيم ضخمة — ميغابايتات في مفتاح واحد تدهور كل قراءة. الحل: قلّص أو خزّن البيانات الوصفية فقط.
  • TTL غير محدودة — الذاكرة تنمو للأبد. الحل: TTL، سياسة إخلاء (LRU/LFU)، حدود حجم.
  • إبطال غير متسق — الكاش لا يُبطل عند الكتابة → تُخدم بيانات قديمة. الحل: مفاتيح بإصدارات أو كتابة عابرة.
  • تخزين بيانات غير مصرّح بها أو مخصصة — الأخطر: تسريب بيانات عبر المستأجرين/المستخدمين. لا تخزّن أبداً في طبقة تتجاوز التفويض (انظر حلقة المطور للتحذير نفسه).

نقش صندوق الإخراج. عندما تكتب خدمة إلى قاعدتها ويجب أن تصدر حدثاً، افعل الاثنين ذرياً: اكتب صف الحدث في جدول صندوق الإخراج في نفس المعاملة مع كتابة الأعمال. ثم ينشر مرحّل (relay) صفوف الصندوق إلى الوسيط. يمنع هذا الفشل الكلاسيكي — «حُدّثت قاعدة البيانات، لم يُرسل الحدث أبداً» — السيناريو ذاته الذي يكسر اتساق المخزون/الطلبات في مثال نظام الطلبات بصمت.

القاعدة: النظام الحدثي جاهز للإنتاج فقط عندما يمكن محاسبة كل رسالة — مستهلكة، أو ميتة-الرسائل، أو قابلة لإعادة التشغيل. إذا كان حدث يمكن أن يختفي بصمت، فالمعمارية غير مكتملة.

القواعد التي تجعله يعمل: مناوب واحد بالضبط في كل وقت، بمسار تصعيد مكتوب وحد زمني قبل إيقاظ أي شخص آخر؛ الحوادث تأخذ قناة وقائداً، ووظيفة القائد تنسيق لا برمجة؛ التقارير البعدية خلال أيام، وتغطي الخط الزمني للحقائق (السجلات، النشرات، التنبيهات — طبقة المراقبة تقدم الأدلة)، وقائمة الإصلاحات تُتتبع كأي عمل آخر — تقرير بعدي بلا إجراء مجدول هو مدونة يومية، لا عملية.

حماية الحمولة الزائدة

  • مهلات زمنية على كل استدعاء خارجي — المهلة المفقودة اعتماد معلق.
  • ميزانيات إعادة المحاولة — سقف لإجمالي المحاولات؛ المحاولات بلا حدود تصير حملاً متتالياً.
  • تأجيل أسي مع تشتيت — يمنع عواصف إعادة المحاولة من نوع القطيع الهادر.
  • قواطع الدائرة — افشل بسرعة تجاه الاعتماد المكسور بدل التراكم عليه.
  • حواجز — اعزل تجمعات الخيوط/الاتصالات لكل اعتماد (طبقة الأنماط الكبرى أنماط الفشل).
  • إسقاط الحمل — أسقط العمل منخفض القيمة (تحليلات، قراءات غير حرجة) قبل أن يسقط المسارات الحرجة.
  • تحديد المعدل — سقوف لكل عميل ولكل خدمة.
  • ضغط خلفي للطابور — عندما يتجاوز المنتجون المستهلكين، دع الطابور يشير بالخلف بدل التخزين المؤقت للأبد.
  • نشر الإلغاء — عندما يستسلم المتصل، ألغِ العمل النهائي حتى لا يظل يحرق الموارد.

المراقبة — تصميم أنظمة يمكن فهمها في الإنتاج

المراقبة ليست «أضف سجلات لاحقاً». إنها متطلب معماري له اسم: إذا لم يمكن رؤية الفشل وتحديد موضعه وإعادة إنتاجه، فالمعمارية غير مكتملة تشغيلياً.

المتطلبات المعمارية

  • معرّفات الارتباط تُنشر عبر كل طلب وحدث — معرّف واحد يربط السجلات والآثار والمقاييس برحلة واحدة (مثال نظام الطلبات يفعل هذا للطلبات).
  • سجلات منظمة (JSON)، لا نص حر — قابلة للبحث والتصفية والتحليل آلياً.
  • نشر الآثار (OpenTelemetry) عبر كل حد خدمة — أثر يتوقف عند خدمة واحدة هو فشل تحديد موضعي.
  • صحة الاعتمادات — كل خدمة تبلغ عن حالة الخدمات التي تستدعيها (خريطة مجالات الفشل، مصنوعة مرئية).
  • تأخر الطابور، نسبة ضرب الكاش، التشبع — المقاييس التي تتنبأ بالمشاكل قبل أن يشعر بها المستخدمون.
  • مقاييس الأعمال — عمليات الدفع، التسجيلات، المدفوعات. الصحة التقنية وحدها لا تثبت أن المنتج يعمل.
  • تنبيهات مربوطة بأثر المستخدم — التنبيهات المزعجة تُتجاهل؛ تنبيه حرق SLO (الموثوقية وتعافي الكوارث) يربط الإنذارات بميزانية الأخطاء.
  • لوحات قيادة لكل خدمة ولكل رحلة حرجة — الخدمة الخضراء قد تحمل رحلة مكسورة.

القاعدة: سلم المراقبة مع الخدمة، لا بعدها. النظام الذي لا يمكن فهمه في الإنتاج ليس مصمماً — إنه منشور فقط.

الوجه العملي لهذه المعمارية: اختيار الأهداف، وتصميم تنبيهات تحترم البشر المناوبين، وتشغيل الحوادث والتقارير البعدية هو الانضباط المجاور — انظر المراقبة والعمليات.

السياقات المحدودة (التصميم الاستراتيجي DDD)

من إريك إيفانز (Domain-Driven Design, 2003) وفون فيرنون (Implementing DDD, 2013):

  • السياق المحدود حد دلالي يُطبَّق داخله نموذج المجال. «الطلب» يعني أشياء مختلفة في المبيعات (عرض، تفاوض) مقابل التنفيذ (انتقاء، تغليف، شحن) مقابل الفوترة (فاتورة، اعتراف بالإيراد).
  • خريطة السياق — علاقات صريحة بين السياقات: شراكة، نواة مشتركة، عميل/مورّد، متأقلم، طبقة مضادة للفساد، خدمة مضيفة مفتوحة، لغة منشورة.
  • القاعدة: سياق محدود واحد = خدمة واحدة (أو وحدة قابلة للنشر في أحادي نمطي). لا تشارك قاعدة البيانات عبر السياقات.

لكل قطعة حالة قابلة للتغيير مالك واحد بالضبط. المالك هو المكون الوحيد الذي يكتبها. كل المكونات الأخرى تقرأ عبر API أو تشترك في الأحداث. هذا هو نسخة النظام من قرار «أين ينتمي هذا؟» لكل ميزة — وثيقة التفكير الشامل (Full-Stack) تحمل تلك النسخة.

الخطيئة الكبرى: خدمتان تكتبان على نفس الجدول. هذا يقترن بنشرهما، وترحيل مخططاتهما، ومجالات فشلهما، وتوسعهما. يحوّل خدمتين إلى أحادي نمطي موزع.

حدود الثقة — أين تتحقق

  • الحد الخارجي (API Gateway / WAF) — تحقق المصادقة، تحديد المعدل، المخطط، الحجم، أنماط الهجوم المعروفة. ارفض مبكراً.
  • حد الخدمة (كل خدمة) — تحقق قواعد الأعمال والتفويض وسلامة البيانات. لا تثق أن البوابة التقطت كل شيء.
  • الحد الداخلي (وحدة/دالة) — تحقق الشروط المسبقة (تصميم بالعقد). افشل بسرعة داخل منطقة الثقة.

القاعدة: تحقق عند كل حد. تكلفة فحص تحقق لا تُذكر؛ تكلفة انتشار حالة فاسدة ليست كذلك.

الطريقة لكل ميزة لإيجاد تلك الحدود — رسم مخطط تدفق البيانات وتشغيل STRIDE على كل عبور — في الأمن ونمذجة التهديدات (نمذجة التهديدات ومثال محلول). هذا القسم هو أين المعمارية؛ تلك الوثيقة هي كيف تُعدّ.

معمارية قاعدة الكود — الشكل المادي للحدود

كل حد أعلاه (سياق محدود، ملكية بيانات، مجال فشل) له تعبير مادي: شجرة المجلدات. إذا لم يرَ الكود الحد، فالحد غير موجود.

  • مسطح مقابل شجرة. المسطح (كل شيء في دليل واحد) ينجح فقط مع البرامج النصية والمشاريع الصغيرة — بمجرد قدوم مطور ثانٍ أو مجموعة اختبارات أو ملف إعداد، ينهار المسطح. الشجرة ليست زينة: إنها نطاقات أسماء (الاستيرادات تحل بالمسار)، ونطاقات أدوات (الفحص/الاختبار/البناء تستهدف شجرة فرعية)، وملكية (مجلد = نطاق انفجار شخص أو فريق). السؤال ليس «مسطح أم شجرة» — بل «ما غرض كل مجلد؟»
  • لماذا src/. جذر كود واحد يبقي الكود المرئي للبناء منفصلاً عن الإعداد والأدوات (package.json, tsconfig, vite.config, ملفات CI) التي تعيش في الجذر. كما يمنح الاستيرادات وقواعد الفحص مرساة واحدة («كل ما تحت src/ هو كود تطبيق»). الاصطلاح أفضل من الإعداد، وsrc/ أقل اصطلاح مثير للجدل في الصناعة.
  • مجلدات الميزات مقابل الطبقات. الطبقات (controllers/, services/, repos/) تنظّم بـالتقنية؛ مجلدات الميزات (checkout/, auth/) تنظّم بـمجال الأعمال. الافتراضي الحديث ميزة-أولاً: كل مجلد ميزة يملك واجهته ومنطقه واختباراته (مكان واحد)، وتنشأ الطبقات داخل الميزة عندما تستحقها. الطبقات على القمة تبسط ميزة واحدة على خمسة مجلدات — الشكل المادي لسياق محدود منتهك. التجميع الموضعي هو المبدأ نفسه بمقياس الملف: الاختبار والأسلوب والقصة تعيش بجوار الكود الذي تصفه، فحذف ميزة يحذف كل ما تملكه.
  • تخطيطات الأطر الموصوفة هي أرخص قرار: app/ (توجيه Next.js بالملفات — انظر Next.js), src/ + index.html (SPA Vite), src/app + NgModules (Angular). التعرف على التخطيط الذي يستخدمه المستودع هو أحد علامات المعسكرات الأربع.
  • تخطيطات المونوريبو يضيفون مستوى آخر: apps/ (منتجات قابلة للشحن) مقابل packages/ (مكتبات مشتركة) — قرار التغليف على مستوى المستودع في التحكم بالإصدارات وCI/CD.
  • جسر التسليم: كل معلم عقد (وحدات وثيقة العمل الحر) يجب أن يرسم إلى مجلد ميزة — شريحة عمودية قابلة للبناء والاختبار والعرض بنفسها. إذا اختلفت المعالم والمجلدات، فأحدهما يكذب؛ عادة هو شجرة المجلدات.

مسطح الفشل — ما يفشل باستقلال؟

ارسم صندوقاً حول كل مكون. اسأل:

  • إذا فقد هذا الصندوق الطاقة، فما الذي يتوقف عن العمل أيضاً؟
  • إذا نُشر هذا الصندوق بخطأ، فما نطاق الانفجار؟
  • إذا فسدت قاعدة بيانات هذا الصندوق، فما البيانات المفقودة؟

الإجابات تعرّف مجالات الفشل لديك. التصميم المعماري الجيد يقلص نطاق الانفجار: فشل في خدمة التوصيات يجب ألا يسقط عمليات الدفع.

لماذا هو أسلوب، لا خوارزمية

مثل حلقة المطور والتفكير التصميمي، التصميم المعماري ليس خوارزمية. لكن السبب مختلف:

  • حلقة المطور تفتقر إلى خطوات حتمية لأن المشكلة تُكتشف أثناء البناء.
  • التفكير التصميمي يفتقر إلى خطوات حتمية لأن المشكلة مجهولة حتى تُؤطَّر.
  • التصميم المعماري له قيود مسماة (CAP، قانون ليتل، أمدال، كونواي) تحصر فضاء الخيارات. لا يمكنك اختيار «اتساق قوي + توافر عالٍ أثناء التقسيم» — CAP يمنعه.

ومع ذلك، القرار بين الخيارات الصالحة حكم، لا اشتقاق.

مقيَّد بالنظريةما زال قراراً بالحكم
لا يمكنك امتلاك CP + AP أثناء التقسيمهل تختار CP (البنوك) أم AP (سلة التسوق)؟
قانون ليتل يحصر حجم الطابورهل تضيف نسخاً مكررة، ترفع المهلة، أم تسقط حملاً؟
قانون كونواي يقترن المنظمة بالمعمارهل تعيد هيكلة الفرق أم تقبل المعمار الذي تنتجه المنظمة؟
أمدال يحصر التسارع المتوازيهل تستثمر في موازاة الـ10% التسلسلية أم تقبل الحد؟

النظريات تلغي الخيارات المستحيلة. لا تختار الخيار الصحيح. ذلك الاختيار هو حيث تعيش الخبرة والسياق والذوق — نفس «الإيقاع» لحلقة المطور، لكن بحواجز حماية أصلب.

النظام الإيكولوجي — كتالوج الأدوات مع معايير القرار

إن انضباط تصميم الأنظمة جيد فقط بقدر الأدوات التي تجعل قراراته مرئية، قابلة للاختبار، وقابلة للتراجع. يسرد هذا القسم فئات الأدوات الأساسية، مع معايير قرار لكل منها.

الفئةالأدوات / المنصاتالمُحفز → الهدفمعايير القرار
سجلات قرارات المعمارية (ADRs) adr-tools، MADR، Architect، Structurizr، Markdown في المستودع قرار جوهري جديد → موثق، قابل للمراجعة، سجل غير قابل للتغيير التغطية: % القرارات مع ADR؛ زمن الاستجابة: وقت من القرار إلى التسجيل؛ المراجعة: % ADRs التي راجعها الفريق
الرسم التخطيطي / النمذجة (C4، UML، ArchiMate) Structurizr، PlantUML، Mermaid، Draw.io، Miro، IcePanel الحاجة إلى نموذج ذهني مشترك → مخطط حي في المستندات/CI الانحراف: تأخر مزامنة المخطط مع الكود؛ التغطية: % الخدمات المودلة؛ الإعداد: وقت فهم الطوبولوجيا
فهرس الخدمات / الملكية Backstage، OpsLevel، Cortex، Port، ServiceNow انتشار الخدمات → خدمات قابلة للاكتشاف، مملوكة، قابلة للقياس التسجيل: % الخدمات المفهرسة؛ الملكية: % بمالك واضح؛ حداثة البيانات الوصفية
إدارة عقود API OpenAPI/Swagger، GraphQL Federation، tRPC، Protobuf/gRPC، Pact، Spring Cloud Contract عقود ضمنية → عقود معرفة بالمخطط، مودرة، محكومة بـ CI كشف التغييرات المدمرة: معدل الإيجابيات/السلبيات الكاذبة؛ تغطية المستهلكين؛ وقت نشر تغيير العقد
المراقبة (مؤشرات، سجلات، تراسات) Prometheus/Grafana، Datadog، Honeycomb، Lightstep، Jaeger، Zipkin، OpenTelemetry فشل غير معروف → نظام مرئي، قابل للتصحيح، مدعوم بـ SLOs التغطية: % الطلبات المتراسة؛ تنبيه معدل حرق SLO؛ MTTD/MTTR؛ تكلفة الكارديناليتي
هندسة الفوضى / اختبار الموثوقية Chaos Mesh، Litmus، Gremlin، Steadybit، AWS Fault Injection Simulator مرونة مفترضة → عزل نطاق الفشل مُحقق تكرار التجارب؛ التحكم في نطاق الانفجار؛ تحسين MTTR؛ معدل الثقة الكاذبة
البنية التحتية ككود / GitOps Terraform، Pulumi، Crossplane، Flux، ArgoCD، Spacelift، env0 بنية تحتية يدوية → بنية تحتية مودرة، قابلة للمراجعة، قابلة للتدقيق وقت كشف الانحراف؛ وقت تنفيذ التغيير؛ وقت التراجع؛ معدل نجاح الخطة/التطبيق
شبكة الخدمة / إدارة حركة المرور Istio، Linkerd، Consul Connect، AWS App Mesh، Cilium بقعة عمياء في الشبكة → mTLS، إعادة محاولات، مهلة، تحويل حركة المرور، مراقبة تغطية الشبكة؛ تعقيد التكوين؛ تكلفة زمن الوصول؛ % اعتماد mTLS
المواصفة الرسمية / التحقق TLA+، Alloy، P، AWS P، Quint، FizzBee بروتوكول حرج → تصميم موثق بالمواصفات، متحقق بالنموذج تغطية المواصفة: % المسارات الحرجة المحددة؛ منع الأخطاء: الملتقطة مقابل الإنتاج؛ منحنى التعلم
أدوات طوبولوجيا الفريق / التصميم التنظيمي لوحة Team Topologies، OrgWeaver، Functionly، قوالب Miro عدم تطابق كونواي → طوبولوجيا فريق مقصودة متوافقة مع المعمارية وضوح نمط التفاعل؛ الحمل المعرفي لكل فريق؛ تكرار التسليم؛ عدد دورات التبعية

قاعدة اختيار: ابدأ بـ ADRs + الرسوم التخطيطية + المراقبة (مجموعة "الحد الأدنى القابل للحياة لأدوات المعمارية"). أضف إدارة العقود عند عدد API > 5. أضف هندسة الفوضى عند وجود SLOs لكن غير مختبرة. أضف IaC/GitOps عند تغييرات البنية التحتية > 1/أسبوع. أضف المواصفة الرسمية فقط للبروتوكولات ذات تكلفة فشل كارثية (المدفوعات، الإجماع، المصادقة). الأداة تخدم القرار — وليس العكس.

المستقبل — أين يتجه التصميم المعماري

إشارة (٢٠٢٤–٢٠٢٦)ما يعنيه للتصميم المعماري
الحوسبة الحافة / الدوال ذات الحالة Cloudflare Workers، Vercel Edge، Fastly Compute، AWS Lambda@Edge. الحوسبة تنتقل للبيانات. حد "الخدمة" يصبح دالة + تخزين مرفق (كائنات دائمة، KV، D1). يجب على التصميم المعماري الآن وضع الحالة جغرافيًا.
WebAssembly كنموذج مكون مكونات WASM (wasmCloud، Spin، Fermyon). مستقل عن اللغة، أمان قائم على القدرة، بدء بارد فوري. حدود الخدمة تصبح حدود مكونات WASM.
منصات ذات حالة كائنات دائمة Cloudflare، D1، KV؛ PlanetScale، Neon، Turso. قاعدة البيانات لم تعد طبقة منفصلة — هي مضمنة في منصة الحوسبة. التصميم المعماري ينتقل من "خدمة + قاعدة بيانات" إلى "دالة ذات حالة".
توحيد طبقة API مكونات خادم React، tRPC، اتحاد GraphQL، gRPC-Web. عقد API يُولد من نظام الأنواع، لا مكتوب يدويًا. يجب على التصميم المعماري فرض عقود آمنة بالنوع كحد أساسي.
الذكاء الاصطناعي كمكون نظام اختيار مستودع المتجهات (pgvector، Pinecone، Weaviate، Milvus)، التنسيق (LangChain، LlamaIndex، مخصص)، خطوط تقييم، حواجز حماية. نموذج ML الآن تبعيات نظام بتوسعه الخاص، إصداره، وأنماط فشله.
التحقق الرسمي على الحدود TLA+ للبروتوكولات الحرجة (تستخدمه AWS لـ S3، DynamoDB). حدّد البروتوكول، نموذج-تحقق منه، ولّد الكود. التصميم المعماري للمسارات عالية المخاطر يصبح موجهًا بالمواصفات.

مفردات البحث — ما اسم هذه الأشياء

لا يمكنك البحث عن مشكلة لا تعرف اسمها. مصطلحات الفن التي تستخدمها هذه الوثيقة، وكل واحدة منها مفتاح بحث عامل:

  • السياق المحدود (Bounded context) — الحد الدلالي الذي يسري فيه نموذج المجال. ابحث "DDD bounded context strategic design".
  • نمط الساغا (Saga) — معاملة موزعة عبر أفعال تعويضية. ابحث "saga pattern choreography vs orchestration".
  • مفتاح التعديل (Idempotency key) — مفتاح يولده العميل يجعل إعادة المحاولة آمنة. ابحث "idempotency key API design stripe".
  • قاطع الدائرة / الحاجز (Bulkhead) — فشل سريع وعزل للاعتماديات العطلة. ابحث "circuit breaker pattern resilience4j".
  • نمط التين الخنق (Strangler fig) — ترحيل تدريجي خلف واجهة توجيه. ابحث "strangler fig pattern migration".
  • Event sourcing / CQRS — سجل الأحداث مصدر الحقيقة؛ نماذج قراءة/كتابة منفصلة. ابحث "event sourcing CQRS explained".
  • نمط الصندوق الخارجي (Outbox) — كتابة قاعدة بيانات وإصدار حدث ذرياً. ابحث "transactional outbox pattern microservices".
  • طابور الرسائل الميتة (DLQ) — حيث تذهب الرسائل السامة بدلاً من أن تتلاشى. ابحث "dead letter queue best practices".
  • ميزانية الأخطاء — بدل عدم الموثوقية القابل للإنفاق تحت SLO. ابحث "error budget google SRE".
  • الضغط العكسي / إلقاء الحمل — النجاة من منتجين أسرع من المستهلكين. ابحث "backpressure load shedding queue".

ملخص — قائمة تحقق معمارية

قبل كتابة أي كود لمجال جديد، تحقق:

سؤالإذا لا…
هل قدرنا السعة (ذروة QPS، حجم البيانات، معدل النمو)؟توقف. لا نموذج سعة = لا خطة توسع.
هل رسمنا مربعات مجالات الفشل وتحققنا من دائرة الانفجار؟توقف. فشل واحد يجب ألا يتسلسل.
هل اخترنا نموذج اتساق لكل مجال بيانات؟توقف. الاتساق "الافتراضي" هو عيب.
هل لكل حالة قابلة للتغيير مالك واحد بالضبط؟توقف. كتابة مشتركة = أحادي موزع.
هل كل حدود ثقة مُتحقق منها (بوابة، خدمة، وحدة)؟توقف. حد غير متحقق = فساد مستقبلي.
هل عقود API معرفة بالمخطط، مصدرة، ومحمية بـ CI؟توقف. العقود الضمنية تكسر بصمت.
هل صممت تكرار المحاولات في كل نقطة نهاية مغيرة للحالة؟توقف. إعادة المحاولات ستفسد الحالة.
هل طوبولوجيا الخدمة تطابق طوبولوجيا الفريق (كونواي)؟توقف. عدم تطابق منظمة/معمارية = احتكاك للأبد.
هل القرارات المعمارية مسجلة كـ ADRs؟توقف. التقليد الشفهي يفقد السياق في ٦ أشهر.

اطبع هذا. ضعه على جدار المعمارية. إذا لم تستطع الملحمة (epic) اجتياز هذه القائمة، فهي غير جاهزة لحلقة المطور.
