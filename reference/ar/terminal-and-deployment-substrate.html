الطرفية وطبقة النشر

الركيزة غير المرئية تحت كل وثيقة أخرى في هذه الرفوف: أوامر الطرفية التي تفتح لك الأبواب (أساسيات الصدفة، والتنقل، وإدارة العمليات، ومتغيرات البيئة، والأنابيب، والشبكات، والأذونات)، والنموذج الذهني لدوكر (الصور مقابل الحاويات، وملفات Dockerfile، وCompose، والمنافذ الشائعة، ولماذا الحاوية ليست جهازًا افتراضيًا)، ومعرفة Kubernetes (Pods وDeployments وServices)، وعصور السحابة الثلاثة (IaaS وPaaS وServerless) — كلٌّ منها مربوط بالوثيقة التي تملك عمقه في الرفوف. اقرأ هذا حين تقول وثيقة «شغّل هذا في طرفيتك»، أو حين لا يقلع خادمك، أو حين تحتاج إلى فهم أين يعمل كودك فعلًا.

اللغة: العربية · English

أين يقع هذا. كل وثيقة في هذه الرفوف تفترض وجود طرفية. هندسة الخلفية تقول إن الخادم يجب أن يكون بلا حالة؛ التحكم بالإصدارات وCI/CD والنشر يشحن صور الحاويات؛ ووردبريس وإنترنت أنظمة إدارة المحتوى يكتب عمليات عملائه بـWP-CLI. لا تتوقف أيٌّ منها لتعليم الأداة التي تحتها. هذه الوثيقة هي ذلك التوقف — طبقة البنية، ضحلة عمدًا:

الجيران وكيف يقسمون العمل:

  • التحكم بالإصدارات وCI/CD والنشر — يملك خط الأنابيب: البناء، والقطع الأثرية، واستراتيجيات الإصدار، وسلامة سلسلة التوريد. هذه الوثيقة تشرح ما هي القطعة الأثرية (حاوية) والأوامر التي تستخدمها محليًا.
  • هندسة الخلفية — يملك حلقة الطلب ولماذا يفرض البلا-خادم اللاحالة. هذه الوثيقة تمدّك بمهارات الطرفية لتشغيل ذلك الخادم وتصحيحه.
  • التصميم المعماري — يملك زمن الاستجابة، والحوسبة الطرفية، ومجالات الفشل، ومتى تكون المنصة مبالغة. هذه الوثيقة تمدّك بخريطة العصور الثلاثة لأهداف النشر.
  • الأمن ونمذجة التهديدات — يملك التهديدات والأسرار. هذه الوثيقة تمدّك بآليات النظافة (أذونات الملفات، وقاعدة «لا تُشغّل sudo أبدًا على خادم»).
  • علوم الحاسوب وهندسة البرمجيات — يملك صفوف التاريخ (دوكر 2013، AWS 2006)؛ هذه الوثيقة لا تكررها.

لماذا توجد هذه الوثيقة منفصلة

لا تعلّم أي وثيقة أخرى في الرفوف الطرفية أو ما هي الحاوية. يفترض المنهج أنك تستطيع تشغيل الأوامر، وقراءة سجل، وتصوّر هدف نشر — ولا يريك كيف أبدًا. ادّعت أدلة الدراسة التي روجعت مقابل هذه الرفوف أن هذه المواضيع مغطاة؛ وجد التدقيق أن نموذج دوكر الذهني (الصورة مقابل الحاوية) وعدة النجاة للطرفية كلها غائبان. تسد هذه الوثيقة تلك الفجوة بأصغر سطح ممكن: الـ~20% من الطرفية التي تحل 99% من مشاكل هندسة الويب، ونماذج الفقرة الواحدة لدوكر وKubernetes، وخريطة السحابة ذات العصور الثلاثة. ملاحظة نطاق واحدة: هذه ليست دورة مسؤول أنظمة أو ديفأوبس — جدول «تجاهل بأمان» في التعريف لا يقل أهمية عن البقية.

كيف تستخدم هذه الوثيقة

ترتيب القراءة: اقرأ هذه الوثيقة مبكرًا — فهي البنية الأساسية لكل ما عداها. تترافق مع التحكم بالإصدارات وCI/CD والنشر (خط الأنابيب الذي يستهلك صور دوكر) وهندسة الخلفية (الخادم الذي تشغّله بهذه الأوامر). الروابط المتقاطعة:

  • القطع الأثرية والترويج: CI/CD والنشر — «ابنِ مرةً وروّج كثيرًا» تعيش هناك؛ مفهوم الحاوية يعيش هنا.
  • عقد اللاحالة: هندسة الخلفية — لماذا يحرّم البلا-خادم الحالة في الذاكرة.
  • زمن الاستجابة والحافة: التصميم المعماري — الفيزياء خلف شبكات CDN والحوسبة الطرفية.
  • التهديدات والأسرار: الأمن ونمذجة التهديدات — حقن أوامر نظام التشغيل، ونظافة الأسرار.
  • التاريخ: علوم الحاسوب وهندسة البرمجيات — دوكر 2013، AWS 2006، الانقلابات.
  • مرجع: المصطلحات.

إن بحثتَ يومًا عن «كيف أُنهي عملية على المنفذ 3000»، أو وقفتَ محتارًا أمام «docker run»، أو أومأتَ بالموافقة حين قال أحدهم «Pods وServices» — فهذه هي الخريطة. اقرأ التعريف (ما هذه الوثيقة وما ليست)، ثم أساسيات الصدفة وعدة النجاة، ثم دوكر والسحابة. الأمثلة العملية حيث يلتئم كل شيء.

التعريف — الركيزة، وما ليست عليه

الركيزة هي كل ما يعمل عليه كودك: نظام التشغيل، والطرفية التي تقوده، وصيغة الحاوية التي تحزمه، وعصور السحابة التي تستأجره. مهندسو الويب لا يديرون هذه الطبقة إداريًا؛ بل يشغّلونها — بما يكفي لفتح الأبواب أمام أنفسهم، وتشغيل كودهم، وفهم أهداف النشر التي يختارها تصميم أنظمتهم.

الطرفية — جهاز التحكم الشامل

الطرفية هي الواجهة الخام لكل أداة في هذه الرفوف. تخفي الواجهات الرسومية التعقيد خلف أزرار؛ تكشف الطرفية العمليات الأساسية — وكل أداة تعلّمها الرفوف (Git، وnpm، وNode، ودوكر، وcurl، وWP-CLI) مصممة طرفية-أولًا. حين توجد واجهة رسومية، فهي جلد فوق نفس الأمر. ما تعطيك إياه الطرفية ولا تستطيعه الواجهات الرسومية:

القدرةلماذا تهم
القابلية للبرمجة النصيةأي شيء تفعله مرة، يمكنك تسلسله وتكراره — خط أنابيب CI الخاص بك هو حرفيًا سلسلة أوامر طرفية تعمل داخل حاوية لينكس
الوصول عن بُعدالطريقة الوحيدة للدخول حين تكون الآلة خادمًا في قارة أخرى (ssh)
الحقيقةالسجلات وقوائم العمليات وأذونات الملفات تُظهر ما هو موجود، لا ما قررت واجهة رسومية عرضه
الدقةأمر واحد يستهدف شيئًا واحدًا بالضبط — PID، أو سطرًا في ملف، أو منفذًا — بدل النقر عبر القوائم

لينكس هو المضيف الشامل. سواء نَشرتَ إلى AWS أو Vercel أو Raspberry Pi أو حاوية، فالبيئة دائمًا لينكس تقريبًا. ماك هو يونكس تحته (مشابه جدًا)؛ يستخدم مطورو ويندوز WSL لمحاكاته. لذا فإن عادات الطرفية التي تبنيها محليًا تنتقل إلى الإنتاج شبه دون تغيير — وهذا بالضبط لماذا «اشتغل في طرفيتي» هي أقرب ما يمكنك الوصول إليه إلى «اشتغل في الإنتاج».

أساسيات الصدفة — البيئة التي تكتب فيها

الطرفية مقابل الصدفة مقابل سطر الأوامر. الطرفية هي النافذة التي تنظر إليها (iTerm2 أو Windows Terminal أو GNOME Terminal)؛ الصدفة هي البرنامج داخلها الذي يفسر ما تكتبه (bash على معظم لينكس، وzsh على ماك منذ Catalina)؛ سطر الأوامر هو الواجهة حيث تكتب. الفرق يهم حين تعدّل إعداد الصدفة: أسماءك المستعارة وإضافات PATH تعيش في ~/.bashrc على لينكس و~/.zshrc على ماك — ضعها في الملف الخاطئ ولن يحدث شيء.

الميزتان اللتان تجعلان الطرفية أسرع من واجهة رسومية: إكمال التبويب — اكتب git ch واضغط Tab ليُكمل إلى git checkout (اضغط Tab مرتين لعرض الخيارات) — وتاريخ الأوامر — سهما ↑/↓ يتنقلان عبر الأوامر السابقة، وCtrl+R يبحث فيها. بدونهما تبدو الطرفية أبطأ من النقر؛ معهما تصبح أسرع بدراماتيكية. تعلّمهما قبل أي أمر.

المسارات. المسار المطلق يبدأ من الجذر: /home/you/projects/my-app. المسار النسبي يبدأ من حيث أنت: ./src/index.js أو ../shared/utils.js. ~ اختصار لمجلد منزلك، و. هو المجلد الحالي، و.. هو الأصل — ولهذا يعمل cd projects من المنزل ولا يعمل من /tmp.

إعادة التوجيه والبدائل والسلسلة — العوامل الثلاثة التي تحول الأوامر إلى نصوص برمجية:

npm run build > build.log 2>&1   # > write output to a file (overwrite); 2>&1 folds errors in too
echo "DB=..." >> .env          # >> append to a file instead of overwriting
rm *.log                        # * matches any text: every .log file in this directory
npm install && npm run dev     # && run the second only if the first succeeded
npm test || echo "failed"       # || run the second only if the first failed
cd src ; ls                      # ; run both, regardless of success

الأسماء المستعارة والمساعدة المدمجة. alias gs='git status' يعرّف اختصارًا ستراه في إعدادات الآخرين. حين تصادف أمرًا لا تعرفه، توثّق الطرفية نفسها: man lsof هو الدليل الكامل، وlsof --help الملخص السريع.

عدة النجاة — الـ20% التي تكفي 99%

ستة جداول صغيرة. هذه ليست «لطيفة أن تعرفها» — بل هي المجموعة التي تفتح 99% من مشاكل هندسة الويب: التنقل، وإيجاد ما يعمل، وتهيئة البيئة، والبحث في السجلات، واختبار النقاط النهائية، وعدم إطلاق النار على قدمك. درّب كلًا منها حتى يصبح رد فعل؛ هذا هو المنهج كله.

د. الأنابيب والبحث — القوة العظمى

فلسفة يونكس: أدوات صغيرة يفعل كل منها شيئًا واحدًا جيدًا، تُسلسل بـ|. مخرجات اليسار تغذي مدخلات اليمين:

cat server.log | grep "ERROR"    # only the error lines of a huge log
history | grep docker            # that complex command you typed yesterday
ps aux | grep node               # find processes without a GUI task manager

وللعثور على ملفات لا أسطر: find . -name "*.env" يبحث في الشجرة من حيث أنت، مصفّيًا بالاسم — تعرف أنه موجود، لا أين.

هذه العادة الواحدة — ابحث في السجل بـgrep بدل التمرير فيه — هي أكبر ترقية تصحيح في الرفوف. وهي بالضبط ما يصفه الاختبار والتصحيح: الأدلة قبل الفرضية.

مفاتيح SSH ومفهوم «البعيد». ssh user@host يفتح نفقًا آمنًا: الأوامر التي تكتبها تُنفَّذ على الخادم لا على حاسبك — ls يعرض ملفات الخادم، وexit يعيدك. تسجيل الدخول بكلمة مرور يعمل لكنه ضعيف ومرهق؛ المعيار هو زوج مفاتيح SSH — مفتاحك الخاص يبقى على حاسبك، ومفتاحك العام يُثبَّت على الخادم (أو على GitHub، من أجل git push عبر SSH). بمجرد إعداد ذلك، لا يحتاج تسجيل الدخول كلمة مرور. الاختصارات تعيش في ~/.ssh/config، حيث يمكنك تعريف ssh prod ليعني المضيف والمستخدم والمنفذ الكاملين. العمق — تدوير المفاتيح، وإعادة توجيه الوكيل — يخص الأمن ونمذجة التهديدات؛ هنا تحتاج النموذج والعادة.

دوكر — وحدة النشر

النموذج الذهني في جملة واحدة: الصورة هي المخطط (وصفة: نظام تشغيل أساسي + وقت تشغيل + كودك + إعداد)، تُبنى مرة واحدة وتُنسَّخ إصداراتها؛ الحاوية هي عملية قيد التشغيل نُشئت من تلك الصورة، تُشغَّل كما تشاء عدة مرات. لا «تعدّل حاوية قيد التشغيل» أبدًا — بل تعيد بناء الصورة وتشغّل واحدة جديدة. تلك الجملة هي النموذج الذهني كله؛ كل ما عداها أدوات.

الصورةالحاوية
النوعالمخطط — تُبنى مرة واحدةالعملية الحية — تُشغَّل مرات كثيرة
دورة الحياةغير قابلة للتغيير، مُنسَّخة الإصدارات (v1.2.0)زائلة — تموت وتُستبدل، ولا تُرقَّع في مكانها أبدًا
التشبيهوصفةوجبة صُنعت منها

الحاوية ليست جهازًا افتراضيًا. الجهاز الافتراضي يحاكي حاسبًا كاملًا — نواته الخاصة، وجيجابايتات، ودقائق للإقلاع. الحاوية عملية مغلفة ومعزولة تشارك نواة لينكس للمضيف (عبر cgroups وnamespaces)، تبدأ في ميلي ثانية وتستهلك ما تحتاجه العملية فقط. الأجهزة الافتراضية تفترض العتاد؛ الحاويات تفترض نظام التشغيل. لهذا الحاويات هي وحدة النشر الافتراضية للويب الحديث، ولهذا يسرد جدول القطع الأثرية في وثيقة CI/CD صور الحاويات الموقَّعة كالخيار الحديث.

لماذا وُجد كل هذا — «اشتغل على جهازي». تطبيقك يعتمد على إصدار Node محدد، ومكتبات نظام تشغيل محددة، ومتغيرات بيئة محددة؛ جهاز زميلك وخادم الإنتاج لديهما إصدارات مختلفة. الصورة تجمّد التركيبة الرابحة — نفس نظام التشغيل الأساسي ووقت التشغيل والكود والإعداد في كل بيئة — فيتحول «اشتغل على جهازي» إلى «اشتغل في هذه الصورة»، والصورة متطابقة في كل مكان. هذا هو السبب الكامل للحاويات.

ملف Dockerfile — الوصفة التي تبني صورة. ملف Dockerfile وصفة خطوة بخطوة؛ كل سطر خطوة، والنتيجة صورة. نادرًا ما تكتب واحدًا من الصفر، لكنك ستقرؤها باستمرار، فتعرف التعليمات الأربع التي تعمل كل العمل:

FROM node:20-alpine        # the base image you build on top of
WORKDIR /app               # the working directory inside the image
COPY package*.json ./      # copy files from your machine into the image
RUN npm ci                 # run a command during the build (install deps)
COPY . .                   # copy the rest of the app
CMD ["npm", "start"]       # the command that runs when the container starts

Docker Compose — وصفة بيئتك المحلية كلها. docker-compose.yml ملف YAML يصف عدة حاويات وكيف تتصل — تطبيقك، وقاعدة بيانات، وكاشًا — فيرفع أمر واحد المكدس كله. هكذا تحصل على Postgres وRedis محليين للتطوير بدل تثبيتهما أصليًا على حاسبك:

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: dev
    ports:
      - "5432:5432"          # host port : container port (see the ports table)
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7
    ports:
      - "6379:6379"

volumes:
  pgdata:

docker compose up يشغّل كل ما يصفه الملف؛ docker compose down يوقفه ويزيله. حين تستنسخ مستودعًا فيه أحد هذه الملفات، لا تثبّت قاعدة بيانات يدويًا — تقرأ الملف لترى ما يحتاجه المشروع، ثم docker compose up. النموذج الذهني مثل نموذج Dockerfile: وصفة تصريحية تقرؤها وتشغّلها، لا تسلسلًا ترتجله.

تعيين المنافذ وتركيب وحدات التخزين — العلمان اللذان ستراهما في كل مكان. للحاوية نطاق شبكة خاص بها: -p 3000:3000 (أو ports: في Compose) يعيّن المنفذ 3000 على جهازك إلى المنفذ 3000 داخل الحاوية — بدونه لا يستطيع متصفحك الوصول إلى خادم الويب في الحاوية. نظام ملفات الحاوية زائل — كل ما كُتب داخلها يُفقد عند توقفها — لذا -v ./src:/app/src (أو volumes:) يركّب مجلدًا من جهازك داخل الحاوية، وهكذا تطوّر داخل حاوية بملفاتك المتزامنة مباشرة.

المنافذ الشائعة — الأرقام خلف كل خدمة

المنفذ رقم يعرّف خدمة واحدة على آلة. آلة واحدة تشغّل خدمات عدة في آنٍ — خادم الويب على 3000، وقاعدة البيانات على 5432، والكاش على 6379 — ونظام التشغيل يوجّه الحركة إلى الصحيح عبر رقم المنفذ. حين تلتقط خدمتان المنفذ نفسه تحصل على EADDRINUSE (مثال المنفذ الشبح أدناه).

الوصلة بخط الأنابيب: CI الخاص بك يشغّل الاختبارات، ويبني الصورة، ويوسمها، ويدفعها إلى سجل؛ استراتيجيات النشر (التدريجي، والأزرق-الأخضر، والكناري) هي فقط «أي نسخة من الصورة تستقبل الحركة». تبني مرة واحدة في CI وتروّج نفس الصورة بالضبط عبر التدريج إلى الإنتاج — لا تعيد البناء لكل بيئة أبدًا. هذه قاعدة «ابنِ مرةً وروّج كثيرًا»، وموطنها CI/CD والنشر؛ هذه الوثيقة تسمّي المفهوم فقط كي يقرأ خط الأنابيب كشيء حقيقي.

تشغيل مكدسك يومًا بيوم: docker compose up للبيئة المحلية، وثلاثة أوامر تصحيح، محفوظة:

تجاهل بأمان: ملفات Dockerfile متعددة المراحل مضبوطة لتطبيقات قديمة، والتحسين الدقيق لطبقات الصور، ودواخل شبكات الحاويات. إذا كنت تقرأ ملف Dockerfile بسيطًا وتشغّل compose، فلديك المعرفة التي تتطلبها هذه الرفوف.

Kubernetes — معرفة التنسيق

Kubernetes (K8s) هو «نظام تشغيل مركز البيانات»: يأخذ صور الحاويات ويقرر أين تعمل، وكم نسخة توجد، وكيف تصلها الحركة. شبه مؤكد أنك لن تدير عنقودًا أبدًا — المنصات المدارة وتحذيرات التصميم المعماري تكفل ذلك — لكن البدائيات تظهر باستمرار في إعلانات الوظائف ووثائق المنصات ومحادثات المعمارية. ثلاثة أسماء تكفي:

البدائيةما هينموذج ذهني في سطر
Podأصغر وحدة قابلة للنشر: حاوية واحدة أو بضع حاويات تشترك في هوية شبكية«حاوية قيد التشغيل (أو اثنتان مترابطتان بإحكام)، بعنوان IP»
Deploymentالحالة المرغوبة التصريحية: كم نسخة Pod، وأي إصدار صورة، وكيف تُدرج التحديثات«أريد 3 نسخ من الصورة v1.2.0، وأريدهن أن يُستبدلن دون توقف»
Serviceاسم ثابت وموازن تحميل أمام مجموعة Pods«الـPods تموت؛ هذا الاسم يستمر بالعمل أيهما أجاب»

الصلة بين الثلاثة: Deployment ينشئ Pods، وService يوجّه الحركة إلى الـPods الصحية خلفه — هذه السلسلة هي كل التوصيلات. حين تقول منصة «انشر Deployment مع Service»، يمكنك الآن أن ترى الشيء: ثلاث حاويات زائلة خلف عنوان ثابت. هذا هو معيار المعرفة كله. اللحظة التي يقترح فيها أحدهم تشغيل Kubernetes بنفسك، تذكّر تحذير الرفوف نفسه — التصميم المعماري يسرد «Kafka + Kubernetes + Istio لفريق CRUD من ثلاثة أشخاص» كمبالغة معيارية. إدارة العناقيد مهنة لا مهارة؛ أنت مرخّص أن تومئ وتؤجل.

السحابة — العصور الثلاثة لاستئجار الحوسبة

منذ أطلقت AWS خدمتَي S3 وEC2 في 2006 (تاريخ علوم الحاسوب وهندسة البرمجيات)، أصبحت الحوسبة قابلة للاستئجار بالدقيقة بدل شرائها كعتاد. ثلاثة عصور من هذا الاستئجار تحدّد كل هدف نشر ستختار منه — كل عصر يستأجر طبقة أعلى في المكدس:

كيف تقيّد السحابة هندسة الخلفية: العصر البلا-خادم يفرض أن تكون حلقة الطلب بلا حالة. الطلب التالي قد يصيب حاوية مختلفة بدأت باردة — فلا يمكن أن تعيش الجلسات والكاش في الذاكرة المحلية. هندسة الخلفية تصوغ العقد بدقة: «الكاش في الذاكرة أصبح رهان بدء بارد. اللاحالة تتوقف عن كونها خيارًا وتصبح العقد». يجب أن تعيش الحالة في قاعدة بيانات أو كاش خارجي (Redis). PaaS يخفيها عنك؛ Serverless يفرضها عليك؛ معرفة الفرق هو غرض خريطة العصور.

الحافة وجاذبية البيانات: قراءة قاعدة بيانات في us-east-1 من مستخدم في طوكيو تدفع عقوبة فيزيائية — سرعة الضوء — ولهذا تدفع شبكات CDN والحوسبة الطرفية العمل إلى حيث المستخدمون. النمط الحديث ينقل الحوسبة إلى البيانات. العمق (ميزانيات زمن الاستجابة، والاتساق عبر الحواف، وكائنات دائمة) يخص التصميم المعماري؛ عمل هذه الوثيقة فقط أن تجعل «الحافة» تعني «أقرب إلى المستخدم، لأن الفيزياء».

مثال عملي — المنفذ الشبح

أكثر أخطاء التطوير المحلي شيوعًا في الوجود: EADDRINUSE. تعيد تشغيل خادمك فيكون المنفذ محجوزًا بعملية نسيتها. رد فعل الخبير، في أربعة أوامر:

$ npm run dev
Error: listen EADDRINUSE: address already in use :::3000

$ lsof -i :3000
COMMAND  PID   USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
node     4821  me     21u  IPv4 12345      0t0  TCP *:3000 (LISTEN)

$ kill -9 4821

$ npm run dev      # works

هذا هو النمط كله، ويعمّم على كل جلسة تصحيح في الرفوف: اقرأ الخطأ ← اعثر على الدليل (سجل، عملية، منفذ) ← تصرّف على ما يسميه الدليل بالضبط ← تحقق. المبتدئ ينقر في الـIDE؛ الخبير يفتح الطرفية، ويلاحق السجل، ويبحث عن الخطأ بـgrep، ويجد الـPID، ويقتله. هذه هي العادة التي تصوغها الاختبار والتصحيح رسميًا — الطرفية هي فقط حيث يعيش الدليل.

مثال عملي — لقد استنسخت مستودعًا للتو

الطقس اليومي الآخر: زميل يسلّمك رابط مستودع وتحتاج تشغيله. السلم كله في جلسة واحدة — قراءة ملفات ومتغيرات بيئة وDocker Compose دفعة واحدة:

$ git clone https://github.com/team/project.git
$ cd project
$ cat README.md            # setup instructions usually live here
$ cat package.json         # check the Node version and the start script
$ npm install
$ cp .env.example .env     # create your env file from the template
$ npm run dev
Error: connect ECONNREFUSED 127.0.0.1:5432
$ docker compose up -d     # the database (port 5432, see the ports table) isn't running
$ npm run dev              # works

النمط نفسه، درجة واحدة إلى أسفل السلم: الخطأ يسمّي عنوانًا (127.0.0.1:5432)، تقرأ docker-compose.yml في المستودع لترى ما يجب أن يملك ذلك المنفذ، تشغّله، تتحقق. ما الذي تغيّر بين المحاولة الأولى والثانية؟ لا شيء في الكود — فقط البيئة التي يعمل فيها الكود. تلك هي الركيزة.

اطبعها. إنها الوثيقة كلها في أحد عشر سطرًا:

#السطر
1الطرفية هي الواجهة الخام؛ لينكس هو المضيف الشامل. ~20% منها تحل 99% من المشاكل.
2قبل أي شيء مدمر: pwd. لا rm -rf أبدًا دون أن تعرف أين أنت.
3منفذ عالق؟ lsof -i :3000 ← kill -9 <PID> ← أعد التشغيل.
4الإعداد يعيش في متغيرات البيئة: export، وsource .env، وإن غابت أداة فاشتبه في $PATH.
5السجلات قبل الإصلاحات: cat log | grep "ERROR" يهزم التمرير في كل مرة.
6اختبر النقاط النهائية بـcurl؛ واصِل الآلات البعيدة بـssh/scp.
7لا تشغّل خادم ويب بـsudo أبدًا. chmod 600 لملفات أسرارك.
8الصورة مخطط يُبنى مرة واحدة؛ الحاوية عملية تُشغَّل مرات كثيرة. الحاوية ليست جهازًا افتراضيًا.
9الـPods تعمل، والـDeployments تعلن، والـServices تسمّي. تقرأ Kubernetes؛ لا تديره.
10عصور السحابة الثلاثة: IaaS تستأجر آلات، وPaaS تستأجر أوقات تشغيل، وServerless يستأجر التنفيذ — والبلا-خادم يجعل اللاحالة عقدًا.
11الحافة موجودة بسبب الفيزياء: تنتقل الحوسبة إلى البيانات حين يهم زمن الاستجابة.
