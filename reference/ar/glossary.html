المصطلحات — مفردات مشتركة عبر رف المراجع

كل مستند مرجعي على هذا الرف يستخدم هذه المصطلحات. هذا المعجم يحددها مرة واحدة، مع روابط العودة للمستند الذي يملك كل مصطلح. إذا كان للمصطلح معنى مختلف قليلاً في مستندين، فهما مدرجان معاً.

اللغة: العربية · English

كيفية استخدام هذا المعجم

المصطلحات مجمعة حسب التخصص الذي يملكها (المستند الذي تُعرّف فيه بعمق). اضغط على مصطلح للانتقال إلى قسمه في المستند المُلك. المصطلحات التي تظهر في عدة تخصصات لها إدخالات متعددة.

خريطة الرف — المنهج الكامل في نظرة واحدة

الرف منهج من سبع طبقات بمستوى Staff. كل طبقة تجيب عن سؤال واحد؛ كل مستند تخصص واحد. قسم "التقاطع مع الجيران" في كل مستند يقول أين تقع حدوده؛ هذه نظرة واحدة. الشريط الختامي يسرد المستندات الداعمة التي تكمل الرف — استطلاعات وملحقات، ليست تخصصات المنهج.

التفكير التصميمي (مالك: design-thinking.html)

المصطلحالتعريفأين يظهر
المشكلة الشريرة (Wicked Problem) مشكلة لا قاعدة توقف لها، لا اختبار صواب/خطأ، لا حل نهائي — فقط أفضل أو أسوأ. تعريف المشكلة هو فعل التصميم (ريتل ووبر، ١٩٧٣). التفكير التصميمي §2، §5
الاستدلال الاستنتاجي (Abductive Reasoning) استنتاج أفضل تفسير. لاحظ سلوكاً → افترض سبباً ("يكافحون لأن النموذج مربك") → اختبر بنموذج أولي. التفكير التصميمي §5
التعلم الحلقي المزدوج (Double-Loop Learning) حلقي أحادي: "صلح الفعل". حلقي مزدوج: "استجوب المتغير الحاكم". إعادة تأطير المشكلة = تعلم حلقي مزدوج (آرجيريس وشون، ١٩٧٨). التفكير التصميمي §5
المرغوبية / القابلية للتنفيذ / الجدوى (Desirability / Feasibility / Viability) إطار آيديو ثلاثي العدسات (١٩٩٨): هل يريد الناس هذا؟ هل نستطيع بناؤه؟ هل له معنى تجاري؟ التفكير التصميمي يعيش في التقاطع. التفكير التصميمي §0، §7
سبرينت التصميم (Design Sprint) تنفيذ بصندوق زمني ٥ أيام للتفكير التصميمي: فهم → رسم → قرار → نموذج أولي → اختبار (جوجل فنشرز، ٢٠١٦). اختراق للإيقاع، لا الانضباط كله. التفكير التصميمي §6، §7
الماسة المزدوجة (Double Diamond) اكتشاف (تباعد) → تعريف (تقارب) → تطوير (تباعد) → تسليم (تقارب). نموذج مرئي من مجلس التصميم UK (٢٠٠٥). التفكير التصميمي §2، §7
عبارة رؤية (Insight Statement) مشكلة معاد صياغتها: "المرضى لا ينسون بسبب الذاكرة — بل ينسون لأن المحفز (الزجاجة) مخفي في بيئتهم". مخرج طور التعريف. التفكير التصميمي §9
مسرح التصميم (Design Theater) أداء المنهجية (ملصقات، ورش عمل) دون تعاطف حقيقي. المخرج يؤكد تحيز الفرقة، لا حاجة المستخدم. (نتاشا جين، ٢٠١٧). التفكير التصميمي §10

التصميم المعماري (مالك: system-design.html)

المصطلحالتعريفأين يظهر
السياق المحدود (Bounded Context) حد دلالي ينطبق فيه نموذج النطاق. "الطلب" يعني أشياء مختلفة في المبيعات (عرض، تفاوض) مقابل التنفيذ (تعبئة، شحن). سياق محدود واحد = خدمة واحدة (DDD الاستراتيجي). التصميم المعماري §7
نظرية CAP (CAP Theorem) في انقسام شبكة، يجب اختيار الاتساق أو التوفر. لا يمكن كليهما. كل نظام بيانات موزع يتخذ هذا الاختيار صريحاً أو ضمنياً. التصميم المعماري §5
PACELC يُحسّن CAP: حتى بدون انقسامات، توجد مفاضلة زمن وصول/اتساق (ELC). "إذا انقسم → أ أو ج؛ وإلا → ز أو ج" (عابدي، ٢٠١٠). التصميم المعماري §5
قانون كونواي (Conway's Law) "المنظمات التي تصمم أنظمة... تنتج تصاميم نسخاً لهياكل اتصالاتها." حدود الخدمة يجب أن تتماشى مع حدود الفريق. التصميم المعماري §5، §9
إخفاء المعلومات (Information Hiding) حدود الوحدات يجب أن تخفي قرارات التصميم المرجح تغييرها، لا مجرد البيانات. "سبب بنية البيانات" هو ما يُخفى (بارناس، ١٩٧٢). التصميم المعماري §5
نموذج الاتساق (Consistency Model) الضمان الذي يعد به API للقراءات/الكتابات: قوي (خطي)، تسلسلي، سببي، نهائي، قراءة كتاباتك، قراءات مترادفة. كل عقد API يعد ضمنياً أو صريحاً بواحد. التصميم المعماري §5، §6
مجال الفشل (Failure Domain) مربع مرسوم حول مكون: إذا فقد هذا الصندوق الطاقة، ماذا يتوقف أيضاً؟ إذا نُشر بخطأ، ما دائرة الانفجار؟ إذا فسد DB الخاص به، ما البيانات المفقودة؟ التصميم الجيد يقلل دائرة الانفجار. التصميم المعماري §7، §10
مفتاح التساوي الذاتي (Idempotency Key) مفتاح مولد من العميل يُحمل على كل طلب مغير للحالة. الخادم يخزن مفتاح → تعيين استجابة لـ ٢٤ ساعة. مفتاح مكرر يعيد الاستجابة الأصلية. يمكّن إعادة المحاولات الآمنة. التصميم المعماري §6، §7؛ تصميم API §8، §9
قاطع الدائرة (Circuit Breaker) توقف عن استدعاء تبعية فاشلة، أفشل بسرعة، أعد المحاولة بعد مهلة. يمنع الفشل المتتالي. (Hystrix، Resilience4j، Go-breaker). التصميم المعماري §6
ملحمة (Saga) معاملة موزعة عبر إجراءات تعويضية: تم_وضع_الطلب → احجز_المخزون → احسب_الدفع → إذا فشل أي منها، شغّل التعويضات بالعكس (أطلق_المخزون، رد_الدفع). التصميم المعماري §6، §10
سجل قرار معماري (ADR) Markdown خفيف: عنوان، حالة، سياق، قرار، عواقب. متعقب بـ Git. يلتقط لماذا، لا ماذا فقط (نيجارد، ٢٠١١). التصميم المعماري §9
أحادي نمطي (Modular Monolith) نشر واحد، حدود وحدات داخلية صارمة (مفروضة بالتقنين، حزم منفصلة، عقود صريحة). معظم فوائد الخدمات المصغرة دون ضريبة النظام الموزع. التصميم المعماري §6
كائنات دائمة (Durable Objects) بدون خادم ذات حالة: حوسبة + تخزين متجاوران عند الحافة. حد "الخدمة" يصبح دالة + تخزين مرفق (Cloudflare، ٢٠٢١+). التصميم المعماري §8، §11
معمارية قاعدة الكود (Codebase Architecture) الشكل المادي للحدود: شجرة المجلدات. مجلدات الميزات مقابل المجلدات الطبقية، الموضع المشترك (colocation)، ولماذا src/. إذا لم يستطع الكود رؤية الحدود فحدودك غير موجودة — ويجب أن تقابل وحدات التسليم مجلدات الميزات (شرائح عمودية). التصميم المعماري §7؛ ممارسة العمل الحر (EN) §النطاق

تصميم API (مالك: api-design.html)

المصطلحالتعريفأين يظهر
عقد الواجهة (الكلي) (Interface Contract) الموارد، العمليات، الإصدار، المصادقة، حدود المعدل، سياسة الإهمال، غلاف الخطأ، استراتيجية التصفح، دلالات التساوي الذاتي. ما يراه المستهلك. تصميم API §0
عقد السلك (الدقيق) (Wire Contract) تنسيق التسلسل، قواعد تطور المخطط، قابلية الحقل للصفر، قابلية التعداد للتمديد، تنسيقات الطابع الزمني، ترميز المؤشر، الضغط، النقل (HTTP/1.1، HTTP/2، HTTP/3، gRPC، WebSocket). ما تقوله البايتات. تصميم API §0
التساوي الذاتي (Idempotency) عملية يمكن تطبيقها عدة مرات بنفس تأثير المرة الواحدة. كل نقطة نهاية مغيرة للحالة يجب أن تقبل encabezado Idempotency-Key. تصميم API §8، §9؛ التصميم المعماري §6
تفاصيل المشكلة RFC 9457 (Problem Details) غلاف خطأ قياسي: type (URI)، title، status، detail، instance، retry_after. العملاء يبدلون (switch) على type، لا مطابقة نصوص. تصميم API §8، §9
قواعد تطور المخطط (Schema Evolution Rules) توافق خلفي/أمامي رسمي: أضف حقولاً اختيارية، لا تزحزح مطلوبة، لا تغير نوع، امتدادات التعداد آمنة إذا أهمل المستهلكون المجهول (Avro/Protobuf/JSON Schema). تصميم API §5
تصفح بالمؤشر (Keyset/Cursor Pagination) تصفح باستخدام مفتاح ترتيب مستقر (after: "cursor") بدلاً من الإزاحة. O(1) مقابل O(n) للصفوف المتخطاة. افتراضي للمجموعات النامية. تصميم API §9، §10
رأس الغروب (Sunset Header) Sunset: Sat, 01 Jan 2027 00:00:00 GMT + Link: ; rel="successor-version". إشعار إهمال قابل للقراءة آلياً. تصميم API §9
اختبار العقد (Contract Testing) بوابة CI: التنفيذ يجب أن يطابق المخطط. Pact (موجه بالمستهلك)، Dredd، Schemathesis. يمنع انحراف المخطط. تصميم API §10
API كمنتج (API as Product) اعتبر العقد منتجاً مع مدير منتج، مقاييس (تبني، زمن وصول p99، تكرار التغيير الكاسر)، ودورة حياة. لا قطعة أثرية تقنية (كين لين). تصميم API §10، §11

تصميم واجهات المستخدم وتجربة المستخدم والويب (مالك: ui-ux-web-design.html)

المصطلحالتعريفأين يظهر
مصفوفة رؤية الحالة (State Visibility Matrix) كل شاشة × كل حالة (سكون/تحميل/خطأ جزئي/خطأ/فارغ/غير متصل) = لا مفاجآت. مخرج أساسي من الإيقاع. UI/UX §9
الرموز كوقت تشغيل (Tokens as Runtime) رموز التصميم تترجم إلى خصائص CSS مخصصة؛ المنصة تحلها. تغيير رمز = تغيير متغير CSS واحد = انتشار فوري لكل مكون. UI/UX §6؛ HTML & CSS §6
إمكانية الوصول كافتراض (Accessibility as Default) HTML الدلالي = إمكانية وصول مجانية؛ ARIA فقط عند وجود فجوة دلالية. WCAG 2.2 AA خط أساس. UI/UX §1، §8؛ HTML & CSS §1، §8
الحركة كمعنى (Motion as Meaning) الحركة تفسر العلاقات المكانية (من أين جاء هذا؟) لا "إبهاج". prefers-reduced-motion يحترم افتراضياً. UI/UX §8؛ HTML & CSS §8
قوانين الجشطالت (Gestalt Principles) القرب، التشابه، الإغلاق، الاستمرارية، الشكل/الأرض، المصير المشترك. تجميع بصري يفسر سلوك المسح. التخطيط = جشطالت مطبق. UI/UX §5
قانون فيتس (Fitts's Law) زمن اكتساب الهدف = f(المسافة، الحجم). أهداف أكبر، أقرب = أسرع. الزوايا/الحواف = حجم لا نهائي (شريط قائمة Mac، زر بدء Windows). UI/UX §5
قانون هيك (Hick's Law) زمن القرار = log₂(n+1) خيارات. قلل الخيارات → قرارات أسرع. كشف تدريجي، افتراضات ذكية، تقطيع. UI/UX §5
بدائيات UI بدون رأس (Headless UI Primitives) سلوك + إمكانية وصول + إدارة حالة، صفر آراء تصميمية (Radix، Headless UI، ARIA Kit). أنظمة التصميم توفر الطبقة البصرية فقط. UI/UX §7
القابلية للإدراك (Affordance) إمكانية فعل يدركها المستخدم. القابلية المُدرَكة ≠ القابلية الحقيقية. الأزرار تبدو قابلة للضغط، والروابط تبدو قابلة للنقر. الإشارات (signifiers) توصل القابلية (جيبسون ١٩٧٧، نورمان ١٩٨٨). UI/UX §5
فجوة التنفيذ / التقييم (Gulf of Execution / Evaluation) فجوة التنفيذ: نية المستخدم → فعل النظام. فجوة التقييم: حالة النظام → فهم المستخدم. الواجهة الجيدة تضيّق الاثنتين (نورمان، ١٩٨٨). UI/UX §5
رموز التصميم (Design Tokens) قرارات تصميم مستقلة عن المنصة (اللون، الفراغ، الخط، الحركة، الحدود، الظل) كبيانات منظمة. تُصرَّف إلى خصائص CSS مخصصة، وiOS، وأندرويد، إلخ (W3C DTCG). UI/UX §7؛ HTML & CSS §7، §8
WCAG / POUR مدرَك، قابل للتشغيل، مفهوم، متين (Perceivable, Operable, Understandable, Robust). معايير نجاح قابلة للاختبار (A/AA/AAA). إمكانية الوصول حق مدني، لا ميزة. UI/UX §5، §8
الأنماط الخادعة (Dark Patterns) أنماط مضللة (فندق الصراصير، التكاليف المخفية، الاستمرارية القسرية). أصبحت منظمة الآن: قانون الخدمات الرقمية الأوروبي (٢٠٢٢)، وقانون حذف كاليفورنيا (٢٠٢٣)، وقاعدة الخيار السلبي FTC. UI/UX §11

AOM (نموذج كائن إمكانية الوصول) / شجرة إمكانية الوصول شجرة موازية مشتقة من DOM، مفلترة للدوال. HTML & CSS §0، §1، §5
شجرة العرض (Render Tree) DOM + قيم محسوبة → صناديق. التدرج، التخطيط، الرسم، والتركيب يحدثون هنا. ثلاث شجرات، مصدر واحد: HTML الذي تكتبه. HTML & CSS §0، §5
خوارزمية تدرج CSS (CSS Cascade Algorithm) المصدر (وكيل المستخدم/المستخدم/المؤلف) → الأهمية (!important) → التحديدية (ID/فئة/نوع) → ترتيب المصدر → قرب النطاق → ترتيب الطبقات. حتمي، قابل للفحص في تبويب DevTools "Computed". HTML & CSS §1، §5
سياق التنسيق (Formatting Context) BFC (كتلي): طفو، هوامش، إزالة. Flex: محور رئيسي/متقاطع، محاذاة، توزيع. Grid: مسارات، خطوط، مناطق، وضع تلقائي. كل سياق خوارزمية تخطيط خاصة. HTML & CSS §1، §5
التحجيم الجوهري (Intrinsic Sizing) min-content = الأصغر بلا تجاوز. max-content = الأكبر بلا تفاف. fit-content(limit) = clamp(min-content، limit، max-content). Grid minmax()، auto-fit، auto-fill تستخدم هذه. HTML & CSS §5
خصائص CSS المخصصة (CSS Custom Properties) الخصائص المخصصة تورث، تتدرج، لها بديل (var(--x, fallback)). @property يسجل نوع (، )، قيمة أولية، توريث: true/false. يمكّن تحريك، تحقق، OM منوع. HTML & CSS §1، §5، §8
التحسين التدريجي (Progressive Enhancement) HTML يعمل بلا CSS. CSS يعمل بلا JS. JS يعزز، لا يحجب. المنصة تضمن هذا إن لم تكسره (مثلاً HTML & CSS §1، §8؛ UI/UX §2؛ معسكرات §2؛ التصميم المعماري §6
استعلام الحاوية (Container Query) @container يستعلم حجم الأب لا المنفذ. المكون يملك منطق تجاوبه. بطاقة في شريط جانبي مقابل عمود رئيسي تحتاج نقاط كسر مختلفة. HTML & CSS §3، §9
النوعية (Specificity) (a,b,c) = (عدد المعرّفات، عدد الأصناف/السمات/الأصناف الزائفة، عدد الأنواع/العناصر الزائفة). #id .class:hover = (1,2,0). الأعلى يفوز. ليست أساس ١٠: (0,11,0) < (1,0,0). HTML & CSS §5
طبقات التتالي (Cascade Layers @layer) ترتيب أصل صريح: @layer reset, base, components, utilities. CSS طرف ثالث داخل طبقتها الخاصة. لا مزيد من تصعيد !important. HTML & CSS §1، §3، §7
الخصائص المنطقية (Logical Properties) margin-inline-start وpadding-inline-end وborder-inline-start تنعكس تلقائياً. Flex وGrid يحترمان dir="rtl" دون CSS إضافي. HTML & CSS §1، §9
OKLCH / OKLAB فراغات لونية إدراكية. الإضاءة محفوظة عبر تغييرات الصبغة؛ لا ألوان علامة تجارية "متهتزة" في الوضع الداكن. تحل محل HSL في أنظمة الرموز. HTML & CSS §1، §9
الألوان المفروضة (Forced Colors) عند @media (forced-colors: active) تُعطَّل الخلفيات والظلال وتتولى ألوان النظام. يضمن border: 1px solid CanvasText الرؤية. HTML & CSS §9

حلقة المطور (مالك: how-developers-think-frontend.html)

المصطلحالتعريفأين يظهر
نموذج ذهني ثلاثي الخيوط (Three-Thread Mental Model) خيط 1: النموذج (هياكل البيانات، شكل الحالة). خيط 2: العرض (البنية + التخطيط). خيط 3: التدفق (أحداث، حركة بيانات، منطق). تدور فيهم، كل دورة أعمق. حلقة المطور §1
الهيكل العظمي → تعميق → تلميع (Skeleton → Deepen → Polish) الدورة 0: توضيح. الدورة 1: أبسط الهياكل، HTML دلالي فقط، معالجات فارغة. الدورة 2: ترقية حيث يظهر الألم. الدورة 3: أداء، حالات حافة، إمكانية وصول. حلقة المطور §1، §3، §4، §5
شكل البيانات يقود واجهة المستخدم (Data Shape Drives UI) الأسماء وحقولها تحدد شجرة المكون، لا التخطيط البصري. إذا كانت بياناتك الأساسية شجرة، واجهة المستخدم ستكون بها تكرار في مكان ما. حلقة المطور §13
الحالة تعيش حيث تُشارك (State Lives Where It's Shared) ارفع الحالة لأدنى سلف مشترك؛ استخلص، لا تكرر. تخزين القيم المستخلصة = أحد أكثر أخطاء حالة الواجهة الأمامية شيوعاً. حلقة المطور §13
نسخ أولاً، افهم لاحقاً (Copy First, Understand Later) المطورون الكبار رأوا النمط (قائمة، نموذج، مودال، لوحة) عشرات المرات. يبنون الهيكل من ذاكرة العضلات، ثم يتكيفون. حلقة المطور §7
YAGNI (أنت لن تحتاجه) ابدأ بأبسط بنية (مصفوفة كائنات). ترقّ إلى Map فقط عندما تحتاج بحثاً سريعاً ("هل هذا في السلة؟" → Map.has هو O(1)). لا تصمم مسبقاً لأداء لا تحتاجه بعد. حلقة المطور §2، §3
الإيقاع، لا الخوارزمية (Rhythm, Not Algorithm) المدخلات غير معرفة مسبقاً، الخطوات غير حتمية، لا إنهاء ثابت. الإيقاع = نمط تتقنه لتتمكن من ارتجاله. المطورون الكبار يعزفون القاعدة الكودية. المبتدئون يعزفون النوتات. حلقة المطور §10
الحالة المشتقة (Derived State) قيم تُحسب من حالة أخرى وقت العرض (قائمة مفلترة، عدد نشط). لا تخزّن قيماً مشتقة في الحالة أبداً — هذا أكثر أخطاء الواجهات الأمامية شيوعاً. حلقة المطور §13
التطوير الحلزوني / التكراري التزايدي (Spiral / IID) التطوير التكراري والتزايدي (لارمان وباسيلي، ٢٠٠٣) أقدم من الشلال. بوهم سماه "حلزونياً" (١٩٨٦): خطة → تحليل مخاطر → هندسة → تقييم، وكل دورة أعمق. حلقة المطور §11
الرسم الخربش / الإطار / النموذج الأولي / MVP ثلاثة محاور: الواقعية (كم يبدو حقيقياً)، وقابلية الرمي (هل يُرمى؟)، والسلوك (ثابت مقابل قابل للنقر). الرسم الخربش = قابلية رمي عالية + واقعية منخفضة + بلا سلوك. MVP = قابلية رمي منخفضة + واقعية إنتاجية + يعمل بالكامل. حلقة المطور §12

المصطلحالتعريفأين يظهر
ضيف في مضيف (Guest in a Host) JS = لغة أساسية؛ المضيف يوفر العموميات (window، fs، Deno، KV). حدد المضيف أولاً. require → Node/CommonJS. import + Deno → Deno. window → متصفح. JS اللغة §6
سلسلة البروتوتايب (Prototype Chain) Object.create(proto) هو البدائي. new + دالة منشئة + .prototype طبقة نحوية رقيقة. class (ES6) سكر نحوي — لا يغير التوريث الأحادي. this يربط في موقع الاستدعاء. JS اللغة §3
حلقة الأحداث (Event Loop) مسار استدعاء واحد. طابور مهام كبرى → مهام دقيقة → رسم. setTimeout = كبيرة. Promise.then/await = دقيقة. رهان Node.js (٢٠٠٩): نفس الحلقة تعمل جانب الخادم. JS اللغة §5
الإغلاقات تلتقط النطاق (Closures Capture Scope) الدالة "تتذكر" بيئتها اللفظية. function outer() { let x = 1; return function inner() { return x++; }; } — inner تتذكر x بعد عودة outer. قلب حساب اللامدا تحت بناء جملة C. JS اللغة §4
TC39 / إيكماسكربت (ECMAScript) المقترحات تمر: المرحلة ٠ (فكرة) → ١ (مقترح) → ٢ (مسودة) → ٣ (مرشح) → ٤ (مكتمل). تطبيقان مستقلان مطلوبان للمرحلة ٤. لهذا الميزات تستغرق سنوات — الويب لا يمكن أن ينكسر. JS اللغة §7
WASM (WebAssembly) هدف تجميع لـ C++/Rust/Go في المتصفح. JS لا يزال الغراء — WASM لا تلمس DOM مباشرة (مقترح anyref قيد التقدم). import { something } from 'wasm-module' = الرفع الثقيل في Rust/C++، JS طبقة تنسيق. JS اللغة §9
الترجمة الآنية (JIT Compilation) V8 يترجم المسارات الساخنة إلى كود آلة. "JS بطيئة" مقولة تجاوزها الزمن منذ عشرين عاماً. لكن: الإحماء (warm-up) موجود، وإلغاء التحسين يحدث، وeval/with يعطّلا التحسين. JS اللغة §8

المعسكر = مركز ثقل، لا نادٍ (Camp = Center of Gravity) المستودعات تخلط المعسكرات؛ تتبع من يملك أول رسم. CSS Zen Garden ≠ تطبيق React. المعسكرات §0
استراتيجية العرض تملي النموذج العقلي (Rendering Strategy Dictates Mental Model) SSR/RSC/Islands/SPA = افتراضات مختلفة لتدفق البيانات. RSC = دوال تعمل مرة لكل طلب/بناء؛ لا حلقة خطافات. المعسكرات §4، §10
TypeScript كحاجز حماية، لا هدف (TypeScript as Guardrail) أنواع على حدود API + props؛ الاستنتاج المحلي يتعامل مع الباقي. المهمة لا تزال JS صحيح أولاً. المعسكرات §7
الإشارات (Signals) وحدة تفاعلية دقيقة: تغيير خلية يحدث تحديثات الربط؛ دالة المكون غالباً لا تعيد التشغيل من أعلى لأسفل كما في رياكت. Angular/Vue/Svelte/Solid/Preact القياسية غير رياكت بحلول ٢٠٢٦. المعسكرات §5
المعسكر A — CMS / خادم كلاسيكي (Camp A: CMS / Classic Server) الخادم يملك المستند (PHP، Rails، Django). JS سكر اختياري. بوابات الإدارة غالباً تطبيقات SPA كاملة. معسكرات §1
المعسكر B — HTML أولاً / الجزر (Camp B: HTML-First / Islands) المستند هو المنتج، وJS أداة دقة. Astro: صفر JS افتراضياً؛ اختر الجزر (React، Preact، Svelte، Vue، Solid) حيث يلزم فقط. HTMX/Alpine: واجهة مدفوعة بالخادم. معسكرات §2
المعسكر C — SPA عميل (Camp C: Client SPA) المتصفح ينزّل قشرة التطبيق؛ توجيه على العميل؛ الخادم API غالباً. أداة البناء Vite. مكتبات الحالة (Redux، Zustand، Pinia). CRA توقف فبراير ٢٠٢٥. معسكرات §3
المعسكر D — ميتا-أطر العمل (Camp D: Meta-Framework) إطار حول مكتبة الواجهة: التوجيه، تحميل البيانات، استراتيجية العرض، التغليف، النشر. Next.js، Remix، React Router FW، Expo، Nuxt، SvelteKit، Angular، SolidStart، Qwik City. معسكرات §4
المعسكر E — عالم الإشارات غير React (Camp E: Signals World) Angular (إشارات + zone.js)، Vue 3 (ref/reactive)، Svelte 5 (runes)، Solid (createSignal)، Preact (@preact/signals). تحديثات دقيقة؛ دالة المكوّن غالباً لا تُعاد من الأعلى للأسفل. معسكرات §5
المعسكر F — WASM / واجهة غير JS (Camp F: WASM / Non-JS UI) Rust/C++/C#/Zig في المتصفح عبر WASM. حساب ثقيل (برامج الترميز، CAD، ألعاب، تشفير). JS عادةً يملك لاصق DOM. Yew/Leptos (Rust)، Blazor (C#). معسكرات §6
نموذج صندوق إعادة العرض (Re-render Box Model) النموذج العقلي لـReact: دالة المكوّن = دالة نقية من props+state → UI. أعد تشغيلها عند تغير الحالة → diff → commit. الإغلاقات تلتقط قيماً مخصوصة بالعرض. لا ينطبق على أطر الإشارات أو مكوّنات الخادم. معسكرات §10

حل المشكلات (مالك: problem-solving.html)

المصطلحالتعريفأين يظهر
المشكلة محددة المعالم (Well-Defined Problem) مشكلة بمدخلات واضحة ومخرجات واضحة ومعايير نجاح موضوعية. تأخذ خوارزمية (تسلسل خطوات ثابت ومحدود). أمثلة: تحديات HackerRank، البراهين الرياضية. حل المشكلات §1
المشكلة الشريرة (Wicked Problem) مشكلة بمدخلات متطورة ومخرجات ذاتية وبلا قاعدة توقف حقيقية. تأخذ إيقاعاً (حلقة تكررية). أمثلة: ميزات الواجهات، قرارات المنتج. قارنها بالمحددة المعالم. حل المشكلات §1؛ التفكير التصميمي §2
مراحل بوليا الأربع (Pólya's Four Phases) الإيقاع العالمي لحل المشكلات (١٩٤٥): افهم ← خطط ← نفّذ ← انظر للخلف. إيقاع لا شلال — تدور وتعود للمراحل المبكرة حين تكشف اللاحقة ثغرات. حل المشكلات §2
الاستدلال الإرشادي (Heuristic) قاعدة تجريبية تساعد غالباً لكنها لا تضمن حلاً. قارنها بالخوارزمية التي تضمن النتيجة. استدلالات بوليا: القياس، التخصيص، العمل بالعكس، التحليل، التغيير، العناصر المساعدة، التعميم. حل المشكلات §4
التفكير الحسابي (Computational Thinking) عدسة هيكلة المشكلات حسابياً (بابيرت ١٩٨٠، وينغ ٢٠٠٦). أربع ركائز: التحليل، التعرف على الأنماط، التجريد، تصميم الخوارزميات. هذه حركات داخل مراحل بوليا. حل المشكلات §3
فوق-الإدراك (Metacognition) التفكير في تفكيرك أثناء حل المشكلات — مراقبة التقدم، تقرير متى تتخلى عن نهج، إعادة التثبيت على الهدف. إضافة شوينفيلد (١٩٨٥) الرئيسية لبوليا: الاستراتيجيات وحدها ضعيفة دون تحكم فوق-إدراكي. حل المشكلات §5
التنقيح التدريجي (Stepwise Refinement) التحليل من الأعلى للأسفل في البرمجة (ويرث، ١٩٧١): ابدأ بالمشكلة كاملة، عبّر عن الحل بـ"صناديق سوداء"، ونقّح نزولاً حتى يصبح كل صندوق عملية ملموسة. مكافئ حل المشكلات لـ"ارسم شكل البيانات أولاً". حل المشكلات §6
نموذج تصميم الخوارزميات (Algorithm Design Paradigm) نهج أساسي لتصميم الخوارزميات. الفئات: القوة الغاشمة (جرّب كل شيء)، الجشع (المثلى المحلي)، فرّق تسد (مسائل فرعية مستقلة)، البرمجة الديناميكية (مسائل فرعية متداخلة)، التراجع (جرّب واقطع)، جدول التجزئة (بحث O(1)). حل المشكلات §7
حفظ الأنماط (Pattern Filing) فعل المرحلة الرابعة (انظر للخلف): تصنيف مشكلة محلولة بنمطها وبالإشارة التي عرّفتك عليه. يبني التعرف على الأنماط مع الوقت. "عدّ التكرارات ← خريطة تجزئة. الإشارة: كم مرة يظهر كل X". حل المشكلات §10
تصحيح البطة المطاطية (Rubber Duck Debugging) شرح الكود سطراً سطراً لجسم جماد (هنت وتوماس، المبرمج البراغماتي، ١٩٩٩). يجبرك على التلفظ بالافتراضات؛ الخطأ عادة في افتراض غير معلن. المرحلة ١ (افهم) مطبقة على كودك. حل المشكلات §9
التصحيح المبني على الفرضيات (Hypothesis-Driven Debugging) تطبيق المنهج العلمي على التصحيح: لاحظ ← افترض ← توقع ← اختبر ← خلص. لا تغيّر الكود دون فرضية مؤكدة؛ التخمين ليس تصحيحاً. حل المشكلات §9
الطلاقة مقابل قوة التخزين (Fluency vs Storage Strength) قراءة حل تبني طلاقة (فهم اللحظة) لا قوة تخزين (استرجاع طويل الأمد). قوة التخزين تأتي من الاسترجاع المجهد: حاول أولاً، حل ثم قارن، أعد الحل من الذاكرة، ونوّع أنواع المشكلات. حل المشكلات §11

الخوارزميات وهياكل البيانات (مالك: algorithms-and-data-structures.html)

المصطلحالتعريفأين يظهر
خريطة التجزئة (Hash Map) مخزن مفتاح→قيمة ببحث O(1) وسطياً. يُجزّأ المفتاح إلى دلو؛ الاصطدامات تُعالَج بالتسلسل أو العنوان المفتوح، وعامل الحمولة يقود إعادة التحجيم. استخدم Map/Set لا كائناً عادياً لدلالات مفاتيح حقيقية. يملك أنماط العد/الرؤية/الزوج التكميلي. الخوارزميات وهياكل البيانات (EN) §2
المؤشران (Two Pointers) مؤشران أيسر/أيمن يتحركان باتجاه واحد لكل منهما على مدخلات مرتبة (أو متناظرة). O(n) لأن كل عنصر يُزار مرتين على الأكثر. مجاميع الأزواج، إزالة التكرار، القلب في المكان، three-sum. الخوارزميات وهياكل البيانات (EN) §2
النافذة المنزلقة (Sliding Window) وسّع يميناً، انكمش يساراً عند كسر القيد، وسجّل الأفضل. O(n) مطفأة. النمط وراء "أطول سلسلة بلا تكرار" و"أقصى مجموع نافذة طولها k" و"أصغر نافذة". الخوارزميات وهياكل البيانات (EN) §2
المكدس الرتيب (Monotonic Stack) مكدس يُبقى مرتباً بالفرقعة بينما يكسر العنصر الجديد الترتيب. يعطي "العنصر الأكبر التالي" في O(n) — النمط الخارق لعائلة كاملة من مسائل المكدسات. الخوارزميات وهياكل البيانات (EN) §3
تري (Trie) شجرة سوابق مشتركة؛ كل عقدة حرف، والكلمات تشارك سوابقها بنيوياً. بحث O(الطول) لعمليات السوابق — الإكمال التلقائي، تقسيم الكلمات، عد السوابق. المشاركة البنيوية تتفوق على تخزين كل سابقة. الخوارزميات وهياكل البيانات (EN) §4
اتحاد-بحث (Union-Find) بنية ترابطية شبه O(1): find يمشي إلى الجذر، union يربط الجذور (بضغط المسار والاتحاد بالرتبة). تتفوق على إعادة تشغيل BFS عند وصول الحواف واحدة تلو الأخرى — المكونات المترابطة، كشف الدورات، كروسكال. الخوارزميات وهياكل البيانات (EN) §5
الترتيب الطوبولوجي (Topological Sort) ترتيب عقد DAG بحيث تشير كل حافة للأمام — خوارزمية كان أو DFS بترتيب لاحق؛ تعمل كشف دورات مزدوجاً. نمط "المتطلبات/التبعيات/الترتيب". الخوارزميات وهياكل البيانات (EN) §5
البحث الثنائي (Binary Search) تنصيف فضاء البحث عبر مسند رتيب، لا مصفوفات مرتبة فقط: "أول فهرس حيث isGood(i) صحيح" على نطاق نصف مفتوح [lo, hi). القالب الذي لا يخطئ بواحد؛ يجيب أيضاً عن مسائل "صغّر أقصى X" الرتيبة. الخوارزميات وهياكل البيانات (EN) §6
البرمجة الديناميكية (Dynamic Programming) تعداد مخزّن للمسائل الفرعية المتداخلة: عرّف الحالة، اكتب الانتقال، حدد الحالات الأساسية، ثم خزّن (أو جدول). نمط "صغّر التكلفة / عظّم القيمة / اختر مجموعات فرعية". العودية المخزنة أولاً هي المسار الكسول الصحيح. الخوارزميات وهياكل البيانات (EN) §7
حجة التبادل (Exchange Argument) البرهان أن اختياراً جشعاً آمن: "إذا اختلف حل أمثل عن حلي، أستطيع مبادلة اختياري دون أن يسوء". دون هذه الحجة، الجشع مقامرة والبرمجة الديناميكية هي الجواب الآمن. الخوارزميات وهياكل البيانات (EN) §8

علوم الحاسوب وهندسة البرمجيات (مالك: cs-and-software-engineering.html)

المصطلحالتعريفأين يظهر
علوم الحاسوب (Computer Science) علم الحساب — ما يمكن حسابه، وبأي كفاءة، وما الحدود الأساسية له. علم: يكتشف الممكن ويثبت النظريات. أسسه تورينج (١٩٣٦). CS & SE §2
هندسة البرمجيات (Software Engineering) الانضباط الهندسي لبناء أنظمة برمجية موثوقة وقابلة للصيانة على نطاق واسع. هندسة: تُبنى تحت قيود، تجري مفاضلات، وتُحكم بالنتائج. رسّخ اسمها مؤتمر ناتو (١٩٦٨). CS & SE §3
سمة الجودة (Quality Attribute) معيار تقيّم به حلاً — وتُسمى أيضاً "متطلباً غير وظيفي" أو "الإيليتيز". ISO 25010 يعرّف ٨: الملاءمة الوظيفية، كفاءة الأداء، التوافق، قابلية الاستخدام، الموثوقية، الأمان، قابلية الصيانة، قابلية النقل. CS & SE §4
تعقيد الوقت (Time Complexity) كيف ينمو زمن تشغيل الخوارزمية مع نمو حجم المدخلات. يُقاس بتدوين O الكبير. O(n) خطي — ضاعِف المدخلات فيتضاعف الزمن. O(n²) تربيعي — ضاعِف المدخلات فيتضاعف الزمن أربع مرات. CS & SE §5
تعقيد الفضاء (Space Complexity) كيف ينمو استهلاك الخوارزمية للذاكرة مع نمو حجم المدخلات. يُقاس بتدوين O الكبير. ترتيب في الموقع يستخدم O(1) فضاء إضافياً؛ خريطة تجزئة تستخدم O(n). CS & SE §5
تدوين O الكبير (Big O Notation) التدوين الرياضي لتصنيف كفاءة الخوارزميات — يصف الحد العلوي لمعدل النمو مع اقتراب حجم المدخلات من اللانهاية. أدخله باخمان (١٨٩٤) وروّجه لانداو في الرياضيات، وتبناه كنوث لعلوم الحاسوب. الفئات القياسية: O(1)، O(log n)، O(n)، O(n log n)، O(n²)، O(2ⁿ)، O(n!). CS & SE §5
المفاضلة (Trade-off) قرار ظرفي يتحسن فيه معيار على حساب آخر. في البرمجيات: الوقت مقابل الفضاء، القراءة مقابل الأداء، البساطة مقابل المرونة. مهارة الهندسة هي جعل المفاضلات صريحة — تسمية ما تضحي به ولماذا. CS & SE §6
جبهة باريتو (Pareto Front) مجموعة الحلول التي لا يمكنك تحسين معيار فيها دون الإضرار بآخر. الحل "باريتو-أمثل" إذا لم يوجد حل آخر أفضل في كل المعايير. معظم قرارات العالم الحقيقي هي اختيار حل باريتو-أمثل يناسب سياقك. CS & SE §6
التحسين المبكر (Premature Optimization) التحسين قبل أن تعرف أنه يهم. كنوث (١٩٧٤): "التحسين المبكر هو أصل كل الشرور". العلاج: قس أولاً، حسّن المسار الحرج فقط، واترك الباقي بسيطاً. CS & SE §7، §9ب
KISS — اجعل البساطة هدفاً (Keep It Simple, Stupid) الأصل: كيلي جونسون في سكونك وركس بلوكهيد (ستينيات القرن العشرين). المبدأ: البساطة هدف رئيسي؛ التعقيد غير الضروري يُتجنب. عملياً: الحل الأبسط عادةً الأكثر قابلية للصيانة والاختبار والأسرع إطلاقاً. CS & SE §8
YAGNI — لن تحتاجه (You Aren't Gonna Need It) الأصل: كينت بيك، البرمجة القصوى (١٩٩٩). المبدأ: "نفّذ الأشياء عندما تحتاجها فعلاً، لا عندما تتوقع فقط أنك ستحتاجها". لا تبنِ مرونة لا تحتاجها بعد. CS & SE §8
DRY — لا تكرر نفسك (Don't Repeat Yourself) الأصل: هنت وتوماس، المبرمج البراغماتي (١٩٩٩). المبدأ: "كل معلومة يجب أن يكون لها تمثيل واحد واضح موثوق". يتعلق بتكرار المعرفة لا بتكرار الكود — دالتان متشابهتان ظاهرياً بقواعد عمل مختلفة يجب ألا تُدمجا. CS & SE §8
SOLID خمسة مبادئ تصميم كائنية: المسؤولية الواحدة، مفتوح-مغلق، استبدال ليسكوف، فصل الواجهات، قلب الاعتماد. الأصل: روبرت سي مارتن (٢٠٠٠)؛ الصيغة المختصرة صاغها مايكل فيذرز (٢٠٠٤). CS & SE §8
ISO/IEC 25010 المعيار الدولي لتقييم جودة البرمجيات (٢٠١١) — استبدل ISO 9126 (١٩٩١). يعرّف ٨ خصائص جودة. الإطار الرسمي لـ"ما يجعل الحل جيداً". CS & SE §4
فصل الاهتمامات (Separation of Concerns) الأصل: ديكسترا (١٩٧٤). قسّم البرنامج إلى أقسام يعالج كلٌّ منها اهتماماً منفصلاً. في الواجهات الأمامية: HTML (البنية)، CSS (العرض)، JS (السلوك) — الفصل نفسه كخيوط الإيقاع الثلاثة (النموذج، العرض، التدفق). CS & SE §8

عملية تطوير البرمجيات (مالك: software-development-process.html)

المصطلحالتعريفأين يظهر
SDLC — دورة حياة تطوير البرمجيات تسلسل المراحل التي يمر بها نظام برمجي من الولادة إلى التقاعد: المتطلبات ← التصميم ← التنفيذ ← الاختبار ← النشر ← الصيانة. يصف ما يحدث، لا كيف تتنقل فيه. عملية تطوير البرمجيات §2
المنهجية (Methodology) مخطط للتنقل في SDLC — يخبرك بالترتيب والإيقاع والأدوار. الشلال ينفذ المراحل تسلسلياً؛ أجايل تكررياً؛ الحلزوني بدورات مدفوعة بالمخاطر. عملية تطوير البرمجيات §1
أجايل (Agile) فلسفة مظلة (ليست إطاراً واحداً) عبّرت عنها بيان أجايل (٢٠٠١). تحت المظلة: سكرم، كانبان، XP، لين، ديفأوبس. ٤ قيم، ١٢ مبدأ. عملية تطوير البرمجيات §1، §3
بيان أجايل (Agile Manifesto) وثيقة ٢٠٠١ بقلم ١٧ مطوراً في سنوبيرد، يوتا. ٤ قيم: الأفراد والتفاعلات فوق العمليات والأدوات، البرمجيات العاملة فوق التوثيق الشامل، تعاون العميل فوق التفاوض على العقود، الاستجابة للتغيير فوق اتباع الخطة. ١٢ مبدأ. عملية تطوير البرمجيات §3
الشلال (Waterfall) المنهجية التسلسلية: أنجز كل المتطلبات، ثم كل التصميم، ثم كل التنفيذ، وهكذا. رويز (١٩٧٠) حذّر فعلاً من المسار الواحد — قرأ الناس المخطط وتجاهلوا التحذير. عملية تطوير البرمجيات §1ب
سكرم (Scrum) إطار أجايل الأكثر اعتماداً. ٣ أدوار (مالك المنتج، المطورون، سكرم ماستر)، ٥ أحداث (سبرنت، تخطيط السبرنت، سكرم يومي، مراجعة السبرنت، استرجاع السبرنت)، ٣ مصنوعات (تراكم المنتج، تراكم السبرنت، الزيادة). مبني على نظرية التحكم التجريبي بالعملية. عملية تطوير البرمجيات §4
السبرنت (Sprint) صندوق زمني ثابت الطول (أسبوعان عادةً) تُنتج خلاله زيادة قابلة للاستخدام. حاوية كل أحداث سكرم الأخرى. عملية تطوير البرمجيات §4
كانبان (Kanban) منهج أجايل مبني على التدفق من نظام إنتاج تويوتا. ٦ ممارسات: صوّر سير العمل، حدّ العمل الجاري، أدر التدفق، اجعل السياسات صريحة، نفّذ حلقات تغذية راجعة، حسّن تعاونياً. مبني على السحب لا الصناديق الزمنية. عملية تطوير البرمجيات §5
العمل الجاري (WIP — Work in Progress) عدد العناصر قيد العمل حالياً. كانبان يحدّ WIP لكل عمود لمنع تبديل السياق وكشف الاختناقات. القيد المفتاحي في كانبان (مقابل صندوق سكرم الزمني). عملية تطوير البرمجيات §5
XP — البرمجة القصوى (Extreme Programming) كينت بيك (١٩٩٩). الممارسات الهندسية التي تجعل أجايل تعمل: TDD، البرمجة الثنائية، التكامل المستمر، إعادة الهيكلة، التصميم البسيط. "اجعلها تعمل، اجعلها صحيحة، اجعلها سريعة". عملية تطوير البرمجيات §6
ديفأوبس (DevOps) تقارب التطوير والتشغيل (٢٠٠٩). يؤتمت الاختبار ← النشر ← الصيانة عبر CI/CD والبنية التحتية ككود والمراقبة. يجعل عمليات النشر المتكررة منخفضة المخاطر ممكنة. عملية تطوير البرمجيات §6
CI/CD — التكامل المستمر / النشر المستمر CI: كل تغيير كود يُدمج ويُختبر آلياً. CD: إذا نجح CI يُنشر الكود للإنتاج آلياً. خط أنابيب ديفأوبس. عملية تطوير البرمجيات §6
التحكم التجريبي بالعملية (Empirical Process Control) النظرية خلف سكرم: حين لا تستطيع تعريف العملية (البرمجيات غير متوقعة)، اجعلها مرئية، افحصها كثيراً، وتكيف. "افحص وتكيف" مقابل العملية المعرفة (التصنيع — الخطوات معروفة، كررها). عملية تطوير البرمجيات §1ه
دورة حياة تطوير الوكلاء (ADLC) دورة حياة جديدة (٢٠٢٤–الحاضر) لبناء وكلاء ذكاء اصطناعي — أنظمة ذاتية تسعى لأهداف، تستخدم أدوات، وتتخذ إجراءات. ٥ مراحل: تصميم الوكيل ← بناء ← تقييم ← نشر بحواجز ← مراقبة الانحراف. المنتج هو وكيل AI نفسه، لا برمجيات تقليدية. عملية تطوير البرمجيات §9د
SDLC المعزز بالذكاء الاصطناعي (AI-augmented SDLC) SDLC التقليدي مع مساعدة AI في كل مرحلة (كوبايلوت يكتب الكود، AI يولد الاختبارات). ليست دورة جديدة — نفس SDLC مع تحول الإنسان من كاتب إلى مُقيّم. عملية تطوير البرمجيات §9د

ووردبريس وإنترنت CMS (مالك: wordpress-and-cms-internet.html)

CMS — نظام إدارة المحتوى نظام منتجه الأساسي تحرير المحتوى: نموذج محتوى مدعوم بقاعدة بيانات (أنواع المنشورات، التصنيفات، الحقول) مع لوحة إدارة ويب. ووردبريس يدير نحو ٤٣٪ من الويب (W3Techs). ووردبريس وإنترنت CMS (EN) §التعريف
