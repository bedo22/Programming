تصميم واجهات البرمجة (API) — كيف تجعل العقود الأنظمة تتحدث دون أن تتكلم

انضباط تعريف عقود تستطيع الخدمات والعملاء التطور المستقل حولها. وثائق شقيقة: التصميم المعماري (الطبقة المعمارية السابقة)، كيف يفكر المطورون (حلقة التنفيذ التالية)، تصميم واجهات المستخدم وتجربة المستخدم والويب (طبقة العرض التي تستهلك العقد).

اللغة: العربية · English

لماذا هذا المستند منفصل

معظم الدروس تعلم "كيف تستدعي API" أو "كيف تكتب ملف OpenAPI". تصميم API يبدأ بـ "ما العقد الذي يسمح للجانبين بالتحرك دون كسر بعضهما". إنه انضباط مستقل بتاريخه وطرقه وأوضاع فشله — ليس "REST مقابل GraphQL" كعقيدة، ليس "كتابة Swagger" كعمل روتيني، ليس "توليد SDK" كحل سحري. يلتقط هذا المستند إياه كاهتمام هندسي من الدرجة الأولى: طبقة الواجهة التي تغذي التصميم المعماري وحلقة المطور. إذا شحنت تغييرًا كاسرة أسقطت تطبيقًا جوّالًا في الإنتاج، فهذه هي الطبقة التي فاتتك.

٠. كيف تستخدم هذا المستند

ترتيب القراءة: مستقل. روابط تقاطعية:

  • أعلى إلى التصميم المعماري — التصميم المعماري يقرر حدود الخدمات وملكية البيانات؛ تصميم API يمثّل تلك الحدود كعقود قابلة للاستدعاء.
  • أسفل إلى كيف يفكر المطورون عند بناء ميزة واجهة أمامية — حلقة المطور تستهلك APIs؛ العقود السيئة تخلق احتكاكًا تمتصه الحلقة (حالات تحميل، معالجة أخطاء، إعادة محاولة، واجهة مستخدم تفاؤلية).
  • تقاطعي مع تصميم واجهات المستخدم وتجربة المستخدم والويب — كل شاشة قراءة وكتابة عبر عقد API؛ العقود العرجاء تتسلل إلى الواجهة كحالات ميتة، وأعاصير تنبيهات، وفشل غير مرئي.
  • تقاطعي مع جافاسكريبت عبر المكدسات — خيارات اللغة وبيئة التشغيل (TypeScript، Rust، Go) تُدار غالبًا بأريحية العقد (توليد الكود، التحقق من المخطط، التدفق).

الإجابة ثنائية الطبقة على "ما عقد API؟"

  • عقد الواجهة (كلي) — الموارد، العمليات، الإصدار، المصادقة، حدود المعدل، سياسة الإهمال، غلاف الخطأ، استراتيجية التصفح، دلالات التساوي الذاتي (idempotency). ما يراه المستهلك.
  • عقد السلك (دقيق) — تنسيق التسلسل، قواعد تطور المخطط، قابلية الحقل للصفر، قابلية التعداد للتمديد، تنسيقات الطابع الزمني، ترميز المؤشر (cursor)، الضغط، النقل (HTTP/1.1، HTTP/2، HTTP/3، gRPC، WebSocket). ما تقوله البايتات.

كلاهما تصميم API؛ لا يكتمل أحدهما دون الآخر. عقد الواجهة يضع الوعود؛ عقد السلك يجعلها قابلة للتحقق.

١. تعريف — ما هو تصميم API وما ليس به

ما هو

تصميم API هو النشاط المنضبط لـ تعريف عقود مستقرة وقابلة للتطور بين مكونات قابلة للنشر المستقل. ينتج قرارات — لا كود — تحدد:

  • طوبولوجيا الموارد — ما هي الأسماء؟ كيف ترتبط؟ (REST) أو ما سطح الاستعلام/التغيير؟ (GraphQL) أو ما توقيعات الخدمة/الطريقة؟ (gRPC).
  • دلالات العمليات — ما الذي تعد به كل استدعاء؟ (الأمان، التساوي الذاتي، ميزانية زمن الاستجابة، نموذج الاتساق).
  • عقد الخطأ — كيف يقول API "لا" بطريقة يستطيع العميل التصرف عليها برمجيًا؟ (رموز الخطأ، retry-after، تفاصيل المشكلة).
  • استراتيجية الإصدار — كيف نضيف، نغير، ونزيل دون كسر العملاء الحاليين؟ (إصدار في الرابط، إصدار في الهيدر، تطور المخطط).
  • الهوية والمصادقة — من يمكنه استدعاء ماذا؟ (OAuth 2.0، OIDC، mTLS، مفاتيح API، SPIFFE).
  • خطافات المراقبة — ما الذي يصدره API حتى يستطيع الجانبان التصحيح؟ (request-id، رؤوس التتبع، سجلات مهيكلة، مقاييس).
  • ضمانات التطور — ما التغييرات "آمنة" (إضافة حقل اختياري، إضافة قيمة تعداد) مقابل "كاسرة" (إزالة حقل، تغيير نوع، تغيير دلالات).

هذه القرارات مكلفة التغيير لاحقًا. هذه هي السمة المميزة: قرارات تصميم API لها تكلفة عكس عالية. تغييرات تنسيق السلك تتطلب نشرات منسقة. تغييرات عقد الواجهة تتطلب هجرات مستهلكين. كلاهما جهود تمتد لأسابيع في أي نظام غير تافه.

٣. تطور — انعكاسات القيد عبر نفس الفكرة

الفكرة الأساسية — حد مستقر بين مكونات قابلة للنشر المستقل — لم تتغير. ما تغير هو القيد المهيمن، والأسلوب الذي فاز:

٤. تقاطع مع الجيران — حيث تحد الممارسات الأخرى

الممارسةDNA مشتركحيث يختلفان
التصميم المعماري حدود الخدمات، ملكية البيانات، نماذج الاتساق، مجالات الفشل التصميم المعماري يقرر التفكيك؛ تصميم API يمثّل الحدود كعقود. تصميم معماري بدون عقود مخطط؛ عقود بدون تصميم معماري متسربة.
حلقة المطور (الواجهة الأمامية) جلب البيانات، التغييرات، معالجة الأخطاء، واجهة مستخدم تفاؤلية، تخزين مؤقت الحلقة تستهلك العقد؛ تصميم API ينتجه. العقود السيئة تجبر الحلقة على الترقيع (مؤشرات تحميل، منطق إعادة محاولة، تأكيدات نوع).
تصميم واجهات المستخدم وتجربة المستخدم والويب رؤية الحالة، إمكانيات الخطأ، هياكل تحميل، التحسين التدريجي UI/UX يقرر ما يراه الإنسان؛ تصميم API يقرر ما تتبادله الآلة. أفضل UX هو عقد يجعل الواجهة الصحيحة تافهة للبناء.
داخلية قاعدة البيانات تطور المخطط، الهجرات، الاتساق، الفهرسة مخطط قاعدة البيانات خاص؛ عقد API عام. تسريب أنواع DB (ObjectId، دقة الطابع الزمني، FK قابل للصفر) في API هو وضع فشل (§١٠).
تصميم البروتوكول (HTTP/QUIC) دلالات النقل، التأطير، الضغط، الأولوية البروتوكول كيف تتحرك البايتات؛ تصميم API ما تعنيه البايتات. المتعدد الإرسال HTTP/2/3 يغير تصميم API (لا تقسيم نطاقات، دفع خادم → تلميحات مبكرة).
تصميم SDK / مكتبة العميل بيئة العمل، أمان النوع، سياسات إعادة المحاولة، مساعدو التصفح SDK طبقة راحة؛ يجب أن يكون العقد الخام قابلاً للاستخدام بدونه. تصميم SDK أسفل من تصميم API.
بوابة API / شبكة خدمة تحديد المعدل، المصادقة، التوجيه، المراقبة، المرونة البوابة تفرض سياسة على الحافة؛ تصميم API يحدد العقد بالداخل. تكوين البوابة يتغير دون تغييرات عقد؛ تغييرات العقد تتطلب تحديثات بوابة.

عمليات متسلسلة متواصلة (CSP) Tony Hoare، ١٩٧٨ العمليات تتواصل عبر قنوات ذات نوع. العقود هي أنواع القنوات؛ الإصدار هو تطور بروتوكول القناة.
ساعات لامبرت و حدث-قبل Leslie Lamport، ١٩٧٨ مفاتيح التساوي الذاتي وتكرار الطلب تعتمد على الترتيب السببي. تسليم "مرة واحدة على الأقل" + التساوي الذاتي = دلالات مرة واحدة بالضبط.
نظرية CAP و PACELC Eric Brewer (٢٠٠٠)، Gilbert & Lynch (٢٠٠٢)، Daniel Abadi (٢٠١٠) كل عملية API تنطوي على خيار اتساق. العقد يجب أن يعلنه (قوي، نهائي، اقرأ كتاباتك، سببي).
قيد HATEOAS / الوسائط الفائقة Roy Fielding، ٢٠٠٠ العملاء يتنقلون عبر الروابط، لا عبر معرفة خارج النطاق. العقد تشمل القابلية للاكتشاف. نادراً ما تُنفذ بالكامل؛ الفكرة تشكل التصفح والإصدار.
قانون بوستل (مبدأ المتانة) Jon Postel، RFC 791 (١٩٨١) "كن ليبرالياً في ما تقبل، محافظاً في ما ترسل." تصميم API يطبق هذا على تطور المخطط: اقبل حقولًا إضافية، لا ترسل أبدًا حقولًا غير متوقعة.
نموذج نضج Richardson Leonard Richardson، ٢٠٠٨ أربع مستويات: RPC فوق HTTP → موارد → أفعال HTTP → وسائط فائقة. تشخيصي، ليس وصفي. معظم APIs الإنتاجية تجلس عند مستوى ٢–٣.
مبدأ تجزئة الواجهة (SOLID) Robert C. Martin، ٢٠٠٠ العملاء لا ينبغي أن يعتمدوا على طرق لا يستخدمونها. في APIs: موارد ضيقة، نماذج قراءة/كتابة منفصلة، تجنب "نقاط نهاية الآلهة" التي تعيد كل شيء.
قواعد تطور المخطط (Avro / Protobuf / JSON Schema) Apache Avro، Google Protobuf، IETF JSON Schema قواعد رسمية للتوافق الخلفي/الأمامي: أضف حقولًا اختيارية، لا تزيل مطلوبة، لا تغير نوع، امتدادات التعداد آمنة إذا أهمل المستهلكون المجهول.

٥ب. النماذج العقلية — كيف يفكر مصممو API فعلياً

النظريات أعلاه هي الحواجز الواقية. النماذج العقلية هي كيف تتنقل بداخلها. كل نموذج يضغط النظريات لسياق قرار محدد:

النموذجالفكرة الأساسيةمتى تصل إليهماذا يحل محل
العقد كمنتج API هو المنتج للمستهلك. الإصدار، الإهمال، الهجرة، والدعم هي إدارة منتج. تقرير مدة دعم v1؛ هل تكسر حقلاً؛ كتابة سجل التغييرات. "إنها مجرد واجهة" (تتعامل مع العقد كتفصيل تنفيذي).
المخطط كمصدر للحقيقة المخطط (OpenAPI، Protobuf، Zod) يولد الأنواع، الاختبارات، الوثائق، النماذج، SDKs. الكود يطابق المخطط، لا العكس. بدء خدمة جديدة؛ فرض التوافق في CI؛ توليد SDKs للعميل. كتابة الأنواع يدوياً؛ وثائق يدوية؛ تحقق مخصص.
العقود الموجهة بالمستهلك المستهلكون ينشرون التوقعات (Pact، Spring Cloud Contract). المزودون يتحققون منها. التغييرات الكاسرة تفشل بسرعة. خدمات دقيقة متعددة اللغات؛ نشر مستقل؛ استقلالية الفريق. مخطط موجه بالمزود؛ مسرح اختبار التكامل.
مفاتيح التساوي الذاتي = مرة واحدة بالضبط الشبكة تفشل؛ إعادة المحاولة تحدث. مفتاح التساوي الذاتي (من توليد العميل) + استبعاد تكرار الخادم = دلالات مرة واحدة بالضبط على نقل "مرة واحدة على الأقل". أي نقطة نهاية تغيير (POST، PATCH، DELETE). خاصة المدفوعات، الطلبات، التوفير. الأمل في أن لا تشحن إعادة المحاولة مرتين؛ معاملات موزعة.
الإصدار بنوع الوسائط، لا الرابط Accept: application/vnd.myapi.v2+json يبقي الرابط مستقراً؛ العملاء يختارون الاشتراك. الروابط تحدد الموارد؛ أنواع الوسائط تحدد التمثيلات. APIs طويلة الأمد مع مستهلكين كثر؛ تجنب تشعب /v1/، /v2/ في الرابط. الإصدار في الرابط (/api/v1/)؛ إصدار في الترويسة بدون نوع وسائط.
البوابة كطبقة ترجمة الخدمات الداخلية تتطور بشكل مستقل؛ البوابة تترجم (GraphQL→REST، Protobuf→JSON، v1→v2). المستهلكون يرون عقدة مستقرة. هجرة الأنظمة القديمة (brownfield)؛ أجزاء داخلية متعددة اللغات؛ APIs الشركاء الخارجيين. تغيير جميع الخدمات في وقت واحد؛ اقتران المكتبة المشتركة.
التطور على الثورة أضف حقولاً، لا تزيل أبداً. أهمل مع الترويسات (Sunset، Deprecation)، جداول زمنية، أدلة هجرة. اكسر فقط عندما تكلفة الحمل > تكلفة الكسر. كل تغيير مخطط؛ تخطيط الإهمال؛ تواصل أصحاب المصلحة. إطلاقات v2 الكبيرة؛ تغييرات كاسرة صامتة.

نمط مضاد: كتابة ملف OpenAPI بعد شحن الكود. المخطط هو العقد — إذا تولد من التنفيذ، فالتنفيذ هو العقد، وفقدت القدرة على تصميمه.

٦. الإيقاع، لا الخوارزمية

مثل التفكير التصميمي و التصميم المعماري، تصميم API هو إيقاع، لا خوارزمية منظمة. يفشل اختبارات الخوارزمية الثلاث:

  • المدخلات غير معرفة مسبقًا. لا تعرف كل حالات استخدام العميل عند تصميم الإصدار الأول. العقد يكتشفها عبر الاستخدام، التغذية الراجعة، وألم الهجرة.
  • الخطوات غير حتمية. لا توجد قاعدة تقول "أضف التصفح الآن". تضيفه عندما يصطدم أول عميل باستجابة ١٠ آلاف صف وينتهي المهلة — حكم استدعاء.
  • لا إنهاء ثابت. "منجز" يعني "العقد يخدم العملاء الحاليين ولديه مسار تطور موثق لـ ١٢ شهرًا قادمة". هذا حكم استراتيجي، لا تحقّق.

هذا هو سبب مقاومة تصميم API لقوائم التحقق التي تتظاهر بالاكتمال. قائمة التحقق تفترض أنك تعرف كل المستهلكين؛ الإيقاع يفترض أنك تعرف ما ينقص الذين لديك — حكم منتج/هندسة.

اختراق إيقاع "المخطط أولاً". المخطط أولاً (اكتب OpenAPI/proto قبل الكود) يحل مشكلة "لا إنهاء ثابت" بجعل العقد قطعة أثرية للمراجعة. العقد تصبح وصف PR. يفشل CI إذا ابتعد التنفيذ عن المخطط. إنه حاجز عملية — مفيد عند فرضه، خطير عندما يصبح المخطط وثيقة احتفالية لا يقرأها أحد.

توجد أساليب مسماة متعددة. لا واحدة قانونية؛ كل واحدة تعبئة مختلفة للقيود لحالة استخدام مهيمنة.

٨. المبادئ — الثوابت المشتركة

عبر كل أسلوب، ثماني مبادئ تصمد:

  1. العقد أولاً. العقد (OpenAPI، proto، GraphQL SDL) هو مصدر الحقيقة. الكود يتولد منه؛ الاختبارات تتحقق ضده؛ الوثائق تُعرض منه.
  2. التساوي الذاتي افتراضيًا على التغييرات. كل POST/PATCH/PUT يغيّر حالة يقبل encabezado Idempotency-Key. إعادة المحاولات آمنة؛ العملاء لا يخمنون.
  3. الخطأ كـ API، لا كحادث. كل خطأ يعيد غلافًا مهيكليًا (RFC 9457 Problem Details أو مكافئ): type، title، status، detail، instance، retry_after. العملاء يبدلون (switch) على type، لا مطابقة نصوص.
  4. الإصدار ككلفة كسر متعمدة. التغييرات الكاسرة تحصل على إصدار جديد (رابط أو هيدر) مع تاريخ غروب. التغييرات غير الكاسرة (إضافة حقل اختياري، إضافة قيمة تعداد) تشحن في نفس الإصدار. تكلفة رفع الإصدار صريحة.
  5. سطح ضيق، قدرة عميقة. تفضل موارد/عمليات صغيرة كثر على "نقطة نهاية إله" واحدة. تجزئة الواجهة تنطبق: العملاء يعتمدون فقط على ما يستخدمون.
  6. أوضاع فشل متوقعة. حدود المعدل تعيد 429 مع Retry-After. فترات المهلة موثقة. الفشلات الجزئية (APIs الدفعية) تعيد حالة لكل بند، لا 500 واحدًا.
  7. المراقبة مدمجة. كل استجابة تتضمن X-Request-ID. التتبعات تنشر traceparent (W3C Trace Context). المقاييس تعرض مئينيات زمن الاستجابة، معدلات الخطأ، التشبع.
  8. القابلية للاكتشاف ≠ الوثائق. المخطط هو العقد. الوثائق تشرح لماذا و كيف؛ المخطط يحدد ما. كلاهما يبقى متزامنًا عبر CI.

٩. مثال محلول — "تصميم API عام لتتبع الشحنات"

مشكلة API عامة واقعية، مشية طرف لطرف عبر الإيقاع.

السياق والشخصيات

  • عمليات الناقل — يفحص الطرود في المحاور (إنتاجية عالية، استيعاب دفعات).
  • منصة التجارة الإلكترونية — تستطلع الحالة لإظهار المشترين (QPS معتدل، يحتاج webhook).
  • العميل النهائي — يفتح صفحة تتبع مرة لكل طلب (QPS منخفض، يحتاج شعور فوري).

خطوة ١ — طوبولوجيا الموارد (عقد الواجهة)

GET   /v1/shipments/{id}              # تفصيل شحنة مفرد
GET   /v1/shipments                   # قائمة مع تصفح بمؤشر (cursor)، تصفية حسب الحالة/التاريخ
POST  /v1/shipments                   # الناقل ينشئ (تساوي ذاتي)
PATCH /v1/shipments/{id}              # الناقل يحدث أحداث الفحص (تساوي ذاتي)
POST  /v1/webhooks                    # المنصة تسجل عنوان رد نداء (callback)
GET   /v1/shipments/{id}/events       # تيار أحداث (Server-Sent Events)

خطوة ٢ — اختر الأسلوب: REST + SSE لتيار الحالة

التبرير: HTTP عام، عملاء غير متجانسين (ويب جوّال، تطبيقات أصلية، خادم)، التخزين المؤقت على GET مهم، SSE يعطي شعورًا فوريًا دون تعقيد WebSocket. GraphQL مرفوض — مبالغ فيه لـ ٣ موارد، قصة تخزين مؤقت أضعف. gRPC مرفوض — ليس أصليًا للمتصفح دون وكيل (proxy).

خطوة ٤ — التساوي الذاتي وأمان التغيير

  • POST /shipments و PATCH /shipments/{id} تتطلب encabezado Idempotency-Key: . الخادم يخزن مفتاح → تعيين استجابة لـ ٢٤ ساعة. مفتاح مكرر يعيد الاستجابة الأصلية.
  • استيعاب الناقل الدفعي يستخدم POST /shipments/batch مع مصفوفة شحنات، لكل منها مفتاح تساوي ذاتي خاص. الاستجابة تتضمن حالة لكل بند.

خطوة ٥ — سياسة الإصدار والإهمال

  • الإصدار في الرابط: /v1/، /v2/. لا إصدار بالهيدر (أبسط لـ API عام).
  • رأس غروب (Sunset) على الإصدار المهمل: Sunset: Sat, 01 Jan 2027 00:00:00 GMT + Link: ; rel="successor-version".
  • دعم أدنى ١٢ شهرًا بعد إصدار الخلف. تواصل: بريد للتطبيقات المسجلة، سجل تغييرات، لافتة بوابة المطورين.

خطوة ٦ — حدود المعدل والحصص

  • مجهول: ٦٠ req/min، ١٠٠٠ req/يوم.
  • موثق (مفتاح API): ٣٠٠ req/min، ١٠٠ ألف req/يوم.
  • شريك ناقل: ٥٠٠٠ req/min، حصة متفاوض عليها.
  • رؤوس على كل استجابة: X-RateLimit-Limit، X-RateLimit-Remaining، X-RateLimit-Reset.

خطوة ٧ — مثال مضاد GraphQL (لماذا لا هنا)

type Query {
  shipment(id: ID!): Shipment
  shipments(filter: ShipmentFilter, first: Int, after: String): ShipmentConnection
}

type Shipment {
  id: ID!
  status: ShipmentStatus!
  events: [ShipmentEvent!]!
  # مشكلة: الأحداث يمكن أن تكون ١٠،٠٠٠+. العميل يجب أن يصفح يدويًا.
  # لا تخزين مؤقت أصلي — كل استعلام POST.
  # تغيير دفعي للناقل = نوع إدخال مخصص، لا قصة تساوي ذاتي.
}

GraphQL يضيف تعقيد محلل (resolver) لمجال قراءة ثقيل، صديق للتخزين المؤقت. تغيير الناقل الدفعي (١٠ آلاف فحص/دقيقة) يناسب REST + مفاتيح تساوي ذاتي أفضل.

القطع الأثرية المنتجة

  • مستند OpenAPI 3.1 (مصدر الحقيقة، مفحوص في المستودع، معتمد بـ CI).
  • مصفوفة خطأ (كل URI type، حالة HTTP، توجيه إعادة المحاولة).
  • مخطط حدث SSE (OpenAPI webhooks منفصل أو components/schemas/EventStream).
  • تقويم إهمال (جدول مشترك + حقن رأس غروب آلي).
  • مجموعة Postman (مولدة من OpenAPI، منشورة في مساحة عمل عامة).
  • أنواع TypeScript (مولدة عبر openapi-typescript، منشورة على npm).

١٠. أكثر أوضاع الفشل شيوعًا

وضع الفشلكيف يبدولماذا يحدث
تفعيل الأسماء (RPC على شكل REST) POST /shipments/{id}/cancel، POST /shipments/{id}/retry-delivery، GET /shipments/{id}/get-status التفكير بأفعال لا موارد. العقد يصبح استدعاء إجراء عن بعد فوق HTTP، يفقد التخزين المؤقت، دلالات التساوي الذاتي، والوسائط الفائقة.
النماذج الداخلية تتسرب عبر API الاستجابة تتضمن _id: ObjectId("...")، createdAt: { $date: 1234567890 }، user_id (مفتاح خارجي)، is_deleted: false تسلسل كيان ORM مباشرة. يربط العملاء بمخطط التخزين. الهجرة تصبح نشرًا منسقًا.
لا تساوي ذاتي على الكتابات → إعادة المحاولات تفسد تطبيق جوّال يعيد POST /shipments عند مهلة شبكة؛ الناقل ينشئ شحنة مكررة. معاملة التساوي الذاتي كـ "لطيف أن يكون". كل نقطة نهاية مغيرة للحالة تحتاج مفتاح تساوي ذاتي؛ تكلفة عدم وجوده فساد بيانات.
حرب دينية: إصدار بالرابط مقابل إصدار بالهيدر الفريق يقضي ٣ أسابيع مناقشين؛ يشحن لا شيء؛ العملاء ينكسرون على إعادة تسمية حقل. ركوب الدراجات النارية (bikeshedding) على الآلية بدل السياسة. اختر واحدة (الرابط أبسط لـ APIs عامة)، ووثق سياسة التغيير الكاسر، تحرك.
تصفح بالإزاحة (offset) على جدول حار GET /shipments?offset=10000&limit=50 يستغرق ٣ ثوانٍ؛ العميل ينهي المهلة. تصفح الإزاحة يتطلب فحص الصفوف المتخطاة. تصفح بالمؤشر (keyset) هو O(1) لكن يتطلب مفتاح ترتيب مستقر. افتراضيًا للمؤشر (cursor).
أخطاء تكذب: HTTP 200 مع جسم {success: false} العميل يتحقق response.ok، يرى true، يحاول تحليل البيانات، ينهار على كائن خطأ. خوف من "كسر" دلالات HTTP. العقد هو حالة HTTP. استخدم 4xx/5xx؛ ضع تفاصيل قابلة للآلة في جسم RFC 9457.
رموز حالة غير موثقة لا يستطيع العملاء التبديل عليها API يعيد 418 (teapot) لـ "الناقل غير متصل"; العميل لا يملك معالجة، يظهر خطأ عامًا. اختراع رموز مخصصة بدلاً من الربط إلى 4xx/5xx قياسية + URI type RFC 9457. العملاء يستطيعون التعامل فقط مع ما يعرفون.
تغيير كاسر يُشحن دون نافذة غروب تعداد status يضيف LOST؛ تطبيق الجوّال ينهار على تعداد مجهول لأن switch استنفادي. معاملة امتداد التعداد كغير كاسر. في عملاء مكتوبين (TypeScript، Swift، Kotlin)، قيم التعداد الجديدة كاسرة. وثق قابلية التعداد للتمديد: "يجب على العملاء التعامل مع المجهول."
المخطط كمراسم، لا كحاجز حماية ملف OpenAPI موجود لكن التنفيذ ينحرف؛ CI لا يتحقق؛ SDK المولدة خاطئة. المخطط أولاً متبنى كمسرح عملية. الإصلاح: يفشل CI إذا استجابة التنفيذ لا تطابق المخطط (Pact، Dredd، Schemathesis).

نقد الممارسين (٢٠١٥–الحاضر)

واجه تصميم API نقدًا جادًا من مجتمع هندسة المنصات:

  • Kin Lane (API Evangelist) — "APIs كمنتجات": معظم المنظمات تعامل APIs كقطع أثرية تقنية، لا كمنتجات مع مدراء منتج، مقاييس، ودورة حياة. العقد هو المنتج؛ كل شيء آخر تغليف.
  • API Handyman (Arnaud Lauret) — "تصميم واجهات برمجة تطبيقات الويب": REST غالبًا ما تحمّل كحمولة عبادة؛ الوسائط الفائقة مهجورة؛ الإصدار غير متناسق؛ تنسيقات الأخطاء مخترعة لكل نقطة نهاية.
  • استطلاعات Stoplight / SmartBear — "حالة API ٢٠٢٣": ٦٠٪ من المنظمات ليس لديها إرشادات تصميم API؛ ٤٠٪ تكتشف تغييرات كاسرة في الإنتاج؛ التحقق من المخطط في CI نادر.
  • Phil Sturgeon (APIs You Won't Hate) — "تصميم أولاً مقابل كود أولاً": الكود أولاً (التوضيحات annotations) ينتج عقودًا تعكس حوادث التنفيذ؛ التصميم أولاً (OpenAPI/proto) ينتج عقودًا تخدم المستهلكين.

الخيط المشترك: النقد ليس أن المبادئ خاطئة — بل أن التبني المؤسسي يفرغها في مربعات اختيار. الإيقاع ينجو؛ المنهجيات المسماة غالبًا لا تنجو.

١١. النظام الإيكولوجي — كتالوج الأدوات مع معايير القرار

تصميم API جيد فقط بقدر الأدوات التي تجعل العقود مرئية، قابلة للاختبار، وقابلة للتطور. يسرد هذا القسم فئات الأدوات الأساسية، مع معايير قرار لكل منها.

الفئةالأدوات / المنصاتالمُحفّز → الهدفمقاييس القرار
تعريف العقد (OpenAPI، Protobuf، GraphQL، AsyncAPI) Swagger Editor، Stoplight، Optic، Buf، GraphQL Codegen، AsyncAPI Studio عقود ضمنية → عقود معرفة بالمخطط، مُصدرة، قابلة للمراجعة التغطية: % النقاط النهائية مع مخطط؛ الانحراف: معدل عدم تطابق المخطط مع التنفيذ؛ زمن المراجعة
اختبار العقد (الموجه بالمستهلك) Pact، Spring Cloud Contract، Specmatic، GraphQL Voyager عدم تطابق المزود/المستهلك → توافق مؤكد في CI معدل الإيجابيات/السلبيات الكاذبة؛ تغطية المستهلك؛ زمن التحقق
سجل المخطط والحوكمة Confluent Schema Registry، Apicurio، Buf Schema Registry، Optic، Spectral انتشار المخططات → مخططات مركزية، محكومة، متطورة معدل نجاح فحص التوافق؛ عدد الإصدارات؛ زمن نقل القيادة
بوابة API / إدارة الحركة Kong، Envoy، AWS API Gateway، GCP API Gateway، Azure API Management، Traefik نقاط نهاية خام → حركة مُدارة (مصادقة، حد المعدل، تحويل، مراقبة) زمن وصول النفقات العامة؛ تغطية السياسة؛ انحراف التكوين؛ تكلفة لكل مليون طلب
عميل SDK / توليد الكود OpenAPI Generator، GraphQL Codegen، tRPC، oRPC، Orval، Fern كود عميل يدوي → عملاء مولدون، آمنين بالأنواع، دائمًا متزامنين الانحراف: العميل مقابل المخطط؛ تكرار إعادة التوليد؛ تغطية الأنواع
التوثيق وبوابة المطورين Redoc، Swagger UI، Stoplight Elements، Mintlify، ReadMe، Postman المعرفة القبلية → وثائق قابلة للاكتشاف، تفاعلية، دائمًا حديثة حداثة التوثيق: أيام منذ آخر نشر؛ معدل نجاح البحث؛ وقت أول استدعاء
المحاكاة والتطوير الموجه بالعقد Prism، Mockoon، WireMock، MSW، Stoplight Prism، Spectral الانتظار للخلفية → تطوير واجهة أمامية متوازٍ ضد محاكاة دقة المحاكاة؛ تغطية العقد؛ زمن استجابة حلقة التغذية الراجعة
التدقيق / فرض الأسلوب Spectral، vacuum، Zally، API Linter، قواعد مخصصة تصميم غير متناسق → معايير مفروضة، مراجعة آلية تغطية القاعدة؛ معدل الإيجابيات الكاذبة؛ وقت إصلاح الانتهاكات
Full-Stack آمن بالأنواع (أنواع من النهاية للنهاية) tRPC، Zod، GraphQL Codegen، oRPC، Orval، Fern، TypeScript انحراف المخطط ↔ الكود → التحقق من العقد في وقت الترجمة تغطية الأنواع؛ زمن اكتشاف الانحراف؛ ثقة إعادة الهيكلة

طريقة اختيار: ابدأ بتعريف العقد + التدقيق + توليد العميل ("مجموعة أدوات API الدنيا القابلة للحياة"). أضف اختبار العقد عند عدد المستهلكين >3. أضف سجل المخطط عند عدد الفرق >5 أو تعدد لغات. أضف بوابة عندما تتجاوز احتياجات إدارة الحركة قدرات المكتبة. أضف Full-Stack آمن بالأنواع عندما تكون TypeScript هي اللغة الأساسية. الأداة تخدم العقد — لا العكس.

١٢. المستقبل — куда يتجه تصميم API

إشارة (٢٠٢٤–٢٠٢٦)ما يعنيه لتصميم API
عقود مولدة بالذكاء الاصطناعي من النية نماذج لغوية كبرى (LLMs) تصيغ OpenAPI/proto من "نحتاج API تتبع شحنات مع استيعاب ناقل واستطلاع عميل". البشر يراجعون، لا يكتبون. حلقة التأليف تصبح حلقة مراجعة.
محاذاة OpenAPI 3.1 + JSON Schema 2020-12 كائن المخطط = JSON Schema كامل. الأدوات (محققات، توليد كود، وثائق) تتقارب. لا مزيد من لهجة "مخطط OpenAPI مقابل JSON Schema".
AsyncAPI يصبح سائدًا العقود الموجهة بالأحداث تحصل على نفس نضج أدوات REST: توليد كود، وثائق، خوادم محاكاة، اختبار عقد. مخططات Kafka/Avro تهاجر لـ AsyncAPI.
تحول تنظيمي "API كمنتج" فرق المنصة توظف مدراء منتج API. العقود لها OKRs (تبني، زمن استجابة p99، تكرار تغيير كاسر). مراجعات التصميم تتضمن PM + DX + أمن.
كامل المكدس آمن النوع افتراضيًا tRPC / Zod / GraphQL Codegen / oRPC تجعل "مخطط → أنواع" صفر إعداد. العقد يصبح تعريف النوع؛ الانحراف خطأ تجميع.
اختبار العقد يتضاعف Pact، Specmatic، Schemathesis في CI على كل PR. عقود موجهة بالمستهلك (Pact) تمنع المزود من كسر المستهلكين. "اختبار التكامل" يتحرك لليسار.
OAuth 2.1 / PASETO / هوية SPIFFE OAuth 2.1 ينهي (يزيل منحاز implicit/password). PASETO يكتسب جرأة كـ "JWT دون فخاخ". SPIFFE/SPIRE لهوية عبء العمل في شبكة خدمة. عقود المصادقة تتطور.

١٣. ملخص — قائمة تحقق العقد

قبل دمج أي تغيير API، تحقق:

السؤالإذا لا…
هل العقد (OpenAPI/proto/GraphQL SDL) مصدر الحقيقة، لا الكود؟توقف. الكود أولاً = التنفيذ يتسرب للعقد.
هل كل نقطة نهاية مغيرة للحالة تقبل مفتاح تساوي ذاتي؟توقف. إعادة المحاولات ستفسد الحالة.
هل كل الأخطاء RFC 9457 Problem Details مع URI type مستقر؟توقف. العملاء لا يستطيعون التعامل برمجيًا مع مطابقة نصوص.
هل استراتيجية الإصدار موثقة مع سياسة غروب؟توقف. التغييرات الكاسرة ستفاجئ المستهلكين.
هل التعدادات موثقة كقابلة للتمديد (يجب على العملاء التعامل مع المجهول)؟توقف. العملاء المكتوبون سينهارون على قيم جديدة.
هل التصفح مبني على مؤشر (cursor) (لا إزاحة) للمجموعات التي تنمو؟توقف. تصفح الإزاحة O(n) وتنتهي مهلة عند المقياس.
هل العقد يمر التحقق من المخطط في CI (التنفيذ يطابق المخطط)؟توقف. انحراف المخطط = SDKs المولدة تكذب.
هل حدود المعدل، الحصص، ورؤوس Retry-After موثقة ومُعادة؟توقف. العملاء لا يستطيعون التراجع؛ يطرقون ويحظرون.
هل يوجد تقويم إهمال مُواصل للمستهلكين المسجلين؟توقف. إهمال مفاجئ = ثقة مفقودة، تسرب (churn).

اطبع هذا. ضعه على جدار مراجعة API. إذا لم يمر PR هذه القائمة، فليس جاهزًا للمستهلكين.
