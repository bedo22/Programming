مرجع · إطار فوق React (ميتا-إطار)

غوص عميق في Next.js

RSC وApp Router والتخزين المؤقت وTurbopack وأنماط عصر الذكاء الاصطناعي — كلها مربوطة بنموذج الدالة+الخطافات. اقرأها بعد وثيقة التحوّل النموذجي، وقبل أن تفترض أن كل ملف React مكوّن عميل.

اللغة: العربية · English

لماذا توجد هذه الوثيقة

بعد أن وضعت React تطبيق Create React App في حالة الغروب (فبراير 2025)، توجّه وثائق React الرسمية بالتطبيقات الجديدة نحو إطار عمل. وفي إعلانات الوظائف وأعمال React الجديدة، غالبًا ما يكون هذا الإطار هو Next.js (من Vercel). هذه الوثيقة ليست درسًا تعليميًا يحل محل nextjs.org — إنها خريطة لمتعلم JS قادم من خلفية C++ يفهم الدوال والإغلاقات والخطافات بالفعل، ويحتاج إلى قراءة كود Next دون أن يغرق.

متطلبات مسبقة في مساحة العمل هذه: التحوّل من الكلاسات إلى الخطافات (خاصة §١٨.٢ RSC و§١٨.١ المترجم)، وقاعدة نموذج صندوق إعادة العرض في التحوّل من الكلاسات إلى الخطافات §٧. سياق الخريطة: frontend camps survey §٥. تفاصيل المنصة بعد الخطافات (React 19، والمترجم، وأمن RSC) تعيش في React 2024 وما بعدها؛ هذه الوثيقة هي طبقة الإطار فوقه.

كيف تستخدم هذه الوثيقة

ترتيب القراءة: class-to-hooks ← React 2024 وما بعدها (المترجم، RSC، المؤسسة) ← هذا الدليل ← frontend camps survey (خريطة المعسكرات الأوسع). حيث تشرح وثائق React في أي عملية يعمل الكود، تشرح هذه الوثيقة كيف ينظّم Next ذلك في تطبيق قابل للنشر — التوجيه، واصطلاحات الملفات، وجلب البيانات، والتخزين المؤقت، وسلسلة الأدوات. النطاق المحدود: ليست درسًا يحل محل nextjs.org، وليست إعادة تدريس لـRSC (§٢/§٤ في React 2024 وما بعدها)، وليست المقارنة الكاملة للمعسكرات (§٥ من camps survey).

إن كانت هذه قراءتك الأولى، اقرأ §١ (الخريطة الذهنية)، §٤ (الخادم مقابل العميل)، §٦ (التخزين المؤقت — الجزء الذي يربك الجميع)، و§١٩ (قائمة القراءة). عُد لاحقًا للأجزاء التاريخية (§١ب–§١و)، والمثال العملي (§١٤)، وأنماط الفشل (§١٥) حين يطرح عليك كود حقيقي سؤالًا.

التعريف — ما هو Next.js (وما ليس هو)

هو: إطار React من فئة ميتا-أطر العمل (meta-framework) — التوجيه، واستراتيجيات التصيير، واصطلاحات جلب البيانات، والتجميع، وتحسينات الإنتاج حول React.

ليس: بديلًا عن نموذج مكونات React. مكونات العميل ما زالت تستخدم نفس الخطافات والإغلاقات وصناديق كل تصيير التي درستها. يقرر Next أين يعمل الكود وكيف تحمّل المسارات بياناتها؛ وما زالت React تقرر كيف تتحدث الواجهة من الحالة.

الطبقة من يملكها نموذجك الذهني
تحديث الواجهة من الحالة React دالة + خطافات، نموذج صندوق إعادة العرض
URL ← شجرة مكونات Next App Router مسارات نظام الملفات تحت app/
عملية الخادم مقابل المتصفح RSC + "use client" Reactان اثنتان (بيانات مقابل حالة)
التخزين المؤقت / إعادة التحقق نموذج تخزين Next دلالات HTTP + تخزين الإطار
التجميع / HMR / بناء الإنتاج Turbopack / Webpack أدوات — نادرًا ما تُحرَّر يدويًا

قاعدة هذه الوثيقة كلها: مهمة مَن هذه؟ التوجيه والبيانات والتخزين المؤقت والتجميع = Next. تحديثات الواجهة المدفوعة بالحالة = React. أبقِ الاثنين منفصلين ويختفي معظم غرابة Next الظاهرية.

التاريخ — خط العشر سنوات

ميزات Next إجابات عن مشكلات محددة ظهرت بالترتيب. معرفة الخط تجعل مواقف تصميم App Router مفهومة (لماذا اصطلاحات الملفات؟ انظر 2022).

السنة المحطة ما الذي تغيّر
2016 Next.js 1.0 (Vercel؛ Guillermo Rauch، Arunoda Susiripala) SSR لـReact دون خادم مخصص. Pages Router.
2020 Next.js 9.3 — getStaticProps / getServerSideProps أصبح جلب البيانات طرقًا صريحة، لا افتراضات SSR ضمنية.
2020 التجديد الثابت التزايدي (ISR) صفحات ثابتة تُعاد التحقق في الخلفية. طُمست خطوط الثابت/الديناميكي عمدًا.
2022 Next.js 13 — App Router (تجريبي) مجلد app/، ومكونات خادم React، وتخطيطات متداخلة، ودفق.
2023 Next.js 14 — App Router مستقر، وإجراءات الخادم مستقرة "use server"، وإجراءات النماذج، ومسارات متوازية ومقترضة.
2024 Next.js 15 — دعم React 19، وTurbopack dev مستقر، وnext.config.ts واجهات الطلبات (cookies()، headers()) أصبحت لازمنية؛ اتجاه use cache يظهر.
2025–26 Cache Components، والتصيير المسبق الجزئي، وتكامل مترجم React التخزين المؤقت أصبح صريحًا وتركيبيًا؛ قشرة ثابتة + فتحات ديناميكية؛ تحسين العميل أولًا بالمترجم.

التطور — انقلابات القيود

كل تخصص على هذه الرفوف يركب انقلابات القيود — يتغير قيدٌ ما ويصير النهج القديم غير كافٍ. Next كثيف بها بشكل غير معتاد:

الانقلاب قبل بعد ما الذي تغيّر
ثابت ← ديناميكي HTML مُصيَّر مسبقًا وقت البناء مُصيَّر على الخادم لكل طلب (SSR) المحتوى أصبح مخصصًا/فوريًا؛ تصيير وقت البناء لم يعد يواكب.
SSR ← دفق HTML كامل يُرسل بعد تحميل كل البيانات القشرة تُرسل فورًا، والبيانات تتدفق عبر Suspense أدرك المستخدمون انتظارًا طويلًا؛ القشرة تتيح للأجزاء البطيئة الوصول لاحقًا.
ترطيب كامل ← ترطيب جزئي شجرة React كاملة تُرطَّب في المتصفح الجزر التفاعلية فقط تُرطَّب؛ مكونات الخادم تشحن صفر JS حجم الحزمة أصبح عنق الزجاجة؛ RSC تزيل JS للواجهات غير التفاعلية.
Webpack ← Turbopack مجمّع مبني على JS مجمّع مبني على Rust سرعة البناء أصبحت عنق زجاجة في تجربة المطور.
تخزين ضمني ← تخزين صريح الإطار يخزّن fetch() افتراضيًا (مربك) use cache، cacheLife، cacheTag، Cache Components لم يستطع المطورون فهم ما هو مخزَّن؛ الصريح يتفوق على الضمني.
افتراضي CRA ← افتراضي إطار create-react-app كنقطة بداية وثائق React توصي بأطر (Next، React Router، Expo) اصطدمت SPAs العميلة فقط بجدران SEO والأداء وجلب البيانات (§٧ في React 2024 وما بعدها).

التقاطع مع الجيران — حيث يلامس ممارسات أخرى

الممارسة الحمض النووي المشترك أين يختلفان
React 2024 وما بعدها (نموذج المكونات) الخطافات، والإغلاقات، وصناديق كل تصيير، وإدارة الحالة React تملك كيف تتحدث الواجهة من الحالة. Next يملك أين يعمل الكود وكيف تحمّل المسارات بياناتها.
System Design استراتيجية التصيير (SSR/RSC/Islands)، وميزانيات زمن الاستجابة، والتخزين المؤقت تصميم النظام يقرر هل نستخدم SSR/RSC/edge. Next تنفيذ لذلك القرار.
API Design إجراءات الخادم، ومعالجات المسارات، ونقاط نهاية REST تصميم API يحدد العقد؛ معالجات مسارات Next وإجراءات الخادم طريقة واحدة لتنفيذه.
UI/UX وتصميم الويب حالات التحميل، والدفق، والهياكل العظمية، والواجهة التفاؤلية UI/UX يقرر ما يراه المستخدم أثناء التحميل؛ Next يوفر loading.tsx وSuspense والدفق كآلية.
HTML وCSS ما يُرسل إلى المتصفح، وCSS الحرجة، وتحميل الخطوط HTML وCSS هما عقد المنصة؛ Next يقرر متى وكيف يولَّد ذلك HTML/CSS ويُسلَّم.
Frontend Camps Survey جزر Astro، ومحمّلات Remix، وSvelteKit، وQwik Next معسكر واحد؛ الاستطلاع يقارن بينها، وهذه الوثيقة تتعمق في Next فقط.
JS Across Stacks وقت تشغيل Node، ووقت تشغيل الحافة، وبلا خادم عبر المكدسات يغطي أين يعمل JS؛ Next مستهلك لتلك الأوقات (Node لـSSR، والحافة للوسيط).

النظرية الأساسية — النماذج التي يبني عليها Next

Next لم يخترع هذه؛ بل حوّلها إلى منتج. حين يكون سلوك Next محيرًا، يكون أحد هذه النماذج غالبًا تحته.

النظرية الأصل ما يأخذه Next منها
مكونات خادم React دان أبراموف، "The Two Reacts" (2024) UI = f(data) على الخادم، وUI = f(state) على العميل — عمليتان، نموذج ذهني واحد (§٢ في React 2024 وما بعدها).
React Fiber / المصالحة React 16+ (2017) دفق SSR وSuspense والتصيير المتزامن — المجدول الذي يتيح لـNext تبادل التصيير والبيانات.
دلالات التخزين المؤقت لـHTTP RFC 9111 — Cache-Control، ETag، stale-while-revalidate طبقات تخزين Next تبني على بدائيات تخزين HTTP؛ revalidate هي stale-while-revalidate بصيغة إطار.
دفق HTML / النقل المجزأ ترميز HTTP/1.1 المجزأ (chunked)، وأطر HTTP/2 يرسل Next القشرة أولًا ثم يدفق حدود Suspense — تسليم HTML مجزأ.
معمارية الجزر (Islands) Jason Miller (Preact)، 2019؛ انظر React 2024 وما بعدها §٩ ترطيب الأجزاء التفاعلية فقط؛ RSC + مكونات العميل في Next مجموعة شاملة لهذه الفكرة.

النماذج الذهنية — ستة تغطي 90% من قراءة Next

النموذج الفكرة الأساسية متى تلجأ إليه ما يغني عنه
"أي React أنا فيها؟" كل ملف مكوّن خادم (لا خطافات، يعمل على الخادم) أو مكوّن عميل (خطافات، يعمل في المتصفح). اسأل أولًا. قراءة أي ملف في app/. افتراض أن كل شيء React عميلة.
"ثابت أم ديناميكي؟" المسار ثابت ما لم يستخدم واجهات ديناميكية (cookies()، headers()، searchParams، fetch غير مخزَّن). تصحيح "لماذا تصل هذه الصفحة إلى الخادم كل مرة؟" التخمين. ابحث عن الإشارات الديناميكية قبل لوم المضيف.
"أين يعمل هذا الكود؟" مكونات الخادم يمكنها استخدام DB/fs/أسرار؛ مكونات العميل يمكنها استخدام window/DOM/خطافات. تقرير ما إذا تضيف "use client". وضع كل شيء في مكونات عميل "لأمان".
"أي طبقة تخزين؟" أربع طبقات — تذكّر الطلب، وتخزين البيانات، وتخزين المسار الكامل، وتخزين الموجّه — لكل منها عمر وإبطال مختلفان. تصحيح بيانات قديمة أو ضربات خادم غير متوقعة. افتراض وجود تخزين واحد. هناك أربعة.
"ترطيب أم لا؟" مكونات الخادم تشحن صفر JS؛ مكونات العميل تُرطَّب. الحد الفاصل هو "use client". تحسين حجم الحزمة؛ فهم لماذا لا يُعاد تصيير مكوّن أبدًا. افتراض أن كل المكونات تُرطَّب.
"الشجرة تقرر، لا الملف" ملف بلا "use client" مكوّن خادم ما لم يستورده مكوّن عميل — عندها ينضم إلى حزمة العميل من تلك النقطة فما دون. تصحيح "لماذا يتسرب استيرادي الحصري للخادم إلى العميل؟" التفكير أن "use client" خاص بالملف. إنه خاص بالشجرة من هناك فما دون.

Pages Router مقابل App Router

كانت لـNext نظاما توجيه متعاقبان. ستصادف الاثنين في البرية.

Pages Router (pages/) App Router (app/)
العصر Next الكلاسيكي (منشور على نطاق واسع) الافتراضي الحالي للتطبيقات الجديدة
واجهات البيانات getServerSideProps، getStaticProps مكونات خادم لازمنية، وتخزين fetch، وإجراءات خادم
التخطيطات _app مخصص / HOCs متداخلة ملفات layout.tsx متداخلة تحفظ الحالة
RSC لا (شجرة React عميلة بعد خصائص البيانات) نعم — مكونات خادم افتراضيًا
اصطلاحات الملفات pages/about.js ← /about app/about/page.tsx ← /about

نصيحة قراءة: إذا رأيت getServerSideProps فأنت في Pages Router. إذا رأيت async function Page() في أعلى ملف مسار بلا "use client" فأنت في مكونات خادم App Router. لا تخلط النموذجين.

اصطلاحات ملفات App Router (المفردات)

تحت app/، أسماء الملفات مميزة:

  • page.tsx — واجهة شريحة مسار (مطلوب لكي يوجد ذلك الـURL).
  • layout.tsx — يلفّ الصفحات؛ لا يُعاد تركيبه عند التنقل بين المسارات الفرعية (الحالة في التخطيط تبقى).
  • loading.tsx — بديل Suspense للشريحة أثناء تحميل محتوى الخادم.
  • error.tsx — حد أخطاء للشريحة (يجب أن يكون مكوّن عميل).
  • not-found.tsx — واجهة 404 للشريحة.
  • route.ts — معالجات HTTP (نقاط نهاية بنمط REST) بدلًا من صفحة.
  • template.tsx — مثل التخطيط لكنه يُعاد تركيبه عند التنقل (أندر).
  • default.tsx — بدائل المسارات المتوازية (متقدم).
app/
  layout.tsx          // root shell (html/body, nav)
  page.tsx            // /
  blog/
    layout.tsx        // wraps all /blog/*
    page.tsx          // /blog
    [slug]/
      page.tsx        // /blog/:slug  (dynamic)
      loading.tsx

الشرائح الديناميكية: [id]، واللاقطة الشاملة [...slug]، واللاقطة الشاملة الاختيارية [[...slug]]. مجموعات المسارات (marketing) تنظّم المجلدات دون التأثير في الـURL. المسارات المتوازية (مجلدات @slot) تعرض شرائح متعددة في تخطيط واحد؛ المسارات المقترضة تعرض نافذة/طبقة فوقية بينما يشير الـURL إلى الصفحة الحقيقية. اعرف أنهما موجودتان كمفردات — ستقابلهما بالاسم قبل أن تقابلهما في الكود. السؤال العام عن الغرض من شجرة مجلدات (مجلدات الميزات، والمزامنة (colocation)، وتخطيطات المونوريبو) يعيش في System Design §Codebase architecture.

مكونات الخادم مقابل مكونات العميل

هذه هي الفكرة الحاملة للوزن. الافتراضي في app/: مكوّن خادم. تختار المتصفح بالتوجيهة:

// app/counter.tsx — must run in the browser (hooks, events, window)
"use client";

import { useState } from "react";

export function Counter() {
  const [n, setN] = useState(0);           // box model applies here
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}

// app/posts/page.tsx — Server Component (default). No hooks. Can use secrets/fs/db.
import { Counter } from "../counter";
import { db } from "@/lib/db";

export default async function PostsPage() {
  const posts = await db.post.findMany();  // runs on the server
  return (
    <main>
      <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>
      <Counter />                          // client island inside server page
    </main>
  );
}

قواعد تمنع الالتباس

  1. لا يمكن لمكونات الخادم استخدام الخطافات أو واجهات المتصفح. لا useState ولا useEffect ولا window. تُصيَّر مرة واحدة لكل طلب (أو وقت البناء) — لا توجد حلقة إعادة تصيير.
  2. لا يمكن لمكونات العميل استيراد وحدات حصرية للخادم (عملاء DB، أو بيئة خاصة بلا NEXT_PUBLIC_). تتدفق البيانات من الخادم إلى العميل كخصائص (قابلة للتسلسل).
  3. اتجاه التركيب: يستطيع الخادم تصيير أطفال من العميل. ويستطيع العميل تصيير أطفال من الخادم فقط عبر أنماط مثل تمرير مكونات الخادم كـchildren أو فتحات — لا باستيراد ملف خادم داخل ملف عميل.
  4. كل ما علّمك إياه مستند التحوّل النموذجي ما زال ينطبق على جانب العميل من الخط. RSC لا تستبدل الخطافات؛ إنها تصغّر أي جزء من الشجرة يحتاجها.
  5. الحد الفاصل خاصية شجرة، لا خاصية ملف. بمجرد أن يستورد مكوّن عميل وحدةً، تُجمَّع تلك الشجرة الفرعية في حزمة العميل — حتى الملفات التي لم تكتب "use client" أبدًا (النموذج الذهني §١و).

صيغة دان أبراموف (§٢ في React 2024 وما بعدها): العميل هو UI = f(state)؛ الخادم هو UI = f(data)؛ معًا UI = f(data, state). عند قراءة ملف، اسأل أولًا: في أي دالة أنا؟

أنماط جلب البيانات

مكونات خادم لازمنية + fetch

في App Router، fetch مدمج مع تخزين Next (تطور السلوك عبر الإصدارات — تحقق دائمًا من إصدار التطبيق الذي تقرأه). الشكل النمطي: 

async function getUser(id) {
  const res = await fetch(`https://api.example.com/users/${id}`, {
    next: { revalidate: 60 },   // ISR-style: revalidate every 60s
  });
  if (!res.ok) throw new Error("Failed");
  return res.json();
}

وصول مباشر إلى الواجهة الخلفية

يمكن لمكونات الخادم استدعاء قواعد البيانات وأنظمة الملفات والخدمات الداخلية مباشرة — لا حاجة لكشف مسار REST عام لبيانات صفحتك. هذا سبب رئيسي لوجود RSC: مزامنة البيانات مع الواجهة دون شحن عميل الاستعلام إلى المتصفح.

إجراءات الخادم

الدوال المعلَّمة بـ"use server" يمكن تمريرها إلى مكونات العميل كاستدعاءات رجوع (مثل action النموذج). تعمل على الخادم عند الاستدعاء. عاملها كـنقاط نهاية عامة — تحقق من المدخلات، وطبّق المصادقة، ولا ترمّز الأسرار أبدًا (انظر §٥ في React 2024 وما بعدها لموجة ثغرات RSC ديسمبر 2025 – يناير 2026). 

// app/actions.ts
"use server";

export async function updateTitle(formData) {
  const title = formData.get("title");
  // validate + auth + db write
}

معالجات المسارات (route.ts)

route.ts مكافئ App Router لمسارات API. تدعم كل طرق HTTP، وتقرأ أجسام الطلبات، وتضبط الكوكيز، ويمكنها دفق الاستجابات. لجأ إليها حين تحتاج نقطة نهاية تستدعيها أطراف أخرى (متصفحات، وويب هوك، خدمات خارجية) — لا لبيانات صفحتك، التي تجلبها مكونات الخادم مباشرة (§٥.٢). 

// app/webhooks/stripe/route.ts — a Route Handler
export async function POST(request: Request) {
  const payload = await request.json();
  // verify signature, do side effects
  return Response.json({ ok: true });
}

النموذج الذهني للتخزين المؤقت — بما فيه Cache Components

قصة تخزين Next هي الجزء الذي يربك مطوري SPA المخضرمين أكثر من غيره. الطبقات التقريبية:

  • تذكّر الطلب — استدعاءات fetch المكررة خلال تصيير خادم واحد يمكن دمجها.
  • تخزين البيانات — نتائج محفوظة عبر الطلبات (مع وسوم/أزمنة إعادة تحقق).
  • تخزين المسار الكامل — حمولة HTML/RSC ثابتة لمسار يمكن إنتاجه مسبقًا.
  • تخزين الموجّه (العميل) — تخزين جلسة عميل للشرائح المزارة لأجل تنقل سريع للخلف/للأمام.

الواجهات الديناميكية — ما يقلب الشريحة من ثابتة إلى ديناميكية

هذه هي الإشارات الديناميكية التي قال لك جدول النماذج الذهنية (§١و) أن تصطادها. استخدام أيٍّ منها يفرض التصيير الديناميكي لتلك الشريحة:

الواجهة الديناميكية الأثر
cookies()، headers() قراءة بيانات خاصة بالطلب ← الشريحة تصبح ديناميكية
fetch غير مخزَّن لا يوجد إدخال تخزين يُعاد استخدامه ← بيانات تُجلب لكل طلب
searchParams يعتمد على الـURL الوارد ← ديناميكي في الأوضاع الشائعة
export const dynamic = "force-dynamic" خروج صريح عن التوليد الثابت

الثابت مقابل الديناميكي خاصية شجرة. استخدام بيانات خاصة بالطلب يفرض التصيير الديناميكي لتلك الشريحة. حين "تصل صفحة إلى الخادم دائمًا" في الإنتاج، ابحث عن تلك الإشارات الديناميكية قبل لوم المضيف. وعند تصحيح بيانات قديمة، السؤال ليس "هل Next معطل؟" بل "أيٌّ من الطبقات الأربع يخدمني؟"

Cache Components — اتجاه Next الحديث

Cache Components (اتجاه Next الحديث): اجعل التخزين المؤقت صريحًا وتركيبيًا — علّم أي أجزاء الشجرة قشرة ثابتة قابلة للتخزين مقابل فتحات ديناميكية، بدلًا من الرجاء أن تطابق الافتراضات العامة نيتك. مساحة الأسماء المستقرة عبر الإصدارات:

  • use cache — علّم ناتج دالة أو مكوّن كقابل للتخزين؛ بديل الاعتماد على تخزين fetch() الضمني.
  • cacheLife — كم تعيش البيانات المخزنة (ملفات seconds، minutes، hours، days).
  • cacheTag — وسِم البيانات المخزنة لتتمكن من الإبطال بالوسم بعد تعديل — revalidateTag("products").

هذه تجعل التخزين المؤقت صريحًا وتركيبيًا وقابلًا للتصحيح. اقرأ وثائق إصدار Next الرئيسي في مشروعك للشكل الدقيق — تطورت الواجهة (مثل revalidate/tags على fetch مقابل الصيغ التوجيهية أعلاه)، والإصدار الذي تقرأه هو الفائز.

أسئلة تصحيح عملية حين يكون المسار بطيئًا أو قديمًا:

  1. هل هذه الشريحة ثابتة، أم ISR، أم ديناميكية؟
  2. أي وسم / زمن يعيد تحقق البيانات؟
  3. هل أنظر إلى HTML من CDN، أم تصيير خادم، أم تخزين موجّه العميل؟

الوسيط (Middleware)، next/image، next/font، والبيانات التعريفية

الوسيط (middleware.ts)

يعمل قبل كل طلب على الحافة. يمكنه إعادة كتابة الـURLات، والتحويل، وضبط الترويسات، وفحص المصادقة، وتشكيل الطلب/الاستجابة. يعمل في وقت تشغيل الحافة (Edge Runtime) — لا واجهات Node.js، ولا نظام ملفات، ولا وصول لقاعدة بيانات. استخدمه لحُرّاس المصادقة، وكشف اللغة، وتشكيل الطلبات. لا تضع منطق أعمال في الوسيط — مكانه إجراءات الخادم أو معالجات المسارات.

next/image — استبدل <img>

يعطي next/image تحميلًا كسولًا، وتحجيمًا متجاوبًا، وتحويل صيغ (WebP/AVIF)، وبدائل ضبابية خارج الصندوق. يحتاج width/height (أو fill) لحجز المساحة وتجنب انزياح التخطيط — صديق مؤشرات الويب الأساسية (Core Web Vitals). الصور البعيدة تتطلب إدراج المضيف في قائمة مسموحة في next.config.ts.

next/font

يستضيف الخطوط ذاتيًا وقت البناء، مما يزيل طلبات <link> الخط الخارجية ويمنع FOIT/FOUT. يستبدل وسم Google Fonts الكلاسيكي <link> باستيراد وقت البناء.

البيانات التعريفية وSEO

ينتج generateMetadata في مكونات الخادم <title> و<meta> وOpen Graph وJSON-LD. البيانات التعريفية الثابتة تُستخرج وقت البناء؛ والديناميكية تعمل لكل طلب. هكذا تبقى صفحات RSC صديقة لـSEO دون طبقة تصيير منفصلة لنظام إدارة محتوى بلا رأس (headless CMS).

Turbopack وسلسلة أدوات البناء

Turbopack هو مجمّع Next المبني على Rust (المسار الذي سبقه Webpack). HMR للتطوير وبناء الإنتاج يعتمدان عليه افتراضيًا بشكل متزايد في إصدارات Next الرئيسية الحالية. بالنسبة لك كقارئ لكود تطبيق:

  • نادرًا ما تضبط Turbopack يوميًا؛ تلاحظه حين تكون البناءات سريعة أو حين يكون إضافة مخصصة لـWebpack فقط وتنكسر تحت Turbopack.
  • خط Next.js منتصف 2026 (مثل إعلانات عائلة 16.x) شدد على تنقل أسرع وتكامل تجريبي/متوسع مع مترجم React — طابق وثائقك المحلية مع إصدار Next المقفل في المستودع.
  • ثبّت إصدارات الإطار في الإنتاج؛ واقرأ ملاحظات الأمان والنسخ التجريبية قبل القفز بين الإصدارات الرئيسية (ثقافة إيقاع أمان شهري في بيئة Next بعد موجة ثغرات RSC — انظر §٥ في React 2024 وما بعدها).

ذو صلة: مترجم React (§٣ في React 2024 وما بعدها) يمكنه العمل في خطوط Next بحيث تحتاج مكونات العميل إلى useMemo/useCallback مكتوبة يدويًا أقل. عامل ترقيات المترجم كترقيات React — إصدارات دقيقة، وتشغيل اختبارات كامل.

التنقل والدفق وبدائيات تجربة الاستخدام

  • <Link> — تنقل عميل مع تحميل مسبق للمسارات الثابتة.
  • useRouter / usePathname / useSearchParams — واجهات تنقل خاصة بالعميل ("use client").
  • الدفق — يمكن لمكونات الخادم دفق حمولة HTML/RSC؛ loading.tsx وSuspense يحددان ما يراه المستخدم بينما تتحلل شجرة فرعية بطيئة.
  • اتجاهات التنقل الفوري/التفاؤلي — تستثمر إصدارات Next الحديثة في جعل انتقالات المسارات تبدو سريعة كـSPA مع الاحتفاظ بفوائد تصيير الخادم. حين ترى "التنقل فوري لكن البيانات تظهر لاحقًا"، فذلك دفق + تخطيطات قشرة — ليس خطأً افتراضيًا.
  • التصيير المسبق الجزئي (PPR) — صيّر القشرة الثابتة مسبقًا وقت البناء، ودفق الفتحات الديناميكية فقط لكل طلب (§٤.٦ في React 2024 وما بعدها). نفس شكل "قشرة + Suspense" الذي تعرفه، لكن محسوب مسبقًا.

قطع React 19.2 التي قد تقابلها داخل تطبيقات Next (§٧ في React 2024 وما بعدها): useEffectEvent، <Activity> — يجب أن يدعمهما إصدارا الإطار وReact معًا.

المصادقة والبيئة والأمان (بجوار الواجهة الأمامية)

  • process.env.NEXT_PUBLIC_* — تُضمَّن في حزمة العميل. أي سر يجب أن يكون في بيئة خاصة بالخادم بدون تلك البادئة.
  • إجراءات الخادم ومعالجات المسارات = سطح هجوم. تحقق منها كواجهات API عامة. فحوصات المصادقة على الخادم، لا واجهة مخفية فقط.
  • بعد ثغرات بروتوكول RSC (ديسمبر 2025 – يناير 2026)، تثبّت فرق الإنتاج React/Next، وتشترك في تنبيهات الأمان، وتجدول التصحيحات. لا تخترع مُسلسِل RSC خاصًا بك.

تفاصيل أمنية تستحق التسمية

الشاغل ماذا تفعل
CSRF لإجراءات الخادم مدمج (فحص الأصل Origin) لإجراءات الخادم؛ معالجات المسارات المخصصة تحتاج رموز CSRF يدوية إذا قبلت كوكيز من المتصفحات.
تسرب كود الخادم إلى العميل ثبّت حزمة server-only؛ علّم الوحدات التي يجب ألا تعبر الحد أبدًا. يصبح استيرادها عميلًا خطأ بناء.
سطح XSS ترويسات سياسة أمان المحتوى (Content-Security-Policy) (تُضبط في ترويسات next.config.ts أو الوسيط).
الأسرار لا ترمّز أبدًا؛ متغيرات بيئة / مدير أسرار فقط (§٥.٣).

الجاهزية للذكاء الاصطناعي — ميزات منتج، لا ضجيج

Next مضيف شائع لواجهات منتجات الذكاء الاصطناعي لأن الدفق وحدود الخادم يناسبان تطبيقات النماذج اللغوية (LLM):

  • استجابات متدفقة من معالجات المسارات أو إجراءات الخادم إلى مكونات العميل (رموز المحادثة).
  • مفاتيح حصرية للخادم لمزوّدي النماذج — لا NEXT_PUBLIC_ أبدًا لأسرار API.
  • Vercel AI SDK (وأمثاله) بأنماطه: خطافات عميل بنمط useChat + مسار خادم يستدعي النموذج. الجانب React ما زال خطافات وإغلاقات؛ الجديد هو التدفقات اللازمنية.
  • RSC لنتائج الأدوات — صيّر واجهة بنيوية ينتجها النموذج على الخادم حين لا تحتاج تفاعلية عميل لتلك الشجرة الفرعية.

إذا كنت تبني ميزات ذكاء اصطناعي في تطبيق، فضّل اختيار مزوّد مدروس وأبقِ الأسرار على الخادم. المهارة الأمامية تبقى: تصيير حالات التحميل/الخطأ/الجزئية دون إغلاقات قديمة.

أهداف النشر

تنشر تطبيق Next، لا كومة من مكونات React. القطعة البنائية (next build) هي وحدة الحقيقة.

الهدف النموذج الحساب الذهني
Vercel مُدار، بلا إعداد، نشر معاينة ارتباط بالمزوّد؛ أبسط مسار؛ أوقات تشغيل الحافة + Node مدمجة
Docker / استضافة ذاتية next build ← صورة ← أي مضيف حاويات تحكم كامل، تملك العمليات، لا آليات نشر معاينة
Amplify / Railway / Render مُدار لكن متعدد الأطر تحسين أقل خصوصية بـNext من Vercel، لكن عمليات أقل من الاستضافة الذاتية
حافة فقط الوسيط + دوال الحافة، بلا SSR على Node أسرع إقلاع بارد، سطح محدود بحدة

الاختبار في Next.js

يجب أن يحترم الاختبار الانقسام بين الخادم والعميل:

  • مكونات الخادم — اختبارات تكامل: استدعِ المكوّن مع البيانات، وأكد ناتج HTML. إعداد next/jest يعالج حد RSC/العميل.
  • مكونات العميل — مكتبة اختبار React كالمعتاد (نموذج صندوق إعادة العرض §٤).
  • إجراءات الخادم / معالجات المسارات — استدعِ الدوال مباشرة مع formData/طلبات وهمية؛ وأكد التحقق + المصادقة + الأثر الجانبي.
  • التدفق الكامل — Playwright / Cypress من طرف إلى طرف.

مثال عملي — صفحة منتج مع مراجعات ودفق

كل ما سبق، مشروحًا عبر مسار واقعي واحد. صفحة تفاصيل منتج مع مراجعات، وزر إضافة إلى السلة، ودفق. 

app/products/[id]/
  layout.tsx                     // product chrome, shared across child routes
  page.tsx                       // server component — fetch product, stream reviews
  loading.tsx                    // shell while the server renders
  error.tsx                      // boundary for the product subtree

شجرة الملفات: layout.tsx (الهيكل)، page.tsx (بيانات خادم + generateMetadata)، loading.tsx (بديل القشرة)، error.tsx (الحد)، مكوّن خادم Reviews.tsx ملفوف في <Suspense>، وورقة عميل AddToCart.tsx. 

// app/products/[id]/page.tsx
import { Suspense } from "react";
import { Reviews } from "./Reviews";
import { AddToCart } from "./AddToCart";

export async function Page({ params }) {
  const product = await getProduct(params.id);      // cacheable, revalidate 60 (§6.2)
  return (
    <main>
      <ProductData product={product} />
      <AddToCart productId={product.id} />          // client leaf — the only island
      <Suspense fallback={<Skeleton />}>
        <Reviews productId={product.id} />          // async server comp — streams in
      </Suspense>
    </main>
  );
}

export function generateMetadata({ params }) { ... }  // SEO from product data

ترتيب القراءة: القشرة وبيانات المنتج تُشحن أولًا (revalidate: 60، ثابت)، والمراجعات تتدفق منفصلة (ديناميكية — لكل مستخدم)، وزر إضافة إلى السلة هو الجزيرة العميلة الوحيدة (خطافات)، وgenerateMetadata يشتق كتلة SEO. إخفاق تخزين أو ديناميكية مفروضة في أي مكان من السلسلة يغيّر ما يراه المستخدم — وهذا موضوع القسم التالي.

أنماط الفشل

نمط الفشل كيف يبدو لماذا يحدث الإصلاح
انتشار "use client" توجيهة واحدة في التخطيط الجذري؛ التطبيق كله يُرطَّب أُضيفت لإصلاح خطأ خطافات، ثم تُركت ادفع الحد إلى الورقة التي تحتاج الحالة (§٤).
جلب متسلسل (Waterfall) الصفحة تستغرق ثوانٍ لأن الجلب يتسلسل await في الأب، ثم الطفل، ثم حفيده Promise.all في الأعلى؛ ودفق الأقسام المستقلة (§٩).
تصيير ديناميكي عرضي صفحة يفترض أن تكون ثابتة تضرب الخادم كل طلب cookies()/headers()/searchParams في شريحة موجهة للثبات ابحث عن الإشارة الديناميكية؛ force-static أو use cache عن قصد.
إفراط في التخزين / بيانات قديمة بيانات قديمة بعد تعديل تخزين عدواني جدًا؛ لا إبطال عند الكتابة revalidateTag بعد التعديلات؛ cacheLife صريح.
عدم تطابق الترطيب "Text content does not match" العميل والخادم صيّرا ناتجًا مختلفًا (Date.now()، Math.random()) قيم خاصة بالمتصفح تُشغَّل وقت التنفيذ في useEffect؛ suppressHydrationWarning نادرًا.
إجراء خادم غير مُتحقق بيانات نموذج سيئة تصل إلى قاعدة البيانات الثقة بـformData عند نقطة النهاية تحقق من المخطط (Zod) + مصادقة داخل كل إجراء (§٥.٣).
كود خادم في حزمة العميل استيراد fs/قاعدة بيانات يرمي خطأً عميلًا مكوّن خادم سُحب أسفل حد العميل حارس server-only؛ أبقِ الخادم فوق الخط (§١و، §١٠).
التباس حالة التخطيط حالة في layout.tsx تُعاد — أو لا — عندما يُتوقع التخطيطات تبقى عبر التنقلات؛ الصفحات تُعاد تركيبها حالة خاصة بالتنقل إلى page.tsx؛ استخدم template.tsx لإعادة التركيب.
الوسيط يفعل منطق الأعمال كود الحافة يصبح طبقة تحكم غير قابلة للاختبار عومل الوسيط كوحدة التحكم الوسيط = مصادقة، تحويلات، ترويسات؛ المنطق في الإجراءات/المعالجات (§٧.١).

المبادئ

المبدأ المعنى
خادم افتراضيًا؛ عميل فقط عند الحاجة كل ملف في app/ مكوّن خادم دون "use client". هذا أقوى رأي في الإطار.
البيانات تعيش حيث تُستخدم مكونات الخادم تجلب مباشرة؛ لا تبني نقطة نهاية REST لتغذية صفحتك (§٥.٢).
التخزين المؤقت صريح، لا سحر revalidate/use cache/cacheTag، لا رجاء. صحيح بالطبقات (§٦).
الحد فاصل خط، لا تدرّج "use client" يرسم خطًا صلبًا يتحت ما دونه يُجمَّع عميلًا (§١و نموذج ذهني، "الشجرة تقرر").
الدفق هو شكل التصيير الافتراضي القشرة أولًا، وحدود Suspense تحدد الكشف التدريجي (§٩).
إجراءات الخادم نقاط نهاية عامة تحقق، وصادق، وقيّد المعدل، ودقّق — عاملها تمامًا كمسارات API (§٥.٣، §٥ في React 2024 وما بعدها).
التطبيق هو وحدة النشر تشحن تطبيق Next مبنيًا، لا مجموعة مكونات (§١٢).

ما ستقرؤه فعلًا في العمل — قائمة الفحص

السؤال إن لم تستطع الإجابة…
هل هذا pages/ أم app/؟ افحص المجلد؛ واجهات البيانات مختلفة (§٢).
هل يبدأ الملف بـ"use client"؟ إن لم يكن، افترض خادمًا؛ خطافات بلا التوجيهة = خطأ أو Pages Router قديم.
من أين تأتي البيانات — fetch، قاعدة بيانات، خصائص، استعلام عميل؟ افحص §٥؛ المصدر يقرر طبقة التخزين (§٦).
هل يوجد إجراء خادم على هذا النموذج؟ عامله كنقطة نهاية عامة؛ تحقق + صادق (§٥.٣).
أي تخطيط يملك الهيكل، وهل تنجو الحالة من هذا التنقل؟ التخطيطات تبقى؛ الصفحات تُعاد تركيبها (§٣، §١٥).
هل الخطأ خطأ نموذج صندوق إعادة العرض React (عميل) أم خطأ تخزين-ديناميكية (Next)؟ إن كانت "واجهة قديمة"، افحص طبقات التخزين الأربع أولًا (§٦).
أين حد العميل، وهل هو أدنى ما يمكن؟ عند الأوراق؟ §٤، §١٦.
هل الأسرار حصرية للخادم؟ NEXT_PUBLIC_* تُشحن إلى المتصفح؛ وكل ما سواها يبقى على الخادم (§٥، §١٠).

ما تغطيه هذه الوثيقة

Next.js هو React زائد توجيه، وانقسام خادم/عميل، وتخزين مؤقت، وأدوات. App Router يعتمد مكونات الخادم افتراضيًا؛ "use client" يعلّم الحد حيث ينطبق نموذجك الذهني للخطافات. التخزين المؤقت والواجهات الديناميكية يفسران كثيرًا من أسئلة "لماذا هذا ثابت/ديناميكي؟". Turbopack ومترجم React طبقتا سلسلة أدوات. الوسيط، والصور/الخطوط، والبيانات التعريفية، ومعالجات المسارات هي الملفات اليومية التي تقابلها في العمل. ميزات الذكاء الاصطناعي غالبًا دفق + أسرار خادم + واجهة React عادية. الأمان: إجراءات الخادم نقاط نهاية عامة. للمشهد الأوسع خارج Next انظر camps survey؛ لطبقة المنصة فوق هذا انظر React 2024 وما بعدها؛ لمسارات المال التي تستخدم هذه المهارات انظر income markets.
