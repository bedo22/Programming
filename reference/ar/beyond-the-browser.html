ما بعد المتصفح — React Native وElectron وجسر المنصات

لأجل: المطوّر الذي يعرف React على الويب ويريد أن يعرف ماذا يحدث حين يغادر الكود المتصفح — القرار، والجسور، وقيود المنصات التي لا وجود لها على الويب.

اللغة: العربية · English

أين يقع هذا. JavaScript Across Stacks يستعرض كل مضيف يعمل فيه JS — الخادم، الحافة، المدمج، الهاتف — ويملك جداول المشهد الأصلي في قسم الهاتف. هذه الوثيقة هي نصف واجهة-التثبيت من تلك القصة، تُروى من مقعد مطوّر React: مصفوفة القرار، وعمارة React Native، وجسر الحاسوب المكتبي، ومعرفة المنصات التي تحتاجها للشحن. لا تُعلّمك Kotlin أو Swift — فهذا مسار مهني مختلف، وهو مُخطَّط له أصلًا في §٤ من وثيقة JS Across Stacks.

التعريف — مشكلة الجسر إلى المنصات

المتصفح صندوق رمل (sandbox) بثلاثة نماذج محددة: نموذج تصيير (DOM + CSS)، ونموذج أمان (نفس الأصل، معزول)، ونموذج توزيع (روابط URL، بلا تثبيت). كل منصة خارج المتصفح تغيّر واحدًا على الأقل من هذه — والأداة التي تحمل JavaScript عبر الحد الفاصل هي الجسر. عالم ما-خارج-المتصفح كله طيفٌ يتراوح حسب بُعدك عن المتصفح، وما تضحّي به:

المفردات الجوهرية: الجسر هو الآلية التي تتيح لـ JS التحدث مع منصة أصلية. يوصّل React Native الـ JS بمكونات واجهة أصلية؛ ويوصّل Electron الـ JS بـ Chromium إضافة إلى Node؛ ويوصّل Capacitor تطبيق ويب بقشرة أصلية. حيثما كان الجسر ثقيلًا (تسلسل، لاتزامن، تقلّب إصدارات)، تتضرر الأداء والصحة — ولهذا فإن تاريخ كل نظام بيئي هو إلى حد كبير تاريخ جعل جسره أرق.

خريطة ما خارج المتصفح — أين يعمل JavaScript

React Native — الجسر إلى الهواتف

كيف يصبح كود React تطبيقًا أصليًا

يحافظ React Native على نموذجك الذهني في React — المكونات، الخصائص، الحالة، الخطافات — لكنه يستبدل ما تصيّر داخله. React على الويب تصيّر عناصر DOM؛ وReact Native تصيّر عروض iOS/Android أصلية. الآلية الرابطة بين الاثنين كانت قصة أداء الإطار:

OLD ARCHITECTURE (pre-2022) — the bridge was the bottleneck:
  JavaScript thread → JSON bridge (async, batched) → Native thread
  (React)            (serialized messages)            (UIKit/Android views)
      Every JS↔native call serialized to JSON and batched → frame drops
      during animations. This was the famous "bridge problem."

NEW ARCHITECTURE (2022+, default since 0.76):
  JavaScript thread → JSI (JavaScript Interface) → Native thread
  (React)             (direct C++ references,      (Fabric renderer,
                       synchronous, no JSON)         TurboModules)
      JS holds direct references to C++ objects. No serialization.
      Synchronous calls. The architectural cousin of React's own move
      from reconciliation to Fiber — remove the serialization layer.

التفاصيل التي ستسمع أسماءها: JSI (واجهة المرجع المباشر التي تستبدل الجسر)، وFabric (المصيّر الجديد الذي يلتزم واجهة المستخدم على الخيط الأصلي)، وTurboModules (وحدات أصلية تُحمَّل كسولًا). لقراءة الكود والتصحيح، اعرف الأسماء؛ أما العمارة المهمة فهي «متزامن، بلا JSON، مراجع مباشرة».

الوحدات الأصلية — عندما لا يكفي JS

عندما تحتاج وصولًا للعتاد (كاميرا، Bluetooth، قياسات حيوية، NFC) أو واجهات خاصة بالمنصة: وحدات Expo تغطي ~90% من الحالات وتصونها فريق Expo؛ وحدات المجتمع (react-native-camera, react-native-maps) تغطي أكثر؛ الوحدات الأصلية المخصصة هي المكان الذي تكتب فيه Kotlin/Swift وتعرضه لـ JS عبر JSI — المكان الوحيد الذي تحتاج فيه معرفة أصلية حقيقية. كل ما عدا ذلك يبقى في TypeScript.

معرفة منصتي Android وiOS — الحد الأدنى للشحن والتصحيح

لا تصبح مطوّر Android. تتعلم ما تفرضه Android وiOS على التطبيق، لأن تلك القيود تشكّل كل قرار في React Native:

المفهومماذا يعني لتطبيق React Native الخاص بك
APK / AABAPK = تثبيت مباشر؛ AAB = صيغة Play Store. Expo يبنيها لك.
الأذوناتالكاميرا، الموقع، التخزين، الإشعارات — يمنحها المستخدم وقت التشغيل. تُصرَّح في AndroidManifest.xml وتُطلب عبر واجهات React Native.
مراجعة Play Storeعادة 1–7 أيام. بخلاف نشر الويب، لا يمكنك الدفع فورًا — خطط للإصدارات.
توقيع التطبيقتوقّع بمخزن مفاتيح (keystore). فقدان المخزن = فقدان القدرة على التحديث. احتفظ بنسخة احتياطية.
Intentsتواصل Android بين التطبيقات: الروابط العميقة، المشاركة، فتح الملفات. واجهة Linking في React Native تدير معظمها.
دورة حياة النشاطيمكن لـ Android قتل تطبيقك في الخلفية. لا تفترض أن JS يعمل. استخدم مهام الخلفية / الدفع.
زر الرجوعAndroid يملك زر رجوع نظاميًا. يجب أن يتعامل تنقلك معه. iOS لا يملك واحدًا.
التجزؤآلاف أحجام الأجهزة وإصدارات Android والمصنعين. اختبر على أجهزة حقيقية لا محاكيات فقط.

iOS باختصار: حزمة IPA، مراجعة App Store أشد صرامة (1–3 أيام، رفضات سياسات؛ يمنحك TestFlight قناة بيتا مغلقة قبل تلك المراجعة)، نظام توقيع Apple (ملفات التزويد والشهادات — يديرها Expo)، تنفيذ خلفية أشد تقييدًا (الدفع هو وسيلة الوصول الأساسية)، إيماءة السحب-للرجوع بدلًا من زر الرجوع، وإرشادات واجهة Apple (أشرطة تبويب أسفل، أشرطة تنقل أعلى). يجب أن تعرف أيضًا سلسلة البناء التي يجرّدها Expo: JS/TS ← مجمّع Metro ← مشروع أصلي ← Gradle (Android) أو Xcode (iOS) ← متجر ← مراجعة ← تثبيت. EAS Build (بناء Expo السحابي) وFastlane يؤتمتان نصف Gradle/Xcode ← متجر من تلك السلسلة — قصة CI/CD الكاملة من اختصاص Version Control & CI/CD.

إمكانية الوصول أصلية، ليست اختيارية. دلالات إمكانية الوصول على الويب تنتقل، لكن الخطافات تختلف: يعرض React Native accessibilityLabel وaccessibilityRole وaccessibilityState على المكونات، يقرؤها VoiceOver (iOS) وTalkBack (Android) — المعادلات الأصلية لتسميات وأدوار aria. اختبر على جهاز حقيقي مع قارئ شاشة، بنفس الطريقة التي تفحص بها الويب بـ NVDA. UI/UX & Web Design تملك الانضباط من ناحية التصميم؛ أما على التلفاز فشكل إمكانية الوصول هو تركيز مدفوع بجهاز التحكم، وهو ما يغطيه قسم التلفاز الذكي.

الإبلاغ عن الأعطال هو مجموعة اختباراتك الأخرى. الأخطاء على الهاتف تأتي بنوعين: استثناءات JS وأعطال أصلية. يلتقط Sentry أو Crashlytics الاثنين — ارفع خرائط المصادر الخاصة بـ Metro لتظهر أخطاء JS كمكدسات استدعاءات قابلة للقراءة، ودع الأداة تعيد بناء تقرير الانهيار الأصلي (iOS/Android) إلى مكدس دالة-وسطر. اربطها قبل الإطلاق؛ إنها الفرق بين «أبلغ المستخدمون عن خطأ» ومكدس استدعاءات في بريدك.

Electron وTauri — جسر الحاسوب المكتبي

العمارة: عمليتان وأنبوب بينهما

Electron هو المضيف المكتبي لسبب واحد بالضبط: يتيح لك شحن تطبيق ويب كتطبيق حاسوب مكتبي أصلي، معيدًا استخدام كل معرفتك بـ React/CSS/المتصفح. يفعل ذلك بتشغيل Chromium (تصيير) وNode.js (وصول للنظام) في تطبيق واحد، مقسومًا على عمليتين:

┌─────────────────────────────────────────────────────────────┐
│                      Electron App                            │
│                                                              │
│  ┌──────────────────┐        IPC          ┌────────────────┐ │
│  │   MAIN PROCESS   │  (ipcMain/ipcRenderer) │ RENDERER      │ │
│  │     (Node.js)    │ ◄──────────────────► │   (Chromium)   │ │
│  │                  │                      │                │ │
│  │ • filesystem     │                      │ • your React   │ │
│  │ • OS APIs        │                      │   app (DOM+CSS)│ │
│  │ • menus / tray   │                      │ • sandboxed by  │ │
│  │ • notifications  │                      │   default (12+) │ │
│  └──────────────────┘                      └────────────────┘ │
│   "owns the OS"         bridge = IPC calls    "owns the UI"    │
└─────────────────────────────────────────────────────────────┘

ما ينتقل من React الويب: كل شيء. يعمل تطبيق React الخاص بك داخل Chromium — DOM وCSS وواجهات المتصفح كلها حاضرة. إنه حرفيًا تبويب متصفح مع وصول نظامي إضافي فوقه. ما يختلف: وصول كامل لنظام الملفات (عبر العملية الرئيسية)، توزيع بالمثبّت (.exe/.dmg/.AppImage)، تحديث تلقائي عبر electron-updater، علبة النظام + اختصارات عامة + إشعارات أصلية، ونموذج أمان يجب فيه إبقاء nodeIntegration مغلقًا في العارض وتمرير الوصول للنظام عبر IPC.

مشكلة Electron: حجم الحزمة

يشحن Electron Chromium (~150MB) + Node.js (~30MB) مع كل تطبيق. لهذا يُثبَّت VS Code بحجم ~100MB وSlack بـ ~200MB. البدائل موجودة بسبب هذا:

الأداةالنهجحجم الحزمةالمفاضلة
ElectronChromium + Node.js~150MB+توافق كامل، نظام بيئي ضخم (VS Code, Slack, Discord, Figma)
TauriWebView النظام + خلفية Rust~3–10MBأصغر بكثير، لكن WebView يختلف حسب نظام التشغيل
WailsWebView النظام + خلفية Go~5–10MBخلفية Go، أصغر من Electron
NeutralinoWebView النظام + خلفية خفيفة~2–5MBأصغر حتى، أقل نضجًا
PWAمبني على المتصفح، قابل للتثبيت0 (يعيد استخدام متصفح موجود)وصول نظامي محدود

القرار: Electron عندما تحتاج أقصى توافق ونظام بيئي؛ وTauri عندما يهمّ حجم الحزمة وتتحمل تباينات WebView. كلاهما يمنح تطبيق React نظام ملفات وعلبة نظام.

PWA وCapacitor — الأرضية الوسطى

PWA (تطبيق الويب التقدمي) — تطبيق الويب الخاص بك يُجعل قابلًا للتثبيت، بلا متجر تطبيقات. عامل الخدمة (دون اتصال + دفع)، بيان تطبيق الويب (طلب التثبيت، الأيقونة، شاشة البداية)، وواجهات ويب للكاميرا/GPS (محدودة مقابل الأصلي). متى يربح: تطبيقات المحتوى، التجارة الإلكترونية، الأدوات الداخلية — أي مكان تريد «قابلًا للتثبيت» دون مراجعة متجر. متى يخسر: تكامل أصلي ثقيل، معالجة خلفية، اكتشاف عبر المتاجر.

Capacitor (فريق Ionic) — تطبيق الويب الخاص بك ملفوف في قشرة أصلية. يعرض WebView تطبيق React؛ توفّر الإضافات الأصلية الكاميرا والدفع والقياسات الحيوية ونظام الملفات؛ قاعدة كود واحدة ← iOS + Android + Web. متى يربح: لديك أصلًا تطبيق ويب وتحتاج نسخة هاتف مع بعض الميزات الأصلية (90% ويب، 10% أصلي). متى يخسر: تحتاج واجهة بإحساس أصلي — تصيير WebView لا يطابق نعومة الحركة/الإيماءات الأصلية.

العلاقة: يمنحك PWA «قابلًا للتثبيت» بقشرة صفرية؛ ويمنحك Capacitor القشرة الأصلية؛ ويمنحك React Native الواجهة الأصلية. اختر أنحف جسر يحقق مصفوفة القرار.

التلفاز الذكي — Tizen وwebOS، شاشات ~300 مليون المخفية

أكبر سوق خارج المتصفح لا يفكر فيه معظم المطوّرين أبدًا: كل تلفاز Samsung منذ 2015 يعمل بـ Tizen، وكل تلفاز LG يعمل بـ webOS — معًا نحو 300M شاشة غرفة معيشة — وكلاهما منصتا تطبيقات ويب. تطبيقك هو HTML وCSS وJavaScript يعمل داخل محرك مشتق من Chromium يشحنه التلفاز. فريق يستطيع بناء واجهة ويب يستطيع بناء قشرة تطبيق تلفاز.

لكن التلفاز جهاز مقيد مبني لغرض محدد، والقيود هي ما يجعله منصته الخاصة:

الواقعماذا يعني
Chromium ثابت لكل سنة طرازمحرك الويب يُثبَّت وقت التصنيع ولا يُرقّى أبدًا. تلفاز 2022 ≈ Chromium 94؛ 2025 ≈ 120؛ 2026 ≈ 126. واجهة ويب شُحنت في Chrome 110 تفشل بصمت على تلفاز 2022. اكشف الميزات، ولا تتفقد الإصدارات أبدًا.
واجهات وسائط أصليةيتحكم AVPlay في Tizen بخط أنابيب وسائط العتاد (DRM، الترجمة، مسارات الصوت، 4K) أبعد من عنصر <video> العادي. يمدد webOS مسار وسائط HTML5.
DRM عبر EMEPlayReady + Widevine عبر Encrypted Media Extensions — أبدًا Apple FairPlay (لا أجهزة Apple هنا). عميل DRM مخبوز في برنامج كل تلفاز؛ لا يمكنك ترقيته في الميدان.
حقيقة الصيغيدعم webOS HLS أصلًا؛ DASH غير مدعوم رسميًا. عبّئ مرة واحدة إلى CMAF واخدم الاثنين.
اعتماد لكل متجريصدّق Samsung TV Seller Office ومتجر LG كلٌّ على حدة، لكل مجموعة طراز — إطلاق < 5s، تنقل زر الرجوع يعمل، لا شاشات فارغة. خطط لعدة جولات إصلاح.
تجربة شاشة بعيدةتنقل تركيز مدفوع بجهاز التحكم، لا مؤشر. يدفع webOS حتى بـ Enact — إطار مبني على React مضبوط لغرفة المعيشة.

بالنسبة لمطوّر React: مهاراتك تنتقل مباشرة (إنه تطبيق ويب في قشرة Chromium). المعرفة الجديدة هي خط أنابيب الوسائط (AVPlay/EME)، وترخيص DRM، وضريبة تجزؤ الأجهزة عبر سنوات الطراز. هذا مسار مهني حقيقي لتطبيقات البث — ومعظم المطوّرين لم يسمعوا به أصلًا.

الألعاب — مسار JavaScript خارج المتصفح

نعم، هرب JavaScript إلى الألعاب — لكن شكله يفاجئ معظم المطوّرين. مسار أجهزة الكونسول الكبير (Unity C#, Unreal C++) ليس JS. مسار JS الحقيقي له جزآن:

1. صندوق رمل الألعاب المصغرة. يستضيف WeChat وTikTok ألعابًا ليست صفحات ويب: بيئة JavaScript بلا DOM مع سياق canvas + WebGL (WebGPU بشكل متزايد)، إضافة إلى واجهات المضيف للتخزين والصوت والشبكات والطبقة الاجتماعية/الدفع. لا window ولا document. حزمتك الأولى محدودة بسقف ~4MB (تُنزَّل الأصول منفصلة). تترجم المحركات إلى هذا الهدف: Cocos Creator وLayaAir وEgret (TypeScript/JS)، مع كون Cocos الافتراضي لأن محركها مثبت مسبقًا في عميل WeChat ولا يُحتسب ضد الـ 4MB. تصل ألعاب Unity إليه فقط عبر تحويل WebGL→mini-game (أو محرك Tuanjie من Unity China، الذي يعامله كهدف أصلي).

2. محركات المتصفح التي تبقى في المتصفح — لكن المهارات تنتقل. تعمل Phaser وPixiJS وThree.js وBabylon.js في تبويب متصفح (WebGL/canvas) وهي تقنيًا ما تزال داخل المتصفح. تهمّ هنا لأن لعبة Three.js قريبة هيكليًا من اللعبة المصغرة — الفجوة هي طبقة المحوّل وميزانية الـ 4MB، لا التصيير.

المساراللغةيعمل فيمتى تختاره
لعبة مصغرة (Cocos/Laya/Egret)TypeScript/JSصندوق رمل WeChat/TikTok، وأيضًا الهاتف الأصليألعاب عابرة لأكبر واجهات المتاجر، فريق JS
محرك ويب (Phaser/Pixi/Three)JSتبويب متصفحألعاب لعب فوري من URL؛ المهارات تنتقل إلى الألعاب المصغرة
Unity / UnrealC# / C++كل شيء، عبر التصدير/WASMثقيلة الأداء، ثلاثية الأبعاد، عبر المنصات — ليست مسار JS

عندما يلمس مطوّر React هذا: انضباطك في المكونات/الحالة/الحلقة ينتقل إلى واجهة اللعبة وإلى حلقة اللعبة (تحديث ← تصيير)، لكن اللعبة عمارة مختلفة عن تطبيق ويب — حلقة تصيير مستمرة بدلًا من تصيير لكل تغيّر حالة. ابدأ بمحرك متصفح؛ إنه أقل حركة مُهدَرة، ونقل اللعبة المصغرة تمرين محوّل + تمرين ميزانية.

كل ما سبق — الهاتف، الحاسوب المكتبي، التلفاز، الألعاب — يصطدم بالجدران نفسها التي ببساطة لا وجود لها على الويب. صمّم في مواجهة هذا الجدول:

هذه أيضًا اهتمامات تصميم نظم — الدفع والمزامنة دون اتصال والربط العميق عمارة لا تجميل، وSystem Design هو المكان الذي تحصل فيه على معاملتها الكاملة.

المشهد الأصلي — اربط، لا تكرر

تحتاج أن تفهم المنصات الأصلية التي تستهدفها جسورك، لكنك لا تحتاج أن تتعلم البناء فيها. يحمل JavaScript Across Stacks §٤ أصلًا جداول المقارنة المتعمقة لكل مسار أصلي — Kotlin/Jetpack Compose (يترجم React Native إلى عروض Android أصلية؛ تكتب Kotlin فقط للوحدات الأصلية المخصصة)، وSwift/SwiftUI (المكافئ في iOS)، وDart/Flutter (بديل Google عبر المنصات بمصيّره الخاص — تختاره لاتساق مثالي عبر المنصات، لا لإحساس أصلي). إذا ظهر قرار أصلي، اقرأ ذلك القسم؛ إنه المرجع، وهذه الوثيقة تتعمد ألا تكرره.

مثال تطبيقي — متتبع عادات، بكل الطرق

The same product, four installable approaches — and one to reject:

1 · Web (PWA):  Next.js + Service Worker + manifest
   Distribution: URL, installable            Choose for: internal
   tool, quick validation, no native features needed.

2 · React Native (Expo): Expo + Expo Router + expo-sqlite
   Distribution: App Store + Play Store      Choose for: consumer
   app, push, offline, native feel.

3 · Capacitor:   existing React SPA + Capacitor shell
   Distribution: App Store + Play Store      Choose for: already have
   a web app, need mobile wrapper + push.

4 · Electron:    React + Electron
   Distribution: desktop installer           Choose for: desktop
   tracker with system tray + notifications.

5 · Native (Kotlin/Swift): full native rewrite
   Rejected here — RN/Expo covers it; native adds cost without a
   real limitation forcing it.

Expo Router version:
  habit-tracker/
  ├── app/                    # file-based navigation (Next.js-style)
  │   ├── _layout.tsx         # root layout (tab navigation)
  │   ├── (tabs)/index.tsx    # home: today's habits
  │   ├── (tabs)/history.tsx  # past completions
  │   ├── (tabs)/settings.tsx
  │   └── habit/[id].tsx      # detail screen
  ├── components/             # HabitCard, StreakBadge, CheckButton
  ├── store/habits.ts         # state (Zustand)
  └── db/schema.ts            # expo-sqlite schema

Web concept             →  React Native equivalent
app/page.tsx            →  app/(tabs)/index.tsx
<div className="card"> →  <View style={styles.card}>
onClick                 →  onPress
localStorage            →  expo-sqlite / AsyncStorage
CSS display:flex        →  flexDirection:"row" (flexbox is default)
Browser notification    →  expo-notifications (native push)
history.pushState       →  router.push("/habit/123")

الخلاصة — قائمة الفحص الذهنية الكاملة

اطبع هذا. إنه الوثيقة كلها في عشرة أسطر:

#السطر
1المتصفح صندوق رمل (تصيير، أمان، توزيع). كل مضيف خارجي جسر عبر واحد من هذه.
2اسأل: هل يحتاج المستخدم إلى تثبيت هذا، وهل يحتاج قدرات أصلية؟ لا/لا ← الويب.
3تثبيت + أصلي + فريق JS ← React Native (Expo أولًا). تثبيت + حاسوب مكتبي + فريق JS ← Electron/Tauri.
4React تنتقل كاملة (المكونات، الخطافات، الإيقاع). DOM وCSS وURLs هي ما يتغير.
5عمارة RN هي قصة ترقّق الجسر: جسر JSON ← JSI/Fabric/TurboModules.
6التنقل ليس توجيهًا: مكدسات/تبويبات/أدراج + ربط عميق تحل محل URLs.
7التلفاز (Tizen/webOS) منصة تطبيقات ويب على ~300M شاشة — Chromium ثابت، AVPlay/EME، اعتماد لكل متجر.
8مسار الألعاب في JS هو صندوق رمل اللعبة المصغرة بلا DOM + محركات المتصفح؛ مسار الكونسول الكبير ليس JS.
9متاجر التطبيقات، الأذونات، دون اتصال، الدفع، الروابط العميقة، ورسوم IAP 30% تنطبق على كل منصة قابلة للتثبيت.
10المشهد الأصلي يعيش في JavaScript Across Stacks §٤ — اربط إليه، لا تكرر.

  • «خذ مثال متتبع العادات وادفعه إلى Tizen — ماذا يتغير لتجربة الشاشة البعيدة المدفوعة بجهاز التحكم، وماذا يفحص الاعتماد فعلًا؟»
