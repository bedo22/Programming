SQL وPostgreSQL

لغة الاستعلام التي تفتح كل مخطط: تشريح SELECT وترتيب التنفيذ، ومعالجة NULL، وJOIN بكل أشكالها، والتجميع وGROUP BY، والاستعلامات الفرعية وتعبيرات الجدول المشترك، والدوال النافذة، وكتابة البيانات (INSERT/UPDATE/DELETE/UPSERT)، والمعاملات في SQL، وميزات PostgreSQL الرابحة (JSONB والمصفوفات والبحث النصي الكامل وLISTEN/NOTIFY والأمان على مستوى الصف RLS والتقسيم والإضافات)، وقراءة الاستعلامات البطيئة بـ EXPLAIN ANALYZE، والاختلافات المهمة في MySQL/MariaDB بالنسبة لـ WordPress، وSQLite للتطوير المحلي — مع مثال عملي يحوّل مخطط تتبع الشحنات في الرف إلى استعلامات حقيقية. اقرأ هذا بعد نمذجة البيانات وقواعد البيانات (تصمّم المستودع هناك؛ تفتحه هنا).

لماذا توجد هذه الوثيقة منفصلة

لا تعلّم أي وثيقة أخرى على الرف كيف تستعلم من قاعدة بيانات. وثيقة نمذجة البيانات تصمّم المخططات بل وتعرض استعلامين مثالين؛ ووثيقة الواجهة الخلفية تسمّي ORM والمعاملات — لكن لا أحد يعلّم اللغة نفسها: ما هو JOIN، ومتى تنطبق GROUP BY، وماذا تفعل الدالة النافذة، وكيف يجعل UPSERT الكتابة ذاتية التساوي. تلك الفجوة تهمّ كل جمهور على هذا الرف: المستقل الذي يصحّح استعلام wp_postmeta في WordPress، ومطوّر React الذي يربط استعلام Supabase بصفحة Next.js، ومهندس الواجهة الخلفية الذي يحسّن مشكلة N+1، ومصمّم الأنظمة الذي يشرح لماذا يوجد جدول الفهرس. SQL هي المهارة الأكثر قابلية للنقل في عمل الواجهة الخلفية — اللغة متطابقة بنحو ~90% عبر PostgreSQL وMySQL وSQLite. هذه الوثيقة تعلّمها مرة واحدة، محايدة تجاه المحرّك أولًا، مع PostgreSQL كمحرّك التوثيق (وهو افتراضي الرف) وقسم مخصص لاختلافات MySQL ذات الصلة بـ WordPress. ملاحظة نطاق واحدة: هذه ليست دورة إدارة قواعد بيانات — ضبط WAL وpg_hba.conf وإعداد الخادم تنتمي إلى المنصة، لا إلى هذا الرف.

التعريف — ما هو SQL، وما ليس هو

SQL لغة تصريحية. تقول ماذا تريد («كل الشحنات لهذا العميل، الأحدث أولًا»)، والمحرّك يقرر كيف يحصل عليها — أي الفهارس يسير فيها، وكيف يدمج، وبأي ترتيب يفعل الأشياء. هذا عكس كودك الإجرائي: في حلقة الطلب تكتب خطوات؛ في SQL تكتب الهدف. مهمة كاتب SQL الجيد هي صياغة الهدف بحيث يرى مخطط المحرّك المسار الرخيص (وهذا موضوع قسمي الفهرس وEXPLAIN).

اللغة نفسها عبر PostgreSQL وMySQL وSQLite وSQL Server — مشتركة بنحو ~90%«مكدس» خلفي — SQL ليست Node ولا .NET؛ إنها ما يستدعيه كلاهما

SQL مقابل NoSQL: المحرّكات الارتباطية تمنحك ACID وJOIN والقيود؛ مخازن المستندات تمنحك مخططات مرنة وتوسعًا أفقيًا. موقف الرف (نمذجة البيانات التعريف، ما بعد الافتراض الارتباطي): الارتباطي افتراضيًا، ومخازن المستندات حين يكون المخطط متغيّرًا فعلًا — ويغطي JSONB في PostgreSQL معظم تلك الحالات دون مغادرة العالم الارتباطي. SQL لن تذهب إلى أي مكان؛ إنها اللغة المشتركة للبيانات.

أساسيات الاستعلام — تشريح SELECT

كل استعلام جملة واحدة: من هذه الجداول، فلتر إلى هذه الصفوف، شكّلْها في هذه الأعمدة. أهم نموذج ذهني في SQL هو أن الترتيب الكتابي وترتيب التنفيذ مختلفان:

-- WRITTEN order (how you type it):
SELECT   department, COUNT(*)
FROM     employees
WHERE    hired_at > '2020-01-01'
GROUP BY department
HAVING   COUNT(*) > 5
ORDER BY department
LIMIT    10;

-- EXECUTION order (how the engine actually does it):
-- 1. FROM        pick the source rows (joins happen here)
-- 2. WHERE       filter rows            (cannot use aliases!)
-- 3. GROUP BY    fold rows into groups
-- 4. HAVING      filter groups          (cannot use aliases!)
-- 5. SELECT      compute output columns (aliases born here)
-- 6. ORDER BY    sort the output        (can use aliases)
-- 7. LIMIT       cut the output

معظم أخطاء SQL أخطاء ترتيب: WHERE كان ينبغي أن تكون HAVING، أو اسم مستعار استُخدم قبل أن يوجد. احفظ ترتيب التنفيذ مرة واحدة وسيصبح الباقي مفردات.

NULL — المصدر الأول لأخطاء SQL

NULL ليست قيمة؛ إنها غياب قيمة، ولا تُقارن كقيمة. NULL = NULL ليست صحيحة — إنها NULL (غير معروفة). القواعد الثلاث التي تنهي الالتباس:

WHERE email IS NULL          -- the ONLY way to test for absence (never = NULL)
WHERE email IS NOT NULL      -- its inverse
WHERE score IS DISTINCT FROM 5   -- "not equal, counting NULL as a value" (PostgreSQL)

SELECT COALESCE(nickname, full_name, 'Anonymous')  -- first non-NULL, left to right
SELECT NULLIF(a, b)          -- NULL if a = b, else a   (handy for divide-by-zero)
SELECT COUNT(*)              -- counts rows, including NULLs
SELECT COUNT(email)          -- counts only non-NULL values — a subtle difference!

CASE والتحويل النوعي

CASE هي if/else الخاصة بـ SQL — تعبير يعيد قيمة لكل صف، ويُستخدم في أي موضع يُقبل فيه تعبير (SELECT وWHERE وORDER BY). التحويل النوعي بـ :: (في PostgreSQL) أو CAST(x AS type) (المعياري) يحوّل الأنواع — وهو فخ أداء كلاسيكي حين يُطبَّق على أعمدة مفهرسة (انظر الأداء).

SELECT CASE WHEN total > 1000 THEN 'large'
            WHEN total > 100  THEN 'medium'
            ELSE 'small' END AS size
FROM shipments;

SELECT '42'::int,  total::numeric(10,2)   -- PostgreSQL cast syntax
SELECT CAST('42' AS INT);                -- standard, works everywhere

JOIN — المهارة الجوهرية

البيانات الارتباطية تعيش في جداول منفصلة؛ JOIN تعيد تجميعها. JOIN هي قاعدة اقتران: لكل صف في اليسار، ابحث عن الصفوف المطابقة في اليمين بمفتاح. وكل ما عداه هو أي الصفوف تُبقى.

SELECT s.tracking_number, c.name AS customer
FROM   shipments s
JOIN   customers c ON c.id = s.customer_id;

كيف يدمج المحرّك (ولماذا قد يكون الاستعلام نفسه سريعًا أو بطيئًا): يختار المخطّط خوارزمية لكل JOIN. Nested loop — لكل صف في اليسار، افحص الجانب الأيمن (ممتاز حين يكون أحد الجانبين صغيرًا أو كان المفتاح مفهرسًا). Hash join — ابنِ جدول تجزئة لأحد الجانبين وافحص بالآخر (ممتاز للمساواة الكبيرة، الافتراضي للمجموعات الكبيرة). Merge join — الجانبان مرتّبان، سِرْ فيهما معًا (ممتاز حين يكون الجانبان مرتّبين مسبقًا بالمفتاح). لا تختارها أنت؛ أنت تشكّلها بإعطاء المخطّط ما يحتاجه — فهرسًا على مفتاح الدمج. فهرس مفقود على مفتاح الدمج هو الطريقة الكلاسيكية التي يفحص بها استعلام ذو مظهر جميل الجدول كاملًا سرًا.

JOIN مقابل الاستعلام الفرعي: أي شيء يفعله استعلام فرعي في FROM أو عبر فلتر مترابط، تعبّره JOIN عادةً بشكل أكثر قابلية للقراءة. الاستثناء: مضادات الدمج بنمط NOT IN وفحوصات الوجود، حيث يكون EXISTS أوضح وأسرع (انظر الاستعلامات الفرعية). قاعدة الإبهام: فضّل JOIN للدمج؛ وفضّل EXISTS للفحص.

مشكلة N+1 — حيث تصطدم الحلقات والاستعلامات. النمط المضاد: جلب 50 طلبًا باستعلام واحد، ثم تشغيل 50 استعلامًا إضافيًا — واحد لكل طلب — لجلب كل عميل (هذا ما تفعله ORM بصمت حين تصل إلى علاقة غير محمّلة). الإصلاح JOIN واحدة (أو استعلام IN واحد)، والموطن الرسمي لهذا النمط هو هندسة الواجهة الخلفية §1e؛ وهذه هي SQL التي تصلحه:

-- N+1 (51 queries): the loop fetches customers one by one
-- one JOIN (1 query):
SELECT o.id, o.total, c.name
FROM   orders o
JOIN   customers c ON c.id = o.customer_id
WHERE  o.created_at > now() - interval '7 days';

LATERAL — الاستعلام الفرعي المترابط كدمج. لا تستطيع JOIN عادية الإشارة إلى الصف الذي تُدمج منه؛ LATERAL تستطيع. وهذا يجعلها أداة «أعلى N لكل مجموعة» والمساعدات لكل صف التي لا يستطيع المخطّط التعبير عنها وإلّا:

-- each customer's 3 most recent orders
SELECT c.name, recent.id, recent.total
FROM   customers c
CROSS JOIN LATERAL (
  SELECT o.id, o.total FROM orders o
  WHERE  o.customer_id = c.id
  ORDER  BY o.created_at DESC LIMIT 3
) recent;

اقرأها على أنها «لكل عميل، شغّل هذا الاستعلام الداخلي باستخدام معرّف العميل» — وهذا بالضبط كيف ينفّذها المحرّك. استخدم LATERAL حين يعيد استعلام فرعي مترابط مجموعة تريد الدمج معها؛ واستخدم دالة نافذة حين تُحسب «أعلى N لكل مجموعة» على القسم كله دفعة واحدة (قسم الدوال النافذة) — تفوز LATERAL حين تحتاج أعمدة أخرى من الاستعلام الداخلي.

التجميع — طي الصفوف في مجموعات

التجميع هو شقيق WHERE على مستوى المجموعة: WHERE يفلتر الصفوف؛ GROUP BY تطويها في مجموعات؛ HAVING تفلتر المجموعات. كل عمود في SELECT يجب أن يكون إما دالة تجميع أو عمود GROUP BY — يفرض المحرّك ذلك، والخطأ صديقك.

SELECT   department, COUNT(*) AS headcount, AVG(salary) AS avg_salary
FROM     employees
WHERE    status = 'active'            -- row filter, before grouping
GROUP BY department
HAVING   AVG(salary) > 50000           -- group filter, after grouping
ORDER BY headcount DESC;

تعبيرات الجدول المشترك (CTE) — بند WITH. تعبّر CTE عن نتيجة وسيطة بالاسم بحيث يُقرأ الاستعلام من الأعلى للأسفل كخط أنابيب. لا تعمل مرة واحدة بطريقة سحرية (حتى تُثبَّت في PostgreSQL، هي أقرب إلى وحدات ماكرو) — قوتها الفائقة هي قابلية القراءة، وحيلتها الفريدة هي التكرار:

WITH active_customers AS (
  SELECT id, name FROM customers WHERE last_order_at > now() - interval '90 days'
)
SELECT c.name, COUNT(o.id) AS orders
FROM   active_customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name;

-- Recursive CTE: walk a tree (categories, org charts, comment threads)
WITH RECURSIVE tree AS (
  SELECT id, name, 1 AS depth FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.name, t.depth + 1 FROM categories c
  JOIN tree t ON c.parent_id = t.id

الدوال النافذة — الترتيب والمجاميع الجارية

دوال التجميع تطوي الصفوف في نتيجة واحدة لكل مجموعة. الدوال النافذة تحسب قيمة بنمط التجميع لكنها تُبقي كل صف. هذا هو الفرق كله — ولهذا تحتاجها «أعلى N لكل مجموعة» (كانت GROUP BY ستطوي الصفوف التي تريد إبقاءها).

SELECT  name, department, salary,
        ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rank_in_dept,
        SUM(salary)   OVER (PARTITION BY department)                       AS dept_total,
        AVG(salary)   OVER (PARTITION BY department ORDER BY hire_date)    AS running_avg
FROM employees;
الدالة النافذةماذا تفعلاستخدام كلاسيكي
ROW_NUMBER()الموضع داخل القسمأعلى N لكل مجموعة: رتّب الصفوف ثم فلتر rank <= 10 في استعلام خارجي
RANK() / DENSE_RANK()ترتيب مع التعادلات (RANK يتخطى أرقامًا، DENSE_RANK لا)لوحات المتصدرين
LAG(col) / LEAD(col)قيمة الصف السابق / التالي في القسمالفروق: total - LAG(total) = التغيّر منذ الشهر الماضي

صياغة النافذة في سطر واحد: FUNCTION OVER (PARTITION BY X ORDER BY Y) — PARTITION BY ترسم المجموعات (مثل GROUP BY)، وORDER BY تحدّد الترتيب الذي تسير فيه الدالة داخل كل مجموعة. نافذة بلا قسمين وبلا ترتيب تحسب على المجموعة كلها.

الإطارات — النافذة داخل النافذة. افتراضيًا يجعل ORDER BY في نافذة الإطار «كل الصفوف حتى الصف الحالي شامله» (لهذا تعمل المجاميع الجارية). يمكنك تصغير الإطار صراحةً — الأداة وراء المتوسطات المتحركة و«آخر 7 أيام»:

-- running total (default frame: current row and everything before it)
SUM(amount) OVER (ORDER BY date)

-- moving average of the last 3 rows
AVG(amount)  OVER (ORDER BY date ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)

-- trailing 7-day sum
SUM(amount)  OVER (ORDER BY date RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW)

اتجه إلى بند الإطار اللحظة التي يظهر فيها «نافذة آخر N صفوف» أو «آخر 7 أيام» — بدونه تحصل على المجموع الجاري كله، ويكون الرقم خاطئًا على نحو خفي.

أعلى N لكل مجموعة، مكتمل:

SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
  FROM employees
) ranked
WHERE rn <= 3;

الترحيل بالمفاتيح (قاتل OFFSET): OFFSET 100000 يجعل المحرّك يسير في 100000 صف ويتخلص منها. الترحيل بنمط المؤشر — «أعطني الصفوف بعد هذا» — يستخدم الفهرس مباشرةً. تصميم واجهات البرمجة (API) تملك عقد المؤشر؛ هذا هو الاستعلام:

-- OFFSET (slow on deep pages):  SELECT * FROM events ORDER BY id LIMIT 20 OFFSET 100000;
-- Keyset (fast, uses the index):
SELECT * FROM events WHERE id > :last_seen_id ORDER BY id LIMIT 20;

كتابة البيانات — INSERT وUPDATE وDELETE وUPSERT

القراءات تهيمن على اللغة، لكن الكتابات هي حيث تعيش الصحة. الأفعال الأربعة، مع إضافات PostgreSQL التي تجعل الكتابات أكثر أمانًا:

INSERT INTO shipments (tracking_number, customer_id, status)
VALUES ('TRK-1001', 42, 'pending')
RETURNING id, tracking_number;          -- get the row back in one round trip

UPDATE shipments SET status = 'in_transit'
WHERE  id = 7;                          -- never UPDATE without WHERE

DELETE FROM shipments WHERE id = 7;     -- never DELETE without WHERE
TRUNCATE  shipments;                    -- wipe all rows instantly (no WHERE allowed)

UPDATE shipments SET status = 'delivered'
FROM   customers c                      -- UPDATE ... FROM: join in the update
WHERE  shipments.customer_id = c.id AND c.plan = 'premium';

UPSERT — الكتابة ذاتية التساوي. مفاتيح التساوي الذاتي في وثيقة تصميم واجهات البرمجة تحتاج قاعدة بيانات لا تخطئ في المحاولة الثانية. INSERT ... ON CONFLICT في PostgreSQL هو ذلك تمامًا: حاول الإدراج؛ إذا اصطدم قيد تفرد، افعل شيئًا آخر (حدّث، أو لا تفعل شيئًا):

-- The idempotent write: retry-safe, no "duplicate key" error on the second call
INSERT INTO payment_events (idempotency_key, amount, status)
VALUES (:key, :amount, 'captured')
ON CONFLICT (idempotency_key) DO UPDATE SET status = EXCLUDED.status
RETURNING id;

INSERT INTO tags (name) VALUES ('sale')
ON CONFLICT (name) DO NOTHING;          -- the "get-or-create" pattern

-- MySQL spelling, for the WordPress-era mental model:
-- INSERT INTO tags (name) VALUES ('sale') ON DUPLICATE KEY UPDATE name = name;

RETURNING (في PostgreSQL) يعيد الصفوف المتأثرة — هدية المطوّر الكسول: رحلة ذهاب وإياب واحدة لإدراج وقراءة المعرّف المولّد، وهذا بالضبط ما يحتاجه معالج الطلب لبناء استجابته. (يدعمه SQLite أيضًا؛ مكافئ MySQL هو LAST_INSERT_ID() متابعةً.)

المعاملات في SQL — BEGIN وCOMMIT وROLLBACK

المعاملة دفعة عبارات تنجح أو تفشل معًا. كتابات حلقة الطلب متعددة الخطوات (خصم + إنشاء شحنة + إشعار) ذرّية فقط إذا وُضعت في غلاف:

BEGIN;                                  -- or START TRANSACTION
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                                 -- both become visible together

-- on any error instead:
ROLLBACK;                               -- both vanish; the world never saw a half-write

ACID عمليًا: الذرّية هي بالضبط ما تشتريه بـ BEGIN/COMMIT/ROLLBACK. الاتساق هو قيود المخطط وهي تؤدي عملها. العزل هو مقبض المستوى — موطنه في نمذجة البيانات — مستويات العزل وهندسة الواجهة الخلفية — §5؛ والسطر الواحد هنا: READ COMMITTED (افتراضي PostgreSQL، لقطة لكل عبارة) مقابل REPEATABLE READ (لقطة لكل معاملة — نفس SELECT مرتين ترى نفس البيانات). المتانة هي WAL، والتي تثق بالمنصة في إدارتها.

نمط الفشلماذا يحدثالتجنّب
معاملة محتجزة طويلًاالأقفال تحجب كل كاتب آخر؛ يستنزف تجميع الاتصالاتأبقِ المعاملات قصيرة — لا استدعاءات واجهات برمجة ولا حلقات داخلها؛ ثبّت وتابع
طريق مسدود (deadlock)معاملتان تحمل كلٌّ منهما قفلًا تريده الأخرى؛ المحرّك يقتل واحدةاقفل الصفوف بالترتيب نفسه دائمًا (مثلًا بالمعرّف)؛ أعد المحاولة للمعاملة المقتولة

نقاط الحفظ — تراجع جزءًا من المعاملة، لا كلها. كتابة طويلة (استورد عميلًا، ثم طلباته، ثم مدفوعاته) لا يجب أن تموت كليًا لأن صفًا واحدًا كان سيئًا. علّم نقطة، وعند الخطأ ارجع إليها فقط:

BEGIN;
INSERT INTO customers (name) VALUES ('Lina') RETURNING id;   -- id = 10
SAVEPOINT orders_done;
INSERT INTO orders (customer_id, total) VALUES (10, 99);      -- fails (bad constraint)
ROLLBACK TO SAVEPOINT orders_done;                            -- customer survives, order rolled back
COMMIT;

قفل الصفوف — ادّعِ الصفوف حتى لا يدّعي عاملان الصف نفسه. SELECT ... FOR UPDATE يقفل الصفوف المرتجعة حتى الالتزام، وبهذا يضمن صفّ انتظار ألا يلتقط عاملان الوظيفة نفسها:

SELECT * FROM jobs WHERE id = 42 FOR UPDATE;                  -- lock this row for the transaction
SELECT * FROM jobs WHERE id = 42 FOR UPDATE SKIP LOCKED;     -- skip rows already locked by others
SELECT * FROM jobs WHERE id = 42 FOR UPDATE NOWAIT;          -- error out instead of waiting

ثلاث كلمات، ثلاثة سلوكيات لصفّ الانتظار: العادي ينتظر القفل (وقد يصل إلى طريق مسدود)، وSKIP LOCKED يقفز إلى الصف الحر التالي (افتراضي عامل الطابور)، وNOWAIT يفشل سريعًا (أفضل من انتظار طويل حين يكون الصف لشخص آخر). عادة إعادة المحاولة في وثيقة اختبار البرمجيات والتصحيح هي ما يجعل SKIP LOCKED آمنة على نطاق واسع.

الأقفال الاستشارية — قفل بشروطك أنت. للأقسام الحرجة على مستوى التطبيق غير المرتبطة بصف جدول (إعادة بناء مخبأ، إعادة تصنيف أسعار)، يتيح لك PostgreSQL قفل عدد صحيح اعتباطي:

SELECT pg_advisory_lock(12345);       -- session lock; release with pg_advisory_unlock(12345)
SELECT pg_advisory_xact_lock(12345);  -- transaction lock; releases automatically on COMMIT/ROLLBACK

الشكل الجلسي يتبع الاتصال، فالقفل المسرَّب يبقى حتى يُغلق الاتصال؛ الشكل المعاملي يتبع المعاملة، وهو ما تريده معاملات حلقة الطلب القصيرة. استخدم أقفال الجداول نادرًا والأقفال الاستشارية نادرًا؛ نمط SKIP LOCKED لصف الانتظار يغطي معظم الحاجات الحقيقية.

-- "Find posts of type 'product' that have meta 'on_sale' = '1'"
SELECT p.ID, p.post_title
FROM   wp_posts p
JOIN   wp_postmeta m ON m.post_id = p.ID
WHERE  p.post_type = 'product' AND p.post_status = 'publish'
  AND  m.meta_key = 'on_sale' AND m.meta_value = '1';

-- "Count published posts per category"
SELECT t.name, COUNT(*) AS post_count
FROM   wp_terms t
JOIN   wp_term_taxonomy tt ON tt.term_id = t.term_id
JOIN   wp_term_relationships tr ON tr.term_taxonomy_id = tt.term_taxonomy_id
JOIN   wp_posts p ON p.ID = tr.object_id
WHERE  tt.taxonomy = 'category' AND p.post_status = 'publish'
GROUP BY t.name;

SQLite ليس خادمًا — إنها مكتبة تقرأ وتكتب ملفًا واحدًا. إنها محرّك قاعدة البيانات الأكثر انتشارًا على وجه الأرض (كل هاتف ومتصفح يحمل واحدًا) ورفيقة التطوير المحلي في الرف: الاختبارات والنماذج الأولية ومخازن طبقة الطرفية المدعومة بملفات.

مثال عملي — طبقة الاستعلام لتتبع الشحنات

صمّم الرف هذا النظام مرتين: المخطط في نمذجة البيانات — المثال العملي، وواجهة البرمجة في تصميم واجهات البرمجة (API). هنا طبقة الاستعلام التي تربطهما — SQL الفعلية وراء أربع نقاط نهاية، كلٌّ منها محسّنة بأدوات هذه الوثيقة.

1. نقطة نهاية التفاصيل — شحنة واحدة مع عميلها (LEFT JOIN، فهرس على المفتاح الأجنبي):

SELECT s.tracking_number, s.status, s.estimated_delivery,
       c.name AS customer_name, c.email
FROM   shipments s
LEFT JOIN customers c ON c.id = s.customer_id
WHERE  s.tracking_number = :tracking_number;

2. الخط الزمني — آخر 20 حدثًا، مرتّبة بالمفاتيح (ترحيل بالدوال النافذة، لا OFFSET):

SELECT * FROM shipment_events
WHERE  shipment_id = :id AND event_id < :cursor   -- keyset: continue after the cursor
ORDER BY event_id DESC
LIMIT  20;

3. لوحة القياس — عدّادات الحالة لكل ناقل هذا الأسبوع (GROUP BY + FILTER):

SELECT carrier,
       COUNT(*)                                            AS total,
       COUNT(*) FILTER (WHERE status = 'delivered')       AS delivered,
       COUNT(*) FILTER (WHERE status = 'in_transit')      AS in_transit,
       COUNT(*) FILTER (WHERE status = 'exception')       AS exceptions
FROM   shipments
WHERE  created_at >= now() - interval '7 days'
GROUP BY carrier
ORDER BY total DESC;

4. معالج الويب هوك ذو التساوي الذاتي (UPSERT — آمن ضد وصول نفس الويب هوك مرتين):

INSERT INTO shipment_events (shipment_id, status, payload, webhook_id)
VALUES (:shipment_id, :status, :payload, :webhook_id)
ON CONFLICT (webhook_id) DO NOTHING
RETURNING id;

مرحلة التحسين: مرّر كلًا منها عبر EXPLAIN ANALYZE. Seq Scan الدالّ على shipment_events في الاستعلام 2 يقول إن الفهرس مفقود؛ الإصلاح هو الفهرس الذي تفرضه وثيقة نمذجة البيانات أصلًا: CREATE INDEX ON shipment_events (shipment_id, event_id DESC); — الزوج يغطي WHERE وORDER BY في بنية واحدة. تلك هي الحلقة كلها: استعلام ← شرح ← فهرس ← إعادة شرح.

وصفات استعلام — الأنماط التي يستخدمها الإنتاج فعلًا

ثلاثة أنماط تظهر في كل قاعدة كود حقيقية تقريبًا. كلٌّ منها وصفة صغيرة قابلة للحفظ تطوي الأقسام السابقة معًا.

الحذف الناعم — «محذوف» كطابع زمني، لا كإزالة. الحذف التدميري مخيف (مسارات تدقيق، أخطاء مفاتيح أجنبية، لا تراجع)؛ النمط هو تعليم الصف وفلترته في كل مكان:

ALTER TABLE orders ADD COLUMN deleted_at timestamptz;      -- NULL = live, timestamp = deleted
UPDATE orders SET deleted_at = now() WHERE id = 42;        -- "delete"
SELECT * FROM orders WHERE deleted_at IS NULL;             -- the live view (every read must add this)
CREATE INDEX ON orders (customer_id) WHERE deleted_at IS NULL;   -- partial index: only live rows

الثمن انضباط — كل استعلام يحتاج فلتر deleted_at IS NULL أو تتسرّب الحذوفات إلى النتائج، وتصطدم قيود UNIQUE بالصفوف القديمة (عميل أعيد إنشاؤه يقاتل عميلًا محذوفًا ناعمًا). استخدمه حين تحتاج مسار تدقيق أو «تراجعًا»؛ للقمامة الخالصة، احذف حذفًا صلبًا. الفهرس الجزئي هو اصطلاح PostgreSQL الذي يُبقي جداول الحذف الناعم سريعة.

صفّ انتظار المهام — ادّعِ الصفوف حتى يحصل عامل واحد فقط على كل وظيفة. أعمال الواجهة الخلفية (رسائل البريد، تغيير حجم الصور، إعادة محاولات الويب هوك) تمر عبر جدول؛ يطالب العمال بالوظائف بـ FOR UPDATE SKIP LOCKED من قسم المعاملات:

-- worker picks exactly one unclaimed job, without fighting other workers:
UPDATE job_queue SET status = 'processing', locked_at = now(), locked_by = :worker
WHERE id = (
  SELECT id FROM job_queue
  WHERE status = 'pending'
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED LIMIT 1
)
RETURNING *;

هذه هي بدائية صفّ الانتظار كلها: جدول وظائف، ومطالبة بـ SKIP LOCKED حتى لا يتصادم العمال المتزامنون، وعمود إعادة محاولة لعادة وثيقة اختبار البرمجيات والتصحيح. أضف عدّادَي attempts/max_attempts وRETURNING * — وستحصل على الشكل نفسه لصفوف الانتظار المدعومة بـ Redis، دون النظام الثاني. هذا هو النمط وراء «لماذا وظيفتي عالقة في pending» — عادةً مات عامل بعد المطالبة، فأضف مهلة تعيد وضع الصفوف processing القديمة في الطابور.
