ما يغطيه هذا المستند

المعسكرات: CMS/خادم كلاسيكي، HTML-first مع جزر، SPA، ميتا-إطار عمل، إشارات، WASM/هجين. لا أطر (paradigm-shift، angular-evolution). لا آليات JS (سلسلة الدروس). لا انقسام JS/TypeScript — ذلك في الوثيقة الشقيقة عبر المنصات. معرفة المعسكرات تنقذك من افتراض أن كل واجهة أمامية نفس النموذج الذهني.

عمق المسح، لا دروس. كل قسم: ما يحسّن له المعسكر، ما ستراه في الكود، ومتى يفوز أو يخسر.

هذه المعسكرات تتداخل. "تطبيق Next.js" هو ميتا-إطار عمل يمكنه التصرف كـ SPA في بعض المسارات. موقع WordPress يمكنه استضافة SPA إدارة React مخصص. تعامل مع التسميات كـ مراكز ثقل، لا نوادٍ حصرية.

ملاءمة المهمة. مهمتك لا تزال أساسيات JS → قراءة React في العمل. هذا المسح توجيه للنصف الثاني. لا تحتاج لإتقان كل معسكر. تحتاج أن تفتح مستودعاً وتقول: "هذا HTML-first مع جزر Preact" أو "هذا تطبيق App Router RSC" دون ذعر.

معسكر A — CMS وتطبيقات مُعرضة من الخادم كلاسيكية

أقدم نمط صناعي: الخادم يملك المستند. PHP (WordPress، Laravel)، Rails، Django، ASP.NET MVC، وأطر مشابهة تعرض HTML في كل طلب. JavaScript سكر اختياري للنماذج، الشرائح، وأدوات الإدارة.

ما ستراه

  • ملفات قوالب (.php، .erb، .jinja) مع HTML ومتغيرات خادم مختلطة.
  • jQuery أو سكربتات DOM خام في مجلدات الثيمات — لا تزال شائعة جداً في WordPress.
  • متغير "CMS منفصل الرأس": Contentful، Sanity، Strapi، WordPress REST/GraphQL — API محتوى + واجهة أمامية مبنية في معسكر آخر.
  • واجهات إدارة تكون SPAs كاملة (Gutenberg، لوحات تحكم مخصصة) تجلس فوق خلفية كلاسيكية.

متى يفوز

  • مواقع محتوى، تسويق، مدونات، كتالوجات تجارة إلكترونية مع سير تحريري ثقيل.
  • فرق مهارتها الأساسية في الخلفية أو عمليات المحتوى، لا هندسة SPA.
  • صفحات حرجة لـ SEO حيث "HTML في الاستجابة الأولى" غير قابل للتفاوض والفريق يعرف الـ CMS بالفعل.

متى يخسر

  • UI منتج تفاعلي للغاية (لوحات زمن حقيقي، أدوات تصميم، حالة عميل معقدة).
  • منتج متعدد المنصات يشارك المنطق مع الموبايل (React Native، إلخ).

نصيحة قراءة لمتعلم JS: لا تخلط بين "هناك وسم script" و "هذا تطبيق React." تتبع من يملك الطلاء الأول: إذا أرسل الخادم HTML كاملاً لمحتوى الصفحة، فأنت في معسكر A (أو B)، حتى لو ثبت ويدجت React لاحقاً.

معسكر B — HTML-first والجزر

أطر HTML-first تعامل المستند كمنتج و JavaScript كأداة دقيقة. السفينة الرئيسية الحديثة هي Astro: تشحن صفر JS افتراضياً؛ تفعيل "جزر" تفاعلية (React، Preact، Svelte، Vue، Solid) فقط حيث يلزم. العائلة ذات الصلة: HTMX / Alpine / UI موجه من الخادم — أبقِ المنطق على الخادم، بادل شظايا HTML عبر السلك.

ما ستراه

  • معظم المسارات HTML ساكنة أو معروضة من الخادم مع حزمة عميل شبه معدومة.
  • توجيهات مثل client:load / client:visible على المكونات (Astro) — حدود ترطيب صريحة.
  • اختيار Preact على React للجزر لأن ~3.5 kB مهم عندما باقي الصفحة ساكنة (انظر §٩).
  • سمات HTMX مثل hx-get، hx-swap — تحديثات صفحة جزئية بلا موجّه عميل.

متى يفوز

  • مواقع تسويق، توثيق، مدونات، تسويق منتج غني بالمحتوى مع بعض الويدجتس التفاعلية.
  • ميزانيات أداء و Core Web Vitals كمؤشرات أداء رئيسية.
  • فرق تعبت من شحن إطار عمل 200 kB لنموذج اتصال.

متى يخسر

  • منتجات شبيهة بالتطبيق حيث كل بكسل تقريباً حالة تفاعلية (أدوات من فئة Figma، لوحات تحكم بحالة عميل كثيفة).
  • عندما ينمو "رسم الجزر" حتى تعيد اختراع SPA بشكل سيء.

معسكر C — SPA (React، Vue، Svelte، Solid)

العميل يملك الواجهة بالكامل بعد التحميل الأول. الخادم يرسل غلاف HTML فارغ + حزمة JS كبيرة. التوجيه، الحالة، جلب البيانات — كلها في المتصفح.

ما ستراه

  • createRoot / mount على div#root فارغ.
  • موجّه جانب عميل (react-router، vue-router، @solidjs/router).
  • جلب بيانات جانب عميل (useQuery، swr، rtk-query، useEffect + fetch).
  • إدارة حالة عالمية (Redux، Zustand، Jotai، Pinia، إشارات Solid).

متى يفوز

  • منتجات عالية التفاعل: لوحات تحكم، أدوات تصميم، تعاون زمن حقيقي، إعدادات معقدة.
  • فرق تستثمر بالفعل في نظام بيئي لـ SPA (مكتبة مكونات، أنماط اختبار، خبرة).
  • عندما SEO ليس المحرك الأساسي (تطبيق خلف تسجيل دخول، لوحة إدارة داخلية).

متى يخسر

  • صفحات تسويق عامة حيث LCP/SEO مهمان — تحتاج SSR/SSG.
  • حزم أولية كبيرة تؤذي المستخدمين على موبايل منخفض المواصفات.
// نموذج SPA React العقلي — العميل يملك الحلقة

  const [user, setUser] = useState(null);
  return ;
}

معسكر D — ميتا-أطر العمل (Next.js، Remix، Nuxt، SvelteKit، Astro + SSR)

ميتا-إطار العمل يملك التقسيم: يقرر لكل مسار ما يُعرض على الخادم، ما يُبنى عند البناء، وما يترطب على العميل. العلم الرئيسي: مكونات خادم React (RSC) في Next.js App Router — الدوال تعمل على الخادم، ترجع UI، لا حافلات (hooks) على الخادم.

ما ستراه

  • موجه نظام ملفات (app/ في Next.js، routes/ في Remix).
  • "use client" توجيهات ترسم حدود العميل/الخادم.
  • جلب بيانات في مكونات الخادم (async function Page() { const data = await db.query() }).
  • Actions، Mutations، و Form actions للـ POST من دون API صريح.
  • بث (Streaming) و Suspense لتهيئة تدريجية.

متى يفوز

  • منتجات تحتاج SEO + تفاعلية (تجارة إلكترونية، SaaS عام، أسواق).
  • فرق تريد قرارات بنية معمارية أقل (الموجه، الجلب، التخزين المؤقت محلولة).
  • نقل تدريجي من SPA: مسار بمسار.

متى يخسر

  • فريق صغير، منتج بسيط — الحمل الزائد للإطار يتجاوز الفائدة.
  • حافة متخصصة حيث وقت بدء WASM البارد يهزم SSR.
// نموذج Next.js App Router العقلي — الخادم يقرر، العميل يتفاعل
// app/dashboard/page.tsx — مكون خادم افتراضي
export default async function Dashboard() {
  const data = await getDashboardData(); // يعمل على الخادم، لا حزمة عميل
  return ;

معسكر E — مكتبات الإشارات (Preact Signals، Solid، Qwik، Vue، Svelte 5 runes)

نموذج تفاعلي مختلف: الإشارات (خلايا تفاعلية دقيقة) بدلاً من الدالة التفاعلية ذات المدى العلوي لـ React. التبعيات تتعقب تلقائياً؛ لا إعادة عرض المكون بالكامل عند تغير حالة ورقة.

ما ستراه

  • const count = signal(0)، count.value++ — تحديثات دقيقة.
  • لا قواعد حافلات (hooks rules)، لا اعتماديات useEffect، لا useMemo/useCallback.
  • إشارات مشتقة (computed(() => count.value * 2)) — تلقائياً محفوظة.
  • Qwik: قابلة للاستئناف — لا ترطيب. HTML مسلسلة مع حالة؛ التفاعل يبدأ فوراً.
المكتبةنمط APIملاحظات
Preact SignalsHooks + إضافة @preact/signalsAPI بشكل React، ويب-first، صغيرة؛ §٩
Solidإشارات أولية، JSX، لا DOM وهميأداء قريب من DOM خام؛ نموذج ذهني مختلف عن React
Qwikاستئناف، useSignal، useClientEffectصفر JS في التحميل الأول؛ التفاعل يستأنف من HTML

متى يفوز

  • تحديثات تكرارية عالية، لوحات تحكم زمن حقيقي، محركات ألعاب في المتصفح.
  • فرق تفضل "الحالة كقيم" على "الحالة كإغلاقات في حلقة عرض".
  • Qwik: منتجات حيث TTI (وقت التفاعل) هو الـ KPI رقم 1.

متى يخسر

  • نظام React البيئي مطلوب (مكتبات مكونات ضخمة، توظيف، معرفة موجودة).
  • الفريق يعرف نموذج React الذهني جيداً؛ تكلفة التحول > الفائدة.

النماذج الذهنية — كيف يفكر ممارسو المعسكرات فعلاً

كل معسكر يدرّب نموذجاً ذهنياً مختلفاً. إذا كنت تعرف نموذج إعادة العرض في React فقط، ستقرأ كود المعسكرات الأخرى خطأً. إليك كيف يفكر ممارسو كل معسكر فعلاً:

المعسكرالنموذج الذهني الأساسيماذا تعني «التغيير»حدس التصحيح
CMS / كلاسيكي (A) الصفحة = قالب + بيانات. الخادم يعيد عرض الصفحة الكاملة عند تغير الحالة. رحلة ذهاب وإياب كاملة أو استبدال جزء جزئي. تتبع القالب + المتحكم. لا ترطيب عميل.
HTML-first / الجزر (B) مستند ثابت بثقوب دقيقة للتفاعلية. الجزيرة وحدها تعيد العرض؛ الباقي HTML خامل. اعثر على توجيه client:* ← هذه حدود React/Preact.
SPA React (C) الواجهة = f(الحالة). إعادة العرض = إعادة تشغيل دالة المكون + الفرق. تغير الحالة ← يعاد تشغيل المكون ← يعيد الأطفال العرض (إلا مع memo). React DevTools: لماذا أعاد هذا العرض؟ إغلاق قديم؟ memo ناقص؟
ميتا-إطار RSC (D) مكونات الخادم = دوال نقية لكل طلب. مكونات العميل = نموذج React. الخادم: طلب جديد = دالة جديدة. العميل: مثل SPA. افحص حد "use client". سجلات الخادم ≠ سجلات العميل.
الإشارات (E) رسم تفاعلي: خلايا (إشارات) ← مشتقات (computed) ← تأثيرات. لا إعادة تشغيل مكون. اكتب إلى إشارة ← المشتركون وحدهم يتحدثون. دالة المكون تعمل مرة غالباً. Signal DevTools: أي الإشارات تغيرت؟ أي تأثيرات اشتعلت؟ لا «عدّاد عرض».
WASM (F) زمن تشغيل لغة أجنبية. JS = صمغ؛ المنطق = وحدة مُجمَّعة. استدعِ الدالة المُصدَّرة ← احصل على النتيجة. لا تفاعلية داخل WASM. حلل وحدة WASM (perfetto، wasm-bugs). جهة JS رقيقة.

مزلقة النقل: جلب نموذج «إعادة العرض» من React إلى أطر الإشارات يسبب فرط الاشتراك (معاملة الإشارات كحالة، وقراءتها أثناء العرض). جلب نموذج «علم الأوساخ» للإشارات إلى React يسبب فقدان memo. تعلم النموذج الأصلي للمعسكر أولاً.

معسكر F — WASM / واجهة أنظمة هجينة

منطق ثقيل (فيزياء، تشفير، معالجة صور، محركات ألعاب) مترجم إلى WebAssembly. JS طبقة غراء رفيعة للـ DOM، الشبكة، والتكامل مع المنصة.

ما ستراه

  • ملفات .wasm محمولة عبر WebAssembly.instantiateStreaming أو وحدات ES.
  • Rust/C++/Go/Zig → wasm-bindgen / wasm-pack / wasi-sdk خطوط إنتاج.
  • واجهة JS: import { processImage } from './pkg' —Typescript definitions مولدة.
  • أحياناً: Leptos، Dioxus، Yew (أطر Rust تعرض DOM من WASM).

متى يفوز

  • حوسبة مكثفة يجب أن تعمل في المتصفح (محررات، CAD، ML استدلال، تشفير).
  • مشاركة كود مع خلفية/موبايل (Rust، Go، C++).

متى يخسر

  • CRUD، نماذج، تسويق — تكلفة WASM غير مبررة.
  • الفريق يفتقر مهارات لغات الأنظمة.

مثال محلول. تفتح مستودعاً فيه package.json يحتوي next وreact وtailwindcss؛ ودليل app/ بملفات layout.tsx وpage.tsx وعدة ملفات تبدأ بـ "use client"، وposts/[slug]/page.tsx؛ وصفحات تسويق بلا مكونات عميل. القراءة:

  1. المعسكر الأساسي: ميتا-إطار (App Router RSC مع جزر عميل).
  2. نموذج العرض: RSC — الصفحات مكونات خادم إلا مع علامة عميل؛ التفاعلية تعيش خلف "use client" فقط.
  3. التوجيه: نظام الملفات؛ [slug] مسار ديناميكي؛ layout.tsx يستمر عبر التنقل.
  4. نموذج البيانات: مكونات الخادم تجلب المحتوى؛ مكونات العميل تدير الحالة التفاعلية.
  5. مناطق الخطر: حد الخادم/العميل، التخزين المؤقت، عدم تطابق الترطيب.
  6. حد النموذج الذهني: نموذج إعادة العرض في React ينطبق داخل مكونات العميل فقط؛ صفحات التسويق تتصرف أشبه بمخرج ثابت / HTML-first.

أبعاد المعسكرات المتقاطعة — العرض، التوجيه، الحالة، البيانات

تختلف المعسكرات في أربعة أبعاد تشترك في الباقي. معرفة أين تجلس قاعدة كود على كل واحد هي «قراءتها» كلها.

الأنماط الهجينة

قواعد الكود الحقيقية غالباً هجينة مقصودة، لا تصميم رديء. سمّ المعسكر الأساسي أولاً، ثم المعسكر الثانوي المضمّن.

الأطر ليست معسكرات. يمكن لإطار أن يخدم معسكرات متعددة حسب استراتيجية العرض وملكية الحالة وميزانية JS: Preact عارض جزر صديق للإشارات (E أو B)، وAngular يمكن أن يكون شبيه ميتا-إطار وقائماً على الإشارات (D أو E)، وAstro يمكن أن يكون معسكر B أو D، وReact يمكن أن يكون جزيرة أو SPA أو ميتا-إطار.

تحول TypeScript

لم يعد TypeScript «جميلاً أن تملكه» في الواجهة الأمامية الصناعية. استطلاعات Stack Overflow أظهرت JavaScript كلغة الأكثر استخداماً سنوات متتالية، مع TypeScript كطبقة معنونة يتبناها معظم الفرق المحترفة لكود التطبيق. للقصة الكاملة JS-مقابل-كل-شيء عبر الخلفية/الجوّال/المدمج/الذكاء الاصطناعي، انظر JavaScript عبر الأكوام. الواقع العملي في 2026:

  • قوالب Next.js / Vite / Angular الجديدة تفترض TypeScript أو تقدمه أولاً.
  • أنواع المكتبات تُشحن داخل الحزمة؛ any رائحة مراجعة كود، لا استراتيجية.
  • مهمتك تبقى صحيحة في JS عادي أولاً — الأنواع تجلس فوق النماذج الذهنية التي تبنيها (النطاق، الإغلاقات، this، الوحدات). تعلّم TS قبل تلك النماذج هو حفظ ترميز لسلوك لا تستطيع التنبؤ به بعد.

حين تضيف TS لاحقاً: ابدأ بـ strict، وعلّم حدود الدوال والبيانات من واجهات API، واترك الاستدلال المحلي وشأنه. الشهادة لا تتطلب TypeScript؛ كود العمل غالباً سيتطلبه.

طبقة عصر الذكاء الاصطناعي (أداة، لا معسكر واجهة)

الذكاء الاصطناعي لم يخترع نموذج عرض جديداً. غيّر كيف يُنتج الكود ويُراجع:

  • المساعدون والوكلاء يولّدون المكونات والاختبارات وإعادة البناء — الجودة ما زالت تعتمد على الإنسان الذي يعرف قراءة الإغلاقات ومصفوفات التبعيات.
  • ميزات منتجات الذكاء الاصطناعي في التطبيقات: واجهات دردشة، رموز متدفقة، واجهات استدعاء أدوات — عادة ما زالت مكونات React/Vue فوق SSE/WebSocket.
  • عمل تدريب / ترميز الذكاء الاصطناعي كمسار دخل لمن يستطيع تقييم جودة الكود والواجهات — انظر أسواق دخل الواجهة الأمامية.

أظهر استطلاع Stack Overflow لعام 2024 أغلبيات كبيرة من المطورين يستخدمون أدوات الذكاء الاصطناعي في العمل. بحلول 2026 أصبح ذلك محيطاً. المميِّز ليس «هل تستطيع الطلب؟» بل «هل تستطيع تمييز متى يكون الخطاف المُولَّد خاطئاً؟». لهذا تعمل هذه المساحة على أساسيات JS قبل موضة الأطر.

الذكاء الاصطناعي لا يزيل اختلافات المعسكرات؛ يجعل التعرف أهم. الكود المُولَّد يمكن أن يبدو مقنعاً في المعسكر الخطأ: اصطلاحات React لصقت في Svelte، وواجهات برمجية مخترعة، ومكونات مفرطة التوليد تخفي نموذج العرض الحقيقي. وظيفة الإنسان في المراجعة هي إعادة تحديد المعسكر، وفحص القيود، والتحقق أن الاصطلاح يطابق فعلاً.

    1. المعسكرات مراكز ثقل. التطبيقات الحقيقية هجينة؛ حدد الأساسي ثم الثانوي.
    2. استراتيجية العرض هي الفاصل الرئيسي. أين يُنتج الـ HTML أهم من صيغة الإطار.
    3. موقع الحالة يحدد النموذج الذهني. خادم، عميل، URL، إشارات، أو ذاكرة WASM يغير طريقة تفكيرك.
    4. ميزانية JS قيد معسكر. HTML-first وWASM يهتمان بالبايتات بشكل مختلف عن SPA.
    5. لا تنقل النماذج الذهنية عمياءً. إعادة عرض React ≠ رسم إشارات ≠ قوالب خادم.
    6. اختر بالقيود لا بالموضة. المحتوى والتفاعلية وSEO والفريق والميزانية تقرر.
    7. الهجرة تدريجية. شجرة خانقة، مسار-بمسار، جزيرة-بجزيرة — لا انفجار كبير أبداً.
    8. المنصة مشتركة. كل معسكر يُترجم في النهاية إلى HTML/CSS/JS/واجهات متصفح.

    قائمة الملخص — قراءة مستودع حقيقي

    الأسئلة التي تحدد فهمك — المرجع عند فتح أي مستودع واجهة:

    السؤالالجواب المختصر
    أي معسكر؟اقرأ التبعيات والإعداد وبنية المجلدات وHTML المصدر — لا كل ملف
    أين يعيش مصدر الحقيقة؟خادم، عميل، URL، إشارات، أم ذاكرة WASM؟
    ما استراتيجية العرض؟كامل من الخادم، جزر، CSR، SSR، SSG/ISR، بث/RSC، أم WASM؟
    من يملك الحالة؟خادم/عميل/URL — وكلاهما يحدد نموذجك الذهني
    هجين؟سمِّ الأساسي ثم الثانوي المضمّن
    ما حدود الخادم/العميل؟"use client"، client:*، المحمّلات/الإجراءات
    ما ميزانية JS؟بايتات المعسكر تحدد توقعات الأداء
    ما منطقة الخطر؟حدود الترطيب، التخزين المؤقت، الأسرار، الوصولية

    مسح المعسكرات جيد فقط بقدر الأدوات التي تجعل حدوده مرئية، قابلة للاختبار، وقابلة للهجرة. يسرد هذا القسم فئات الأدوات الأساسية، مع معايير قرار لكل منها.

    الفئةالأدوات / المنصاتالمُحفّز → الهدفمقاييس القرار
    تحديد المعسكر وكشف الإطار Wappalyzer، BuiltWith، Framework Detector (Astro)، @astrojs/compiler، استدلالات مخصصة قاعدة كود غير معروفة → معسكر معروف + إصدار + تكوين دقة الكشف؛ معدل الإيجابيات الكاذبة؛ وقت التحديد؛ تغطية التكوين
    أدوات الهجرة (معسكر-إلى-معسكر) هجرة جزر Astro، Next.js Codemods، React → Svelte/Vue/Solid codemods، @vue/compiler-sfc، Svelte migrate، Mitosis، Qwik CLI معسكر مصدر → معسكر هدف مع كود عاملي، أصيل درجة الأصالة؛ معدل اجتياز الاختبارات؛ % الإصلاح اليدوي؛ زمن المراجعة
    تحليل الحزمة وفرض الميزانية webpack-bundle-analyzer، Vite Bundle Analyzer، next-bundle-analyzer، @next/bundle-analyzer، bundlesize، ci-size حزمة غير معروفة → مقاسة، محددة الميزانية، مقفلة اجتياز/فشل الميزانية؛ اتجاه حجم الحزمة؛ عدد القطع؛ كشف التكرار
    أدوات الجزر / الترطيب الجزئي Astro (توجيهات client:*)، Qwik (قابلة للاستئناف)، Fresh (Preact)، Marko، Elder.js، 11ty + جزر ترطيب كامل → ترطيب انتقائي قائم على الجزر % بايتات تفاعلية؛ وقت الترطيب؛ TTI؛ عدد الجزر؛ تعقيد التكوين
    هجرة TypeScript وأمان الأنواع ts-migrate، TS Morph، tsc --isolatedModules، type-fest، Zod، Valibot، ArkType JS/TS فضفاض → TS صارم أصيل للمعسكر % any؛ تغطية الأنواع؛ سرعة الهجرة؛ تقليل أخطاء وقت التشغيل
    مقارنة نموذج التفاعل React DevTools، Svelte DevTools، Vue DevTools، Solid DevTools، @preact/signals-devtools، Knip نموذج ذهني خاطئ → فهم تفاعل مناسب للمعسكر عدد إعادة العرض؛ دقة الحالة المشتقة؛ تكافؤ إشارة/حافلة؛ وقت التصحيح
    ترجمة المعسكر بمساعدة الذكاء الاصطناعي GitHub Copilot، Cursor، Sourcegraph Cody، Continue، Cody، Windsurf، Cline "ترجم هذا المكون للمعسكر X" → كود هدف عامل، أصيل درجة الأصالة؛ معدل اجتياز الاختبارات؛ % الإصلاح اليدوي؛ زمن المراجعة

    طريقة اختيار: ابدأ بتحديد المعسكر + كشف الإطار ("مجموعة أدوات المسح الدنيا القابلة للحياة"). أضف أدوات الهجرة عند تقرير الانتقال. أضف تحليل الحزمة عند وجود ميزانية أداء. أضف أدوات الجزر عند استهداف HTML-first/ترطيب جزئي. أضف الترجمة بمساعدة الذكاء الاصطناعي عندما يعرف الفريق المعسكر المصدر لكن ليس الهدف. الأداة تخدم الهجرة — لا العكس.

      ما يغطيه هذا المستند

      يمكنك وضع قاعدة كود في معسكر (CMS، HTML-first، SPA، ميتا-إطار عمل، مكتبة إشارات، WASM هجين)، تعرف ما يحسّن له كل منها، وتعرف ما إذا كان نموذجك الذهني لإغلاقات React ينطبق كما هو، ينطبق فقط على جزيرة العميل، أو يجب تجاوزه. الهدف هو التعرف في العمل — لا تحويل كل مشروع لمعسكرك المفضل.
