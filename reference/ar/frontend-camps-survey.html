أي معسكر؟ → ما الذي يحسّن له → كيف يبدو الكود → متى يفوز/يخسر

ما يغطيه هذا المستند

المعسكرات: CMS/خادم كلاسيكي، HTML-first مع جزر، SPA، ميتا-إطار عمل، إشارات، WASM/هجين. لا أطر (paradigm-shift، angular-evolution). لا آليات JS (الـ ١٢ درس). لا انقسام JS/TypeScript — ذلك في الوثيقة الشقيقة عبر المنصات. معرفة المعسكرات تنقذك من افتراض أن كل واجهة أمامية نفس النموذج الذهني.

عمق المسح، لا دروس. كل قسم: ما يحسّن له المعسكر، ما ستراه في الكود، ومتى يفوز أو يخسر.

مرجع: المصطلحات — مفردات مشتركة عبر جميع مستندات المرجع.

هذه المعسكرات تتداخل. "تطبيق Next.js" هو ميتا-إطار عمل يمكنه التصرف كـ SPA في بعض المسارات. موقع WordPress يمكنه استضافة SPA إدارة React مخصص. تعامل مع التسميات كـ مراكز ثقل، لا نوادٍ حصرية.

ملاءمة المهمة. مهمتك لا تزال أساسيات JS → قراءة React في العمل. هذا المسح توجيه للنصف الثاني. لا تحتاج لإتقان كل معسكر. تحتاج أن تفتح مستودعاً وتقول: "هذا HTML-first مع جزر Preact" أو "هذا تطبيق App Router RSC" دون ذعر.

١. معسكر A — CMS وتطبيقات مُعرضة من الخادم كلاسيكية

أقدم نمط صناعي: الخادم يملك المستند. PHP (WordPress، Laravel)، Rails، Django، ASP.NET MVC، وأطر مشابهة تعرض HTML في كل طلب. JavaScript سكر اختياري للنماذج، الشرائح، وأدوات الإدارة.

ما ستراه

  • ملفات قوالب (.php، .erb، .jinja) مع HTML ومتغيرات خادم مختلطة.
  • jQuery أو سكربتات DOM خام في مجلدات الثيمات — لا تزال شائعة جداً في WordPress.
  • متغير "CMS منفصل الرأس": Contentful، Sanity، Strapi، WordPress REST/GraphQL — API محتوى + واجهة أمامية مبنية في معسكر آخر.
  • واجهات إدارة تكون SPAs كاملة (Gutenberg، لوحات تحكم مخصصة) تجلس فوق خلفية كلاسيكية.

متى يفوز

  • مواقع محتوى، تسويق، مدونات، كتالوجات تجارة إلكترونية مع سير تحريري ثقيل.
  • فرق مهارتها الأساسية في الخلفية أو عمليات المحتوى، لا هندسة SPA.
  • صفحات حرجة لـ SEO حيث "HTML في الاستجابة الأولى" غير قابل للتفاوض والفريق يعرف الـ CMS بالفعل.

متى يخسر

  • UI منتج تفاعلي للغاية (لوحات زمن حقيقي، أدوات تصميم، حالة عميل معقدة).
  • منتج متعدد المنصات يشارك المنطق مع الموبايل (React Native، إلخ).

نصيحة قراءة لمتعلم JS: لا تخلط بين "هناك وسم script" و "هذا تطبيق React." تتبع من يملك الطلاء الأول: إذا أرسل الخادم HTML كاملاً لمحتوى الصفحة، فأنت في معسكر A (أو B)، حتى لو ثبت ويدجت React لاحقاً.

٢. معسكر B — HTML-first والجزر

أطر HTML-first تعامل المستند كمنتج و JavaScript كأداة دقيقة. السفينة الرئيسية الحديثة هي Astro: تشحن صفر JS افتراضياً؛ تفعيل "جزر" تفاعلية (React، Preact، Svelte، Vue، Solid) فقط حيث يلزم. العائلة ذات الصلة: HTMX / Alpine / UI موجه من الخادم — أبقِ المنطق على الخادم، بادل شظايا HTML عبر السلك.

ما ستراه

  • معظم المسارات HTML ساكنة أو معروضة من الخادم مع حزمة عميل شبه معدومة.
  • توجيهات مثل client:load / client:visible على المكونات (Astro) — حدود ترطيب صريحة.
  • اختيار Preact على React للجزر لأن ~3.5 kB مهم عندما باقي الصفحة ساكنة (انظر مستند التحول §18.5b).
  • سمات HTMX مثل hx-get، hx-swap — تحديثات صفحة جزئية بلا موجّه عميل.

متى يفوز

  • مواقع تسويق، توثيق، مدونات، تسويق منتج غني بالمحتوى مع بعض الويدجتس التفاعلية.
  • ميزانيات أداء و Core Web Vitals كمؤشرات أداء رئيسية.
  • فرق تعبت من شحن إطار عمل 200 kB لنموذج اتصال.

متى يخسر

  • منتجات شبيهة بالتطبيق حيث كل بكسل تقريباً حالة تفاعلية (أدوات من فئة Figma، لوحات تحكم بحالة عميل كثيفة).
  • عندما ينمو "رسم الجزر" حتى تعيد اختراع SPA بشكل سيء.

٣. معسكر C — SPA (React، Vue، Svelte، Solid)

العميل يملك الواجهة بالكامل بعد التحميل الأول. الخادم يرسل غلاف HTML فارغ + حزمة JS كبيرة. التوجيه، الحالة، جلب البيانات — كلها في المتصفح.

ما ستراه

  • createRoot / mount على div#root فارغ.
  • موجّه جانب عميل (react-router، vue-router، @solidjs/router).
  • جلب بيانات جانب عميل (useQuery، swr، rtk-query، useEffect + fetch).
  • إدارة حالة عالمية (Redux، Zustand، Jotai، Pinia، إشارات Solid).

متى يفوز

  • منتجات عالية التفاعل: لوحات تحكم، أدوات تصميم، تعاون زمن حقيقي، إعدادات معقدة.
  • فرق تستثمر بالفعل في نظام بيئي لـ SPA (مكتبة مكونات، أنماط اختبار، خبرة).
  • عندما SEO ليس المحرك الأساسي (تطبيق خلف تسجيل دخول، لوحة إدارة داخلية).

متى يخسر

  • صفحات تسويق عامة حيث LCP/SEO مهمان — تحتاج SSR/SSG.
  • حزم أولية كبيرة تؤذي المستخدمين على موبايل منخفض المواصفات.

٤. معسكر D — ميتا-أطر العمل (Next.js، Remix، Nuxt، SvelteKit، Astro + SSR)

ميتا-إطار العمل يملك التقسيم: يقرر لكل مسار ما يُعرض على الخادم، ما يُبنى عند البناء، وما يترطب على العميل. العلم الرئيسي: مكونات خادم React (RSC) في Next.js App Router — الدوال تعمل على الخادم، ترجع UI، لا حافلات (hooks) على الخادم.

ما ستراه

  • موجه نظام ملفات (app/ في Next.js، routes/ في Remix).
  • "use client" توجيهات ترسم حدود العميل/الخادم.
  • جلب بيانات في مكونات الخادم (async function Page() { const data = await db.query() }).
  • Actions، Mutations، و Form actions للـ POST من دون API صريح.
  • بث (Streaming) و Suspense لتهيئة تدريجية.

متى يفوز

  • منتجات تحتاج SEO + تفاعلية (تجارة إلكترونية، SaaS عام، أسواق).
  • فرق تريد قرارات بنية معمارية أقل (الموجه، الجلب، التخزين المؤقت محلولة).
  • نقل تدريجي من SPA: مسار بمسار.

متى يخسر

  • فريق صغير، منتج بسيط — الحمل الزائد للإطار يتجاوز الفائدة.
  • حافة متخصصة حيث وقت بدء WASM البارد يهزم SSR.
// نموذج Next.js App Router العقلي — الخادم يقرر، العميل يتفاعل

٥. معسكر E — مكتبات الإشارات (Preact Signals، Solid، Qwik، Vue، Svelte 5 runes)

نموذج تفاعلي مختلف: الإشارات (خلايا تفاعلية دقيقة) بدلاً من الدالة التفاعلية ذات المدى العلوي لـ React. التبعيات تتعقب تلقائياً؛ لا إعادة عرض المكون بالكامل عند تغير حالة ورقة.

ما ستراه

  • const count = signal(0)، count.value++ — تحديثات دقيقة.
  • لا قواعد حافلات (hooks rules)، لا اعتماديات useEffect، لا useMemo/useCallback.
  • إشارات مشتقة (computed(() => count.value * 2)) — تلقائياً محفوظة.
  • Qwik: قابلة للاستئناف — لا ترطيب. HTML مسلسلة مع حالة؛ التفاعل يبدأ فوراً.
المكتبةنمط APIملاحظات
Preact SignalsHooks + إضافة @preact/signalsAPI بشكل React، ويب-first، صغيرة؛ مستند التحول §18.5b
Solidإشارات أولية، JSX، لا DOM وهميأداء قريب من DOM خام؛ نموذج ذهني مختلف عن React
Qwikاستئناف، useSignal، useClientEffectصفر JS في التحميل الأول؛ التفاعل يستأنف من HTML
Vue 3 / Svelte 5ref()/reactive()، runesإشارات مدمجة في DX الإطار

متى يفوز

  • تحديثات تكرارية عالية، لوحات تحكم زمن حقيقي، محركات ألعاب في المتصفح.
  • فرق تفضل "الحالة كقيم" على "الحالة كإغلاقات في حلقة عرض".
  • Qwik: منتجات حيث TTI (وقت التفاعل) هو الـ KPI رقم 1.

متى يخسر

  • نظام React البيئي مطلوب (مكتبات مكونات ضخمة، توظيف، معرفة موجودة).
  • الفريق يعرف نموذج React الذهني جيداً؛ تكلفة التحول > الفائدة.

٦. معسكر F — WASM / واجهة أنظمة هجينة

منطق ثقيل (فيزياء، تشفير، معالجة صور، محركات ألعاب) مترجم إلى WebAssembly. JS طبقة غراء رفيعة للـ DOM، الشبكة، والتكامل مع المنصة.

ما ستراه

  • ملفات .wasm محمولة عبر WebAssembly.instantiateStreaming أو وحدات ES.
  • Rust/C++/Go/Zig → wasm-bindgen / wasm-pack / wasi-sdk خطوط إنتاج.
  • واجهة JS: import { processImage } from './pkg' —Typescript definitions مولدة.
  • أحياناً: Leptos، Dioxus، Yew (أطر Rust تعرض DOM من WASM).

متى يفوز

  • حوسبة مكثفة يجب أن تعمل في المتصفح (محررات، CAD، ML استدلال، تشفير).
  • مشاركة كود مع خلفية/موبايل (Rust، Go، C++).

متى يخسر

  • CRUD، نماذج، تسويق — تكلفة WASM غير مبررة.
  • الفريق يفتقر مهارات لغات الأنظمة.

٣ب. مسارات الهجرة بين المعسكرات

الفرق نادراً ما تبقى في معسكر واحد للأبد. هجرات شائعة ونقاط احتكاكها:

من → إلىالمحفزالحالة الهدفالخطواتالمخاطرإشارات النجاحالجدول الزمني

نمط مضاد: إعادة كتابة كبيرة. كل هجرة ناجحة في الجدول أعلاه تدريجية، مسار بمسار، أو جزيرة بجزيرة. حدود المعسكر في جدول المسح (§٠) هي مراكز ثقل — لا جدران.

    ١١. النظام الإيكولوجي — كتالوج الأدوات مع معايير القرار

    مسح المعسكرات جيد فقط بقدر الأدوات التي تجعل حدوده مرئية، قابلة للاختبار، وقابلة للهجرة. يسرد هذا القسم فئات الأدوات الأساسية، مع معايير قرار لكل منها.
