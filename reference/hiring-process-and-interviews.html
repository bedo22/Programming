Definition — the funnel, and what this doc is not

The hiring process is a filtering funnel: each stage removes candidates cheaply so the expensive stages see few people. HR screens for risk and fit; technical rounds screen for skill and judgment; the offer stage screens for compensation alignment. How hiring changed — why the funnel looks like this

The funnel is not a law of nature; it's a response to volume. Each era added a filter because the previous one let too many candidates through to the expensive stages:

EraHiring modelWhat changed
Local & classifiedsAds, referrals, walk-ins; the geography constrained the poolHiring was a neighborhood conversation; no funnel needed
Online job boardsMonster, Indeed, LinkedInGlobal visibility → applications per role exploded → the resume became the first filter
ATS eraMachine parsing, keyword scoringResumes are read by software first; structure and keywords stopped being optional
Skills-based screeningHackerRank, LeetCode, take-homesProof of skill replaced credential checking; the technical screen became the gate
Remote & globalAsync rounds, recorded interviews, time-zone negotiationWritten communication and autonomy became filters (§4)

Why this matters for you: every new filter lands on the candidate before the expensive stages, so the resume gets thinner, the screen gets earlier, and your written communication gets more heavily weighted. The doc's §1, §3, and §4 rules are responses to exactly these three shifts.

1. The resume & the application — the signal gate

The resume is not a biography; it is a filter for the next filter. Recruiters spend seconds, not minutes, and an automated system (ATS) may read it before a human. Three rules:

  1. One page until you have a decade of relevant work. Recruiters skim; a two-page entry-level resume is a self-inflicted skip.
  2. Outcomes, not duties. "Built the checkout flow" is a duty; "Rebuilt the checkout flow: 41% fewer abandoned carts in two months" is a signal. Numbers, when honest, are the strongest signal an early-career resume has.
  3. Tailor to the JD. If the posting names TypeScript and testing, those words should appear in your resume because they're true — this is alignment, not keyword-stuffing. The shelf's rule from Freelance Web Practice §Portfolio applies 1:1: a portfolio is a case study, not a gallery — three case studies with measurable outcomes beat a wallpaper store of screenshots.

What belongs on an entry-level frontend resume, in order: one line of identity and contact, one line of positioning ("frontend developer, JavaScript/React/TypeScript"), skills grouped by honesty level (fluent vs used vs seen — the .NET doc's honest-framing principle), 2–3 case-study projects with outcomes, and education/certs. Your GitHub is a second resume: clean commit history, a README that explains why the project exists, and a live link. A repo with no README is a wall of walls.

The failure mode to avoid: the "skills soup" resume — every framework ever touched listed as equal, no projects, no outcomes. Interviewers read it as "no judgment about what I actually know", which is the first risk signal of the whole funnel.

The bullet formula: every line is action verb + what you did + measurable impact + tools/context. The impact is what converts a duty into a signal:

Weak (a duty)Strong (a signal)
Built a websiteBuilt a client website with WordPress and a custom theme, reducing page-load time by 35%
Used ReactBuilt a React dashboard with filtering and pagination, improving task-completion time for 20 internal users
Fixed bugsFixed the checkout validation bug, reducing failed submissions by 12%

No work experience yet? Projects count — write them with the same formula: "Built a task manager with React and localStorage, implementing optimistic UI, empty states, and keyboard navigation." A project written as a signal beats a job written as a duty.

Junior-specific guidance: everything you lack in tenure, compensate with proof you can ship. Before applying: 2–3 case studies with a live demo, README, and one measured outcome; a clear positioning line; and practice explaining those projects out loud until they're 60-second stories. If you have no referrals, apply thoughtfully and follow up — quality of application, not volume, is the junior's only leverage.

2. The cover letter & the application package

The cover letter is optional at most startups and expected at enterprises, agencies, and anywhere a human reads before an ATS does. When it's required, three short paragraphs, no more: who you are and what you build; why this company (the same specific thing you'd say to "why our company" — one concrete feature or problem, not a template); and what you'd bring that the JD didn't ask for. It is a filter too: a template letter with the company name swapped in reads as "applied to a hundred of these".

The rest of the package is your portfolio and public identity: the portfolio is a case study, not a gallery (Freelance Web Practice §Portfolio — three projects with outcomes beat a wallpaper store); LinkedIn is the resume's public copy, so keep it consistent with the resume rather than a second, contradictory story; and the GitHub profile is checked by engineers — clean commit history, a README that explains why, and a live link. One ATS reality: machines parse text, so keep the resume's structure standard (headings, dates, plain text) — a clever two-column layout that scans well for humans can parse to gibberish for the filter that reads it first.

The ATS checklist — a machine reads it first:

  • Standard headings: Experience, Projects, Skills, Education — no clever titles.
  • Plain text where possible; avoid tables, images, and graphics that parse badly.
  • Tailor keywords honestly: if the JD names TypeScript and testing and it's true, it belongs on the page.
  • Include links: GitHub, portfolio, live demos — but keep them in text, not icons.
  • Quantify outcomes wherever you honestly can; the parser passes numbers through.

What the portfolio must prove — one project, five signals:

Portfolio elementWhat it proves
Live demoYou can ship something real
GitHub repoYou can organize code
READMEYou can explain the project (the writing-sample signal)
Case studyYou can describe problem → decisions → outcome
TestsYou care about correctness
Deploy pipelineYou understand delivery (CI/CD)

The case-study structure (write one per flagship project, 3–5 paragraphs): 1) the problem, 2) the constraints, 3) your approach, 4) the key decisions and trade-offs, 5) the outcome with a number, 6) what you'd improve. That last point is the senior tell — a project without a "what I'd do differently" reads as a project you've stopped thinking about.

3. The screening call & the technical screen

The screening call is a sanity check, not a test: do you speak the stack's language, do you know what you applied for, are your salary expectations in range, and can you communicate in the interview's working language. Have answers ready for what do you do, why this role, and a range, not a single number, when asked about salary — the shelf's own advice (Frontend Income Markets §Caveats) is to negotiate with a range.

The technical screen takes three forms — live coding, a take-home, or a video call with questions. The behavior is the same in all three:

  • Think out loud. The interviewer is evaluating your debugging and judgment, not just your syntax memory. Silence reads as "stuck and hiding it". Say what you're weighing, even when you don't know yet: "I could use a hash map here, but let me trace the edge case where the input has duplicates."
  • Plan before you code. State the approach in one or two sentences, sketch the input/output, then write. This is Pólya's phase two applied to an interview — Problem-Solving §Pólya's four phases is the whole method.
  • Correctness first, optimization second. A working solution you can explain and test beats a half-finished "optimal" one. The complexity budget in Algorithms & Data Structures shows why: O(n²) is fine for the n in the problem; say why it's fine.
  • Trace a concrete example by hand before running — it catches bugs early and shows the interviewer how you debug, which is the point.
  • Never fake fluency. If you don't know something, say what you do know and how you'd find the rest. The honest-framing line from .NET & the Enterprise Lane is the template for the whole funnel, not just .NET.

The live-coding playbook — the seven-step order that makes the five behaviors above automatic:

  1. Clarify. Input? Output? Edge cases? Constraints? Ask before you assume — ambiguity is where most solutions die.
  2. Restate it. "So the goal is to return the first non-repeating character, case-sensitive, null if none exists?" Confirming the contract out loud prevents solving the wrong problem.
  3. Start brute force. A correct O(n²) that you can explain beats a broken O(n). Optimize from correct, never from nowhere.
  4. Name the complexity. "This is O(n²) from the nested loop; I can get to O(n) with a hash map" — the interviewer is grading the awareness, not the final constant.
  5. Implement. Readable, clear variable names, no premature optimization. The code is a draft you'll talk through, not a submission.
  6. Test. Empty input, single element, duplicates, large input, invalid input — run the edge-case axis from the failure-modes table.
  7. If stuck: say what you're considering, try a concrete example, simplify the problem, ask whether your direction is reasonable. "Stuck but communicating" reads as a strong candidate; "stuck and silent" reads as a failure.

The review habit from Testing & Debugging is the exact muscle: read for correctness first, then maintainability, then performance — and always phrase the finding as the code's problem, not the author's.

For a take-home: read the prompt fully first, timebox it (the prompt or recruiter usually says how long it should take — a 4-hour cap is a filter, not a suggestion), commit cleanly, and write a short README covering how to run it and what you'd do next. A take-home judged on "did they finish, does it run, is it clean, could I review it" — all four are in your control. The take-home checklist:

One red flag to protect yourself with: a reasonable take-home is 2–5 hours. A large unpaid project — a full app, a week of work — is a red flag unless it's paid, optional, or clearly portfolio-worthy. Your time is a filter you control; use it.

Recruiter communication — the small mechanics that compound: reply within 24–48 hours, keep answers short, confirm the time zone in writing, state your availability clearly, ask about the process timeline, and follow up once after the stated timeline. Recruiters juggle dozens of funnels; a candidate who communicates predictably is a candidate they route to the front of.

4. The remote & async interview — time zones, recorded rounds, English

If you're targeting global remote, the funnel changes shape: rounds happen across time zones, technical screens are often async (a recorded round, a timed assessment, or a written answer), and the working language may be English you rarely speak day to day. Three mechanics most candidates get wrong:

  • Own the time-zone math. The recruiter's "10am" is your job to convert and confirm — write it down in your local time, check it the night before, and arrive early. "Which time zone was that?" during the call is a small signal that you're not used to global work, which is precisely the job you're applying for.
  • Async recorded rounds reward narration in writing. There's no interviewer to rescue a silence, so your reasoning has to survive on the page: state assumptions, name the trade-off you chose and why, and note what you'd do next. A recorded round where you solve silently is a silent rejection. (The "think out loud" rule from §3 becomes "explain in the text".)
  • English clarity beats English speed. Slow, plain, correct sentences read as competent; fast, tangled, accented ones read as anxious. Pause, keep sentences short, and if you miss a word, ask for it plainly. The market doc says English is a filter for remote work — treat every async written answer as a writing sample, because that's literally what it is.

One honesty check that belongs here because remote funnels hide it: work authorization is a top-of-funnel filter, not a negotiation point. If a posting requires a visa or specific employment status you don't have, asking "can you sponsor?" once is fine; applying anyway and hoping is not — it wastes everyone's funnel and burns the referral that got you in.

The remote environment checklist — the mechanics that never get evaluated out loud but always are:

ItemCheck
CameraEye-level, face clearly lit, clean or blurred background
MicrophoneNo echo, audible; test it in the same room you'll use
InternetStable; a phone hotspot as backup, already configured
IDE / editorReady, clean, readable font — nothing to fix at minute one

None of these is "the interview" — each one is a small way the interview can silently become about you instead of your answers. Eliminate them before the call, not during it.

5. The HR & behavioral interview — the "messy" questions

This is the room the intro asks about: "where do you see yourself in five years", "why our company", "why should we hire you", "what's your biggest weakness", leadership and teamwork, "what if a coworker struggles", "what if you need a holiday while the team is busy", how you'd handle your boss, your coworkers, your clients. It feels like small talk with landmines. Here is the lens that makes it legible: HR is doing risk assessment on you — the same discipline Security & Threat Modeling applies to systems, applied to a new dependency (you). Three risks are being priced:

  • Will you break the system? (ego, defensiveness, inability to take feedback)
  • Will you crash under load? (burnout, poor communication, panic)
  • Will you leave early? (mismatched expectations, impulse to quit at the first difficulty)

Every "messy" question is one of those three risks wearing a costume. Answer the risk, not the costume:

The questionThe risk being pricedThe answer shape
"Where do you see yourself in five years?"Will you leave early? Are your goals aligned with our budget?Mastery + ownership, tied to the work, not the job title. "Deep mastery of [the stack], owning increasingly complex features, mentoring juniors as the team scales."
"Why did you choose our company?"Did you apply here deliberately, or spam 500 applications?Name something specific and true: a shipped feature, a technical blog post, the user problem they solve. One concrete thing beats five generic compliments.
"Why should we choose you?"What is your value proposition vs. the other candidates?Bridge code and outcome: "I don't just write code; I understand the business outcome the code serves — maintainable, tested, shipped."
"What is your biggest weakness?"Do you have self-awareness, or is your ego a liability?Name a real, technical trade-off you struggle with, plus the mitigation. "I lean toward over-engineering; I now timebox design and apply YAGNI." Never "I work too hard."
"Tell me about a time you disagreed with a coworker/boss."Will you be a nightmare to review with? Do you hold grudges?Assume positive intent + data. "We disagreed on a schema; I benchmarked both read paths, the data decided, we moved on." The disagreement, the process, the resolution.
"What if a coworker is struggling with their task?"Teamwork and leadership without hierarchyOffer help directly, respect their autonomy, escalate only if it affects the deadline — and frame it as the team's problem, not gossip.
"What if you need a holiday while the team is busy?"Do you understand business priorities? Do you communicate early?Plan ahead and communicate: merge your PRs, document the handoff, align with the lead weeks out so the sprint isn't derailed. The point is the planning, not the holiday.
"How would you handle a difficult client / boss?"Do you set boundaries without burning bridges?Translate their need, state scope honestly, bring options — the exact scoping discipline Freelance Web Practice teaches for clients.

Two mechanics make every answer work:

  • STAR, always. Situation, Task, Action, Result — a 30-second story with a concrete result. An answer without an example is a claim; an answer with a STAR is evidence.
  • Answer the question asked. The classic failure is the rambling non-answer that dodges the risk being priced. If they ask about a weakness, give one — and the mitigation. A 90-second answer to a 20-second question reads as evasive.

Build your story bank before the interviews, not during them. Prepare 6–8 STAR stories, one per category, each re-tellable from memory in 30 seconds. The categories cover every behavioral prompt you'll meet:

CategoryExample prompt
Conflict"Tell me about a disagreement with a teammate."
Failure"Tell me about a time something broke."
Ambiguity"Tell me about working without clear requirements."
Deadline pressure"Tell me about a tight deadline."
User impact"Tell me about improving something for a user."
Learning"Tell me about learning a new technology quickly."
Initiative"Tell me about taking ownership without being asked."
Feedback"Tell me about receiving difficult feedback."

No work history? The stories come from wherever real work happened: a project, coursework, freelance, open source, a hackathon, volunteering. What makes a story evidence is the result, not the employer. If none of your stories has a number yet, go get one — build the thing that produces it. That's the §1 rule aimed at the behavioral round.

6. The system design round

When the funnel reaches architecture, the shelf's own framing is the correct mindset: the 45-minute whiteboard (URL shortener, rate limiter, chat) is a sample of the discipline, not the discipline — System Design §The discipline is the week-long work, not the 45-minute exercise. In the interview, the evaluators are watching for process, not a perfect diagram:

  1. Estimate before you design. Rough numbers for users, writes, reads, storage — the back-of-envelope discipline the System Design doc's capacity sections teach.
  2. Name the failure domains and consistency model before drawing boxes. One line each: "reads-heavy, eventual consistency is fine, the failure domain is the database" is senior-sounding because it is senior.
  3. Define the API contract — endpoints, payloads, error codes — the API Design habits.
  4. Verbalize trade-offs ("I chose X over Y because of the read pattern; if writes dominated I'd flip it"). Trade-offs are the actual signal in the round.
  5. Use the trust-boundary vocabulary from Security & Threat Modeling — where authentication lives, what an attacker sees. It is cheap and it marks you as someone who thinks adversarially.

The failure mode: jumping straight to boxes and load balancers. The interviewers learn nothing about your judgment and conclude "knows a diagram, doesn't know why". The checklist order — capacity → domains → consistency → contract → trade-offs — is the thing to practice until it's reflexive.

7. Panel rounds, culture fit & the reference check

Bigger firms add two rounds that smaller ones skip, and both feel like "not really an interview" — which is exactly why they filter people who only prepped for technical rounds.

Panel rounds. Several people, one session: the engineering manager weighs delivery, a senior weighs code quality, a product person weighs communication. They're not each testing everything — each owns one axis. The senior's question set and the PM's question set need different answers even though the room is the same; listen for who's asking and answer to their axis (the §6 contract habit — same skill, new room).

Culture fit. Often disguised as "let's meet the team over coffee" or "a chat with your future coworkers". It is not off-the-clock: it's the three risks from §5 priced socially — would I dread this person in review, in a deadline, in a disagreement. The answers are the same STAR discipline, one notch lighter. Two mistakes to avoid: treating it as a real test (answers become guarded) and treating it as truly off-the-record (complaining about a past boss to your future coworkers is a self-rejection). It's a conversation where you are also evaluating: do these people want what you want? Both parties filtering is the point.

The reference check. Near the offer, they call a past manager or peer. This one you control: choose references who can speak to a specific outcome (not "he's nice"), tell them you're using them so they're not surprised, and warn them the call is coming. A reference who says "I had no idea" is a worse signal than a reference you never listed. Honest framing applies backward too — never invent a reference, because the call is exactly how it's caught.

8. Presentation — dress, body language, how you talk

The shelf is not a finishing school, and this section stays deliberately small. The whole of it is one heuristic: mirror the company's baseline, plus ten percent. A bank or enterprise (the .NET lane) means a button-down or a neat sweater; a startup or agency means a clean, plain shirt — never a full suit at a modern tech startup, which signals you misread the culture. When in doubt, one notch above the recruiter's own level.

  • In person: hands on the table, slight forward lean, eye contact when they speak — the posture of engagement, not interrogation.
  • Remote: look at the camera lens when making a point; on video, the lens is the eyes. Test audio and background beforehand — "can you hear me" eats your first three minutes.
  • How you talk: short answers, then stop. Pause before answering (it reads as thinking, not stalling). Say "I don't know" plainly and offer your nearest knowledge — the honest-framing rule again.
  • In a technical round, the senior's body language is thinking out loud. Silence is the only posture that fails. Narrate your weighing of options even when you're not sure — that narration is the evidence of judgment.

9. Questions to ask them — the two-way interview

Every round ends with "do you have any questions for us?" — and "no" is the only wrong answer, because it signals you weren't evaluating them. A candidate who asks nothing reads as someone who'd take any job; a candidate with three sharp questions reads as someone who is choosing. You are also filtering, so ask what you actually need to decide:

  • The compounding question: "What would 'great' look like for this role in six months?" — it forces the manager to define success, and it reads as a candidate who plans to stay. (Same question, one more rung down the funnel, is your onboarding anchor — §10.)
  • Process questions: "How is code reviewed here?" / "How is feedback given when something ships wrong?" — these price the work environment you'll actually live in, and the Testing & Debugging review habit is the exact thing they'll describe.
  • Honest-framing questions: "What's the thing the team most needs to improve right now?" — a senior-framed question that also tells you whether the team can talk about its own debt (a huge signal).
  • Not this: anything the JD already answered, salary as the first question in round one (keep it to the screening range, §3), or a "gotcha" that makes you look like you're interrogating back.

One rule governs all of it: ask what you'll actually use. A rehearsed question you don't care about the answer to is as hollow as a rehearsed answer.

10. The offer, negotiation, and onboarding

An offer is not the end of the funnel; it is the last filter — compensation alignment. The shelf's rule from Frontend Income Markets §Caveats: negotiate with a range, not a single number. Anchor from the market data you gathered (the income docs' boards and peer anecdotes), and compare total compensation, not base alone — equity, bonus, benefits, remote flexibility, and growth all change the real number. Two more rules:

  • Say yes or no, not maybe. Once you have an offer, you are past the interview phase; ghosting or endless delay burns the goodwill you just earned.
  • Get it in writing. A verbal offer is a statement of intent; the signed offer letter is the contract. This mirrors the freelance rule that the contract is the relationship's memory. Local labor law and the written terms matter too — a signed letter is the baseline; read it.

The offer evaluation framework — "compare total comp" only works if you know what's in the total:

ComponentQuestions to ask
Base salaryIs it market-aligned for your level and location?
BonusHow often? How reliable? Target vs. guaranteed?
EquityVesting schedule? Cliff? Valuation? Liquidity?
BenefitsHealth, insurance, retirement
PTODays, sick leave, holidays
Remote policyFully remote, hybrid, equipment budget
GrowthMentorship, promotion path, learning budget
TeamManager quality, team stability
ProductDo users need it? Is it growing?
StabilityFunding, revenue, runway

Weight by level: for a junior, growth and mentorship may outweigh a small salary difference (the first two years of compounding mentorship are worth real money); for a senior, compensation and scope dominate. The framework is the same — only the weights change.

Negotiation — phrases, not scripts. These are shapes to adapt, not word-for-word answers. The doc's anti-script rule (the "Safely ignore" table) applies to memorized answers under interview pressure; planning your offer-stage ask is different — there you control the conversation. The moves:

MoveThe phrase shape
Salary range"Based on my research and the responsibilities of the role, I'm looking for a range around X to Y. I'm flexible depending on the full package."
Counter-offer"Thank you for the offer; I'm excited about the role. Based on the market and my experience, I was expecting a base closer to X. Is there flexibility there?"
Multiple offers"I'm in final stages with another company and expect an answer by [date]. I'm very interested here — can we align on a timeline?"
Need time"Thank you. Can I have 2–3 business days to review the full package and get back to you?"

Every phrase is honest, calm, and range-based — no ultimatums, no invented offers. A counter works when the only issue was compensation and trust survives the ask; if the reasons you were looking are bigger than money, no counter fixes them (the §11 rule, one stage early).

Then onboarding — the first 90 days. This is where offers succeed or quietly die, and it is the phase no doc on the shelf owns. The 90-day shape: first days, read and set up (the Terminal & Deployment Substrate doc is your friend — the repo will expect you to run things); first weeks, ship something small and take the team's code review as a gift, not a threat (the Testing & Debugging doc's review habit); first months, ask the question that compounds — "what would 'great' look like for this role in six months?" — and then do that. Ask questions early and in writing; a candidate who asks "what does great look like" reads as someone who plans to stay. The phased shape:

PhaseGoalActions
First weekSetup and orientationEnvironment setup, meet the team, understand the product
First monthSmall contributionShip a small fix, learn the codebase, ask questions in writing
First 90 daysTrust and directionOwn a small feature, clarify expectations, build relationships
ProbationProve reliabilityDeliver consistently, communicate early, ask for feedback

Questions to ask your manager in week one — each one converts a vague 90 days into a measurable 90 days:

  • What would success look like after 30/60/90 days?
  • What is the biggest team priority right now?
  • How is feedback usually given here?
  • What does good communication look like in this team?

11. Multiple offers, counter-offers & rejection

Two situations the funnel only reaches if it's going well — and one it always reaches eventually.

Multiple offers. The best position to negotiate from is a real alternative, but handle it honestly: tell each recruiter where you are in their timeline and when you need an answer from them, rather than silently running three funnels in parallel. Compare on total comp (the §10 rule), growth, and ownership — not the delta on base alone. If you're using offer B to push offer A, say so plainly and once; invented competing offers are the fastest way to get a "congratulations, go with them".

Counter-offers. When your current employer counter-offers to keep you, the honest framing is: you just told them you were leaving. The classic advice is that most people who accept a counter leave within a year anyway — the reasons you started looking don't disappear because they raised the number. The exception is when the real blocker was purely compensation and they fixed exactly that; the rule is to decide on the original reasons, not the flattery of being wanted.

Rejection. The funnel rejects most candidates most of the time — that is its design, not a verdict on you. Treat it as a data point: ask the one question that's actually answerable ("what would have made this a yes?") and mine the pattern across rejections rather than over-reading any single one. One rejection is noise; three pointing at the same thing (say, "no real project depth") is a signal with a fix — go build the case study the §1 rules describe. And when the process goes silent (ghosting): one polite follow-up, then move on. The funnel is a filter; a filter that ghosts you wasn't going to be a good manager anyway.

The thank-you and follow-up mechanics — small, low-cost, and consistently skipped:

WhenWhat to send
After an interviewA short thank-you, referencing one specific thing you discussed — not a template
After silence past the timelineOne polite follow-up: "You mentioned updates around [date]. Is there any update on next steps?"
After a rejectionAsk for one actionable piece of feedback; thank them for the process
After an offerAsk, in writing, for time to review the full package

Track your rejections — the pattern is the signal:

CompanyStage rejectedFeedbackPattern?
Company AResumeNo responseResume / portfolio issue?
Company BTechnicalStruggled to explainPractice thinking out loud
Company CBehavioralToo vagueBuild the STAR story bank (§5)

One rejection is noise; the stage of repeated rejections is the diagnostic. Rejected at the resume stage three times → the application package is the problem. Rejected at the technical stage three times → the interviews, not the resume. Fix the stage, not the whole funnel.

The AI era — what changes, and what doesn't

Hiring is automating the same way code is. The funnel doesn't disappear; the filters change what they measure:

SignalWhat it changes
AI resume screeningResumes must be clear, parseable, and evidence-based — the §1 rules get stricter, not softer
AI coding screensAI may assist or evaluate; disclosure policies matter — know the company's rules before the round
AI-assisted take-homesCompanies may ask about AI usage; honesty matters (§3's rule, one stage later)
AI interviewsRecorded or automated interviews reward clear narration — the §4 written-reasoning rule goes live
Human premiumJudgment, communication, debugging, and evaluation become more valuable — the things AI is worst at
Portfolio importanceProof of real work matters more when AI can generate code — the case study is your counter-evidence

One rule for the whole era: if a company asks whether you used AI, answer honestly according to their policy. The evaluation skill — explaining, verifying, and improving code — is exactly what the funnel now prices, and it's also what AI can't replace. The candidate who uses AI as a reviewer, not a ghostwriter, is the candidate the human premium is about.

Worked example — one funnel, end to end

Let's run one candidate, Amina, through the whole funnel to see the shape of each stage. She's a JS/React learner following the shelf, applying to a local product company that uses TypeScript, React, and a REST backend — and running one remote application in parallel for the §4 async round.

1 · Resume + cover letter: one page, "frontend developer ·
     JavaScript/React/TypeScript". Three projects with outcomes — "cut
     load time 40%", "12% fewer abandoned carts" — each linking to a repo
     with a README. The cover letter names one feature she actually uses.

2 · Screening call: she names what she built, why this company (a feature
     she actually uses), and gives a salary RANGE from the market doc.
     → Passes: real projects, real answer, realistic expectations.

3 · Live coding screen: "debounce an input that fetches results."
     She says the plan out loud, traces the fast-typing edge case by hand,
     then writes. → Passes: thinking out loud + correctness over cleverness.

4 · The parallel remote funnel (async): a recorded round. Same skill, but
     she writes her reasoning — assumptions, the trade-off chosen, next
     steps — because no interviewer is there to rescue a silence.
     → Passes: clarity in the text.

5 · HR behavioral: "biggest weakness?" Over-engineering, YAGNI mitigation,
     in STAR. "Disagree with a coworker?" — the schema disagreement, the
     benchmark, the data deciding. 30 seconds each.
     → Passes: self-awareness + evidence, no rambling.

6 · System design: "design a URL shortener." She estimates reads vs writes,
     says "reads-heavy, eventual consistency is fine", defines the API
     contract, names the DB as the failure domain. 45 minutes, one page.
     → Passes: process and trade-offs, not a perfect diagram.

7 · Panel + culture fit: the EM asks about delivery, a senior about code
     quality, a PM about communication — she answers to each axis. She also
     asks the compounding question: "What would 'great' look like here in
     six months?" → Passes: reads the room, filters back.

8 · Offer: base, equity, benefits. She compares total comp against the
     range from the market doc, negotiates the range, gets it in writing.

9 · First 90 days: sets up the repo, ships something small, takes review
     as a gift, asks "what does great look like in six months?" — and does it.

The pattern: every stage is passed by the same three habits — honest framing, thinking out loud, and answering the question that is actually being asked. The funnel is not nine different skills; it is one communication discipline wearing nine hats. That is why this doc is one doc.

Summary — the complete mental checklist

Print this. It is the entire doc in twenty-two lines:

#The line
1The funnel is a filter: every stage removes candidates cheaply. Know which filter you're passing.
2Resume = outcomes, not duties; one page; case studies with numbers; a repo README that explains why.
3Tailor to the JD — alignment, not keyword-stuffing; the cover letter names one real thing about them.
