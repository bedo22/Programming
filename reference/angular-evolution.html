Angular's Evolution — The Class, the Rewrite, and the Signal

How Angular's mental model of state and components evolved across three eras: AngularJS (dirty-checking + $scope), Angular 2+ (classes + zone.js), and modern Angular (Signals, standalone, zoneless). A companion to the class-to-hooks React doc.

Why this doc exists

The class-to-hooks paradigm doc covers React's internal arc. This doc covers the same period (2010-2026) for Angular — a different framework's answer to the same problems. At work you may encounter Angular monorepos (enterprise/government niches per the frontend camps survey). Understanding Angular's arc lets you place the code you're reading without converting it to React's model.

The key contrast throughout: where React moved reactivity from instance fields into function call order (hooks), Angular moved it from a broadcast-driven cycle (zone.js) into fine-grained subscriptions (Signals). Same direction — narrower watching — different mechanism.

0. The three eras — a timeline

Angular is not one framework. It is three frameworks with the same name — each rewriting the state and reactivity model from scratch. The eras:

EraYearsParadigmState mechanismReactivity model
1. AngularJS2010–2016MVW (Model-View-Whatever), controllers, $scope$scope tree — mutable objects linked to the templateDirty-checking — digest cycle walks the $scope tree comparing old vs new values
2. Angular 2+2016–2023Class components, TypeScript, DI, NgModulesClass instance fields — mutable, decorated via @Input / @OutputZone.js — monkey-patches browser APIs, then broadcasts "something changed" to all components, runs change detection
3. Modern Angular2023+Standalone components, Signals, zonelesssignal() / computed() / effect() — reactive primitivesSignal-based — a built-in subscription graph triggers only the components that depend on changed signals

The pattern: each era widened the developer experience and narrowed what the framework had to watch. AngularJS watched everything in the $scope tree (expensive). Angular 2+ watched all components on every async event (less expensive but still broad). Signals watch only the signal's dependency graph (minimal). React's evolution (classes → hooks → compiler) has the same direction but a different mechanism: instead of narrowing the watcher, React narrowed the component's own awareness of what changed (from this.setState to deps arrays to compiler inference).

1. Era 1 — AngularJS (2010–2016): dirty-checking and $scope

AngularJS was released in 2010 by Miško Hevery, solving the same problem as Backbone and Ember: make dynamic web apps manageable with structure. Its pitch was "Model-View-Whatever" — you put data in a $scope object, and Angular synced it to the HTML template automatically.

How state worked — $scope and dirty-checking

A controller function received a $scope from Angular's DI. You set properties on it directly. The template referenced them. Angular's digest cycle periodically "checked" each watched expression by comparing current value to the previous:

angular.module('app', [])
  .controller('CounterCtrl', function($scope) {
    // $scope is a regular JS object — mutating it IS the state change
    $scope.count = 0;

    $scope.increment = function() {
      $scope.count++;                    // mutate — no special API
      // Angular doesn't know yet. Next digest will see the change.
    };

    // $watch registers an expression for dirty-checking each digest cycle
    $scope.$watch('count', function(newVal, oldVal) {
      console.log('count changed from', oldVal, 'to', newVal);
    });
  });

Dirty-checking was brilliant for 2010 and painful by 2015. On every async event (click, setTimeout, XHR), Angular ran a "digest cycle" that walked every registered watch expression (often thousands), compared current vs previous value, and updated the DOM where they differed. If a watched expression returned a new array/object every time, Angular would see "change!" every cycle — forcing the developer to learn $scope.$watchCollection, $watch(…, true) for deep equality, and "track by" in ng-repeat. Performance was bounded by how many watches you had and how deep the tree was.

Two-way binding — the signature feature

AngularJS's killer feature was ng-model: changes in the input automatically updated $scope, and changes in $scope (from code) automatically updated the input. No event listeners, no setState — the framework owned the sync:

<input ng-model="user.name" />        // type here → $scope.user.name updates
<p>Hello, {{ user.name }}</p>          // $scope.user.name changes → text updates

The trouble: two-way binding made reasoning about data flow non-linear. Component A binding to $scope.shared.item and Component B also binding to it — who changed what, and in what order? In large apps, the digest cycle became a source of "Why did this update happen?" debugging, with watch count as the standard metric of "how fast is your app."

Why it collapsed

By 2014-2015, large AngularJS apps had accumulated thousands of watches. The digest cycle took 50-200ms — visible lag on every interaction. The team tried solutions (one-time binding ::, limiting watcher count, "controller as" syntax instead of raw $scope), but the architecture was the bottleneck. You cannot make dirty-checking over a complete tree cheap at scale.

The Angular team decided: the fix is a rewrite. Not a migration — a rewrite from zero, with TypeScript, a proper module system, and a completely different reactivity model.

2. Era 2 — Angular 2+ (2016–2023): classes, TypeScript, zone.js

Angular 2 (2016) was a full rewrite. Same team, same company, same problem domain — but everything else new: TypeScript-first, class components with decorators, dependency injection, a proper module system (NgModules), and zone.js as the reactivity engine.

How state worked — class instance fields + zone.js

Instead of mutating $scope, you wrote a class with decorated fields. Angular DI injected services via the constructor. The template bound to class properties:

@Component({
  selector: 'app-counter',
  template: `
    <p>Count: {{ count }}</p>
    <button (click)="increment()">+</button>
  `
})
export class CounterComponent {
  count = 0;                             // class instance field = state

  constructor(private logger: LoggerService) {}  // DI injection

  increment() {
    this.count++;                        // mutate directly — zone.js catches it
  }
}

No this.setState, no special state API. You mutated a class field directly. Angular trusted zone.js to notify it that "something happened" — any async operation (click handler, setTimeout, XHR response) was intercepted by zone.js, which signaled Angular to run change detection on all components (with the OnPush escape hatch per component). This was the key difference from React: React kept the "you must call setState" discipline; Angular removed it and paid the cost at the framework level.

Unidirectional data flow — the React influence

Angular 2 abandoned two-way binding as the default. Instead: @Input() passes data into the component (from the parent template), @Output() emits events up (via EventEmitter). The component's own state is its class fields. This was a direct React influence (2013-2015 React had proven that unidirectional flow beats two-way binding for debugging).

@Component({
  selector: 'app-child',
  template: `<p>{{ data }} <button (click)="onClick()">send</button></p>`,
  changeDetection: ChangeDetectionStrategy.OnPush  // opt out of zone-driven checks
})
export class ChildComponent {
  @Input() data: string;                 // from parent
  @Output() notify = new EventEmitter<string>();  // to parent

  onClick() {
    this.notify.emit('clicked!');
  }
}

Zone.js — the broadcast engine

Zone.js monkey-patches all browser async APIs (setTimeout, addEventListener, fetch, XHR, requestAnimationFrame). When any patched API fires, zone.js notifies Angular that "something happened." Angular then runs change detection from the root component down the tree — checking which components have @Input values that changed.

This "broadcast all" approach was a middle ground between AngularJS's "check every watch" and React's "re-render the function and diff the VDOM." It was faster than AngularJS but still had a cost: a click in a deeply nested button triggered a tree walk from the root, even if only one leaf component changed.

The OnPush strategy was the per-component escape hatch: "I will only update if my inputs change by reference, or if an event originated inside me." This was Angular's manual optimization layer — analogous to React's React.memo and shouldComponentUpdate.

Why this era didn't end well either

Zone.js was expensive. Every async event triggered a full tree walk (even with OnPush, Angular still traversed the tree to decide which components should re-check). Teams that aggressively used OnPush often reintroduced bugs where components should update but didn't — because zone.js had fired, but the input references hadn't changed per Angular's check. The tension: zone.js was too broad (check everything), but narrowing it required manual OnPush discipline that was easy to get wrong.

The same tension existed in React's class era: componentDidUpdate + setState worked, but knowing when and why a component re-rendered required manual profiling. React's solution was hooks (narrow the reactivity to explicit deps arrays). Angular's solution was Signals (narrow the reactivity to explicit subscriptions).

3. Era 3 — Modern Angular (2023–present): Signals, standalone, zoneless

Starting with Angular 16 (2023, preview) and stabilizing in 17+ (2024), Angular introduced three changes that retroactively define "modern Angular": standalone components (no NgModules), Signals (fine-grained reactivity), and (in v18+) zoneless change detection.

Standalone components — no NgModules

In Angular 2-15, every component must be declared in a NgModule — a separate class listing components, directives, pipes, and imports. This created a parallel file for every feature. Standalone components (v14 preview, v15 stable, v17 default) let the component declare its own dependencies without the NgModule wrapper:

@Component({
  selector: 'app-counter',
  standalone: true,
  imports: [CommonModule],              // direct dependencies, no NgModule file
  template: `<p>Count: {{ count() }} <button (click)="increment()">+</button></p>`
})
export class CounterComponent {
  count = signal(0);                     // reactive signal, not a plain field

  increment() {
    this.count.update(c => c + 1);       // set() or update() — framework sees the change
  }
}

Signals — signal(), computed(), effect()

The core Signal primitives:

  • signal(value) — a writable reactive reference. Call .set() to replace, .update(fn) to derive from current, .mutate() to modify the internal value in-place.
  • computed(fn) — a read-only derived value. Re-evaluated lazily only when its dependencies change. No "deps array" — Angular tracks dependencies at runtime (like Vue's computed or Preact Signals).
  • effect(fn) — a side-effect runner scheduled when its tracked dependencies change. The successor to ngOnInit/ngOnDestroy and manual subscription cleanup. The effect's cleanup is the return value of the function.
export class CartComponent {
  items = signal<Item[]>([]);            // writable signal
  total = computed(() =>                 // derived — no deps array needed
    this.items().reduce((sum, item) => sum + item.price, 0)
  );

  constructor() {
    effect(() => {
      console.log('Cart total:', this.total());  // re-runs only when items change
      // cleanup: return () => unsubscribe()
    });
  }

  addItem(item: Item) {
    this.items.update(list => [...list, item]);
  }
}

The key difference from React hooks: Angular Signals have no "rules of hooks." You can call signal() inside if, inside loops, inside event handlers, or at the class constructor — there's no call-order constraint because Signals are objects with a settable value and a subscription graph, not slot indices in a fiber. This is exactly the flexibility React said no to (see React's §2.9 — "Why Isn't X a Hook?"). Preact Signals proved this approach works; Angular Signals made it official.

Zoneless — why Signals can replace zone.js

Zone.js broadcasts "something changed" to all components. Signals know exactly which component depends on which signal. Once a signal's dep graph is in place, zone.js is redundant — Angular can fire change detection only on the components that subscribe to changed signals, plus their ancestors in the input-passing chain.

Angular 18 (2024) introduced experimental provideZonelessChangeDetection. Angular 20+ (2026) is moving toward zoneless as the default for new projects. This is the era's defining migration: remove zone.js, rely entirely on Signals for reactivity. The cost: all shared state must go through signal() or signal()-wrapped models. The payoff: zero-waste change detection — only the components that need to update, update.

4. The three eras through one lens — where state lives and who watches it

The React doc's §3 expansion asked: where does state live, who owns it, and how do you touch it? The same lens for Angular:

EraState lives in…You read state by…You write state by…Mental modelWho detects the change?
1. AngularJS A $scope object (mutable, linked to the template) $scope.property inside the controller $scope.property = newVal — direct mutation State is a plain object that syncs to the DOM; write to it and the framework syncs it The digest cycle — walks every registered watch expression on every async event
2. Angular 2+ A class instance field (mutable, decorated) this.property inside the component class this.property = newVal — direct mutation State is a class member; the framework detects mutations via zone.js broadcasting Zone.js — catches all async events and signals Angular to check all components
3. Modern Angular A signal() or signal()-backed model count() — call the signal as a getter count.set(n) / count.update(fn) — explicit mutation through the signal API State is a reactive node; only subscribers to that node get notified The signal's own dependency graph — knows exactly which components depend on which signals

The pattern: wider detection → narrower detection. AngularJS detected by brute force (walk everything). Angular 2+ detected by broadcast + tree walk (add OnPush to narrow). Modern Angular detects by subscription (only the subscribers). React's direction is the same but starts from a different place: React always had narrow detection (only components that called setState). React's evolution (hooks deps arrays → compiler) is about narrowing what you have to manually specify, not narrowing the framework's watcher.

5. Why Angular didn't follow React's hooks path

React hooks and Angular Signals both solve "how does a component hold state and react to changes?" — but they solve it from opposite starting points:

React started from functions. A React function component has no instance, no this, no constructor. To give it state, React had to invent a storage system outside the function — the fiber's hook slots. This required the rules of hooks (call order must be stable) because the hook slot is identified by its position in the call sequence, not by a name.

Angular started from classes. An Angular component is an instance with a constructor, DI injection, and class fields. To give it fine-grained reactivity, Angular had to replace the mutation-detection mechanism (zone.js) with an explicit subscription mechanism (Signals). But it could keep the class structure — Signals are just objects assigned to fields, no call order constraints, no "rules of Signals."

Crossing over would have cost each framework its defining feature:

  • If Angular adopted a hooks-like model, it would lose DI (you cannot inject into a function's call order — DI requires a constructor). DI is Angular's superpower for testability and large-team code organization.
  • If React adopted Signals as a replacement for useState, it would lose the per-render closure model (Signals return the latest value, not a snapshot — the stale-closure "problem" is actually the feature that makes React's per-render values predictable).

Both frameworks narrowed reactivity. They narrowed different things. React narrowed from "re-render everything" to "only re-render if deps change" to "let the compiler figure it out." Angular narrowed from "check everything on any async event" to "only check components that subscribe to changed signals." The direction is the same; the mechanism is constrained by each framework's original design — React's functions vs Angular's classes.

6. What you'll encounter in Angular code at work

Unlike React's class-to-hooks transition (where function components existed throughout but were second-class), Angular's eras are physically visible in the code — the file structure, imports, and syntax changed completely between versions:

AngularJS (2010-2016) — you will recognize it

  • .controller('Name', function($scope) {...}) — no @Component decorator
  • .directive for reusable components (conceptually similar to React components, but written as a factory function returning { template, scope, link })
  • ng-repeat, ng-click, ng-model as HTML attributes
  • $scope.$watch, $scope.$apply, $timeout as manual sync triggers
  • Dependency injection strings: function($http, $scope, myService) { ... }
  • If you see this, the codebase is 8-15 years old and likely being maintained, not actively developed

Angular 2-15 (2016-2023) — the mainstream enterprise codebase

  • @Component() decorator with template or templateUrl
  • Class component with lifecycle hooks (ngOnInit, ngOnDestroy, ngOnChanges)
  • NgModule files alongside feature modules (at least one per feature)
  • @Input() / @Output() for parent↔child communication
  • Services injected via constructor (constructor(private http: HttpClient))
  • RxJS Observables for async state — this.http.get(...).subscribe(...) with manual unsubscribe in ngOnDestroy
  • This is what most "Angular at work" repos look like in 2026

Modern Angular (2024+) — what new code looks like

  • standalone: true in the component decorator — no NgModule file
  • signal() for local state, computed() for derived values, effect() for side effects
  • @Input() / @Output() still exist but can also be input.required() (v17.2+) — a signals-based alternative
  • No manual ngOnDestroy cleanup for Signals-based state — effect() cleanup is automatic
  • Zoneless configuration (provideZonelessChangeDetection()) in the app config
  • This is what new Angular projects scaffold in 2026

The good news: if you can read Angular 2-15 code, you can read modern Angular code. The class structure, decorators, DI, and TypeScript are the same. The differences are additive (Signals) not replacive (no "components are functions now" shock like React's hooks migration).

7. Lifecycle translation: AngularJS ↔ Angular 2+ ↔ React

Two tables. First: how AngularJS's component lifecycle maps to Angular 2+. Then: how Angular 2+ maps to React hooks — so you can read code in any of the three paradigms without re-learning the mental model from scratch.

Table A — AngularJS → Angular 2+

AngularJS lifecycleAngular 2+ equivalentNotes
$onInit() — called when the controller's bindings are readyngOnInit() — called after Angular initializes the component's inputsBoth are "the data is ready, now set up." In modern Angular, ngOnInit is often replaced by effect() or a signal-backed constructor for data-fetching.
$onChanges(changes) — called when bindings change (AngularJS 1.5+)ngOnChanges(changes: SimpleChanges) — called when @Input values changeBoth give you the previous and current values. In modern Angular, you can also effect(() => this.input()) — a signals-based watch that doesn't require the lifecycle hook.
$doCheck() — called on each digest cycle, for custom change detectionngDoCheck() — called during every change detection runBoth are escape hatches for detecting changes Angular misses. Rarely needed in modern Angular with Signals.
$onDestroy() — called before the controller/scope is destroyedngOnDestroy() — called before Angular destroys the componentBoth clean up subscriptions, timers, and event listeners. In modern Angular, effect()'s return value IS the cleanup — no manual ngOnDestroy needed for signal subscriptions.
$postLink() — called after the controller's DOM is linkedngAfterViewInit() — called after the component's view and child views are initializedBoth are "the template is live." Used for third-party DOM library integration.

Table B — Angular 2+ → React hooks

Angular 2+ lifecycleReact hooks equivalentNotes
constructor() — DI injection, initial field valuesTop-level function body (outside useState), or useRef for DI-like singleton accessReact has no constructor. Initialize state via useState(initialValue). Services live outside React components (custom hooks or a DI container, if needed).
ngOnInit() — called once after inputs are bounduseEffect(() => {...}, []) with empty depsBoth run once after the first render/initialization. React's effect captures the first render's values; Angular's ngOnInit reads fresh @Input values (no stale closure risk).
ngOnChanges(changes) — called when @Input values changeuseEffect(() => {...}, [prop]) — re-run when prop changesReact's deps array replaces the imperative "which values changed" check. The effect runs after the render; ngOnChanges runs before Angular processes the component (during change detection). Different timing, same purpose.
ngAfterViewInit() — called after child views renderuseLayoutEffect(() => {...}, [])Both fire after the DOM is available but before the browser paints. Used for measuring DOM elements or integrating non-React DOM libraries.
ngOnDestroy() — cleanup before destructionuseEffect(() => { return () => cleanup; }, []) — the return value of the effectBoth clean up subscriptions, timers, event listeners. In Angular, you write a separate method; in React, the cleanup lives next to the setup inside the same effect.
ngDoCheck() — custom change detection on every run(No direct equivalent) — use useRef + manual comparisonAngular's "I need to know every time change detection runs" has no React parallel because React doesn't have an external change detection runner. If you need to know the previous value, use useRef to store it.
No direct equivalent — Angular has no "re-run the function" modeluseRef — mutable, persists across rendersAngular's class field is persistent (the instance lives until destruction). React's function-call-per-render model requires useRef for the "persistent field" use case.

The key insight for reading Angular code as a React developer: Angular's lifecycle methods are a biography ("at birth, at change, at destruction") — same as React's class components. React hooks replaced the biography with a synchronization model ("this effect syncs these values with this side effect"). Angular's Signals push in the same direction — effect() is closer to React's useEffect than ngOnInit + ngOnDestroy are. Modern Angular is converging on the same pattern React adopted in 2018 — synchronization, not biography. The difference: Angular kept the class and added Signals; React removed the class and added hooks.

8. Where Angular stands now (2026)

  • Current stable: Angular (v22 or v23 at time of reading — the version number increases by 2 per year since v17). 19.x LTS remains supported for enterprise holdouts.
  • Signals: The recommended state primitive for all new code. Zone.js still supported but the ecosystem is migrating toward zoneless defaults.
  • Standalone components: The default for new projects. NgModules in legacy code only — no new features added to the NgModule API since v17.
  • RxJS: Still the dominant async pipeline for HTTP and event streams, but Signal-based APIs are replacing Observable-heavy patterns incrementally (httpResource() in v20+ as a Signal-based HTTP client).
  • Enterprise niche: Angular holds the "rules-heavy, many-contributors, long-lived project" niche. Banks, insurance, government, and large internal tools. React leads in consumer-facing products, startups, and the meta-framework ecosystem (Next.js).
  • Reading vs writing: You will read more Angular code than you write (unless you join an Angular-first shop). The majority of Angular codebases in production are Angular 2-15 with NgModules and zone.js — migrated incrementally, if at all, to Signals.
  • The React contrast (2026): React adopted the compiler to solve the "deps array tax" problem. Angular adopted Signals to solve the "zone.js tax" problem. Both removed a manual bookkeeping burden. Both kept their component model (React's functions, Angular's classes). Neither is "ahead" — they solved different bottlenecks from different starting points.

What this doc covers

Q: Why did Angular rewrite from scratch in 2016?

A: AngularJS's digest cycle scaled poorly — thousands of watched expressions caused visible lag on every user interaction. The team decided that the architecture could not be fixed incrementally. The rewrite bet on TypeScript + class decorators + DI + zone.js as the future-proof foundation. The bet paid off (Angular 2+ has been stable for a decade) but the cost was a 0% migration path — AngularJS apps had to be rewritten entirely, which created the "Angular 1 → anything else" migration wave in 2016-2019.

Q: Did Angular copy React's unidirectional data flow?

A: Yes — Angular 2 abandoned AngularJS's two-way binding as the default. Instead: @Input() passes data down, @Output() emits events up. The template syntax (property binding [value] and event binding (click)) was directly inspired by React's JSX pattern, adapted to HTML attributes. Angular kept class fields as local state (no this.setState), and added zone.js as the change-detection broadcast engine — a design React never needed because setState was already the explicit trigger.

Q: Why did Angular adopt Signals when React declined?

A: Signals and React hooks solve different bottlenecks. React already had per-render snapshots captured in closures — Signals would break that model because they return the latest value unconditionally. React's bottleneck was the deps array tax (manual bookkeeping of effect dependencies), solved by the compiler. Angular's bottleneck was zone.js broadcast (checking everything on every async event), solved by Signals' fine-grained subscription graph. Same diagnosis (the framework reacts too broadly), different treatment (React: compiler narrows the developer's manual work; Angular: Signals narrow the framework's automatic work).

Q: Will I write Angular at work?

A: More likely read than write — Angular's enterprise niche means legacy codebases are large and slow to migrate. If you join a bank, insurance company, government contractor, or large internal-tools team, you may encounter Angular monorepos with NgModules and zone.js. Writing Angular from scratch is common in those same environments for new projects — the ecosystem is active (Signals, standalone, zoneless) but adoption lags behind React's in the startup/meta-framework world. The reading skills (class components, DI, @Input/@Output, lifecycle hooks) transfer across all eras. The writing skills (Signals, standalone, zoneless) are for new code only.
