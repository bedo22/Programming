Design Thinking (owner: design-thinking.html)

TermDefinitionWhere it appears
Wicked Problem A problem with no stopping rule, no true/false test, no ultimate solution — only better or worse. The problem definition is the design act (Rittel & Webber, 1973). Design Thinking §2, §5
Abductive Reasoning Inference to the best explanation. Observe behavior → hypothesize cause ("they struggle because the form is confusing") → test with a prototype. Design Thinking §5
Double-Loop Learning Single-loop: "fix the action." Double-loop: "question the governing variable." Reframing the problem = double-loop learning (Argyris & Schön, 1978). Design Thinking §5
Desirability / Feasibility / Viability The IDEO three-lens framework (1998): Do people want it? Can we build it? Does it make business sense? Design Thinking lives in the intersection. Design Thinking §0, §7
Design Sprint A 5-day timeboxed execution of Design Thinking: Understand → Sketch → Decide → Prototype → Test (Google Ventures, 2016). A rhythm hack, not the whole discipline. Design Thinking §6, §7
Double Diamond Discover (diverge) → Define (converge) → Develop (diverge) → Deliver (converge). Visual meta-model from Design Council UK (2005). Design Thinking §2, §7
Insight Statement A reframed problem: "Users don't forget because of memory — they forget because the trigger is hidden by their environment." Output of the Define stage. Design Thinking §9
Design Theater Performing the method (sticky notes, workshops) without real empathy. The output validates the team's bias, not the user's need. (Natasha Jen, 2017). Design Thinking §10

System Design (owner: system-design.html)

TermDefinitionWhere it appears
Bounded Context A semantic boundary within which a domain model applies. "Order" means different things in Sales (quote, negotiation) vs Fulfillment (pick, pack, ship). One bounded context = one service (DDD strategic design). System Design §7
CAP Theorem In a network partition, you must choose Consistency or Availability. You cannot have both. Every distributed data system makes this choice explicitly or implicitly. System Design §5
PACELC Refines CAP: even without partitions, there's a Latency/Consistency tradeoff (ELC). "If partitioned → A or C; Else → L or C" (Abadi, 2010). System Design §5
Conway's Law "Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations." Service boundaries must align with team boundaries. System Design §5, §9
Information Hiding Module boundaries should hide design decisions likely to change, not just data. The "reason for the data structure" is what's hidden (Parnas, 1972). System Design §5
Consistency Model The guarantee an API makes about reads/writes: Strong (linearizable), Sequential, Causal, Eventual, Read-your-writes, Monotonic reads. Every API contract implicitly or explicitly promises one. System Design §5, §6
Failure Domain A box drawn around a component: if this box loses power, what else stops? If deployed with a bug, what's the blast radius? If its DB corrupts, what data is lost? Good design minimizes blast radius. System Design §7, §10
Codebase Architecture The physical form of the boundaries: the folder tree. Feature folders vs. layered folders, colocation, why src/. If the code can't see the boundary, the boundary doesn't exist — and delivery modules should map to feature folders (vertical slices). System Design §7; Freelance Web Practice §Scoping
Idempotency Key A client-generated key carried on every mutating request. Server stores key → response mapping for 24h. Duplicate key returns original response. Enables safe retries. System Design §6, §7; API Design §8, §9
Circuit Breaker Stop calling a failing dependency, fail fast, retry after timeout. Prevents cascade failures. (Hystrix, Resilience4j, Go-breaker). System Design §6
Saga Distributed transaction via compensating actions: OrderPlaced → ReserveInventory → ChargePayment → if any fails, run compensations in reverse (ReleaseInventory, RefundPayment). System Design §6, §10
ADR (Architecture Decision Record) Lightweight markdown: Title, Status, Context, Decision, Consequences. Git-tracked. Captures why, not just what (Nygard, 2011). System Design §9
Modular Monolith Single deployable, strict internal module boundaries (enforced by linting, separate packages, explicit contracts). Most microservice benefits without distributed-system tax. System Design §6
Durable Objects Stateful serverless: compute + storage co-located at the edge. The "service" boundary becomes function + attached storage (Cloudflare, 2021+). System Design §8, §11

API Design (owner: api-design.html)

TermDefinitionWhere it appears
Interface Contract (Macro) Resources, operations, versioning, auth, rate limits, deprecation policy, error envelope, pagination strategy, idempotency semantics. What the consumer sees. API Design §0
Wire Contract (Micro) Serialization format, schema evolution rules, field-level nullability, enum extensibility, timestamp formats, cursor encoding, compression, transport (HTTP/1.1, HTTP/2, HTTP/3, gRPC, WebSocket). What the bytes say. API Design §0
Idempotency An operation that can be applied multiple times with the same effect as once. Every mutating endpoint must accept an Idempotency-Key header. API Design §8, §9; System Design §6
Problem Details (RFC 9457) Standard error envelope: type (URI), title, status, detail, instance, retry_after. Clients switch on type, not string matching. API Design §8, §9
Schema Evolution Rules Formal backward/forward compatibility: add optional fields, never remove required, never change type, enum extensions safe if consumers ignore unknown (Avro/Protobuf/JSON Schema). API Design §5
Cursor Pagination (Keyset) Pagination using a stable sort key (after: "cursor") instead of offset. O(1) vs O(n) for skipped rows. Default for growing collections. API Design §9, §10
Sunset Header Sunset: Sat, 01 Jan 2027 00:00:00 GMT + Link: ; rel="successor-version". Machine-readable deprecation notice. API Design §9
Contract Testing CI gate: implementation must match schema. Pact (consumer-driven), Dredd, Schemathesis. Prevents schema drift. API Design §10
API as Product Treat the contract as a product with a PM, metrics (adoption, p99 latency, breaking-change frequency), and lifecycle. Not a technical artifact (Kin Lane). API Design §10, §11

UI/UX & Web Design (owner: ui-ux-web-design.html)

TermDefinitionWhere it appears
Affordance Action possibility perceived by the user. Perceived affordance ≠ real affordance. Buttons look pressable; links look clickable. Signifiers communicate affordance (Gibson 1977, Norman 1988). UI/UX §5
Fitts's Law Time to acquire target = f(distance, size). Bigger, closer targets = faster. Corners/edges = infinite size (Mac menu bar, Windows Start). UI/UX §5
Hick's Law Decision time = log₂(n+1) choices. Reduce choices → faster decisions. Progressive disclosure, smart defaults, chunking. UI/UX §5
Gulf of Execution / Evaluation Gulf of execution: user intent → system action. Gulf of evaluation: system state → user understanding. Good UI narrows both (Norman, 1988). UI/UX §5
Design Tokens Platform-agnostic design decisions (color, space, type, motion, border, shadow) as structured data. Compile to CSS custom properties, iOS, Android, etc. (W3C DTCG). UI/UX §7; HTML & CSS §7, §8
State Visibility Matrix Every screen × every state (idle, loading, partial success, error, empty, offline). Maps directly to HTML states (aria-busy) and CSS states (:hover, [data-loading]). UI/UX §9; HTML & CSS §0, §4
Headless UI Primitives Behavior + accessibility + state management, zero styling opinions (Radix, Headless UI, ARIA Kit). Design systems provide visual layer only. UI/UX §7, §11
WCAG / POUR Perceivable, Operable, Understandable, Robust. Testable success criteria (A/AA/AAA). Accessibility as civil right, not feature. UI/UX §5, §8
Motion as Meaning Motion explains spatial relationships (where did this come from?) not "delight." FLIP animations, shared element transitions, View Transitions API. UI/UX §11
Dark Patterns Deceptive patterns (roach motel, hidden costs, forced continuity). Now regulated: EU DSA (2022), California Delete Act (2023), FTC negative option rule. UI/UX §11

HTML & CSS (owner: html-and-css.html)

Forced Colors
TermDefinitionWhere it appears
DOM (Document Object Model) The parsed HTML tree — elements, attributes, text nodes. What the browser exposes to JavaScript. document.querySelector('article') returns a DOM node. HTML & CSS §0
AOM (Accessibility Object Model) / Accessibility Tree A parallel tree derived from the DOM, filtered for semantics. HTML & CSS §0
Render Tree DOM + computed styles → boxes. Cascade, layout, paint, composite happen here. Three trees, one source: the HTML you write. HTML & CSS §0
Cascade Algorithm Origin (UA/user/author) → Importance (!important) → Specificity (ID/Class/Type) → Source Order → Scope Proximity → Layer Order. Deterministic, inspectable in DevTools "Computed" tab. HTML & CSS §1, §5
Specificity (a,b,c) = (ID count, Class/Attr/Pseudo-class count, Type/Pseudo-element count). #id .class:hover = (1,2,0). Higher wins. Not base-10: (0,11,0) < (1,0,0). HTML & CSS §5
Formatting Context BFC (Block Formatting Context): floats, margins, clears. Flex: main/cross axis, alignment, distribution. Grid: tracks, lines, areas, auto-placement. Each context has its own layout algorithm. HTML & CSS §1, §5
Intrinsic Sizing min-content = smallest without overflow. max-content = largest without wrapping. fit-content(limit) = clamp(min-content, limit, max-content). Grid minmax(), auto-fit, auto-fill use these. HTML & CSS §1, §5
Container Queries @container queries the parent's size, not viewport. A card in a sidebar vs main column needs different breakpoints. Component owns its responsive logic. HTML & CSS §1, §3, §9
Cascade Layers (@layer) Explicit origin ordering: @layer reset, base, components, utilities. Third-party CSS in its own layer. No more !important escalation. HTML & CSS §1, §3, §7
Logical Properties margin-inline-start, padding-inline-end, border-inline-start mirror automatically. Flex/Grid honor dir="rtl" on . No extra CSS for RTL. HTML & CSS §1, §9
OKLCH / OKLAB Perceptual color spaces. Lightness preserved across hue shifts; no "vibrating" brand colors in dark mode. Replaces HSL for token systems. HTML & CSS §1, §9
@media (forced-colors: active) disables backgrounds/shadows; system colors take over. border: 1px solid CanvasText ensures visibility. HTML & CSS §9

JavaScript: The Language (owner: javascript-the-language.html)

TermDefinitionWhere it appears
Prototype Chain Objects inherit directly from other objects — no class as separate entity. Object.create(proto) is the primitive. dog.__proto__ === Animal.prototype. JS Language §3
Lexical Closure A function "captures" its surrounding scope. function outer() { let x = 1; return function inner() { return x++; }; } — inner remembers x after outer returns. JS Language §4
Event Loop Single call stack, single thread. Macrotasks (setTimeout) run after current task + all microtasks + render. Microtasks (Promise.then, await) run before next macrotask. JS Language §5
Host Environment JS is a guest. The spec (ECMAScript) defines core; the host provides everything else: window/document/fetch (browser), global/fs/process (Node), Deno, Bun, fetch/KV/Durable Objects (Cloudflare Workers). JS Language §6
TC39 Process Stage 0 (strawperson) → Stage 1 (proposal) → Stage 2 (draft) → Stage 3 (candidate) → Stage 4 (finished). Two independent implementations required for Stage 4. Features take years — the web cannot break. JS Language §7
JIT Compilation V8 compiles hot paths to machine code. "JS is slow" is 20 years out of date. But: JIT warm-up exists, deoptimization happens, eval/with disable optimization. JS Language §8
WebAssembly (WASM) Compile target for C++/Rust/Go in browser. Partner, not competitor. WASM cannot directly touch DOM (anyref in progress). JS remains mandatory DOM/host glue. JS Language §9

Frontend Camps Survey (owner: frontend-camps-survey.html)

TermDefinitionWhere it appears
Camp A: CMS / Classic Server Server owns document (PHP, Rails, Django). JS optional sugar. Admin UIs often full SPAs. Camps §1
Camp B: HTML-First / Islands Document is product, JS is precision tool. Astro: zero JS default; opt into islands (React, Preact, Svelte, Vue, Solid) only where needed. HTMX/Alpine: server-driven UI. Camps §2
Camp C: Client SPA Browser downloads app shell; client-side routing; server mostly API. Vite bundler. State libraries (Redux, Zustand, Pinia). CRA sunset Feb 2025. Camps §3
Camp D: Meta-Framework Framework around UI library: routing, data loading, rendering strategy, bundling, deployment. Next.js, Remix, React Router FW, Expo, Nuxt, SvelteKit, Angular, SolidStart, Qwik City. Camps §4
Camp E: Signals World (non-React) Angular (signals+zone.js), Vue 3 (ref/reactive), Svelte 5 (runes), Solid (createSignal), Preact (@preact/signals). Fine-grained updates; component function often doesn't re-run top-to-bottom. Camps §5
Camp F: WASM / Non-JS UI Rust/C++/C#/Zig in browser via WASM. Heavy compute (codecs, CAD, games, crypto). JS usually owns DOM glue. Yew/Leptos (Rust), Blazor (C#). Camps §6
Re-render Box Model React's mental model: component function = pure function of props+state → UI. Re-run on state change → diff → commit. Closures capture render-scoped values. Does not apply to signals frameworks or server components. Camps §10

Developer Loop / How Developers Think (owner: how-developers-think-frontend.html)

TermDefinitionWhere it appears
Model / View / Flow (Three Threads) The mental loop: Thread 1 = Data structures & state shape. Thread 2 = Structure + layout (HTML). Thread 3 = Events, data movement, logic. Intertwined, not sequential. Dev Loop §1
Skeleton → Deepen → Polish Round 0: Clarify. Round 1: Simplest structures, semantic HTML, stub handlers. Round 2: Upgrade where pain appears, full styling, real logic. Round 3: Perf, edge cases, a11y. Dev Loop §1, §3–5
Data Shape First Sketch the nouns, fields, collection types, operations, component state ownership before writing HTML. The shape determines the UI structure; changing it late is expensive. Dev Loop §2, §13
Derived State Values computed from other state at render time (filtered list, active count). Never store derived values in state — it's the most common frontend bug. Dev Loop §13
Spiral Development / IID Iterative & Incremental Development (Larman & Basili, 2003) — older than Waterfall. Boehm named it "Spiral" (1986): Plan → Risk Analysis → Engineering → Evaluation, each cycle deeper. Dev Loop §11
Wireframe / Mockup / Prototype / MVP Three axes: Fidelity (how real), Disposability (throw away?), Behavior (static vs clickable). Wireframe = high disposability + low fidelity + no behavior. MVP = low disposability + production fidelity + fully working. Dev Loop §12

Problem-Solving (owner: problem-solving.html)

TermDefinitionWhere it appears
Well-Defined Problem A problem with clear input, clear output, and objective success criteria. Gets an algorithm (a fixed, finite sequence of steps). Examples: HackerRank challenges, math proofs. Problem-Solving §1
Wicked Problem A problem with evolving input, subjective output, and no true stopping rule. Gets a rhythm (an iterative loop). Examples: UI features, product decisions. Contrast with well-defined. Problem-Solving §1; Design Thinking §2
Pólya's Four Phases The universal problem-solving rhythm (1945): Understand → Plan → Execute → Look back. A rhythm, not a waterfall — you cycle, returning to earlier phases when later ones reveal gaps. Problem-Solving §2
Heuristic A rule of thumb that usually helps but doesn't guarantee a solution. Contrast with algorithm, which guarantees a result. Pólya's heuristics: analogy, specialization, working backwards, decomposition, variation, auxiliary elements, generalization. Problem-Solving §4
Computational Thinking The lens for structuring problems computationally (Papert 1980, Wing 2006). Four pillars: decomposition, pattern recognition, abstraction, algorithm design. These are the moves within Pólya's phases. Problem-Solving §3
Metacognition Thinking about your own thinking while problem-solving — monitoring progress, deciding when to abandon an approach, re-anchoring on the goal. Schoenfeld's (1985) key addition to Pólya: strategies alone are weak without metacognitive control. Problem-Solving §5
Stepwise Refinement Top-down decomposition for programming (Wirth, 1971): start with the whole problem, express the solution using "black boxes," refine each downward until every box is a concrete operation. The problem-solving equivalent of "sketch the data shape first." Problem-Solving §6
Algorithm Design Paradigm A fundamental approach to designing algorithms. Categories: brute force (try all), greedy (local optimum), divide & conquer (independent sub-problems), dynamic programming (overlapping sub-problems), backtracking (try & prune), hash table (O(1) lookup). Problem-Solving §7
Pattern Filing The Phase 4 (Look back) act of categorizing a solved problem by its pattern and the signal that identified it. Builds pattern recognition over time. "Count occurrences → hash map. Signal: 'how many times each X appears.'" Problem-Solving §10
Rubber Duck Debugging Explaining code line by line to an inanimate object (Hunt & Thomas, The Pragmatic Programmer, 1999). Forces articulation of assumptions; the bug is usually in an unstated assumption. Phase 1 (Understand) applied to your own code. Problem-Solving §9
Hypothesis-Driven Debugging Applying the scientific method to debugging: observe → hypothesize → predict → test → conclude. Never change code without a confirmed hypothesis; guessing is not debugging. Problem-Solving §9
Fluency vs Storage Strength (Problem-Solving) Reading a solution builds fluency (in-the-moment "I get it") but not storage strength (long-term retrieval). Storage strength comes from effortful retrieval: attempt first, solve then compare, re-solve from memory, interleave problem types. Problem-Solving §11

Algorithms & Data Structures (owner: algorithms-and-data-structures.html)

TermDefinitionWhere it appears
Hash Map A key→value store with O(1) average lookup. The key is hashed to a bucket; collisions are handled by chaining or open addressing, and the load factor (keys ÷ buckets) drives resizing. Use Map/Set, never a plain object, for real key semantics. Owns the count/seen/complement patterns. Algorithms §2
Two Pointers Left/right pointers moving one direction each over a sorted (or palindromic) input. O(n) because each element is visited at most twice. Pair sums, dedup, in-place reversal, three-sum. Algorithms §2
Sliding Window Expand right, shrink left while a constraint breaks, record the best. Amortized O(n). The pattern behind "longest substring with no repeats", "max sum of k-length window", "minimum window". Algorithms §2
Monotonic Stack A stack kept ordered by popping while the new element violates the order. Yields "next greater element" in O(n) — the superpower pattern for a whole family of stack problems. Algorithms §3
Trie A tree of shared prefixes; each node is a character, words share their prefixes structurally. O(length) lookups for prefix operations — autocomplete, word break, prefix counts. Structural sharing beats storing every prefix. Algorithms §4
Union-Find A near-O(1) connectivity data structure: find walks to a root, union links roots (with path compression and union by rank). Beats re-running BFS when edges arrive one by one — connected components, cycle detection, Kruskal's MST. Algorithms §5
Topological Sort Ordering a DAG's nodes so every edge points forward — Kahn's algorithm or DFS post-order; doubles as cycle detection. The "prerequisites / dependencies / ordering" pattern. Algorithms §5
Binary Search Halving a search space via a monotonic predicate, not just sorted arrays: "first index where isGood(i) is true" over half-open range [lo, hi). The template that never off-by-ones; also answers "minimize the max X" monotonic problems. Algorithms §6
Dynamic Programming Cached enumeration of overlapping subproblems: define state, write the transition, set base cases, then memoize (or tabulate). The "minimize cost / maximize value / choose subsets" pattern. Memoized recursion first is the lazy correct path. Algorithms §7
Exchange Argument The proof a greedy choice is safe: "if an optimal solution differs from mine, I can swap my choice in without making it worse." Without that argument, greedy is a gamble and DP is the safe answer. Algorithms §8

Computer Science & Software Engineering

TermDefinitionOwning section
Computer Science The science of computation — what can be computed, how efficiently, and what the fundamental limits are. A science: discovers what is possible, proves theorems. Founded by Turing (1936). CS & SE §2
Software Engineering The engineering discipline of building reliable, maintainable software systems at scale. An engineering discipline: builds under constraints, makes trade-offs, judged by outcomes. Named at the 1968 NATO conference. CS & SE §3
Quality Attribute A parameter along which you evaluate a solution — also called "non-functional requirement" or "the ilities." ISO 25010 defines 8: functional suitability, performance efficiency, compatibility, usability, reliability, security, maintainability, portability. CS & SE §4
Time Complexity How an algorithm's runtime grows as the input size grows. Measured in Big O notation. O(n) = linear (double the input, double the time). O(n²) = quadratic (double the input, quadruple the time). CS & SE §5
Space Complexity How an algorithm's memory usage grows as the input size grows. Measured in Big O notation. An in-place sort uses O(1) extra space; a hash map uses O(n) space. CS & SE §5
Big O Notation The mathematical notation for classifying algorithm efficiency. Describes the upper bound of growth rate as input size approaches infinity. Coined by Bachmann (1894) and Landau in math; adopted for CS by Knuth. Standard classes: O(1), O(log n), O(n), O(n log n), O(n²), O(2ⁿ), O(n!). CS & SE §5
Trade-off A situational decision where improving one parameter diminishes another. In software: time vs space, readability vs performance, simplicity vs flexibility. The engineering skill is making trade-offs explicit — naming what you're sacrificing and why. CS & SE §6
Pareto Front The set of solutions where you can't improve one parameter without degrading another. A solution is "Pareto-optimal" if no other solution is better on all parameters. Most real-world decisions involve choosing which Pareto-optimal solution fits your context. CS & SE §6
Premature Optimization Optimizing before you know it matters. Knuth (1974): "Premature optimization is the root of all evil." The fix: measure first, optimize only the critical path, leave the rest simple. CS & SE §7, §9b
KISS — Keep It Simple, Stupid Origin: Kelly Johnson, Lockheed Skunk Works (1960s). Principle: simplicity should be a key goal; unnecessary complexity should be avoided. In practice: the simplest solution is usually the most maintainable, testable, and fastest to ship. CS & SE §8
YAGNI — You Aren't Gonna Need It Origin: Kent Beck, Extreme Programming (1999). Principle: "Always implement things when you actually need them, never when you just foresee that you need them." Don't build flexibility you don't need yet. CS & SE §8
DRY — Don't Repeat Yourself Origin: Hunt & Thomas, The Pragmatic Programmer (1999). Principle: "Every piece of knowledge must have a single, unambiguous, authoritative representation." About knowledge duplication, not code duplication — two similar-looking functions with different business rules should NOT be merged. CS & SE §8
SOLID Five object-oriented design principles: Single Responsibility, Open-Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. Origin: Robert C. Martin (2000); acronym coined by Michael Feathers (~2004). Make code more understandable, flexible, and maintainable. CS & SE §8
ISO/IEC 25010 The international standard for software quality evaluation (2011). Superseded ISO 9126 (1991). Defines 8 quality characteristics. The formal framework for "what makes a solution good." CS & SE §4
Separation of Concerns Origin: Dijkstra (1974). Divide a program into sections that each address a separate concern. In frontend: HTML (structure), CSS (presentation), JS (behavior) — the same separation as The Rhythm's three threads (Model, View, Flow). CS & SE §8

Software Development Process

TermDefinitionOwning section
SDLC — Software Development Life CycleThe sequence of phases a software system goes through from birth to retirement: Requirements → Design → Implementation → Testing → Deployment → Maintenance. Describes what happens, not how you navigate it.SDP §2
MethodologyA blueprint for navigating the SDLC — tells you the order, the cadence, and the roles. Waterfall does the phases sequentially; Agile does them iteratively; Spiral does them in risk-driven cycles.SDP §1
AgileAn umbrella philosophy (not a single framework) expressed in the Agile Manifesto (2001). Under the umbrella: Scrum, Kanban, XP, Lean, DevOps. 4 values, 12 principles.SDP §1, §3
Agile ManifestoThe 2001 document by 17 software developers at Snowbird, Utah. 4 values: individuals over processes, working software over documentation, customer collaboration over contracts, responding to change over plans. 12 principles.SDP §3
WaterfallThe sequential methodology: finish all Requirements, then all Design, then all Implementation, etc. Royce (1970) actually warned against single-pass — people read the diagram, skipped the warning.SDP §1b
ScrumThe most widely adopted Agile framework. 3 roles (Product Owner, Developers, Scrum Master), 5 events (Sprint, Sprint Planning, Daily Scrum, Sprint Review, Sprint Retrospective), 3 artifacts (Product Backlog, Sprint Backlog, Increment). Based on empirical process control theory.SDP §4
SprintA fixed-length timebox (usually 2 weeks) during which a usable increment is created. The container for all other Scrum events.SDP §4
KanbanA flow-based Agile method from the Toyota Production System. 6 practices: visualize workflow, limit WIP, manage flow, make policies explicit, implement feedback loops, improve collaboratively. Pull-based, not timeboxed.SDP §5
WIP — Work in ProgressThe number of items currently being worked on. Kanban limits WIP per column to prevent context switching and expose bottlenecks. The key constraint in Kanban (vs Scrum's timebox).SDP §5
XP — Extreme ProgrammingKent Beck (1999). The engineering practices that make Agile work: TDD, pair programming, continuous integration, refactoring, simple design. "Make it work, make it right, make it fast."SDP §6
DevOpsThe convergence of Development and Operations (2009). Automates Testing → Deployment → Maintenance via CI/CD, infrastructure as code, and monitoring. Makes very frequent, low-risk deployments possible.SDP §6
CI/CD — Continuous Integration / Continuous DeploymentCI: every code change is integrated and tested automatically. CD: if CI passes, the code deploys to production automatically. The DevOps pipeline.SDP §6
Empirical Process ControlThe theory behind Scrum: when you can't define the process (software is unpredictable), make it visible, inspect frequently, and adapt. "Inspect and adapt." vs defined process (manufacturing — steps are known, repeat them).SDP §1e
Agent Development Lifecycle (ADLC)A new lifecycle (2024–present) for building AI agents — autonomous systems that pursue goals, use tools, take actions. 5 phases: Agent Design → Build → Evaluate → Deploy with guardrails → Monitor for drift. The product IS an AI agent, not traditional software.SDP §9d
AI-augmented SDLCThe traditional SDLC with AI assisting each phase (Copilot writes code, AI generates tests). Not a new lifecycle — the same SDLC with the human shifting from writer to evaluator.SDP §9d

Payments & Commerce (owner: payments-and-commerce.html)

TermDefinitionWhere it appears
Authorization / Capture / Settlement The three legs of a card payment: auth = hold on the card, capture = the money is requested, settlement = it lands in your account days later. Every payment is a promise until settlement. Payments & Commerce §Definition, §How payments work
PSP (Payment Service Provider) Stripe, Adyen, PayPal, Square — the API that compresses the institution stack (acquirer, gateway, network certifications) into one integration. The fee is the price of not building a bank. Payments & Commerce §Definition
Idempotency Key Money edition: a per-logical-operation key on charges — same key = same charge, forever. The guard against double charges on retry. Payments & Commerce §Integration patterns; Backend Engineering §5
Webhook as Source of Truth Payment outcomes (paid, failed, disputed) arrive as provider webhooks; the synchronous API response is only optimism. Verify signatures, dedupe by event id, record transitions. Payments & Commerce §Integration patterns
Chargeback (Dispute) The customer's bank pulls money back plus a fee while evidence is reviewed. The default way money returns in card systems — design for the reversal. Payments & Commerce §Refunds & disputes, §Fraud
PCI DSS The card-industry security standard. Scope is a design choice: hosted checkout = tiny scope; storing PANs = full audit program. Tokenization everywhere. Payments & Commerce §PCI DSS; Security & Threat Modeling
3D Secure (3DS) Customer authenticates with their issuing bank during checkout (challenge or silent). The liability shift is the point: with 3DS the bank owns fraud chargebacks, without it the merchant does. PSD2/SCA mandates it in the EU. Payments & Commerce §Fraud, §Integration patterns
Merchant of Record (MoR) Paddle, Lemon Squeezy, FastSpring — the legal seller of the product: owns tax calculation/remittance, refunds, chargebacks, PCI. Higher fee (5%+ vs. ~2.9%) for the whole compliance surface. Payments & Commerce §Ecosystem

JOIN The pairing rule that recombines relational tables: INNER keeps matches only, LEFT keeps all left rows with NULLs for the unmatched. The N+1 fix, and the reason foreign keys need indexes. SQL & PostgreSQL §JOINs; Backend Engineering §1e (N+1); Data Modeling & Databases §Indexing
