Programming primitives, the four theories of computation, how data becomes values becomes variables becomes state, and why "state" is the same word across Turing machines and React hooks. 1. When did "programming" appear?

Two words people use loosely that we have to separate first: algorithm and program.

  • An algorithm is an abstract procedure — a finite, step-by-step recipe for solving a problem (e.g. "to compute GCD of two numbers, repeatedly subtract the smaller from the larger until they equal"). It can be written on paper, described in words, or even executed by a human with paper, with no machine in sight. Algorithms have existed as long as mathematics has: the Euclidean algorithm for GCD is from ~300 BCE.
  • A program is a concrete implementation of one or more algorithms in a specific language, runnable on a specific machine. The Euclidean algorithm is ~2300 years old; the oldest computer program implementing it ran decades ago. Same algorithm, different programs, millennia apart.

The word "algorithm" itself is a 1,200-year-old loan from Al-Khwarizmi (Muḥammad ibn Mūsā al-Khwārizmī, c. 780–850 CE, the Persian polymath at the House of Wisdom in Baghdad). His name was Latinized in medieval Europe as Algoritmi, and "algorithm" literally means "of Khwarizmi." The same scholar's book al-Jabr gave us the word "algebra." So the word for "a step-by-step procedure" is older than the computer by about a millennium — the concept existed long before any machine could run it.

The idea of giving a machine a sequence of instructions to carry out is much newer than algorithms themselves:

  • 1843 — Ada Lovelace wrote the first algorithm intended for a machine (Babbage's Analytical Engine, a mechanical, theoretical machine never completed in her lifetime). She wrote a plan for computing Bernoulli numbers. Crucially: she wrote an algorithm for a machine that did not yet exist — a program with no computer to run on. She is called the first programmer because she was the first to think through what a machine — once built — would have to be told step by step. Programming as an idea tied to a machine starts here, even though no machine ran it.
  • 1936 — Alan Turing published "On Computable Numbers," defining the Turing machine — the mathematical model of "anything that can compute." This proved which problems are solvable by any machine at all. It is the theory under programming, not programming itself.
  • 1941 — Konrad Zuse's Z3 was the first working programmable computer (electromechanical, in Germany) — the first time an algorithm became a program that actually ran. Limited, but real.
  • 1945-46 — ENIAC in the US was the first general-purpose electronic programmable computer. It was programmed by women rewiring cables between panels — "soft" instructions didn't exist yet; the program was a physical configuration. The first programmers in the modern sense were the "ENIAC girls."
  • 1957 — Fortran was the first widely-used high-level programming language. For the first time you wrote X = Y + Z on punch cards and a compiler turned it into machine code. This is when "programming" starts to mean what you do today: typing text that becomes instructions.

So: the algorithm as a concept is older than mathematics itself; the word "algorithm" is ~1,200 years old (from Al-Khwarizmi); the idea of programming a machine is from the 1840s (Lovelace); the practice of running programs on real machines from the 1940s (Zuse, then ENIAC); and what you'd recognize as programming today from the 1950s (Fortran). The 70 years since Fortran are variations on one theme: tell a machine how to transform inputs into outputs.

2. The four theories underneath — what makes programming possible at all

The last section told you when things happened. This section tells you what the ideas are that make programming work. Four theories, all worked out between 1936 and 1948 — and they are not historical footnotes. The code you write today directly radiates from them. If you skip this section, "variable," "function," "type," and "state" will feel like arbitrary labels from a language spec. They aren't. Every strange term in the subsections below will be defined on first use — but be patient: the first two subsections are the most abstract, and they pay off in the last two, which connect directly to the hardware and to JS.

2.1 The Turing machine (Alan Turing, 1936) — what is "computable"?

The problem Turing was solving. In 1928, the German mathematician David Hilbert asked the Entscheidungsproblem (German for "decision problem"): given a fixed set of axioms (like the rules of arithmetic) and a mathematical statement (like "there are infinitely many prime numbers"), is there a general, mechanical procedure that can decide, for any statement, whether it is provable or not? In 1936, Alan Turing and Alonzo Church working independently proved the answer is no — no such general procedure can exist. But to prove that, Turing first had to define what "general procedure" meant in a mathematically precise way. He did it by inventing a machine that is so simple you can understand every part of it in a few minutes — and 90 years later, it remains the foundation of everything we call "computing."

The machine. Imagine an infinitely long paper tape divided into squares (cells). Each square has a symbol (say, 0, 1, or blank). A read/write head sits over one square at a time. There is a control box that is in exactly one state at any moment, from a finite set of possible states (say: "start," "seek 1," "found 1," "halt"). The machine follows a table of rules. Each rule says:

IF the control box is in state X AND the square under the head contains symbol Y, THEN: write symbol Z over the current square, move the head left (L) or right (R) by one square, and switch the control box to state W.

A state is the current configuration of the control box (one value from a finite set). A transition is a rule that defines what happens in one step. The tape is the unlimited memory. Halting is when no rule applies — either the machine stops, or it runs forever. That is the entire machine — tape, head, state, rules — and Turing proved that this absurdly simple thing can compute anything any real computer can compute, given enough tape and enough time. Every modern CPU, every programming language, every AI model is the Turing machine with more moving parts and infinite tape replaced by finite RAM.

What Turing proved — the Halting Problem and the boundary of the possible. The most important single result in computing: there exists no Turing machine that can take the description of any other Turing machine plus its input, and decide whether that machine will halt or run forever. This is not a "we haven't figured it out yet" — it is a proven logical impossibility, like asking someone to draw a square circle. The practical consequence: every compiler, every linter, every type checker, every static analysis tool has false negatives (it misses some real bugs) and false positives (it flags correct code as wrong), and this is mathematically unavoidable. No improvement in AI, no new type system, no magic tool can ever cross this boundary. It's the bedrock limit of computation.

Three things every programmer inherits from Turing:

  • "Turing-complete" is the minimum bar. A language is Turing-complete if it can simulate any Turing machine. C is. JS is. Python is. Lisp is. Haskell is. Excel formulas are. Minecraft redstone is. Any Turing-complete language can compute anything any other Turing-complete language can compute, given infinite time and memory. This means: the difference between OOP, FP, and procedural is about convenience, readability, and safety — NOT about what the language can do. Everything React hooks do could be done in class components with more ceremony. The paradigm shift is an ergonomic improvement, not a capability upgrade.
  • The re-render loop is a Turing cycle. React calls your component → component reads state and returns JSX → event handler calls setState → React re-calls the component. This is the Turing cycle: read the current state, execute the transition (your function), write new state, repeat. Every useReducer you write is a Turing machine minus the tape — a pure finite state machine where the reducer is the transition table.
  • "State" is the Turing word. When we say "the button is in the loading state," we are using the exact word Turing chose for his control-box register — a finite set of configurations, one active at a time, with defined transitions between them. The React mental model (UI = f(state)) is Turing's architecture with a rendering system attached.

2.2 The lambda calculus (Alonzo Church, 1936) — the other way to compute

The same problem, a different direction. Church was working on the same Entscheidungsproblem at the same time as Turing, but his background was logic and mathematics, not physics and mechanics. He invented the lambda calculus — a formal system where everything is a function, there are no machines, no tapes, no memory, no state. Only pure functions that take arguments and return results. Zero side effects, zero mutation, zero "write to memory." Just transformation.

What it looks like. The lambda calculus has exactly three things:

  • A variable — a name like x or y.
  • An abstraction — a function definition: λx.<body> means "a function that takes argument x and produces body." λx.x is "a function that takes x and returns x" (the identity function).
  • An application — calling a function with an argument: (λx.x) 5 means "call the identity function with argument 5" → returns 5.

That is the entire system. From these three things (variables, function definitions, function calls), Church built the entire machinery of arithmetic: numbers (the Church numeral for 0 is λf.λx.x — "a function that takes f and x and applies f zero times to x"), addition, multiplication, conditionals (true is λx.λy.x, false is λx.λy.y), loops (recursion), and data structures (pairs are λx.λy.λf.f x y). All from nothing but functions. You cannot mutate any variable; you can only create a new value. This is the mathematical origin of "pure function," "immutability," and "no side effects" in the FP tradition.

Key terms, each defined:

  • Pure function: a function that always returns the same output for the same inputs and has no side effects (does not modify anything outside itself). add(2, 3) always returns 5, no matter when or how many times you call it. The lambda calculus only has pure functions because there's no memory to mutate — every call returns a fresh result.
  • First-class function: a function can be treated like any other value — assigned to a variable, passed as an argument, returned as a result. In lambda calculus, functions ARE the only values, so "first-class" is not a feature — it's the whole system.
  • Higher-order function: a function that takes another function as input or returns one as output. λf.λx.f(f(x)) is "a function that takes callback f and returns a function that applies f twice." array.map(fn) is a higher-order function: it takes fn as input and applies it to every element.
  • Lexical closure: when a function "captures" variables from the scope where it was defined. In lambda calculus, a function body can reference variables that were bound in its enclosing abstraction — λx.λy.x creates a function that "remembers" x even after the outer function has returned. JS closures are this exact mechanism.
  • Currying: converting a function that takes multiple arguments into a chain of functions each taking one argument. add(x, y) becomes add(x)(y). The example λx.λy.x is the curried version of "take x and y, return x" — it takes x, returns a function that takes y, and returns x.

The Church-Turing thesis — the equivalence that underlies all of computing. When Turing published "On Computable Numbers" in 1936, Church was already known for the lambda calculus. Church recognized that Turing's machine model and his own function model were aiming at the same target. He invited Turing to Princeton University for a Ph.D. under his supervision — Turing arrived in 1936 and they worked together to prove the Church-Turing thesis:

The Church-Turing thesis: Every function that is "intuitively calculable" by any finite, mechanical procedure can be computed by a Turing machine, AND equivalently by a lambda-calculus expression. Two models built on completely different intuitions — one mechanical (tape, states, mutation), one mathematical (functions, purity, no state) — turn out to compute exactly the same class of functions.

This is called a "thesis" rather than a "theorem" because you cannot mathematically prove something about "intuitively calculable" — that would require a mathematical definition of intuition, which is a philosophical problem, not a mathematical one. But the thesis has been tested for 80+ years: every new model of computation proposed (recursive functions, cellular automata, quantum computers, DNA computing, typed lambda calculi) has turned out to compute exactly the same class. If we ever meet aliens, the working assumption is that their computation is equivalent to ours.

The relation between Turing and Church — a summary for the reader. The Turing machine is the computer-as-mechanic: there is a physical-looking machine with moving parts, it holds state over time, it mutates memory. The lambda calculus is computer-as-mathematician: pure transformations, no time, no memory, no mutation, just functions producing values from values. The thesis says both are the same. This is NOT obvious: the Turing machine is procedural with mutation; the lambda calculus is functional without mutation. They LOOK like opposites. The thesis says they compute the same things. This is why React could move from classes (Turing-machine paradigm: state inside objects, mutation via methods) to hooks (lambda-calculus paradigm: pure functions, immutable state, composition — see the later sections). Both are mathematically equivalent; moving between them is choosing a different organizing metaphor, not adding new power.

Why this matters for the code you write:

  • JavaScript functions are lambda calculus descendants. Lisp (1958), the second-oldest language still in wide use, was built explicitly on the lambda calculus. JavaScript's first-class functions, lexical closures (a closure "captures" its surrounding variables just like lambda calculus binds them), higher-order functions (map / filter / reduce), and the ability to pass functions as arguments are all inheritance from the Lisp/lambda-calculus tradition. Brendan Eich, who created JS in 10 days in 1995, has said he wanted a Lisp-like language but had to use Java-like syntax to pass management approval. Under the { } braces is a lambda-calculus heart beating in a C-shaped body.
  • The lambda calculus gives you currying and partial application. That pattern const add = x => y => x + y; add(2)(3) is Church's currying directly. The lesson on currying in this workspace (lesson 0007) is actually teaching 1936 mathematics that became practical through Lisp.
  • FP is not a fashion. When people dismiss FP as "academic" or "impractical," they are dismissing a model of computation that Church proved equivalent to the one behind every real machine. The difference is organization, not capacity. React adopting hooks was not "trendy" — it was choosing one of the two equivalent models over the other, for concrete engineering reasons (the three problems from the main doc's intro: reuse, lifecycles, and bind).

2.3 The Halting Problem (Turing, 1936) — the boundary of what machines can know

The question. Can you write a program that reads any other program + its input, and correctly answers "does this program halt or run forever?"

The proof (by contradiction). Suppose such a program H exists. H takes two inputs: a program P and an input x. It outputs true if P(x) halts, false if it loops forever.

Now build a new program D ("the diagonalizer"):

// D takes a program P as input
function D(P) {
  // Run H on P with P itself as input
  if (H(P, P) === true) {
    // H says P(P) halts — so we loop forever
    while (true) { }  // infinite loop
  } else {
    // H says P(P) loops — so we halt immediately
    return "done";
  }
}

What happens when we run D(D) — feeding D to itself?

  • If H(D, D) says "halts" → D(D) enters the infinite loop → does NOT halt
  • If H(D, D) says "loops" → D(D) returns immediately → halts

Both cases contradict H's prediction. Therefore H cannot exist. No program can solve the halting problem for all programs.

What this means for you. There is no tool, no static analyzer, no AI, no "sufficiently smart compiler" that can catch all infinite loops, all deadlocks, all "will this function terminate?" questions. The boundary is mathematically proven, not engineering-limited. Every linter, type checker, and IDE warning is a sound but incomplete approximation — it catches some bugs, misses others, and sometimes flags correct code. You will always need human judgment at the edge.

2.4 The von Neumann architecture (John von Neumann, 1945) — the hardware that made computation real

From mathematical model to physical machine. The Turing machine is an abstraction with an infinite tape that doesn't exist in the physical world. To actually build a working computer, someone had to design the engineering layout. That design was described in 1945 in "First Draft of a Report on the EDVAC," written by John von Neumann, a mathematician and physicist working as a consultant on the EDVAC project at the University of Pennsylvania. The architecture it described is so universal that we barely notice it as an invention — but every CPU in every laptop, phone, server, and embedded device today is still a "von Neumann machine."

Three core ideas, each with its own name and consequence:

  1. Stored program (the program is data). Before 1945, "the program" was how the machine was physically wired. ENIAC — the giant electronic computer completed in 1945 — had to be rewired for every new program, a process that took days. Von Neumann's insight: represent the program's instructions as data in the same memory where the data lives. The CPU reads an instruction from memory, decodes it (what does this bit pattern mean?), executes it (load, add, jump, compare), and moves to the next instruction. The instruction is a number — the bit pattern for "ADD" is just another number, no different from the bit pattern for 42. This is why today you can eval("let x = 5") in JS — the engine reads a string (data) and compiles it into instructions (code). It's why functions can be passed as values (a function is data that the engine can execute). The boundary between "code" and "data" is a choice, not a physical reality.
  2. Separate CPU and memory, connected by a bus. The CPU (Central Processing Unit — the "brain") does the actual work: arithmetic, comparisons, logic. Memory (RAM — Random Access Memory) stores the instructions and data. A "bus" — just wires — connects them. The CPU places a memory address on the address bus, reads or writes data on the data bus. Each cycle: fetch an instruction from memory at the current "program counter" address, execute it, increment the program counter. A variable is a memory address with a human-readable name attached. Assignment is a bus write: the CPU places the address on the bus, places the value on the data bus, and the memory chip at that address stores the new bits. That is literally what x = 5 means at the hardware level.
  3. Sequential execution (one instruction at a time). The CPU executes instructions one at a time, top to bottom, with "jumps" for loops (while), branches (if), and function calls (call / ret). This is the origin of the "procedural" or "imperative" paradigm — "do this, then do that, then if X do Y" — because that is literally how the CPU works. Every sequential imperative language (C, Pascal, Fortran, and the shape of JS inside function bodies despite its FP heart) radiates from this.

A footnote on credit. Eckert and Mauchly, who actually built ENIAC, argued after von Neumann's draft that the stored-program idea was theirs before von Neumann wrote about it. The term "von Neumann architecture" stuck because his draft was the first written description that circulated and became standard. Some people use "stored-program architecture" to avoid taking sides on the credit dispute. The idea itself is what matters — whichever direction it came from, it is the design of every modern computer.

Connection to your C/C++ background and to the rest of this doc:

  • Your C/C++ background: memory is real. In C, a variable IS a memory address. int count = 5 in C allocates 4 bytes at a specific address — the compiler knows the address at compile time (for globals / stack locals) or at link time (for heap allocations). The & (address-of) operator gives you the actual address. In JS, a variable is a name binding managed by the engine — you cannot take its address; the engine moves values around in memory freely. But underneath both, the von Neumann machine hums: eventually the value ends up in a RAM chip at some address connected by a bus to a CPU.
  • Why OOP felt natural in 2013. this.state.count++ in a class component means: "go to the memory address assigned to this instance, find the state field offset, find the count field offset at that address, read the integer at that address, increment it by 1, write the new integer back." The class instance IS a block of memory; its methods are subroutines that know the memory layout of their object. This maps directly to how the von Neumann machine works: a chunk of memory with operations that mutate it.
  • Why functional code feels inefficient (and why the React Compiler existed). When React moved from classes (mutate the instance field) to hooks (call setCount(count + 1) which returns a new value and asks the component to re-run from scratch), it moved away from the von Neumann mutation model and toward the lambda-calculus purity model. But the hardware underneath is STILL von Neumann: the CPU is sequential, mutable, address-based. The functional layer sits on top of this with an efficiency tax — React has to call the entire component again, diff the output, and only apply the minimal DOM changes. This is why manual optimization (useMemo, useCallback, React.memo) was necessary: the functional pattern is mathematically clean but doesn't map naturally to the sequential mutation machine. The React Compiler (see the main paradigm-shift doc) is the automatic version of these optimizations — it lets you write functional code and have the compiler translate it efficiently to von Neumann execution. The compiler exists because the lambda calculus and the von Neumann machine are equivalent but not identical.

2.4 Information theory (Claude Shannon, 1948) — why "bits" and "types" exist

The fourth question: what IS information? Turing asked "what can be computed?" Von Neumann asked "how do we build the machine?" In 1948, Claude Shannon, an American mathematician and electrical engineer, asked a different question: "what is information itself, and how can we measure it?" Before his paper "A Mathematical Theory of Communication" (1948), "information" was an informal, everyday word — "this letter contains information." After it, information was a quantifiable quantity, measured in bits. This is the theory that made the internet, digital media, compression, and modern communication possible.

Two proofs that changed engineering forever:

  1. Any information can be encoded in bits. A black-and-white photo (1000×1000 pixels, each pixel's brightness 0–255) → 1,000,000 numbers × 8 bits each → 8,000,000 bits. A text file → each character is 8 bits (ASCII) or 16-32 bits (Unicode) → the total in bits. A song → 44,100 samples per second × 16 bits × 2 stereo channels = 1,411,200 bits per second. Shannon proved that if you can describe the information, you can encode it in binary — 0s and 1s — with a known maximum number of bits needed. There is a finite, computable number that is "how much information this source produces."
  2. Information can be quantified — entropy. Shannon defined entropy — a measure of how much information a source produces, based on the probability of each symbol it emits. If a source emits every symbol equally often (all letters of the alphabet with equal probability), its entropy is high — each symbol carries a lot of information because it's surprising. If a source emits 'e' 50% of the time and 'q' 0.01% of the time, its entropy is low — the symbols are predictable, and a message of the same length carries less actual information. This difference is the mathematical basis of compression: a low-entropy source like English text can be compressed to ~50% of its size (common letters get short codes, rare letters get long codes — the principle behind zip, gzip, DEFLATE). A high-entropy source like random noise or already-encrypted data cannot be compressed at all — it already has maximum information per bit.

The word "bit." The term "bit" — short for "binary digit" — was coined by John Tukey in 1947, the same time Shannon was developing his theory. It is perhaps the most consequential single word of engineering jargon ever created — simple enough for anyone to say, precise enough for every communication protocol to depend on.

Why this matters for every line of JS you write, and for this doc:

  • Types exist because Shannon proved bits cannot interpret themselves. The von Neumann machine stores the byte 00110101 at address 0x1000. That byte is simultaneously: the integer 53, the ASCII character '5' (since '5' = 0x35 = 53), the boolean true (any non-zero value), a shade of gray at 20.7% brightness, a small fraction of a larger number if this byte is part of a 32-bit integer, and eight individual flags. The type is what disambiguates: "read these bits as a number. Read those bits as a character." Without a type, the byte is just bits — 00110101 with no meaning. Before Shannon, this problem wasn't even recognized as a problem — you had bits and you assumed everybody agreed on what they meant. Shannon proved that encoding and interpretation are separate concerns. The storage medium (von Neumann memory) handles the bits; the programming language (types) handles the interpretation. This is why in JS, typeof 5 = "number" and typeof "5" = "string" — same visual character, completely different bits, completely different interpretations.
  • The variable/value/type stack. The von Neumann machine gives you memory addresses. Shannon's encoding proves those addresses hold bits that need a type interpretation. A variable (like let count = 5) is the three layers together: a name (variable) pointing at bits in memory (von Neumann) that are to be interpreted as a number (Shannon type). If you change what count points to (count = "5"), the bits at that address change (from the IEEE 754 floating-point representation of the integer 5 to the UTF-8 byte 0x35 for the character '5') and the type changes (from number to string). The name count is still the same variable — but the value it points to has changed both bits and type. This is the full picture: data is the abstract idea, a value is the bits+type in memory, a variable is a handle pointing to a value.
  • Serialization is Shannon's theorem applied. When you write JSON.stringify(obj), you are doing exactly what Shannon described: take the information in memory (a JS object with all its fields and values), decide an encoding convention (JSON: ASCII text with curly braces and commas), produce a sequence of bits (the resulting string as bytes), transmit or store it, then decode by JSON.parse to recover a JS object. This is why you cannot "just save" a JS object to a file — the file system is a different kind of storage (von Neumann talks to von Neumann, but the bits need to be the right bits) — and Shannon's theorem tells you that any encoding works as long as both sides agree on the convention.
  • Why entropy matters for optimization. When React talks about "performance" and "re-renders," the underlying information theory says: a component that produces the same output for the same input is like a low-entropy source — predictable, compressible, optimizable. Memoization (useMemo, React.memo) is compression for computation: skip the work when the input hasn't changed, because the output would be the same. The React Compiler automates this by analyzing which computations produce pure output — which is Shannon's information measure applied to function calls.

3. The two primitives — data and operations

Strip away all the paradigms (OOP, FP, procedural, declarative) and programming has just two building blocks:

  1. Data — abstract information. The number 5. The text "hello." A color value. Independent of any machine, any language. Purely conceptual.
  2. Operations — abstract transformations on data. "Add two numbers." "Compare two values." "Find the larger of two numbers." Also conceptual, machine-independent.

Data and operations are in the model layer — they exist as ideas, independent of any programming language or hardware. A recipe on paper has data (flour, eggs) and operations (mix, bake). An algorithm on a chalkboard has data (the two numbers to compare) and operations (subtract, compare). No variables, no functions, no machine. Just information and what you can do with it.

To run on a machine, you need a language layer — a specific programming language that represents data and operations with names you can write and read. Variables and functions are the language layer's handles for data and operations:

  • A variable is a name that points to a value in memory. You read the value by writing the variable's name; you store a new value by assigning to it. count = 5 in JS means: "find the memory location that the engine has associated with the name count, and write the bits for the number 5 there."
  • A function is a named reusable block of operations. You call it by writing its name followed by arguments. add(2, 3) means: "go to the memory location that stores the instruction block for add, pass it the values 2 and 3, execute, and return the result."

A handle is a general term for "a name that gets you to a thing without knowing where that thing actually lives." A variable handle gets you to a value. A function handle gets you to a block of operations. A ref (useRef in React) is a handle for a mutable box that persists across renders. A file descriptor in operating systems is a handle for an open file — you don't know the file's disk sector; you just hold the number the kernel gave you. A URL is a handle for a web resource. A memory address in C/++ is a handle for a location in RAM. In every case, the same idea: a stable, unnamed name that lets you reach something without knowing its internals. When you read "variable" in later sections, know that it is one kind of handle among many — and React's design is largely about giving you the right handles at the right level (hooks for state, refs for mutable boxes, props for passed-in values).

Value Data as encoded in memory, with a type interpretation Shannon (bits + type = a value). Bits encode anything; types interpret them. 5 in JS memory: the IEEE 754 floating-point bit pattern for 5, with typeof = "number". "5" in JS: the UTF-16 bytes for '5', with typeof = "string".

The key relationship: data (abstract) → value (= bits + type per Shannon) → variable (= handle per von Neumann) → state (= role when lifetime is long per Turing). State is NOT a new kind of thing added at the end — it is the same variable-value-bits-data from earlier layers, playing the role of "persistence across events." The "state" label only appears at the top because it is a property of how the variable is used, not a property of the variable itself.

Does "handle" make things clearer or messier? Clearer, because a single idea ("a name that gets you to something without knowing its address") unifies variables, functions, refs, file descriptors, DOM refs, and URLs into one concept. This reduces the number of distinct mental objects you need to track. Messier? Only if you try to use "handle" everywhere the doc says "variable" — but the doc uses "variable" when pointing at values, "function" when pointing at operations, and will introduce "ref" when pointing at React's mutable boxes. The word "handle" sits above all three in the abstraction hierarchy, not replacing them.

Everything else — types, classes, modules, hooks, components — is a way of organizing variables and functions. Classes bundle variables with the functions that operate on them. Modules group related functions and variables under a namespace. Hooks are functions backed by hidden storage (React's state-slot array). The two atoms (data via variables, operations via functions) never go away.

4. Types — the contract on a value

Every value has a type — number, string, boolean, object, function, etc. The type tells the machine how to interpret the bits at that memory location, and which operations are valid: + works on numbers; .length works on strings and arrays; () calls a function. Attempting the wrong operation on the wrong type is a type error.

You came from C/C++, where types are enforced at compile time — the compiler refuses to compile if a variable declared int is read as char*. JavaScript is dynamically typed: a variable can hold a number now and a string later, and type errors surface only at runtime. The trade-off: faster to write, easier to refactor, harder to catch a whole class of bugs before the code runs. TypeScript (a typed superset of JS) was invented to give back what dynamic typing gave up — compiler-checked types — without losing JS itself. Most production React apps today are written in TypeScript, not plain JS.

In dynamically-typed JS, variables don't have types; values do — a variable is just a name binding to whatever value you assigned it last. let x = 5; — x is bound to a number value. x = "hello"; — x is re-bound to a string value. In statically-typed C, a variable's type is fixed at compile time by the declaration: int x; x = "hello"; won't compile. JS swapped compile-time type safety for run-time flexibility — a trade-off that made rapid iteration easier and a whole class of bugs harder to catch.

5. The key distinction — variables ≠ state

Here is the distinction this whole doc leans on. People say "state is data in memory," and that is true but it is not the part that matters. State IS normal variables. There is no special "state" cell type in memory. What we call "state" is a role a variable plays, not a different kind of thing. The label just says this particular normal variable matters across events.

The real distinction is not "variable vs state" — it is three properties that any variable has:

PropertyThe question it answersValues
LifetimeHow long does the value have to live?One function call · block · module · program runtime
ScopeWho can see the variable by name?Function · block · module · global
ReachabilityWho can reach the variable to modify it?Just one code path · several · everything

"State" is the label we give a variable when its lifetime is long enough that next events depend on the values previous events wrote into it, AND its reachability is wide enough that more than one call site can modify it. That is it. Closure counters are state. Module-level counters are state. Class instance fields are state. Globals are the most extreme kind of state (max lifetime, max scope, max reachability).

State vs global — the question you're about to ask. A global is a maximum-scope variable (everyone can see it). State is a variable whose lifetime/reachability is high enough that it matters across events. These are two different axes, not competing categories. A closure counter is state but NOT global. A global const PI is global but NOT state (it never changes, so calling it state adds nothing).

How does state get modified — and isn't that just what normal variables do?

Yes — by the same mechanism as any variable: assignment. There is no special state-modification opcode. What changes across patterns is not the operation (it's always "write a new value into a binding") but who performs the write and who owns the binding:

  • You own the binding, you write directly: let count = 0; ...; count++; — direct assignment. The "role" of state emerges because count lives across calls. No framework involved.
  • A closure owns the binding, you write via a setter it hands you: function makeCounter() { let n = 0; return [() => n, (v) => { n = v }]; } — the caller can't write n by name (it's not in their scope), but they can call the setter, which walks back into the closure and assigns on their behalf. Same assignment operation; you just handed off the right to do it.
  • React owns the binding, you write via a setter that also schedules a re-render: const [count, setCount] = useState(0); ...; setCount(count + 1) — you never see the actual variable. React holds it in an internal slot indexed by the order you called useState. setCount is the only authorized path: it assigns into React's slot AND tells React "this changed, re-render me." Direct assignment like count++ wouldn't work because the count you destructured is a snapshot for this render — React's real storage lives elsewhere, and mutating the snapshot does nothing to it.

"But useState's variable can't be assigned directly — doesn't that contradict 'state is normal variables'?" No — it confirms it. The reason you can't assign directly is exactly the reason state has to live in a *normal variable* somewhere: someone has to be the storage. With useState, that someone is React. The count you destructured is a read-only copy React handed you *for this render*; React keeps the mutable original in its own slot. If you wrote count++ you'd be mutating a local snapshot that disappears when the function returns — which would silently lose state, the bug that hooks were designed to prevent. So the API forces you to go through setCount, which performs the assignment into React's real storage and triggers a re-render. The mechanism is still ordinary assignment. What changed: you no longer own the variable, so you no longer have the right to write it directly — you have to ask the owner.

This is the same design as the closure-setter pattern above, with one extra rule: the setter also schedules a re-render. So "you can't write directly" isn't evidence that state is a special kind of object — it's evidence that the owner controls writes, and the owner here is a framework that needs to know when state changes.

So "if state can be modified, isn't it just a normal variable?" — yes, that is the whole point. State is a normal variable stored in an ordinary binding. The label exists because some normal variables matter across events and have to be treated with care (re-render me when this one changes; do not reset this one on every call; do not let two callers race on this one). The "rules" around state — go through the setter, don't mutate the snapshot — are about *coordinating* the writes, not about state being a different kind of object. The rest of the main paradigm-shift doc is the story of where that normal-but-persistent variable lives: closure, class field, hook slot, server. Same variable, different owner.

A few examples to make the gap sharp:

  • A function-local variable — not state. function add(a, b) { let result = a + b; return result; } — result lives for the duration of one call. When add returns, result is gone. The next call to add starts fresh with no memory of the previous call. result is a variable, not state — its value doesn't need to survive the function returning.
  • A counter — state. let count = 0; function increment() { count++; } — here count must survive across calls to increment. The 5th click needs to know the 4th click happened (otherwise it would say "1" every time). count is state: its value persists across events, and the next event's behavior depends on the value produced by the previous one.
  • A const used as a label — not state. const GREETING = "Hi"; — never changes, so calling it state adds nothing. It is data, but it has no temporal dependency. Constants are the opposite of state: they are values that don't change across the lifetime of the program.
  • A global counter outside any function — state. Same as the counter above, but now visible everywhere. Still state, because the value must persist across whatever events read or write it.

So the test for "is this variable state?" is not "does it live in memory?" (everything does) — it is "does the next event / call / render depend on the value this variable had after the previous one?" If yes, it's state. If no, it's just a temporary scratch variable.

6. Lifetime — the property that makes a variable into state

The single word that distinguishes state from a regular variable is lifetime: how long does the value have to live, and across what?

Variable kindLifetimeIs it state?Example
Function-localUntil the function returnsNo — next call starts freshlet sum = a + b; inside a function
Block-localUntil the enclosing block exitsNo — gone when the block ends{ let temp = compute(); use(temp); }
Module-scopedFor the lifetime of the program/moduleYes — survives across function calls in that moduleA module-level let nextId = 1; counter
Closed-over (closure)As long as something still holds a reference to the closureYes — survives across calls of the closureThe count in a function makeCounter() { let n = 0; return () => ++n; }
On an object instanceAs long as the instance is aliveYes — instance fields are state; they outlive each method call on the objectthis.count on a class instance
GlobalFor the whole program's runYes (the most extreme kind)window.foo = 5;

The longer a value has to live, the more "state" it is. The shorter, the more it is just a scratch variable. This is why functions are stateless by default — their locals die when they return — and why React's class components (each instance holding this.state for the lifetime of the instance) were naturally stateful: the instance was the persistence mechanism.

5b. Mental models — how developers actually reason about state

Before any framework is involved, the developer's mental model of state determines how they design code. The same runtime program is "obviously correct" or "obviously broken" depending on which of three mental models the developer carries.

Era / ModelCore abstractionWhere state livesWhat "stale" meansDebugging reflex
Imperative (C/Pascal) Memory addresses, manual allocation A variable is a named cell; the program mutates it in place Whatever the address says now Print the address; single-step; look at &x
OO (Java/Smalltalk) Object as identity + lifetime An object's instance fields; lifetime equals object lifetime "Is the field set on this instance?" Inspect the instance in the debugger; check who owns the reference
Functional (Haskell/ML) Value as immutable snapshot; state is a stream of values There is no mutable cell; state is the function from time to value "What value did this expression evaluate to at step n?" Trace the function; replay with fixed inputs; the value at a moment is the state
Reactive (React/Signals) Computation that re-runs when its inputs change State is in a slot; reading is subscription; writing triggers re-evaluation "What were the inputs at the time this computation ran?" Inspect the dependency array; trace the data flow; the closure captured the wrong inputs

The shift: React's hooks (and Signals) did not invent a new kind of state — they re-framed the developer's mental model. Under the hood, state is still a mutable cell somewhere. What changed is the contract the developer reads: "this effect re-runs when its inputs change." The mental model of "state = cell" still works for understanding storage, but the mental model of "state = stream of values" is what makes hooks feel natural.

Stale-closure is a mental-model bug, not a runtime bug. When a closure captures a value and the developer thinks "this is current," they are mentally treating a snapshot as live. The runtime is correct — it stored what it was told to store — but the developer's model assumed freshness. Closing this gap is what the class-to-hooks paradigm shift is.

7. The whole rest of the class-to-hooks doc, in one sentence

State is a thing that persists and that the next event depends on. The history of UI programming is the history of where that state lives: in a global variable, in a closure, in a class instance field, in a framework store, in a hook slot, in a server database. Each migration was a different answer to one question: where does the state live, and who is responsible for keeping it alive across events? React itself moved state roughly every 3-5 years — class instance (2013) → hook slot (2018) → client/server split (2022) → compiler-memoized hooks (2024) — and the main paradigm-shift doc is the inside of that story.
