REFERENCE · JS ACROSS STACKS

JavaScript Across Stacks — Where JS Runs, and Who Fights It

How JS looks from the frontend, backend, mobile, embedded, and AI perspectives — what each one uses of JS, what about JS doesn't fit, and the languages written to fill that gap (TypeScript, .NET/C#, Java/Spring Boot, Kotlin, Dart, Rust, Python). For each competitor: one positioning table on what justifies creating a new language instead of extending an existing one. Companion to javascript-the-language.

Why this doc exists

JS-the-language is one thing (javascript-the-language). JS-as-deployed is five different stories. Where JS runs changes what you use of it, what you wish were different, and who was built to replace it. This doc answers: "if JS is everywhere, why are there still five other major languages in the industry?" Sibling to javascript-the-language and frontend-camps-survey — the camps survey covers the frontend-only framework camps; this one covers language-level competition across every stack.

0. How to use this doc

Reading order: standalone. What "perspective" means here: same language, different host + different constraints = a different competitor set. Each section follows the same template: what this perspective uses of JS → what doesn't fit → the competitors → one positioning table per competitor (what each optimizes for) → one paragraph on the theory that justifies creating it instead of extending Java/C++. Reference: Glossary — shared vocabulary across all reference docs.

Scope. This doc is about language-level competition across stacks — which host uses what of JS, what doesn't fit, and which languages were created to fill that gap. It does not teach JavaScript mechanics (javascript-the-language), frontend framework camps (frontend-camps-survey), React paradigm shifts (class-to-hooks-paradigm-shift), component/framework architecture (nextjs-deep-dive, react-2024-and-beyond), service architecture (system-design), or API contract design (api-design). Those docs own their lane; this one only enters it when language/runtime choice changes the consequences.

The pattern. Across all perspectives, one rule emerges from the data: a new language wins when the dominant constraint changes and the old language's design bet conflicts with the new constraint. JS won the browser because the constraint was 1995 download size + scripting glue. TypeScript won JS tooling because the constraint changed to large-team maintainability. Go won networked services because the constraint changed to concurrency-first. Rust won systems because the constraint changed to memory safety without GC. Java extended C++ syntax but won on the JVM bet (write once, ship anywhere). The rule: extend when the constraint is unchanged, invent when it inverts.

1. The Frontend Perspective

What the frontend uses of JS: the language + DOM + fetch + Canvas/WebGL + WASM interop. The browser only runs JS (and WASM). There is no language-level competitor on the frontend — the browser chooses for you.

What doesn't fit: heavy numerics (WASM handles this), real threads (Workers are separate memory, not shared), type-safe large codebases (TypeScript is the answer, not a new language).

Compile-to-JS languages that tried: CoffeeScript (syntax sugar, died when ES6 arrived), PureScript/Elm/ReasonML (typed functional, niche), Dart (compiled to JS, pivoted to Flutter). None survived as a mainstream alternative because the browser's JS monopoly is absolute — you compile to JS, you don't replace it.

Positioning table — TypeScript vs JavaScript (the one competitor that survived):

The theory—Extending JS with gradual typing, not replacing it. The "compile away" design means no runtime cost, no separate ecosystem, no migration cliff. This is why TS won where Dart/CoffeeScript failed — they required a runtime or a clean break.

2. The TypeScript Shift (the JS competitor that survived)

TS is not a separate perspective — it's the frontend perspective's internal evolution. But it deserves its own section because it's the only "competitor" that didn't fight JS from outside; it replaced JS from inside.

Timeline: 2012 release (Anders Hejlsberg, creator of C# and Turbo Pascal). 2014 Angular 2 bets on TS — one of the first mainstream frameworks to require it. 2018 Babel 7 can transpile TS syntax, but type-checking still needs a separate pass. 2020 "TS as default" inflection: Create React App, Next.js, Vue CLI all default to TS. Recent Stack Overflow surveys consistently rank TS among the most-admired languages.

The theory — why extend, not replace: The constraint didn't invert. The codebase grew, the team grew, the maintainability burden grew — but the target (the browser) and the runtime (JS) stayed the same. Adding types on top preserves 100% of the JS ecosystem, 100% of the runtime, 100% of the developer's mental model. The "compile away" property is the key: at runtime, there is no TS. This is the general rule — if the constraint is "the same platform, more safety," you extend. If the constraint is "a different platform," you invent.

2b. Writing typed JS — the type system in practice

§2 argued why TS exists. This is how it works as a system of rules: a static overlay that type-checks before the engine ever runs, then erases to plain JS. Three ideas are the whole job.

IdeaWhat it meansThe trap it pre-empts
Types are erased, not enforced at runtime tsc checks the types, strips them, emits pure JS. There is no instanceof-style runtime check for interfaces. The type system is a compile-time contract with the development team, nothing more. Assuming a type guarantees runtime safety. It doesn't — it guarantees the compiler checked your call sites. Runtime data (API payloads, user input) is untyped no matter what you annotate.
Shape over name TS is structural, not nominal. Two objects with the same fields are the same type regardless of how they're declared. interface and type define a shape; any value matching it is accepted. Writing "factory" boilerplate or ceremony to match types when plain structural compatibility already suffices. JS's duck typing is preserved, just checked early.
Annotation is smallest-first, inference expands You can let TS infer most types (declarations rarely need one). Add annotations at boundaries: function parameters, return types, API shapes. Annotate where the contract meets the untyped world. Over-annotating everywhere (type salad), or never annotating (loses the guard). The discipline: infer inside, annotate at the edges.

The strict-mode gate: tsc --strict is the only mode worth using. It turns on the checks that prevent the classic bugs — implicit any, non-null assertion assumptions, no implicit index-signature access. Without strict, TS quietly degrades back toward plain JS and the value is mostly lost.

2b.2 The runtime boundary — where types stop

BoundaryWhy it matters
Interfaces, type aliases, generics, annotationsErased 100% — never in output. Zero runtime cost.

Type-narrowing story: a union isn't valid at runtime until you narrow it. typeof, in, and discriminated-union checks (if (x.kind === 'a')) narrow. TS's value is that narrowing is type-checked as you go — write the check, the compiler vouches for the branch.

type Result =
  | { status: "ok";   data: string[] }
  | { status: "err"; error: string };

function handle(r: Result): number {
  if (r.status === "ok") return r.data.length; // narrows to the ok branch
  return r.error.length;                        // narrows to the err branch
}

What this section is not: a full TS tutorial. It's the language — to build logic per project-model, practice typing alongside any JS in this series. For the toolchain (tsc, tsconfig, JSX vs not) see javascript-the-language §11 tooling; the type-system rules above are the part that ever matters.

2b.3 TypeScript in production — value and traps

The value: shape mismatches caught before runtime, refactoring without fear (types flag every call site the change breaks), self-documenting APIs, and editor intelligence (go-to-definition, find-references, safe rename). All of it is free at runtime because the annotations erase. The value compounds with team size — the bigger the codebase, the more the compiler does.

The traps — the ones that cost real incident hours:

TrapWhy it bitesThe habit that fixes it
Assuming types validate runtime dataTypes erase; an API payload or user input passes a type-check unverifiedValidate at the boundary (§2b.2) — schema libs (zod, valibot, arktype) at the I/O edge
any as a reflexQuiets the compiler, not the bug; the type silently stops guarding that pathUse unknown, then narrow; keep any for structured interop shims only
Strict offMuch of the value disappears with implicitAny un-enforcedShip tsconfig with strict: true from day one (the only mode to end games in)
Enum ceremonyRuntime objects with all the ceremony; often the wrong toolPrefer union string literals + as const — tree-shakeable, exact
Migrating cold turkeyOne-shot rewrite is the highest-risk path in a large appGradual adoption: allowJs, @ts-check per file, .d.ts for plain deps, then enable strictness

Gradual adoption path: point tsc at existing JS with allowJs; enable checkJs so // @ts-check on a file starts complaining; add .d.ts for untyped packages (or declare module); then flip strict once the code compiles clean on basic settings. Every file migrates on its own schedule — which is exactly why TS won instead of a new language: it lets you extend one production codebase inside the existing runtime.

3. The Backend Perspective

What backend uses of JS: Node.js — the event loop + npm + fs/net/http modules. One process multiplexes thousands of connections on a single thread's event loop: non-blocking I/O + async callbacks, with a small OS thread pool for blocking work (fs, crypto, DNS). The same loop from the browser, transplanted to the server.

What doesn't fit: CPU-bound work (blocks the loop), real threads (Worker threads exist but are heavy), sandboxed memory (V8 isolates are not JVM-grade), the decades of enterprise backend tooling (JMX, JPA, Spring, .NET diagnostics), the talent pool that knows Java/C# from university.

4. The Mobile Perspective

What mobile uses of JS: React Native (Expo, bare), Capacitor/Ionic (WebView + native plugins), NativeScript. JS runs on a JS engine (Hermes on Android, JavaScriptCore on iOS) bridged to native modules. UI is native (React Native) or WebView (Capacitor).

What doesn't fit: native performance (bridge overhead, JSI helps but doesn't eliminate), native UI primitives (you're reimplementing platform conventions), App Store review (WebView apps face scrutiny), the talent pool that knows Swift/Kotlin from university.

Dart is "what JS would be if it had a sound type system and an AOT compiler."

5. The Embedded / IoT Perspective

What IoT uses of JS: Espruino (JS on microcontrollers), Johnny-Five (Node on host + Firmata on device), Tessel, low.js. JS runs on devices with ≥100KB RAM (ESP32, STM32). The event loop model actually fits IoT well — sensors are async events.

What doesn't fit: RAM pressure (V8 needs ~MB), hard real-time (GC pauses), battery life (interpreted > compiled), no stdlib for bare metal.

Competitors:

One-paragraph theory: JS's event loop is actually well-suited to IoT (sensors = async events). The wall is RAM, not the language model. C/C++ win because they compile to 2KB binaries with zero runtime. Rust is the newer entrant: memory safety for firmware without GC. The constraint didn't invert — it just got harder (smaller chips, more safety regulation). The languages that win embedded are the ones that can shed their runtime.

5b. Mental models — how cross-stack reasoning actually works

When developers move between stacks (frontend, backend, mobile, embedded, AI), they don't just learn new syntax — they swap mental models. Each stack has a primary abstraction that determines what "easy" and "hard" mean. The same code pattern that is idiomatic in one stack is an anti-pattern in another.

StackPrimary abstractionWhat "state" meansWhat "performance" meansWhat "correct" means
Frontend (browser) DOM tree + event loop Live in the document; mutations trigger repaint Render time, jank, bundle size, perceived latency Same result across browsers; correct accessibility semantics
Backend (Node) Request/response + async I/O Per-request or shared via DB/cache; mutations go through explicit boundaries Throughput, p99 latency, memory under load Idempotency, correct error propagation, no resource leaks
Mobile (RN/Native) Native UI bridge + constrained device Hybrid: JS-side store + native UI mirror Frame budget (16ms), memory pressure, cold start Same UX offline, gestures don't feel broken, no jank
Embedded (MCU) Hardware registers + interrupt loop Global state, often no heap; everything is a static buffer Bytes, cycles, watts; no GC pauses allowed Deterministic timing; never miss an interrupt; never crash
AI / Data Tensors + computational graph Model weights; "state" of a running process is the computation history FLOPs, memory bandwidth, GPU utilization Numerical reproducibility; the answer is approximately right, with bounded error

The shift: The hardest part of polyglot work is not the syntax — it is noticing which mental model is in play. A backend developer reading frontend code will treat the DOM as state; a frontend developer reading backend code will treat requests as instantaneous; an embedded developer will be terrified by garbage collection. None of them are wrong — they are carrying the right model for a different stack. The skill is the meta-skill of switching models on entry.

JS's specific edge: Because JS lives in so many stacks, the same syntax (await, Promise.all, an event handler) has to work in all of them. This is why the language has stayed small but flexible — every stack reuses the same primitives. The cost is that JS code in the wild often looks the same across stacks but means different things depending on the model in the developer's head.

6. The AI / Data-Science Perspective

What AI uses of JS: almost nothing in the model layer (PyTorch/JAX/CUDA are Python/C++). Everything in the application layer: Next.js + Vercel AI SDK + fetch to model APIs, LangChain.js, Transformers.js (WASM), TensorFlow.js (WebGL/WASM). JS is the delivery vehicle for models trained elsewhere.

What doesn't fit: training (no CUDA, no autograd ecosystem, no distributed training), massive tensors (WASM memory limits), the talent pool (every PhD learns Python).

Competitor: Python (the model layer) / Mojo (the challenger)

DimensionJS (app layer)Python (model layer)Mojo (emerging)
What it optimizes forProductizing models, web UIs, edge inferenceResearch, training, data pipelines, model authoringPython syntax + systems perf, no GIL, compile to GPU
EcosystemVercel AI SDK, LangChain.js, TF.jsPyTorch, JAX, HuggingFace, NumPy, PandasMAX platform (Modular), early stage
The theoryJS won the app layer by defaultLibrary lock-in (NumPy 2006 → PyTorch 2016)Constraint inversion: Python's perf wall is the GIL + interpreter; Mojo keeps syntax, adds compiler

One-paragraph theory: AI picked Python because NumPy existed in 2006, before "AI" meant LLMs. The lock-in is library lock-in, not language lock-in. JS owns the application layer because the web is the delivery target. Mojo (Chris Lattner, 2023) is the first serious attempt to invert the constraint: keep Python syntax, add a compiler, remove the GIL, target accelerators directly. If it works, it's the first language that extends Python's syntax but replaces its runtime — the inverse of TypeScript's "compile away" strategy.

7. The "Other" Perspective: Edge, Serverless, Build Tools

Where JS is the default entirely due to the host being JS: Cloudflare Workers, Vercel Edge Functions, Deno Deploy, Bun, esbuild/rolldown/Vite (written in Go/Rust but drive the JS ecosystem). The edge runtime picked JS because V8 is already there, the security sandbox already exists, and cold-start matters more than steady-state perf.

Competitor: WASM on the edge. Cloudflare supports WASM components; Fastly Compute@Edge is WASM-first. But WASM still needs JS glue for DOM/HTTP in the browser, and the edge is converging on the same APIs (WinterCG). Here JS has no real language competitor — WASM is a partner, not a replacement, same as in the browser.

8. The Pattern: When Does a New Language Beat Extending an Old One?

Across all seven perspectives, one rule emerges from the data:

A new language wins when the dominant constraint changes and the old language's design bet conflicts with the new constraint.

Old LanguageOld ConstraintOld Design BetNew ConstraintNew LanguageNew Design Bet
C++Bare metal controlManual memory, zero overheadNetworked services at Google scaleGoGoroutines, fast compile, opinionated tooling
C++Bare metal controlManual memoryMemory safety without GCRustBorrow checker, affine types, fearless concurrency
JavaPortable enterprise serversJVM + GCAndroid needed modern language, frozen Java 6KotlinJVM bytecode target, null safety, coroutines, less boilerplate
Objective-CC superset + dynamic runtimeMessage passing, fragile binary interfaceMemory safety, value semantics, modern compilerSwiftLLVM ownership, value types, protocol-oriented
JavaScript1995 browser scriptingDynamic, prototype, single-threadedLarge-team maintainabilityTypeScriptGradual typing, compiles away, zero runtime cost
JavaScriptBrowser monopolyOnly language the browser runsNative mobile performance without bridgeDart/FlutterOwn rendering engine, AOT, sound types, multi-platform
PythonScripting / scientific glueDynamic, GIL, interpreterAI training at scaleMojo (attempt)Python syntax + compiler + aiming to drop the GIL + GPU native

The inverse also holds: when the constraint doesn't invert, extension wins. Java kept C-flavored syntax but bet on the JVM. C# was shaped by Java but added LINQ, async, and richer type features on the CLR. TypeScript extends JS syntax but compiles away. Kotlin extends the JVM bytecode target but replaces the language. The platform or runtime bet is what changes; the syntax is negotiable.

JS's original constraint: a scripting language for Netscape Navigator 2.0, downloaded over 28k modem, written in 10 days. That constraint is gone. The new constraints (large teams, mobile, edge, AI delivery) each spawned their own response — TS, RN/Flutter, Workers, Vercel AI SDK. None replaced JS because none inverted the browser constraint. The browser still only runs JS (and WASM). As long as that's true, JS survives at the center and the competitors orbit around it.

9. Choosing a Stack

The pattern (§8) explains winners after the fact; this is the forward version — how to pick a stack today. Same rule, applied first: identify the dominant constraint, then the language whose design bet matches it. "Which language is best?" is the wrong question. "Which constraint dominates, and who bet on it?" is the one that answers.

ConstraintQuestion to askWhat to check
HostWhere does the code run?Browser/edge runtimes are JS-only (plus WASM) — non-negotiable. Backend and mobile are open lanes.
ConfidenceEvent-driven I/O, CPU-heavy, realtime, or batch?I/O-bound → Node. CPU-bound spikes → Go or worker threads. Realtime presence → Elixir or Node.
Latency & throughputIs p99 latency or raw QPS the priority?Throughput ceilings and GC pauses matter at scale; not before.
Memory safetyIs memory corruption unacceptable?Systems/embedded/security → Rust or C/C++ judgment.
Startup timeDo cold starts dominate?Edge/serverless/functions → keep the runtime small (JS wins; JVM loses).
Team skill & hiringCan this team ship and operate it?The best language you can't staff is the wrong one. Skill + hiring pool are real constraints.
Ecosystem & opsAre the libraries and tooling mature?Maturity, observability, deploy path, and nobody-googles-it-in-vain matter.
InteropWill it sit next to a JS system?FFI, WASM, contracts (Rust via napi-rs, Go as a service, Python over HTTP).
ReversibilityHow costly is changing it later?Strangler-fig-able = cheap; a new platform rewrite = expensive.

Do not choose a language because it is better in the abstract. Choose the language whose design bet matches the dominant constraint.

The lazy rule: prefer the path that extends what exists. Migrations that keep the runtime and platform (JS→TS) are cheap; migrations that change the runtime (Node→Go/Rust) should be targeted at hot paths, not done wholesale.

12. Principles

The durable takeaways — the parts to carry into any polyglot decision.

PrincipleMeaning
Constraint first, language secondThe dominant constraint determines the right language, not the reverse
Extend when the platform is unchangedTS wins because the JS runtime stays; why Dart-to-JS failed
Invent when the constraint invertsGo/Rust/Swift — the old design bet no longer fits
Ecosystem beats syntaxLibraries and tooling decide adoption (Python's NumPy·PyTorch)
Interop beats purityLanguages that integrate spread faster than "better" ones
Runtime matters more than syntaxSame syntax means next to different things per host (§5b)
Types do not replace runtime validationStatic checks stop at the boundary; validate external data
Team skill is a real constraintThe best theoretical language you can't staff is the wrong choice
Migration cost is part of the designChoice includes the cost of moving later (§10)

The product: multi-user document editing — live cursors, presence, offline edits, instant sync, server persistence.

What the example shows: no single "best language" — each slice answers a different dominant constraint. The same product spans five lanes, and this doc's rule picks a language for each independently. The seams (shared CRDT code, the typed BFF↔core contract, presence on the socket) are where interop cost is paid (§9, §11).
