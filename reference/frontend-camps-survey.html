Frontend camps survey

A map of how real products ship UI in 2026: CMS, HTML-first, SPA, meta-frameworks, WASM, TypeScript, and the AI layer. Read this to recognize which camp a codebase is in — not to pick a religion.

Why this doc exists

The class-to-hooks paradigm doc answers: how does React think about components? This doc answers a different question: what is the rest of the frontend world doing? At work you will open repos that are not "a Vite React SPA." Some are WordPress themes with a React island. Some are Astro sites. Some are Angular monorepos. Some are Next.js apps with Server Components. For the JS language foundation behind all of them, see JavaScript: The Language. Knowing the camps saves you from assuming every frontend is the same mental model.

Survey depth, not tutorials. Each section: what the camp optimizes for, what you will see in code, and when it wins or loses.

These camps overlap. A "Next.js app" is a meta-framework that can still behave like a SPA on some routes. A WordPress site can host a React admin SPA. Treat the labels as centers of gravity, not exclusive clubs.

Mission fit. Your mission is still JS fundamentals → read React at work. This survey is orientation for that second half. You do not need to master every camp. You need to open a repo and say: "this is HTML-first with Preact islands" or "this is an App Router RSC app" without panicking.

Reference: Glossary — shared vocabulary across all reference docs.

1. Camp A — CMS and classic server-rendered apps

The oldest industrial pattern: the server owns the document. PHP (WordPress, Laravel), Rails, Django, ASP.NET MVC, and similar stacks render HTML on each request. JavaScript is optional sugar for forms, carousels, and admin widgets.

What you will see

  • Template files (.php, .erb, .jinja) with HTML and server variables mixed.
  • jQuery or vanilla DOM scripts in theme folders — still extremely common in WordPress.
  • A separate "headless CMS" variant: Contentful, Sanity, Strapi, WordPress REST/GraphQL — content API + a frontend built in another camp.
  • Admin UIs that are full SPAs (Gutenberg, custom dashboards) sitting on top of a classic backend.

When it wins

  • Content sites, marketing, blogs, e-commerce catalogs with heavy editorial workflows.
  • Teams whose primary skill is backend or content operations, not SPA architecture.
  • SEO-critical pages where "HTML in the first response" is non-negotiable and the team already knows the CMS.

When it loses

  • Highly interactive product UI (real-time boards, design tools, complex client state).
  • Cross-platform product sharing logic with mobile (React Native, etc.).

Reading tip for a JS learner: do not confuse "there is a script tag" with "this is a React app." Trace who owns the first paint: if the server sent full HTML of the page content, you are in Camp A (or B), even if a React widget mounts later.

2. Camp B — HTML-first and islands

HTML-first frameworks treat the document as the product and JavaScript as a precision tool. The modern flagship is Astro: ship zero JS by default; opt into "islands" of interactivity (React, Preact, Svelte, Vue, Solid) only where needed. Related family: HTMX / Alpine / server-driven UI — keep logic on the server, swap HTML fragments over the wire.

What you will see

  • Most routes are static or server-rendered HTML with almost no client bundle.
  • client:load / client:visible style directives on components (Astro) — explicit hydration boundaries.
  • Preact chosen over React for islands because ~3.5 kB matters when the rest of the page is static (see paradigm doc §18.5b).
  • HTMX attributes like hx-get, hx-swap — partial page updates without a client router.

When it wins

  • Marketing sites, docs, blogs, content-heavy product marketing with a few interactive widgets.
  • Performance budgets and Core Web Vitals as primary KPIs.
  • Teams tired of shipping a 200 kB framework for a contact form.

When it loses

  • App-like products where almost every pixel is interactive state (Figma-class tools, dashboards with dense client state).
  • When the "island" graph grows until you reinvent a SPA poorly.
// Astro mental model (pseudo) — HTML first, island second
---
// frontmatter runs on the server / at build
const posts = await getPosts();
---
<h1>Blog</h1>
{posts.map(p => <article>{p.title}</article>)}

// only this island ships client JS
<SearchBox client:load />

Related names you will hear: Enhance, 11ty + islands, Fresh (Deno), partial hydration experiments across the ecosystem. The shared slogan: default to HTML; earn your JavaScript.

3. Camp C — Client SPAs

Single-Page Applications: the browser downloads an app shell; client-side routing swaps views; the server is mostly an API. This is the model Create React App trained a generation on, and it still powers huge product UIs.

What you will see

  • react-router / Vue Router / Angular Router owning navigation.
  • A fetch / React Query / SWR layer talking to REST or GraphQL.
  • Vite (or Webpack legacy) as the bundler; "just a SPA" without a full-stack framework.
  • State libraries: Redux, Zustand, Pinia, NgRx — because the client owns long-lived state.

When it wins

  • Authenticated products behind a login wall (SEO less critical).
  • Highly interactive UI where the server would thrash if it re-rendered every interaction.
  • Teams that already have a strong API backend and want a clean client/server split.

When it loses

  • Public content pages that need fast first paint and crawlable HTML without extra SSR work.
  • Greenfield 2025+ apps where the React team itself now recommends a framework (CRA sunset Feb 2025 — paradigm doc §18.6).

Important 2026 nuance: SPA is not dead. "SPA as the default starter" is dead. Many production apps remain SPAs; new React guidance pushes Next.js, React Router framework mode, or Expo for apps that need routing + data + deployment conventions.

4. Camp D — Meta-frameworks (the industrial default for new React)

A meta-framework is a framework around a UI library: routing, data loading, rendering strategy, bundling, and often deployment. For React, that means Next.js first, then Remix / React Router framework mode, and mobile-adjacent Expo. Outside React: Nuxt (Vue), SvelteKit, Angular's modern CLI+SSR path, SolidStart, Qwik City.

What you will see

  • File-system or config-based routing (app/ in Next.js App Router).
  • Server Components / loaders / actions — data close to the server, UI split across processes (paradigm doc §18.2).
  • Caching and revalidation as first-class concepts, not afterthoughts.
  • Deploy targets that assume the framework (Vercel, Netlify, Cloudflare adapters, self-hosted Node).

When it wins

  • Product + marketing in one codebase.
  • Teams that want conventions for data fetching, code splitting, and SEO without inventing them.
  • Anything that benefits from RSC: less client JS for data-heavy pages, direct server resource access.

When it loses

  • Tiny widgets or pure static sites (Camp B is lighter).
  • Teams that need total control of a bespoke SPA architecture and already have it working.
  • When framework abstractions leak and the team does not yet understand the split-process model — debugging cost spikes.

Deep dive for the React path you are on: Next.js Deep Dive.

5. Camp E — The other major UI libraries (signals world)

Not everything is React. By 2026 the non-React mainstream largely standardized on signals (or signal-like runes) for fine-grained updates:

StackReactivity unitNotes for a React reader
Angular (v17+ → v22)Signals + (still) zone.js legacyEnterprise default in many shops; Signals+Vite in modern setups. Full evolution doc.
Vue 3ref / reactive (signal-like)Template + Composition API; gentler learning curve for many teams
Svelte 5Runes ($state, etc.)Compiler-first; less runtime framework in the browser
SolidcreateSignalJSX like React, reactivity like signals — no virtual DOM re-render model
PreactHooks + @preact/signals add-onReact-shaped API, web-first, tiny; paradigm doc §18.5b

React's answer remains the Compiler + re-render model, not signals-as-public-API (paradigm doc §18.5). Do not translate 1:1. In signals frameworks, changing a cell updates bindings; the component function often does not re-run top-to-bottom the way a React function component does.

C++ analogy. React re-render ≈ recomputing a pure function of state and diffing the result. Signals ≈ dirty-flagging dependent nodes in a graph and updating only those nodes. Both can implement the same UI; the debugging stories differ.

5b. Mental models — how camp practitioners actually reason

Each camp trains a different mental model. If you only know the React re-render model, you will misread code in other camps. Here is how practitioners in each camp actually think:

CampCore mental modelWhat "change" meansDebugging intuition
CMS / Classic (A) Page = template + data. Server re-renders full page on state change. Full round-trip or partial fragment swap. Trace the template + controller. No client hydration.
HTML-first / Islands (B) Static document with precision holes for interactivity. Only the island re-renders; rest is inert HTML. Find the client:* directive → that's your React/Preact boundary.
SPA React (C) UI = f(state). Re-render = re-run component function + diff. State change → component re-runs → children re-render (unless memoized). React DevTools: why did this re-render? Closure staleness? Missing memo?
Meta-framework RSC (D) Server components = pure functions per request. Client components = React model. Server: new request = fresh function. Client: same as SPA. Check "use client" boundary. Server logs ≠ client logs.
Signals (E) Reactive graph: cells (signals) → derived (computed) → effects. No component re-run. Write to signal → only subscribers update. Component function often runs once. Signal DevTools: which signals changed? Which effects fired? No "render count".
WASM (F) Foreign language runtime. JS = glue; logic = compiled module. Call exported function → get result. No reactivity in WASM. Profile the WASM module (perfetto, wasm-bugs). JS side is thin.

Transfer trap: bringing React's "re-render" mental model to signals frameworks causes over-subscription (treating signals like state, reading in render). Bringing signals "dirty flag" model to React causes missing memoization. Learn the camp's native model first.

6. Camp F — WASM and non-JS UI engines

WebAssembly lets languages like Rust, C++, C#, and Zig run in the browser (and on the edge) at near-native speed. Frontend use cases cluster around:

  • Heavy compute in the client: image/video codecs, CAD, games, crypto, data viz pipelines.
  • Porting existing C++ engines to the web (your background is an asset here).
  • Edge logic where cold starts and CPU matter (some Cloudflare / Wasmtime deployments).

JS still usually owns the DOM glue. Frameworks like Yew / Leptos (Rust), Blazor (C#), and custom engines exist, but most production "WASM frontends" are hybrid: React/Vue shell + WASM modules for hot paths.

When it wins: algorithmic bulk that would jank on the main thread in plain JS. When it loses: ordinary forms and CRUD — the toolchain tax is not worth it.

7. The TypeScript shift

TypeScript is no longer "nice to have" in industrial frontend. Stack Overflow surveys have shown JavaScript as the most-used language for years running, with TypeScript as the typed layer most professional teams adopt for app code. For the full JS-vs-everything story across backend/mobile/embedded/AI, see JavaScript Across Stacks. Practical reality in 2026:

  • New Next.js / Vite / Angular scaffolds default to TypeScript or offer it first.
  • Library types ship in the package; any is a code-review smell, not a strategy.
  • Your mission still correctly stays in plain JS first — types sit on top of the mental models you are building (scope, closures, this, modules). Learning TS before those models is memorizing annotations for behavior you cannot yet predict.

When you do add TS later: start with strict, type function boundaries and data from APIs, leave local inference alone. The cert does not require TypeScript; work code often will.

8. The AI-era layer (tooling, not a UI camp)

AI did not invent a new rendering model. It changed how code is produced and reviewed:

  • Copilots and agents generate components, tests, and refactors — quality still depends on the human who can read closures and deps arrays.
  • AI product features in apps: chat UIs, streaming tokens, tool-calling frontends — usually still React/Vue components over SSE/WebSocket.
  • AI training / annotation work as an income path for people who can evaluate code and UI quality — see Frontend income markets.

Stack Overflow's 2024 survey already showed large majorities of developers using AI tools at work. By 2026 that is ambient. The differentiator is not "can you prompt"; it is "can you tell when the generated hook is wrong." That is why this workspace drills JS fundamentals before framework fashion.

Teams rarely stay in one camp forever. Common migrations and their friction points:

Route-level dual maintenance; cache invalidation bugs Bundle -40%; LCP <2.5s; no regression in Core Web Vitals 4–8 sprints

Two runtimes; shared state sync; CSS conflicts Zero Angular bugs in new features; team velocity ↑ 6–18 months

Anti-pattern: Big-bang rewrites. Every successful migration in the table above is incremental, route-by-route, or island-by-island. The camp boundaries in the survey table (§0) are centers of gravity — not walls.

      You can place a codebase into a camp (CMS, HTML-first, SPA, meta-framework, signals library, WASM hybrid), know what each optimizes for, and know whether your React closure mental model applies as-is, applies only on the client island, or should be set aside. The point is recognition at work — not converting every project to your favorite camp.
