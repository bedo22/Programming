Next.js deep dive

RSC, App Router, caching, Turbopack, and AI-era patterns — tied back to the function+hooks model. Read this after the paradigm doc, before assuming every React file is a client component.

Why this doc exists

After Create React App was sunset (Feb 2025), React's own docs steer new apps toward a framework. In job postings and greenfield React work, that framework is often Next.js (Vercel). This doc is not a tutorial that replaces nextjs.org — it is a map for a C++-background JS learner who already understands functions, closures, and hooks, and needs to read Next code without drowning.

Prerequisites in this workspace: class-to-hooks paradigm shift (especially §18.2 RSC and §18.1 compiler), and re-render box model. Landscape context: frontend camps survey §5.

1. What Next.js is (and is not)

Is: a React meta-framework — routing, rendering strategies, data fetching conventions, bundling, and production optimizations around React.

Is not: a replacement for React's component model. Client components still use the same hooks, closures, and per-render boxes you already studied. Next decides where code runs and how routes load data; React still decides how UI updates from state.

2. Pages Router vs App Router

Next had two successive routing systems. You will meet both in the wild.

Pages Router (pages/)App Router (app/)
EraClassic Next (widely deployed)Current default for new apps
Data APIsgetServerSideProps, getStaticPropsasync Server Components, fetch cache, server actions
LayoutsCustom _app / nested HOCsNested layout.tsx that preserve state
RSCNo (client React tree after data props)Yes — server components by default
File conventionspages/about.js → /aboutapp/about/page.tsx → /about

Reading tip: if you see getServerSideProps, you are in Pages Router. If you see async function Page() at the top of a route file with no "use client", you are in App Router Server Components. Do not mix the mental models.

3. App Router file conventions (the vocabulary)

Under app/, filenames are special:

  • page.tsx — the UI for a route segment (required for that URL to exist).
  • layout.tsx — wraps pages; does not remount on navigation between child routes (state in a layout survives).
  • loading.tsx — Suspense fallback for the segment while server content loads.
  • error.tsx — error boundary for the segment (must be a client component).
  • not-found.tsx — 404 UI for the segment.
  • route.ts — HTTP handlers (REST-style endpoints) instead of a page.
  • template.tsx — like layout but remounts on navigation (rarer).
  • default.tsx — parallel route fallbacks (advanced).
app/
  layout.tsx          // root shell (html/body, nav)
  page.tsx            // /
  blog/
    layout.tsx        // wraps all /blog/*
    page.tsx          // /blog
    [slug]/
      page.tsx        // /blog/:slug  (dynamic)
      loading.tsx

Dynamic segments: [id], catch-alls [...slug], optional catch-alls [[...slug]]. Route groups (marketing) organize folders without affecting the URL.

4. Server Components vs Client Components

This is the load-bearing idea. Default in app/: Server Component. You opt into the browser with the directive:

// app/counter.tsx — must run in the browser (hooks, events, window)
"use client";

import { useState } from "react";

export function Counter() {
  const [n, setN] = useState(0);           // box model applies here
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}

// app/posts/page.tsx — Server Component (default). No hooks. Can use secrets/fs/db.
import { Counter } from "../counter";
import { db } from "@/lib/db";

export default async function PostsPage() {
  const posts = await db.post.findMany();  // runs on the server
  return (
    <main>
      <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>
      <Counter />                          // client island inside server page
    </main>
  );
}

Rules that prevent confusion

  1. Server Components cannot use hooks or browser APIs. No useState, no useEffect, no window. They render once per request (or at build time) — there is no re-render loop.
  2. Client Components cannot import server-only modules (db clients, private env without NEXT_PUBLIC_). Data flows server → client as props (serializable).
  3. Composition direction: server can render client children. Client can render server children only via patterns like passing server components as children or slots — not by importing a server file into a client file.
  4. Everything your paradigm doc taught still applies on the client side of the line. RSC does not replace hooks; it shrinks how much of the tree needs them.

Dan Abramov's formula (paradigm doc §18.2): client is UI = f(state); server is UI = f(data); together UI = f(data, state). When reading a file, ask first: which function am I in?

5. Data fetching patterns

5.1 async Server Components + fetch

In App Router, fetch is integrated with Next's cache (behavior has evolved across versions — always check the version of the app you are reading). Typical shape:

async function getUser(id) {
  const res = await fetch(`https://api.example.com/users/${id}`, {
    next: { revalidate: 60 },   // ISR-style: revalidate every 60s
  });
  if (!res.ok) throw new Error("Failed");
  return res.json();
}

5.2 Direct backend access

Server Components can call databases, file systems, and internal services directly — no need to expose a public REST route for your own page data. That is a major reason RSC exists: colocate data and UI without shipping the query client to the browser.

5.3 Server Actions

Functions marked with "use server" can be passed to client components as callbacks (e.g. form action). They run on the server when invoked. Treat them as public endpoints — validate inputs, auth, and never hardcode secrets (paradigm doc §18.4 RSC CVEs).

// app/actions.ts
"use server";

export async function updateTitle(formData) {
  const title = formData.get("title");
  // validate + auth + db write
}

6. Caching mental model (including Cache Components)

Next's cache story is the part that confuses experienced SPA developers most. Rough layers:

  • Request memoization — duplicate fetch calls during one server render can dedupe.
  • Data cache — persisted results across requests (with revalidation tags / time).
  • Full route cache — static HTML/RSC payload for a route when it can be produced ahead of time.
  • Router cache (client) — client-side session cache of visited segments for snappy back/forward.

Cache Components (the direction of modern Next): make caching explicit and compositional — mark which parts of the tree are cacheable static shells vs dynamic holes, instead of hoping global defaults match your intent. Read the project's Next major version docs for the exact APIs (use cache, dynamic APIs like cookies() / headers() that opt a subtree into dynamic rendering, etc.). The stable idea across versions:

Static vs dynamic is a tree property. Using request-specific data (cookies, headers, uncached fetch, search params in some modes) forces dynamic rendering for that segment. Pure data with revalidation can be static or ISR-like. When a page "always hits the server" in production, search for those dynamic signals before blaming the host.

Practical debugging questions when a page is slow or stale:

  1. Is this segment static, ISR, or dynamic?
  2. What tag / time revalidates the data?
  3. Am I looking at CDN HTML, server render, or client router cache?

7. Turbopack and the build toolchain

Turbopack is Next's Rust-based bundler (Webpack successor path). Dev HMR and production builds increasingly default to it in current Next majors. For you as a reader of application code:

  • You rarely configure Turbopack day to day; you notice it when builds are fast or when a plugin is Webpack-only and breaks under Turbopack.
  • Next.js mid-2026 line (e.g. 16.x family announcements) emphasized faster navigation and experimental / expanding React Compiler integration — align local docs with the repo's locked Next version.
  • Pin framework versions in production; read security and canary notes before jumping majors (monthly security cadence culture in the Next ecosystem after the RSC CVE wave).

Related: the React Compiler (paradigm doc §18.1) can run in Next pipelines so client components need less hand-written useMemo / useCallback. Treat compiler upgrades like React upgrades — exact versions, full test runs.

8. Navigation, streaming, and UX primitives

  • <Link> — client navigation with prefetch of static routes.
  • useRouter / usePathname / useSearchParams — client-only navigation APIs ("use client").
  • Streaming — Server Components can stream HTML/RSC payload; loading.tsx and Suspense define what the user sees while a slow subtree resolves.
  • Instant / optimistic navigation trends — modern Next versions invest in making route transitions feel SPA-fast while keeping server rendering benefits. When you see "navigation is instant but data pops in later," that is streaming + shell layouts, not a bug by default.

React 19.2 pieces you may meet inside Next apps (paradigm doc §18.6): useEffectEvent, <Activity> — framework and React versions must both support them.

9. Auth, env, and security (frontend-adjacent)

  • process.env.NEXT_PUBLIC_* — inlined into the client bundle. Anything secret must be server-only env without that prefix.
  • Server Actions and Route Handlers = attack surface. Validate like public APIs. Auth checks on the server, not only hidden UI.
  • After the Dec 2025 – Jan 2026 RSC protocol CVEs, production teams pin React/Next, subscribe to security advisories, and schedule patches. Do not invent your own RSC serializer.

10. AI readiness (product features, not hype)

Next is a common host for AI product UI because streaming and server boundaries fit LLM apps:

  • Streaming responses from Route Handlers or Server Actions into client components (chat tokens).
  • Server-only keys for model providers — never NEXT_PUBLIC_ for API secrets.
  • Vercel AI SDK (and similar) patterns: useChat-style client hooks + server route that calls the model. The React side is still hooks and closures; the new piece is async streams.
  • RSC for tool results — render model-produced structured UI on the server when you do not need client interactivity for that subtree.

If you are building AI features into an app in this workspace's broader skill ecosystem, prefer a deliberate provider choice and keep secrets server-side. The frontend skill remains: render loading/error/partial states without stale closures.

11. What you will actually read at work — a checklist

  1. Is this pages/ or app/?
  2. Does the file start with "use client"? If no, assume server; look for hooks — if hooks exist without the directive, something is wrong or you are not in App Router.
  3. Where does data come from — fetch, db, props from a parent server component, or a client-side React Query call?
  4. Is there a Server Action on this form?
  5. Which layout owns the chrome, and will its state survive this navigation?
  6. Is the bug a React box-model bug (client) or a cache/dynamic-rendering bug (Next)?
// Decision sketch when debugging "UI shows old data"
// 1) Client state? → box model, deps, React Query keys
// 2) Server Component props? → revalidate / cache tags / dynamic APIs
// 3) Router cache? → refresh / hard navigation test
// 4) CDN? → deployment / purge / ISR window

What this doc covers

Next.js is React plus routing, server/client split, caching, and tooling. App Router defaults to Server Components; "use client" marks the boundary where your hooks mental model applies. Caching and dynamic APIs explain many "why is this static/dynamic?" mysteries. Turbopack and the React Compiler are toolchain layers. AI features are mostly streaming + server secrets + normal React UI. Security: Server Actions are public endpoints.
