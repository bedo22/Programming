Reference · Meta-framework on top of React

Next.js deep dive

RSC, App Router, caching, Turbopack, and AI-era patterns — tied back to the function+hooks model. Read this after the paradigm doc, before assuming every React file is a client component.

Why this doc exists

After Create React App was sunset (Feb 2025), React's own docs steer new apps toward a framework. In job postings and greenfield React work, that framework is often Next.js (Vercel). This doc is not a tutorial that replaces nextjs.org — it is a map for a C++-background JS learner who already understands functions, closures, and hooks, and needs to read Next code without drowning.

Prerequisites in this workspace: class-to-hooks paradigm shift (especially §18.2 RSC and §18.1 compiler), and the re-render box rule in class-to-hooks paradigm shift §7. Landscape context: frontend camps survey §5. The post-hooks platform details (React 19, compiler, RSC security) live in React 2024+; this doc is the framework layer on top.

Reading order: class-to-hooks → React 2024+ (compiler, RSC, foundation) → this guide → frontend camps survey (the wider camp map). 1. Definition — what Next.js is (and is not)

Is: a React meta-framework — routing, rendering strategies, data fetching conventions, bundling, and production optimizations around React.

Is not: a replacement for React's component model. Client components still use the same hooks, closures, and per-render boxes you already studied. Next decides where code runs and how routes load data; React still decides how UI updates from state.

Layer Who owns it Your mental model
UI update from state React Function+hooks, box model
URL → tree of components Next App Router Filesystem routes under app/
Server vs browser process RSC + "use client" Two Reacts (data vs state)
Caching / revalidation Next cache model HTTP + framework cache semantics
Bundling / HMR / prod build Turbopack / Webpack Tooling — rarely hand-edited

The rule of this whole doc: whose job is this? Routing, data, caching, bundling = Next. State-driven UI updates = React. Keep the two from blurring and most of Next's apparent strangeness disappears.

1b. History — the 10-year line

Next's features are answers to specific problems that appeared in order. Knowing the line makes the App Router's design positions legible (why file conventions? see 2022).

Year Milestone What shifted
2016 Next.js 1.0 (Vercel; Guillermo Rauch, Arunoda Susiripala) SSR for React without custom server. Pages Router.
2020 Next.js 9.3 — getStaticProps / getServerSideProps Data fetching became explicit methods, not implicit SSR assumptions.
2020 Incremental Static Regeneration (ISR) Static pages revalidate in the background. The static/dynamic line blurred on purpose.
2022 Next.js 13 — App Router (beta) app/ dir, React Server Components, nested layouts, streaming.
2023 Next.js 14 — App Router stable, Server Actions stable "use server", form actions, parallel + intercepting routes.
2024 Next.js 15 — React 19 support, Turbopack dev stable, next.config.ts Request APIs (cookies(), headers()) became async; use cache direction appears.
2025–26 Cache Components, Partial Prerendering, React Compiler integration Caching became explicit and compositional; static shell + dynamic holes; compiler-first client optimization.

1c. Evolution — constraint inversions

Every discipline on this shelf rides constraint inversions — a constraint changes and the old approach stops being sufficient. Next is unusually dense with them:

Inversion Before After What changed
Static → dynamic Pre-rendered HTML at build time Server-rendered per request (SSR) Content became personalized / real-time; build-time rendering couldn't keep up.
SSR → streaming Full HTML sent after all data loads Shell sent immediately, data streams in via Suspense Users perceived long waits; the shell lets the slow parts arrive later.
Full hydration → partial hydration Entire React tree hydrated in the browser Only interactive islands hydrate; server components ship zero JS Bundle size became the bottleneck; RSC removes JS for non-interactive UI.
Webpack → Turbopack JS-based bundler Rust-based bundler Build speed became a developer-experience bottleneck.
Implicit caching → explicit caching Framework cached fetch() by default (confusing) use cache, cacheLife, cacheTag, Cache Components Developers couldn't reason about what was cached; explicit beats implicit.
CRA default → framework default create-react-app as starting point React docs recommend frameworks (Next, React Router, Expo) Client-only SPAs hit SEO, performance, and data-fetching walls (§7 in React 2024+).

1e. Underlying theory — the models Next builds on

Next didn't invent these; it productized them. When a Next behavior is confusing, one of these is usually underneath.

Theory Origin What Next takes from it
React Server Components Dan Abramov, "The Two Reacts" (2024) UI = f(data) on the server, UI = f(state) on the client — two processes, one mental model (React 2024+ §2).
React Fiber / reconciliation React 16+ (2017) Streaming SSR, Suspense, concurrent rendering — the scheduler that lets Next interleave rendering and data.
HTTP caching semantics RFC 9111 — Cache-Control, ETag, stale-while-revalidate Next's caching layers build on HTTP cache primitives; revalidate is stale-while-revalidate in framework form.
Streaming HTML / chunked transfer HTTP/1.1 chunked encoding, HTTP/2 frames Next sends the shell first, then streams Suspense boundaries — chunked HTML delivery.
Islands architecture Jason Miller (Preact), 2019; see React 2024+ §9 Hydrate only interactive parts; Next's RSC + Client Components is a superset of this idea.

1f. Mental models — six that cover 90% of Next reading

Model Core idea When you reach for it What it replaces
"Which React am I in?" Every file is a Server Component (no hooks, runs on server) or a Client Component (hooks, runs in browser). Ask first. Reading any file in app/. Assuming everything is client-side React.
"Static or dynamic?" A route is static unless it uses dynamic APIs (cookies(), headers(), searchParams, uncached fetch). Debugging "why does this page hit the server every time?" Guessing. Search for dynamic signals before blaming the host.
"Where does this code run?" Server components can use DB/fs/secrets; client components can use window/DOM/hooks. Deciding whether to add "use client". Putting everything in client components "to be safe."
"Which cache layer?" Four layers — request memoization, data cache, full route cache, router cache — each with different lifetime and invalidation. Debugging stale data or unexpected server hits. Assuming just one cache. There are four.
"Hydration or not?" Server components ship zero JS; client components hydrate. The boundary is "use client". Optimizing bundle size; understanding why a component never re-renders. Assuming all components hydrate.
"The tree decides, not the file" A file without "use client" is a Server Component unless a client component imports it — then it joins the client bundle from that point down. Debugging "why is my server-only import leaking to the client?" Thinking "use client" is per-file. It is per-tree from there down.

2. Pages Router vs App Router

Next had two successive routing systems. You will meet both in the wild.

Pages Router (pages/) App Router (app/)
Era Classic Next (widely deployed) Current default for new apps
Data APIs getServerSideProps, getStaticProps async Server Components, fetch cache, server actions
Layouts Custom _app / nested HOCs Nested layout.tsx that preserve state
RSC No (client React tree after data props) Yes — server components by default
File conventions pages/about.js → /about app/about/page.tsx → /about

Reading tip: if you see getServerSideProps, you are in Pages Router. If you see async function Page() at the top of a route file with no "use client", you are in App Router Server Components. Do not mix the mental models.

3. App Router file conventions (the vocabulary)

Under app/, filenames are special:

  • page.tsx — the UI for a route segment (required for that URL to exist).
  • layout.tsx — wraps pages; does not remount on navigation between child routes (state in a layout survives).
  • loading.tsx — Suspense fallback for the segment while server content loads.
  • error.tsx — error boundary for the segment (must be a client component).
  • not-found.tsx — 404 UI for the segment.
  • route.ts — HTTP handlers (REST-style endpoints) instead of a page.
  • template.tsx — like layout but remounts on navigation (rarer).
  • default.tsx — parallel route fallbacks (advanced).
app/
  layout.tsx          // root shell (html/body, nav)
  page.tsx            // /
  blog/
    layout.tsx        // wraps all /blog/*
    page.tsx          // /blog
    [slug]/
      page.tsx        // /blog/:slug  (dynamic)
      loading.tsx

Dynamic segments: [id], catch-alls [...slug], optional catch-alls [[...slug]]. Route groups (marketing) organize folders without affecting the URL. Parallel routes (@slot folders) render multiple segments in one layout; intercepting routes show a modal/overlay while the URL still points at the real page. Know they exist as vocabulary — you'll meet them by name before you meet them in code. The general question of what a folder tree is for (feature folders, colocation, monorepo layouts) lives in System Design §Codebase architecture.

4. Server Components vs Client Components

This is the load-bearing idea. Default in app/: Server Component. You opt into the browser with the directive: 

// app/counter.tsx — must run in the browser (hooks, events, window)
"use client";

import { useState } from "react";

export function Counter() {
  const [n, setN] = useState(0);           // box model applies here
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}

// app/posts/page.tsx — Server Component (default). No hooks. Can use secrets/fs/db.
import { Counter } from "../counter";
import { db } from "@/lib/db";

export default async function PostsPage() {
  const posts = await db.post.findMany();  // runs on the server
  return (
    <main>
      <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>
      <Counter />                          // client island inside server page
    </main>
  );
}

Rules that prevent confusion

  1. Server Components cannot use hooks or browser APIs. No useState, no useEffect, no window. They render once per request (or at build time) — there is no re-render loop.
  2. Client Components cannot import server-only modules (db clients, private env without NEXT_PUBLIC_). Data flows server → client as props (serializable).
  3. Composition direction: server can render client children. Client can render server children only via patterns like passing server components as children or slots — not by importing a server file into a client file.
  4. Everything your paradigm doc taught still applies on the client side of the line. RSC does not replace hooks; it shrinks how much of the tree needs them.
  5. The boundary is a tree property, not a file property. Once a client component imports a module, that subtree compiles into the client bundle — even files that never wrote "use client" (mental model §1f).

Dan Abramov's formula (React 2024+ §2): client is UI = f(state); server is UI = f(data); together UI = f(data, state). When reading a file, ask first: which function am I in?

5. Data fetching patterns

5.1 async Server Components + fetch

In App Router, fetch is integrated with Next's cache (behavior has evolved across versions — always check the version of the app you are reading). Typical shape: 

async function getUser(id) {
  const res = await fetch(`https://api.example.com/users/${id}`, {
    next: { revalidate: 60 },   // ISR-style: revalidate every 60s
  });
  if (!res.ok) throw new Error("Failed");
  return res.json();
}

5.2 Direct backend access

Server Components can call databases, file systems, and internal services directly — no need to expose a public REST route for your own page data. That is a major reason RSC exists: colocate data and UI without shipping the query client to the browser.

5.3 Server Actions

Functions marked with "use server" can be passed to client components as callbacks (e.g. form action). They run on the server when invoked. Treat them as public endpoints — validate inputs, auth, and never hardcode secrets (see React 2024+ §5 for the Dec 2025–Jan 2026 RSC CVE wave). 

// app/actions.ts
"use server";

export async function updateTitle(formData) {
  const title = formData.get("title");
  // validate + auth + db write
}

5.4 Route Handlers (route.ts)

route.ts is the App Router equivalent of API routes. They support every HTTP method, read request bodies, set cookies, and can stream responses. Reach for them when you need an endpoint others (browsers, webhooks, external services) call — not for your own page data, which Server Components fetch directly (§5.2). 

// app/webhooks/stripe/route.ts — a Route Handler
export async function POST(request: Request) {
  const payload = await request.json();
  // verify signature, do side effects
  return Response.json({ ok: true });
}

6. Caching mental model — including Cache Components

Next's cache story is the part that confuses experienced SPA developers most. Rough layers:

  • Request memoization — duplicate fetch calls during one server render can dedupe.
  • Data cache — persisted results across requests (with revalidation tags / time).
  • Full route cache — static HTML/RSC payload for a route when it can be produced ahead of time.
  • Router cache (client) — client-side session cache of visited segments for snappy back/forward.

6.1 Dynamic APIs — what flips a segment from static to dynamic

These are the dynamic signals the mental model table (§1f) told you to hunt. Using any of them forces dynamic rendering for that segment:

Dynamic API Effect
cookies(), headers() Read request-specific data → segment becomes dynamic
Uncached fetch No cache entry to reuse → data fetched per request
searchParams Depends on the incoming URL → dynamic in common modes
export const dynamic = "force-dynamic" Explicit opt-out of static generation

Static vs dynamic is a tree property. Using request-specific data forces dynamic rendering for that segment. When a page "always hits the server" in production, search for those dynamic signals before blaming the host. When debugging stale data, the question is not "is Next broken" but "which of the four layers is serving me?"

6.2 Cache Components — the direction of modern Next

Cache Components (the direction of modern Next): make caching explicit and compositional — mark which parts of the tree are cacheable static shells vs dynamic holes, instead of hoping global defaults match your intent. The stable namespace across versions:

  • use cache — mark a function or component output as cacheable; the replacement for relying on implicit fetch() caching.
  • cacheLife — how long cached data lives (seconds, minutes, hours, days profiles).
  • cacheTag — label cached data so you can invalidate by tag after a mutation — revalidateTag("products").

These make caching explicit, compositional, and debuggable. Read the project's Next major-version docs for the exact shape — the API evolved (e.g. revalidate/tags on fetch vs the directive forms above), and the version you're reading wins.

Practical debugging questions when a route is slow or stale:

  1. Is this segment static, ISR, or dynamic?
  2. What tag / time revalidates the data?
  3. Am I looking at CDN HTML, server render, or client router cache?

7. Middleware, next/image, next/font, and metadata

7.1 Middleware (middleware.ts)

Runs before every request at the edge. It can rewrite URLs, redirect, set headers, check auth, and shape the request/response. It runs in the Edge Runtime — no Node.js APIs, no filesystem, no database access. Use it for auth guards, locale detection, and request shaping. Do not put business logic in middleware — that belongs in Server Actions or Route Handlers.

7.2 next/image — replace <img>

next/image gives lazy loading, responsive sizing, format conversion (WebP/AVIF), and blur placeholders out of the box. It needs width/height (or fill) to reserve space and avoid layout shift — a core-web-vitals friend. Remote images require the host allowlisted in next.config.ts.

7.3 next/font

Self-hosts fonts at build time, eliminating external font <link> requests and preventing FOIT/FOUT. Replaces the classic Google Fonts <link> tag with a build-time import.

7.4 Metadata and SEO

generateMetadata in Server Components produces <title>, <meta>, Open Graph, and JSON-LD. Static metadata extracts at build time; dynamic runs per request. This is how RSC pages stay SEO-friendly without a separate headless-CMS rendering layer.

8. Turbopack and the build toolchain

Turbopack is Next's Rust-based bundler (Webpack predecessor path). Dev HMR and production builds increasingly default to it in current Next majors. For you as a reader of application code:

  • You rarely configure Turbopack day to day; you notice it when builds are fast or when a plugin is Webpack-only and breaks under Turbopack.
  • Next.js mid-2026 line (e.g. 16.x-family announcements) emphasized faster navigation and experimental / expanding React Compiler integration — align local docs with the repo's locked Next version.
  • Pin framework versions in production; read security and canary notes before jumping majors (monthly security cadence culture in the Next ecosystem after the RSC CVE wave — see React 2024+ §5).

Related: the React Compiler (React 2024+ §3) can run in Next pipelines so client components need less hand-written useMemo / useCallback. Treat compiler upgrades like React upgrades — exact versions, full test runs.

9. Navigation, streaming, and UX primitives

  • <Link> — client navigation with prefetch of static routes.
  • useRouter / usePathname / useSearchParams — client-only navigation APIs ("use client").
  • Streaming — Server Components can stream HTML/RSC payload; loading.tsx and Suspense define what the user sees while a slow subtree resolves.
  • Instant / optimistic navigation trends — modern Next versions invest in making route transitions feel SPA-fast while keeping server rendering benefits. When you see "navigation is instant but data pops in later," that is streaming + shell layouts — not a bug by default.
  • Partial Prerendering (PPR) — pre-render the static shell ahead of time at build, stream only the dynamic holes per request (React 2024+ §4.6). Same "shell + Suspense" shape you already know, now precomputed.

React 19.2 pieces you may meet inside Next apps (React 2024+ §7): useEffectEvent, <Activity> — framework and React versions must both support them.

10. Auth, env, and security (frontend-adjacent)

  • process.env.NEXT_PUBLIC_* — inlined into the client bundle. Anything secret must be server-only env without that prefix.
  • Server Actions and Route Handlers = attack surface. Validate like public APIs. Auth checks on the server, not only hidden UI.
  • After the Dec 2025 – Jan 2026 RSC protocol CVEs, production teams pin React/Next, subscribe to security advisories, and schedule patches. Do not invent your own RSC serializer.

10.1 Security specifics worth naming

Concern What to do
CSRF for Server Actions Built-in (Origin checking) for Server Actions; custom Route Handlers need manual CSRF tokens if they accept cookies from browsers.
Server code leaking to client Install server-only package; mark modules that must never cross the boundary. Importing them client-side becomes a build error.
XSS surface Content-Security-Policy headers (set in next.config.ts headers or middleware).
Secrets Never hardcode; env vars / secrets manager only (§5.3).

11. AI readiness — product features, not hype

Next is a common host for AI product UI because streaming and server boundaries fit LLM apps:

  • Streaming responses from Route Handlers or Server Actions into client components (chat tokens).
  • Server-only keys for model providers — never NEXT_PUBLIC_ for API secrets.
  • Vercel AI SDK (and similar) patterns: useChat-style client hooks + server route that calls the model. The React side is still hooks and closures; the new piece is async streams.
  • RSC for tool results — render model-produced structured UI on the server when you do not need client interactivity for that subtree.

If you are building AI features into an app, prefer a deliberate provider choice and keep secrets server-side. The frontend skill remains: render loading/error/partial states without stale closures.

You deploy a Next app, not a pile of React components. The build artifact (next build) is the unit of truth.

13. Testing in Next.js

Testing has to respect the server/client split:

  • Server Components — integration tests: call the component with data, assert HTML output. next/jest config handles the RSC/client boundary.
  • Client Components — React Testing Library as usual (§4 box model).
  • Server Actions / Route Handlers — call the functions directly with mock formData/requests; assert validation + auth + side effect.
  • Full flow — Playwright / Cypress end-to-end.

14. Worked example — a product page with reviews and streaming

Everything above, walked through one realistic route. A product detail page with reviews, an add-to-cart button, and streaming. 

app/products/[id]/
  layout.tsx                     // product chrome, shared across child routes
  page.tsx                       // server component — fetch product, stream reviews
  loading.tsx                    // shell while the server renders
  error.tsx                      // boundary for the product subtree

The file tree: layout.tsx (chrome), page.tsx (server data + generateMetadata), loading.tsx (shell fallback), error.tsx (boundary), a Reviews.tsx server component wrapped in <Suspense>, and an AddToCart.tsx client leaf. 

// app/products/[id]/page.tsx
import { Suspense } from "react";
import { Reviews } from "./Reviews";
import { AddToCart } from "./AddToCart";

export async function Page({ params }) {
  const product = await getProduct(params.id);      // cacheable, revalidate 60 (§6.2)
  return (
    <main>
      <ProductData product={product} />
      <AddToCart productId={product.id} />          // client leaf — the only island
      <Suspense fallback={<Skeleton />}>
        <Reviews productId={product.id} />          // async server comp — streams in
      </Suspense>
    </main>
  );
}

export function generateMetadata({ params }) { ... }  // SEO from product data

The reading order: shell and product data ship first (revalidate: 60, static), reviews stream separately (dynamic — per-user), the add-to-cart button is the only client island (hooks), and generateMetadata derives the SEO block. A cache miss or a forced dynamic anywhere in that chain changes what the user sees — and that's the next section.

15. Failure modes

Failure mode What it looks like Why it happens Fix
"use client" sprawl One directive at the root layout; entire app hydrates Added to fix a hook error, then left in place Push the boundary to the leaf that needs state (§4).
Waterfall fetching Page takes seconds because fetches chain await in parent, then child, then grandchild Promise.all at the top; stream independent sections (§9).
Accidental dynamic rendering Should-be-static page hits the server every request cookies()/headers()/searchParams in a static-minded segment Find the dynamic signal; force-static or use cache deliberately.
Over-caching / stale data Old data after a mutation Caching too aggressive; no invalidation on write revalidateTag after mutations; explicit cacheLife.
Hydration mismatch "Text content does not match" Client vs server rendered different output (Date.now(), Math.random()) Run-time browser-only values in useEffect; suppressHydrationWarning rarely.
Unvalidated Server Action Bad form data reaches the DB Trusting formData at the endpoint Schema-validate (Zod) + auth inside every action (§5.3).
Server code in client bundle fs/db import throws client-side Server component pulled below the client boundary server-only guard; keep server above the line (§1f, §10).
Layout state confusion State in layout.tsx resets — or doesn't — when expected Layouts persist across navigations; pages remount Navigation-specific state to page.tsx; use template.tsx for remounting.
Middleware doing business logic Edge code becomes untestable controller layer Middleware treated as the controller Middleware = auth, redirects, headers; logic in Actions/Handlers (§7.1).

16. Principles

Principle Meaning
Server by default; client only when needed Every app/ file is a Server Component without "use client". This is the framework's strongest opinion.
Data lives where it is used Server Components fetch directly; don't build a REST endpoint to feed your own page (§5.2).
Caching is explicit, not magic revalidate/use cache/cacheTag, not hope. Debug by layer (§6).
The boundary is a line, not a gradient "use client" draws a hard line below which everything compiles client-side (§1f mental model, "the tree decides").
Streaming is the default rendering shape Shell first, Suspense boundaries define progressive disclosure (§9).
Server Actions are public endpoints Validate, authorize, rate-limit, audit — treat exactly like API routes (§5.3, React 2024+ §5).
The app is the deployment unit You ship a built Next app, not a set of components (§12).

19. What you will actually read at work — the checklist

Is this pages/ or app/? Check the folder; the data APIs are different (§2).

What this doc covers

Next.js is React plus routing, server/client split, caching, and tooling. App Router defaults to Server Components; "use client" marks the boundary where your hooks mental model applies. Caching and dynamic APIs explain many "why is this static/dynamic?" questions. Turbopack and the React Compiler are toolchain layers.
