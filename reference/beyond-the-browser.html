Definition — the platform bridge problem

The browser is a sandbox with three specific models: a rendering model (DOM + CSS), a security model (same-origin, sandboxed), and a distribution model (URLs, no install). Every platform outside the browser changes at least one of these — and the tool that carries your JavaScript across the boundary is the bridge. The whole outside-the-browser world is a spectrum of how far from the browser you go, and what you trade:

DimensionWebReact NativeElectronNative
RenderingDOM + CSSNative UI componentsDOM + CSS (Chromium)Platform UI toolkit
DistributionURL, no installApp Store / Play StoreInstaller / auto-updateApp Store / Play Store
SecuritySame-origin, sandboxedOS permissionsNode.js access + ChromiumOS permissions
Update modelInstant (deploy)App-store review (days)Instant (auto-update)App-store review
OfflineLimited (Service Worker)Full (native storage)Full (local filesystem)Full
Hardware accessLimited (Web APIs)Full (native modules)Full (Node.js)Full

The core vocabulary: a bridge is the mechanism that lets JS talk to a native platform. React Native bridges JS to native UI components; Electron bridges JS to Chromium plus Node; Capacitor bridges a web app to a native shell. Where the bridge is heavy (serialization, async, version churn), performance and correctness suffer — which is why each ecosystem's history is largely the history of making its bridge thinner.

The decision matrix — when to use what

Every platform decision reduces to one question: "Does the user need to INSTALL this, and does it need NATIVE capabilities?"

Your situationBest choiceWhy
Content site, marketing, blog, docsWeb (Next.js/Astro)SEO, instant updates, no install friction
Internal tool, dashboard, admin panelWeb (React SPA)No distribution needed, fast iteration
App that's 90% web content + 10% native featuresPWA or CapacitorWeb code + native shell for the 10%
Consumer app needing native feel (camera, GPS, push, offline)React NativeNative UI + JS developer velocity
Desktop app (VS Code, Slack, Discord, Figma)Electron (or Tauri)Web UI + filesystem/system access
Living-room / 10-foot app, streaming, set-top UXTizen / webOSThe only way onto ~300M TVs; it's a web app anyway
Casual game targeting the biggest app store in ChinaMini-game (Cocos/Laya) or web engineDOM-less JS sandbox, instant play, social distribution
Performance-critical, platform-specific UX, large teamNative (Kotlin/Swift)Maximum performance, platform fidelity
Game, AR/VR, heavy GPUNative or Unity/UnrealReact Native/Electron can't compete
Prototype / MVP to validate an ideaWeb or Expo (React Native)Fastest path to users

The four-way short version: no install, no native → web. Install + native + JS team → React Native. Install + desktop + JS team → Electron/Tauri. Install + maximum fidelity + native team → Kotlin/Swift. Everything else is a middle-ground variant of one of those.

React Native — the mobile bridge

How your React code becomes a native app

React Native keeps your React mental model — components, props, state, hooks — but replaces what you render into. Web React renders DOM elements; React Native renders native iOS/Android views. The mechanism connecting the two has been the story of the framework's performance:

OLD ARCHITECTURE (pre-2022) — the bridge was the bottleneck:
  JavaScript thread → JSON bridge (async, batched) → Native thread
  (React)            (serialized messages)            (UIKit/Android views)
      Every JS↔native call serialized to JSON and batched → frame drops
      during animations. This was the famous "bridge problem."

NEW ARCHITECTURE (2022+, default since 0.76):
  JavaScript thread → JSI (JavaScript Interface) → Native thread
  (React)             (direct C++ references,      (Fabric renderer,
                       synchronous, no JSON)         TurboModules)
      JS holds direct references to C++ objects. No serialization.
      Synchronous calls. The architectural cousin of React's own move
      from reconciliation to Fiber — remove the serialization layer.

The details you'll hear named: JSI (the direct-reference interface replacing the bridge), Fabric (the new renderer that commits UI on the native thread), and TurboModules (lazily-loaded native modules). For reading code and debugging, know the names; the architecture that matters is "synchronous, no JSON, direct references."

What transfers from your React knowledge — and what doesn't

Web ReactReact Native
Renders to DOM (<div>, <span>)Renders to native components (<View>, <Text>, <Image>)
CSS for stylingStyleSheet (flexbox-based, no selectors, no cascade)
Browser handles navigationYou handle it (React Navigation, Expo Router)
Browser handles scroll<ScrollView>, <FlatList>, <SectionList>
onClick, onChangeonPress, onLongPress, gesture handlers
Service Worker for offlineAsyncStorage, SQLite, native filesystem
URL routingStack/Tab/Drawer navigation (no URLs by default)

What transfers completely: components, props, state, hooks (useState, useEffect, useRef), context, reducers, composition, the re-render model, stale closures, dependency arrays. The Model → View → Flow rhythm is identical — the platform around it changed. What disappears: DOM APIs (document, window), CSS, browser storage, and the assumption that "the browser renders my HTML." The OS renders native views now.

Navigation — the biggest web→mobile mental shift

Web:    /home → /product/123 → /checkout        (URLs are state)
Mobile: HomeStack → ProductScreen(id: 123) → CheckoutScreen
        (the navigation STACK is state; there are no URLs by default)
  • Stack navigation — push/pop screens (a stack of cards).
  • Tab navigation — bottom tabs, each with its own stack.
  • Drawer navigation — side menu.
  • Deep linking — mapping URLs to screens, for push notifications and external links.

Libraries: React Navigation (community standard) and Expo Router (file-based, deliberately Next.js-like — app/(tabs)/index.tsx ↔ app/page.tsx). This is the single biggest re-learning cost for a web React developer, so budget for it.

Native modules — when JS isn't enough

When you need hardware access (camera, Bluetooth, biometrics, NFC) or platform-specific APIs: Expo modules cover ~90% of cases and are maintained by the Expo team; community modules (react-native-camera, react-native-maps) cover more; custom native modules are where you write Kotlin/Swift and expose it to JS via JSI — the one place you need real native literacy. Everything else stays in TypeScript.

Android & iOS platform literacy — the minimum to ship and debug

You don't become an Android developer. You learn what Android and iOS impose on an app, because those constraints shape every RN decision:

ConceptWhat it means for your RN app
APK / AABAPK = direct install; AAB = Play Store format. Expo builds these for you.
PermissionsCamera, location, storage, notifications — user grants at runtime. Declared in AndroidManifest.xml, requested via RN APIs.
Play Store reviewUsually 1–7 days. Unlike web deploys, you can't push instantly — plan releases.
App signingYou sign with a keystore. Lose the keystore = lose the ability to update. Back it up.
IntentsAndroid's inter-app communication: deep links, sharing, opening files. RN's Linking API handles most.
Activity lifecycleAndroid can kill your app in the background. Don't assume JS is running. Use background tasks / push.
Back buttonAndroid has a system back button. Your navigation must handle it. iOS doesn't have one.
FragmentationThousands of device sizes, Android versions, manufacturers. Test on real devices, not just emulators.

iOS, briefly: the IPA package, stricter App Store review (1–3 days, policy rejections; TestFlight gives you a closed-beta channel before that review), Apple's signing system (provisioning profiles & certificates — Expo handles it), stricter background execution (push is the primary reach), the swipe-back gesture instead of a back button, and Apple's Human Interface Guidelines (tab bars at bottom, navigation bars at top). You should also know the build chain Expo abstracts: JS/TS → Metro bundler → native project → Gradle (Android) or Xcode (iOS) → store → review → install. EAS Build (Expo's cloud build) and Fastlane automate the Gradle/Xcode → store half of that chain — the full CI/CD story is Version Control & CI/CD territory.

Accessibility is native, not optional. Web a11y semantics transfer, but the hooks differ: RN exposes accessibilityLabel, accessibilityRole, and accessibilityState on components, read by VoiceOver (iOS) and TalkBack (Android) — the native equivalents of aria labels and roles. Test on a real device with a screen reader, the same way you'd check the web with NVDA. UI/UX & Web Design owns the design-side discipline; on TV, the a11y shape is remote-driven focus, which the Smart TV section covers.

Crash reporting is your other test suite. Errors on a phone arrive as two kinds: JS exceptions and native crashes. Sentry or Crashlytics catches both — upload the Metro source maps so JS errors surface as readable stack traces, and let the tool symbolicate the native crash report (iOS/Android) back to a function-and-line stack. Wire it in before launch; it's the difference between "users reported a bug" and a stack trace in your inbox.

Electron & Tauri — the desktop bridge

Architecture: two processes and a pipe between them

Electron is the desktop host for exactly one reason: it lets you ship a web app as a native desktop application, reusing all your React/CSS/browser knowledge. It does this by running Chromium (rendering) and Node.js (system access) in one app, split across two processes:

┌─────────────────────────────────────────────────────────────┐
│                      Electron App                            │
│                                                              │
│  ┌──────────────────┐        IPC          ┌────────────────┐ │
│  │   MAIN PROCESS   │  (ipcMain/ipcRenderer) │ RENDERER      │ │
│  │     (Node.js)    │ ◄──────────────────► │   (Chromium)   │ │
│  │                  │                      │                │ │
│  │ • filesystem     │                      │ • your React   │ │
│  │ • OS APIs        │                      │   app (DOM+CSS)│ │
│  │ • menus / tray   │                      │ • sandboxed by  │ │
│  │ • notifications  │                      │   default (12+) │ │
│  └──────────────────┘                      └────────────────┘ │
│   "owns the OS"         bridge = IPC calls    "owns the UI"    │
└─────────────────────────────────────────────────────────────┘

What transfers from web React: everything. Your React app runs in Chromium — DOM, CSS, browser APIs, all present. It's literally a browser tab with extra OS access layered on top. What's different: full filesystem access (via the main process), installer distribution (.exe/.dmg/.AppImage), auto-update via electron-updater, system tray + global shortcuts + native notifications, and a security model where nodeIntegration must be kept off in the renderer and OS access goes through IPC.

The Electron problem: bundle size

Electron ships Chromium (~150MB) + Node.js (~30MB) with every app. That's why VS Code installs at ~100MB and Slack at ~200MB. The alternatives exist because of this:

ToolApproachBundle sizeTrade-off
ElectronChromium + Node.js~150MB+Full compatibility, huge ecosystem (VS Code, Slack, Discord, Figma)
TauriSystem WebView + Rust backend~3–10MBMuch smaller, but the WebView varies by OS
WailsSystem WebView + Go backend~5–10MBGo backend, smaller than Electron
NeutralinoSystem WebView + lightweight backend~2–5MBEven smaller, less mature
PWABrowser-based, installable0 (reuses existing browser)Limited OS access

The decision: Electron when you need maximum compatibility and ecosystem; Tauri when bundle size matters and you can tolerate WebView inconsistencies. Both give your React app a filesystem and a system tray.

PWA and Capacitor — the middle ground

PWA (Progressive Web App) — your web app made installable, with no app store. Service Worker (offline + push), Web App Manifest (install prompt, icon, splash screen), and web APIs for camera/GPS (limited vs native). When it wins: content apps, e-commerce, internal tools — anywhere you want "installable" without store review. When it loses: heavy native integration, background processing, store discovery.

Capacitor (Ionic team) — your web app wrapped in a native shell. WebView renders your React app; native plugins provide camera, push, biometrics, filesystem; one codebase → iOS + Android + Web. When it wins: you already have a web app and need a mobile version with some native features (90% web, 10% native). When it loses: you need native-feeling UI — WebView rendering doesn't match native animation/gesture smoothness.

The relationship: PWA gets you "installable" with zero shell; Capacitor gets you the native shell; React Native gets you native UI. Choose the thinnest bridge that satisfies the decision matrix.

Smart TV — Tizen & webOS, the hidden ~300M screens

The biggest outside-the-browser market most developers never think about: every Samsung TV since 2015 runs Tizen, every LG TV runs webOS — together roughly 300M living-room screens — and both are web-app platforms. Your app is HTML, CSS, and JavaScript running inside a Chromium-derived engine the TV ships with. A team that can build a web frontend can build the shell of a TV app.

But a TV is a constrained, purpose-built device, and the constraints are what make it its own platform:

RealityWhat it means
Fixed Chromium per model yearThe web engine is set at manufacturing time and never upgraded. 2022 TVs ≈ Chromium 94; 2025 ≈ 120; 2026 ≈ 126. A web API shipped in Chrome 110 fails silently on a 2022 TV. Feature-detect, never version-sniff.
Native media APIsTizen's AVPlay controls the hardware media pipeline (DRM, subtitles, audio tracks, 4K) beyond the plain <video> element. webOS extends the HTML5 media path.
DRM via EMEPlayReady + Widevine through Encrypted Media Extensions — never Apple's FairPlay (no Apple devices here). DRM client is baked into each TV's firmware; you can't upgrade it in the field.
Format realitywebOS natively supports HLS; DASH is not officially supported. Package once into CMAF and serve both.
Per-store certificationSamsung TV Seller Office and LG's store each certify separately, per model group — launch < 5s, back-key navigation works, no blank screens. Plan multiple fix rounds.
10-foot UXRemote-driven focus navigation, not pointer. webOS even pushes Enact — a React-based framework tuned for the living room.

For a React developer: your skills transfer directly (it's a web app in a Chromium shell). The new literacy is the media pipeline (AVPlay/EME), DRM licensing, and the device-fragmentation tax of model years. This is a genuine career lane for streaming apps — and most developers have never heard of it.

Gaming — the JS lane outside the browser

Yes, JavaScript escaped into gaming — but the shape of it surprises most developers. The big console lane (Unity C#, Unreal C++) is not JS. The real JS lane has two parts:

1. The mini-game sandbox. WeChat and TikTok host games that are not web pages: a DOM-less JavaScript environment with a canvas + WebGL (increasingly WebGPU) context, plus the host's APIs for storage, audio, networking, and the social/payment layer. No window, no document. Your first package is capped at ~4MB (assets download separately). Engines compile to this target: Cocos Creator, LayaAir, Egret (TypeScript/JS), with Cocos the default because its engine runtime is pre-installed in the WeChat client and doesn't count against your 4MB. Unity games reach it only via a WebGL→mini-game transform (or Unity China's Tuanjie engine, which treats it as a native target).

2. Browser engines that stay in the browser — but the skills travel. Phaser, PixiJS, Three.js, Babylon.js run in a browser tab (WebGL/canvas) and are technically still in the browser. They matter here because a Three.js game is structurally close to a mini-game — the gap is the adapter layer and the 4MB budget, not the rendering.

LaneLanguageRuns inWhen to choose it
Mini-game (Cocos/Laya/Egret)TypeScript/JSWeChat/TikTok sandbox, also native mobileCasual games for the largest game storefronts, JS team
Web engine (Phaser/Pixi/Three)JSBrowser tabInstant-play games from a URL; skills transfer to mini-games
Unity / UnrealC# / C++Everything, via export/WASMPerformance-heavy, 3D, cross-platform — not a JS lane

When a React developer touches this: your component/state/loop discipline transfers to game UI and to the game loop (update → render), but a game is a different architecture than a web app — a persistent render loop instead of a render-per-state-change. Start with a browser engine; it's the least wasted motion, and the mini-game port is an adapter + a budget exercise.

The native landscape — link, don't duplicate

You need to understand the native platforms your bridges target, but you don't need to learn to build in them. JavaScript Across Stacks §4 already carries the deep comparison tables for each native lane — Kotlin/Jetpack Compose (React Native compiles to native Android views; you write Kotlin only for custom native modules), Swift/SwiftUI (the iOS equivalent), and Dart/Flutter (Google's cross-platform alternative with its own renderer — you choose it for pixel-perfect cross-platform consistency, not native feel). If a native decision comes up, read that section; it is the authority, and this doc deliberately does not repeat it.
