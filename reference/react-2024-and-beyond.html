React 2024 and beyond — compiler, RSC, foundation

What changed in React after hooks settled: the React Compiler v1.0, React Server Components splitting rendering across computers, the React Foundation under the Linux Foundation, the RSC security lesson (CVE-2025/2026), why React didn't adopt signals, .5b Preact as the structural branch, and React 19.2's useEffectEvent and Activity. The class-to-hooks story is complete; this doc is what happened next.

How this relates to the main paradigm-shift doc

The class-to-hooks paradigm-shift reference ends at the compiler era (§12) and sends you here for the 2024+ details. Everything in this doc builds on the hooks mental model from that reference — client components still capture values per render, useState still works exactly as described there. The big news: the compiler is stable, RSC splits the process, and React is now foundation-governed.

1. The React Compiler is stable (Oct 2025) and ship-by-default (2026)

The React Compiler v1.0 shipped October 7, 2025 — the first stable release after nearly a decade of research (the team's Prepack experiments started in 2017). The compiler is a Babel plugin that lowers your code into its own High-Level Intermediate Representation, runs data-flow and mutability analysis, and inserts memoization where it helps — including in places where useMemo cannot legally go, like after an early return.

What changed in 2026: new apps now start with the compiler on by default. Expo SDK 54+ ships it enabled. Vite and Next.js create-* templates include it as an opt-in choice. The compiler also powers the lint rules in eslint-plugin-react-hooks's recommended preset — so even teams not ready to adopt the compiler get its validation. The rules encode the Rules of React and surface latent bugs (set-state-in-render, set-state-in-effect, unsafe ref access during render).

For you, reading code at work: useMemo, useCallback, and React.memo become escape hatches, not the default. New code written under the compiler can be the simple version from the main doc's "original function-component vision" — a plain function with hooks, no manual memoization, no wrapper components — because the compiler puts the optimization back. Existing code keeps working; you do not have to remove existing memoization to adopt the compiler.

One real lesson from the past year: do not pin the compiler to a SemVer range. The team recommends --save-exact (e.g. 1.0.0, not ^1.0.0) and manual upgrades with end-to-end testing. The compiler rewrites memoization, and in code that quietly breaks the Rules of React, a different memoization pattern can change which effects fire. Treat a compiler upgrade the way you'd treat a React major upgrade — read the changelog and run the suite.

2. React Server Components split rendering across two computers

The Class→Hooks arc was about how a component manages state inside one process. React Server Components (RSC) answered a different question: which process the component runs in — yours (the browser) or the server's. Dan Abramov framed it cleanly in The Two Reacts (Jan 2024):

  • Client components: UI = f(state). State lives in the browser, code runs in the browser, interactions are instant. Your Counter component from the paradigm-shift doc lives here.
  • Server components: UI = f(data). Data lives on the server, code runs on the server (at request time or build time), and the browser only receives the rendered UI — not the raw data, not the dependencies, not the bundler. PostPreview reads files with fs.readFile at build time and ships only the rendered HTML and a serialized payload to the client.

The combined formula is UI = f(data, state). The two components interleave freely: a server component can render a client component as a child; a client component can pass props into a server component via a callback slot. The mental extension is small: everything from the paradigm-shift doc still applies to client components, and server components are functions closer to the data — they don't have useState or useEffect because they don't have a render loop, they only render once.

RSC is not a new paradigm replacing hooks — it is the function+hooks model deciding where each function runs. Read it as: "client component" still means everything in the paradigm-shift doc; "server component" is a subset (no hooks, no events, no window) that buys you zero-bundle-size code and direct access to server-only APIs.

3. The React Foundation (Feb 2026): Meta is no longer the sole owner

On February 24, 2026, the React Foundation launched under the Linux Foundation. React, React Native, and JSX are no longer owned by Meta — they're owned by the foundation, governed by a board with eight Platinum founding members: Amazon, Callstack, Expo, Huawei, Meta, Microsoft, Software Mansion, and Vercel.

Why this matters for reading code at work: who funds React shapes what gets prioritized. When one company owns a framework, that company's internal needs shape the roadmap (this was the story of React 16-18 — Meta's newsfeed constraints drove features like concurrent rendering and Suspense). With eight companies on the board — including hyperscalers (Amazon, Microsoft) and major mobile players (Expo, Software Mansion) — the priorities broaden. Expect less single-company urgency and more ecosystem coordination: stable APIs for hosting vendors, clearer upgrade contracts for enterprises, and a slower, more deliberate release rhythm.

Technical governance stays independent of the board — the contributors set technical direction, the foundation manages assets and infrastructure. A provisional leadership council is determining the long-term structure. The next React Conf is being planned.

4. The security lesson: RSC changed what counts as a "trust boundary" (Dec 2025 – Jan 2026)

Server Functions and the RSC wire protocol gave attackers a new surface. In December 2025, a critical CVE (CVSS 10.0) allowed remote code execution through the RSC protocol. The fixes shipped, then researchers found follow-ups — a high-severity Denial of Service (CVE-2025-55184), a medium-severity source-code exposure (CVE-2025-55183), and a further DoS in January 2026 (CVE-2026-23864).

Three practical takeaways for production code:

  1. Treat any Server Function as a public endpoint. It runs on your server with your secrets. Validate inputs the way you'd validate a REST route. Don't accept the argument that "it's internal — only my client calls it."
  2. Never hardcode secrets in Server Function source. CVE-2025-55183 leaked source code through stringified arguments. process.env.SECRET was unaffected; const key = "sk_live_..." was. Use env vars.
  3. Pin React dependencies and read the blog. The Dec 2023 fixes shipped to 19.0.x, 19.1.x, and 19.2.x three times — the first patch was incomplete. This is now normal for critical CVEs in any framework; budget for it.

Next.js adopted a formal monthly security release cadence in July 2026, with advance notice before each patch drops. Treat framework security releases like OS updates — schedule them, don't let them drift.

5. The Signals question — and why React didn't adopt them

By 2026, every other major reactive framework standardized on Signals as the primary reactivity primitive: Angular (v17+), Vue 3.5+, Svelte 5 (runes), Solid, Preact, and even Ember. A Signal is a fine-grained reactive cell — when its value changes, only the DOM that reads it updates, not the whole component. The pitch is faster updates and a simpler mental model: state is a value with subscribers, not a "re-render the function" event.

React's answer is still no — for the reasons Dan Abramov laid out in 2019: signals-as-primitives break composition (one custom hook subscribing to signals would interfere with another), and they make debugging harder (the data flow goes through hidden subscriptions instead of explicit props). React's bet is that the Compiler closes the performance gap without changing the mental model: you write plain functions and props, the compiler tracks which values each component depends on, and re-renders only what changed. The compiler internally achieves the same fine-grained update that signals give you — but as a build step, not a language feature.

For reading code at work: if you touch Angular, Vue, Svelte, or Solid, you will see signals (named signal(), ref(), $state, or createSignal). They look like useState but behave differently — the component doesn't re-run; the binding updates. Don't translate 1:1. Read each framework's signals doc before assuming the same model.

6. Preact — the branch that asks "what if React were 3.5 kB?"

Preact appeared in 2013, the same year React open-sourced. It is a separate implementation of the same component model — same JSX, same hooks (eventually), same mental model you read in the paradigm-shift doc — but a different codebase, with different goals. The original pitch was threefold (and is still on the project goals page):

  • Size: ~3.5 kB minified+gzip, vs React's ~30-40 kB. mattered a lot in 2013-2016 when mobile data was slow and bundlers were primitive.
  • Performance: avoid React's synthetic event system and the rest of the abstraction tax; use the browser's native addEventListener directly.
  • Understandability: the whole codebase is readable in a few hours. React's is not.

6.1 Why wasn't Preact folded into React?

Three reasons, and they're the same reasons Preact still exists separately in 2026:

  1. Different non-goals, by design. React's team optimizes for a complex, multi-platform abstraction (web, native, VR, server, fibers, concurrent rendering, Suspense, RSC). Preact's non-goals explicitly exclude PropTypes, the synthetic event system, and legacy IE8 compatibility. Folding Preact into React would mean abandoning those non-goals; folding React into Preact would mean abandoning the abstraction tax Preact was built to avoid. Preact's differences page is unusually direct: "Preact is not intended to be a reimplementation of React. … The reason Preact does not attempt to include every single feature of React is in order to remain small and focused — otherwise it would make more sense to simply submit optimizations to the React project, which is already a very complex and well-architected codebase."
  2. Cross-platform vs web-only. React was always written for multiple targets (the React Native renderer, the custom renderers in the React-Three-Fiber family, RSC's split-process model). Preact is honest about being web-only — it follows the DOM specification more closely (class not className, onInput not onChange, native SVG attributes, native Custom Element and Custom Event support). The trade-off is real and there is no neutral middle.
  3. Compatibility is already a solved problem. preact/compat is a thin aliasing layer — point your bundler at "preact/compat" instead of "react" and most React libraries work. So the React ecosystem already absorbs Preact through tooling, not through merger. You don't need Preact to be React; you need Preact to run React-component-shaped code, and it does.

6.2 Why Preact matters even more in 2026

Preact's small size and web-first stance made it the natural fit for two camps the rest of this doc describes elsewhere:

  • HTML-first / islands frameworks. Astro supports Preact as a first-class island renderer, and many Astro sites use Preact for their interactive islands precisely so the islands ship minimal JavaScript. If you're going to add 5 KB of JS to an otherwise-static marketing page, you reach for the 3.5 kB React-shaped library, not the 35 kB one.
  • Embedded / constrained environments. Web views inside native apps, kiosks, low-end Android, edge-rendered SPAs where every kilobyte shows up in core-web-vitals. Preact's users here overlap heavily with the WASM-from-React crowd.

Preact also adopted signals early (Sep 2022 — Introducing Signals, before the broader signals wave) and ships them as an official add-on. So if you read in §5 that signals beat re-render-the-component for fine-grained updates and you wonder "does anyone actually use that in a React-shaped API?" — yes, Preact does, and it is the proof-by-existence that the React team's "no" is about React's governance decision (composition, debugging, backward compat) not about technical impossibility.

6.3 Reading Preact at work

If you encounter a Preact codebase, the differences from React that will trip you are exactly the ones on Preact's differences page:

  • JSX uses native DOM attribute names: class, for, tabindex, stroke-width — not className, htmlFor, tabIndex, strokeWidth. Quirks of React vanish.
  • Form input uses onInput, not React's onChange. (Unless preact/compat is enabled — then React's onChange semantics are restored.)
  • Class components can take render(props, state) as arguments — a small Preact-only convenience. You'll see it in Preact-class code; don't reproduce it in React.
  • Events don't bubble through Portal — a behavioral difference from React that occasionally surfaces in modal and tooltip code.

Everything else from the paradigm-shift doc — closures, hooks, deps arrays, the storage models, the lifecycle table — applies as-is. Preact's version compatibility policy tracks current and previous React major releases.

6.4 Will Preact replace React (or vice versa)?

No. The split is stable because it is structural, not stylistic:

  • React is the multi-platform, abstraction-rich, foundation-backed default. It is what enterprise teams, RSC apps, and React Native reach for. The compiler closes the perf gap on the dimension Preact used to win outright (re-render optimization) — but React's bundle size will not collapse to Preact's, because React carries the cross-platform and RSC tax by choice.
  • Preact is the web-only, web-spec-first, size-and-readability-first branch. It wins where minimal JS matters (Astro islands, embeddable widgets, low-end devices, learning resources, demos) and where the synthetic-event abstraction is cost without benefit. It also functions as the proof that the React component model — the same mental model from the entire paradigm-shift doc — is small and simple enough to fit in 3.5 kB when you drop the parts React keeps for non-web reasons.

The likely 2026-and-beyond state: both continue, both share the React-ecosystem libraries via preact/compat, and the choice between them is per-project, settled by the size vs abstraction trade-off — not by either one "winning." The React Foundation makes this easier, not harder: a foundation-governed spec and a community-maintained smaller implementation is a healthier long-term arrangement than one company owning both.

7. React 19.2 and the routing renaissance

React 19.2 (Oct 2025) shipped three features that change daily code: Activity (preserves a subtree's state when it's hidden from the tree — solves the "I navigated away and lost my form" problem at the framework level), useEffectEvent (a non-reactive hook for event handlers — the documented solution to the "deps array lies because I want latest props in the handler" pattern from the paradigm-shift doc's §11), and React Performance Tracks (DevTools overlays for what actually re-rendered and why).

In parallel, React Router shipped a "framework mode" and React's official recommendation for new apps shifted. Sunsetting Create React App (Feb 14, 2025) made it explicit: new React apps should use a framework — Next.js, React Router (in framework mode), or Expo. CRA deprecation is the end of "just a Vite React app" as the default starting point. Build tools (Vite, Parcel, Rsbuild) remain valid for learners and for apps that genuinely don't need routing.

The pattern: React is moving up-stack. The component model (covered in the paradigm-shift doc) is settled. The next layer is the framework — routing, data fetching, code splitting, server rendering, caching — and React's team now writes about that layer, not about hooks.

8. What stays the same for you, reading code at work

None of this doc changes the core mental model from the paradigm-shift reference:

  • Client components still capture values per render. useState, useEffect, useRef still behave exactly as described there.
  • useEffectEvent is the new official tool for "I want the latest value without adding it to the deps array" — read it as the fix for the patterns described as bugs in the paradigm-shift doc's §11.
  • Server components are a subset of function components — no hooks, no events, run once. If you understood the capture-vs-mutate distinction, you already understand the boundary: server components are pure-capture-only, client components get the full model.
  • Class components remain in legacy code, still readable using the lifecycle table from the paradigm-shift doc's §15.

The arc is now: classes (2013-2018) → functions+hooks (2018-2024) → functions+hooks+compiler+split-process (2024-now). The compiler removes manual memoization. RSC splits the process. Signals did not win inside React; the compiler did the same work without changing the model. The foundation move makes the model's long-term stability a governance question, not a single-company question.
