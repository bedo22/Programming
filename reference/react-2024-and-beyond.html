React 19 — the platform shift

React 19 (Dec 2024) turned several community patterns into platform features. This is the release the compiler and RSC depend on, and the one every "2024 and beyond" check in this guide is measured against. The mental model from class-to-hooks is unchanged — what changed is that more things the ecosystem used to build with libraries are now part of React itself.

Reading 19-era code: when you see useActionState + a <form action={asyncFn}> + useOptimistic, the shape is "mutate, show predicted, reconcile." This replaces the old "submit + setLoading + setError" hand-rolled dance. The patterns from class-to-hooks §1 still apply — this is a new arrangement of the same state rules, not a new state model.

Actions and forms — progressive enhancement returns

React 19 made form submission a React concern. A form can take an action function instead of (or alongside) an onSubmit:

function ProfileForm() {
  const [state, action, pending] = useActionState(updateProfile, null);
  return (
    <form action={action}>
      <input name="name" />
      {pending ? "Saving…" : <SaveButton />}
      {state?.error >&& <p className="error">{state.error}</p>}
    </form>
  );
}

Reading map:

  • Action — the async function that runs the mutation. When an action starts, React automatically defers the update to a transition priority (non-blocking UI).
  • useFormStatus — a child form control asks "is my enclosing form pending?" without lifting state.
  • useActionState — the pairing of "this function" with "its latest result + pending flag." The first arg is the previous state (enables resubmission with the same shape).
  • useOptimistic — render a predicted value immediately; React rolls back to the server-authoritative value when the action settles.
  • Server Action — an action marked "use server" that executes on the server. Form + server action = modern progressive enhancement.

Server Actions are endpoints. Being "server-side" does not make a function safe. Server Actions are public HTTP endpoints: validate every argument, authorize the caller, rate-limit sensitive operations, and treat return values as untrusted. Form data is user input — never assume the types at the boundary (§4).

The React Compiler is stable (Oct 2025) and ship-by-default (2026)

The React Compiler v1.0 shipped October 7, 2025 — the first stable release after nearly a decade of research (the team's Prepack experiments started in 2017). The compiler is a Babel plugin that lowers your code into its own High-Level Intermediate Representation, runs data-flow and mutability analysis, and inserts memoization where it helps — including in places where useMemo cannot legally go, like after an early return.

What changed in 2025-2026: new apps now start with the compiler on by default. Expo SDK 54+ enables it in new templates. Vite and Next.js create-* templates include it as an opt-in choice. The compiler also powers the lint rules in eslint-plugin-react-hooks's recommended/recommended-latest presets — so even teams not ready to adopt the compiler get its validation. The rules encode the Rules of React and surface latent bugs (set-state-in-render, set-state-in-effect, unsafe ref access during render).

For you, reading code at work: useMemo, useCallback, and React.memo become escape hatches, not the default. New code written under the compiler can be the simple version from the main doc's "original function-component vision" — a plain function with hooks, no manual memoization — because the compiler puts the optimization back. Existing code keeps working; you do not need to remove existing memoization to adopt the compiler.

Adoption and upgrade rules (the parts practice-care about):

  • Do not pin the compiler to a SemVer range. The team recommends --save-exact (e.g. 1.0.0, not ^1.0.0) and manual upgrades with end-to-end testing.
  • Turn on the lint rules first. The compiler is only as correct as the code feeding it; the lint rules tell you when that code breaks the Rules of React before the compiler can mangle behavior.
  • Test effect dependencies after enabling. Compiler-generated memoization can change which effects fire when code quietly violates the Rules of React. Read the changelog and run the suite — treat a compiler upgrade like a React major upgrade.

React Server Components split rendering across two processes

The class→hooks arc was about how a component manages state inside one process. RSC answers a different question: which process a component runs in — yours (the browser) or the server's. Dan Abramov framed it cleanly in The Two Reacts (Jan 2024):

  • Client components: UI = f(state). State lives in the browser, code runs in the browser, interactions are instant. Your Counter component from the paradigm-shift doc lives here.
  • Server components: UI = f(data). Data lives on the server, code runs on the server (at request time or build time), and the browser receives the serialized UI payload plus only the client-component code it needs — not the raw data, not the server deps, not the entire bundler. PostPreview reads files with fs.readFile at build time and ships just the rendered output to the client.

The combined formula is UI = f(data, state). The two component kinds interleave: a server component can render a client component (passing serializable props into it), and a client component can receive server-rendered content as children. What a client component cannot do is pass arbitrary functions or non-serializable values into a server component — props crossing the boundary must be serializable. The mental extension is small: everything from the paradigm-shift doc applies to client components; server components are functions closer to the data — no useState/useEffect because they aren't per-frame re-rendered the way client components are (they run per request or per revalidation).

RSC is not a new paradigm replacing hooks — it is the function+hooks model deciding where each function runs. Read "client component" as everything in the paradigm-shift doc; "server component" as a strict subset (no hooks, no events, no window) that buys zero-bundle-size code and direct access to server-only APIs.

1 The RSC boundary rules

These are the rules that define the boundary. Everything in this doc about the compiler (§3) still applies to client components; these apply to server vs client:

RuleMeaning
Server components cannot use hooksNo useState, useEffect, useReducer, useContext…
Server components cannot use browser APIsNo window, localStorage, document…
Server components can be asyncThey can await data access directly (fetch, DB, fs)
Server components can render client componentsServer composes client interactivity — passes serializable props down
Client components can receive server-rendered childrenThe composition escape hatch: the server wraps the client part
Client components cannot pass functions into server componentsProps into server components must be serializable (server can't execute client data)
Context is client-onlyProviders/consumers live in the client tree; server components can't read client context
Server code must not ship secretsServer files don't go to the client — but data leaked through server output still matters (§5)

2 Where to place the client boundary

Default to server components for data display; push client down to the interactive leaves. Move a component to client only when it needs state, effects, an event handler, a browser API, or context.

Rendering strategy is an accessibility decision. SSR and RSC give screen readers content immediately (the HTML is in the first response); a client-only SPA gives assistive tech nothing until hydration finishes. But the client boundary is also where focus management can break — a hydrated Client Component that moves or restores focus poorly is an accessibility regression no audit will catch without a screen reader. Treat this as a seam owned jointly by UI/UX (the a11y discipline) and HTML & CSS (the platform controls), not as a rendering-only detail.

3 Caching and revalidation — the mental model

RSC's hardest bugs are almost never render bugs — they're caching bugs: stale data, over-cached personalized content, or data that appears fresh but was rendered from the wrong cache. When reading RSC-fed code, ask which cache is in play:

Cache layerQuestion it answers
Request memoizationDoes this fetch dedupe within one render pass?
Router cacheDoes the framework cache server-rendered UI on the client across navigations?
HTTP cacheIs this response cacheable by browsers/CDNs now?
Data cacheIs fetched data persisted across requests?
RevalidationWhen does cached data go stale, and who forces a refresh?
PersonalizationIs user-specific content accidentally shared with the cache?

Framework specifics (Next.js router/data caches) live in the Next.js deep dive; from React's angle, only know: server data is cache-owned by the framework, and interacting UI must not silently depend on that cache's freshness.

4 State management after RSC

RSC changes where state belongs. The old "everything in a global client store" model predates server-owned data:

State typeWhere it belongs
Server-fetched dataServer components / framework data cache — not a client store
URL stateRouter / search params
Local UI stateClient useState / useReducer
Shared interactive stateContext, Zustand, Redux Toolkit, Jotai
Mutation state (pending/optimistic/error)Actions + useActionState + useOptimistic (§2)

The rule: if data is server-owned and read-only, keep it on the server. Client state is for interaction — not a shadow copy of server data. The era of "fetch into Redux on mount" is over; the compiler memoizes, the server owns data, and client state shrinks to what's interactive.

5 Error handling and error boundaries

Error boundaries are client-only — they cannot be server components. A server component at the root of a failing subtree has no error.tsx-equivalent for the whole tree, and nested error boundaries wrap client trees. The practical shape in the framework era: a route-level error file (Next.js error.tsx, React Router error elements) is the server-aware catch-all; component-level boundaries belong on interactive client leaves. Errors must be serialized only as strings across the boundary — never share live objects or functions (§4.1).

6 Streaming and partial prerendering

Server rendering can ship progressively. Streaming (Suspense on the server) sends the shell first and each suspended server component's content as it finishes; partial prerendering (PPR, Oct 2023) pre-renders the static shell at build time and streams only the dynamic parts per request. When reading code, a "shell plus suspense around one region" shape usually means the slow, user-specific part is isolated so the static majority ships instantly — the same Suspense mental model, now precomputed.

The security boundary: RSC changed what a "trust boundary" means (Dec 2025 – Jan 2026)

Server Functions and the RSC wire protocol gave attackers a new surface. In December 2025, a critical CVE (CVSS 10.0) allowed remote code execution through the RSC protocol. The fixes shipped, then researchers found follow-ups — high-severity Denial of Service (CVE-2025-55184), medium-severity source-code exposure (CVE-2025-55183), and a further DoS in January 2026 (CVE-2026-23864).

The practical checklist for production:

  1. Treat every Server Function as a public endpoint. It runs with your server's secrets and privileges. Validate and authorize every argument; don't accept "it's internal — only my client calls it." A public RSC protocol reaches it directly.
  2. Never hardcode secrets in Server Function source. CVE-2025-55183 leaked source code through stringified arguments. process.env.SECRET is fine; const key = "sk_live_..." is not. Env vars, secrets manager.
  3. Validate at the boundary regardless of types. TypeScript checking ends at the server boundary. Schema-validate every Server Function argument (zod/typebox/valibot) — types erased, payloads untyped.
  4. Pin React deps and read the security blog. The Dec 2025 fixes shipped to the affected 19.x lines multiple times — the first patch was incomplete. This is now normal practice for critical CVEs in any framework; budget for it.
  5. Run framework security releases like OS updates. Next.js adopted a formal monthly security cadence with advance notice — schedule them, don't let them drift.

The React Foundation (Feb 2026): Meta is no longer the sole owner

On February 24, 2026, the React Foundation launched under the Linux Foundation. React, React Native, and JSX are no longer owned by Meta — they are now owned by the foundation, governed by a board with eight Platinum founding members: Amazon, Callstack, Expo, Huawei, Meta, Microsoft, Software Mansion, and Vercel. Seth Webster serves as executive director.

Why this matters for reading code: who funds React shapes what gets prioritized. One company's (Meta's) internal needs drove React 16-18's roadmap — newsfeed constraints produced concurrent rendering and Suspense. Eight board members — hyperscalers (Amazon, Microsoft), mobile players (Expo, Software Mansion), hosting (Vercel) — broaden the priorities. Expect less single-company urgency and more ecosystem coordination: stable APIs for hosting vendors, clearer upgrade contracts for enterprise, a slower, more deliberate release rhythm.

Technical governance stays independent of the board — contributors set technical direction; the board manages assets and infrastructure. A provisional leadership council is determining the long-term structure; React Conf planning continues.

In parallel, React's official recommendation for new apps shifted: Sunsetting Create React App (Feb 14, 2025) made it explicit — new React apps should use a framework. CRA deprecation ended "just a Vite React app" as the default starting point. The pattern: React is moving up-stack. The component model is settled; the next layer is the framework — routing, data fetching, code splitting, server rendering, caching.

The signals question — and why React didn't adopt them

By 2026, every other major reactive framework standardized on signals as the primary reactivity primitive: Angular (v17+), Vue 3.5+, Svelte 5 (runes), Solid, Preact, and even Ember. A signal is a fine-grained reactive cell — when its value changes, only the DOM that subscribes updates, not the whole component. The pitch: faster updates and a simpler mental model — state as a value with subscribers, rather than "re-render the function."

React's answer is still no — for the reasons Dan Abramov laid out in 2019: signals-as-primitives break composition (a hook subscribing to signals interferes with another), and they make debugging harder (data flows through hidden subscriptions instead of explicit props). React's bet is that the compiler closes the performance gap without changing the mental model: you write plain functions and props, the compiler tracks dependencies, re-renders only what changed. To be precise: the compiler reduces unnecessary re-rendering through memoization — it is not signal-style fine-grained DOM subscription. They are solving the same symptom through different mechanisms; the mental model difference (explicit props vs hidden subscriptions) is the whole point of React's "no".

For reading code at work: if you touch Angular (signal()), Vue (ref()), Svelte ($state), Solid (createSignal), or Preact (signal()), they look like useState but behave differently — the component doesn't re-run; the binding updates. Don't translate 1:1 between the two reactivity models; read each framework's signals doc.

Preact — the structural branch that asks "what if React were 3.5 kB?"

Preact appeared in 2015. It is a separate implementation of the same component model — same JSX, same hooks (eventually), same mental model — but a different codebase with different goals. The original pitch (still on the project goals page):

  • Size: ~3-4 kB minified+gzip, vs React DOM's ~40 kB+. mattered a lot in 2015-2016 when mobile data was slow.
  • Performance: avoids React's synthetic event system and the rest of the abstraction tax; uses the browser's native addEventListener directly.
  • Understandability: the whole codebase is readable in a few hours. React's is not.

1 Why wasn't Preact folded into React?

Three reasons, same reasons Preact still exists separately in 2026:

  1. Different non-goals, by design. React optimizes for a complex, multi-platform abstraction (web, native, VR, fibers, concurrent rendering, Suspense, RSC). Preact's non-goals exclude the synthetic event system, PropType-like ceremony, and legacy IE8. "Preact is not intended to be a reimplementation of React… otherwise it would make more sense to simply submit optimizations to the React project."
  2. Cross-platform vs web-only. React targets multiple renderers (React Native, RSC split process). Preact is honest about being web-only and follows the DOM spec more closely (class not className, onInput not onChange, native Custom Element support).
  3. Compatibility is a solved problem. preact/compat is a thin aliasing layer — point the bundler at preact/compat and most React libraries work. The ecosystem absorbs Preact through tooling, not merger.

2 Why Preact matters even more in 2026

  • Islands frameworks. Astro supports Preact as a first-class island renderer — minimal JS for interactive islands on mostly-static pages. If you're adding 5 kB to a marketing page, you reach for the 3.5 kB React-shaped library, not the 35 kB one.
  • Embedded / constrained environments. Web views in native apps, kiosks, low-end Android, edge SPAs where every kilobyte shows up in core-web-vitals.

Preact also adopted signals early (Sep 2022, Introducing Signals) as an official add-on — proof-by-existence that React's "no" is a governance/design decision (§8), not a technical impossibility.

3 Reading Preact at work

The differences that will trip you are exactly the ones on Preact's differences page: native DOM attribute names (class, for, stroke-width), onInput instead of onChange (unless preact/compat), class components can take render(props, state) arguments, and events don't bubble through portals. Everything else — closures, hooks, deps arrays, lifecycle — applies as-is from the paradigm-shift doc.

4 Will Preact replace React?

No. The split is stable because it is structural, not stylistic: React is the multi-platform, abstraction-rich, foundation-backed default; Preact is the web-only, web-spec-first, size-first branch. The compiler closes the re-render gap on one of Preact's dimensions, but React's bundle will not collapse to Preact's — the cross-platform and RSC tax is a deliberate choice. A foundation-governed spec alongside a community-maintained smaller implementation is, if anything, more sustainable than one company owning both.
