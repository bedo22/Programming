The terminal — the universal remote

The terminal is the raw interface to every tool on this shelf. GUIs hide complexity behind buttons; the terminal exposes the underlying operations — and every tool the shelf teaches (Git, npm, Node, Docker, curl, WP-CLI) is designed terminal-first. When a GUI exists, it is a skin over the same command. What the terminal gives you that GUIs cannot:

CapabilityWhy it matters
ScriptabilityAnything you do once, you can chain and repeat — your CI pipeline is literally a sequence of terminal commands running in a Linux container
Remote accessThe only way in when the machine is a server in another continent (ssh)
TruthLogs, process lists, and file permissions show what is, not what a GUI decided to display
PrecisionOne command targets exactly one thing — a PID, a line in a file, a port — instead of clicking through menus

Linux is the universal host. Whether you deploy to AWS, Vercel, a Raspberry Pi, or a container, the environment is almost always Linux. macOS is Unix underneath (very similar); Windows developers use WSL to emulate it. So the terminal habits you build locally transfer to production almost unchanged — which is exactly why "it worked in my terminal" is the closest thing to "it works in production" you will ever get.

Shell fundamentals — the environment you type into

Terminal vs. shell vs. command line. The terminal is the window you look at (iTerm2, Windows Terminal, GNOME Terminal); the shell is the program inside it that interprets what you type (bash on most Linux, zsh on macOS since Catalina); the command line is the interface where you type. The distinction matters when you edit shell config: your aliases and PATH additions live in ~/.bashrc on Linux and ~/.zshrc on macOS — put them in the wrong file and nothing happens.

The two features that make the terminal faster than a GUI: tab completion — type git ch and press Tab to complete to git checkout (press Tab twice to list the options) — and command history — the ↑/↓ arrows walk through past commands, and Ctrl+R searches them. Without these the terminal feels slower than clicking; with them it is dramatically faster. Learn them before any command.

Paths. An absolute path starts at the root: /home/you/projects/my-app. A relative path starts from where you are: ./src/index.js or ../shared/utils.js. ~ is shorthand for your home directory, . is the current directory, .. is the parent — which is why cd projects works from home but not from /tmp.

Redirection, wildcards, and chaining — the three operators that turn commands into scripts:

npm run build > build.log 2>&1   # > write output to a file (overwrite); 2>&1 folds errors in too
echo "DB=..." >> .env          # >> append to a file instead of overwriting
rm *.log                        # * matches any text: every .log file in this directory
npm install && npm run dev     # && run the second only if the first succeeded
npm test || echo "failed"       # || run the second only if the first failed
cd src ; ls                      # ; run both, regardless of success

Aliases and built-in help. alias gs='git status' defines a shortcut you will see in other people's configs. When you meet a command you don't know, the terminal documents itself: man lsof is the full manual, lsof --help the quick summary.

The survival kit — the 20% for 99%

Six small tables. These are not "nice to know" — they are the set that unblocks 99% of web engineering problems: moving around, finding what is running, configuring the environment, searching logs, testing endpoints, and not shooting yourself in the foot. C. The environment & variables

Backend Engineering treats configuration as environment variables (process.env.DATABASE_URL). The terminal is where those live and get loaded:

echo $MY_VAR               # print it — verify
echo $PATH                 # the directories the shell searches for commands
source .env                # load a .env file into the session (or use a dotenv loader)

D. Pipes & searching — the superpower

The Unix philosophy: small tools that do one thing well, chained with |. Output of the left feeds input of the right:

cat server.log | grep "ERROR"    # only the error lines of a huge log
history | grep docker            # that complex command you typed yesterday
ps aux | grep node               # find processes without a GUI task manager

And for finding files rather than lines: find . -name "*.env" searches the tree from where you are, filtering by name — you know it exists, just not where.

This one habit — grep the log instead of scrolling it — is the single biggest debugging upgrade on the shelf. It is exactly what Testing & Debugging prescribes: evidence before hypothesis.

E. Networking & remote access

SSH keys and the concept of "remote". ssh user@host opens a secure tunnel: the commands you type execute on the server, not your laptop — ls lists the server's files, and exit brings you back. Logging in with a password works but is weak and awkward; the standard is an SSH key pair — your private key stays on your laptop, your public key is installed on the server (or on GitHub, for git push over SSH). Once that is set up, logging in needs no password. Shortcuts live in ~/.ssh/config, where you can define ssh prod to mean the full host, user, and port. The depth — key rotation, agent forwarding — belongs to Security & Threat Modeling; here you need the model and the habit.

F. Permissions — the security baseline

CommandWhat it doesShelf context
chmod +x script.shMake a script executableDeploy scripts, CI helpers
chmod 600 .envSecrets file readable only by youSecrets hygiene — Security
sudo <cmd>Run a command as rootOnly for system-level installs; see the rule below

The rule that saves servers: never run your Node/Python server with sudo. If the app is compromised, an attacker inherits root and owns the whole machine. Run as an unprivileged user; the process manager or platform does the privileged parts.

Docker — the deployment unit

The mental model in one sentence: an image is the blueprint (a recipe: base OS + runtime + your code + config), built once and versioned; a container is a running process created from that image, started as many times as you like. You never "edit a running container" — you rebuild the image and start a new one. That one sentence is the entire mental model; everything else is tooling.

ImageContainer
KindThe blueprint — built onceThe live process — run many times
LifecycleImmutable, versioned (v1.2.0)Ephemeral — dies and is replaced, never patched in place
AnalogyA recipeA meal made from it

A container is not a VM. A VM emulates a whole computer — its own kernel, gigabytes, minutes to boot. A container is a packaged, isolated process sharing the host's Linux kernel (via cgroups and namespaces), starting in milliseconds and consuming only what the process needs. VMs virtualize hardware; containers virtualize the OS. This is why containers are the default deployment unit of the modern web, and why the CI/CD doc's artifact table lists signed container images as the modern choice.

Why it all exists — "it works on my machine". Your app depends on an exact Node version, specific OS libraries, and specific environment variables; your coworker's machine and the production server have different versions. The image freezes the winning combination — the same base OS, runtime, code, and config in every environment — so "it works on my machine" becomes "it works in this image", and the image is identical everywhere. That is the entire reason to containerize.

The Dockerfile — the recipe that builds an image. A Dockerfile is a step-by-step recipe; each line is a step, and the result is an image. You rarely write one from scratch, but you will read them constantly, so recognize the four instructions that do all the work:

FROM node:20-alpine        # the base image you build on top of
WORKDIR /app               # the working directory inside the image
COPY package*.json ./      # copy files from your machine into the image
RUN npm ci                 # run a command during the build (install deps)
COPY . .                   # copy the rest of the app
CMD ["npm", "start"]       # the command that runs when the container starts

Docker Compose — the recipe for your whole local environment. docker-compose.yml is a YAML file that describes several containers and how they connect — your app, a database, a cache — so one command brings up the entire stack. This is how you get local Postgres and Redis for development instead of installing them natively on your laptop:

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: dev
    ports:
      - "5432:5432"          # host port : container port (see the ports table)
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7
    ports:
      - "6379:6379"

volumes:
  pgdata:

docker compose up starts everything the file describes; docker compose down stops and removes it. When you clone a repo that has one of these files, you do not install a database by hand — you read the file to see what the project needs, then docker compose up. The mental model is the same as the Dockerfile: a declarative recipe you read and run, not a sequence you improvise.

Port mapping and volume mounts — the two flags you'll see everywhere. A container has its own network namespace: -p 3000:3000 (or ports: in Compose) maps port 3000 on your machine to port 3000 inside the container — without it, your browser cannot reach the container's web server. A container's filesystem is ephemeral — everything written inside is lost when it stops — so -v ./src:/app/src (or volumes:) mounts a directory from your machine into the container, which is how you develop inside a container with your files live-synced.

Common ports — the numbers behind every service

A port is a number that identifies one service on a machine. One machine runs many services at once — the web server on 3000, the database on 5432, the cache on 6379 — and the OS routes traffic to the right one by the port number. When two services grab the same port you get EADDRINUSE (the ghost-port example below).

PortServiceWhat it is

The pipeline connection: your CI runs tests, builds the image, tags it, and pushes it to a registry; deployment strategies (rolling, blue-green, canary) are just "which version of the image is receiving traffic". You build once in CI and promote the exact same image through staging to production — never rebuild per environment. That's the build-once-promote-many rule, and its home is CI/CD & Deployment; this doc only names the concept so the pipeline reads as real.

Running your stack day to day: docker compose up for the local environment, and three debugging commands, memorized:

CommandWhat it does

Safely ignore: multi-stage Dockerfiles tuned for legacy apps, image-layer micro-optimization, and container networking internals. If you can read a simple Dockerfile and run compose, you have the literacy this shelf requires.

Kubernetes — orchestration literacy

Kubernetes (K8s) is the "operating system of the data center": it takes container images and decides where they run, how many copies exist, and how traffic reaches them. You will almost certainly never administer a cluster — managed platforms and system-design warnings see to that — but the primitives appear constantly in job posts, platform docs, and architecture conversations. Three nouns are enough:

PrimitiveWhat it isOne-line mental model
PodThe smallest deployable unit: one or a few containers that share a network identity"A running container (or two tightly-coupled ones), with an IP"
DeploymentThe declarative desired state: how many Pod replicas, which image version, how to roll updates"I want 3 copies of image v1.2.0, and I want them swapped out without downtime"
ServiceA stable name and load balancer in front of a set of Pods"Pods die; this name keeps working regardless of which Pod answers"

The connection between the three: a Deployment creates Pods, and a Service routes traffic to the healthy Pods behind it — that chain is the whole wiring. When a platform says "deploy a Deployment with a Service", you can now picture the thing: three ephemeral containers behind a stable address. That is the entire literacy bar. The moment someone proposes running Kubernetes yourself, remember the shelf's own warning — System Design lists "Kafka + Kubernetes + Istio for a 3-person CRUD team" as the canonical overkill. Cluster administration is a career, not a skill; you are licensed to nod and defer.

Cloud — the three eras of renting compute

Since AWS launched S3 and EC2 in 2006 (CS & SE history), compute has been rentable by the minute instead of bought as hardware. Three eras of that rent define every deployment target you will choose from — each rents one layer higher up the stack:

EraYou rentYou manageExamplesThe constraint it imposes
IaaS
Infrastructure as a Service		Virtual machinesOS, runtime, and appAWS EC2, DigitalOcean, Azure VMsFull control, full ops burden — you are the admin
PaaS / managed
Platform as a Service		The runtime or the databaseJust your app (and your schema)Heroku, Vercel, Render, AWS RDS, Neon, SupabasePush code, the platform runs it — configuration replaces administration
Serverless / edge
Execution as a Service		The execution itselfOnly your function's logicAWS Lambda, Cloudflare Workers, Vercel Edge FunctionsScales to zero when idle — and your code must tolerate it

How cloud constrains backend engineering: the serverless era forces the request loop to be stateless. The next request may hit a different, cold-started container — so sessions and caches cannot live in local memory. Backend Engineering puts the contract exactly: "an in-memory cache is now a cold-start gamble. Statelessness stops being a choice and becomes the contract." State must live in an external database or cache (Redis). PaaS hides this from you; serverless enforces it on you; knowing the difference is what the eras map is for.

Edge & data gravity: reading a database in us-east-1 from a user in Tokyo pays a physics penalty — the speed of light — which is why CDNs and edge compute push work to where the users are. The modern pattern moves compute to the data. The depth (latency budgets, consistency across edges, Durable Objects) belongs to System Design; this doc's job is just to make "edge" mean "closer to the user, because physics".

Where does your code run — one map

The terminal, Docker, and cloud sections are three views of the same ladder. Every environment below is a place your code runs, with a different way in, different common failure, and different debug reflex — learn the ladder so a "works locally" report always gets the follow-up: where?

Worked example — the ghost port

The most common local-development bug in existence: EADDRINUSE. You restart your server and the port is taken by a process you forgot about. The senior reflex, in four commands:

$ npm run dev
Error: listen EADDRINUSE: address already in use :::3000

$ lsof -i :3000
COMMAND  PID   USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
node     4821  me     21u  IPv4 12345      0t0  TCP *:3000 (LISTEN)

$ kill -9 4821

$ npm run dev      # works

That is the whole pattern, and it generalizes to every debugging session on the shelf: read the error → find the evidence (log, process, port) → act on exactly what the evidence names → verify. The junior clicks around the IDE; the senior opens the terminal, tails the log, greps for the error, finds the PID, and kills it. This is the habit Testing & Debugging formalizes — the terminal is just where the evidence lives.

Worked example — I just cloned a repo

The other daily ritual: a teammate hands you a repo URL and you need it running. The whole ladder in one session — reading files, env vars, and Docker Compose all at once:

$ git clone https://github.com/team/project.git
$ cd project
$ cat README.md            # setup instructions usually live here
$ cat package.json         # check the Node version and the start script
$ npm install
$ cp .env.example .env     # create your env file from the template
$ npm run dev
Error: connect ECONNREFUSED 127.0.0.1:5432
$ docker compose up -d     # the database (port 5432, see the ports table) isn't running
$ npm run dev              # works

Same pattern, one rung down the ladder: the error names an address (127.0.0.1:5432), you read the repo's docker-compose.yml to see what should own that port, you start it, you verify. What changed between first and second try? Nothing in the code — only the environment the code runs in. That is the substrate.
