Definition — what a product shape is, and what it is not

A product shape is a recurring archetype of web work with its own dominant constraint — the one property that, if mishandled, sinks the project. A landing page is constrained by load speed and conversion; a dashboard by data density and state; a booking system by time math. The shape is not the discipline: a dashboard still needs APIs, data, and security, but those are the how — the shape tells you which how matters most and which failure kills you first.

Two kinds of shape appear in the taxonomy below. Product archetypes (landing page, dashboard, SaaS, CRUD, e-commerce, content, booking, portfolio) answer "what must exist?" — they are the thing you build. Engagement shapes (API integration, CMS customization, migration, performance) answer "what must be changed safely?" — they are the job you are hired to do to an existing product. Different scoping questions, but the same triage machinery: name the constraint, name the death mode, route to the owning doc.

What a shape is not: it is not a technology choice (WordPress vs. Next.js is a camp decision, see Frontend Camps), not a business model (that's Product Strategy), and not a skill (that's the discipline docs). Shapes and skills overlap — a SaaS product is usually a dashboard under the hood — but the dominant constraint differs, so the triage differs.

History — why work arrives as shapes, not disciplines

Disciplines are how the industry organized knowledge; shapes are how work actually arrives. The first web projects were marketing pages and catalogs — two shapes that are still the bulk of small-budget work. As the web industrialized, the shapes multiplied: dashboards arrived with internal tooling, SaaS arrived with subscription billing, booking systems arrived with scheduling services. Each new shape was a response to a business need, and each carries the constraint of the business it serves — a checkout must not double-charge, a booking must not double-book. The discipline docs abstracted the underlying skill; this doc keeps the business reality attached to it.

Underlying theory — the constraint is the shape

Every shape has one property that fails first and fails visibly. That property is its dominant constraint, and it comes from the shape's business purpose, not its technology:

  • The constraint determines the decision order. A dashboard's permission model matters before its chart library; a booking system's time handling matters before its UI. Get the constraint right and the rest of the decisions slot into the discipline docs.
  • The constraint determines the failure mode. Each shape has a canonical way to die: slow landing page, stale dashboard, double-charged checkout, double-booked slot, lost migration, leaked tenant data. Name the death mode and you've named the constraint.
  • Shapes nest. A SaaS is a CRUD app with multi-tenancy and billing; a storefront is a content site with a checkout; a booking system is a CRUD app with calendar logic. When shapes nest, the outer constraint dominates.

Shape lifecycle — when a project changes shape

Projects are not frozen at triage. The same client, six months later, is asking for a different shape — and the scope and quote must change with it. The shape changed → the quote must change (see Freelance Web Practice for the commercial side).

Per-shape link maps — the decisions each shape stresses

Each map names the 2–3 decisions that actually differ by shape and points to the discipline doc that owns the rest. The discipline docs teach the full method; these maps say which sections to read for this shape.

Landing page / marketing site

  • What differs: performance budget, SEO structure, analytics/conversion setup. The design serves one action.
  • Owns the how: HTML & CSS (rendering, Core Web Vitals, forms) · UI/UX (conversion design, accessibility) · Camps (Camp B HTML-first / Camp D SSG) · Product Strategy (what "conversion" means here).
  • Death mode: slow load or untracked traffic — performance is the product, and it must be measurable.

Dashboard / admin panel

  • What differs: data-fetching strategy (poll vs. WebSocket vs. SSE), table virtualization, permission model, chart choice.
  • Owns the how: System Design (data flow, caching) · API Design (pagination, filtering) · UI/UX (state visibility, data density) · Security (role-based access) · Camps (Camp C SPA).
  • Death mode: stale data or a slow table — every cell can be loading, empty, error, or stale, and the design must say which.

SaaS product

  • What differs: tenant isolation, auth provider, billing/subscription model, feature flags, onboarding.
  • Owns the how: Data Modeling (multi-tenancy) · Payments & Commerce (subscriptions) · Backend Engineering (auth, background jobs) · API Design (idempotency for billing) · Product Strategy (pricing, CAC/LTV).
  • Death mode: tenant data leak or billing bug — technical decisions are downstream of the pricing decision.

CRUD app / internal tool

  • What differs: form design, validation timing, workflow states, role-based access, audit trail, bulk operations.
  • Owns the how: Backend Engineering (the CRUD loop, transactions) · API Design (resource contracts, error envelopes) · UI/UX (form design, error affordances) · Data Modeling (schema, constraints, migrations).
  • Death mode: the gap between "works in Postman" and "works in production" — validation and edge cases are where the complexity lives.

E-commerce site

  • What differs: platform vs. custom, payment integration, inventory, shipping, cart persistence, checkout SEO.
  • Owns the how: Payments & Commerce (checkout, refunds, PCI, fraud) · API Design (idempotency) · System Design (inventory consistency) · UI/UX (checkout flow, trust).
  • Death mode: a double-charge or a lost order — the tolerance for error is near zero.

Content site / blog / docs

  • What differs: content model, SEO structure, search, reading experience. The technology should disappear.
  • Owns the how: WordPress & CMS (content modeling, editing) · HTML & CSS (semantic HTML, typography, performance) · UI/UX (readability, navigation) · Camps (Camp A CMS / Camp B HTML-first).
  • Death mode: an unmaintainable content model — the reader never notices the tech, and the editor can't edit.

Booking / scheduling system

  • What differs: time-zone handling, conflict detection, recurring bookings, buffers, reminders.
  • Owns the how: Data Modeling (the slot model, constraints) · Backend Engineering (transactions, background jobs for reminders) · API Design (booking contracts, idempotency) · System Design (consistency).
  • Death mode: a double-booked slot or a wrong time zone — the data model must be right before any UI.

Portfolio / personal site

  • What differs: design bar, simplicity, near-perfect performance. The smallest shape with the highest design ceiling.
  • Owns the how: HTML & CSS (platform, performance) · UI/UX (visual design, motion) · Camps (SSG / hand-coded HTML).
  • Death mode: fast but generic — the design is the entire value proposition.

API integration / automation

  • What differs: error handling, retry/backoff, webhook verification, data mapping, rate-limit compliance, monitoring.
  • Owns the how: API Design (contracts, error envelopes) · Backend Engineering (background jobs, error handling) · Version Control, CI/CD (deployment, rollback) · Testing & Debugging.
  • Death mode: the happy path is easy and the error paths are the entire product — it fails catastrophically at 3 AM.

WordPress / CMS customization

  • What differs: client editability is the primary requirement — the tech serves the content workflow, not the reverse.
  • Owns the how: WordPress & the CMS Internet — the whole doc: mechanics, content modeling, Gutenberg/headless, workflow, migration, ops, the "I can edit myself" reality.
  • Death mode: a site the client can't edit — or one the client edits into breakage. Editability is a deliverable, not a feature.

Migration / redesign

  • What differs: migration strategy (big-bang vs. strangler fig), SEO preservation, data mapping, parallel-run testing, rollback.
  • Owns the how: System Design §3b (migration paths) · WordPress & CMS (migration paths) · Version Control, CI/CD (deployment, rollback) · API Design (contract compatibility) · Data Modeling (schema evolution).
  • Death mode: SEO ranking drops overnight or data is lost — a successful migration is one nobody notices.

Performance optimization

  • What differs: what to measure (LCP, CLS, INP), what to optimize (images, JS, CSS, fonts, server), and knowing when to stop.
  • Owns the how: HTML & CSS §6j (Core Web Vitals ↔ platform knobs) · System Design (caching, CDN) · UI/UX (perceived performance).
  • Death mode: endless optimization — the discipline is knowing when the improvement stops being worth the cost.

Principles — the shared constants across every shape

  • Identify the shape before the stack. Every wrong build starts with a missing triage.
  • Name the death mode out loud. If you can't say how this shape dies, you haven't found its constraint.
  • One dominant constraint per project. When two compete, the outer one wins (see the nesting table).
  • Route to the owning doc. The discipline docs already answer the hard questions; the shape doc points to the right one.
  • The client's words are the brief. "I can edit it myself" is a constraint, not a preference.
  • Scope follows shape. An honest scope for a landing page is smaller than for a SaaS — quote accordingly (Freelance Web Practice owns the arithmetic).

Worked example — one brief, triaged end to end

Brief: "Our clinic needs a website where patients can book appointments, and I need to be able to update the content myself."

1 · Triage: which shape? "Patients book appointments" → booking shape.
     "I need to update the content myself" → CMS/editability constraint.
     Outer constraint wins: this is a BOOKING system the client must edit.

2 · The death mode: a double-booked slot in the wrong time zone.
     → The booking data model and conflict detection matter more
       than the page design or the stack.

3 · Which discipline docs answer the hard questions?
     → WordPress & the CMS Internet (the platform, client editability)
     → Data Modeling (the slot model, time-zone handling, constraints)
     → Backend Engineering (confirmation/reminder jobs)

4 · The scope this shape demands:
     → A bookable calendar (slots, buffers, time zones, conflict check)
     → An editing surface the clinic can use without touching code
     → A reminder path (email/SMS on booking and before the slot)
     → Payments only if they said "and take a deposit" — they didn't.

5 · What this shape does NOT demand:
     → No tenant isolation (single clinic), no billing lifecycle,
       no feature flags, no table virtualization. Skipping them is
       correct, not lazy — they belong to other shapes.

The same brief mis-triaged as "a website with a form" would produce a site the clinic can't edit and a calendar that double-books. The shape isn't decoration — it is the scope.

Worked example — the shape that hides behind a smaller brief

1 · Triage: "a bakery wants to sell cakes online + post weekly menus"
     → e-commerce (money) + content (the menus) nest.
     Money shape dominates: a lost order loses revenue; a stale
     menu loses an occasional reader. This is a SHOP first.

2 · The death mode: a lost order or double-charge at checkout.
     → Payments reliability and inventory matter more than the
       menu design or the cake photography.

3 · Which discipline docs answer the hard questions?
     → Payments & Commerce (checkout, refunds, order flow)
     → Data Modeling (inventory, order lines, stock consistency)
     → System Design (cart persistence, checkout consistency)

4 · The scope this shape demands:
     → A checkout that cannot double-charge or lose an order
     → Inventory that cannot oversell (or a clear "no stock" path)
     → A content area for weekly menus — the CMS, not the shop,
       owns that, and it's the small part
     → Order notifications/confirmation so nothing is silent

5 · What this shape does NOT demand:
     → No accounts, no subscriptions, no tenant isolation.
       A bakery sells cakes, not seats. Skipping SaaS machinery
       is correct — it belongs to another shape.

Here the tempting mis-triage is to hear "weekly menus" and build a content site with a store bolted on. The money shape wins, and the scope follows: the shop is the product, the menus are the decoration.

The freelancer's scoping checklist — run before you quote

Five questions, answered from the brief before any code or any price:

  1. Which shape is this? Match the client's words to the taxonomy; if two shapes nest, name the outer one.
  2. What is the dominant constraint? The one property that, if wrong, kills the project.
  3. Which discipline docs answer the hard questions? Point the shape at its owning docs; read only as deep as the shape demands.
  4. What are the failure modes to watch for? Name the death mode and make the scope prevent exactly that.
  5. What is the client's ability to maintain this after handoff? "I can edit it myself" is a scope item, not a wish (Freelance Web Practice owns the delivery).

The future — AI changes which shapes appear, not the triage

AI erodes the build cost of the simple shapes fastest: landing pages, content sites, and simple CRUD apps can now be scaffolded by a model. The shapes don't disappear — but their marginal constraints get sharper. A landing page is no longer hard because it's hard to build; it's hard because conversion and speed are measurable, and the bar rises. The complex shapes (SaaS, booking, migration, performance) survive because their constraints — tenant isolation, time math, preservation, measurement — are exactly what AI is worst at. The triage discipline survives because the death modes don't change: a double-booking is a double-booking whether the calendar was hand-built or AI-generated. The premium shifts from writing the code a shape needs to recognizing which shape the brief is and where the real risk sits — which is the whole job of this doc.

AI also introduces new emerging shapes, each with its own constraint and death mode:

  • AI chat product — grounded responses and safety policy; death mode is confident hallucination the user trusts.
  • AI agent product — tool permission boundaries and an audit trail of actions taken; death mode is an agent acting with authority it was never given.
  • AI feature inside a SaaS — evaluation and trust: you can't ship what you can't score, and users will not trust a black box with their data (Data Modeling §PII / Security).

AI doesn't remove shapes — it changes which ones are commodity. The building of the simple shapes cheapens; the constraints of every shape remain.
