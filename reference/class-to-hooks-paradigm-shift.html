The class-to-function paradigm shift in React

A comprehensive reference. Why React moved from classes to functions+hooks, what changed, what stayed, and why "functional programming" alone wasn't the answer.

Why this doc exists

Lesson 5 introduced this and bind because you'll meet them in older React code at work. But you asked the rightMeta question: why did React move away from classes at all? Wasn't the functional style enough? This doc answers both — because the answer is counterintuitive: React already had function components before hooks, and they weren't enough. Hooks were the missing piece that made functions viable for real components. The story has four eras.

0. Before the classes: a word on foundations

This section used to hold a deep prequel on programming primitives, the four theories of computation (Turing machine, lambda calculus, von Neumann architecture, information theory), the data→value→variable→state chain, types, and lifetime. That prequel now lives in its own reference doc — What Is "State"? — A Prequel to Programming in React — and the JavaScript language foundation (history, design, runtime model) lives in JavaScript: The Language. Read both if the phrase "Turing's state register is the same concept as useState" doesn't feel immediately obvious.

What you need from that prequel to follow the rest of this doc: state is a normal variable whose value persists across events — nothing more, nothing less. The rest of this doc is the story of where that persistent variable lives: closure, class field, hook slot, server. Same variable, different owner. If that distinction is clear, you have what you need to continue.

1. OOP — the paradigm classes came from

Before we can talk about why React moved away from classes, we have to ask: what paradigm do classes belong to, and why did anyone think it was the right fit for UIs in the first place?

The three major programming paradigms

ParadigmHeart unitState lives…Computation is…Origin
Procedural / imperativefunctions acting on dataIn shared data structures, mutated by functionsA sequence of instructions: do this, then thatC, Fortran, assembly

The key insight: a "class" in JavaScript is a thin syntax wrapper over the prototype chain (Lesson 3 — new four-step dance). But conceptually, choosing class is choosing the OOP paradigm: the idea that the right unit of a program is an object bundle of state plus the methods that operate on that state. You instantiate the class once, you get one persistent instance, the instance holds the state, and the methods mutate it over time. this is how a method refers to its own instance.

The four pillars of OOP — and how React classes map to each

This is why OOP felt natural for UIs in 2013. A button is naturally something with state (hovered, pressed, disabled), and OOP's pitch was "state belongs inside objects that know how to manage themselves." A class with this.state and this.handleClick reflected that intuition. It's no accident that React, Angular, Ember, Backbone, and Vue all started with class-style components — OOP was the dominant paradigm of the 2000s-2010s.

Why OOP fell out of fashion for UIs — and three specific signs

OOP didn't die. It's still alive in systems programming, game engines, and plenty of languages. But for the specific problem of building user interfaces, three signs appeared over a decade of real-world use:

Sign 1 — Inheritance trees get tangled. Real React codebases rarely extended React.Component more than one level. When they did, it was painful: a BaseModal extends React.Component and ConfirmModal extends BaseModal quickly turned into "which lifecycle hook does this thing use, and has the parent overridden it?" Inheritance invited ceremony; components were better when flat. The class extending the base class was a tedious tax to get setState.

Sign 2 — Mutable state inside objects is hard to reason about. this.state.count changes over time, and any method anywhere can read it. When something is wrong on screen, you have to trace which code path mutated this.state to which value at what point in the component's lifetime. This is the classic OOP debugging pain — "object identity over time" — concentrated in a system that re-renders constantly.

Sign 3 — Logic reuse wanted functions, not inheritance. When two components needed the same stateful logic, inheritance wasn't the answer (you can't extend two base classes). The React community invented workarounds: higher-order components (HOCs) (a function that takes a component, returns a wrapped component) and render props (a component whose child is a function). Both of these are function-composition patterns smuggled back into the class world. They worked, but they made the wrapper-hell problem: real apps in 2017 were wrapped in five layers of HOCs, all so the underlying class could keep its this. The community was reaching for FP-style composition while still paying the OOP tax.

// HOCs — function composition pretending to be OOP
function withAuth(WrappedComponent) {
  return class extends React.Component {
    state = { user: null };
    componentDidMount() { fetchUser().then(u => this.setState({ user: u })); }
    render() { return this.state.user ?  : null; }
  };
}

function withTheme(WrappedComponent) {
  return class extends React.Component { /* ... reads theme context ... */ };
}

// wrapper hell — three layers deep, props threading through each
export default withAuth(withTheme(withRouter(MyComponent)));
// DevTools: withAuth > withTheme > withRouter > MyComponent
// None of this is inheritance — it's FP composition routed through classes.

The pattern that became the React team's motivation. The official Hooks introduction names "hard to reuse stateful logic" as problem #1. The community couldn't solve this naturally with classes because the stateful logic was glued to the class instance: this.state, this.setState, this.componentDidMount are all instance properties. To reuse them, you had to wrap the whole class. Hooks let you write the logic as a function (a custom hook) that any component can call — because the state now lives in React, not in a class instance.

The pivot — what React kept from OOP, what it dropped

React didn't abandon EVERYTHING from OOP. It kept: encapsulation of UI logic inside a component boundary (today's function component still encapsulates — just with hooks instead of methods), and the abstraction that "a component is a thing you can compose inside other components" (today still true). It dropped: inheritance (the React base class is gone in the function world), mutable this (no this at all in function components), and the "object-as-unit-of-state" idea (state now flows through hooks, not through instance fields).

It also kept OOP's pragmatic sibling: imperative escape hatches. useRef gives you a mutable box — exactly what an instance field was — for the cases where you need imperative state that doesn't trigger re-render. React didn't go pure-functional; it kept a small imperative door for the cases where OOP-style "this thing has mutable state" is genuinely the right model (DOM refs, timer IDs, "latest value" caches).

You can read the whole shift as: React took OOP's encapsulation + FP's composition, and dropped OOP's inheritance + mutable-this. Hooks are literally functions you compose; useRef is the one place the old OOP instance-field model survives.

2. What is "state"? A prequel — before we can talk about React's choices

Section 1 took "state" as a given. That skips the most important part of the story. State is not a React concept, nor a JavaScript concept — it is a stolen idea with a 70-year history, and the way React treats it today is the result of several migrations across paradigms. If you do not know where state lived before React, you cannot tell what is unusual about where React puts it now.

2.1 The original meaning — automata theory (1936–1960s)

The word state comes from computer science before computers had screens: automata theory. A Turing machine has a state register — a finite set of configurations the machine can be in, with transition rules that say "if you are in state X and read symbol Y, go to state Z." A finite state machine (FSM) is the same idea compressed: an engine that is in exactly one state at a time, and events move it from state to state.

This is the deep origin of every UI state conversation. When we say "the button is in the disabled state" or "the form is in the submitting state," we are using the FSM vocabulary — the component is a machine with discrete configurations and defined transitions. Even the React team's mental model ("UI is a function of state") is automata-descended: state is the input, the transition is an event, the new state is the output.

Two ideas we will reuse. (1) State is distinct from the data you compute from it — the FSM is in one state, but a log of past states is different data. (2) State persists across events — that is the whole point of having it; without persistence you would just have a stream of inputs.

2.2 MVC (1979) — state leaves the view, moves into a model

In 1979, Trygve Reenskaug working at Xerox PARC on Smalltalk-80 wrote the original Models-Views-Controllers note. The problem he was solving: if a UI element holds its own data and draws itself, every change ripples through the screen and you cannot have two views of the same data (e.g. a list view and a detail view of the same record). His proposal:

  • Model — holds the state and the domain logic. Knows nothing about screens.
  • View — reads the model and renders. Listens for change notifications.
  • Controller — takes input, asks the model to update, tells the view to re-render.

State moved out of the view, into a separate object whose only job was to hold and validate state. Views became projections — read-only functions of the model. This was a profound move: it is why today we still say "the component should not own its data; the data should live in a store/model and the component should read it."

MVC's specific bug was two-way binding: controllers updated models and models notified views and views sent events back to controllers, and tracing a single user click through that loop was hard. Every UI architecture since 1979 has been a variation on "split model from view, but fix the feedback loop MVC left behind."

2.3 The web's stateless origin (1991–2004)

HTTP was designed stateless — each request is independent, the server forgets you between requests. Browsers rendered HTML, JavaScript was a tiny assistant for form validation, and state lived in three places, none of them "the component":

  • The DOM — the HTML document was the state. "Is this checkbox checked?" was a property of the DOM node, queried imperatively. The DOM was the database.
  • The URL — which page you were on was state.Bookmarkable. Refresh-stable.
  • The server's session — logged-in identity, cart contents. Keyed by a cookie. The browser's "state" was a token, not actual values.

Vanilla JS of the 1995-2005 era had no concept of component state. You wrote document.getElementById('count').innerHTML = newCount — the count lived in a DOM node, your code mutated that node directly, and "state" as a first-class concept did not exist in your codebase. State was a property of the document, not of your program.

2.4 jQuery (2006) — implicit state via closures and the DOM

jQuery didn't add a state abstraction either. It made DOM mutation cleaner ($('#count').text(n)), but state still lived in the DOM. The new thing jQuery enabled accidentally: state in closures. A click handler closure could capture a let count = 0 in its enclosing function, and that count would persist across clicks — state living in JS memory, reachable only via the closure, not in any DOM attribute. Lesson 2 of this workspace covers exactly this pattern:

// jQuery-era implicit state — the count lives in the closure, not the DOM
$(function() {
  var count = 0;                          // state = a closed-over variable
  $('#btn').on('click', function() {
    count++;
    $('#count').text(count);              // projection of state into the DOM
  });
});

This is the first time JavaScript-side state became common — but it was implicit, scattered, and each plugin/widget reinvented its own. There was no shared vocabulary for "this widget has state X." Plugins like jQuery UI had to invent a widget factory with _create, _setOption, option() — a half-hearted OOP state model bolted on top of closures.

2.5 Backbone, Angular 1, Ember (2010–2013) — explicit model state returns

As single-page apps grew, the closure-scattered-state pattern collapsed under its own weight. Three frameworks independently reinvented MVC's "put state in a model object" idea for JavaScript:

  • Backbone.js (2010) — Backbone.Model with get/set and a change event. Explicit. Architecturally honest. Verbose.
  • Angular 1 (2010) — $scope as a hierarchical state tree mirrored to templates via dirty-checking. Two-way binding; the famous digest cycle.
  • Ember (2011) — routes as the unit, controllers and models holding state, computed properties with explicit dependencies.
  • Knockout, CanJS, Sencha ExtJS — variations on the same: a model/observable object holds state, the view binds to it.

What every one of these did was bring state back out of the DOM and into a JS object (a model, a scope, a controller). They differed in how changes propagated. State was no longer a property of the document; it was a property of your JS application — but the framework owned it, not the component.

For Angular's full arc — from AngularJS through the 2016 rewrite to modern Signals — see the companion doc: Angular's evolution: the class, the rewrite, and the signal.

2.6 React 2013 — state moves into the component (a contrarian move)

React's 2013 launch did the opposite of where Backbone and Angular were going. Where they pulled state into framework-wide stores or scopes, React pushed state down into each component, as this.state on the class instance:

class Counter extends React.Component {
  constructor(props) {
    super(props);
    this.state = { count: 0 };       // state lives on the component instance itself
  }
}

This was contrarian and controversial at the time. Critics called it a regression — "we just spent five years pulling state out of views, why put it back?" The React team's argument:

  • The unit of reuse is the component, not the model.
  • State scoped to a component is easier to reason about than state in a global scope tree (Angular's $scope digests were notorious).
  • "UI = f(state)" replaces "state, view, controller each touch each other bidirectionally."

The big trade: state moved closer to where it was used, at the cost of cross-component state becoming hard again. That cost is what Flux and Redux were about to fix.

2.7 Flux (2014) and Redux (2015) — state moves partially back out

By 2014, the React community had rediscovered MVC's original problem: if every component owns its own state, two siblings cannot share it without awkward parent-passing. Facebook's Flux pattern was a counter-reaction: a single store holding application state, dispatched actions mutating it, components subscribing. Redux (Dan Abramov, 2015) generalized Flux with reducers — pure functions of (state, action) → newState, inspired by Elm.

The pendulum swung. State was partly back out of the component, into a single store outside the component tree. React components kept their this.state for local UI state (form inputs, hover, transient toggles), but the domain state — the user, the cart, the orders — moved to Redux.

That split — "domain state in a store, UI state in components" — has held through hooks (2018), the compiler (2025), and into RSC (2024+). It is the dominant shape of React apps in 2026.

2.8 Hooks (2018) — state moves to React's runtime, locked by call order

The 2018 hooks launch did not change where state conceptually lived (still per-component), but it changed how it was stored. With classes, state was literally an instance field: this.state was a property of the object this, the object lived as long as the component was mounted, and you accessed it as count = this.state.count. State lived on the instance, OOP-style.

With useState, state lives in React's runtime storage, keyed by call order inside the component function:

function Counter() {
  const [count, setCount] = useState(0);        // first useState call → slot 0
  const [name, setName] = useState('');         // second call → slot 1
  // React keeps an array per component instance, indexed by call order
}

This is the most invisible and important change in the whole arc. State stopped being a property of the component (an OOP instance field) and became a property of React itself, on a per-instance basis. The component function is now just a description of "I want state at slots 0 and 1"; React stores it. This is why the rules of hooks exist (you cannot call useState conditionally — the slot would be out of order next time) — §8 of this doc.

The trade React made: a function that "is stateful" via call order is weirder than a class with fields, but you can now extract stateful logic into a custom hook — because the logic is just function calls, not an instance. That is exactly the wrapper-hell problem from §1 solved at the storage layer.

2.9 Signals (2022+) — state as a graph node, not a slot

The most serious alternative to React's hook-call-order model is signals, popularized in the JS world by Solid (2018+) and Preact (2022), and earlier in Vue 3's ref/reactive and Svelte's stores. A signal is not a slot keyed by call order — it is a standalone value cell with subscribers:

// Preact signals — state is a graph node, lives where you put it
import { signal } from '@preact/signals';

const count = signal(0);                 // cell in the JS heap; not scoped to a component
function Counter() {
  return ;
}

When count.value changes, only the bindings that read it update — not the whole component function re-running. Conceptually this is closer to MVC's "model with change notifications" than to React's "function of state." React did not adopt signals (see React 2024 and beyond), but Angular did — see Angular's evolution: the class, the rewrite, and the signal for the framework that adopted signals to replace zone.js. Reading code in the signals world (Preact, Solid, Vue, Svelte runes, Angular 17+) you should recognize: this is a different answer to the same question. State is a graph node, not a slot.

2.10 React Server Components (2024+) — state splits from data

The latest migration: state and data stop being one thing. Server Components have no state (no useState, no hooks) — they are pure functions of data fetched on the server: UI = f(data). Client Components keep state: UI = f(state). The full app: UI = f(data, state) (see the React 2024 and beyond doc).

In effect RSC splits the question "where does state live?" in two: state (UI state, things the user does) lives in the browser, in client components; data (records pulled from a database) lives on the server, fetched fresh per request. They used to be the same concept — both were "this.state" on a class. Now they have different storage and different lifecycles.

2.11 The future — what the compiler changes, what it does not

The React Compiler (see React 2024 and beyond) does not move state again. State stays where hooks put it — in React's runtime, locked by call order, per component instance. What the compiler changes is derivation: where you used to manually memoize with useMemo / useCallback to keep derived values stable, the compiler does that automatically. State stays; memoization bookkeeping disappears.

What the next migration might be is genuinely open. Candidates signals-world advocates push: (a) state as graph nodes (signals fully replacing hook slots) — React has said no (see the React 2024 and beyond doc); (b) state pushed back out of components into stores with first-class framework support (Redux/Zustand becoming framework-native instead of community-driven); (c) state on the server, snapshots shipped to the client — the "single-flight mutations" research area. None of these are settled as of 2026. What is settled: state has moved roughly every 5–7 years since 1979 (MVC → web DOM → jQuery closures → Backbone/Angular models → React components → Flux/Redux stores → hooks slots → RSC split). Expect the next move before 2030.

The one-sentence history. State started as a separate object (MVC model), got pushed into the document (web), leaked into closures (jQuery), got pulled back into framework models (Backbone/Angular), got pushed into the component (React classes), got pulled halfway out into stores (Flux/Redux), got stored in React itself by call order (hooks), and most recently got split between browser-state and server-data (RSC). Every one of these moves solved a specific bug and introduced a new one. Reading React today means understanding which of these eras the file you are looking at belongs to.

4. Era 1 — Class components, the original model

React shipped in 2013 with one component model: classes. A class component is an object with a render() method, mutable this.state, and lifecycle methods that fire at specific points in the component's existence.

class Counter extends React.Component {
  constructor(props) {
    super(props);                       // required when extending — calls the parent constructor
    this.state = { count: 0 };          // state lives on the instance
    this.handleClick = this.handleClick.bind(this);  // pre-bake this so the callback keeps it
  }

  handleClick() {
    this.setState(prev => ({ count: prev.count + 1 }));
  }

  componentDidMount() {                 // runs once, after first render
    document.title = `Count: ${this.state.count}`;
  }

  componentDidUpdate() {                // runs after every update
    document.title = `Count: ${this.state.count}`;
  }

  componentWillUnmount() {              // runs once, before removal
    console.log("Counter unmounting");
  }

  render() {
    return ;
  }
}

The mental model: a component is an instance of a class. The instance lives as long as the component is mounted. this references that instance. React mutates this.state and this.props over time so the latest values are always readable through this. Lifecycle methods are hooks into the instance's biography — birth (componentDidMount), middle (componentDidUpdate), death (componentWillUnmount).

What was good

  • Clear instance model. One object per component, holding state and methods. Familiar to OOP programmers.
  • Lifecycle biography. Setup in mount, cleanup in unmount — felt natural.
  • this as a time-travelling reference. Read this.state.count anywhere, any time — it always points to the latest.

What was painful — and why the React team eventually moved away

The official Hooks introduction (React blog, 2019) names three problems. They are not about performance.

Problem 1 — Hard to reuse stateful logic between components. If two components both needed "subscribe to a friend's online status" logic, you couldn't just extract a function. You needed a higher-order component (HOC) or a render prop, both of which wrap your component in another layer. Real apps ended up in "wrapper hell" — DevTools showing five layers of withAuth(withTheme(withRouter(withUser(MyComponent)))). Each layer added indirection, naming collisions, and ref-forwarding headaches.

// The HOC pattern — wrapper hell
const EnhancedComponent = withAuth(withTheme(withRouter(MyComponent)));
// In DevTools: withAuth > withTheme > withRouter > MyComponent
// Each layer re-renders MyComponent; props pass through all of them

Problem 2 — Complex components become hard to understand. Lifecycle methods lumped unrelated logic together. A single componentDidMount might set up a subscription, start a timer, AND fetch initial data — three unrelated concerns in one method. componentWillUnmount cleaned up all three. Related code was scattered across methods; unrelated code was crammed into the same method. As components grew, this became a mess.

class ChatRoom extends React.Component {
  componentDidMount() {
    this.fetchMessages();        // concern 1: data fetching
    this.subscribeToSocket();    // concern 2: real-time subscription
    this.startTypingTimer();     // concern 3: typing indicator
  }

  componentDidUpdate(prevProps) {
    if (prevProps.roomId !== this.props.roomId) {
      this.unsubscribe();        // cleanup for concern 2
      this.fetchMessages();      // concern 1 again
      this.subscribeToSocket();  // concern 2 again
    }
  }

  componentWillUnmount() {
    this.unsubscribe();           // cleanup for concern 2
    this.stopTypingTimer();      // cleanup for concern 3
  }
}

Three concerns, scattered across three methods, interleaved with each other. Reading any single concern required jumping between all three methods.

Problem 3 — Classes confuse both people and machines. The React team wrote this verbatim in the official motivation. Three sub-issues:

  • this in JavaScript is unlike this in most other languages. You must remember to bind event handlers. Without class fields (ES2022), constructor boilerplate is verbose. People understand props, state, and top-down data flow perfectly well — yet still struggle with classes.
  • Classes don't minify well — the minifier can't collapse method names because they might be called by React's internals.
  • Classes make hot reloading flaky — the minified class identity changes between edits, breaking state preservation.
  • Ahead-of-time compilation strategies (component folding, Prepack experiments) hit dead ends with class patterns.

5. Era 2 — Function components appear, but they're second-class (2015)

In 2015 React added function components — a simpler way to write components that had no state and no side effects:

function Greeting({ name }) {
  return 
Hello, {name}
;
}

Cleaner than the class version for presentational components. But function components were limited by design — they couldn't:

  • Hold state (no setState).
  • Run side effects (no lifecycle methods).
  • Read context (that required a class or a consumer component).
  • Access refs.

If your component needed any of those, you had to rewrite it as a class. Most real components need state or effects — so most components were classes. Function components were for the leaf presentational nodes of your tree.

This is the answer to "wasn't functional enough?" — no, it wasn't. Pure functions can render a UI from props, but a real interactive component needs to hold state over time and respond to the outside world (timers, subscriptions, DOM mutations, fetches). Pure functions can't do that. Something had to bridge the gap. In classes, the bridge was the instance and its lifecycle methods. In functions, the bridge didn't exist yet.

5b. Mental models — how React developers actually reason

Before hooks, React developers reasoned in lifecycle phases: mount → update → unmount. Each phase had a specific method. The mental model was "what do I do when the component mounts? What about when props change? What about cleanup?"

After hooks, the mental model shifted to effects and dependencies: "what side effect do I want to run, and when should it re-run?" The dependency array ([deps]) became the central reasoning artifact — it declares the relationship between the effect and the reactive values it depends on.

EraCore mental modelKey reasoning questionDebugging intuition
Classes (Era 1) Lifecycle phases (mount/update/unmount) "Which lifecycle method handles this concern?" React DevTools: component tree + "Why did this render?" (post-16.8). Console: look for setState in render.
Functions pre-hooks (Era 2) Pure function of props → UI "What props does this need?" No state debugging — purely presentational.
Hooks (Era 3+) Reactive closures + dependency arrays "What values does this effect/state depend on?" Rules of Hooks lint; stale closure bugs; missing deps; useEffect firing twice in strict mode.

The closure trap: Function components capture the values from their render. A useEffect with [] deps sees the values from the first render forever. This is not a bug — it's the model. The fix is the dependency array, which tells React: "re-create this closure when these values change." Understanding when a closure is created is the mental skill hooks demand.

6. Era 3 — Hooks (2018): making functions first-class

Hooks shipped in React 16.8 (February 2019). The name is literal: a hook hooks into React's features (state, effects, context, refs) from inside a function. The function is no longer stateless — it just delegates its state to React via a hook call.

function Counter() {
  const [count, setCount] = useState(0);     // ask React for a state slot

  useEffect(() => {                          // synchronize something with the outside world
    document.title = `Count: ${count}`;
    return () => console.log("cleanup");     // optional cleanup
  }, [count]);                               // only re-run when count changes

  return ;
}

The function is called on every render. Each call creates fresh local variables (fresh boxes — see the re-render box model reference). useState asks React to remember a value across calls. useEffect schedules side-effect work after the DOM has been painted. No this, no bind, no constructor, no super().

Why hooks solve the three problems

Problem 1 fixed — stateful logic reuse via custom hooks. Instead of HOCs wrapping your component, you write a function that calls hooks. Any component can call it. No wrappers, no nesting.

// Custom hook — reuse stateful logic without wrapper hell
function useFriendStatus(friendID) {
  const [isOnline, setIsOnline] = useState(null);

  useEffect(() => {
    const handler = (status) => setIsOnline(status.isOnline);
    ChatAPI.subscribe(friendID, handler);
    return () => ChatAPI.unsubscribe(friendID, handler);
  }, [friendID]);

  return isOnline;
}

// Two unrelated components can both use it — no nesting
function FriendListItem({ friend }) {
  const isOnline = useFriendStatus(friend.id);
  return 
  • {friend.name} {isOnline ? "🟢" : "⚪"}
    • ;
}

function ChatHeader({ friend }) {
  const isOnline = useFriendStatus(friend.id);
  return {isOnline ? "online" : "offline"};
}

    No layers of wrappers. Each component that needs the logic just calls the hook. The state is private to each caller — two components calling useFriendStatus get independent state.

    Problem 2 fixed — related logic stays together. Instead of scattering one concern across three lifecycle methods, you write one useEffect per concern. Related setup and cleanup live in the same function. Unrelated concerns live in separate effects.

    function ChatRoom({ roomId }) {
  const [messages, setMessages] = useState([]);

  // Concern 1: data fetching — setup + cleanup together
  useEffect(() => {
    let active = true;
    fetchMessages(roomId).then(m => { if (active) setMessages(m); });
    return () => { active = false; };
  }, [roomId]);

  // Concern 2: real-time subscription — independent effect
  useEffect(() => {
    const handler = (msg) => setMessages(prev => [...prev, msg]);
    ChatAPI.subscribe(roomId, handler);
    return () => ChatAPI.unsubscribe(roomId, handler);
  }, [roomId]);

  // Concern 3: typing indicator — separate again
  useEffect(() => {
    const id = setInterval(() => {/*...*/}, 5000);
    return () => clearInterval(id);
  }, []);

  return ;
}

    Three concerns, three effects. Each is self-contained: setup right next to cleanup. To understand "how does this component fetch data?" you read one effect, not three lifecycle methods.

    Problem 3 fixed — no this, no bind, no constructor. Look at the Counter above: no this, no this.handleClick.bind(this), no super(), no class at all. The function's locals (including the setter from useState) are ordinary variables. Event handlers defined in the body are closures over those locals — no this to lose.

    The deeper reason — functions capture values, classes don't

    Dan Abramov wrote a famous post titled "How are function components different from classes?" (2019). The headline: function components capture the rendered values. This is a fundamental difference that has nothing to do with hooks — it existed since function components were introduced, but most people didn't notice until hooks made functions mainstream.

    The example: a "Follow" button that shows an alert 3 seconds after click.

    // Function version — captures props at click time
function ProfilePage({ user }) {
  const showMessage = () => alert("Followed " + user);
  const handleClick = () => setTimeout(showMessage, 3000);
  return ;
}

// Class version — reads latest this.props, not the clicked props
class ProfilePage extends React.Component {
  showMessage = () => alert("Followed " + this.props.user);
  handleClick = () => setTimeout(this.showMessage, 3000);
  render() { return ; }
}

    If you click Follow on Dan's profile, then navigate to Sophie's profile before 3 seconds pass:

    • Function version alerts "Followed Dan" — the user variable was captured at click time. Each render has its own user box; the click handler closes over that box. The box doesn't change.
    • Class version alerts "Followed Sophie" — this.props is mutable; React mutates it on every render. this.showMessage reads the current this.props.user, not the one at click time.

    The function behavior is correct (you followed Dan, even if you then navigated away). The class behavior is buggy. And you can't fix it by binding — binding pins this, but the bug is that this mutates. The fix is to capture the value at the moment you care about: which is exactly what closures do, and exactly what function components are made of.

    This is the deepest reason for the shift. Closures over captured values are correct by default in React's model (UI is a function of state — each render is a snapshot). this in classes is a mutable escape hatch from that model. It causes the bugs React spent five years watching users hit. Hooks embrace the closure model instead of fighting it.

    7. The stale-closure "problem" — and why it isn't one

    Once people started using hooks, a new complaint appeared: the stale-closure bug. An effect captures a state value at render time; by the time the effect runs, the value might be old. Example:

    function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);
    return () => clearInterval(id);
  }, []);   // empty deps — effect runs once, captures count === 0 forever

  return 
    {count}
    ;
}

    This counts to 1 and stops. The interval was set up once, with count === 0 captured. Every tick calls setCount(0 + 1) — always 1. The closure is "stale" because it keeps reading the render-0 box forever.

    The naive read: "closures are the problem — classes were better because this.state.count always reads fresh." The correct read (from Dan Abramov's Complete Guide to useEffect): closures aren't the problem. The deps array lied. The effect does depend on count; writing [] told React "don't re-run this" — which froze the closure. The fix is to be honest:

    // Fix: include count in deps — effect re-runs whenever count changes
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, [count]);

    Now the effect tears down and re-creates the interval on every count change. The closure is always fresh. This works but causes the interval to reset every second — annoying. The better fix removes the dependency entirely by using the functional updater form:

    // Better: remove the dependency by using the updater form
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);   // now truly doesn't depend on count — updater form handles it

    The lesson: closures capture values; that's a feature, not a bug. The stale-closure bugs happen when you lie to React about which values the effect reads. The exhaustive-deps lint rule catches this automatically. Fix the deps (or restructure to avoid them) — don't go back to this.

    8. The rules of hooks — and where the design came from

    Hooks have two rules (enforced by a linter):

    1. Only call hooks at the top level — not inside loops, conditions, or nested functions.
    2. Only call hooks from React function components (or custom hooks).

    Why? React identifies hook state by call order — the first useState call in a render is the same slot as the first useState in the next render. If you call a hook conditionally, the slot order shifts between renders and React loses track of which state belongs to which hook. (Dan Abramov wrote a separate post, "Why Isn't X a Hook?", explaining which React APIs were considered as hooks but rejected — like useBailout — because they'd break composition: one custom hook calling useBailout would interfere with another calling it.)

    For useState, both rules are safe — adding a new unconditional call doesn't break other hooks, and you can't break other state slots by updating one. The design chose only the hooks that composed cleanly. That's why there's no useMemo-free useShouldComponentUpdate hook — it would conflict between custom hooks.

    9. The storage models — three places state can live in React

    For the full treatment with diagrams, see the re-render box model reference. This is a summary.

    React has three storage models, each answering "where does this value live between renders?":

    StorageWhat it holdsLifetimeUse when
    State (useState, useReducer)Values that trigger re-render when they changePersisted across renders for a mounted componentUI-relevant values
    Ref (useRef)Mutable values that DON'T trigger re-renderPersisted across renders for a mounted componentDOM nodes, interval IDs, "latest value" escape hatch, things that don't affect the render output
    Local variables (plain let/const in the function body)Per-render scratch spaceDies at end of this renderDerived values, memoized intermediates, anything that's recomputed each render anyway

    In classes there were effectively two places: this.state (state) and instance fields (this.something = refs). Hooks split these cleanly: useState for trigger-render state, useRef for doesn't-trigger mutable boxes, function-body let for throwaway scratch.

    11. Why not just use functional programming without hooks?

    You asked the key question: wasn't functional enough? The honest answer: pure functional programming — functions that take props and return JSX, with no side effects — works perfectly for presentational components. The problem is that real interactive UIs are not pure functions. They need:

    • To remember values across renders (state).
    • To react to the outside world — subscribe, poll, fetch, mutate the DOM (side effects).
    • To be testable in isolation by extracting reusable stateful logic.

    Pure functions can't do any of those. So a UI framework has two options:

    1. Wrap the function in an object that holds state and lifecycle. → class components. This works, but falls into the three class problems (logic reuse, lifecycle scattering, this confusion).
    2. Have the function ask the framework to provide state and effects. → hooks. The function stays a function; it just calls useState and useEffect to ask React for stateful capabilities. The framework wires them up behind the scenes.

    Hooks are the second approach. They didn't replace functional programming — they made functional programming viable for real components, by giving functions access to the stateful capabilities that pure functions can't have on their own. Functional programming alone was never enough; what was needed was a way for functions to opt into state and effects without becoming classes.

    This is also why the React docs say (2023): "We've taught React with function components and Hooks from the beginning." Classes are still supported (the legacy API section documents them) but the new docs don't teach them at all — they teach hooks-first because that's the model the React team chose.

    13. Where classes still live — and whether to learn them

    Should you learn class components?

    Yes — enough to read them. Most production React codebases still have class components in older files. You won't write new ones, but you'll read and debug them. The minimum you need to recognize:

    • this.state and this.setState (mutable state, the "always latest" model).
    • constructor, super(props), and this.method.bind(this) (the bind dance from Lesson 5).
    • componentDidMount / componentDidUpdate / componentWillUnmount (the lifecycle biography — when refactoring to hooks, these map roughly to effects).
    • Class-field arrow methods (handleClick = () => {...}) as the pre-hooks no-bind workaround.

    No — don't invest in mastering them. You won't write new class components in 2025. Spend that time on hooks (useState, useEffect, useRef, useMemo, useCallback, useContext) and on the closure mental model (the re-render box model). That's what you'll write.

    When refactoring a class component to a function component (or reading an old one), here's how the lifecycle biography maps to effects:

    The mental shift: lifecycle methods are a biography ("what happens at birth / middle / death") while effects are a synchronization ("keep this external state in sync with this render's values"). Dan Abramov's Complete Guide to useEffect frames this as: stop asking "when does this run?" and start asking "what am I synchronizing, and with which values?"

    15. The current state — and what you'll write

    As of 2025, modern React is function components + hooks + (optionally) the React Compiler. The dominant mental model:

    • Components are functions called once per render; each call has its own local boxes for state and props.
    • useState asks React to remember a value across calls; useEffect synchronizes external state with render values.
    • Closures over those values are correct by default; "stale closures" happen only when the deps array lies.
    • Refs give you the mutable-instance-field equivalent without this.
    • The compiler removes the last remaining hooks-era friction (manual memoization).

    Classes are still in the spec, still work, and are documented under "Legacy API" at react.dev. They will not be removed — too many production codebases use them. But no one is teaching them as the first model anymore. That signal from the React team is deliberate: classes are the past you'll read; functions+hooks are the present you'll write.

    Is there a "next paradigm after functional"? Not in React's component model — but the surrounding stack did not freeze in 2023. The function+hooks model held, and the next shifts happened around it, not against it. The next section covers those shifts.
