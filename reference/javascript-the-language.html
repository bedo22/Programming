JavaScript: The Language — History, Design, and the Runtime Model

How JS became JS: the 1995 Netscape/Sun deal, the Brendan Eich 10-day sprint, Mocha → LiveScript → JavaScript → ECMAScript, the prototype model, the event loop, single-threaded concurrency, and why a scripting language for form validation became the only language that runs natively in every browser. A foundation doc for the rest of the reference shelf. Sibling to HTML & CSS (the platform substrate JS manipulates).

Why this doc exists

The other reference docs (React paradigm, Angular evolution, Next.js deep dive, camps survey) treat JS as a given. This doc steps back and asks: what is JS, why does it look the way it does, and what design bets made it the language that runs everywhere? Sibling to what-is-state-prequel (which covers programming theory broadly) and parent-context for class-to-hooks. Its companion across-stacks doc (javascript-across-stacks) covers where JS runs and who fights it in each lane.

Reading order: standalone. One sitting. 1. The 10 days in May 1995

May 1995. Netscape Navigator 1.1 ships. The web is static HTML. Marc Andreessen wants the browser to be programmable — not just display documents, but react to the user. He tasks Brendan Eich, a 34-year-old systems programmer who joined Netscape that April, with building a scripting language for the browser. Constraints: must run in the browser, must be easy for non-programmers (designers, HTML authors), must ship in Netscape 2.0 by September.

Eich has 10 days to produce a working prototype. He draws on two lineages:

  • Scheme (Lisp) — first-class functions, lexical closures, a tiny core. Eich wanted this.
  • Java — the Netscape/Sun alliance meant "Java-like syntax" was a management requirement. The { } braces, ; terminators, new, typeof — all Java-shaped.

The prototype was called Mocha. Shipped in Netscape Navigator 2.0 beta as LiveScript. Renamed JavaScript in December 1995 — the Sun/Netscape marketing handshake: "Java is to the enterprise as JavaScript is to the browser." The name has caused 30 years of confusion. Java and JavaScript share syntax (curly braces) and almost nothing else.

Primary source → Brendan Eich, FAQ: Why is JS designed the way it is? (2011): "I wanted a Lisp-like language but had to use Java-like syntax to pass management approval. Under the { } braces is a lambda-calculus heart beating in a C-shaped body."

2. Why a new language, not a Java applet or C++ extension

The theory you asked for: why create a new language instead of extending Java or C++? The answer is platform constraints.

  • Java applets were already coming (1995). They had a heavyweight JVM, a compile step, static typing, a sandbox. They were for applications inside the browser — heavy, slow to start, overkill for "validate this form before submit."
  • C++ — no one ships a C++ compiler to a browser. No garbage collection, manual memory management, no safe sandbox. The browser needed a language that could not crash the process.
  • The platform needed glue. A scripting shell: mutate the DOM, handle events, validate forms, talk to the server (later: XMLHttpRequest). Glue languages are dynamically typed, garbage-collected, interpreted, and forgiving. Java and C++ are none of these.

The pattern that repeats: A platform deserves a language designed for its constraints, not a hand-me-down from a different platform. This is the same theory that later justifies TypeScript (a JS uplift for large-team maintainability, not a replacement), Go (a C++ replacement designed for networked servers, not a general-purpose systems language), Rust (a C++ replacement that solves memory safety without GC). The constraint changed — the language changed.

3. The design: prototype model, not classes

Eich chose prototypes over classes. The influence: Self (a Smalltalk descendant, prototype-based, from Sun Microsystems labs). In a prototype system, objects inherit directly from other objects — no class as a separate entity. You create an object, it becomes the prototype for others. Object.create(proto) is the primitive.

JavaScript's new + constructor function + .prototype is a thin syntactic layer over this:

// The prototype chain in action
function Animal(name) { this.name = name; }
Animal.prototype.speak = function() { console.log(this.name + ' makes a sound'); };

const dog = new Animal('Dog');
dog.speak(); // Dog makes a sound

// dog.__proto__ === Animal.prototype
// Animal.prototype.__proto__ === Object.prototype
// Object.prototype.__proto__ === null

ES6 class (2015) is syntax sugar over prototypes — not a full class system. It does not introduce private fields (those came later, 2022), does not change single inheritance, does not add multiple dispatch. It hides the delegation. When you read class Dog extends Animal, the prototype chain is still there underneath. Understanding the prototype model matters because the sugar leaks: this binding, method extraction, Object.getPrototypeOf, __proto__ all expose the mechanism.

4. The design: first-class functions, closures, the lambda-calculus heart

The Scheme/Lisp lineage. JavaScript functions are values — they can be assigned, passed, returned, created at runtime. This enables:

  • Higher-order functions — map/filter/reduce take functions as arguments.
  • Lexical closures — a function "captures" its surrounding scope. function outer() { let x = 1; return function inner() { return x++; }; } — inner remembers x after outer returns.
  • Currying — partial application by returning functions that take the next argument.

These are not "features added later." They were there in the 10-day prototype because Eich implemented the lambda calculus directly. The function keyword is a lambda. The closures lesson and currying lesson cover the mechanics; this doc covers the why.

Primary source → Brendan Eich, JavaScript at 20 (2015): "The lambda-calculus heart was there from day one. The C-shaped body was the compromise."

5. The design: single-threaded + event loop

JavaScript is single-threaded by design. One call stack. One thread of execution. The browser's DOM is single-threaded — two threads repainting the same DOM would race. The event loop is the concurrency model:

// Simplified event loop (browser)
// while (queue.length) {
//   const task = queue.shift();
//   task();  // run to completion
//   while (microtaskQueue.length) { microtaskQueue.shift()(); }
//   render();
// }

What maps onto the loop:

APIQueueNotes
setTimeout / setIntervalMacrotaskRuns after current task + all microtasks + render
Promise.then / awaitMicrotaskRuns before next macrotask, after current sync code
queueMicrotaskMicrotaskExplicit microtask scheduling
requestAnimationFrameAnimation frameRuns before next render, after microtasks

The Node.js bet (2009): the same loop works server-side. No threads per request — one loop, many concurrent I/O operations. This is why Node handles 10k connections on one thread while a threaded server needs 10k threads. The trade-off: CPU-bound work blocks the loop. The solution: worker threads (2018) or offload to another process.

5b. Mental models — how developers actually reason about the event loop

Most JS bugs are not syntax bugs — they are mental-model bugs about when code runs. The same loop is the answer, but how a developer imagines the loop determines whether they predict correctly. The four most common mental models in practice:

Mental modelWhat the developer believesWhere it breaksDebugging clue
"Synchronous until proven otherwise" JS runs top-to-bottom; async/await just "waits" inline Mutations after await look like they happen "before" the awaited promise resolves — the developer forgets the continuation is scheduled "Why is x still the old value after I awaited the assignment?" → the assignment is in a microtask after the awaiter already resumed
"setTimeout(fn, 0) means 'immediately'" 0ms = now The callback runs after the current task and all microtasks and render; for heavy pages this can be hundreds of ms "Why didn't my callback fire?" → check the queue; render and microtasks drain first
"await unwraps the value" await p gives you p's value, like sync assignment await yields the current task to the microtask queue; control returns to the event loop first. Anything that ran between the await and the resumption will observe a partial state "Why did my competitor callback see the old state?" → it ran in the microtask gap
"All callbacks are async" Everything JS does is "callback-based", so order doesn't matter Sync code runs to completion first; only when the stack is empty do queued tasks run. Order matters within a task "Why is my callback reading state from a task I thought ran later?" → it ran inside an earlier task, not after

The discipline. The "correct" model is: a single stack runs to completion; tasks queued during the run are processed in queue order after the stack is empty; microtasks drain before the next macrotask. Once this is internalized, the four models above collapse into one. The hard part is that the language lets you write each of the four wrong models and produces sensible-looking output until the bug surfaces in production. This is why "mental model" sections exist in every serious JS doc — not because the loop is complex, but because the developer is often thinking in one of the four shortcuts.

6. The host environment, not the language

The biggest JS insight: JS is a guest in a host. The language spec (ECMAScript) defines the core — syntax, types, objects, functions, the event loop. The host provides everything else:

HostGlobals it provides
Browserwindow, document, fetch, localStorage, WebGL, WebAssembly
Node.jsglobal, require/import, fs, net, process, Buffer
DenoDeno, Deno.serve, Deno.readFile, web-standard APIs
BunBun, Bun.serve, Bun.file, Node-compatible + web APIs
Cloudflare Workersfetch, caches, KV, Durable Objects — no fs, no net

This is why window doesn't exist in Node, fs doesn't exist in the browser, and "isomorphic" code breaks when it assumes a host global. The language is the same; the host changes. The lesson: when reading unfamiliar JS, identify the host first. require → Node/CommonJS. import + Deno → Deno. window → browser.

6b. The core semantics map — what ECMAScript itself defines

The host table above gives the environment. This section maps the language — the semantic model ECMAScript specifies independently of any host: types, equality, scope, this, prototypes, modules, iteration, errors, and memory. This is not a tutorial; the lessons walk the mechanics. This is the design system underneath: how each dimension behaves, so that when you read a program you can predict it. One sentence to hold the whole model:

JavaScript is dynamically typed, lexically scoped, prototype-based, and single-threaded. Its functions are first-class values, its objects delegate through prototype chains, and its concurrency is driven by an event loop — not shared-memory threads.

6b.1 Types — primitives versus objects

JavaScript has two families of values. Everything that is not an object is a primitive:

CategoryValuesBehaviour
Primitivesstring, number, bigint, boolean, undefined, symbol, nullImmutable; compared by value
Objectsplain objects {}, arrays, functions, dates, maps, sets, wrappersMutable; compared by reference

Three facts that shape every program:

  • Functions are objects — they can be assigned, passed, and given properties (see §4). Arrays are objects — with a special length that tracks the highest index, not a count of elements.
  • typeof null === "object" is a historical bug (null's type tag was stored as the object tag for lack of a better one). Preserved forever — the web cannot break.
  • Wrappers exist but should stay invisible. new String("x"), new Number(1), new Boolean(true) create object wrappers that mostly behave like primitives but compare by reference — new Number(1) === 1 is false. Never construct them explicitly; let primitives auto-wrap when you call methods ("abc".toUpperCase()).

6b.2 Equality and coercion — the specified, but surprising, rules

Coercion is not random — it is fully specified. It was designed for a small 1995 scripting language, so many cases surprise developers raised on stricter languages. Start by memorizing the operator choice, then the mental model of coercion.

OperatorMeaningUse
=== / !==Same type and same valueDefault; use almost always
== / !=Abstract equality — coerces, then comparesRare, explicit cases only
Object.isSame-value equality; treats NaN as itself and -0 separately from +0Special cases

Rules of thumb that cover real code:

  • Prefer === by default. The "Loose/lazy" developer who writes == is choosing coercion they usually did not intend.
  • Use == only where coercion is the point — e.g. checking null or undefined: x == null covers both.
  • Make conversions explicit. Number(x), String(x), Boolean(x) — not +x, "" + x, !!x. Explicit is greppable and intention-revealing.
  • Truthiness is a numeric convenience, not a type. 0, "", NaN, null, undefined, false are falsy; everything else — including "0" and [] — is truthy. [] == false is true because [] coerces to "" then 0.

6b.3 Scope, hoisting, the Temporal Dead Zone, and closures

Scope answers "which variables can this code see?" and it is lexical — determined by where code is written, not where it runs. That one fact powers closures and, via them, callbacks, modules, and React hooks.

ConceptMeaningWhy it matters
Lexical scopeScope is resolved by where code appears in sourceEnables closures; the let/const loop fix works because each iteration gets its own binding
varFunction-scoped, hoisted to the top of its functionLegacy behavior; the "all closures see the last value" bug
let / constBlock-scopedModern default; each { } block is a scope boundary
HoistingDeclarations are processed before the rest of the code runsExplains why var is in TDZ let a ReferenceError
Temporal Dead Zonelet/const variables exist but are uninitialized until their declaration lineAccessing before the declaration throws — prevents a class of var bugs
ClosureA function captures the lexical scope in which it was createdPowers callbacks, event handlers, React hooks the values

The var-versus-let loop is the clearest demonstration:

// var: one shared binding — all callbacks see 3
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
// 3 3 3

// let: a fresh binding per iteration — 0, 1, 2
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
// 0 1 2

Closures are not a "feature added later" — they are in the upper half of both real-world model categories: they remember the scope where they were created, not where they run. Mechanics live in the closures lesson; here the point is why closures exist: they are the language's answer to "how does a function keep access to the data it needs after its creator has finished?"

6b.4 this — determined by the call site

Most languages give this a lexical meaning. JavaScript does not — except arrow functions. The single rule:

this is bound by how the function is called (the call site), not where it is defined. Arrow functions are the only exception: they have no this of their own and inherit one from the surrounding scope.

Call typethis value
Plain call: fn()undefined in strict mode / modules; the global object otherwise
Method call: obj.method()The object before the dot
Constructor: new Foo()A newly created object
Explicit: fn.call(x) / fn.apply(x) / fn.bind(x)The object passed explicitly
Arrow functionLexical — inherits from surrounding scope

The consequence that bites real code is method extraction: pulling obj.method out and passing it elsewhere changes the call site, so this changes. This is why React class components needed this.handleClick = this.handleClick.bind(this) and why the fix is arrow functions or bind. The same rule explains the classic callback "lost this" bug.

6b.5 The prototype model, in depth

Section 3 explained the design. Here is the mechanism: objects delegate missing properties up a chain of linked objects. When you read obj.prop, the engine:

// 1. own property? obj.hasOwnProperty('prop')
// 2. else walk the chain: obj.__proto__, .__proto__, ...
// 3. until null → undefined
ConceptMeaning
Object.create(proto)Object that delegates to proto — the raw primitive (§3)
Constructor + newCalling new F() creates an object whose prototype is F.prototype
.prototype / __proto__F.prototype is the delegate of instances; __proto__ reads the actual link (modern: Object.getPrototypeOf)
instanceofChecks the chain, not a classical type
hasOwnPropertyOwn property only — not inherited
Object.prototypeFallback root of almost every chain; links to null

Practical consequences of owning the prototype:

  • Property lookup is a chain walk, not a lookup. Adding Animal.prototype.speak after instances are created still works — the instances find it on the chain at call time.
  • Check own properties when it matters. obj.hasOwnProperty(k), or Object.keys(obj), if inherited keys would break your logic.
  • Descriptors, getters/setters. Object.defineProperty gives any prop a getter/setter, writable/configurable flags. Class accessor get age()/set age() compile down to a descriptor.
  • Freeze and seal are shallow. Object.freeze(obj) prevents adding/removing/changing properties at the top level only — nested objects remain mutable.
  • Prototype pollution is a real 0-day. If untrusted keys are merged deep (e.g. {...source}) and the merge assigns to Object.prototype, every object in the runtime can gain attacker-controlled behavior. Mitigate with JSON.parse, strict key allowlists, Map, or a parse-only merger. Libraries like lodash have shipped CVEs in merge from exactly this.

6b.6 Reference vs value — why mutations "leak"

This is the language feature behind most state bugs, including in React:

KindBehaviour
PrimitivesCopied by value
Objects / arrays / functionsShared by reference — a variable holds a reference to the object, and copies point at the same object
Function parametersReceive the reference for objects. The function can mutate the caller's object, but reassigning the parameter does not affect the caller
structuredCloneDeep copy for most built-in values
Object.freezeShallow blocking of mutation
 
// reference sharing — the classic surprise
const a = { x: 1 };
const b = a;      // b is a second *reference*, not a copy
b.x = 2;
console.log(a.x); // 2 — a saw the change too

This is why "don't mutate the previous state" advice matters: if state.is an object you share, mutation breaks ===-based change detection. The React rule "return a new object, don't mutate the old" exists because the reference model makes mutation undetectable at the boundary.

6b.7 Modules — the history that explains modern imports

JavaScript had no module system for two decades. Every module mechanism since is a answer to "how do we split code across files without poisoning the global namespace?", and this section is why import/export look the way they do and why interop still hurts.

EraModule systemNotes
Early JSGlobals and IIFEsNo official system; window.foo = ... and (function(){ ... })()
Node.jsCommonJSrequire, module.exports — synchronous, runtime loading
BrowserAMDAsync loading for browsers. define
InteropUMDWrapped to work in both
ES2015+ESMimport/export — static, analyzable at parse time
ModernESM + package exportsTop-level await; conditional exports; tree-shaking

The two mental models that resolve most module questions:

  • CommonJS is dynamic and runtime-loaded (require is a call that runs when executed; you can require in a condition). ESM is static and parse-time (import statements are hoisted and resolved before execution — the top of the file).
  • Static structure is what enables tree-shaking: a bundler can see which exports are referenced and drop the rest at build time. Dynamic require cannot be shaken.
  • Interop is still pain. A package may ship both CJS and ESM copies; if their versions diverge you get two copies of the same module — the dual-package hazard.
  • ESM is the standard. Choose "type": "module" in new Node projects; understand exports map for dual shipping.

6b.8 Iteration protocols — what for...of and spread have in common

Modern syntax (for...of, spread, destructuring of iterables) all depend on the same pair of protocols. Once you know the protocol, the syntax becomes interchangeable.

ConceptMeaning
IterableAn object with a [Symbol.iterator]() method returning an iterator
IteratorAn object with next() returning { value, done }
for...ofConsumes an iterable, one next() per loop
Spread ...Consumes an iterable into a new array / call args
Generatorsfunction* — a function that yields values lazily and implements the iterator protocol for you
Async iteratorsfor await...of — yields promises, awaits each in sequence; used by streams and pagination

The mental-model guardrail:

Arrays are iterable — but not everything iterable is an array. Set, Map, string, generators are iterable and spread/for...of work on them directly. Plain objects are not iterable by default; use Object.keys/values/entries instead.

6b.9 Error handling — thrown as values

JavaScript errors are objects: they can be constructed, thrown, caught, subclassed, given properties, and inspected. That power cuts both ways — it is the same mechanism for simple mistakes and for framework-scale error hierarchies.

  • throw anything; but prefer throwing Error-shaped values so stack traces survive.
  • try/catch/finally — catch runs on throw, finally always runs (cleanup, logging).
  • Built-in error types — Error, TypeError, ReferenceError, SyntaxError, RangeError, URIError; bundlers and runtimes keep the pedigree right.
  • Custom error classes — class ApiError extends Error with super(message), then err instanceof ApiError downstream.
  • Stack traces — captured on construct; reading them requires host tools (err.stack).
  • Async failure is a distinct failure mode. throw outside a try in a promise chain becomes an unhandled rejection — it does not crash the page by default in the way an uncaught exception does, and it can vanish silently. Handle rejections at the boundary (.catch / try/await); register process/browser global rejection handlers as a safety net.
  • Promise.allSettled / AggregateError — when several failures and successes must coexist, allSettled gives you results per promise; Promise.any/AggregateError for "at least one succeeded".

6b.10 Memory and garbage collection

JavaScript is garbage-collected — you never free memory manually. The mental model that prevents leaks matters more than the algorithm:

Memory leaks in JS are almost never "forgot to free". They are accidentally keeping a reference alive — a interval, a listener, a closure, or a global cache holding objects you meant to discard.

ConceptMeaning
Mark-and-sweep GCFrom roots (globals, the stack, handle), follow references; anything unreachable is collected
Reference retentionClosures, timers, event listeners, cached arrays keep objects alive — the leak mechanism
WeakMap / WeakSetKeys held weakly — if nothing else references the key, the entry can be collected. Perfect for per-object metadata and caches
WeakRef / FinalizationRegistryAdvanced: observe or act when an object is collected

The lazy but effective habits: remove event listeners you no longer need, clearInterval when done, prefer bounds/limits on growing caches, and reach for WeakMap when metadata is a side-channel of object identity.

6b.11 Strict mode — the language's self-cleanup

ES5 (2009) added strict mode as a opt-in for new code without breaking old code:

  • Disables silent errors (assignment to read-only props throws).
  • Prevents accidental globals (undeclared x = 1 now throws).
  • Makes plain-function this undefined instead of the global object (see §6b.4) — catching more call-site bugs.
  • Kills a few legacy syntax traps; banning with, octals with 0 prefix.

In modern code you almost never write "use strict" yourself: modules and classes are strict by default. Modules always; classes always. Fine-grained that fixed behaviors arrive even for code that never opted in.

What ECMAScript does not define: DOM, CSSOM, fetch, timers, console, the file system, network sockets, environment variables, browser storage, Web Workers, service workers. All of these are host facilities (§6). When code "doesn't run" in a new environment, the first question is which host API it assumed.

7. Standardization: ECMAScript, TC39, the ES6/2015 tipping point

1996: Netscape hands JS to Ecma International → ECMAScript (the spec name; "JavaScript" is the trademark).

EditionYearMilestone

ES2016+AnnualYearly cadence. async/await (2017), optional chaining ?. (2020), nullish coalescing ?? (2020), top-level await (2022), private fields #x (2022), Object.groupBy / Map.groupBy (2024), etc.

The same pattern as §2, applied to the standard itself — the dominant constraint of an era shaped the next language:

Dominant constraintLanguage response
Browser needed safe glueDynamic, interpreted, GC'd scripting language (§2)
Java syntax required politicallyC/Java-shaped syntax over Scheme-like semantics (§1)
Early tooling was weakForgiving syntax and runtime; survival over rigor
ES3 stagnation → platform divergenceES5 (2009) rescued the already-shipped practical features

Large teams needed maintainabilityStrict mode, then TypeScript around JS (2012+)
Multiple runtimes emerged (Node, Deno, Bun, workers)Host separation got more deliberate (§6); web-standard primitives got first-class
Annual cadenceFeatures arrive in small, additive, browser-verified steps
AI-assisted codingSemantic clarity and runtime mental models matter more; tooling terrain shifts

TC39 process: proposals go through Stage 0 (strawperson) → Stage 1 (proposal) → Stage 2 (draft) → Stage 3 (candidate) → Stage 4 (finished). Two independent implementations required for Stage 4. This is why features take years — the web cannot break.

The web compatibility rule is the engine of all this conservatism: old web code must not break. It is why typeof null === "object" and == coercion survive, why features are almost always additive rather than breaking, and why a genuinely better design that breaks existing pages effectively cannot land. When JS surprises you, ask "what old code does this protect?" first.

8. The engines: V8, SpiderMonkey, JavaScriptCore

Three engines, three lineages:

  • V8 (Google, 2008) — hidden classes + JIT compilation. Also the Node.js runtime. The engine that made JS fast.
  • SpiderMonkey (Mozilla, 1995) — the Eich original. First JS engine. Still powers Firefox.
  • JavaScriptCore (Apple/Safari, forked from KJS) — powers Safari, WebKit, and Bun.

Why engines matter for readers: JIT means performance characteristics are runtime-dependent. Micro-benchmarks lie. "JS is slow" is 20 years out of date — V8 compiles hot paths to machine code. But: JIT warm-up exists, deoptimization happens, and eval/with disable optimization. The engine is part of the platform; the language spec does not guarantee performance.

9. The WASM junction

WebAssembly (2017, cross-browser 1.0) is the partner, not a competitor. WASM is the compile target for C++/Rust/Go in the browser. JS is still the glue — WASM cannot directly touch the DOM (the anyref proposal is in progress). The 2023 WASM Component Model and GC proposal move toward direct host access, but as of 2026, JavaScript remains the required glue layer for any DOM interaction.

Reading code in 2026: if you see import { something } from 'wasm-module' — the heavy lifting is in Rust/C++, JS is the orchestration layer. This is the intended division.

12. Principles — the design bets that survive every change

Everything above, compressed to the rules you can carry and re-derive the details from:

13. Worked examples — semantics and runtime in one trace

Two small programs that exercise the model end to end. Run each mentally; the answer is the whole point.

13a. Ordering: sync, microtask, macrotask

console.log(1);

setTimeout(() => console.log(2), 0);

Promise.resolve()
  .then(() => console.log(3));

console.log(4);
// 1, 4, 3, 2

Why. 1 and 4 are synchronous — they run to completion first. 3 is a microtask: it drains after the current task, before the next macrotask. 2 is a macrotask from the timer — it runs last, after the microtask queue is empty. The answer is 1, 4, 3, 2. This is the ordering rule from §5b in one trace: sync → microtasks → macrotasks → render.

13b. Prototype delegation is a runtime walk

const animal = {
  speak() { console.log("generic sound"); },
};

const dog = Object.create(animal);
dog.speak(); // generic sound — delegated up the chain

dog.speak = function () { console.log("bark"); };
dog.speak(); // bark — own property shadows the chain

delete dog.speak;
dog.speak(); // generic sound — the chain is walked again

Why. Setting dog.speak created an own property that shadowed the delegated one; delete removed it and the chain walk resumed. Nothing was copied between objects at any point — lookup is delegation (§6b.5). This is also why class methods that you expect to "exist on the instance" actually live on the prototype.
