JavaScript: The Language — History, Design, and the Runtime Model

How JS became JS: the 1995 Netscape/Sun deal, the Brendan Eich 10-day sprint, Mocha → LiveScript → JavaScript → ECMAScript, the prototype model, the event loop, single-threaded concurrency, and why a scripting language for form validation became the only language that runs natively in every browser. A foundation doc for the rest of the reference shelf. Sibling to HTML & CSS (the platform substrate JS manipulates).

The other reference docs (React paradigm, Angular evolution, Next.js deep dive, camps survey) treat JS as a given. 1. The 10 days in May 1995

May 1995. Netscape Navigator 1.1 ships. The web is static HTML. Marc Andreessen wants the browser to be programmable — not just display documents, but react to the user. He tasks Brendan Eich, a 34-year-old systems programmer who joined Netscape that April, with building a scripting language for the browser. Constraints: must run in the browser, must be easy for non-programmers (designers, HTML authors), must ship in Netscape 2.0 by September.

Eich has 10 days to produce a working prototype. He draws on two lineages:

  • Scheme (Lisp) — first-class functions, lexical closures, a tiny core. Eich wanted this.
  • Java — the Netscape/Sun alliance meant "Java-like syntax" was a management requirement. The { } braces, ; terminators, new, typeof — all Java-shaped.

The prototype was called Mocha. Shipped in Netscape Navigator 2.0 beta as LiveScript. Renamed JavaScript in December 1995 — the Sun/Netscape marketing handshake: "Java is to the enterprise as JavaScript is to the browser." The name has caused 30 years of confusion. Java and JavaScript share syntax (curly braces) and almost nothing else.

Primary source → Brendan Eich, FAQ: Why is JS designed the way it is? (2011): "I wanted a Lisp-like language but had to use Java-like syntax to pass management approval. Under the { } braces is a lambda-calculus heart beating in a C-shaped body."

2. Why a new language, not a Java applet or C++ extension

The theory you asked for: why create a new language instead of extending Java or C++? The answer is platform constraints.

  • Java applets were already coming (1995). They had a heavyweight JVM, a compile step, static typing, a sandbox. They were for applications inside the browser — heavy, slow to start, overkill for "validate this form before submit."
  • C++ — no one ships a C++ compiler to a browser. No garbage collection, manual memory management, no safe sandbox. The browser needed a language that could not crash the process.
  • The platform needed glue. A scripting shell: mutate the DOM, handle events, validate forms, talk to the server (later: XMLHttpRequest). Glue languages are dynamically typed, garbage-collected, interpreted, and forgiving. Java and C++ are none of these.

The pattern that repeats: A platform deserves a language designed for its constraints, not a hand-me-down from a different platform. This is the same theory that later justifies TypeScript (a JS uplift for large-team maintainability, not a replacement), Go (a C++ replacement designed for networked servers, not a general-purpose systems language), Rust (a C++ replacement that solves memory safety without GC). The constraint changed — the language changed.

3. The design: prototype model, not classes

Eich chose prototypes over classes. The influence: Self (a Smalltalk descendant, prototype-based, from Sun Microsystems labs). In a prototype system, objects inherit directly from other objects — no class as a separate entity. You create an object, it becomes the prototype for others. Object.create(proto) is the primitive.

JavaScript's new + constructor function + .prototype is a thin syntactic layer over this:

// The prototype chain in action
function Animal(name) { this.name = name; }
Animal.prototype.speak = function() { console.log(this.name + ' makes a sound'); };

const dog = new Animal('Dog');
dog.speak(); // Dog makes a sound

// dog.__proto__ === Animal.prototype
// Animal.prototype.__proto__ === Object.prototype
// Object.prototype.__proto__ === null

ES6 class (2015) is syntax sugar over prototypes — not a full class system. It does not introduce private fields (those came later, 2022), does not change single inheritance, does not add multiple dispatch. It hides the delegation. When you read class Dog extends Animal, the prototype chain is still there underneath. Understanding the prototype model matters because the sugar leaks: this binding, method extraction, Object.getPrototypeOf, __proto__ all expose the mechanism.

4. The design: first-class functions, closures, the lambda-calculus heart

The Scheme/Lisp lineage. JavaScript functions are values — they can be assigned, passed, returned, created at runtime. This enables:

  • Higher-order functions — map/filter/reduce take functions as arguments.
  • Lexical closures — a function "captures" its surrounding scope. function outer() { let x = 1; return function inner() { return x++; }; } — inner remembers x after outer returns.
  • Currying — partial application by returning functions that take the next argument.

These are not "features added later." They were there in the 10-day prototype because Eich implemented the lambda calculus directly. The function keyword is a lambda. The closures lesson and currying lesson cover the mechanics; this doc covers the why.

Primary source → Brendan Eich, JavaScript at 20 (2015): "The lambda-calculus heart was there from day one. The C-shaped body was the compromise."

5. The design: single-threaded + event loop

JavaScript is single-threaded by design. One call stack. One thread of execution. The browser's DOM is single-threaded — two threads repainting the same DOM would race. The event loop is the concurrency model:

// Simplified event loop (browser)
// while (queue.length) {
//   const task = queue.shift();
//   task();  // run to completion
//   while (microtaskQueue.length) { microtaskQueue.shift()(); }
//   render();
// }

What maps onto the loop:

APIQueueNotes
setTimeout / setIntervalMacrotaskRuns after current task + all microtasks + render
Promise.then / awaitMicrotaskRuns before next macrotask, after current sync code
queueMicrotaskMicrotaskExplicit microtask scheduling
requestAnimationFrameAnimation frameRuns before next render, after microtasks

The Node.js bet (2009): the same loop works server-side. No threads per request — one loop, many concurrent I/O operations. This is why Node handles 10k connections on one thread while a threaded server needs 10k threads. The trade-off: CPU-bound work blocks the loop. The solution: worker threads (2018) or offload to another process.

5b. Mental models — how developers actually reason about the event loop

Most JS bugs are not syntax bugs — they are mental-model bugs about when code runs. The same loop is the answer, but how a developer imagines the loop determines whether they predict correctly. The four most common mental models in practice:

Mental modelWhat the developer believesWhere it breaksDebugging clue
"Synchronous until proven otherwise" JS runs top-to-bottom; async/await just "waits" inline Mutations after await look like they happen "before" the awaited promise resolves — the developer forgets the continuation is scheduled "Why is x still the old value after I awaited the assignment?" → the assignment is in a microtask after the awaiter already resumed
"setTimeout(fn, 0) means 'immediately'" 0ms = now The callback runs after the current task and all microtasks and render; for heavy pages this can be hundreds of ms "Why didn't my callback fire?" → check the queue; render and microtasks drain first
"await unwraps the value" await p gives you p's value, like sync assignment await yields the current task to the microtask queue; control returns to the event loop first. Anything that ran between the await and the resumption will observe a partial state "Why did my competitor callback see the old state?" → it ran in the microtask gap
"All callbacks are async" Everything JS does is "callback-based", so order doesn't matter Sync code runs to completion first; only when the stack is empty do queued tasks run. Order matters within a task "Why is my callback reading state from a task I thought ran later?" → it ran inside an earlier task, not after

The discipline. The "correct" model is: a single stack runs to completion; tasks queued during the run are processed in queue order after the stack is empty; microtasks drain before the next macrotask. Once this is internalized, the four models above collapse into one. The hard part is that the language lets you write each of the four wrong models and produces sensible-looking output until the bug surfaces in production. This is why "mental model" sections exist in every serious JS doc — not because the loop is complex, but because the developer is often thinking in one of the four shortcuts.

6. The host environment, not the language

The biggest JS insight: JS is a guest in a host. The language spec (ECMAScript) defines the core — syntax, types, objects, functions, the event loop. The host provides everything else:

HostGlobals it provides
Browserwindow, document, fetch, localStorage, WebGL, WebAssembly
Node.jsglobal, require/import, fs, net, process, Buffer
DenoDeno, Deno.serve, Deno.readFile, web-standard APIs
BunBun, Bun.serve, Bun.file, Node-compatible + web APIs
Cloudflare Workersfetch, caches, KV, Durable Objects — no fs, no net

This is why window doesn't exist in Node, fs doesn't exist in the browser, and "isomorphic" code breaks when it assumes a host global. The language is the same; the host changes. The lesson: when reading unfamiliar JS, identify the host first. require → Node/CommonJS. import + Deno → Deno. window → browser.

7. Standardization: ECMAScript, TC39, the ES6/2015 tipping point

1996: Netscape hands JS to Ecma International → ECMAScript (the spec name; "JavaScript" is the trademark).

EditionYearMilestone
ES11997First standard. Baseline.
ES21998Editorial fixes.
ES31999The IE6 era baseline. try/catch, instanceof, regex. No updates for 10 years.
ES4AbandonedOver-ambitious (classes, packages, namespaces, type system). Political death.
ES52009The rescue. Strict mode, JSON, accessor properties (get/set), Object.create, Array.isArray, Function.prototype.bind.
ES6 / ES20152015The rewrite. let/const, arrow functions, class, modules (import/export), Promises, Map/Set, destructuring, default params, rest/spread, Symbol, Proxy, Reflect. Modern JS is born.
ES2016+AnnualYearly cadence. async/await (2017), optional chaining ?. (2020), nullish coalescing ?? (2020), top-level await (2022), private fields #x (2022), Array.groupBy (2024), etc.

TC39 process: proposals go through Stage 0 (strawperson) → Stage 1 (proposal) → Stage 2 (draft) → Stage 3 (candidate) → Stage 4 (finished). Two independent implementations required for Stage 4. This is why features take years — the web cannot break.

8. The engines: V8, SpiderMonkey, JavaScriptCore

Three engines, three lineages:

  • V8 (Google, 2008) — hidden classes + JIT compilation. Also the Node.js runtime. The engine that made JS fast.
  • SpiderMonkey (Mozilla, 1995) — the Eich original. First JS engine. Still powers Firefox.
  • JavaScriptCore (Apple/Safari, forked from KJS) — powers Safari, WebKit, and Bun.

Why engines matter for readers: JIT means performance characteristics are runtime-dependent. Micro-benchmarks lie. "JS is slow" is 20 years out of date — V8 compiles hot paths to machine code. But: JIT warm-up exists, deoptimization happens, and eval/with disable optimization. The engine is part of the platform; the language spec does not guarantee performance.

9. The WASM junction

WebAssembly (2017, cross-browser 1.0) is the partner, not a competitor. WASM is the compile target for C++/Rust/Go in the browser. JS is still the glue — WASM cannot directly touch the DOM (the anyref proposal is in progress). The 2023 WASM Component Model and GC proposal move toward direct host access, but as of 2026, JS remains the mandatory DOM/has mandatory for any DOM interaction.

Reading code in 2026: if you see import { something } from 'wasm-module' — the heavy lifting is in Rust/C++, JS is the orchestration layer. This is the intended division.
