Complexity — the quick review

The full theory lives in CS & Software Engineering; the working version:

ClassMeansPractical rule of thumb
O(1)Constant — hash lookup, array indexInstant; the target for lookups
O(log n)Halving — binary search, balanced tree opsn = 1 million → ~20 steps. The surprise: it's nearly free
O(n)Single passn = 1 million → 1M steps; fine
O(n log n)Sorting, divide-and-conquerThe default ceiling for "good" solutions
O(n²)Nested loopsn = 1,000 → 1M steps (ok); n = 100,000 → disaster
O(2ⁿ), O(n!)ExponentialOnly for n ≤ 20 (brute-force search, permutations)

Amortized analysis — the one idea that surprises: an operation that's sometimes expensive is measured averaged over many calls. Pushing onto a dynamic array is "O(1) amortized": most pushes are O(1), the occasional resize (doubling) is O(n), but doubling means each element is copied at most ~log n times — so the average is constant. When a solution "feels" O(n²) but passes, you're often looking at amortized behavior (e.g., a string built with += in a loop, or two-pointer scans that each element enters once).

Space-time trade-off: almost every "fast" trick buys time with memory — hash maps cache results, DP tables store states, prefix sums precompute ranges. When a problem says "must be O(n)" and you're stuck, the question to ask is "what could I remember?"

Arrays, strings, and hashing — the 80%

Most interview problems — and most production code — are these three structures. Master this section and you can pass the majority of easy and many medium problems.

Hash maps and sets — how O(1) actually works

  • Internals: the key is hashed to a bucket; collisions are handled by chaining (a list per bucket) or open addressing. The O(1) claim depends on the load factor (keys ÷ buckets) staying low — that's why hash maps resize when they fill up.
  • When O(1) degrades to O(n): adversarial keys that all hash to one bucket (a known attack — some languages randomize hashing), or — in JS — the classic trap of using an object as a map and getting prototype pollution or string-coerced keys (obj[1] and obj["1"] are the same key). Use Map/Set for real key semantics.
  • The pattern that wins problems: "count occurrences" (frequency map), "have I seen this before?" (seen set), "complement lookup" (two-sum family: store target - current and check it next).

Two pointers — the template

// sorted array: find the pair summing to target
let lo = 0, hi = arr.length - 1;
while (lo < hi) {
  const sum = arr[lo] + arr[hi];
  if (sum === target) return [lo, hi];
  sum < target ? lo++ : hi--;
}
return null;

When it applies: sorted arrays (pair sums, dedup, three-sum families), palindrome checks, "reverse in place". The invariant: pointers only move one direction, so total work is O(n) — each element is visited at most twice.

Sliding window — the template

// longest substring with no repeating characters
let seen = new Set(), left = 0, best = 0;
for (let right = 0; right < s.length; right++) {
  while (seen.has(s[right])) seen.delete(s[left++]);
  seen.add(s[right]);
  best = Math.max(best, right - left + 1);
}
return best;

When it applies: "longest/contiguous/subarray" phrases — max sum of k-length window, substring with at most k distinct, minimum window. The shape is always: expand right, shrink left while the constraint breaks, record the best. Amortized O(n): left and right each traverse once.

Prefix sums

Precompute prefix[i] = sum of elements 0..i-1, then any subarray sum is prefix[j+1] - prefix[i] in O(1). The upgrade pattern: "range sum queries" or "subarray sums equal to k" become a hash map of prefix counts — a classic "what could I remember?" move.

Stacks, queues, and linked lists — the shapes

Stack — the monotonic-stack pattern

A stack is "next thing to undo", "matching pairs", and — the interview superpower — the monotonic stack: keep the stack increasing (or decreasing) by popping while the new element violates the order. That yields "next greater element" in O(n):

// next greater element for each position, -1 if none
const out = new Array(nums.length).fill(-1), stack = [];
for (let i = 0; i < nums.length; i++) {
  while (stack.length && nums[stack[stack.length - 1]] < nums[i])
    out[stack.pop()] = nums[i];
  stack.push(i);
}
return out;

Classic stack problems: valid parentheses (push openers, pop on closer, check the top matches), expression evaluation (two stacks: values + operators), daily temperatures, largest rectangle in histogram.

Queue — BFS's partner

A queue is "first in, first out" — the shape of breadth-first traversal and of any "process in arrival order" problem. In JS, an array with shift() is O(n); for correctness-first solutions it's fine, for performance use an index pointer or a real queue.

Linked lists — rarely the answer, often the question

  • The honesty rule: in JS (and most high-level languages), arrays beat linked lists for nearly everything — cache locality, indexing, memory. Linked-list problems are asked because they test pointer discipline and recursion, not because production code uses them much.
  • Core operations to have memorized: reversal (iterative: three pointers — prev, curr, next), cycle detection (Floyd's tortoise and hare: slow +1, fast +2, they meet iff a cycle exists), finding the middle (same hare technique), merging two sorted lists (dummy-head pattern).
  • The dummy-head trick: start every insertion-heavy list algorithm with a dummy node before the head so the "empty list" and "insert at front" cases need no special handling. It removes a whole class of edge-case bugs.

Worked example — the LRU cache

The one linked-list problem that is also a real production structure: an LRU (least-recently-used) cache is a doubly linked list for order plus a hash map for O(1) lookup of each node. get and put must both be O(1) — the list gives O(1) remove-and-move-to-front, the map gives O(1) find — and evicting is "pop the tail". The dummy-head trick keeps the list operations edge-free:

class LRUCache {
  constructor(cap) {
    this.cap = cap;
    this.map = new Map();            // key → node, for O(1) lookup
    this.head = { key: null, prev: null, next: null };  // most recent
    this.tail = { key: null, prev: null, next: null };  // least recent
    this.head.next = this.tail; this.tail.prev = this.head;
  }
  _remove(node) { node.prev.next = node.next; node.next.prev = node.prev; }
  _insert(node) {                    // splice right after the head (most recent)
    node.prev = this.head; node.next = this.head.next;
    this.head.next.prev = node; this.head.next = node;
  }
  get(key) {
    const node = this.map.get(key);
    if (!node) return -1;
    this._remove(node); this._insert(node);   // touch → most recent
    return node.value;
  }
  put(key, value) {
    if (this.map.has(key)) this._remove(this.map.get(key));
    const node = { key, value, prev: null, next: null };
    this.map.set(key, node);
    this._insert(node);
    if (this.map.size > this.cap) {      // evict the tail
      this.map.delete(this.tail.prev.key);
      this._remove(this.tail.prev);
    }
  }
}

The takeaway: the hash map alone can't track recency, and the list alone can't find a node in O(1) — the pair is the whole point. Recognize "cache with a size limit" and you've recognized this shape.

Trees and heaps — the hierarchies

Binary trees — traversals first

Traversals are the grammar of every tree problem; the four patterns, memorized:

// recursive in-order — the shape of all three
function inorder(node, out = []) {
  if (!node) return out;
  inorder(node.left, out);
  out.push(node.val);
  inorder(node.right, out);
  return out;
}
  • Pre-order (node, left, right): copy/serialize a tree, expression prefix.
  • In-order (left, node, right): a BST in in-order is sorted — the most reused fact in tree problems (validate BST by checking the in-order traversal is ascending).
  • Post-order (left, right, node): delete/child-dependent work, expression evaluation — compute children first, then combine at the parent.
  • Level-order (BFS) with a queue: "zigzag", "right side view", "min depth" — anything phrased per-level.

Iterative replacements: interviews often ban recursion's implicit stack for deep trees — in-order iteratively = a stack you push lefts onto and pop between right moves; pre-order = push right then left. The recursive version is the memory anchor; derive the iterative one from it under pressure.

BST and the balanced-tree fact

A BST's insert/search/delete are O(log n) when balanced. Unbalanced (sorted input, naive insert) they degrade to O(n) — a linked list in disguise. That's the whole reason AVL/Red-Black trees exist (self-balancing on every insert). In interviews: know that balanced BSTs give you ordered operations with O(log n) — and that production code uses library structures instead: JS's Map/Set, or a sorted array + binary search, which is O(n) to insert but O(log n) to search and is fine for small n.

Trie — prefix matching

A trie is a tree of characters: each node holds a map of child characters and a flag "a word ends here". Insert and search are O(word length).

class Trie {
  constructor() { this.root = { children: {}, end: false }; }
  insert(word) {
    let node = this.root;
    for (const ch of word) {
      node.children[ch] ??= { children: {}, end: false };
      node = node.children[ch];
    }
    node.end = true;
  }
  search(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children[ch]) return false;
      node = node.children[ch];
    }
    return node.end;
  }
}

When it wins: autocomplete (descend to the prefix, then enumerate the subtree), word-search on a board, "starts with" queries. The alternative — a hash map of every prefix — works but wastes memory; the trie shares prefixes structurally.

Heap / priority queue — the top-K pattern

A heap is a binary tree with one invariant: the parent is ≤ (min-heap) or ≥ (max-heap) its children. push and pop are O(log n), peek is O(1). That gives the two classic wins:

  • Top-K: "k largest/smallest, k most frequent, k closest" — a min-heap of size k: push each element; when the heap exceeds k, pop the smallest. Result: the k largest, in O(n log k) — no full sort needed.
  • Median maintenance: two heaps — a max-heap for the lower half, a min-heap for the upper half, rebalanced after each insert. Median = peek of the larger heap (or average of both peaks). O(log n) per insert.
  • Merge k sorted lists: push each list's head, pop the smallest, push its successor — the standard "merge k things" shape.

JS has no built-in heap — the interview move is to implement a small binary heap (~25 lines: push/pop with sift-up/sift-down) once, from memory, or use Array.sort() when n is small enough (sorting is often the lazier correct answer).

class MinHeap {
  constructor() { this.a = []; }
  size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(v) {
    this.a.push(v);
    let i = this.a.length - 1;
    while (i > 0) {                 // sift-up: swap with parent
      const p = (i - 1) >> 1;
      if (this.a[p] <= this.a[i]) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]];
      i = p;
    }
  }
  pop() {
    const top = this.a[0];
    const last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;
      while (true) {                // sift-down: swap with smaller child
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < this.a.length && this.a[l] < this.a[m]) m = l;
        if (r < this.a.length && this.a[r] < this.a[m]) m = r;
        if (m === i) break;
        [this.a[m], this.a[i]] = [this.a[i], this.a[m]];
        i = m;
      }
    }
    return top;
  }
}

The two invariants to keep straight: sift-up on push (new element walks toward the root while it's smaller than its parent), sift-down on pop (the promoted last element walks toward the leaves while it's larger than a child). For a max-heap, flip the comparisons. For "k largest", push into a min-heap of size k — the root is the smallest of the current top-k, so it's the one to evict.

Recursion — the self-referential move

Every structure above is finite and concrete; recursion is the idea that a function can be its own template — a problem solved by solving a smaller version of the same problem. You've been using it since the tree traversals (§4): inorder(node) calls inorder(node.left). A standalone treatment because it is the engine behind DFS (§6), divide-and-conquer (§7), and DP (§8), and because the two failure modes are common and cheap to fix.

The shape, always two parts: a base case that stops the recursion (smallest input, no further call), and a recursive case that calls itself on a strictly smaller input. If the recursive case ever fails to shrink toward the base case, you get infinite recursion → stack overflow. That's the whole discipline.

// power(x, n): multiply x by power(x, n-1) — smaller input, base case at n === 0
function power(x, n) {
  if (n === 0) return 1;              // base case
  return x * power(x, n - 1);         // recursive case, strictly smaller
}

How to write one under pressure: 1) identify the smallest input and write its answer as the base case; 2) trust that the recursive call works for smaller inputs (the "leap of faith" — don't trace it); 3) ask "given the answer for a smaller instance, how do I build the answer for this one?" The last step is the same question DP asks — recursion with a cache is memoized DP, so a clean recursive solution is one memo away from a DP solution (§8).

When to abandon recursion: every call burns a stack frame; deep chains (a grid of 10,000 cells in DFS, a very long list) overflow the call stack — a recursion limit, not a logic error. Two escapes: make it iterative with an explicit stack (you control the memory), or use BFS (§6), which never recurses. Anything you can write recursively you can write with a stack you push onto — the stack is the recursion. Rule of thumb: recursion for tree depth (safe, O(log n)); explicit stack for graph depth (arbitrary).

Divide-and-conquer vs DP — the distinction that clarifies both

Both divide a problem into subproblems, solve them, and combine. The difference is what the subproblems overlap on:

Divide-and-conquerDP
SubproblemsDisjoint — each appears once (merge sort halves don't overlap)Overlapping — the same subproblem recurs (fib(5) needs fib(3) twice)
CombinationCombine independent results up the tree (merge two sorted halves)Reuse the cached answer; no re-computation
Work shapeEach level splits; total O(n log n)-ishEach state computed once; total O(states · transition)
ClassicMerge sort, quicksort, binary search, "count inversions"Fibonacci, LCS, coin change, grid paths
The tell"Split in half, solve each, merge" — subproblems are independent"Same subproblem asked again" — a recursion tree where nodes repeat

The test that settles it: draw the recursion tree for your recurrence. If the same state appears in multiple branches, the naive recursion recomputes it — that's the DP signal (add a cache). If every state appears once, you have divide-and-conquer, and caching buys nothing.

Weighted vs unweighted changes nothing in the representation — weights live on the edges — but changes the algorithm: unweighted → BFS for shortest path; weighted → Dijkstra.

BFS — the template

// shortest path (unweighted) from start; dist of -1 = unreachable
function bfs(graph, start, n) {
  const dist = new Array(n).fill(-1);
  dist[start] = 0;
  const queue = [start];
  for (let qi = 0; qi < queue.length; qi++) {   // index pointer = O(1) shift
    const u = queue[qi];
    for (const v of graph[u] ?? []) {
      if (dist[v] === -1) { dist[v] = dist[u] + 1; queue.push(v); }
    }
  }
  return dist;
}

The rules: first visit = shortest distance (that's what makes BFS the shortest-path algorithm on unweighted graphs); mark visited at enqueue, not dequeue, or you enqueue duplicates; the index-pointer queue avoids O(n) shift(). "Rotting oranges", "walls and gates", "nearest 0" — all the same shape with a multi-source start (enqueue all sources first).

DFS — recursive and iterative

// connected components: every node gets its component id
function components(graph, n) {
  const comp = new Array(n).fill(-1);
  let id = 0;
  function dfs(u) {
    for (const v of graph[u] ?? []) if (comp[v] === -1) { comp[v] = id; dfs(v); }
  }
  for (let u = 0; u < n; u++) if (comp[u] === -1) { comp[u] = id; dfs(u); id++; }
  return comp;
}

When DFS beats BFS: reachability, cycle detection (directed: three states — unvisited / in-progress / done — an edge to an in-progress node is a back edge), topological sort (see below), and anything recursive (grid flooding — "number of islands" is this loop with a flood-fill dfs). For deep grids, recursion can blow the call stack — the iterative version uses an explicit stack, and a visited set at push time.

Topological sort — DFS or Kahn's

Dependency ordering: "finish all prerequisites" or "course schedule". Kahn's algorithm: count in-degrees, enqueue zero-degree nodes, process, decrement neighbors; if the processed count < V, there's a cycle. The DFS version is a post-order accumulation, reversed. Both are O(V + E) and both double as cycle detectors — the "can it even be done?" answer the problem is really asking.

Dijkstra — the weighted shortest path

BFS's weighted cousin: same "first settle = best" idea, but the queue becomes a priority queue keyed by distance, and you skip stale entries:

function dijkstra(graph, start, n) {
  const dist = new Array(n).fill(Infinity); dist[start] = 0;
  const pq = [[0, start]]; // binary heap of [dist, node]
  while (pq.length) {
    const [d, u] = heapPop(pq);
    if (d > dist[u]) continue;            // stale entry — skip
    for (const [v, w] of graph[u] ?? []) {
      if (d + w < dist[v]) { dist[v] = d + w; heapPush(pq, [dist[v], v]); }
    }
  }
  return dist;
}

The rule that matters: Dijkstra fails on negative edges (an already-settled node can be improved later) — that's Bellman-Ford's job. And "shortest path in a grid" is BFS only when all moves cost the same; a 0/1 grid can use a deque (0-cost moves push front).

Union-Find — connectivity without building the graph

class UnionFind {
  constructor(n) { this.parent = Array.from({length: n}, (_, i) => i); this.rank = new Array(n).fill(0); }
  find(x) { while (this.parent[x] !== x) { this.parent[x] = this.parent[this.parent[x]]; x = this.parent[x]; } return x; }
  union(a, b) {
    const ra = this.find(a), rb = this.find(b);
    if (ra === rb) return;
    if (this.rank[ra] < this.rank[rb]) [ra, rb] = [rb, ra];
    this.parent[rb] = ra;
    if (this.rank[ra] === this.rank[rb]) this.rank[ra]++;
  }
}

Why it's the hidden winner: "number of connected components in a network", "friend circles", "accounts merge", Kruskal's MST — anything about connectivity that grows edge by edge. Path compression (the find loop shortcutting to the root) + union by rank make both operations near-O(1) amortized — faster than re-running BFS after every new edge.

Binary search — the template that never off-by-ones

// first index where isGood(i) is true, else hi+1... pattern:
let lo = 0, hi = arr.length;          // search space [lo, hi)
while (lo < hi) {
  const mid = (lo + hi) >> 1;         // floor, no overflow in JS
  if (isGood(mid)) hi = mid;          // good → keep mid
  else lo = mid + 1;                  // bad → discard mid
}
return lo;                            // first good index
  • The invariant: the range [lo, hi) half-open, "first index where the predicate flips from false to true". Search for a value: isGood = arr[mid] >= target — the answer is the first element ≥ target (which handles "target exists" and "insert position" in one).
  • The variants (first/last occurrence, ceiling, rotation point) all reduce to choosing the predicate — never rewrite the loop body, change isGood.
  • The hidden pattern: binary search works on any monotonic predicate, not just sorted arrays — "find the smallest capacity that can ship in d days", "find the kth smallest pair distance" — if the answer space is monotonic (can I afford X? yes → also yes for larger X), binary search the answer.

Dynamic programming — the state machine of optimization

DP is the hardest family because it looks like recursion and is actually cached enumeration. The framework, applied every time:

  1. Define the state — the minimal description of a subproblem: "dp[i] = max profit with i items", "dp[r][c] = paths to cell (r, c)". The state is the single most important decision; a wrong state means a wrong answer that looks right.
  2. Write the transition — how dp[i] is built from smaller states: "dp[i] = max(dp[i-1], dp[i-2] + v[i])". If you can't write the transition, you don't understand the recurrence yet — go back to state definition.
  3. Set the base cases — dp[0], dp[1], the empty grid row/col. Base cases are where most off-by-ones die.
  4. Choose memoization or tabulation — memo = recursion + a cache (write the brute-force recursion, add the cache, done — the laziest correct path); tabulation = build the table bottom-up, which avoids recursion and often needs less space.

The lazy order under time pressure: 1) brute-force recursion (correct, slow), 2) add a memo cache (now O(n · states)), 3) if memory is the constraint, convert to tabulation and compress the table (keep only the last row/column — most 1D and 2D DPs need only one or two rows). Steps 1–2 are often enough to pass.

A functional note (the FP edge): memoized DP is pure functions + a cache — the same "remember the answer" idea the lambda calculus gets by substitution. reduce is the tabulation loop in disguise: states.reduce((acc, x) => transition(acc, x), base) is a 1D DP with a single accumulator. The shelf's FP foundations (What Is State, JavaScript: The Language) are all the FP you need here — no monads required.

Greedy — the beautiful lie

Greedy: take the locally best move and hope it's globally optimal. When it works it's O(n) and elegant; when it doesn't it's wrong with a plausible-looking answer. The test is the exchange argument: "if an optimal solution differs from mine, I can swap my choice in without making it worse" — if you can't sketch that argument, greedy is a gamble, and DP is the safe answer.

  • Interval scheduling — "max non-overlapping meetings": sort by end time, always take the earliest-ending compatible one. The canonical greedy and the exchange argument everyone learns first.
  • Activity selection / jumps — "jump game": at each position, remember the furthest reach; greedy works because the reachable set only grows.
  • Huffman coding — always merge the two smallest; optimal prefix codes fall out.
  • The tell: problems phrased "minimize the number of X" or "maximize Y with these resources" where a simple ordering argument exists. When in doubt, DP.

Bit manipulation and math — the trick drawer

  • XOR properties: a ^ a = 0, a ^ 0 = a, XOR is commutative/associative → "the single number that appears once among pairs" is arr.reduce((a, b) => a ^ b). XOR also swaps two variables and finds the two unique numbers (xor all, then split on a set bit).
  • Bit tricks: n & (n - 1) clears the lowest set bit (→ count bits by looping it), n & -n isolates the lowest set bit (→ the split trick above), x >> 1 is division by 2 (the binary-search mid).
  • Masks: a bitmask is a set of small integers — "subsets of n items" = iterate 0..2ⁿ-1 and test mask & (1 << i). Only for n ≤ 20.
  • Math staples: GCD via Euclid (while (b) [a, b] = [b, a % b]), modular arithmetic (a mod m rules; modular exponentiation by repeated squaring), the sieve of Eratosthenes for primes up to n in O(n log log n), combinatorics (n choose k via Pascal's triangle / multiplicative formula).
