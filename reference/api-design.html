API Design — How Contracts Make Systems Speak Without Speaking

The discipline of defining contracts that services and clients can evolve independently around. Sibling docs: System Design (the architectural layer upstream), Backend Engineering (the server implementation layer behind the contract), How Developers Think (the frontend implementation loop downstream), UI/UX & Web Design (the rendering layer that consumes the contract).

Language: English · العربية

Why this doc exists separately

Most tutorials teach "how to call an API" or "how to write an OpenAPI file." API Design starts at "what contract lets both sides move without breaking each other." It is a distinct discipline with its own history, methods, and failure modes — not "REST vs GraphQL" as a religion, not "Swagger authoring" as a chore, not "SDK generation" as a silver bullet. This doc captures it as a first-class engineering concern: the interface layer that feeds system design and the developer loop. If you've ever shipped a breaking change that took down a mobile app in production, this is the layer you missed.

How to use this doc

Reading order: standalone. Cross-links:

  • Upstream to System Design — system design decides service boundaries and data ownership; API design materializes those boundaries as callable contracts.
  • Downstream to How Developers Think When Building a Frontend Feature — the developer loop consumes APIs; bad contracts create friction the loop absorbs (loading states, error handling, retries, optimistic UI).
  • Cross-cutting to UI/UX & Web Design — every screen is a read and write through the API contract; awkward contracts intrude on the UI as dead states, toast storms, and invisible failures.
  • Cross-cutting to JavaScript Across Stacks — language and runtime choices (TypeScript, Rust, Go) are often driven by contract ergonomics (codegen, schema validation, streaming).
  • Reference: Glossary — shared vocabulary across all reference docs.

The two-layer answer to "what is an API contract?"

  • Interface contract (macro) — resources, operations, versioning, authentication, rate limits, deprecation policy, error envelope, pagination strategy, idempotency semantics. What the consumer sees.
  • Wire contract (micro) — serialization format, schema evolution rules, field-level nullability, enum extensibility, timestamp formats, cursor encoding, compression, transport (HTTP/1.1, HTTP/2, HTTP/3, gRPC, WebSocket). What the bytes say.

Both are API design; neither is complete without the other. The interface contract sets the promises; the wire contract makes them verifiable.

Definition — what API design is and what it is not

What it is

API Design is the disciplined activity of defining stable, evolvable contracts between independent deployables. It produces decisions — not code — that determine:

  • Resource topology — what are the nouns? How do they relate? (REST) or what is the query/mutation surface? (GraphQL) or what are the service/method signatures? (gRPC).
  • Operation semantics — what does each call promise? (safety, idempotency, latency budget, consistency model).
  • Error contract — how does the API say "no" in a way the client can programmatically act on? (error codes, retry-after, problem details).
  • Versioning strategy — how do we add, change, and remove without breaking existing clients? (URL version, header version, schema evolution).
  • Identity & auth — who can call what? (OAuth 2.0, OIDC, mTLS, API keys, SPIFFE).
  • Observability hooks — what does the API emit so both sides can debug? (request-id, trace headers, structured logs, metrics).
  • Evolution guarantees — what changes are "safe" (add optional field, add enum value) vs "breaking" (remove field, change type, change semantics).

These decisions are expensive to change later. That is the defining characteristic: API design decisions have high reversal cost. Wire-format changes require coordinated deployments. Interface-contract changes require consumer migrations. Both are multi-week efforts in any non-trivial system.

What it is not

Evolution — constraint inversions across the same idea

The core idea — a stable boundary between independent deployables — did not change. What changed is the dominant constraint, and the style that won:

Dominant constraintWinning styleWhy it fit
Language interop + binary efficiency (1990s)CORBA / DCOM / RMIIDL + stubs gave compile-time safety across C++, Java, VB. Network was LAN; latency negligible.
Enterprise integration + tooling (early 2000s)SOAP / WSDLXML Schema + WSDL gave contract-first tooling for Java/.NET enterprises. Firewalls allowed HTTP 80/443.
Web-scale + browser clients (mid 2000s)REST + JSONHTTP semantics (caching, verbs) + JSON (lightweight, JS-native) + URL versioning = deployable by two-pizza teams.
Mobile bandwidth + many clients (2010s)GraphQLSingle request, exact fields, introspection. Mobile teams own the query; backend owns the resolver map.
Internal microservices + streaming (2015+)gRPC / ProtobufHTTP/2 multiplexing, binary encoding, codegen in 10+ languages, streaming RPC. Latency & throughput critical.
Event-driven + loose coupling (2017+)AsyncAPI / CloudEventsProducer doesn't know consumer. Schema registry + consumer-driven contracts. Replay, audit, choreography.
Type-safe DX + monorepo (2020+)tRPC / Zod / GraphQL CodegenSchema = source of truth. Types flow to client without codegen step. Colocation beats contract testing.
AI-augmented authoring (2023+)LLM → OpenAPI → SDK → DocsHuman writes intent; machine writes contract + artifacts. Review loop replaces authoring loop.

The pattern repeats: when the dominant constraint changes (binary efficiency → firewall traversal → browser native → mobile bandwidth → internal throughput → loose coupling → developer experience → AI authoring), the old style's ergonomics become friction and a new style absorbs the constraint.

Underlying theory — what makes a contract designed not accidental

TheoryOriginWhat API design takes from it
Communicating Sequential Processes (CSP) Tony Hoare, 1978 Processes communicate via typed channels. Contracts are channel types; versioning is channel protocol evolution.
Lamport Clocks & Happened-Before Leslie Lamport, 1978 Idempotency keys and request deduplication rely on causal ordering. "At least once" delivery + idempotency = exactly-once semantics.
CAP Theorem & PACELC Eric Brewer (2000), Gilbert & Lynch (2002), Daniel Abadi (2010) Every API operation implies a consistency choice. The contract must declare it (strong, eventual, read-your-writes, causal) — Dynamo made the dial concrete with tunable N/R/W quorums (api-design-Δ10).
HATEOAS / Hypermedia Constraint Roy Fielding, 2000 Clients navigate via links, not out-of-band knowledge. The contract includes discoverability. Rarely fully implemented; the idea shapes pagination and versioning. Fielding's uniform interface has four facets worth checking a design against: resource identification, manipulation through representations, self-descriptive messages, hypermedia (api-design-Δ3).
Postel's Law (Robustness Principle) Jon Postel, RFC 791 (1981) "Be liberal in what you accept, conservative in what you send." API design applies this to schema evolution: accept extra fields, never send unexpected ones.
Richardson Maturity Model Leonard Richardson, 2008 Four levels: RPC over HTTP → Resources → HTTP Verbs → Hypermedia. A diagnostic, not a prescription. Most production APIs sit at Level 2–3.
Interface Segregation Principle (SOLID) Robert C. Martin, 2000 Clients shouldn't depend on methods they don't use. In APIs: narrow resources, separate read/write models, avoid "god endpoints" that return everything.
Schema Evolution Rules (Avro / Protobuf / JSON Schema) Apache Avro, Google Protobuf, IETF JSON Schema Formal rules for backward/forward compatibility: add optional fields, never remove required, never change type, enum extensions are safe if consumers ignore unknown.

Mental models — how API designers actually reason

The theories above are the guardrails. The mental models are how you navigate inside them. Each model compresses the theories for a specific decision context:

ModelCore ideaWhen you reach for itWhat it replaces
Contract as product The API is the product for the consumer. Versioning, deprecation, migration, and support are product management. Deciding how long to support v1; whether to break a field; writing changelogs. "It's just an interface" (treats contract as implementation detail).
Schema as source of truth The schema (OpenAPI, Protobuf, Zod) generates types, tests, docs, mocks, SDKs. Code conforms to schema, not vice versa. Starting a new service; enforcing compatibility in CI; generating client SDKs. Writing types by hand; manual docs; ad-hoc validation.
Consumer-driven contracts Consumers publish expectations (Pact, Spring Cloud Contract). Providers verify against them. Breaking changes fail fast. Polyglot microservices; independent deployments; team autonomy. Provider-driven schema; integration test theater.
Idempotency keys = exactly-once Network fails; retries happen. Idempotency key (client-generated) + server dedup = exactly-once semantics on "at-least-once" transport. Any mutation endpoint (POST, PATCH, DELETE). Especially payments, orders, provisioning. Hoping retries don't double-charge; distributed transactions.
Versioning by media type, not URL Accept: application/vnd.myapi.v2+json keeps URL stable; clients opt in. URLs identify resources; media types identify representations. Long-lived APIs with many consumers; avoiding /v1/, /v2/ URL sprawl. URL versioning (/api/v1/); header versioning without media type.
Gateway as translation layer Internal services evolve independently; gateway translates (GraphQL→REST, Protobuf→JSON, v1→v2). Consumers see stable contract. Brownfield migration; polyglot internals; external partner APIs. Changing all services simultaneously; shared library coupling.
Evolution over revolution Add fields, never remove. Deprecate with headers (Sunset, Deprecation), timelines, migration guides. Break only when cost of carry > cost of break. Every schema change; deprecation planning; stakeholder communication. Big-bang v2 launches; silent breaking changes.

Anti-pattern: Writing the OpenAPI file after the code ships. The schema is the contract — if it's generated from implementation, the implementation is the contract, and you've lost the ability to design it.

The rhythm, not the algorithm

Like Design Thinking and System Design, API Design is a rhythm, not a structured algorithm. It fails the three algorithm tests:

  • Inputs aren't predefined. You don't know all client use cases when you design the first version. The contract discovers them through usage, feedback, and migration pain.
  • Steps aren't deterministic. There is no rule that says "now add pagination." You add it when the first client hits the 10k-row response and times out — a judgment call.
  • No fixed termination. "Done" means "the contract serves current clients and has a documented evolution path for the next 12 months." That is a strategic judgment, not a predicate.

This is why API design resists checklists that pretend to be complete. A checklist assumes you know all consumers; the rhythm assumes you know what's missing for the ones you have — a product/engineering judgment.

The "Schema-First" rhythm hack. Schema-first (write OpenAPI/proto before code) solves the "no fixed termination" problem by making the contract the artifact of review. The contract becomes the PR description. CI fails if the implementation diverges from the schema. It's a process guardrail — useful when enforced, dangerous when the schema becomes a ceremonial document nobody reads.

Methodologies / styles — the named approaches

Multiple named styles exist. None is canonical; each is a different packaging of constraints for a dominant use case.

StyleCore constraintsOriginBest for
REST (Level 2–3) Resources + HTTP verbs + status codes + JSON + URL versioning + HATEOAS (optional) Fielding (2000), Richardson (2008) Public HTTP APIs, many heterogeneous clients, caching critical, team autonomy over client SDKs.
GraphQL Schema + resolvers + client queries + introspection + single endpoint + mutations Facebook (2015) Mobile-first, many client teams, over/under-fetching pain, product-driven backend.
gRPC / Protobuf IDL (proto) + HTTP/2 + codegen + streaming + deadline propagation Google Stubby (2001), open-sourced 2015 Internal microservices, polyglot, high throughput, streaming, strong typing across languages.
AsyncAPI / Event-driven Message schemas + channels + bindings (Kafka, AMQP, MQTT, HTTP webhook) + correlation IDs AsyncAPI Initiative (2017), CloudEvents (2019) Loose coupling, event sourcing, choreography, audit/replay, multiple unknown consumers.
tRPC / Zod / Type-safe full-stack TypeScript-first, inferred types from runtime validators, no codegen step, colocation tRPC (2021), Zod (2020) Monorepo / full-stack TypeScript, end-to-end types without schema files, rapid iteration.
Webhooks (push contracts) POST to registered URL + signature verification + retry with backoff + idempotency key GitHub, Stripe, Slack (2010s) Server-to-server notifications, async completion, third-party integrations.

One cross-style note: deadlines and cancellation are contract citizens, not client afterthoughts — gRPC promotes them to first-class RPC arguments, and REST approximates them with timeouts documented per endpoint.

All seven share the same DNA: define the boundary → make it machine-verifiable → evolve it without breaking consumers. The differences are transport, serialization, coupling model, and who owns the query shape.

Principles — the shared constants

Across every style, eight principles hold:

  1. Contract-first. The contract (OpenAPI, proto, GraphQL SDL) is the source of truth. Code generates from it; tests verify against it; docs render from it.
  2. Idempotency by default on mutations. Every POST/PATCH/PUT that mutates state accepts an Idempotency-Key header. Retries are safe; clients don't guess.
  3. Error as API, not accident. Every error returns a structured envelope (RFC 9457 Problem Details or equivalent): type, title, status, detail, instance, retry_after. Clients switch on type, not string matching. JSON problem details are served as application/problem+json (api-design-Δ6).
  4. Versioning as deliberate breaking-cost. Breaking changes get a new version (URL or header) with a sunset date. Non-breaking changes (add optional field, add enum value) ship in the same version. The cost of a version bump is explicit.
  5. Narrow surface, deep capability. Prefer many small resources/operations over one "god endpoint." Interface Segregation applies: clients depend only on what they use.
  6. Predictable failure modes. Rate limits return 429 with Retry-After. Timeouts are documented. Partial failures (batch APIs) return per-item status, not a single 500.
  7. Observability built-in. Every response includes X-Request-ID. Traces propagate traceparent (W3C Trace Context). Metrics expose latency percentiles, error rates, saturation.
  8. Discoverability ≠ documentation. The schema is the contract. Docs explain why and how; the schema defines what. Both stay in sync via CI.

Collections — pagination, filtering, sorting, and search

Collections are where most contracts earn their complexity. Decide these once and reuse across every list.

Pagination styles

StyleUse whenRisk
Offset (?offset=)Small datasets, admin UIsO(n) scans; drift under concurrent writes
Cursor / keysetLarge or actively written datasetsRequires a stable sort key
Page numberSimple low-scale UISame problems as offset
Streaming / SSEContinuous, append-heavy updatesMore complex client state

Cursor guidance: cursors are opaque; encode the sort position, not the raw ID unless safe; handle deleted items gracefully; return next_cursor (not just a boolean has_more); define expiry if the cursor contains signed state.

Filtering / sorting conventions

GET /shipments?
    status=IN_TRANSIT&
    created_after=2026-01-01T00:00:00Z&
    sort=created_at:desc,status:asc&
    limit=50&
    cursor=abc123
  • Use direct field names or filter[field] — pick one syntax and stay consistent.
  • sort=field:asc|desc, repeatable for multiple fields; document the default sort.
  • Enforce a maximum limit; document what happens when a client exceeds it.
  • Invalid filter values are 400 with a field-level validation error (validation errors), never a silent ignore.

Validation errors & transactional safety

A 422 that just says "bad request" is a dead end for a frontend form. Field-level validation errors turn an error into recoverable UI state.

{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Validation Failed",
  "status": 422,
  "detail": "Request body failed validation.",
  "instance": "/v1/shipments",
  "errors": [
    { "field": "status",       "code": "invalid_enum",   "message": "Status must be one of CREATED, PICKED_UP, IN_TRANSIT." },
    { "field": "destination.country_code", "code": "invalid_format", "message": "Country code must be two uppercase letters." }
  ]
}
  • One machine-readable code per error; one human-readable message.
  • Field paths handle nested errors (location.country_code).
  • Keep error types stable — they're part of the contract, so version them.
  • Never expose stack traces or internals in error bodies.
  • Distinguish client errors (4xx) from server errors (5xx) — clients branch on it.

Concurrency & optimistic locking

When two clients mutate the same resource, naive read-modify-write loses updates silently.

ProblemContract solution
Two clients update the same resourceIf-Match with an ETag / version
Stale read before a mutationReturn a version field on the resource
Batch updates conflictPer-item status and version
Concurrent cancellationIdempotency + version check
  • Return a version token (version field or ETag) on every mutable resource.
  • Require If-Match: "18" on updates where a lost update is harmful — return 412 Precondition Failed when stale.
  • Treat PATCH as lossy without a version; idempotency keys (post) and versions (requests) look different, but both guard mutation safety.
  • Document a client default: fetch, apply change, re-PATCH with the current version, retry once on 412.

Long-running operations — 202, job resources, and webhooks

Not every operation finishes inside one request. Where work is not immediate, model it explicitly so clients are not blocked, misled, or polling forever.

POST /v1/reports
Idempotency-Key: 4f9c2...

202 Accepted
Location: /v1/reports/jobs/job_123

Job resource:

{ "id": "job_123", "status": "RUNNING", "queued_at": "2026-01-01T12:00:00Z",
  "expires_at": "2026-01-01T13:00:00Z", "result_url": null, "error": null }

States: QUEUED → RUNNING → SUCCEEDED | FAILED | CANCELED.

  • Return 202 Accepted + Location for work that is not immediate; never fake a synchronous completion.
  • Provide a job resource; support cancellation where feasible.
  • Offer webhook notification on completion so clients do not poll.
  • Make job-status reads idempotent; define result expiry; always let clients stop polling (a deadline, never forever).
  • For events, see schema evolution and the streaming patterns.

For push completion, a webhook is the natural counterpart — its delivery contract matters as much as its payload:

ConcernRequirement
AuthenticationHMAC signature header, verified with a shared secret
Replay protectionTimestamp + nonce, or event-ID deduplication
OrderingDo not guarantee unless explicitly designed (and documented as such)
RetriesExponential backoff, with a cap
IdempotencyConsumers must deduplicate by event ID
Failure handlingDead-letter queue + replay option
TestingTest endpoint or CLI
Secret rotationSupport multiple active secrets

A webhook is not "fire and forget." It is a contract with delivery, signature, retry, and idempotency requirements. Design it like any other endpoint, not as a side effect.

Realtime and streaming contracts

When a client needs updates pushed, the transport choice is a contract decision with UX consequences.

PatternUse when
PollingSimple, low frequency, latency-tolerant
Long pollingServer can hold the request until something changes
Server-Sent Events (SSE)One-directional server-to-client updates over HTTP
WebSocketBidirectional, low-latency interaction
gRPC streamingService-to-service high-throughput streams

SSE guidance

  • Use event: names; use id: for resume; support Last-Event-ID on reconnect.
  • Keep messages small; send periodic heartbeats so proxies know the stream is alive.
  • Authenticate before opening the stream where possible.

WebSocket guidance

  • Define a message envelope (event type + payload + sequence number).
  • Handle reconnection and resynchronization (e.g., replay missed sequence numbers).
  • Send heartbeats; limit message size; apply rate limits; authenticate on connect or via a short-lived ticket.

An API that cannot explain what a client misses after a disconnect — or what a reconnect restores — is not streaming, it is firing. The schema (event: names) is the contract; see Ecosystem for the failure that ignores it.

Token & scope contracts

  • Validate iss, aud, exp, nbf, and the signature.
  • Keep token lifetimes short; rotate signing keys; handle refresh tokens securely.
  • Do not put sensitive claims in an unencrypted JWT payload.
  • Do not treat JWT possession as authorization — check scopes and resource ownership.
  • Scopes: shipments:read, shipments:write, webhooks:manage, reports:read.

The discipline behind these mechanics — why bearer tokens exist, when a JWT is the wrong tool, how to threat-model the exchange, and the OWASP classes this contract is exposed to — lives in Security & Threat Modeling (IAM and Application security sections). This section is the how; that doc is the when and why.

Browser constraints

  • CORS allowlists must be explicit; never Access-Control-Allow-Origin: * with credentials.
  • Understand preflight for custom headers (e.g., Idempotency-Key).
  • Use SameSite cookies correctly; never expose secrets to browser bundles.

File uploads & binary contracts

Binary exchange has its own patterns. The contract must cover transport, validation, and access control, not just the endpoint.

PatternUse when
Direct multipart uploadSmall files, simple API
Presigned URL uploadLarge files — offload to object storage
Resumable uploadLarge or unreliable networks
Streaming downloadLarge files
Range requestsPartial content / resume

Always cover: content-type validation, size limits, virus scanning, signed URLs with expiry, access control, checksums, and separation of metadata from the binary.

AI-safe tool contracts

AI agents consume APIs as tools — a capability boundary that must be especially explicit and safe. Ambiguous tools become unsafe actions.

ConcernGuidance
Tool schemaStrict JSON Schema / typed input
IdempotencyMutations must be retry-safe
Least privilegeScope tools narrowly
Human approvalRequire confirmation for destructive actions
Audit loggingRecord tool calls and outcomes
Rate / cost capsPrevent runaway agent loops
Error clarityReturn actionable machine-readable errors
Side effectsDescribe them explicitly in tool metadata
ReversibilityPrefer undoable operations

For AI agents, an API is a capability boundary. The same contract that gives a human a form gives an agent an action. A fuzzy, destructive tool with no approval gate is an exploitation vector — design tools as if they will be called by an automatic, over-optimistic caller.

Worked example — "Design a Public Shipment Tracking API"

A realistic public API problem, walked end-to-end through the rhythm.

Context & personas

  • Carrier operations — scans packages at hubs (high throughput, batch ingest).
  • E-commerce platform — polls for status to show buyers (moderate QPS, needs webhook).
  • End customer — opens tracking page once per order (low QPS, needs real-time feel).

Step 1 — Resource topology (interface contract)

GET   /v1/shipments/{id}              # single shipment detail
GET   /v1/shipments                   # list with cursor pagination, filter by status/date
POST  /v1/shipments                   # carrier creates (idempotent)
PATCH /v1/shipments/{id}              # carrier updates scan events (idempotent)
POST  /v1/webhooks                    # platform registers callback URL
GET   /v1/shipments/{id}/events       # event stream (Server-Sent Events)

Step 2 — Choose style: REST + SSE for status stream

Rationale: public HTTP, heterogeneous clients (mobile web, native apps, server), caching on GET matters, SSE gives real-time feel without WebSocket complexity. GraphQL rejected — overkill for 3 resources, caching story weaker. gRPC rejected — not browser-native without proxy.

Step 4 — Idempotency & mutation safety

  • POST /shipments and PATCH /shipments/{id} require Idempotency-Key: header. Server stores key → response mapping for 24h. Duplicate key returns original response.
  • Carrier batch ingest uses POST /shipments/batch with array of shipments, each with its own idempotency key. Response includes per-item status.

Step 5 — Versioning & deprecation policy

  • Version in URL: /v1/, /v2/. No header versioning (simpler for public API).
  • Sunset header on deprecated version: Sunset: Sat, 01 Jan 2027 00:00:00 GMT + Link: ; rel="successor-version".
  • 12-month minimum support after successor releases. Communication: email to registered apps, changelog, developer portal banner.

Step 6 — Rate limits & quotas

  • Anonymous: 60 req/min, 1000 req/day.
  • Authenticated (API key): 300 req/min, 100k req/day.
  • Carrier partner: 5000 req/min, negotiated quota.
  • Headers on every response: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset.

Step 7 — GraphQL counter-example (why not here)

type Query {
  shipment(id: ID!): Shipment
  shipments(filter: ShipmentFilter, first: Int, after: String): ShipmentConnection
}

type Shipment {
  id: ID!
  status: ShipmentStatus!
  events: [ShipmentEvent!]!
  # Problem: events can be 10,000+. Client must paginate manually.
  # No native caching — every query is a POST.
  # Carrier batch mutation = custom input type, no idempotency story.
}

GraphQL adds resolver complexity for a read-heavy, cache-friendly domain. The carrier's batch mutation (10k scans/min) fits REST + idempotency keys better.

Artifacts produced

  • OpenAPI 3.1 document (source of truth, checked into repo, CI-validated).
  • Error matrix (every type URI, HTTP status, retry guidance).
  • SSE event schema (separate OpenAPI webhooks or components/schemas/EventStream).
  • Deprecation calendar (shared spreadsheet + automated Sunset header injection).
  • Postman collection (generated from OpenAPI, published to public workspace).
  • TypeScript types (generated via openapi-typescript, published to npm).

The most common failure modes

Failure modeWhat it looks likeWhy it happens
Verbing nouns (RPC-shaped REST) POST /shipments/{id}/cancel, POST /shipments/{id}/retry-delivery, GET /shipments/{id}/get-status Thinking in actions not resources. The contract becomes a remote procedure call over HTTP, losing caching, idempotency semantics, and hypermedia.
Internal models leak through the API Response includes _id: ObjectId("..."), createdAt: { $date: 1234567890 }, user_id (FK), is_deleted: false Serializing the ORM entity directly. Couples clients to storage schema. Migration becomes a coordinated deploy.
No idempotency on writes → retries corrupt Mobile app retries POST /shipments on network timeout; carrier creates duplicate shipment. Treating idempotency as "nice to have." Every mutating endpoint needs an idempotency key; the cost of not having it is data corruption.
Version-by-URL vs version-by-header religious war Team spends 3 weeks debating; ships neither; clients break on a field rename. Bikeshedding the mechanism instead of the policy. Pick one (URL is simpler for public APIs), document the breaking-change policy, move on.
Pagination by offset on a hot table GET /shipments?offset=10000&limit=50 takes 3 seconds; client times out. Offset pagination requires scanning skipped rows. Cursor pagination (keyset) is O(1) but requires stable sort key. Default to cursor.
Errors that lie: HTTP 200 with body {success: false} Client checks response.ok, sees true, tries to parse data, crashes on error object. Fear of "breaking" HTTP semantics. The contract is the HTTP status. Use 4xx/5xx; put machine-readable details in RFC 9457 body.
Undocumented status codes clients can't switch on API returns 418 (teapot) for "carrier offline"; client has no handling, shows generic error. Inventing custom codes instead of mapping to standard 4xx/5xx + RFC 9457 type URI. Clients can only handle what they know.
Breaking change shipped without sunset window status enum adds LOST; mobile app crashes on unknown enum because it uses exhaustive switch. Treating enum extension as non-breaking. In typed clients (TypeScript, Swift, Kotlin), new enum values are breaking. Document enum extensibility: "clients must handle unknown."
Schema as ceremony, not guardrail OpenAPI file exists but implementation diverges; CI doesn't validate; generated SDK is wrong. Schema-first adopted as process theater. The fix: CI fails if implementation response doesn't match schema (Pact, Dredd, Schemathesis).
Validation errors that leave the client in the dark PATCH returns generic 400 Bad Request; the form shows one vague message and the user can't fix anything. No field-level error catalog (validation errors). A validation error is UI state for a frontend form — it needs field paths, machine codes, and messages clients can branch on, not a dead-end status.
Lost updates from blind read-modify-write Two support agents edit the same shipment's destination; the later overwrite silently drops the other's change. No version token or If-Match on the write (validation errors). Idempotency keys stop duplicate creates but not concurrent overwrites — a version check returns 412 so the client can retry against the current state.
Spinning a client on "forever" operations Carrier polls a report status for 20 minutes; timeout kills the job mid-run; no signal. Long work was exposed as a synchronous call instead of 202 + job resource + webhook on completion (202 / job resources / webhooks). Operations that can exceed a request budget need an explicit job lifecycle so clients don't poll into a wall.
Webhook replay wrecks downstream state Event delivered twice (retry after timeout); consumer double-charges a shipment on the duplicate. Webhook treated as fire-and-forget with no idempotency or signature check (202 / job resources / webhooks). Consumers must dedupe on event-ID and verify the HMAC — a webhook is an endpoint, not a side effect.
Streaming that isn't resumable SSE/WebSocket drops mid-push; client silently misses events and shows a stale tracking page. No event id + Last-Event-ID resume, no sequence numbers (realtime and streaming). "Real-time" is only a contract if a reconnect can recover exactly what was missed.
Scopes that never shrink A public client with a token minted for shipments:write also gets reports and user reads. Token possession treated as authorization (security and browser contracts). Authorization is a scope + ownership check per request, not "has a valid JWT." Every permission should be as narrow as the calling client needs.

The practitioner critique (2015–present)

API design has faced serious critique from the platform engineering community:

  • Kin Lane (API Evangelist) — "APIs as Products": most orgs treat APIs as technical artifacts, not products with PMs, metrics, and lifecycle. The contract is the product; everything else is packaging.
  • API Handyman (Arnaud Lauret) — "The Design of Web APIs": REST is often cargo-culted; hypermedia is abandoned; versioning is inconsistent; error formats are invented per endpoint.
  • Stoplight / SmartBear surveys — "State of API 2023": 60% of orgs have no API design guidelines; 40% discover breaking changes in production; schema validation in CI is rare.†
  • Phil Sturgeon (APIs You Won't Hate) — "Design First vs Code First": code-first (annotations) produces contracts that mirror implementation accidents; design-first (OpenAPI/proto) produces contracts that serve consumers.

The common thread: the critique is not that the principles are wrong — it's that the institutional adoption hollows them into checkboxes. The rhythm survives; the branded methodologies often don't.

Selection heuristic: Start with Contract Definition + Linting + Client Generation (the "minimum viable API toolkit"). Add Contract Testing when consumer count >3. Add Schema Registry when team count >5 or polyglot. Add Gateway when traffic management needs exceed library capabilities. Add Type-Safe Full-Stack when TypeScript is the primary language. The tool serves the contract — not the reverse.

Summary — the contract checklist

Before any API change merges, verify:

QuestionIf no…
Is the contract (OpenAPI/proto/GraphQL SDL) the source of truth, not the code?Stop. Code-first = implementation leaks into contract.
Does every mutating endpoint accept an idempotency key?Stop. Retries will corrupt state.
Are all errors RFC 9457 Problem Details with a stable type URI?Stop. Clients can't programmatically handle string matching.
Is the versioning strategy documented with a sunset policy?Stop. Breaking changes will surprise consumers.
Are enums documented as extensible (clients must handle unknown)?Stop. Typed clients will crash on new values.
Is pagination cursor-based (not offset) for collections that grow?Stop. Offset pagination is O(n) and times out at scale.
Does the contract pass schema validation in CI (implementation matches schema)?Stop. Schema drift = generated SDKs lie.
Are rate limits, quotas, and Retry-After headers documented and returned?Stop. Clients can't back off; they hammer and get banned.
Do mutable resources expose a version token (ETag / If-Match) for safe concurrent writes?Stop. Read-modify-write will silently lose updates (validation errors).
Do long-running and push contracts exist deliberately — 202 + job resource, webhook with signature + event-ID, resumable streams?Stop. Clients will poll, replay, or miss events with no way out (202 / job resources / webhooks, realtime and streaming).
Is there a deprecation calendar communicated to registered consumers?Stop. Surprise deprecation = lost trust, churn.

Print this. Put it on the API review wall. If the PR can't pass this checklist, it's not ready for consumers.
