Definition — what SQL is, and what it is not

SQL is a declarative language. You say what you want ("all shipments for this customer, newest first"), and the engine decides how to get it — which indexes to walk, how to join, what order to do things in. That is the opposite of your imperative code: in the request loop you write steps; in SQL you write the goal. The job of a good SQL writer is to phrase the goal so the engine's planner can see the cheap path (which is what the index and EXPLAIN sections are about).

What SQL isWhat SQL is not
A declarative set language — you describe the result setAn imperative language — you do not describe the steps
Standardized (SQL-92, SQL:1999, SQL:2003, SQL:2016, SQL:2023) with vendor dialectsOne dialect — every engine adds its own superset (PostgreSQL's ON CONFLICT, MySQL's ON DUPLICATE KEY)
The same language across PostgreSQL, MySQL, SQLite, SQL Server — ~90% sharedA backend "stack" — SQL is not Node or .NET; it is what they both call
About sets: WHERE filters rows, JOIN combines sets, GROUP BY folds sets, window functions rank within setsAbout imperative loops — the N+1 problem happens exactly when you translate loops into queries

SQL vs NoSQL: relational engines give you ACID, joins, and constraints; document stores give you flexible schemas and horizontal scale-out. The shelf's position (Data Modeling §Definition, §Beyond the relational default): relational by default, document stores when the schema is genuinely variable — and PostgreSQL's JSONB covers most of those cases without leaving the relational world. SQL is not going anywhere; it is the lingua franca of data.

Query fundamentals — the SELECT anatomy

Every query is one sentence: from these tables, filter to these rows, shape them into these columns. The single most important mental model in SQL is that the written order and the execution order are different:

-- WRITTEN order (how you type it):
SELECT   department, COUNT(*)
FROM     employees
WHERE    hired_at > '2020-01-01'
GROUP BY department
HAVING   COUNT(*) > 5
ORDER BY department
LIMIT    10;

-- EXECUTION order (how the engine actually does it):
-- 1. FROM        pick the source rows (joins happen here)
-- 2. WHERE       filter rows            (cannot use aliases!)
-- 3. GROUP BY    fold rows into groups
-- 4. HAVING      filter groups          (cannot use aliases!)
-- 5. SELECT      compute output columns (aliases born here)
-- 6. ORDER BY    sort the output        (can use aliases)
-- 7. LIMIT       cut the output

Most SQL bugs are order bugs: a WHERE that should be a HAVING, an alias used where it does not exist yet. Memorize the execution order once and the rest is vocabulary.

ClauseWhat it doesTraps
SELECTPick and compute columns; SELECT DISTINCT dedupes whole rowsSELECT * in production — see Failure modes
FROM ... JOIN ...Choose sources and combine themForgot the join key → cartesian product
WHEREFilter rows before groupingFiltering a group property here instead of in HAVING
ORDER BYSort; DESC for newest-first; multiple keys in priority orderSorting costs time and blocks LIMIT pagination on big sets
LIMIT ... OFFSET ...Cut output; page with OFFSETDeep OFFSET scans and skips — use keyset pagination instead (see Window functions)

NULL — the number one source of SQL bugs

NULL is not a value; it is the absence of a value, and it does not compare like one. NULL = NULL is not true — it is NULL (unknown). The three rules that end the confusion:

WHERE email IS NULL          -- the ONLY way to test for absence (never = NULL)
WHERE email IS NOT NULL      -- its inverse
WHERE score IS DISTINCT FROM 5   -- "not equal, counting NULL as a value" (PostgreSQL)

SELECT COALESCE(nickname, full_name, 'Anonymous')  -- first non-NULL, left to right
SELECT NULLIF(a, b)          -- NULL if a = b, else a   (handy for divide-by-zero)
SELECT COUNT(*)              -- counts rows, including NULLs
SELECT COUNT(email)          -- counts only non-NULL values — a subtle difference!

CASE and casting

CASE is SQL's if/else — an expression that returns a value per row, usable anywhere an expression is (SELECT, WHERE, ORDER BY). Casting with :: (PostgreSQL) or CAST(x AS type) (standard) converts types — and is a classic performance trap when applied to indexed columns (see Performance).

SELECT CASE WHEN total > 1000 THEN 'large'
            WHEN total > 100  THEN 'medium'
            ELSE 'small' END AS size
FROM shipments;

SELECT '42'::int,  total::numeric(10,2)   -- PostgreSQL cast syntax
SELECT CAST('42' AS INT);                -- standard, works everywhere

JOINs — the core skill

Relational data lives in separate tables; JOINs bring it back together. A JOIN is a pairing rule: for each row on the left, find matching rows on the right by a key. Everything else is which rows you keep.

SELECT s.tracking_number, c.name AS customer
FROM   shipments s
JOIN   customers c ON c.id = s.customer_id;
Join typeWhat it keepsMental model
INNER JOIN (plain JOIN)Only matched pairsThe intersection — "orders that have a customer"
LEFT JOINAll left rows + matches; unmatched left rows get NULLs on the right"Every customer, and their orders if any" — the workhorse
RIGHT JOINMirror of LEFT — all right rowsRarely used; flip the tables and use LEFT instead
FULL OUTER JOINAll rows from both sides"Both sides, matched where possible" — for reconciliation reports
CROSS JOINEvery row of one × every row of the otherThe cartesian product — almost always a bug; deliberate only for grids of combinations
Self-joinA table joined to itself (aliases required)Hierarchies: e.manager_id = m.id — employees and their managers in one table

How the engine joins (why the same query can be fast or slow): the planner picks an algorithm per join. Nested loop — for each left row, probe the right side (great when one side is tiny or the key is indexed). Hash join — build a hash table of one side, probe with the other (great for large equi-joins, the default for big sets). Merge join — both sides sorted, walk them in lockstep (great when both sides are already sorted by the key). You do not choose these; you shape them by giving the planner what it needs — an index on the join key. A missing join-key index is the classic way a fine-looking query secretly table-scans.

JOIN vs subquery: anything a subquery does in the FROM or via a correlated filter, a JOIN usually expresses more readably. The exception: NOT IN-style anti-joins and existence checks, where EXISTS is both clearer and faster (see Subqueries). The rule of thumb: prefer JOINs for combining; prefer EXISTS for testing.

The N+1 problem — where loops and queries collide. The anti-pattern: fetch 50 orders with one query, then run 50 more queries — one per order — to fetch each customer (this is what ORMs silently do when you access an unloaded relation). The fix is one JOIN (or one IN query), and the shelf's home for the pattern is Backend Engineering §1e; this is the SQL that fixes it:

-- N+1 (51 queries): the loop fetches customers one by one
-- one JOIN (1 query):
SELECT o.id, o.total, c.name
FROM   orders o
JOIN   customers c ON c.id = o.customer_id
WHERE  o.created_at > now() - interval '7 days';

LATERAL — the correlated subquery as a join. A normal JOIN can't reference the row it's joining from; LATERAL can. That makes it the tool for "top N per group" and per-row helpers the planner can't otherwise express:

-- each customer's 3 most recent orders
SELECT c.name, recent.id, recent.total
FROM   customers c
CROSS JOIN LATERAL (
  SELECT o.id, o.total FROM orders o
  WHERE  o.customer_id = c.id
  ORDER  BY o.created_at DESC LIMIT 3
) recent;

Read it as "for each customer, run this inner query using the customer's id" — which is exactly how the engine executes it. Use LATERAL when a correlated subquery returns a set you want to join against; use a window function when the "top N per group" is computed over the whole partition at once (Window functions section) — LATERAL wins when you need other columns from the inner query.

Aggregation — folding rows into groups

Aggregation is WHERE's sibling at the set level: WHERE filters rows; GROUP BY folds them into groups; HAVING filters the groups. Every column in the SELECT must be either an aggregate function or a GROUP BY column — the engine enforces this, and the error is your friend.

SELECT   department, COUNT(*) AS headcount, AVG(salary) AS avg_salary
FROM     employees
WHERE    status = 'active'            -- row filter, before grouping
GROUP BY department
HAVING   AVG(salary) > 50000           -- group filter, after grouping
ORDER BY headcount DESC;
AggregateWhat it doesNote
COUNT(*) / COUNT(col)Rows / non-NULL valuesThe NULL difference is a classic off-by-one
SUM, AVG, MIN, MAXNumeric / ordered aggregatesSUM(NULL) → NULL; use COALESCE for zero
COUNT(DISTINCT col)Unique valuesExpensive on big sets — needs a sort or hash
FILTER (WHERE ...)PostgreSQL: aggregate over a subset of rowsOne pass instead of several CASE tricks: COUNT(*) FILTER (WHERE status='failed')
GROUPING SETS, ROLLUP, CUBEMultiple grouping levels in one queryReport subtotals — reach for it when a dashboard needs totals alongside per-group rows

Aggregate + JOIN trap: joining before grouping can multiply rows (one order, two line items → COUNT(*) says 2). Count from the joined side's own key or use COUNT(DISTINCT o.id). When a report disagrees with a simple query, suspect a fan-out.

ROLLUP — subtotals and a grand total in one query. Dashboards want per-group rows and the totals; ROLLUP emits both, sparing you three queries and the client-side summing that always drifts:

SELECT carrier, COUNT(*)
FROM   shipments
GROUP BY ROLLUP (carrier);
-- rows: one per carrier, then one NULL row = the grand total
-- CUBE does the same for every combination of the grouping columns (ROLLUP's superset)

Subqueries and CTEs — composing queries

A query can appear inside another query in three places, with three different meanings:

KindShapeUse it when
Scalar subqueryReturns one value, used in an expressionWHERE total > (SELECT AVG(total) FROM orders) — a single computed threshold
Derived table (in FROM)Returns a set, aliased, queried like a tableAggregate first, then filter/join on the result — the "subquery in FROM" workhorse
Correlated subqueryReferences the outer query's rowPer-row calculations — but it runs once per outer row; re-check as a JOIN or window function
EXISTS / NOT EXISTSTests whether any row matchesThe fast, clear way to filter by related data — often beats IN and subqueries
 
-- EXISTS vs IN: same question, different engines
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);  -- stops at first match

SELECT * FROM customers
WHERE id IN (SELECT customer_id FROM orders);                      -- builds the full list first

-- Derived table: the max per group, then joined back
SELECT t.department, t.max_salary, e.name
FROM   (SELECT department, MAX(salary) AS max_salary FROM employees GROUP BY department) t
JOIN   employees e ON e.department = t.department AND e.salary = t.max_salary;

CTEs — the WITH clause. A CTE names an intermediate result so the query reads top-down like a pipeline. They do not magically run once (until PostgreSQL materializes them, they are more like macros) — their superpower is readability, and their unique trick is recursion:

WITH active_customers AS (
  SELECT id, name FROM customers WHERE last_order_at > now() - interval '90 days'
)
SELECT c.name, COUNT(o.id) AS orders
FROM   active_customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name;

-- Recursive CTE: walk a tree (categories, org charts, comment threads)
WITH RECURSIVE tree AS (
  SELECT id, name, 1 AS depth FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.name, t.depth + 1 FROM categories c
  JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree;

Window functions — ranking and running totals

Aggregates fold rows into one result per group. Window functions compute an aggregate-style value but keep every row. That is the entire difference — and why "top N per group" needs them (GROUP BY would collapse the rows you want to keep).

SELECT  name, department, salary,
        ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rank_in_dept,
        SUM(salary)   OVER (PARTITION BY department)                       AS dept_total,
        AVG(salary)   OVER (PARTITION BY department ORDER BY hire_date)    AS running_avg
FROM employees;
Window functionWhat it doesClassic use
ROW_NUMBER()Position within the partitionTop-N per group: rank rows, then filter rank <= 10 in an outer query
RANK() / DENSE_RANK()Rank with ties (RANK skips numbers, DENSE_RANK does not)Leaderboards
LAG(col) / LEAD(col)The previous / next row's value in the partitionDeltas: total - LAG(total) = change since last month
SUM(...) OVER (ORDER BY ...)Cumulative sum over the ordered windowRunning totals, balances
NTILE(n)Split the partition into n bucketsPercentiles, A/B bucketing
FIRST_VALUE / LAST_VALUEEdges of the window"First purchase date per customer"

Window syntax in one line: FUNCTION OVER (PARTITION BY X ORDER BY Y) — PARTITION BY draws the groups (like GROUP BY), ORDER BY defines the order the function walks within each group. A window with neither partitions nor order computes over the whole set.

Frames — the window within the window. By default ORDER BY in a window makes the frame "all rows up to and including the current one" (that's why running totals work). You can shrink the frame explicitly — the tool behind moving averages and "last 7 days":

-- running total (default frame: current row and everything before it)
SUM(amount) OVER (ORDER BY date)

-- moving average of the last 3 rows
AVG(amount)  OVER (ORDER BY date ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)

-- trailing 7-day sum
SUM(amount)  OVER (ORDER BY date RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW)

Reach for a frame clause the moment "window of last N rows" or "last 7 days" shows up — without it you get the whole running total, and the number is subtly wrong.

Top-N per group, complete:

SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
  FROM employees
) ranked
WHERE rn <= 3;

Keyset pagination (the OFFSET killer): OFFSET 100000 makes the engine walk and discard 100000 rows. Cursor-style pagination — "give me rows after this one" — uses the index directly. API Design owns the cursor contract; this is the query:

-- OFFSET (slow on deep pages):  SELECT * FROM events ORDER BY id LIMIT 20 OFFSET 100000;
-- Keyset (fast, uses the index):
SELECT * FROM events WHERE id > :last_seen_id ORDER BY id LIMIT 20;

Writing data — INSERT, UPDATE, DELETE, UPSERT

Reads dominate the language, but writes are where correctness lives. The four verbs, with the PostgreSQL extras that make writes safer:

INSERT INTO shipments (tracking_number, customer_id, status)
VALUES ('TRK-1001', 42, 'pending')
RETURNING id, tracking_number;          -- get the row back in one round trip

UPDATE shipments SET status = 'in_transit'
WHERE  id = 7;                          -- never UPDATE without WHERE

DELETE FROM shipments WHERE id = 7;     -- never DELETE without WHERE
TRUNCATE  shipments;                    -- wipe all rows instantly (no WHERE allowed)

UPDATE shipments SET status = 'delivered'
FROM   customers c                      -- UPDATE ... FROM: join in the update
WHERE  shipments.customer_id = c.id AND c.plan = 'premium';

UPSERT — the idempotent write. The API-design doc's idempotency keys need a database that does not error on the second attempt. PostgreSQL's INSERT ... ON CONFLICT is exactly that: try to insert; if a unique constraint trips, do something else (update, or do nothing):

-- The idempotent write: retry-safe, no "duplicate key" error on the second call
INSERT INTO payment_events (idempotency_key, amount, status)
VALUES (:key, :amount, 'captured')
ON CONFLICT (idempotency_key) DO UPDATE SET status = EXCLUDED.status
RETURNING id;

INSERT INTO tags (name) VALUES ('sale')
ON CONFLICT (name) DO NOTHING;          -- the "get-or-create" pattern

-- MySQL spelling, for the WordPress-era mental model:
-- INSERT INTO tags (name) VALUES ('sale') ON DUPLICATE KEY UPDATE name = name;

RETURNING (PostgreSQL) returns the affected rows — the lazy developer's gift: one round trip to insert and read the generated id, which is exactly what a request handler needs to build its response. (SQLite supports it too; MySQL's equivalent is a follow-up LAST_INSERT_ID().)

Transactions in SQL — BEGIN, COMMIT, ROLLBACK

A transaction is a batch of statements that succeed or fail together. The request loop's multi-step writes (charge + create shipment + notify) are only atomic if wrapped:

BEGIN;                                  -- or START TRANSACTION
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                                 -- both become visible together

-- on any error instead:
ROLLBACK;                               -- both vanish; the world never saw a half-write

ACID in practice: Atomicity is exactly what BEGIN/COMMIT/ROLLBACK buy you. Consistency is the schema's constraints doing their job. Isolation is the level knob — the shelf's home is Data Modeling §Isolation levels and Backend Engineering §5; the one-liner for here: READ COMMITTED (PostgreSQL default, per-statement snapshot) vs REPEATABLE READ (per-transaction snapshot — the same SELECT twice sees the same data). Durability is the WAL, which you trust the platform to own.

Failure modeWhat happensAvoidance
Held-too-long transactionLocks block every other writer; the connection pool drainsKeep transactions short — no API calls or loops inside; commit and move on
DeadlockTwo transactions each hold a lock the other wants; the engine kills oneAlways lock rows in the same order (e.g., by id); retry the killed transaction
Orphaned rollbacksApplication crashes mid-transactionThat is what ROLLBACK on disconnect is for — the pool cleans up; just don't leak a transaction across requests

Savepoints — roll back part of a transaction, not all of it. A long write (import a customer, then their orders, then their payments) shouldn't die wholesale because one row was bad. Mark a point, and on error rewind only to it:

BEGIN;
INSERT INTO customers (name) VALUES ('Lina') RETURNING id;   -- id = 10
SAVEPOINT orders_done;
INSERT INTO orders (customer_id, total) VALUES (10, 99);      -- fails (bad constraint)
ROLLBACK TO SAVEPOINT orders_done;                            -- customer survives, order rolled back
COMMIT;

Row locking — claim rows so two workers don't claim the same one. SELECT ... FOR UPDATE locks the returned rows until commit, which is how a queue makes sure two workers never pick the same job:

SELECT * FROM jobs WHERE id = 42 FOR UPDATE;                  -- lock this row for the transaction
SELECT * FROM jobs WHERE id = 42 FOR UPDATE SKIP LOCKED;     -- skip rows already locked by others
SELECT * FROM jobs WHERE id = 42 FOR UPDATE NOWAIT;          -- error out instead of waiting

Three words, three queue behaviors: plain waits for the lock (and can deadlock), SKIP LOCKED jumps to the next free row (the queue-worker default), NOWAIT fails fast (better than a long wait when the row is someone else's). The Testing & Debugging doc's retry habit is what makes SKIP LOCKED safe at scale.

Advisory locks — locking on your own terms. For application-level critical sections that aren't tied to a table row (a cache rebuild, a price re-bucket), PostgreSQL lets you lock an arbitrary integer:

SELECT pg_advisory_lock(12345);       -- session lock; release with pg_advisory_unlock(12345)
SELECT pg_advisory_xact_lock(12345);  -- transaction lock; releases automatically on COMMIT/ROLLBACK

The session form follows the connection, so a leaked lock holds until the connection closes; the xact form follows the transaction, which is the one the request-loop's short transactions want. Use table locks rarely and advisory locks rarely; the queue's SKIP LOCKED pattern covers most real needs.

PostgreSQL features — why the shelf defaults to it

The data-modeling doc chooses PostgreSQL for good reason; this section is the syntax behind that choice. Everything here is PostgreSQL-specific (until noted), and each feature answers a real shelf need.

JSONB — documents inside a relational world

CREATE TABLE events (
  id   bigserial PRIMARY KEY,
  meta jsonb NOT NULL DEFAULT '{}'
);

SELECT meta->>'user_agent'                AS ua          -- ->> text, -> json
FROM   events
WHERE  meta @> '{"plan": "premium"}'      -- @> containment: does meta contain this?
ORDER BY (meta->>'score')::numeric DESC;

CREATE INDEX ON events USING GIN (meta);  -- GIN makes the @> query use an index

JSONB stores binary JSON, indexed via GIN, with @> containment and the ? key-existence operators. The data-modeling doc's rule stands: JSONB for genuinely variable shapes, not as a substitute for columns you actually query. It also covers most document-store use cases — the reason MongoDB stays "later" on this shelf.

Arrays, full-text search, LISTEN/NOTIFY, RLS, partitioning

-- Arrays as a column type
CREATE TABLE posts (id bigserial PRIMARY KEY, tags text[] NOT NULL DEFAULT '{}');
SELECT * FROM posts WHERE 'sale' = ANY(tags);
SELECT * FROM posts WHERE tags @> ARRAY['sale','new'];

-- Full-text search without Elasticsearch
CREATE INDEX ON posts USING GIN (to_tsvector('english', title || ' ' || body));
SELECT * FROM posts
WHERE to_tsvector('english', title || ' ' || body) @@ to_tsquery('sales & report');

-- LISTEN/NOTIFY — pub/sub inside the database (Supabase Realtime's engine)
NOTIFY events_changed, 'shipment-1001';
LISTEN events_changed;                   -- a waiting connection receives the payload

-- Row-Level Security: multi-tenant enforcement in the engine, not the app
CREATE POLICY tenant_isolation ON shipments
  USING (tenant_id = current_setting('app.tenant_id'));
ALTER TABLE shipments ENABLE ROW LEVEL SECURITY;

-- Partitioning — the scaling lever from system-design, in syntax
CREATE TABLE events_part (id bigint, created_at timestamptz)
PARTITION BY RANGE (created_at);
CREATE TABLE events_2026 PARTITION OF events_part
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE documents (id bigserial PRIMARY KEY, content text, embedding vector(1536));

-- DISTINCT ON: the most recent event per shipment (ORDER BY picks which row wins)

FROM   shipment_events

-- Generated column: total that can't drift out of sync with its inputs
CREATE TABLE order_lines (
  id        bigserial PRIMARY KEY,
  price     numeric(10,2) NOT NULL,
  quantity  integer NOT NULL,
  total     numeric(10,2) GENERATED ALWAYS AS (price * quantity) STORED
);

-- TABLESAMPLE: a 1% slice for testing, without a full scan
SELECT * FROM events TABLESAMPLE SYSTEM (1);

Performance — reading and fixing slow queries

The tuning loop belongs to Data Modeling §Indexing and §Reading EXPLAIN ANALYZE — this section is the query side of that loop: what to look for, and the anti-patterns that defeat the planner.

EXPLAIN ANALYZE SELECT ... -- run the query for real, show the plan + measured timings
-- what to look for, in order:
--   1. Seq Scan on a big table  → the WHERE/JOIN column needs an index
--   2. "rows=..." wildly off    → stale statistics (ANALYZE) or a cast hiding the index
--   3. Nested Loop with huge re-probes → the inner key is not indexed
Anti-patternWhy it is slowThe fix
SELECT *Drags every column across the network; kills covering indexesName the columns the request actually needs
Function on an indexed column: WHERE DATE(created_at) = '2026-01-01'The index is on created_at; the function hides the valueRange form: WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'
Implicit cast: comparing text to intSame story — the planner cannot use the index through a castCast the parameter, not the column
Missing index on a JOIN keyHash join becomes fine, nested loop becomes a scan per rowIndex every foreign key you join on (data-modeling §Indexing says the same)
Deep OFFSET paginationWalks and discards every skipped rowKeyset pagination (Window functions section)
N+1 from the ORMA loop of small queries instead of one setEager loading / one JOIN (JOINs section)

Finding the slow ones: pg_stat_statements (an extension) tracks every query's total time and call count — the "top 10 slowest queries" list. VACUUM and autovacuum: PostgreSQL does not overwrite rows in place; dead rows accumulate until VACUUM reclaims them. Autovacuum normally handles this — the production problems happen when it is disabled or overwhelmed, and bloat shows up as tables growing beyond reason. Know that it exists; leave the tuning to the platform.

Connection pooling (PgBouncer): PostgreSQL's per-connection memory makes hundreds of idle app connections wasteful. PgBouncer sits in front and reuses a small pool. Transaction mode — a connection is held only for the duration of one transaction, which is what stateless request loops want; session mode pins a connection per client session, needed for prepared statements that must survive. The shelf's statelessness rule (Backend §Serverless) is exactly the constraint that makes transaction mode the default choice.

WordPress runs on MySQL/MariaDB. The language you just learned is ~90% the same; this section is the 10% that differs, plus the schema shape you will actually query as a freelancer.

The WordPress schema — what you will actually touch: everything lives in a handful of tables with the wp_ prefix, and the engine's wpdb object issues the queries. The two tables that look nothing like a normal schema deserve a mental note: wp_options is a giant key-value store (site settings, plugin options) — one row per option, values in a LONGTEXT column; wp_postmeta is an entity-attribute-value table — one row per post-metadata pair, which makes "posts with meta" queries a join against a tall table (exactly the EAV shape the data-modeling doc warns about, and the reason heavy meta usage is a performance smell).

-- "Find posts of type 'product' that have meta 'on_sale' = '1'"
SELECT p.ID, p.post_title
FROM   wp_posts p
JOIN   wp_postmeta m ON m.post_id = p.ID
WHERE  p.post_type = 'product' AND p.post_status = 'publish'
  AND  m.meta_key = 'on_sale' AND m.meta_value = '1';

-- "Count published posts per category"
SELECT t.name, COUNT(*) AS post_count
FROM   wp_terms t
JOIN   wp_term_taxonomy tt ON tt.term_id = t.term_id
JOIN   wp_term_relationships tr ON tr.term_taxonomy_id = tt.term_taxonomy_id
JOIN   wp_posts p ON p.ID = tr.object_id
WHERE  tt.taxonomy = 'category' AND p.post_status = 'publish'
GROUP BY t.name;

SQLite — the embedded engine

SQLite is not a server — it is a library that reads and writes a single file. It is the most deployed database engine on earth (every phone and browser ships one) and the shelf's local-development companion: tests, prototypes, and the terminal substrate's own file-backed stores.

When SQLite winsWhen it does not
Local development and automated tests — zero setup, in-memory modeConcurrent writes — one writer at a time (an app with many users writing simultaneously will serialize)
Small, low-traffic production (a tool, a dashboard, an internal app)High write throughput — the single-writer limit is the ceiling
Reading/exporting data with the sqlite3 CLI on any machineDistributed deployment — one file, one machine

The good news: the SQL you learned here is SQLite's SQL. The data-modeling ecosystem rule applies — SQLite for embedded/local, PostgreSQL for anything non-trivial. The migration path is a dump-and-load (.dump in SQLite; pg_dump + psql in PostgreSQL) with a few type-name touch-ups.

Worked example — the query layer for shipment tracking

The shelf has designed this system twice: the schema in Data Modeling §Worked example, the API in API Design. Here is the query layer that connects them — the actual SQL behind four endpoints, each optimized with the tools from this doc.

1. The detail endpoint — one shipment with its customer (LEFT JOIN, index on the FK):

SELECT s.tracking_number, s.status, s.estimated_delivery,
       c.name AS customer_name, c.email
FROM   shipments s
LEFT JOIN customers c ON c.id = s.customer_id
WHERE  s.tracking_number = :tracking_number;

2. The timeline — the latest 20 events, keyset paginated (window-function pagination, not OFFSET):

SELECT * FROM shipment_events
WHERE  shipment_id = :id AND event_id < :cursor   -- keyset: continue after the cursor
ORDER BY event_id DESC
LIMIT  20;

3. The dashboard — status counts per carrier this week (GROUP BY + FILTER):

SELECT carrier,
       COUNT(*)                                            AS total,
       COUNT(*) FILTER (WHERE status = 'delivered')       AS delivered,
       COUNT(*) FILTER (WHERE status = 'in_transit')      AS in_transit,
       COUNT(*) FILTER (WHERE status = 'exception')       AS exceptions
FROM   shipments
WHERE  created_at >= now() - interval '7 days'
GROUP BY carrier
ORDER BY total DESC;

4. The idempotent webhook handler (UPSERT — retry-safe against the same webhook arriving twice):

INSERT INTO shipment_events (shipment_id, status, payload, webhook_id)
VALUES (:shipment_id, :status, :payload, :webhook_id)
ON CONFLICT (webhook_id) DO NOTHING
RETURNING id;

The optimization pass: run each through EXPLAIN ANALYZE. The tell-tale Seq Scan on shipment_events for query 2 says the index is missing; the fix is the index the data-modeling doc already prescribes: CREATE INDEX ON shipment_events (shipment_id, event_id DESC); — the pair covers the WHERE and the ORDER BY in one structure. That is the whole loop: query → explain → index → re-explain.

Query recipes — the patterns production actually uses

Three patterns appear in almost every real codebase. Each is a small, memorizable recipe that folds the earlier sections together.

Soft delete — "deleted" as a timestamp, not a removal. Destructive deletes are scary (audit trails, FK errors, no undo); the pattern is to flag the row and filter it everywhere:

ALTER TABLE orders ADD COLUMN deleted_at timestamptz;      -- NULL = live, timestamp = deleted
UPDATE orders SET deleted_at = now() WHERE id = 42;        -- "delete"
SELECT * FROM orders WHERE deleted_at IS NULL;             -- the live view (every read must add this)
CREATE INDEX ON orders (customer_id) WHERE deleted_at IS NULL;   -- partial index: only live rows

The cost is discipline — every query needs the deleted_at IS NULL filter or deletes leak into results, and UNIQUE constraints now collide with old rows (a re-created customer fights a soft-deleted one). Use it when you need an audit trail or "undo"; for pure junk, hard delete. The partial index is the PostgreSQL idiom that keeps soft-deleted tables fast.

Job queue — claim rows so only one worker gets each job. Backend work (emails, image resizes, webhook retries) goes through a table; workers claim jobs with the FOR UPDATE SKIP LOCKED from the Transactions section:

-- worker picks exactly one unclaimed job, without fighting other workers:
UPDATE job_queue SET status = 'processing', locked_at = now(), locked_by = :worker
WHERE id = (
  SELECT id FROM job_queue
  WHERE status = 'pending'
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED LIMIT 1
)
RETURNING *;

That's the entire queue primitive: a table of jobs, a claim with SKIP LOCKED so concurrent workers never collide, and a retry column for the Testing & Debugging doc's retry habit. Add attempts/max_attempts counters and a RETURNING * — and you have the same shape as Redis-backed queues, without the second system. This is the pattern behind "why is my job stuck in 'pending'" — usually a worker died after claiming, so add a timeout that requeues stale processing rows.

COPY — bulk load/export without INSERT loops. The request loop inserts rows one at a time; when you have a thousand, COPY is the engine's native bulk path:

COPY shipments FROM '/tmp/shipments.csv' WITH (FORMAT csv, HEADER true);   -- import
COPY (SELECT * FROM shipments WHERE created_at > '2026-01-01')
  TO '/tmp/export.csv' WITH (FORMAT csv, HEADER true);                     -- export a query

COPY in the app runs as \copy in psql (client-side, no server path needed). For real migrations of millions of rows, the data-modeling doc's migration discipline applies — COPY into a staging table, validate, then swap.

Summary — the complete mental checklist

#The line
1SQL is declarative — you say WHAT, the planner decides HOW; your job is phrasing the goal for the index.
2Execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Order bugs are the #1 class.
3NULL never equals anything, including NULL — use IS NULL, COALESCE, IS DISTINCT FROM.
4JOINs pair by key; LEFT JOIN keeps the left side; index the join keys; one JOIN beats N+1 queries.
5WHERE filters rows, GROUP BY folds sets, HAVING filters groups, window functions rank without folding.
6CTEs read top-down; recursive CTEs walk trees; EXISTS beats IN for existence checks.
7UPSERT (ON CONFLICT) is the idempotent write; RETURNING is the free round trip.
8Writes are atomic only inside BEGIN/COMMIT; keep transactions short; lock in consistent order.
9PostgreSQL wins on JSONB, arrays, full-text, LISTEN/NOTIFY, RLS, partitioning, and extensions — that is why the shelf defaults to it.
10Slow query? EXPLAIN ANALYZE → find the Seq Scan → index the WHERE/JOIN column → re-explain.
11MySQL differs in UPSERT syntax, JSON, arrays, and feature dates — WordPress's engine, same language.
12SQLite is a file, not a server — for local dev and small loads; the SQL transfers.
13Parameterize everything; user input in SQL is the security doc's injection, in syntax.
