1b. Definition — what the dev loop is and what it is not

What it is

The development loop is the implementation rhythm that turns a known solution into a working UI feature. It is three threads — Model (data/state), View (structure/layout), Flow (events/logic) — cycled in rounds (Skeleton → Deepen → Polish), each round deeper than the last. It produces working code — the feature itself. The rhythm is universal: the same Model→View→Flow cycle applies whether you're building a todo list, a dashboard, or a complex form.

What it is not

  • Not problem-solving. Problem-solving (see that reference) finds the solution — the algorithm, the plan, the verified logic. The dev loop takes that solution and implements it as a feature. A HackerRank challenge needs problem-solving; a React feature needs problem-solving then the dev loop.
  • Not system design. System design structures the solution across services and boundaries (see that reference). The dev loop structures the solution within one feature — the data shape, the component tree, the event flow.
  • Not the SDLC. The SDLC is a project-scale phase model (Requirements → Design → Implementation → Testing → Deployment). The dev loop is smaller and older — it's the rhythm of a single feature, a single afternoon's work. As §9 shows, it predates every named methodology.
  • Not a fixed algorithm. You can't write down "step 1: do this, step 2: do that" for building a feature — the steps change as you learn. It's a rhythm: you cycle through the threads, you feel the friction, you deepen when it creaks. See §10 for why.
  • Not just for React. The three-thread loop predates React — it applies to Vue, Svelte, Angular, even vanilla JS. React just made it visible because a component is a small enough unit to round-trip in an hour.

Well-defined vs wicked — where the loop lives

The dev loop lives squarely in wicked problem territory (see Problem-Solving §1): the requirements evolve, the success criteria are subjective ("does it look right?"), and there's no clear stopping rule — only better or worse. This is why it's a rhythm, not an algorithm. A HackerRank challenge (well-defined) gets an algorithm; a UI feature (wicked) gets a rhythm. Both use the same underlying thinking process (Pólya's four phases), but they converge to different output types.

The rhythm survives because it's the shape of iterative work itself, not a tool.

1e. Underlying theory — why the loop works (the cognitive science)

The three-thread loop wasn't derived from cognitive science — it was derived from practice, from decades of developers noticing what works. But cognitive science explains why it works, providing the theoretical foundation.

Working memory limitations — why you can't hold all three threads at once

Working memory is severely limited (Miller 1956: ~7±2 items; Cowan 2001: ~4). You cannot simultaneously hold the data shape (Model), the component tree (View), and the event flow (Flow) in working memory while also writing code. The loop is the workaround: you focus on one thread at a time, holding the others lightly, and cycle through them. Each pass is shallow enough to fit in working memory. This is the same principle as Pólya's "offload to external representation" (see Problem-Solving §1e) — the rounds let you externalize one thread while holding another.

Cognitive load theory — why shallow-then-deep beats all-at-once

Sweller's cognitive load theory (1980s) identifies three types of mental effort: intrinsic (the problem's difficulty), extraneous (how info is presented), and germane (effort to build schemas). Building a feature all-at-once maximizes extraneous load — you're juggling data, layout, and logic simultaneously. The rounds reduce extraneous load: in Round 1 (Skeleton) you only deal with the simplest possible data + one element + one event. As you deepen, you add one thread at a time, keeping total load within working memory capacity. The rounds are a cognitive load management strategy.

Feedback loops — why hot reload changed everything

A feedback loop uses information about current status to influence future status (Wikipedia). The tighter the loop, the faster you learn. Before hot reload (Vite, Fast Refresh), the feedback loop was: edit → compile → refresh → see result (seconds to minutes). After: edit → see result (milliseconds). This is why the frontend loop works at the feature scale — you can cycle through Skeleton → Deepen → Polish in minutes because you see each change instantly. Boehm's spiral model (1986) worked at project scale because the feedback loop was months; React works at feature scale because the feedback loop is milliseconds.

The "feel the friction" signal — metacognition in the loop

The signal to move from one round to the next — "feel the friction" — is a metacognitive judgment, not a mechanical rule. This is Schoenfeld's metacognition (see Problem-Solving §5) applied to feature building: you monitor your own progress and decide "this round is creaking, it's time to deepen." You can't turn it into a checklist because a checklist assumes you know what to do next — the loop assumes you know what's missing, which is an aesthetic judgment. Senior devs have internalized this signal through hundreds of iterations; juniors build it through deliberate practice (§8).

The spiral model — the formal ancestor

Barry Boehm's spiral model (1986, Wikipedia) is the named ancestor of the frontend loop. Each spiral cycle has four quadrants: Plan → Risk Analysis → Engineering → Evaluation. You go around, each cycle deeper. The spiral is risk-driven: the level of detail in each cycle is determined by the risks you need to resolve. The frontend loop inherits this: Round 1 (Skeleton) resolves the risk "does the data shape work?"; Round 2 (Deepen) resolves "does the UI look right?"; Round 3 (Polish) resolves "does it handle edge cases?"

IID — older than waterfall

Larman and Basili's 2003 IEEE paper (Wikipedia) traced iterative and incremental development back to the 1950s — it's older than Waterfall. Project Mercury (NASA) code was built iteratively. The spiral didn't invent the loop; it named what good developers already did. The frontend loop is the same pattern, at a different scale — the latest inversion in an 80-year lineage of iterative practice.

1. The three-thread mental model — not a sequence, a loop

When a senior developer sits down to build a feature, they do not follow a waterfall: "first structure, then layout, then functionality." Instead they hold three intertwined threads and cycle through them, each pass deeper than the last:

┌─────────────────────────────────────────────────────────────┐
│  THREAD 1: MODEL        │  THREAD 2: VIEW          │ THREAD 3: FLOW   │
│  Data structures        │  Structure + Layout      │  Events, data    │
│  State shape            │  Visual hierarchy        │  movement, logic │
│  (what the app "knows") │  (what the user "sees")  │  (what happens)  │
└─────────────────────────────────────────────────────────────┘
                    ↑_____________________________↓
                     You cycle these, round by round

Each round touches all three threads, but at a different fidelity:

Round Name Model thread View thread Flow thread
0 Clarify What data does the system hold? Where does it come from/go? What does the user see and do? What are the entry/exit points? What triggers what?
1 Skeleton Pick simplest structures (array, plain object). Defer Map/Set. Semantic HTML only. No CSS. Just structure. Name handlers, wire empty functions, one state setter.
2 Deepen Upgrade structures where pain appears (O(1) lookups → Map). Full styling. Responsive. Accessibility. Real logic. Async, error states, edge cases.
3 Polish Performance: memo, virtualize, index only if measured. Micro-interactions, loading skeletons, empty states. Debounce, retries, analytics, defensive guards.

Key insight: You do not finish Thread 1 before starting Thread 2. You sketch the data shape (Thread 1), immediately write the skeleton HTML (Thread 2), immediately stub the click handler (Thread 3) — then you go around again. The threads are intertwined because each one constrains the others. The data shape determines what UI is even possible; the UI structure reveals missing fields in the data; the event flow exposes derived state you forgot to model.

2. Round 0 — The three clarifying questions (the hardest part)

Before any code, before any HTML, you answer these three questions. This is where the data shape starts — not because you're designing algorithms, but because the shape of the data determines everything downstream.

  1. What does the user see and do? — "A list of products. User clicks 'Add to cart'. Cart badge updates."
  2. What data does the system hold? — "Products have id, name, price, image. Cart is a list of product ids + quantities."
  3. Where does the data come from and go? — "Products from an API. Cart stays in local state (maybe localStorage)."

Do developers think about algorithms at the start?

For frontend, usually no — unless the feature involves search, sort, filtering, or complex state transitions. Most frontend "logic" is CRUD (create, read, update, delete) + UI wiring. You think about algorithms when performance bites you: "this list has 10,000 items, render is slow, I need virtualization or a better data structure." The default posture: start with the simplest structure, upgrade only when you feel the pain.

---

3. Round 1 — Skeleton pass (the thinnest end-to-end slice)

You touch all three threads with the cheapest version of each. The goal: a working end-to-end path, however minimal.

Thread 1: Model — Data shape and state decisions

  • Finalize the data shape. Often a TypeScript interface or a sketch on paper.
  • Identify what state the component holds vs what it receives as props.
  • Pick the data structures: plain objects, arrays, Map, Set — whatever fits right now.

Example — a product cart:

Product = { id, name, price, image }
Cart = Map   ← or just an array, decide later

How you decide the structure:

  • Start with the simplest version (array of objects).
  • Upgrade to Map only when you need fast lookups ("is this in the cart?" → Map.has is O(1)).
  • You don't design ahead for performance you don't yet need (YAGNI — You Aren't Gonna Need It).

Thread 2: View — Structure + Layout

This is where you write HTML structure — semantic tags, not styled yet. Layout comes right after or interleaved with structure.

Do devs use templates? Yes — constantly. You almost never start from a blank file:

  • Framework templates: npx create-react-app, npm create vite, Next.js starter — scaffolds the folder structure.
  • Component conventions: your team has patterns — "a list component maps over an array and renders for each."
  • Design systems / UI libraries: Material UI, shadcn/ui, Tailwind UI — you compose pre-built buttons, cards, dialogs instead of building them from scratch. This is the closest thing to "layout templates."
  • Copy-paste from your own codebase: the last ProductCard you wrote is your template for the next one.

So the structure isn't chosen in isolation — it's an inheritance chain:

framework layout → project convention → component pattern → your variation

Layout specifically: You rarely invent layouts. You reach for the same small set of CSS patterns: flexbox for one-direction (rows/columns), grid for two-direction (galleries, dashboards). The decision is "flex or grid?" then "how many columns?" — not "what novel layout should I invent?"

Thread 3: Flow — Events + Data Movement

  • Wire up the skeleton of behavior: a click handler that does nothing yet, a state setter that just holds a value.
  • You name the functions ("addToCart", "removeFromCart") before you fill them in.
  • This is where you think about the data flow: "user clicks → component calls addToCart → cart state updates → badge re-renders."

Declarative vs imperative: If you're using React, the flow is: state changes → React re-renders → DOM updates. You don't manually touch the DOM. This is called declarative flow and it's the biggest mental shift in modern frontend.

5. Round 3 — Edge cases and polish (the difference between works and ships)

  • What if the API fails? (→ error state)
  • What if the list is empty? (→ empty state)
  • What if the user clicks twice? (→ debounce, disabled state)
  • Accessibility: keyboard nav, aria labels, focus management
  • Performance: memoization, lazy loading, virtualization only if needed

5b. Mental models — how developers actually reason across rounds

The loop in §1–§5 is a sequence of passes, but the developer's mental model is more like a triple-thread: a thread for "is this correct?" a thread for "is this complete?" and a thread for "is this cheap?" Different camps weight these threads differently.

CampDominant threadWhat "done" meansWhat gets cut firstFailure mode
Junior / bootcamp "Does it run?" The screenshot matches the mockup Edge cases, error states Works on happy path; crashes in production
Mid-level generalist "Is it feature-complete?" All listed requirements ship, nothing is broken Performance, refactor Feature-creep without ownership of cost
Senior generalist "Will this still be maintainable in 18 months?" Tests exist, seams are clear, naming carries intent Speed-to-ship if the cost is just "code volume" Over-engineering for problems that never materialize
Performance specialist "Is it cheap to run?" Profiled numbers, not assumptions Polish, micro-features Optimization for code paths nobody executes
Architect "Will the next team be able to extend this?" Bounded contexts, named seams, ADR's written Premature detail; anything below the seam Seam-obsession; the seam becomes the product

The loop is the same for all camps; the weighting differs. Knowing which thread you are neglecting is half the diagnostic. If you ship a feature in two days and it crashes in production, you skipped the "complete" thread. If you ship a feature in two weeks and nobody can read the code, you skipped the "maintainable" thread. The loop is not a checklist — it is a set of competing demands, and seniority is the ability to balance them under time pressure.

7. The honest truth about how senior devs work

  1. They copy first, understand later. They've seen the pattern (list, form, modal, dashboard) dozens of times. They skeleton it from muscle memory, then adapt.
  2. They defer decisions. "I'll use an array, change to Map if needed" — not "let me design the optimal cart structure."
  3. They don't separate thinking into threads the way this doc draws them — it becomes one fluid loop because they've internalized it.
  4. Structure follows state, not the other way around. The shape of your data determines your component tree. Get the data shape right and the UI structure often falls out naturally.
  5. They do the simplest thing that could possibly work, then refactor. Premature optimization is the cardinal sin.

8. Your takeaway — the deliberate practice loop

If you're learning, practice the skeleton → deepen → polish loop deliberately:

  1. Pick a small feature (e.g., a todo list).
  2. Sketch the data shape on paper before coding (what does a todo look like? where is it stored?).
  3. Build the skeleton HTML — semantic, unstyled.
  4. Add one piece of flow — adding a todo.
  5. Add a second bit — toggling complete.
  6. Add a third — deleting.
  7. Now style it fully.
  8. Now handle edge cases — empty list, double-submit.

That loop — shallow all three, then deepen, then deepen again — is the algorithm. It's not a template you download, it's a rhythm you develop by doing it 50 times.

9. What is this process called? — Entity types and terminology

The loop described above (Model → View → Flow, shallow then deepen) is not the SDLC. It's smaller and older than any named methodology. Here's the map:

TermScaleWhat it covers
SDLC (Software Development Life Cycle) Whole project, months to years Requirements → Design → Implementation → Testing → Deployment → Maintenance. A phase model — you move forward through phases.
Methodology (Agile, Waterfall, Spiral) Project, weeks to months How you navigate the SDLC — Agile does it in small loops called sprints, Waterfall does it once top-to-bottom.
Workflow Team, hours to weeks Who does what in what order with what tools — "open ticket → branch → PR → review → merge." A coordination pattern.
Best practice Task, minutes to hours A habit that works — "name booleans with is/has", "validate at the trust boundary." A rule of thumb, not a sequence.
The loop I described Single feature, minutes to hours A micro-process — smaller than a workflow, bigger than a best practice. It's a thinking rhythm for one unit of work.

So the honest answer: it doesn't have one canonical name because it sits below the SDLC/methodology layer. The closest named things are:

  • "Spiral development" (Barry Boehm, 1986) — the ancestor concept: iterate through risk-driven loops, each deeper than the last. My "shallow → deepen → polish" is the spiral pattern at feature scale.
  • "Incremental development" — build the thinnest end-to-end slice, then add. The "skeleton pass" is the thinnest slice.
  • "Iterative and incremental development" (IID) — the formal name in the literature. Craig Larman and Victor Basili wrote the canonical history of it.
  • Inside Agile/Scrum: it shows up as the "sprout → grow → harden" rhythm within a sprint. Not official Scrum vocabulary, but it's how practitioners describe it.
  • Inside Lean UX / design: it's called "build-measure-learn" (Eric Ries, The Lean Startup, 2011) — same loop with a feedback step bolted on.

So the entity type is: a micro-process — a thinking rhythm at the task level, below SDLC, below methodology, below workflow. It's more cousin to a best practice than to a methodology, but it has sequence (which best practices don't) and looping (which Waterfall doesn't).

10. Why is it a rhythm, not a structured algorithm?

Because a structured algorithm has predefined inputs, deterministic steps, and a fixed termination condition. QuickSort is a structured algorithm: give it an array, it sorts it, you're done. The steps are the same every time.

The model-view-flow loop fails all three:

  • Inputs aren't predefined. You don't know what the feature really is when you start. Part of the loop is discovering that. A feature starts as "make a cart" and becomes "make a cart with quantity editing, persisted across sessions, with a max-items alert" — you discover the scope by building it.
  • Steps aren't deterministic. There's no rule that says "now do Round 2 of the View thread." You do it when you feel the friction — when the skeleton is too ugly to leave, when the data shape is too wrong to keep going. Senior devs feel the friction; juniors need checklists until they develop the feel.
  • There's no fixed termination. "Done" is a judgment call: is this good enough to ship? That's a taste decision, not a predicate check. (If you work in a regulated domain — medical, aerospace — you do have termination criteria, which is why those fields do have structured algorithms like MC/DC coverage. Frontend doesn't.)

A rhythm is a pattern you internalize so you can improvise around it. Like playing jazz: there's a chord progression, but what you actually play depends on what just happened. Senior devs play the codebase. Juniors play the sheet music. The loop is the chord progression.

This is why it resists being turned into a checklist that you follow robotically: a checklist assumes you know what to do next — the loop assumes you know what's missing, which is an aesthetic judgment, not a mechanical one.

11. History of this loop — from NASA to React

The thread runs through the whole history of software:

Year / EraName / EventWhat it contributed
1960s–70s Waterfall (Winston Royce, 1970) The myth was: design everything upfront, build once. Royce's paper actually warned against doing it as a single pass — people read the diagram, skipped his warning. Worked fine when bug fixes meant reordering punch cards.
1986 Spiral Model (Barry Boehm) First formal "loop" model. Each spiral cycle has four quadrants: Plan → Risk Analysis → Engineering → Evaluation. You go around, each cycle deeper. The named ancestor of "skeleton → deepen → polish."
1980s–90s IID — Iterative & Incremental Development Larman & Basili's 2003 IEEE paper traced this back to the 1950s — it's older than Waterfall. Project Mercury (NASA) code was built iteratively. The spiral didn't invent the loop; it named what good devs already did.
1999 Extreme Programming / XP (Kent Beck) "Make it work, make it right, make it fast." That's the same three rounds, in code form: working skeleton → refactor for clarity → optimize for performance. Beck explicitly said he took it from the Smalltalk community's rhythm of "spike → stabilize → harden."
2001 Agile Manifesto Institutionalized the loop at sprint scale. Two-week spirals.
2011 Lean Startup (Eric Ries) "Build-measure-learn" externalized the loop to product discovery (build the thinnest slice, see if users want it, decide whether to deepen).
2015–now Modern frontend (React, Vue, Svelte) Component model made the loop visible in code — because a component is a small enough unit to round-trip in an hour, the rhythm moved from project scale down to feature scale. "Skeleton → deepen → polish" is now how a single React component gets written, not just how a project gets run.

So: Boehm named it (spiral), Beck operationalized it (XP), Agile institutionalized it (sprints), and React made it work at the component scale. What this doc describes is the bottom of that stack — the same pattern, but at the scale of an afternoon's work.

12. The vocabulary map — wireframe, mockup, prototype, MVP, rough draft, versioning

You hear a lot of names because the same loop runs at different scales with different vocabulary. Here's the complete map:

TermScaleFidelityDisposabilityUsed for
Sketch Minutes Low (paper, whiteboard) Disposable Thinking. You throw it away once you understand the problem.
Wireframe Hours Low (grey boxes, no color) Disposable-ish Structure of pages — what goes where, no visual design. The "skeleton pass" at the page level.
Mockup Hours–days High visual, no behavior Kept as reference Look — colors, fonts, spacing, real-ish content. Static. Still no flow.
Prototype Days Variable (often clickable) Meant to be thrown away Flow — you can click through, see how it feels. Figma prototypes, clickable mockups. The deepening pass at UX scale.
PoC (Proof of Concept) Days Throwaway code Disposable Will this even work? — technical risk reduction, never shipped.
Spike (Agile term) Hours–days Throwaway code Disposable What's the real cost/shape of this feature? — you build it to throw it away so you can estimate the real one.
MVP (Minimum Viable Product) Weeks–months Production-quality small slice Shipped, kept The smallest version users will actually use. Not disposable — this is the product, just small.
Rough draft Informal term Whatever Variable Just means "first pass, expect to revise." A cross-scale, cross-fidelity term.
Version Any scale Marker of history Cumulative The artifact's history. v1, v2, v3 — each version is a checkpoint, you can go back. Doesn't say anything about fidelity, only about sequence.
Release Project scale Production-ready Branded, public The subset of versions you actually ship to users. v1.0.0, v2.0.0.

The three axes — locate any artifact on these

Three independent axes you can locate any artifact on:

  1. Fidelity — how real does it look/feel? (sketch: low, mockup: high)
  2. Disposability — is this meant to be thrown away? (PoC: yes, MVP: no)
  3. Behavior — does it do anything, or just sit there? (mockup: static, prototype: clickable)

                              production-worthy
                                   MVP      ─────►  v1.0  v1.1  v2.0  (versions/releases)
                                     ↑ (shipping, kept)

"Wireframe" = high disposability + low fidelity + no behavior. "Prototype" = medium disposability + variable fidelity + clickable. "MVP" = low disposability + production fidelity + fully working. They are not synonyms — they're the same loop at different points on those axes.

Versioning is orthogonal to all of it: it's the history of any artifact at any fidelity. A wireframe can have v3. A release can have v3. Versioning isn't part of the loop; it's the bookkeeping of the loop.

12b. Principles — the shared constants

Across every framework, every era, every tool, certain principles don't change. These are the constants that survive React, Vue, Svelte, and whatever comes next.

PrincipleWhy it's constant
Cycle, don't waterfallYou can't know everything upfront. Requirements change, data shapes evolve, UIs look different once rendered. The spiral (Boehm 1986) and IID (Larman & Basili 2003) proved this empirically: iterative beats upfront-design for wicked problems. The rounds (Skeleton → Deepen → Polish) are the same principle at feature scale.
Feel the friction to know when to deepenThe signal to move from one round to the next is metacognitive (§1e). You can't checklist it — it's an aesthetic judgment about what's missing. Senior devs have internalized it; juniors build it through practice (§8). This is Schoenfeld's metacognition applied to feature building.
Sketch the data shape firstThe data shape determines the component tree (§13). Getting it wrong costs minutes if caught early, hours if caught late. This is the same "structure before code" principle as stepwise refinement (Problem-Solving §6) — the shape is the contract; the code fills it.
Derived state is never storedIf a value can be computed from other state (filtered list, active count), don't store it — recompute it. Storing derived state is the most common frontend bug: two sources of truth that drift apart. This is invariant across React, Vue, Svelte.
Thinnest end-to-end slice firstRound 1 (Skeleton) is the thinnest slice that works end-to-end: one piece of data, one element, one event. Not "build all the data then all the UI then all the logic" — that's waterfall in disguise. The thinnest slice validates the data shape and the flow before you invest in depth.
Structure follows stateThe shape of your data determines your component tree. Get the data shape right and the UI structure often falls out naturally. This is why §7 says "seniors defer decisions" — they sketch the data, let the structure emerge, and refactor when the data shape proves wrong.
Do the simplest thing that could possibly work, then refactorPremature optimization is the cardinal sin (§7). Start with an array, change to Map if needed. Start with plain CSS, reach for Tailwind if the pain appears. The loop's rounds are designed for this: Round 1 is the simplest thing; Round 2 is where you upgrade.
Defer decisions until you need them"I'll use an array, change to Map if needed" — not "let me design the optimal cart structure." Seniors defer because they know the data shape will evolve once they see it rendered. Deciding too early locks you into a structure that may be wrong.

13. "Sketching the data shape" — what it actually means, with a full worked example

This is the part that confuses everyone, and it's the most important one. The data shape is the structure of the values your program holds in memory while running. Not the database, not the API response, not the UI — what your code is actually pushing around. It's the answer to: "what kind of value is at the heart of this feature?"

It has nothing to do with visual layout. It's about the logical skeleton of the information. If your program were a body, the data shape is the bones — the UI is the skin. You don't design a face before you know if it's a fish or a human.

---

Worked example: "I'm building a todo app"

The naive instinct is to start writing HTML — "I'll have an input box, a button, a list." Wrong. You freeze the input box before you know what it's supposed to capture.

What you do instead:

Step 1 — Name the nouns

What are the things this app is about? Not UI elements — the real things.

  • A todo — a single task to do
  • A list of todos — the collection
  • (Maybe) a filter — "all / active / completed"

Step 2 — Give each noun a shape

A single todo. What fields does it have? You might sketch on paper:

todo = {
  id:      ???      ← what identifies it? number? string? uuid?
  text:    string   ← the task description
  done:    boolean  ← is it complete?
  when:    Date     ← when was it created?
}

Now you have decisions to make, and making them now (before code) is cheap:

  • id — number is fine for 10 items, but what if I add persistence later? UUIDs are safer. Decide.
  • done — boolean is simple, but what if I want "in progress"? Maybe it should be a status enum. Decide. For an MVP, boolean is fine.
  • when — do I need this for an MVP? Maybe skip. Decide.

This is what "sketching the data shape" looks like — writing down the fields, deciding their types, deferring or committing to each.

Step 3 — Give the collection a shape

How do you hold many todos? The options:

Option A:  todos: Todo[]                  ← an array
Option B:  todos: Map           ← keyed by id
Option C:  todos: { [id]: Todo }          ← object as a map

Each has consequences:

  • Array — simplest. Adding is push. Finding by id is find (linear scan, O(n)). Fine for 50 todos, painful for 50,000.
  • Map — adding by id is set (O(1)). Finding is has/get (O(1)). Better when "is this id in the list?" matters often (like checking for duplicates).
  • Object-as-map — works, but keys must be strings, and you inherit Object.prototype noise. Map is cleaner.

For a todo app MVP, you pick array — because you'll render the list in order, and iterating an array is trivial. You note on the sketch: "if we ever do 10k+ items, re-evaluate." That note is the sketch's whole point — you record the assumption so you can revisit it.

Step 4 — Sketch the operations

Now describe what the user does to this shape — not in code, in plain operations:

- add a new todo       → push {id, text: "buy milk", done: false} to array
- toggle a todo        → find by id, flip done
- delete a todo        → find by id, remove from array
- filter by status     → array.filter(t => t.done === false)
- count active         → array.filter(...).length          ← or, cache this

You don't write the code. You just check: are these operations natural on the shape I picked? If you'd picked a Map, "filter by status" would be awkward (you'd have to iterate values). If you'd picked an array, "is id X in the list?" would be awkward (you'd scan). The sketch surfaces these frictions before you've written a line of code.

Step 5 — Sketch the components at the level of "what state does each one hold?"

Only now do you start thinking about the UI:


  state: todos (array), currentFilter ("all"|"active"|"completed")


  state: nothing (just shows count, derived from todos)

  state: draftText (string — what's currently in the box)

  state: nothing (receives todos + filter as props, derives the filtered list)

  state: nothing (receives one todo, calls back on toggle/delete)

Notice the wiring falls out of the data shape:

  • You hold todos at the App level because multiple components need it (header count, list rendering, item actions).
  • You hold draftText locally at NewTodoInput because only that input cares about the half-typed text.
  • You don't hold "filtered list" as state — you derive it. Storing derived values is one of the most common bugs in frontend state.

A senior dev does this in their head in 30 seconds. A junior does it on paper. The point isn't the artifact — the point is the thinking: forcing yourself to ask "what is this thing made of?" before you commit code to a particular shape.

---

Why data shape first — three reasons

  1. The shape determines the UI structure, not the other way around. If your core data is a tree (categories nested in categories), your UI will have recursion in it somewhere. If your core data is a flat list, the UI will be flat. Knowing the shape tells you what UI is even possible.
  2. Changing the data shape late is expensive. If you build the UI around an array and then realize you need O(1) lookups, you have to plumb a Map through every component. If you sketch it first, you've lost 30 minutes. If you discover it after writing 500 lines of UI, you've lost a day.
  3. The shape exposes the decisions that matter. "Boolean or enum?" "Array or Map?" "Where does this state live?" are decisions that won't show up if you just start writing HTML. They're invisible until they bite. Sketching the data shape shines a light on them early.
---

Second example — even simpler: a search box

You're building a search box. Naive: write an input. Smart: sketch first.

state:
  query: string              ← what's in the box right now
  results: Product[]        ← what the search returned
  status: "idle" | "loading" | "done" | "error"   ← key insight
  └─ do you have status as a separate field, or pack it into results?
     packing it (e.g. results = null while loading) is a bug factory
     — separate field is the senior move

That tiny sketch — three fields — determines that you won't make the classic junior mistake of using results === null to mean "still loading" and then getting confused about "loading" vs "loaded but empty results." You saw the trap before writing code.

This is what sketching the data shape buys you: you see the traps while they cost minutes, not days.

13b. The most common failure modes

These are the characteristic ways the dev loop goes wrong — the traps that catch practitioners at every level, from junior to senior.

Failure modeWhat happensThe fix
Premature polishingYou start styling (Round 3) before the skeleton works (Round 1). Two hours in, you have a beautiful button that doesn't do anything, and the data shape is wrong — so the styling has to be redone.Force yourself through Round 1 first: the thinnest end-to-end slice that works, unstyled. Only start styling when the data shape and flow are validated.
Over-planning (analysis paralysis)You spend an hour designing the perfect data shape on paper, trying to anticipate every field and operation. But you can't know until you see it rendered — the shape evolves.Sketch the data shape (§13) but timebox it: 5-10 minutes, not an hour. The sketch is a starting point, not a final design. The loop will refine it.
Skipping the data-shape sketchYou jump straight to code: "I'll figure out the data as I go." Result: you build a component tree for the wrong data shape, and refactoring it costs hours.Always sketch first — nouns, fields, collection type, operations. Even 2 minutes of sketching catches the "loading vs empty" trap before it costs days (§13).
Storing derived stateYou store a filtered list in state alongside the full list. Now you have two sources of truth. When the full list changes, the filtered list drifts — the most common frontend bug.Derived values are computed at render time, never stored. const visible = items.filter(i => i.active) — not const [visible, setVisible] = useState(...). See §14 checklist.
Waterfall in disguiseYou build all the data layer, then all the components, then all the events. It feels like progress, but you haven't seen anything work end-to-end until the end — and by then, the data shape is baked in and wrong.The rounds are rounds, not phases. Round 1 should be a working slice — data + one element + one event — not "finish the data layer." Cycle through all three threads shallowly, then deepen.
Copy-paste without understandingYou copy a pattern (a modal, a form, a list) from a previous component or Stack Overflow. It works, but you don't understand why. When it breaks, you can't debug it.Copy first, understand later is OK for seniors (§7) who've internalized the patterns. But if you're learning: build the skeleton yourself, then compare to the copied version. The effort builds the schema (Problem-Solving §1f).
Premature optimizationYou reach for useMemo, useCallback, React.memo, or a state management library before the feature works. Each adds complexity; each is a decision you can defer until you feel the pain of not having it.Do the simplest thing first (§7). An array, a useState, a plain function. Reach for optimization tools only when you feel the friction — slow rendering, duplicate logic, prop drilling. The React Compiler (§13d) is increasingly automating this.
Not feeling the frictionYou follow the rounds mechanically — "I'm on Round 2 now" — without noticing what's actually creaking. You deepen the wrong thing, or skip deepening where it matters.The "feel the friction" signal is metacognitive (§1e). Build it through deliberate practice (§8): build 50 features, each time noticing what made you want to deepen. Over time, the signal becomes automatic.

13c. Ecosystem — tooling catalog with decision metrics

The dev loop is only as fast as its feedback loop allows. Here's the catalog of tools that make the loop work, with decision metrics for choosing the right ones.

CategoryToolBest forDecision metric
Data-shape sketchingPen and paperRound 0 (clarifying questions), the data-shape sketch (§13).The single most important tool. Offloads working memory (§1e). No setup, no distraction, no AI doing the thinking for you. Always start here.
TypeScript types / JSDocExternalizing the data shape into the code.Use after the paper sketch. TypeScript types are executable documentation — they catch shape mismatches at compile time. If you're not using TS, JSDoc is the lighter alternative.
WireframingExcalidraw / pen and paperQuick, disposable sketches of the View thread.High disposability + low fidelity. Perfect for Round 0/1 — you're sketching structure, not pixel-perfect design. Throw away after the skeleton works.
FigmaHigher-fidelity mockups, design systems.Use when the View thread needs real visual design (Round 2-3). Not needed for the skeleton pass. Overkill for a todo list; essential for a dashboard.
Prototyping / dev serverViteInstant hot reload — the tight feedback loop that makes feature-scale iteration possible.The default. Millisecond feedback is why the rounds work at all (§1e). If your dev server takes more than 1 second to reload, fix that first — slow feedback kills the loop.
Next.js dev serverSame, but with server components.Use when the Model thread is server-rendered (RSC). The loop is the same; the feedback loop is slightly longer because of server compilation, but still fast enough for feature-scale iteration.
State managementuseState / useReducerComponent-level state. The default.Start here always. useState for simple values, useReducer for complex state transitions. Don't reach for a library until you feel the friction of prop drilling or shared state.
Zustand / Redux / JotaiCross-component shared state.Reach only when prop drilling becomes painful (the "feel the friction" signal). Zustand is the lightest; Redux is the heaviest (and most over-adopted). The React Compiler (§13d) may reduce the need for some of these.
DebuggingReact DevToolsInspecting component tree, state, props.Essential for Round 2-3. Lets you see the Model and View threads live. The "Inspect" tool shows you what state each component holds.
Browser DevToolsInspecting the DOM, network, console.For the Flow thread — seeing what events fire, what the API returns, what the DOM looks like. See HTML & CSS §5b for the platform-level mental model.
AI toolsCopilot, ChatGPTScaffolding the skeleton (Round 1), generating boilerplate.Use with caution. AI can scaffold Round 1 for common patterns (todo list, form, table), but the Deepen and Polish rounds need human judgment — the "feel the friction" signal is yours, not the AI's. Never let AI generate the data-shape sketch — that's the decision that catches traps (§13). See Problem-Solving §13c for the same caution.

The one tool that matters most: pen and paper. The data-shape sketch (§13) is the single most important upfront decision, and it should happen on paper before any code. No tool substitutes for the act of writing "what are the nouns? what fields? what collection type?" by hand. The tightest feedback loop is between your pen and your brain.

13d. The future — where the dev loop is heading

React Compiler: automating the optimization round

The React Compiler (2024+) automatically handles memoization — the manual useMemo, useCallback, and React.memo that developers reach for in Round 2-3. This doesn't change the loop's shape (you still cycle Model → View → Flow), but it changes what Round 2 (Deepen) produces: instead of manually optimizing re-renders, the compiler does it for you. The human's Round 2 shifts from "performance optimization" to "making the data and flow right" — which is where the judgment actually matters.

Server Components: the Model thread splits

React Server Components (RSC, 2023+) changed where the Model thread runs. Before: the entire loop ran in the browser (SPA). After: the Model thread partially runs on the server (data fetching, rendering), and the View/Flow threads run on the client (interactivity). The loop is the same (Model → View → Flow), but the boundary shifted. See React 2024+ and Next.js Deep Dive. The implication for the loop: the data-shape sketch (§13) now needs to account for what's server-side vs client-side — a new dimension in Round 0.

AI scaffolding: the skeleton round gets automated

AI tools (Copilot, ChatGPT) can now generate the skeleton (Round 1) for common patterns — a todo list, a form, a table with sorting. This doesn't eliminate Round 1; it changes what the human does in it: reviewing the AI's skeleton against the data-shape sketch, rather than writing it from scratch. The Deepen and Polish rounds still need human judgment — the "feel the friction" signal (§1e) is the human's job, not the AI's. But the fluency trap (see Problem-Solving §11) intensifies: AI makes it easy to feel you understand the feature without building the schema that lets you improvise when it breaks.

The enduring rhythm

Frameworks change. React becomes Next.js becomes whatever comes next. But the three-thread loop (Model → View → Flow, cycled in rounds) has survived from Boehm's spiral model (1986) through XP (1999) through Agile (2001) through React (2013) through Server Components (2023) through the React Compiler (2024). The rhythm survives because it's the shape of iterative work itself — the same pattern that Larman and Basili traced back to the 1950s, applied at the scale of a single afternoon's work. Learn the rhythm once, and it serves you across every framework, every era. That's why this reference exists: not to teach you React, but to teach you the thinking process that generates features — the one skill that compounds across your entire career.

14. Summary — the complete mental checklist

Next time you sit down to build a feature, run this checklist. If you can answer each, you're ready to code. If not, sketch until you can.

QuestionIf you can't answer…
What are the nouns in this feature? (todo, cart, product, user…)Sketch the domain model first
What fields does each noun have? What are their types?Sketch the data shape (Step 2)
What collection type holds the nouns? (array, Map, Set…)Sketch the collection shape (Step 3)
What operations does the user perform on the data?Sketch the operations (Step 4)
Are those operations natural on your chosen structure?Reconsider the structure
What state lives where in the component tree?Sketch the component state (Step 5)
What is derived (not stored)?Mark it derived — don't put in state
What's the thinnest end-to-end slice I can build first?That's your Round 1 (Skeleton)

Print this table. Put it on your wall. Run it before every feature. The first five rows are "sketch the data shape." The last three are "the loop." That's the entire method.
