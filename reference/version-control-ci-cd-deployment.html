Reference · The delivery layer — getting code from a commit to users running it

Version Control, CI/CD & Deployment

What version control is (a team's shared, versioned history of source), how Git works inside (the content-addressed DAG that explains every command, branches, and the pull-request loop), and how teams take a passing push all the way to production — Continuous Integration (verify every change), Continuous Delivery, and the deployment strategies (rolling, blue-green, canary, feature flags) that ship it safely. Read this to understand the layer that sits between a commit on your machine and live code running in front of users.

1. Definition — what version control is and what it is not

Version control is a system that tracks changes to source over time, letting many developers work without overwriting each other, and lets anyone recover any past state (Wikipedia). Git (2005, Linus Torvalds) is the dominant distributed version-control system; teams commonly pair it with GitHub, GitLab, or Bitbucket for hosting, review, and automation.

But version control alone is half the story. CI/CD is shorthand for two continuous practices:

  • Continuous Integration (CI) — every change integrated into a shared mainline and verified automatically (build + tests) and fast (Fowler).
  • Continuous Delivery — the team keeps the deliverable production-ready and releases it manually or by flag; continuous deployment releases without a human gate. The two are often conflated; §4 keeps them apart.

Deployment is putting a verified, versioned release into a running environment — strategy in §5.

What this doc is NOT

  • Not the process layer. This is not about sprints/backlogs/Agile — that's The Process. This doc is the layer of automation that ships code.
  • Not a testing manual. The pipeline automates test evidence; Software Testing explains test levels, test strategy, doubles, and production verification.
  • Not a click-through manual. The goal is the model, so every command and service makes sense — not a sequence of steps.
  • Not infrastructure operations or SRE. Monitoring and deployment health appear where they affect safe delivery; deep operations practice is a separate specialty.

1b. History — from file-locking to Git and the distributed pull request (2005–present)

Version control has a clear lineage, each generation solving the previous one's failure mode:

YearSystem / eventWhat it contributed
1970s–80sRCS (local, single-file)Revision control on files, local, per-file. Could only see one file's deltas at a time — tiny scope.
1986CVSThe first central concurrent-version system: many files, many developers, "check in/check out". Introduced the idea of a shared server as the source of truth — but merges were clumsy.
2000SVN (Subversion)Fixed CVS's non-atomic commits and poor rename/reference handling. For a decade, the default. Still centralized — the server is the only store of truth.
2005Git (Linus Torvalds)Built for the Linux kernel to solve the failure of distributed collaboration. Distributed: every clone is a complete repository with full history, not a snapshot. Content-addressed, DAG-based (see §2/§1e). No central server required (Pro Git).
2008GitHubGave Git a web UI, social layer, and the pull request. Made the distributed tool collaborative for teams and normalized hosted review plus automation workflows.
2010sGitLab, Bitbucket, GitHub ActionsJoined hosting with CI/CD — the "monorepo-to-release" pipeline became one product.

The recurring theme — the same frustration the Process doc traces in methodology: each generation moves from locking edges / a single truth / manual merging toward parallel, cheap, reversible, distributed. Git + the PR loop is where "collaboration without a human bottleneck" arrived.

1c. Evolution — the constraint inversions

Version control's evolution is a sequence of constraint inversions, one per era:

  • From "file-by-file" to "snapshot-of-the-whole-tree". RCS tracked per-file; Git snapshots the entire tree each commit. Change is atomic across the whole project, so a multi-file feature is one recoverable unit.
  • From central authority to every clone is the repository. Centralized systems such as SVN depend operationally on a server-side repository. Git gives every clone a complete local history, so collaboration and recovery do not depend on one central copy being continuously available.
  • From PATCHES (applied) to MERGES + PR. Not a single "patch" but a request to integrate a branch: reviewable, divisible, gated. The pull request refactored "change-joined-mainline" into a social collaboration artifact.
  • From "build it somewhere else" to "pipeline as code." Deploys moved from a human's runbook into a checked-in workflow file — versioned like code, so the delivery definition is under control too (the same versioning the source gets).

1e. Underlying theory — content-addressing and the snapshot model (why every Git command clicks)

Git isn't a list of files with version numbers — it's a content-addressed, snapshot-based, directed acyclic graph (DAG). Understand that, and every command decomposes into three primitives (Pro Git: Git Objects):

  • Blob — a file's contents, stored once by a hash of that content.
  • Tree — a sorted list of entries (blobs and sub-trees) with names and modes; the entire directory structure at one point.
  • Commit — points at one tree, plus the parent commit(s), author/message/timestamp. Commits are the DAG's nodes; each commit carries the full snapshot.

The commands operate across four locations:

LocationWhat lives thereCommands that move it
Working treeThe files you edit on disk.checkout, switch, restore
Index / staging areaThe snapshot you are preparing for the next commit. This is why git add and git commit are separate steps.add, restore --staged
Local repositoryCommitted objects and local refs: branches, tags, and HEAD — the pointer to your current branch or commit.commit, merge, rebase, reset
Remote repositoryThe shared repository plus your local remote-tracking refs, such as origin/main.fetch, push, pull

Two consequences that explain Git's "weird" behavior:

  1. Git objects are content-addressed and normally immutable. Identical content hashes to the same blob, so storing many snapshots costs little. Commits and other objects are not edited after creation, but refs, the index, and the working tree do move, and unreachable objects can eventually be garbage-collected.
  2. Branches are just names pointing at commits. A branch is a movable pointer, not a container. Moving HEAD (checkout, switch), adding a node (commit), and moving the branch pointer (merge) are all just "point the names at nodes". rebase goes further: it replays commits as new commit objects onto a new base, then moves the branch pointer. That's why branches are nearly free and merging is a graph problem, not a file-copy problem.

Why this matters beyond "knowing Git": the DAG snapshot model is the same shape as the pipeline: immutable artifacts connected by provenance. Every release you ship is a commit's content that was verified; every artifact the CI builds is a tree snapshot. Understand the graph, and CI/CD reads as "walk the verified chain of commits to production."

1f. Mental models — how senior engineers actually reason about delivery

Experts don't memorize git commands; they carry mental models that make the command set follow:

  • "Branches are cheap pointers; the cheap thing is to branch, the expensive thing is to not merge." Branch often, keep them short-lived, merge/mainline frequently. Long-lived un-merged branches are where the pain lives.
  • "Everything is append-only; recoverable." Commits are never lost (barring GC). git reflog recovers a "lost" commit; git reset/rebase rewrite pointers, not history. Safety is a mental given, so trying things is free.
  • "Deploy is not the same as release." Code can be deployed (present in an environment) but not released (not exposed to users) — feature flags, canaries. Separating the two is the senior move that makes "ship small, often" safe.
  • "CI is a gate, not a report." Green on every push is the guarantee that main is always releasable. When CI turns red, it blocks — because "main is broken" is the highest-priority bug; everything else stops until green returns.

2. Branching strategies — how teams share the DAG

Branches are how many people safely work on one shared history. A strategy is a policy for "who is allowed to protect them, how often they merge, and how they're integrated." The two dominant approaches (trunkbaseddevelopment.com):

Trunk-based development (the CI-friendly default)

  • All work happens on short-lived feature branches branching off main and merging back within a day or two (short branches, frequent integration).
  • Main is always releasable; CI verifies every merge. This is the model CI wants — small, frequent, integrated.
  • GitHub Flow is trunk-based with a PR as the merge vehicle: branch → commit → PR → review → merge → deploy.

GitFlow (more ceremony — for release trains)

  • Adds develop (integration), release/*, hotfix/* branches. Better for scheduled versioned releases with long-lived support; heavier, and generally overkill for teams deploying daily.

How to choose: can you deploy main to prod at any moment? Then GitHub Flow/trunk-based. Do you publish tagged versions to paying customers with a strict cadence? Then a release branch adds structure. When in doubt, start trunk-based — the ceremony emerges when a release actually needs it (§9b "over-engineering").

The pull request as the unit of change (with CI + review)

GitHub-style workflows treat a pull request as the reviewable, gated unit: branch → commit a slice → push → open a PR → CI runs checks → peers review → merge (or at a green gate). The PR is where the Process doc's "verify before you integrate" physically lives — the enforced discipline of committing small, reviewable, and gated live by branch protection that won't merge a busted main.

2b. The collaboration loop — push/pull, merge, and the pull request

The daily rhythm of a contributor who uses the model above:

  1. Branch off a green main: git checkout -b feat/login-ui.
  2. Work, committing small slices: each commit is a recoverable snapshot.
  3. Push your branch to the remote (git push -u origin feat/...) — the branch now exists for everyone; CI builds it.
  4. Open a PR (or merge request) describing what changed and why; the review + CI gate it.
  5. Merge to main when green and reviewed.
  6. Pull others' changes regularly — git pull fetches remote changes and then integrates them, usually by merge but sometimes by rebase depending on flags or configuration. Resolve the occasional merge conflict — which is Git asking you to arbitrate two legitimate edits to the same line, not a failure.

Merge vs rebase (one mental lever each): merge fuses lines of history and preserves both; rebase replays your commits as new commits onto a new base for a linear history. Teams favor one; don't mix both. Never force-push a shared branch casually; if a coordinated rewrite is unavoidable, use protected branches and --force-with-lease.

3. Continuous Integration — what a pipeline actually runs, and why it's a gate

CI is the practice of integrating every change into the shared mainline and verifying it automatically and fast, so errors surface minutes after they're written, not weeks later at release (Fowler). Concretely, CI:

  1. Trigger — runs on push / on the PR, not on a button.
  2. Checkout & install — get clean source; install pinned dependencies in a clean env (proving "doesn't work only on my machine" false).
  3. Verify — lint, type checks, tests, compile/bundle, and security checks appropriate to the change. Software Testing explains test levels and strategy; the pipeline's job is to run them quickly and consistently.
  4. Gate — a failed required check blocks the PR/merge (branch protection: cannot be overridden casually). Main stays usable.
  5. Artifact — when the pipeline's job includes packaging, CI or a later build stage produces a versioned build artifact (bundle/image) that deployment consumes. Some CI runs only validate source and do not package; the principle is the same — verified output must be traceable to source.

Why the gate is the point, not the report: a CI that only reports is decoration. A CI that blocks makes "main is verified" enforceable rather than aspirational. Green is not proof that production is safe — it only means the configured checks passed. Migrations, environment differences, dependency drift, and operations still need the release and observability controls below. Tools (per §9): GitHub Actions, GitLab CI, Jenkins, CircleCI — all "workflow/pipeline as a file in the repo."

Pipeline security and supply-chain integrity

A modern pipeline verifies more than application behavior. The build itself is part of the software supply chain, so it should also check and protect:

  • Lockfiles and pinned dependencies — keep dependency resolution reproducible instead of silently changing between builds.
  • Dependency vulnerability scanning — detect known vulnerable packages before promotion.
  • Secret scanning — stop credentials before they enter history or artifacts; rotate anything that leaks.
  • SBOMs — record the exact dependency inventory that produced an artifact.
  • Artifact signing and provenance — prove "this artifact came from this source, built by this trusted workflow" (SLSA).
  • Protected build environments — run untrusted code and secrets with least privilege; do not let a PR inherit production credentials casually.

4. Continuous Delivery & Continuous Deployment — get the distinction right

The "CD" umbrella hides two genuinely different promises (Fowler, continuousdelivery.com):

Continuous Delivery (CD for short)Continuous Deployment
DefinitionKeep every change in a production-ready state; releasing is a deliberate, low-cost extra step.Every merge that passes the pipeline goes automatically to production. No human gate.
The release decisionA human presses "deploy" (or a flag flips) — business can batch, schedule, or pair with a changeAutomatic by default — every passing push is live.
When to chooseAlmost always the right default — you get control and frequency.When deploys are tiny, reversible, and fully warmed by flags/canaries (§6) so automation is safe.
Joke to rememberYou could deploy at any time.You do deploy every time it passes.

Both share a hard precondition: the pipeline must be so reliable and the rollback so cheap that "every passing change to live" (or "any change to live in minutes") is safe. Without §6's strategies and §8's rollback, neither can be honest.

5. Deployment strategies — the "ship it safely" toolbox

Deployment is not one button; it's a set of strategies trading risk/frequency/rollback. Typical modern constellation (frontend) Vercel/Netlify: a preview deploy per PR (see below), then a production deploy on merge. The classic strategies (Fowler: blue-green):

StrategyWhat it doesWhen it shines
Rolling updateReplace the old version with the new one incrementally across instances (many small waves).Simple, always-on; you have a working old version at every instant.
Blue-greenRun two identical environments; deploy to the idle (green), then flip the router to it; the old (blue) becomes the rapid rollback target.Near-zero downtime and quick traffic reversal — useful when you can afford duplicate environments and your data/schema changes remain compatible.
CanarySend a small percentage of real traffic to the new version; watch; if fine, ramp to 100%.When you want real-world validation on live users before committing all.
Feature flagsShip code dark (deployed, not enabled); toggle visibility for an audience instead of deploying newer builds.Separating "deploy" from "release" — reduce exposure by flag. A flag does not undo data writes, schema changes, external side effects, or incompatible code paths.

Deploy ≠ release. Deployed code can be invisible (flag off), and a release can be gradual (canary). This mental split lets teams ship small (deploy) while controlling user exposure (release later / partially). That's exactly §1f's senior model, now mechanized.

Deployment targets and environment promotion

The same pipeline idea changes shape by target:

TargetTypical artifactTypical deployment shape
Static / frontendVersioned static bundlePreview URL per PR; production on merge; instant content rollback.
Server applicationVersioned package or VM imageRolling or blue-green replacement across instances; health checks gate promotion.
ContainerSigned container imageImage built once, promoted across environments; orchestration handles rollout.
Kubernetes / orchestrated serviceContainer image + declarative manifestsRolling updates, readiness/liveness checks, canary via service mesh or ingress.
InfrastructureTerraform/OpenTofu plan or policy bundlePlan reviewed in CI; applied through environment promotion with state protection.

The common pattern is build once, promote many: development → staging → production uses the same artifact and configuration inputs, not a rebuild that might silently differ.

Observability and deployment verification

Deployment is not finished when the command exits. It is finished when production evidence says the new version is healthy:

  • Health checks — readiness and liveness tell the platform whether an instance should receive traffic.
  • Smoke checks — a small set of critical requests proves the deployment is alive and serving the expected version.
  • Metrics — error rate, latency, saturation, and business indicators reveal behavior tests did not cover.
  • Logs and traces — explain why a failure happened across service boundaries.
  • Alerts and SLOs — define when a degradation is urgent and how much error the service can afford (Google SRE).
  • Canary analysis — compare the canary's real-traffic metrics against the stable version before increasing exposure.

Database changes, migrations, and rollback limits

Application rollback is easy only while the database contract remains compatible. If a new version changes schema or writes data the old version cannot read, "roll back the app" may be unsafe. Mature delivery uses:

  • Backward-compatible migrations — make the schema work for both old and new versions during rollout.
  • Expand-and-contract — add the new shape, deploy code that can use both, migrate data, then remove the old shape after compatibility is no longer needed.
  • Separate data and schema risk — a flag can hide a feature, but it cannot un-write corrupted data.
  • Roll-forward — sometimes the safer recovery is a small forward fix, not a return to an incompatible previous artifact.
  • Rollback drills — prove the recovery path before the incident; untested rollback is a hope, not a plan.

5b. SemVer and releases — naming the snapshots you ship

Commits are for developers; versions are the language for users and consumers. The near-universal scheme is Semantic Versioning (SemVer 2.0.0), semver.org): MAJOR.MINOR.PATCH:

  • MAJOR — breaking changes (public API/behavior that breaks consumers).
  • MINOR — additive, backward-compatible features.
  • PATCH — backward-compatible bug fixes.

Plus pre-release labels: 1.0.0-alpha, 2.3.0-rc.1. Precedence: 1.0.0-alpha < 1.0.0-beta < 1.0.0 (pre-releases sort below their release).

Why SemVer in this doc: your pipeline reads the version — bump on release, git tag the commit, build artifact named v2.1.0, reference the exact artifact for deploy/rollback. Version control + CI + releases all speak = MAJOR.MINOR.PATCH, the one string that ties a commit to a live artifact (cf. §1d, API Design).

Release governance — deciding what users get, and when

A deploy makes code present; a release makes it meaningful to users. Governance makes that decision explicit:

  • Release notes and changelogs — explain user-visible changes, migrations, and known risks.
  • Approvals and ownership — define who can promote to production and under what evidence.
  • Release trains — batch changes on a predictable cadence when coordination or customer communication matters.
  • Artifact retention — keep enough verified artifacts to roll back or audit what ran.
  • Environment promotion — advance the same artifact through development, staging, and production with environment-specific configuration.

Decision logic — use the hosting you already have: code on GitHub means GitHub Actions is the frictionless start; for frontend-only work, a git-connected platform (Vercel/Netlify) gives preview + deploy + rollback with the least config; for server/container work, Actions/GitLab/Jenkins. Don't run a third pipeline engine alongside the repo — fewer places wins.

9. Worked example — the HackerRank repo, shipped

Make it concrete with a real project: your solutions repo (built during Problem-Solving practice). Goals: nothing ever lost, tests run on every push, and a clean versioned release per completed challenge.

Setup (one-time):

  1. git init a repo, add challenges/<name>/solution.ext, commit, push to GitHub (or GitLab).
  2. Add a CI workflow (.github/workflows/ci.yml): on push and pull_request to main → run your test runner (e.g. npm test / pytest), plus dependency and secret scanning if available.
  3. Enable branch protection on main: require CI checks and a review before merge.

The rhythm (every challenge):

  1. git checkout -b challenge/heap-median — branch off a green main.
  2. Solve it (Problem-Solving rhythm), commit small slices, push. CI lints/tests each push — red means fix before proceeding.
  3. Open a PR; a reviewer checks it (Big-O, trade-offs, test evidence). CI gates merge.
  4. Merge to main — protected, CI green, so main stays verified by the configured checks.
  5. Tag milestones if the repo needs named checkpoints: git tag v1.3.0. Define the repo's own tagging convention; SemVer is only required when the repository has a public API or compatibility contract.

What this buys you: every solution recoverable (git history + reflog); nothing breaks silently (CI); a versioned, reviewable record of growth (tags + PRs); and if you later deploy it as a site, you push to Vercel and every merge ships a preview URL first. All the theory above, used daily.

9c. The future — where the delivery layer is heading

Trends with real momentum, not speculation:

  • The pipeline is already code; AI writes more of it. Workflow files are versioned in the repo; AI-assisted pipeline authoring and self-healing failing builds are the visible next step — delegating the "fix a red build" loop.
  • Supply-chain integrity becomes a standard pipeline output. SBOMs, signed builds, provenance, and policy gates verify "this exact artifact = this exact source + dependency set" — integrity and audit move from afterthought to pipeline gate.
  • Environments everywhere. Preview/environment-branch deploys mean every PR ships its own URL to browse — the review loop becomes "browse the preview," and production is just the last environment.
  • Shift-left security. Secret scanning, vulnerability checks, and policy gates move earlier into CI, so the pipeline verifies more than "does it build".

9d. The complete mental checklist

If you remember only one image, remember the DAG-and-pipeline picture: commits are snapshots in a content-addressed graph; branches are pointers; CI verifies every change; CD keeps it releasable; deployment ships it reversibly.

Question to askCheck
Can I recover any past state, and can anyone see the history?Committed, pushed to a remote, meaningful messages.
Is every push verified automatically before it matters?CI runs on push + PR; a red build blocks merge.
Is main always releasable?Green CI, protected branch, review required.
If a deploy goes wrong, can I recover within minutes?Known tested route: compatible rollback, roll-forward, or exposure control; migrations considered.
Do I know which exact version is live, and can I find its commit?SemVer tag → release → artifact; changelog kept.
Are secrets out of the repo?No secrets in git history; env/vault at deploy time.
Am I keeping deploy separate from release where it matters?Feature flags for reversible feature exposure; canary with metrics for real-traffic validation.
Can I prove the deployment is healthy after release?Smoke checks, health signals, metrics, logs, traces, alerts, and SLO/error-budget criteria.
Can I prove this artifact came from trusted source and dependencies?Lockfiles, SBOM, signed artifact/provenance, protected build environment.

The maturity test: count how many you answer "yes" without effort. Every "no" is the next thing to automate. That checklist is the delivery layer in practice — the same feedback-loop discipline the Process doc describes, made mechanical.
