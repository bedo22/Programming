Re-render Box Model — Quick Reference

The mental model that makes useState, useEffect, stale-closure bugs, and useRef cohere. Not React-specific — this is just JS scope + closures applied to a function that gets called many times.

Why this doc exists

React components are functions that re-run. Each run creates fresh variable boxes. Closures capture the boxes from their birth render. useState and useRef are just two ways to survive the re-render — one with fresh boxes, one with a stable box. This doc gives you the vocabulary to read any React code and explain its bugs without guessing. Prerequisites: closures lesson, class-to-hooks paradigm shift (§6, §9, §16).

0. How to use this reference

Reading order: standalone. When you hit a React bug involving stale values, intervals, or subscriptions, map it to one of the four bug shapes in §3, apply the fix, and move on. The table in §2 is your cheat sheet for "what survives a re-render?"

1. The rule

  • Every function call creates a fresh scope with fresh boxes for its let/const/parameter names.
  • Reassigning a variable changes the contents of one box. Calling the function again creates a new box with the same name, in a different scope.
  • A closure is born in one specific scope. It holds a pointer to that scope's boxes. It cannot see boxes from later calls of the same function — those boxes live in different scopes the closure has no pointer to.
  • React never rewrites old scopes. It updates its internal store and re-runs your component → new boxes.

2. Plain JS minimal example

// Two renders, two different boxes
let renderNumber = 0;
function Profile() {
  const count = renderNumber;          // fresh box each call
  function readLater() { return count; }
  return readLater;
}
const a = Profile(); renderNumber = 1;
const b = Profile();
console.log(a());  // 0  ← born in call 1, sees call 1's count box
console.log(b());  // 1  ← born in call 2, sees call 2's count box
// Profile was called twice → two count boxes → two different captured values.
// Same name, different boxes. Pointer to one doesn't reach the other.

3. Three storage models in React

Key insight. useState gives you a new box each render (React swaps the pointer). useRef gives you the same box forever (you mutate .current yourself). Both survive the re-run; they differ in which box the callback sees.

4. The four classic bug shapes (and their fix vocabulary)

4.1 Stale value inside a long-lived callback / interval / subscription

Bug: tick function born in render N reads N's count forever.

Fix: useRef — one stable box across all renders; on each render, write latest value into ref.current; the tick function reads through ref.current and always sees the latest. (Do not put the ever-changing value in the deps array if the effect itself drives the change — that creates a teardown/re-run feedback loop.)

4.2 Writing throughput is fine, but reading is stale

Bug: setCount(count + 1) reads the captured count, not the latest.

Fix: functional updater setCount(c => c + 1) — React hands the updater the freshest internal value.

4.3 Need to read the latest value in a callback without re-subscribing each render

Bug: deps array would tear down the subscription too aggressively.

Fix: store the value in a ref and read ref.current — one stable box across all renders.

4.4 First-render-only setup (subscribe once, read latest later)

Bug: empty deps [] makes the setup die after render 1, captured values frozen.

Fix: deps array with [] for setup, but read latest values via refs or use a recent React API (useSyncExternalStore, etc.) — context-specific.

5. Heuristic

Reading code with a callback inside a React component? Ask three questions:

  1. In which render was this callback born? (one specific call of the component)
  2. Which boxes did that render create? (every let/const/useState in the component body)
  3. Are the boxes the callback reads still the ones holding the values I want? (often no — re-renders made new boxes)

6. Why this matches Lesson 2

This is exactly the closure rule, nothing more. A function's birth scope is fixed at birth. Per-render boxes are just per-call boxes. The only thing React adds is that your function gets called many times automatically, so the "new box per call" fact keeps mattering.
