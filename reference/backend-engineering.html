Why this doc exists

Most tutorials teach backend syntax — how to write a route, how to call an ORM method. Almost none teach the thinking process that precedes it: how an experienced engineer answers "what does this request do to the data, and when?" before writing a line. The frontend micro-loop is now well mapped (The Rhythm). The backend has no equivalent map — engineers transfer the React mental model to the server and it silently breaks them: they hold state in memory that should be in the database, they treat each request as if the previous one left everything in place, they write queries without thinking about transactional boundaries. This doc is the missing map. If you've ever written an endpoint that worked in Postman and fell apart under load or concurrency, this is the layer you missed.

Definition — what backend engineering is and is not

Backend engineering is the mental model that says: every server feature is a loop of one disposable request. The scaffold your framework gives you is 20%. The discipline is the long tail. It is not a toolchain, a set of APIs, or a database pattern — it is the thinking process that precedes every line of code. This doc is the map for that process.

History — the constraint inversions

Backend engineering evolved through constraint inversions, the same pattern that shaped every discipline on this shelf:

InversionBeforeAfter

Monolith → ServiceOne process, one databaseMany deployable services, each owning its data

The pattern: every inversion pushed the loop toward smaller, stateless, asynchronous units. The request is the atom; state lives in deliberate external places.

Rhythm, not algorithm — the update-the-loop discipline

Backend work is not a fixed algorithm; it is a rhythm of three rounds. The skeleton is fast. The deepen is thoughtful. The polish is obsessive. The same three rounds apply whether you're writing a single route or a full service. The only difference from The Rhythm is that the "hot reload" is a curl or a test.

The backend mental model — one request at a time

Backend work is a loop, not a toolchain. The scaffold your framework generates is the easy 20%; the mental model is the long tail.

The three threads of a request

ThreadWhat it isServer example
RequestWhat arrives: verb, path, params, body, headers, identityPOST /orders with { items, address } and an Authorization header
ProcessWhat happens: parse, validate, authorize, read/write data, side effectsValidate the body, check the token, read the cart, reduce stock, save the order
ResponseWhat returns: status, body, headers201 Created with the order payload

The difference that matters: the frontend loop (Model → View → Flow) runs over living, persistent state — the component tree holds it across events. The backend loop runs over one disposable request. Every variable your handler created is garbage the moment the response leaves. The entire discipline reduces to one question: before the response goes out, did every value that must survive land in a place that survives? That place is almost always the database (or a signed token the client owns).

Where state is allowed to live on the server

StorageLifetimeSurvives a second request?Use for
Local variableOne requestNoIntermediate computation, request context
In-memory process state (a module-level Map, a global)Process lifetimeSame instance only — lost on restart, not shared across instancesHot caches, rate-limit windows — never as truth
DatabaseDurableYes, every instanceThe source of truth — users, orders, carts
Signed token / cookieToken expiryClient-owned, re-sent per requestIdentity and short-lived session claims

The signature backend bug is scope confusion: putting truth in a module-level Map (lost on restart, invisible to other instances) or in a process-global mutable variable that two requests touch concurrently — then wondering why an endpoint "sometimes" returns stale data. The golden rule: if two requests must see the same value, it is a database row, not a variable. In-memory state is only ever a cache with a known invalidation story (§4).

The request lifecycle — the timeline inside the brackets

An experienced backend dev reads a handler as a timeline, not a block. The route you wrote is a fraction of what actually runs:

StageWho runs itWhat can go wrong
Transport (network → runtime)Framework / reverse proxyMalformed request, timeout, oversized body
Middleware chainMounted middleware, in orderAuth runs too late; CORS misconfigured; body already consumed
RoutingRouterWrong method; param shape mismatch
HandlerYour codeEverything else — validation, authn/authz, reads and writes, business rules
Serialization → responseYou / serializerLeaking internal columns; circular references
Error boundaryError middlewareUnhandled throw → 500 with a stack trace teleported to the client

Middleware is an onion, not a list. A request travels in through each middleware, reaches the handler, then the response travels out through the same layers in reverse. Order decides everything:

// order matters: parse → auth → route → error handler
app.use(cors());                     // 1. headers for everyone
app.use(express.json());             // 2. parse body — BEFORE auth needs req.body
app.use(requireAuth);                // 3. authenticate — the route must not run without this
app.post('/orders', handleOrder);    // 4. the handler
app.use(errorHandler);               // 5. LAST — catches anything thrown downstream

The middleware-ordering bug — the most common new-backend mistake — is exactly this: mounting a protected route before the auth middleware (so the route runs unauthenticated), or parsing the body after a middleware that needs it. You debug it by reading the mount order as a timeline, not by staring at the handler.

Result-shaping rule: shape the response at the handler boundary, never by default-serializing your ORM entity (see API Design §10). Serializing the entity couples your API to your storage schema: rename a column and you break the public contract.

Evolution — the constraint inversions

Like every discipline on this shelf, backend engineering evolved through constraint inversions — moments when a constraint changed and the old approach stopped being sufficient:

InversionBeforeAfterWhat changed
Stateful → StatelessServer held session state in memory; users stuck to "their" server (sticky sessions)Servers are disposable; identity travels with the client (cookies, then signed JWTs / opaque tokens)The constraint: scaling out. If state lives in memory, adding a server breaks the session. Stateless auth let any instance serve anyone. Sessions still exist — but they live in token claims or external stores (Redis), not instance memory.
Monolith → ServiceOne process, one databaseMany deployable services, each owning its dataTeam and scaling pressure (see System Design). The loop doesn't change — each service still runs Request → Process → Respond — but the data you may not touch now has a hard boundary.
Synchronous → AsynchronousEvery side effect ran inside the request: email, image processing, notificationsHeavy or optional work is queued; the request answers fast; the worker catches upThe constraint: response time is a product feature. A 20 ms reply said "200" and e-mailed later. This added a second actor to reason about — the worker (§3).
Manual SQL → ORM → conscious choiceHand-written SQL everywhereORMs abstract the database; then leaks surface (N+1, migration drift)The constraint: developer velocity vs. correctness. The mature position is neither — know both and pick per query (§1e).
Server-ful → ServerlessYou manage the process; it runs foreverThe runtime scales your functions to zero when idleThe constraint: cost and ops. Serverless makes the request the only unit — but reintroduces the state problem: an in-memory cache is now a cold-start gamble. Statelessness stops being a choice and becomes the contract.

The pattern: every inversion pushed the loop toward the same shape — smaller, stateless, asynchronous units. The request is the atom; state lives in deliberate external places; work that doesn't belong in the response is deferred. Learn that shape once and every framework — Express, FastAPI, Go's net/http — is just notation for it.

Authentication vs. authorization — identity, then permission

The two words are routinely conflated. They are different layers with different failure modes:

Authentication (Who are you?)Authorization (May you do this?)
AnswersEstablishes identityEnforces permission
ImplementationVerify credentials — password + salt/hash, OAuth/OIDC exchange, session or token validityCheck a policy — roles, ownership ("is this the user's own record?"), scopes
Where it failsCredential theft, token stolen, password hash unsaltedMissing check, overly-broad check (admin-only instead of owner-or-admin), IDOR
Where it livesUsually one middleware, early in the chain: req.user = decode(token)Per-handler or per-resource: requireRole('admin'), ownership check next to the read it protects

The most common backend security failure is a forgotten authorization check, not a broken login. The login gate works — identity is established — and then a handler fetches something without asking "is this theirs?" (IDOR — Insecure Direct Object Reference). Logged in is not the same as allowed. Two rules cover most of it:

  • Never trust the client for identity or permission. A signed token proves who sent the request; it never proves the user may see this record. Check ownership against the data.
  • Centralize authN, distribute authZ. Authentication is one middleware; authorization is a per-resource check that lives next to the read it guards.

Where the token itself lives (session vs. JWT, expiry, refresh) is a contract matter — see API Design for the client side of that exchange.

Auth in practice — providers and integration

The theory above assumes you own the credentials. In the real web you usually don't — you delegate identity to a provider. The integration pattern is always the same:

  • The redirect dance: app → provider login → provider redirects back with a one-time code → your backend exchanges the code for tokens (and the user's profile) → your app issues its own session/token. The provider's token never leaves your server; the browser only ever holds your app's session. (The exact OAuth/OIDC steps live in API Design's auth exchange notes.)
  • Who owns the account: you can delegate authentication entirely (OAuth providers, passkeys, magic links) or keep a password login — but for any real product, treat the provider as the identity source of truth and your database as the profile cache: a provider user-id is a key, not a credential.
ApproachYou implementDecision trigger
Managed auth (Auth0, Clerk, Supabase Auth, Firebase Auth)Almost nothing — SDK + session handling; providers, MFA, password reset, sessions UI out of the boxShip fast; never want to own credential storage or the password-reset edge cases
Framework batteries (NextAuth/Auth.js, Django allauth, Rails devise)Configuration, not protocol — sessions and OAuth flows provided, runs in your processYou want provider support and sessions without a SaaS dependency or data leaving your stack
Hand-rolled (passwords + OAuth clients)Everything: hashing, reset flows, rate limiting, OAuth clients, session managementOnly when a specific requirement rules out the above — and then copy the managed providers' feature list; every row of it is an edge case you now own

The practical rule: the auth decision is mostly a business decision — how much do you want to own credential security, and how fast do you need to ship — not an engineering showcase. Passwords and 2FA are a compliance surface (see Security & Threat Modeling); a managed provider moves that surface into someone else's SLA. For a small product or a client build, managed auth is rarely the wrong answer; for a large organization, identity is a product and the provider choice is strategic. The Security doc covers what still lands on your plate either way: your app's own authorization, account-takeover recovery, audit logging, and the seam where "logged in" meets "your user's data is now in your system."

Data access — ORMs vs. raw SQL

The ORM is a shorthand for "the entity is a class." Raw SQL is a shorthand for "the database is the system." Both are patterns; neither is a default religion:

DimensionORM (Prisma, Sequelize, Django ORM, ActiveRecord)Raw SQL / query builder (Knex, Drizzle)
Velocity for single-table CRUDFast — model and schema are declared togetherSlower — every read is written by hand
Complex queries, joins, aggregatesCan express them; syntax gets uglyExpressive — the SQL is the SQL
Migrations / schema lifecycleFirst-class (the ORM usually owns them)You own them (or a tool: Flyway, DBmate, Drizzle-kit)
Performance trapsN+1: lazy loading fires a query per rowYou write the queries, so you see the query count
Type safetyExcellent at the model boundaryThinner; you document the contract

The N+1 problem — the most common ORM performance bug: you fetch a list of orders, then the ORM fetches the items for each order one query at a time. A list of 200 orders becomes 201 queries. Fix: eager load (a join/include at fetch time) or batch the reads. Test: count the queries on a large load — if it scales with the row count, it's N+1. The SQL that fixes it — the single JOIN replacing the loop — is in SQL & PostgreSQL §JOINs.

The mature rule is a fence-line, not a religion:

  • ORMs win for everyday single-resource reads/writes, schema evolution, and consistent validation.
  • Raw SQL wins for analytics, bulk operations, and anything the ORM would express wrong — when you catch yourself shaping the query to fit the ORM instead of the data, drop to SQL.
  • The wire format is never the entity (§1b result-shaping). The database row is not the API payload.

The connection layer — pooling

A database connection is expensive to establish and heavy to hold. Postgres budgets roughly ~10MB per connection — 100 app instances × 10 pooled connections each is a gigabyte of server memory before any query runs. The pool is the layer between the loop and the vault:

Pooling optionHow it worksWhen to use
Application-level pool (ORM/driver pool)The process keeps a small set of connections and reuses themEvery app, always — the baseline; pick your ORM's pool and tune min/max
PgBouncer (transaction mode)A proxy pools connections across many app instances, releasing each connection between transactionsMultiple instances/workers sharing one Postgres — the standard production setup (~100KB per connection)
PgBouncer (session mode)Connection held for the whole client sessionPrepared-statement-heavy workloads or long-lived sessions that transaction mode breaks

The rules: set a hard max_connections budget — pool size × instances must fit, or queries queue instead of failing fast; transaction mode breaks session features (prepared statements, session-scoped settings), so know which your driver uses; and treat pool exhaustion as a signal worth alerting on — it is the first thing to die under load spikes.

The three rounds — how a server feature actually gets built

The Rhythm's rounds apply here too, with a server-specific spine. The loop per feature is the same Skeleton → Deepen → Polish cycle:

RoundFrontend (The Rhythm)Backend
SkeletonThinnest end-to-end slice of UIThe route + handler returns a valid empty shape — the right envelope with a placeholder body, correct status code and CORS headers. "Hello from the endpoint."
DeepenStates, bounds, styling made realProcessing made real: body validation, authentication, authorization, the actual read/write, error paths and correct statuses.
PolishEdge cases, a11y, perfRaces, transactions, idempotency, cache invalidation, pagination shape, logging and metrics.

The feedback-loop difference: the frontend sees its result in milliseconds (hot reload). The backend sees its result only when it receives a request — so your "hot reload" is a script, a one-off client call, or a test that hits the route. Senior devs treat a curled request / minimal integration test with exactly the seriousness the frontend gives Fast Refresh: the tighter the loop, the faster the learning.

Background work — queues, jobs, and why you defer

The asynchronous inversion (§1c) made deferred work a first-class part of the loop. Mental model: a request answers fast; heavy or optional work is queued.

PatternWhat it isWhen to reach for itBeware
Inline (synchronous)Everything happens in the request; the client waitsShort ops whose result the response needs (write the record, read the aggregate)Response-time spikes
Background job (worker)Take a task from a queue and run it outside the requestEmail, notifications, image processing, report generation — work the client doesn't need in the replyRetries, failure visibility (dead-letter queue), and idempotency of the job itself
Scheduled / delayedRun at a time or after an interval (digest emails, cleanup, expiring resources)The work is time-triggered, not event-triggeredClock drift; at-most-once instead of at-least-once delivery

The rule that pays for itself: anything the user doesn't watch finish, don't make them wait for. If a notification can arrive thirty seconds late and nobody cares, it belongs in a queue — the endpoint changes from "must not fail" to "returns instantly." The discipline is two obligations: the job must be retryable (failures retried, never silently lost) and idempotent (a retry does not double-send).

And the queue must be durable — a broker (BullMQ/Redis, SQS, RabbitMQ, Kafka), never "a list in memory on one process." Same rule as state above: if more than one worker can exist, the queue is external.

Caching — the three layers where latency hides

Cache turns a slow read into a fast answer. Mental model: three layers, each with its own invalidation story — and invalidation is the actual engineering:

Cache layerWhat is cachedInvalidationDanger
Browser / clientGET responses via HTTP headers (Cache-Control, ETag)Careful response headers; the server is not involvedStale data served fresh-looking when later responses forget headers
Shared / edge (Redis, CDN)Expensive identical responses served to manyTTL; explicit key invalidation on writeAny write must invalidate the key, or cache and DB start disagreeing
In-process / instancePer-process memo of expensive computeTTL, explicit evict, process restartNot shared across instances; this is a cache with an invalidation story, never truth (§1, §4)

The invalidation rule that keeps teams honest: a cache and its source are the same truth until a write happens. Every write path must evict or refresh the affected keys, or the cache becomes a source of fabrication. The classic pattern is cache-aside: on read, try cache; on miss, read the DB and write the cache; on write, write the DB then invalidate the key.

Caching is not the fix for a query that is slow because it is huge. The fix for huge is pagination, a read model, or aggregation. Caching buys nothing for queries nobody repeats.

Redis — the shared cache, queue, and session store

Redis is the concrete face of the shared layer above — an in-memory data store that the whole request loop reaches for, not just for caching. It runs single-threaded, which sounds like a limit and is actually the point: every operation is atomic, so two instances incrementing the same counter cannot race. The five uses, each mapped to a section of this doc:

UseHowThis doc's home
Cache-asideTTL keys; read cache → miss → DB → write cache; invalidate on write (SET key val EX 300)§4 — the invalidation rule applies verbatim
Session storeSession id → data (GET/SET with TTL), reachable from every instance§7 — stateless servers, shared state outside the process
Queue / job brokerBullMQ-style lists (LPUSH/BRPOP) — durable work waiting for workers§3 — "the queue must be durable", never a list in memory
Rate limitingAtomic INCR + expiry window per key per user§1d — the guardrail between the user and the loop
Pub/subPUBLISH/SUBSCRIBE channels for real-time fan-out§3 — background work's notification side

Data structures in one line each: string (values, counters, TTL), hash (a record: session fields), list (FIFO queues), set (uniqueness: "is this user in the cohort?"), sorted set (leaderboards, rate-limit windows, by-score range queries). Persistence (RDB snapshots / AOF log) is a durability option, not a promise — treat Redis as a cache and queue, never as the source of truth your database should be; the write-through discipline is the database's job. For the data-store selection decision and where it sits beside Postgres: Data Modeling §Ecosystem. Hosted faces: Upstash, Supabase Redis, any PaaS's managed Redis — the Substrate §Cloud eras apply.

Transactions and concurrency — "the row changed since I read it"

Two requests hitting the same record is the normal form of failure under load, and it is the most under-taught topic in backend code. Two concepts make it legible:

Transactions — several writes must move together or not at all

Any handler that writes several rows that must all land or none land — order + item + stock decrement — needs a transaction: begin → do the writes → commit, and if any step throws, rollback. The mental model: the observed DB state is either "everything I wrote" or "nothing I wrote."

await db.transaction(async tx => {
  const order = await tx.orders.create({ userId, items });
  await tx.stock.decrement({ sku, by: qty });
  await tx.payments.create({ orderId, amount });
}); // any throw rolls all of it back

Optimistic locking — the fix when two writers may book the same record: a version column bumped on every write, and the update predicate is WHERE id = ? AND version = <read version>. The second writer affects zero rows, you detect the race, and you retry or surface it. Use it when a lost update is worse than retrying a request.

But note the scope: reads do not need transactions; writes do. A read-only endpoint that starts a transaction is usually noise. If a read feeds a later write, those must be in the same transaction. See API Design for idempotency keys on the write side of the contract.

Worked example — trace the loop end to end

One mini-feature, all three rounds: the user adds an item to a cart.

Round 1 (Skeleton) — the envelope

app.post('/api/cart/items', requireAuth, async (req, res) => {
  // right shape, right code; body becomes real next round
  res.status(201).json({ items: [], total: 0 });
});

Round 2 (Deepen) — the processing

app.post('/api/cart/items', requireAuth, async (req, res) => {
  // 1. validate — the body is untrusted input
  const { productId, qty } = parseItemBody(req.body);      // throws → 400
  // 2. durable truth — the cart is a DB row keyed by user (§1)
  const cart = await findOrCreateCart(req.userId);
  // 3. authorize — ownership, not just identity (§1d)
  assert(cart.userId === req.userId, 403);
  const product = await findProduct(productId);             // DB read
  // 4. multiple writes, one unit (§5)
  await db.transaction(async tx => {
    await tx.cartLines.create({ cartId: cart.id, productId, qty });
    await tx.carts.updateTotal(cart.id);                    // recompute
  });
  // 5. shape the response — never the entity
  res.status(201).json(shapeCart(await readCart(cart.id)));
});

Round 3 (Polish) — the edges

  • Idempotency: a double-click sends two identical payloads — an Idempotency-Key header dedupes the side effect.
  • Concurrency: two tabs add the same SKU with a stale stock value — optimistic locking catches it (§5).
  • Cache invalidation: the cart write evicts the cached cart keys (§4).
  • Observability: log userId, timing, and status on every read and write.

That is the whole loop: three rounds, each one deeper, the same Request → Process → Respond model. The Rhythm's rounds — minus the hot-reload luxuries — with the source of truth replaced by "the database decides."

State — the identity and session decision

Where identity lives is a state decision that shapes every handler, so it deserves its own section and terminates the loop backward to §1:

ApproachState livesTrade-off
Session cookie (server-side sessions)Lookup table in a store (DB or Redis), keyed by cookieRevocable instantly; but state must be reachable by every instance
Signed token (JWT / opaque tokens)Claims inside the token the client holdsStateless, scales trivially; revocation is hard — you killed the token, the client still holds it until expiry
HybridShort-lived access token + refresh tokenFast worker auth (first-party) plus revocation at the refresh boundary

Rule to live by: choose based on which you need to revoke. Sessions revoke instantly because a server-side record is looked up per request; a stateless JWT is only revocable before it expires (short lifetime, or a token-blocklist/refresh-token boundary). If "log this user out now" is a requirement (account security, admin bans), you need a server-side record that can be checked or invalidated — a session store, or a token-blocklist/refresh-token revoke. If revocation isn't a business need, stateless claims win. Read both sides in API Design before choosing.

CRUD — the shape of most web apps

Four verbs built a third of the web. "It's just CRUD" is said dismissively; the professional version of CRUD is where the loop's discipline shows — every handler is a request → validate → authorize → mutate → respond sequence, and the five steps below are where most real bugs live.

Create — validate before insert

  • Server-side validation is the boundary: types, lengths, enums, required fields — never trust the client's validation, only its data. The validation schema (Zod, joi, Pydantic) is also your API contract's type source.
  • Return 201 Created plus the persisted resource (its server-assigned id, defaults, timestamps) — the client should not guess what the server stored.
  • Idempotency keys for anything a retry could double-apply — payments especially (see Payments & Commerce).

Read — the query is the contract

  • Fix the resource shape by what the consumers need (the API Design "design the response" rule), then fetch for it — the N+1 trap in §1e is this decision done wrong.
  • Pagination is a default, not a feature: limit/offset or cursor keys; sort and filter as explicit, whitelisted query params.
  • Reads are the one verb where caching is almost always a win — but invalidate on write, or the cache is a lie.

Update — full replace vs. partial patch

  • PUT replaces the whole resource; PATCH updates fields. Pick per route and enforce the difference — a sloppy update clobbers fields the client didn't send.
  • Version or optimistic-lock (an updated_at or version field compared at write) to stop last-writer-wins from silently eating another user's edit — the editing-collision problem every collaborative app hits.

Delete — hard, soft, or tombstone

  • Hard delete: gone forever — audits, history, and links break.
  • Soft delete (deleted_at): recoverable, but every query must remember the filter — it's a bug factory.
  • Tombstone/trash: deleted state plus a retention window, then a scheduled purge. The deliberate default for anything users care about.
  • Choose per resource type — orders and accounts get tombstones; temp uploads get hard deletes — and state the rule in one place, not per handler.

The ownership check

The CRUD authorization rule from §1d, applied verb: every handler that touches a user's data checks "is this theirs?" — even admin routes (ownership or role). The IDOR test is the checklist: fetch record 123 with user B's token, and the handler must fail. This one rule, applied per resource, is the entire difference between "we had a data breach" and "we had a login page."

If your whole API is CRUD over a database, the abstraction is thin: Express + an ORM route-generator (or tools like Fastify + Drizzle, NestJS modules, Django's generic views, PostgREST) cover it. The part that is never "just CRUD" is the loop around it — validation, ownership, idempotency, events (see API Design and Data Modeling).

Anti-tooling clause: before adopting role-based access control because a framework shipped it, ask whether ownership or admin, not roles, is what the data requires. Observability — see the loop, not just run it

Backend engineering is invisible until it fails. The loop is observable when you put these signals on every request:

SignalWhat it showsHow to emit it
Request IDTrace across logs, traces, metricsUUID in header or correlation ID
TimingP99 latency, slow pathsTiming wrapper around handler
Status2xx vs 4xx/5xx rateCount per status code
Authz checkWho tried, who succeededPer-resource ownership log
Cache hit/missCache effectivenessCounter on every cache path
Queue job statusRetries, dead-letter rateWorker emit job state

Rule: if you can't correlate a request across logs, traces, and metrics, you're blind. The loop is only as observable as your signals.

What to do with the signals once they exist — targets, alerts, incidents, postmortems — is the operational discipline: see Observability & Operations.

Error handling — the error is part of the contract

Backend engineering is not just happy-path code. The error contract is part of the API:

StatusMeaningResponse shapeGuideline
4xxClient error{ "error": "Validation failed", "details": [...] }Always return 4xx; never 500
5xxServer error{ "error": "Internal error", "requestId": "..." }Log + return 500 with requestId
429Rate limit{ "error": "Rate limit exceeded" }Respect retry-after header

Rule: the error response is part of the contract. Never leak internal stack traces to the client. Use requestId for correlation. The error boundary middleware (last in the chain) catches everything.

The most common failure modes

FailureWhat happensFix / mental model
Scope confusionTruth kept in code memory instead of durable storage — lost on restart, invisible to other instances, "sometimes" stale.If two requests must see the same value, it's a database. In-memory state is a cache with an eviction story (§1, §4).
Forgotten authorizationIdentity works but a route fetches a record by ID without ownership checks (IDOR).Authz per resource, next to the field it guards (§1d).
N+1 queriesORM lazy-loads a query per row; 200 orders → 201 queries.Eager load / join the aggregation; count queries on a big load (§1e).
Broken transactionMulti-write endpoint partially written when a step fails; orphaned rows.Multi-write moves go in a transaction; the atomic unit is your boundary (§5).
Middleware misorderProtected route runs unauthenticated, or body parsing runs behind auth; CORS misconfigured.Read the chain as a timeline: parse → auth → route → error (§1b).
Endpoint leaks internalsThe ORM entity (column names) becomes the API payload — a schema change becomes a breaking API change.Shape responses at the boundary with an explicit DTO/serialization schema; never serialize entities (§1b).
Cache and DB driftCache returns a stale value after a write touches the same key.Every write invalidates; cache-aside discipline (§4).
Queue jobs not retryable / not idempotentDeferred work lost on crash, or double-notification on retry.At-least-once delivery plus an idempotent worker (§3).
