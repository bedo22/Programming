Definition — the enterprise lane, and what literacy means

.NET is Microsoft's application platform: the C# language, the CLR runtime (like V8 is Node's runtime), ASP.NET Core for web (the .NET equivalent of Express/Fastify/Next), EF Core for data access (an ORM, like Prisma/Drizzle), and SQL Server as its natural database. It is not a "language" in the way the shelf uses the word — it is a stack, and its market position is what matters more than its syntax:

Market segmentDominant backendsWhy
Enterprise / banking / government (US, EU, Gulf, Egypt)C#/.NET, Java/SpringLegacy systems, Microsoft enterprise contracts, compliance, long maintenance cycles
Startups / scale-upsNode/TypeScript, Python, GoIteration speed, one language across the stack, hiring pool
Freelance / agency / small businessNode, PHP/WordPress, PythonClient budgets, CMS ecosystem, speed — the CMS internet
Offshoring / outsourcing hubs (Egypt, India, Eastern Europe)C#/.NET, Java, NodeEU/US enterprises offshore their enterprise systems — and those systems are .NET

Literacy means three things, in this order: (1) you can read a C# codebase — follow an endpoint from controller to database; (2) you can map every concept onto mental models you already own — nothing here is new, only renamed; (3) you know where the lane is — when .NET appears in your professional life and what it signals. It does not mean writing production C# or chasing the ecosystem. If you later choose the lane deliberately, the shelf's backend/API/SQL docs are the curriculum; this doc is the map that makes them transferable.

The request loop, C# edition

The shelf's backend mental model — Request → Auth → Logic → Data → Response — is exactly what ASP.NET Core runs. Nothing here is new; everything is renamed:

Backend Engineering concept (section)ASP.NET Core spellingWhat it is
The middleware chain (§1, §1b)UseAuthentication(), UseAuthorization(), custom middleware classesThe pipeline: every request flows through the chain in order — same mental model as Express middleware
Routing a request to a handler (§1)[ApiController] + [Route("api/shipments")] + action methodsOne class per resource; each method is an endpoint — like a router file with handler functions
Extracting parameters and validating (§1)Model binding + [FromBody], [FromQuery], data annotationsRequest bodies become typed objects automatically; validation runs on binding
The response contract (§1, and API Design)ActionResult<T>, Problem() (RFC 9457), status helpersreturn Ok(dto), NotFound(), Problem() — the same statuses and envelopes your API-design doc prescribes
Authn vs authz (§1d)[Authorize] attributes + JWT bearer middlewareAttribute = permission gate; middleware = identity; the split is the same as Backend §1d
Business logic layer (§1)Services (the "service layer" convention)Controllers stay thin; services hold the request-loop logic — the same structure as your Node handlers
Statelessness & serverless constraint (Substrate §Cloud)Azure Functions, containerized ASP.NET CoreSame rules: state lives outside the process; cold starts are the same gamble

Read any ASP.NET Core endpoint as: middleware → controller → service → EF Core → SQL Server → response. That is the entire bridge.

C# reading literacy — the TypeScript translation table

C# is not exotic if TypeScript is home — it is a sibling: both are statically-typed, class-first languages with async/await, generics, and modern nullability. The translation table covers what you will actually see while reading:

TypeScript you knowC# you will readNotes
interface User { id: number }record User(int Id, string Name) or class with propertiesRecords are typically immutable data carriers; PascalCase properties are the norm
async/await, Promise<T>async Task<T>Task ≈ Promise — same idea, different engine (see the async note below)
Array.map/filter/reduceLINQ: .Select(...), .Where(...), .Aggregate(...)LINQ is SQL-flavored functional programming — your SQL intuition transfers directly
const x = ... / let y = ...var (type inferred), readonlyvar is not dynamic typing — the type is inferred at compile time
null / optional chaining ?.null, ? nullable annotations, null-coalescing ??Same habits: ?? is COALESCE, ?. is optional chaining — the NULL rules from SQL apply to your code too
type / generics <T>Generics <T>, interfaces, abstract classesSame shape; heavier ceremony (more keywords) but nothing new conceptually
Dependency injection by handIServiceCollection, constructor injectionThe framework hands services to constructors — read it as "the framework does DI for you"

Reading rule of thumb: when you meet an unknown C# idiom, ask "what is the TypeScript/JavaScript equivalent?" — there is one, and it is usually the same idea with a different word.

The one place "same word, different meaning" actually bites: async. JS runs on a single-threaded event loop; C# runs on a shared thread pool. The await you write looks identical, but the engine underneath is not — and the footgun differences show up the moment you read real service code:

JavaScript / NodeC# / .NET
Event loop: one thread interleaves I/OThread pool: a worker thread is borrowed while a Task runs
await yields back to the event loopawait returns the thread to the pool; work resumes on a pooled thread
No sync-over-async; blocking stalls the whole loop.Result / .Wait() blocks a pool thread — the classic deadlock in web apps
setTimeout / setIntervalTask.Delay — same idea, only spelled differently

Read async Task methods as: the work can wait without blocking a thread. And treat .Result as a red flag worth flagging out loud — it is the C# equivalent of a memory-leaking long-lived setInterval: it works until it doesn't.

EF Core — the ORM you already understand

Backend Engineering §1e gives you the ORM-vs-raw-SQL decision; EF Core is a fully-featured instance of that decision. What you need to read:

ORM concept (from Backend §1e / SQL doc)EF Core spellingWhat to watch for
The schema mappingDbContext + DbSet<T> propertiesEach DbSet is a table; the class is the row shape
Migrationsdotnet ef migrations add / database updateThe data-modeling migration rules apply unchanged
QueryingLINQ: context.Shipments.Where(s => s.CustomerId == id)LINQ-to-SQL translates to the query language you already know; the same WHERE/JOIN mental model applies
The N+1 trapLazy loading (default off) vs .Include(...)Un-included navigation properties = the N+1 problem from SQL §JOINs, wearing a LINQ hat
The raw escape hatchFromSqlRaw / ExecuteSqlRawSame rules as raw SQL in Node: parameterize or get injected

The one genuinely new-looking piece is change tracking: EF Core watches the objects you loaded and writes back only what changed — an ORM convenience that Node ORMs emulate to varying degrees. When you read context.SaveChanges(), that is the "write the transaction" moment.

Dependency injection & the framework shape

ASP.NET Core is built around constructor injection: services register once, and the framework constructs everything for you. The three lifetimes map directly onto the shelf's statelessness discussion (Backend §7, Substrate §Cloud):

LifetimeWhat it meansShelf translation
SingletonOne instance for the process lifetimeLike a module-level constant — fine for stateless config, dangerous for state (the serverless in-memory-state rule)
ScopedOne instance per HTTP requestThe request-scoped context — the natural lifetime for the DbContext and anything tied to one request
TransientA fresh instance every injectionCheap stateless helpers — like importing a pure function

Reading any .NET service layer: follow the constructor. Whatever the class asks for, the framework provides — and the lifetime labels tell you whether shared state is a deliberate choice or an accident waiting to happen (a singleton holding per-request state is the .NET classic bug, the same class of bug as a module-level cache in a serverless function).

Decoding the version — what ".NET" means in a listing

A job listing that just says ".NET" is ambiguous, because the ecosystem has been through three names for the same product line. Reading the listing correctly is part of the literacy:

What the listing saysWhat it actually is
.NET Framework 4.8 / "ASP.NET"The Windows-only classic (2002–2019, frozen at 4.8). Old banks and government systems still run it — you will read it as legacy, not write it
.NET Core 2.x / 3.1The cross-platform rewrite (2016–2020). Mostly a migration-era marker now
.NET 5 / 6 / 8Modern .NET — Core renamed to drop the "Core". LTS is even-numbered (6, 8); 8 is current, 10 is the next even line
".NET" with no numberAmbiguous by definition — ask the number in the interview. "Which .NET?" is a real interview question, not a trick

One rule of thumb: even number = Long-Term Support, odd number = latest features. If a codebase targets net8.0, it is the modern line — read it with this doc; if it says net48, expect legacy patterns and an older ASP.NET shape.

SQL Server — the T-SQL dialect

.NET shops default to SQL Server, and T-SQL is the SQL you know with a different accent. The reading differences, in one table:

PostgreSQL (the shelf)SQL Server / T-SQL
LIMIT n OFFSET mTOP n (or OFFSET ... FETCH NEXT n ROWS)
now(), interval '7 days'GETDATE(), DATEADD(day, -7, GETDATE())
bigserial auto-incrementIDENTITY(1,1)
ON CONFLICT ... DO UPDATEMERGE (or INSERT ... WHERE NOT EXISTS); no direct UPSERT until recent versions
text[] arrays, JSONBNo arrays; JSON with weaker support — SQL Server's comfort zone is structured relational data
ILIKE, ~ regexLIKE (case-insensitivity depends on collation), no native regex
pg_dump / psqlsqlcmd, SSMS, BACKUP DATABASE

The shared 90% — SELECT anatomy, JOINs, GROUP BY, window functions (T-SQL supports them well), transactions — is exactly what SQL & PostgreSQL teaches. Read any T-SQL query as the same language with these six renames.

When NOT to pick .NET

Literacy is not advocacy. The lane map has a mirror side — the cases where .NET is the wrong tool, and where "why is this .NET?" is the correct reaction:

  • Small business / client work: a WordPress site, a landing page, a small shop — the CMS internet exists because enterprises over-buy. .NET is overhead, not capability.
  • Startup iteration: one language across the stack, fast deploys, small teams — Node/TS wins on hiring pool and iteration speed.
  • Team of one / freelance: the ecosystem weight (Visual Studio, Azure, solution files, project ceremony) is a tax a solo developer pays for nothing.
  • Edge/serverless frontend work: Next.js, Vercel, Supabase — the shelf's Next.js path — has no .NET chapter.

The signal to look for: existing Microsoft enterprise contracts, compliance regimes, and ten-year maintenance horizons. That is where .NET earned its place — and where reading it pays.

Worked example — reading a .NET codebase

A real-shaped ASP.NET Core endpoint, read with the shelf's eyes. The endpoint: GET /api/shipments/{id} — the same shipment-tracking world as SQL §Worked example:

// 0. The entry point — Program.cs: the first file you open
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Shipments")));
builder.Services.AddScoped<IShipmentService, ShipmentService>();   // DI registration
var app = builder.Build();
app.UseAuthentication();   // middleware pipeline: runs in this order, wraps the request
app.UseAuthorization();
app.MapControllers();      // route attributes now work
app.Run();

// 1. The controller — thin, like a Node route handler with validation
[ApiController]
[Route("api/shipments")]
public class ShipmentsController : ControllerBase
{
    private readonly IShipmentService _svc;          // ← DI hands the service in

    public ShipmentsController(IShipmentService svc) => _svc = svc;

    [HttpGet("{id:long}")]                            // GET /api/shipments/42
    public async Task<ActionResult<ShipmentDto>> Get(long id)
    {
        var shipment = await _svc.GetByIdAsync(id);   // ← the request-loop logic lives here
        return shipment is null ? NotFound() : Ok(shipment);
    }
}

// 2. The service — the request loop, in the "service layer" convention
public class ShipmentService : IShipmentService
{
    private readonly AppDbContext _db;                // ← EF Core's DbContext (scoped)

    public async Task<ShipmentDto?> GetByIdAsync(long id) =>
        await _db.Shipments                          // a DbSet — the table
            .Where(s => s.Id == id)                  // WHERE — LINQ translates to SQL
            .Select(s => new ShipmentDto(s.Id, s.TrackingNumber, s.Status))
            .SingleOrDefaultAsync();                 // one row, or null → NotFound
}

// 3. The DTO — the API contract (api-design: the response shape is a deliberate artifact)
public record ShipmentDto(long Id, string TrackingNumber, string Status);

Where to start reading — the first three files:

  • Program.cs — the entry point: DI registrations and the middleware pipeline, in the order they run.
  • appsettings.json — configuration: the connection string, feature flags, and logging settings.
  • *.csproj — the dependency manifest (the package.json of .NET); the <TargetFramework>net8.0</TargetFramework> line tells you which version of the story you are reading.

Read end to end: route binds → controller asks service → EF Core translates LINQ to the SQL you learned → SQL Server answers → DTO out.
