System Design tells the reader which database to choose. API Design tells the reader how to expose the data. But nobody on the shelf teaches the reader how to actually design the schema — the normalization, the keys, the indexes, the migration path. That is this doc's gap. Definition — what data modeling is and what it is not

Data modeling is the discipline of turning facts, relationships, and access patterns into durable structures with enforced rules. It is the answer to three questions asked together: What must survive? What must stay consistent? How will it be read back?

It is not ORM mastery — an ORM is a tool for talking to a schema, not a substitute for designing one. It is not database administration — backups, replication, and capacity are operations. It is not "which database should I pick" — that is System Design's decision, and it only sets the sandbox. And it is not drawing boxes in a diagram tool — the diagram is notation, the design is the decision about keys, constraints, and access paths. A data model is judged by what it enforces and how it performs under the queries the app actually issues.

History — from navigational to relational and back

Data modeling evolved through the same constraint inversions that shaped every discipline on this shelf:

InversionBeforeAfter
Navigational → Declarative (Codd, 1970)Hierarchical/network databases (IMS, CODASYL); you wrote code to walk pointers between recordsThe relational model: state in tables, relationships declared, queried by set logic, not by traversal. What you want, not how to walk to it
Rows → Objects (Hibernate 2001, ActiveRecord in Rails 2004)SQL by hand; object-relational mismatch was a manual choreORMs map tables to classes; schema lifecycle moves into the ORM. Speed for CRUD, leaks for anything the model doesn't fit
Schema → Schema-optional (MongoDB 2009, DynamoDB 2012)One relational schema for everythingDocument and key-value stores drop rigid schemas for flexibility and scale-out; the schema returns as the application's hidden debt
Diagrams → Migrations-as-code (Flyway 2010, Prisma Migrate, Drizzle-kit)Schema changes applied by hand in a consoleEvery schema change is a versioned, reviewable, CI-gated migration file
Purist → Pragmatic (Postgres JSONB 2014 in 9.4, SQLite everywhere, pgvector)Strict relational purism or full schemalessHybrid stores: constraints where they matter, JSONB blobs where they don't, vectors as first-class citizens

The pattern: every inversion pushed modeling toward declaring intent and letting the engine enforce it, then circled back to add flexibility where enforcement costs more than it saves. The vault is designed, not assembled — but it is designed for the queries, not for the theory.

Relational modeling — keys, constraints, and normalization (1NF–3NF)

Normalization is the discipline of removing redundant storage by analyzing what a table's facts depend on. Each normal form removes one class of update anomaly: store a fact once, change it once, and it is true everywhere.

First normal form (1NF)

Columns hold atomic values — no repeated groups, no lists in a cell. If a shipment can have multiple tracking events, "events" is not a column; it is a table.

Non-normalized1NF violation
shipments(id, status, events) where events is "delivered@10:02;out_for_delivery@09:15"Parsing a string to learn the history — every query re-splits the fact
customers(id, name, phone1, phone2, phone3)Adding a fourth phone is a schema change

Fix: each repeated value becomes its own row in a child table, joined by the parent's key.

Second normal form (2NF)

Every non-key column must depend on the whole primary key. Violations appear when the key is composite: a column that depends on only part of the key will be repeated for every combination that shares that part.

ViolationWhyFix
shipment_items(shipment_id, item_id, item_name, quantity)item_name depends only on item_id, not on the pairSplit: items(item_id, item_name); keep the join row with just the pair and quantity

Third normal form (3NF)

Every non-key column depends on the key directly, not through another non-key column. Otherwise the transitive dependency stores the same fact repeatedly and updates drift.

ViolationWhyFix
shipments(id, address_id, city, country)city depends on address_id, not on the shipmentMove city/country into addresses; the shipment references the address by key

The normalization pitfalls — where the theory stops being free

PitfallWhat it costsThe counter-rule
Over-normalizationEvery read becomes a 5-table join; the join count is the tax on each queryStop at 3NF unless a read path proves it needs more; prove it with EXPLAIN
Natural keys as primary keysEmail changes, phone numbers change, product codes get reusedSurrogate key (autoincrement/UUID) as PK, natural keys as UNIQUE columns
Denormalization without a storyCopied data drifts silently — the duplicate is wrong and nobody noticesDenormalize only for a measured read path, with the invalidation rule written in the migration
Nullable-everything"Maybe" columns mean every consumer re-implements the fallbackNOT NULL is the default claim; NULL is a deliberate decision with a meaning
EAV (entity-attribute-value) tables"Flexible" key-value rows make every query a pivot problemOnly for genuinely heterogeneous attributes; prefer JSONB columns for sparse-but-known shapes

BCNF and when to stop normalizing

Boyce-Codd Normal Form tightens 3NF: every determinant must be a candidate key. In practice, 3NF covers the overwhelming majority of real schemas; BCNF matters only with overlapping candidate keys (two natural keys that cross). The pragmatic rule: stop at 3NF unless a specific anomaly proves it needs more. The cost of normalization is join complexity — if a read path needs five joins for a simple result, that schema is over-normalized for that path. Denormalize for a measured read, and document the invalidation story in the migration.

Relationship patterns — cardinality and keys

Relationships are the join between tables — and each cardinality has a canonical shape:

RelationshipPatternExample
One-to-oneFK with UNIQUE, or shared primary keyusers → user_profiles (rarely-needed fields kept apart)
One-to-manyFK on the "many" sidecustomers → shipments
Many-to-manyJunction table with composite primary keyshipments ↔ items via shipment_items
Self-referentialFK pointing at the same tableemployees.manager_id → employees.id (or categories.parent_id for a tree)
PolymorphicAvoid — a single commentable_type + commentable_id pair can't hold a real FK"comments on posts or photos" modeled as one column pair

The many-to-many rule: the junction table is a first-class entity — composite primary key of both FKs, its own timestamps, and its own attributes (quantity, role, enrolled_at). Treating it as an afterthought is how "items" columns and comma-splitting creep in.

Why polymorphic associations are a smell: the commentable_id can't be a foreign key — there's no single parent table — so the engine enforces nothing. Orphaned comments, dangling IDs, and join conditions that must guess the type are the result. Alternatives: separate FK columns per parent with a CHECK guaranteeing exactly one is set, or separate junction tables. The schema is allowed to repeat a shape to keep enforcement.

Data types — choosing column types

The type is the schema's smallest unit of correctness: it enforces domain rules, decides storage and index behavior, and outlives every query. Choose the most specific type that fits the fact.

Domain conceptRecommended typeWhyAnti-pattern
MoneyNUMERIC or integer minor unitsExact arithmetic; no binary floating-point driftFLOAT / DOUBLE PRECISION (0.1 + 0.2 ≠ 0.3)
TimestampsTIMESTAMPTZTimezone-aware; stores UTC, renders localTIMESTAMP without timezone — 9am in which timezone?
DatesDATEDate without a time of dayStoring dates as strings (no ordering, no arithmetic)
BooleansBOOLEANNative semanticsSMALLINT 0/1 with app-level mapping
Identity (internal)BIGSERIAL / BIGINT + sequence8 bytes, sequential, cache-friendlyNatural keys as PK (emails change)
Identity (public/distributed)UUID16 bytes, generated anywhere, opaqueVARCHAR(36) — storage and index costs with no benefit
Enums (stable)Native ENUMType safety enforced by the engineVARCHAR + app-level validation that drifts
Enums (evolving)Reference tableAdding a value is an INSERT, not a migration/lockENUM for values that change (statuses that grow)
Short textTEXT (Postgres: no penalty vs VARCHAR(n))No arbitrary limit to hitCHAR(n) — blank-padded fixed length
Variable payloadsJSONBBinary, queryable, GIN-indexableJSON text storage — slower queries, no index path
IP addressesINETNative type; supports containment and range queriesVARCHAR — no CIDR matching

BIGSERIAL vs. UUID — the decision rule: autoincrement for internal identity (compact, sequential, friendly to B-Tree index locality, natural for joins); UUID when identifiers are generated outside the database (distributed writers) or exposed publicly (no count/order leakage, no enumeration). For UUIDs on hot tables, prefer a time-ordered variant (UUIDv7) — random UUIDs fragment clustered indexes. Public-facing identity never means "send the internal id" — it means a separate opaque identifier, shaped at the boundary (see Backend Engineering §1b).

Constraints — the enforcement toolkit

The database enforces what the app merely hopes. Each constraint is a cheap, permanent invariant — write the claim in DDL, and every future writer (including the ones you forgot) obeys it.

ConstraintWhat it enforcesExample
NOT NULLThe column always has a valuename TEXT NOT NULL — "unknown" and "absent" are different; be deliberate about which is allowed
UNIQUENo duplicate valuesemail TEXT UNIQUE — natural identifiers and idempotency keys live here
PRIMARY KEYUnique + NOT NULL — identifies the rowid BIGSERIAL PRIMARY KEY
FOREIGN KEYReferential integrity — the value exists in the parentcustomer_id BIGINT REFERENCES customers(id)
CHECKArbitrary boolean claim about a rowCHECK (quantity > 0), CHECK (end_time > start_time)
EXCLUSIONNo two rows satisfy a condition simultaneouslyPrevent overlapping time ranges (EXCLUDE USING gist (room WITH =, during WITH &&))
DEFERRABLEConstraint checked at transaction end, not per statementCircular FKs — insert both sides, then verify once

Every foreign key should state its ON DELETE behavior explicitly — the default (NO ACTION) is rarely what you want:

  • ON DELETE CASCADE — strong ownership: delete the parent, children go too (shipment_events under shipments).
  • ON DELETE SET NULL — optional reference: the child survives without the parent.
  • ON DELETE RESTRICT — weak reference: refuse to delete a parent that still has children (an audit record's subject).

And index every FK column — the FK is the default join path, and unindexed FKs make deletes and joins scan.

Indexing strategies — the read path

The query planner will use an index only if it estimates it's cheaper than walking the table. The index is the read path: designing the schema includes designing which paths exist.

Index typeBest forCost / notes
B-Tree (default)Equality, range (<, >, BETWEEN), ORDER BY, joins, unique/PK constraints, prefix LIKE 'foo%'O(log n) lookups; ordered — returns sorted output for free
HashEquality only (=)O(1) point lookups; useless for ranges or ordering. Durable since Postgres 10 — before that, crashes could corrupt them
GIN (inverted)Multi-value containment: arrays, JSONB containment, full-text search vectorsOne entry per component value; heavier to maintain on writes
CompositeFilters combining several columnsLeftmost-prefix rule: (a, b, c) serves a, a+b, a+b+c — not b alone
PartialHot subset: WHERE status = 'active' on a table with millions of stale rowsIndex only the rows queries touch — tiny index, same speed
Covering (index-only scan)Queries that only need the indexed columnsEngine never visits the table at all — fastest read; widen with INCLUDE

The decision rule: index what the actual queries use — columns in WHERE, JOIN keys (foreign keys are the most commonly forgotten indexes), and ORDER BY — then verify with EXPLAIN. Every index taxes writes and storage; the lazy discipline is: add an index when a real query proves it needs one, not preemptively for hypothetical ones. For the full treatment: Use The Index, Luke.

Pagination: avoid OFFSET — it scans and discards every skipped row (OFFSET 10000 pays for 10,020 rows to return 20). Keyset pagination uses the index directly:

-- Bad: OFFSET  — cost grows with page depth
SELECT * FROM shipment_events ORDER BY id LIMIT 20 OFFSET 10000;

-- Good: keyset — the index jumps straight to the page
SELECT * FROM shipment_events WHERE id > :last_seen_id ORDER BY id LIMIT 20;

Reading EXPLAIN ANALYZE — the tuning loop

The query planner picks the cheapest estimated plan. When a query is slow, the plan tells you why — and the gap between estimated and actual tells you whether the problem is the schema or the statistics. The loop:

1. EXPLAIN (ANALYZE, BUFFERS) your_slow_query;
2. Find the node where most execution time is spent.
3. Compare estimated rows vs. actual rows (node by node).
4. Fix what the gap points at (missing index, stale stats, bad join order).
5. Re-run. The plan is the ground truth; everything else is opinion.

What to look for:

SignalWhat it meansFix
Seq Scan on a large table with high actual time, filter removing many rowsThe query qualifies rows but the engine has no cheaper pathMissing index — add it, re-run
Estimated rows off from actual by ~10× at the lowest nodeStale statistics or correlated columns; the bad estimate cascades into every join above itRun ANALYZE after bulk loads; re-check
Nested Loop with high loops=NThe inner node runs once per outer row — time multiplies by loopsMultiply times by loops before comparing; index the inner join key
High shared read vs. shared hit on a hot queryWorking set misses the buffer cache; disk-boundIndex to shrink the read set, or the cache story belongs to System Design
Actual ≪ estimated rowsPlanner overestimated selectivity — built a big hash/sort for a tiny resultStale stats or skewed data; re-analyze, consider extended stats

The cost numbers are planner units, not milliseconds — compare nodes inside one plan, never across queries. ANALYZE executes the query, so never run it on production writes during peak load (see the PostgreSQL EXPLAIN documentation).

Schema evolution — migrations as design decisions

A schema change is a deployment with an extra hazard: the data already exists and old code is still running against it. The safe pattern is expand and contract (a.k.a. parallel change) — the same discipline API Design uses for contracts, applied to rows.

PhaseWhat you shipRollback
ExpandAdd the new column/table (nullable or defaulted); new writes go to both old and new structures; reads still use the oldSafe — drop the addition, no data touched
MigrateBackfill existing rows in the background; write both structures; verify parity on a subset before cutting overSafe — old structure still authoritative
ContractReads switch to the new structure; once no writes touch the old, drop itHard — after this point, rollback needs a reverse migration

The discipline around the pattern:

  • Forward-only migrations. Every change is a numbered, reviewable, CI-gated file. Never edit a migration that has been applied anywhere — write a new one that fixes the damage.
  • Expand-contract for breaking changes (changing cardinality, splitting a table, renaming a column) — each phase deploys independently and the system stays up the whole time.
  • Online tools for the heavy cases: pgroll (Postgres, reversible, expand–contract built in) and gh-ost (MySQL) run large table changes without locking the table.
  • Deploy is a sibling concern — the pipeline, canaries, and rollback limits live in Version Control, CI/CD & Deployment.
  • Backfill in batches. Updating millions of rows in one statement locks the table for its whole run. Process in bounded batches (WHERE id > last AND id <= last + batch) so locks are short and the system stays up.
  • Test the rollback path. Every migration must be reversible until the contract phase — and "reversible" means tested, not imagined. If you can't roll back, you're not ready to deploy.

Reads that feed writes must sit in the same transaction — and the migration file is where such consistency decisions get documented, not the changelog.

CAP applied to schema design

CAP is usually discussed at the infrastructure level (see System Design §6c): which store, which consistency model. But the choice is made in the schema. The vault is not uniformly consistent — you decide per structure how fresh a read may be and what a write must atomically move.

Schema decisionWhat it tradesWhen it wins
Denormalized copy (e.g. orders.total alongside order lines)Consistency of the copy vs. read speed without a joinHot read path; the copy is recomputed by the same transaction that writes the source
Read replica for reportingFreshness (replica lag) vs. isolation of heavy queriesAnalytics queries that must not compete with the write path
Append-only event log instead of mutable stateImmutable facts (audit-perfect, replayable) vs. "current state" convenienceLedgers, audit trails, anything where history is the product
Idempotency keys (a UNIQUE column for client-generated operation IDs)Extra column and constraint cost vs. safe retriesPayment-adjacent writes; the constraint enforces what middleware hopes
Soft deletes (deleted_at)Rows accumulate; every query must filter, every FK can point at a ghostRecovery and audit needs outweigh the query tax — make the filter a partial-index ally

Key rule: state the consistency choice per table in the migration file. "This column is eventually consistent, refreshed by job X" is a design decision that must be written down where the schema change lives — otherwise the next engineer inherits a mystery.

Isolation levels — the transaction knob

ACID's I is a dial, not a switch: each isolation level permits a different class of concurrency anomaly, and the schema is where the choice is made per transaction. (The transaction itself — what moves together in the handler — lives in Backend Engineering §5; this is the consistency side.)

Isolation levelWhat it preventsWhat it allowsWhen to use
READ UNCOMMITTEDNothingDirty reads, non-repeatable reads, phantomsAlmost never; Postgres doesn't even implement it as specified
READ COMMITTED (Postgres default)Dirty readsNon-repeatable reads, phantomsMost applications — the correct default
REPEATABLE READDirty + non-repeatable readsPhantomsReporting and financial calculations that need one consistent snapshot
SERIALIZABLEAll anomaliesNone — but transactions may abort and need a retryStrict consistency where anomalies are unacceptable and aborts are handled

The key insight: isolation is a per-transaction decision, not a per-database one. Run READ COMMITTED for everyday traffic and escalate SERIALIZABLE for the specific transactions that must not interleave. And design the schema to make the common case cheap: short transactions, indexed lookups, and constraints that fail fast instead of waiting on locks.

Beyond the relational default — read models and event sourcing

Not every fact belongs in a normalized table. Two patterns recur when the access paths stop fitting:

Read models

A projection table shaped exactly like a hot query — denormalized on purpose, rebuilt from source facts. The source of truth stays normalized (write path); the read model serves the UI (read path). The rebuild is the invalidation story: batch, on-event, or via a queue. The write is a second write — commit to it in the migration, don't let it drift.

Event sourcing — schema as an append-only log

Instead of "current state" rows that get overwritten, store the facts: shipment_events(shipment_id, happened_at, type, payload) — immutable, ordered, replayable. Current state is a projection over the log, computed on read or maintained as a read model. The trade-off table:

DimensionState tablesEvent sourcing schema
HistoryOnly what you explicitly stored (audit tables)Everything, by construction — the log is the truth
Write pathUPDATE in place; transactions keep consistencyAppend-only INSERT — no overwrite, no lost updates, no locking
Read pathDirect, indexed, fastNeeds a projection (read model) or replay — the read path is your responsibility
VersioningSchema evolves by migrationEvents never change — new event types coexist; you never rewrite history
CostBounded by table sizeLog grows forever; compaction is an operational concern

When JSONB beats tables: sparse, varied, or shape-changing payloads (webhook payloads, feature-flag config, event payloads) — a jsonb column with a CHECK constraint is a schema with a softer enforcement. The rule: enforce structurally what must never be wrong; let JSONB hold what varies. For the storage-and-streaming side of this — document vs. key-value vs. wide-column vs. graph stores, and when to leave the relational model entirely — see System Design §6c (data architecture) and §6e (event and queue reliability). The lazy rule for stores: don't add one unless the relational model has a proven, measured limitation; every extra store is another synchronization problem.

Views and materialized views — shaping reads without duplicating writes

TypeWhat it isWhen to use
ViewA saved query — computed on every access, no storageHide complex joins from app code; give a stable interface over a changing schema; grant access to a view instead of the table
Materialized viewA saved query result — stored on diskExpensive aggregations and denormalized read models that don't need real-time freshness — the schema-level cousin of the read model

Views are free (they are just named queries) — use them liberally as the read-side interface. Materialized views are caches: they must be refreshed (REFRESH MATERIALIZED VIEW) on a schedule or after source writes, and the freshness trade-off is exactly the invalidation story this doc keeps asking for — write it down next to the view definition.

Multi-tenancy — sharing the vault safely

When one deployment serves many customers (tenants), the isolation choice is a schema decision:

PatternHow it worksIsolationCostWhen to use
Separate database per tenantEach tenant gets its own databaseStrongHigh — connection and migration overhead per tenantStrict isolation, regulatory demands, few large tenants
Separate schema per tenantOwn schema in a shared databaseMediumMedium — one migration run per tenant schemaModerate isolation with a manageable tenant count
Shared schema with tenant_idAll tenants share tables; rows carry a tenant keyWeak unless enforcedLow — cheapest at scaleMany tenants, cost-sensitive — the common default

The shared-schema pattern requires database-level enforcement. Every table carries tenant_id, and every query must filter by it — but never trust application code to remember. Postgres Row-Level Security makes the engine the enforcer:

ALTER TABLE shipments ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON shipments
  USING (tenant_id = current_setting('app.tenant_id')::BIGINT);

The tenant key belongs in the primary key of every tenant-scoped table (so the partition or index structure follows it), and the tenant_id filter must reach the engine even through ORMs — a missed filter is a data leak, not a bug.

Tenant isolation is a security control, not just a schema decision: the threat model it defends against, and the other layers that must hold when the schema's enforcement fails, live in Security & Threat Modeling (Infrastructure section and the security checklist).

Schema in code — ORMs, query builders, raw SQL

How the schema is declared and accessed is a tooling decision — the schema itself is the design. The decision table (the runtime side lives in Backend Engineering §1e):

ToolDeclaresWins whenCosts when
ORM (Prisma, ActiveRecord, Hibernate, SQLAlchemy)Schema + access in one language model; migrations usually owned by the toolSingle-table CRUD, small teams, rapid iterationN+1 queries, leaks surface, complex queries fight the abstraction

The lazy rule: start with the tool that makes the schema versioned and reviewable (that is non-negotiable), and pick ORM-vs-builder-vs-raw by how much of your workload is one-table CRUD. Whatever you choose, the schema is designed in this doc's terms first — tools then translate it.

Worked example — "Design the schema for a shipment tracking system"

API Design's worked example designs the public tracking API; this is its vault — the schema that example's endpoints read. Start from the facts, not the UI:

Facts to survive: a customer places a shipment; a shipment has addresses, an ordered list of status events, and items; the API must answer "what is the status of shipment X" and "what happened, when".

Normalized core (3NF) — as forward-only migration files:

-- 001_create_customers.sql
CREATE TABLE customers (
  id BIGSERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  email TEXT UNIQUE NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 002_create_addresses.sql
CREATE TABLE addresses (
  id BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  line1 TEXT NOT NULL,
  city TEXT NOT NULL,
  country TEXT NOT NULL
);
CREATE INDEX idx_addresses_customer_id ON addresses(customer_id);   -- FK = join path

-- 003_create_shipments.sql
CREATE TABLE shipments (
  id BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id),
  origin_address_id BIGINT NOT NULL REFERENCES addresses(id),
  dest_address_id BIGINT NOT NULL REFERENCES addresses(id),
  carrier TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'created' CHECK (status IN
    ('created','picked_up','in_transit','out_for_delivery','delivered','exception','returned')),
  tracking_number TEXT UNIQUE NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_shipments_customer_id ON shipments(customer_id);
CREATE INDEX idx_shipments_status_active ON shipments(status)
  WHERE status IN ('in_transit','out_for_delivery');                -- partial: hot subset

-- 004_create_items_and_events.sql
CREATE TABLE items (
  id BIGSERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  weight_grams INT NOT NULL CHECK (weight_grams > 0)
);
CREATE TABLE shipment_events (
  id BIGSERIAL PRIMARY KEY,
  shipment_id BIGINT NOT NULL REFERENCES shipments(id) ON DELETE CASCADE,
  happened_at TIMESTAMPTZ NOT NULL,
  type TEXT NOT NULL,
  payload JSONB
);
CREATE INDEX idx_shipment_events_shipment_id_happened_at
  ON shipment_events(shipment_id, happened_at DESC);                -- timeline read path

-- 005_create_shipment_items.sql
CREATE TABLE shipment_items (
  shipment_id BIGINT NOT NULL REFERENCES shipments(id) ON DELETE CASCADE,
  item_id BIGINT NOT NULL REFERENCES items(id),
  quantity INT NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (shipment_id, item_id)                                -- junction: composite PK
);

Decision log: tracking_number is a natural key the business knows — it gets a UNIQUE constraint, not the PK (customers can exist without shipments yet; the surrogate keeps every FK stable). shipment_events is an append-only log: history is a product requirement here, so events are never updated — that is the event-sourcing pattern applied where it pays.

Access paths → indexes:

  • "Status of shipment X" → shipments.tracking_number already unique-indexed; status gets a partial index (WHERE status IN ('in_transit','out_for_delivery')) — the active set is a hot subset.
  • "Events for shipment X, newest first" → shipment_events(shipment_id, happened_at DESC) composite; the FK index is the join path.
  • "Customer's shipments" → shipments(customer_id, created_at) composite.
  • Timeline queries filtering by status + date → (status, happened_at) once the partial index stops matching.

The tuning loop in action — "recent events for a hot shipment":

EXPLAIN (ANALYZE, BUFFERS)
SELECT type, happened_at, payload FROM shipment_events
WHERE shipment_id = $1 ORDER BY happened_at DESC LIMIT 20;

 Index Scan using shipment_events_shipment_id_happened_at_idx
   (actual time=0.05..0.08 rows=20 loops=1)
   Buffers: shared hit=3                       ← cached, no disk read

Without the composite index, the same query is a Seq Scan over the whole events table — rows=all, filter removed thousands. The index turned a table walk into a 0.05ms point read.

Schema evolution — adding a delivery window: the API needs delivery_window on shipments. Expand-contract: ALTER TABLE shipments ADD COLUMN delivery_window jsonb; (nullable, additive — safe alone) → backfill from carrier responses in the background → app reads it once populated → no contract phase needed because the column is a pure addition. One migration file, one deploy, the system stayed up.

The same schema in code — the Prisma declaration is the translation of the migration files, not a second design (see the Schema in code section). Premature denormalizationCopied columns go stale; reports and app disagreeNormalize first; denormalize for a measured read path with a written invalidation story
Foreign keys without indexesJoins and deletes suddenly slow at scale — FK columns are ignored by the optimizer until indexedIndex every FK column; it is the default join path
Money as FLOATRounding errors in invoices; 0.1 + 0.2 ≠ 0.3Integer minor units or NUMERIC — never binary floats
Enum-itisAdding a status value is a migration, sometimes a table lockEnums for tiny stable sets; reference tables when values evolve
Nullable-foreverColumns added nullable "just in case" become permanently unconstrainedPlan the backfill in the same migration; contract the null away

God tableOne table with 50+ columns consumed by every service — a shared variable in the databaseDecompose by domain; let each bounded context own its rows (see System Design §6c)

The future — where data modeling is going

SignalWhat it changes
AI-assisted migrationsDiffing schema to schema, generating and reviewing migrations — the design decisions stay human, the boilerplate leaves
Schema drift detectionCI now compares prod schema to migration history — drift becomes a failing check, not a Friday discovery
Vectors in the vaultEmbeddings as first-class columns (pgvector); similarity joins alongside relational ones
Streaming databasesMaterialize/risingwave-style systems treat the query as the storage — read models become continuous, not rebuilt
Serverless SQLiteLocal-first apps with real relational schemas; the vault shrinks to the device and syncs
Constraints on soft dataJSONB grows up — CHECK constraints and generated columns let "schemaless" columns carry real rules

The direction is not "less schema" or "more schema" — it is schema where it must be enforced, softer where it must vary, with the choice made explicitly and recorded in the migration.

Summary — the complete mental checklist

Before you create a table, run this. If you can answer each row, you're ready to write the migration; if not, sketch until you can.

QuestionIf you can't answer…
What facts must survive — and which are derived?List the nouns of the domain; derived values (totals, counts) are not facts
What is the key, and what does it claim?Decide the surrogate PK; put natural identifiers in UNIQUE constraints
Which non-key column depends on what?Run the 3NF dependency check — every column depends on the key, fully and directly
What does each real query need indexed?Map WHERE/JOIN/ORDER BY to index types; verify with EXPLAIN
Is this read a join away, and does the plan show it?Run the tuning loop before adding the column, not after the incident
How does this change ship — and roll back?Write the expand–contract phases as migration files
How fresh may this read be?State the consistency choice in the migration (replica, denormalized copy, event log)
Which tool declares this schema?Pick ORM / builder / raw SQL by workload shape — versioned and reviewable is non-negotiable
Does anything leak from the vault through the API?Shape at the boundary; the column name is not the contract

Print this table. Put it on your wall. Run it before every table you create. The first rows are "know what is true"; the last rows are "know who reads it." That's the entire method.
