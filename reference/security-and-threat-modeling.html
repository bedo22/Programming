Why this doc exists separately

API Design teaches how to issue a JWT. Backend Engineering teaches how to check ownership before returning a record. System Design teaches where to put a trust boundary. But nobody on the shelf teaches the discipline itself: how to enumerate the ways a system can be attacked (STRIDE), how to decide what must be protected and how much that protection costs, and how to say no when the answer matters more than shipping. Security is not a checklist of HTTP headers or ORM settings — it is adversarial thinking plus risk management, and it has its own history (the perimeter dissolved), its own mental models (defense in depth, least privilege), and its own failure modes (security theater, rolling your own crypto). That is the gap this doc fills: everything else on the shelf assumes a well-intentioned user; this doc assumes an adversary with a plan.

Definition — security as the CIA triad

Security is not "adding encryption." It is the preservation of three properties, together, for as long as the system exists — the CIA triad:

PropertyThe questionWhat a failure looks like
ConfidentialityCan unauthorized actors read this?A leaked database dump, an IDOR that returns another user's invoice, secrets in a public repo
IntegrityCan unauthorized actors alter this?An attacker rewriting a price, tampering with a JWT claim, poisoning a training dataset
AvailabilityCan authorized actors access this when needed?A DDoS taking the site down, ransomware encrypting the database, a dependency outage taking everything with it

The triad is a trade-off engine, not a slogan: every design choice trades one leg against another, and every leg has a cost. Stronger confidentiality (encrypt everything, verify everyone) costs availability (more failure points, slower requests). Perfect integrity (immutable append-only everything) costs availability and storage. Security work is the explicit, recorded answer to "which leg does this system bet on, and what did we give the adversary instead?" — the same posture this shelf takes toward CAP (see System Design §6c) and consistency (see Data Modeling & Databases). The availability leg is where security meets reliability: an attacker's cheapest move is often to make the system unusable, which is why denial-of-service shows up in the threat model below and why SRE work is security work.

History — the constraint inversions

Security evolved through the same pattern of constraint inversions as every discipline on this shelf — each one forced by the previous model breaking:

InversionBeforeAfterWhat changed
Castle → Zero Trust"Trust everything inside the corporate firewall.""Never trust, always verify" — mTLS, identity-aware proxies, per-request authorizationThe perimeter dissolved: cloud, remote work, mobile, third-party APIs. The network stopped being a trust boundary (see System Design §5d)
Monolith → Supply Chain"We wrote all the code.""90% of our code is open-source dependencies."Log4Shell (2021) proved the biggest risk is the code you didn't write: a one-line property in a logging library, exploitable from the internet, patched in tens of thousands of systems for months. The wake-up call that made SBOMs and SLSA mainstream (see CI/CD — Pipeline security)
Gatekeeper → Shift-LeftSecurity audits at the end of the SDLC — a review gate before releaseSAST, secret scanning, dependency checks, and threat modeling in the IDE and PR — before code mergesFixing a flaw in production costs ~100x more than fixing it in design; the gate moved from the end of the process to every step of it
Passwords → Federated IdentityEvery app stores its own hashed passwords, its own session logic, its own lockout rulesOIDC/SAML, Passkeys, WebAuthn, identity as a service (Okta, Auth0)Identity became a specialized, audited service — not an app feature. Most apps should buy auth, not write it

The pattern: each inversion moved trust away from a place it could be assumed (the network, the codebase, the end of the pipeline, the app itself) to a place it must be proven — and pushed the proof earlier in the process. The constant: adversarial thinking is the skill; the tools just moved where it happens.

Underlying theory — threat modeling

Threat modeling is the core skill of the discipline: enumerating, before you build, the ways an adversary can abuse what you're building — then choosing which ones to defend against. It has three parts.

The STRIDE taxonomy

STRIDE (Kohnfelder & Garg, Microsoft, 2003 — "The Threats to Our Products") is the checklist that makes threat enumeration complete instead of vibes-based. For every element of the system (each endpoint, each store, each boundary), ask all six:

LetterThreatWhat it attacksCanonical example
SSpoofingAuthentication — "who are you?"Forging a JWT, replaying a stolen session cookie, a phishing page that passes as the real login
TTamperingIntegrity — "can this be changed?"Modifying a signed claim, altering a row mid-request, swapping a file in an upload
RRepudiationNon-repudiation — "who did this, and can they deny it?"No audit log: an admin deletes data and the system cannot say who or when
IInformation disclosureConfidentiality — "can this be read?"IDOR returning another user's record, verbose stack traces, secrets in error messages
DDenial of serviceAvailability — "can it be used when needed?"Flooding a login endpoint, unbounded query parameters, a cache-busting loop that empties the store
EElevation of privilegeAuthorization — "can a low-privilege actor become a high-privilege one?"A regular user hitting an admin-only endpoint, an SSRF letting an internal service read cloud metadata

Trust boundaries and data-flow mapping

A trust boundary is any line where data passes from a context the code does not control into a context it does (or from one privilege level to another). The browser is outside the boundary. The network is outside it. The client SDK is outside it. Every crossing is where validation must happen — and where an attacker operates.

The discipline: draw the data-flow diagram first — every actor (user, cron job, other service, admin tool), every store, every process, and every arrow of data between them. Then mark every boundary. Then run STRIDE on each arrow. The drawing is the threat model's skeleton; STRIDE is its muscle. A feature with no diagram has no threat model, and a feature with no threat model ships bugs on purpose. (The architecture-side treatment of where boundaries go, and how blast radius contains a breach, is System Design §5d; this is the per-feature method.)

Running a threat model — the process

STRIDE and trust boundaries are the vocabulary; this is the session. The output of a threat model is not "we looked at it" — it is a written register of threats, priorities, and decisions, reviewed when the system changes:

StepWhat you doOutput
1. Define scopeWhat system or feature are we modeling? What's in, what's out (third-party services, internal tools, future plans)?Scope statement, system boundary
2. Draw the data-flow diagramEvery actor, process, store, and data arrow; mark every trust boundaryDFD with boundaries
3. Enumerate threatsRun STRIDE on each arrow and each store. No boundary gets a free passThreat list, categorized
4. PrioritizeScore by likelihood × impact (or DREAD: Damage, Reproducibility, Exploitability, Affected users, Discoverability); attack trees for the complex goalsPrioritized threat register
5. Choose treatmentPer threat: mitigate (add a control), accept (documented residual risk — see the risk section), transfer (vendor, insurance), or avoid (don't build it)Mitigation plan with owners
6. ValidateVerify the controls actually hold: code review against the register, tests for the listed attacks, scanners (SAST in CI, DAST against staging, SCA on dependencies — see the ecosystem section)Test results, scan findings
7. Document and reviewRecord the threats, decisions, and owners; re-run the model when the system changes — a threat model is a living document, not a launch artifactThreat model document, review cadence

This is the classic method (Microsoft's STRIDE-based practice). Alternatives exist and are worth knowing by name: PASTA (a 7-stage risk-centric process), TRIKE (risk-management-focused, with a requirements model), and attack trees (decompose an attacker's goal into AND/OR sub-attacks — good for single high-stakes goals like "steal the database"). Tools (the Microsoft Threat Modeling Tool, OWASP Threat Dragon) automate the drawing and the STRIDE prompts, but the discipline is the session, not the tool — a diagram nobody reasoned over is decoration.

Risk management — the decision framework

"Security is risk management" is the thesis; this is the machinery. A risk is a threat with a likelihood and an impact, and every security decision is a treatment choice made on that math:

StepWhat you do
Identify assetsWhat data, systems, and capabilities must be protected? (The CIA triad asks each one: read, change, or stop it?)
Identify threatsWhat could go wrong? STRIDE, threat intelligence, past incidents, the OWASP classes
Assess likelihoodHow probable is each threat? Historical data, industry reports, exposure ("this endpoint is public" raises everything)
Assess impactWhat does it cost if it happens? Financial, reputational, legal, operational — measured in real units
Calculate riskRisk = Likelihood × Impact — the same arithmetic as the prioritization step of a threat model
Decide treatmentMitigate (add controls) · Accept (document the risk with an owner — the disciplined version of "it's fine") · Transfer (insurance, a vendor's SLA, a managed provider) · Avoid (don't build the thing)
Monitor and reviewRisks change: re-assess on system changes, new threats, and after incidents — the register is a living document

The risk register — one row per accepted-or-mitigated risk, kept where the team can see it:

ThreatAssetLikelihoodImpactRiskTreatmentOwnerReview
SQL injectionUser databaseMediumHighHighParameterized queries (Backend §1e) + scanner in CIBackend leadQuarterly
Credential stuffingAuth serviceHighMediumHighRate limiting + MFA + breach monitoringSecurity ownerQuarterly
Dependency compromiseProduction depsMediumHighHighSCA scanning, pinning, blast-radius review (checklist row 7)Platform leadMonthly
Leaked secretsDeploy pipelineLowCriticalHighSecret scanning, managed secrets, rotationPlatform leadMonthly

Measuring posture — the metrics that matter: the register lives or dies on a few numbers you can actually move: vulnerability density (open findings per component — trend it down), patch SLA (% of critical patches applied within 7 days — the Log4Shell lesson), threat-model coverage (% of new features with a register entry), and pen-test findings by severity (zero critical/high at launch). Detection-and-response measurement — MTTD/MTTR, how fast you notice and contain a breach — is the observability domain and lives in System Design §6f (SLOs, on-call, incident response); security consumes those numbers but doesn't own that machinery. The operational practice — alert design, incident response, postmortems — is Observability & Operations.

Mental models — frames for thinking about security

FrameCore questionKey insight
Defense in depthIf this control fails, what else catches it?No single control is perfect. WAF fails → gateway validates. Gateway fails → app validates. App fails → DB constraints reject. Layered controls are the difference between "breached" and "a firewall log entry"
Least privilegeWhat is the minimum this could be granted?Every service, user, and function gets exactly the permissions it needs and nothing more — the DB user can't drop tables, the cron role can't read PII, the frontend can't reach the admin API. A breach inherits the grant's scope
The human is the weakest linkWhere does a technical control get a human bypass?Phishing, password reuse, misconfigured S3 buckets, "temporarily" opened firewalls — more breaches start in humans than in zero-days. Controls must assume a tired person with a deadline on the other end
Don't roll your own cryptoWhat has this algorithm survived?Cryptography is math that punishes arrogance. XOR, base64, and hand-rolled hashes are not encryption. Use audited libraries (Argon2, AES-GCM via your language's crypto module) and managed KMS for keys
Fail safe, not fail openWhat does this do with garbage?Developers test that the system works; security tests that it fails safely. Unknown input, missing header, expired token → deny, log, close — never default to "probably fine, let it through"
Security is a cost center with a business caseWhat are we betting against?Perfection is unaffordable; the discipline is risk management. Threat model → decide what's worth defending → measure whether the controls hold — then say no to the rest

Identity & Access Management (IAM)

IAM is the discipline of answering two different questions that are constantly confused:

  • Authentication — "Who are you?" Proving identity: passwords (hashed — see the cryptography section), MFA, passkeys/WebAuthn, biometrics, device attestation. The login gate.
  • Authorization — "What can you do?" Deciding permission: RBAC (roles), ABAC (attributes/policy), ReBAC (relationships). The per-request check. The mechanics of the check live in Backend Engineering §1d — and the most common backend breach is a missing authorization check, not a broken login (IDOR).

Three decisions dominate real systems:

DecisionThe optionsThe rule
Session vs. tokenServer-side session (revocable instantly, stateful) vs. stateless token (JWT, scales trivially, hard to revoke)Choose by revocation needs — if "log this user out now" matters, you need server-side state. See Backend Engineering §7 and API Design §10
Who owns identity?In-house auth vs. an identity provider (OIDC/SAML with Okta, Auth0, Cognito) vs. passkeysDefault to buying it — identity is an audited specialized service, not an app feature. Write auth only when the business case is explicit
Authorization modelRBAC / ABAC / ReBAC / capability / policy engine — see the five-model table belowRBAC for most; finer-grained models when permissions genuinely vary per resource. Whatever the model, the check must be a scope + ownership check per request — token possession is not authorization (API Design §8h)

The five authorization models, and when each earns its complexity:

ModelHow it worksWhen to useLimitation
RBAC (Role-Based)Users get roles; roles get permissionsSimple orgs and apps with clear job functions — the defaultCoarse-grained; role explosion as exceptions multiply ("admin plus a few extras")
ABAC (Attribute-Based)Policies evaluate attributes of user, resource, and environment ("user.department == resource.owner.department AND time < 18:00")Fine-grained, dynamic permissions — orgs with many conditional rulesPolicies get complex to write, test, and audit
ReBAC (Relationship-Based)Permissions derive from relationships — owner, member, viewer, shared-with (Google Docs, GitHub)Collaborative/social systems where access is about connectionsRelationship graphs need care and indexing (who-can-see-this can be an expensive query)
Capability-basedUnforgeable tokens (API keys, signed capabilities) grant specific access directlyService-to-service, decentralized systems, scoped API keysRevocation is hard; tokens must be managed, scoped, and rotated
Policy engines (OPA, Cedar, Casbin)An external engine evaluates policies against a request, consistently across servicesMicroservices needing one policy language and central auditA new dependency and a policy-language learning curve

The same failure seen from the attack side is broken access control (OWASP A01) — and its most common form is IDOR: a valid user reaching a resource that isn't theirs because an ownership check was missing. The attack class is the OWASP section's job; the prevention lives in Backend Engineering §1d (the ownership check in the request loop) and §7b (the CRUD check per resource). Cross-reference both when you design an authorization model: the model you choose decides how you express the check; the per-request ownership check decides whether the model is enforced.

The wire-level mechanics — OAuth 2.1 flows, OIDC claims, JWT vs. opaque tokens, refresh boundaries, mTLS and SPIFFE for service-to-service — are API Design's job (§8h, §10). What belongs here: the mental model that authentication is a gate and authorization is a per-request decision, and the two must never be merged into "has a valid token".

Cryptography & data protection

Cryptography is the tool for confidentiality, integrity, and non-repudiation — and the three jobs use different primitives that are constantly swapped for each other:

PrimitiveJobCorrect choiceCommon abuse
HashingVerify a secret without storing it (passwords)Argon2 (or bcrypt) — slow, salted, memory-hard, designed for exactly thisMD5/SHA-1/SHA-256 for passwords — fast hashes are easy for attackers to brute-force, which is the opposite of what a password hash wants
EncryptionHide data from readersAES-GCM for data at rest (authenticated — tampering is detected; one unique nonce per key per message — nonce reuse is catastrophic), TLS 1.3 for data in transitBase64 ("obfuscation with a decoder ring"), XOR, custom ciphers, or writing the key next to the data
SigningProve who wrote something and that it wasn't alteredEd25519/RSA signatures; JWTs are signed, never encrypted, so don't put secrets in an unencrypted payload (API Design §8h)Using encryption when signing was needed (or vice versa) — a signed-but-readable token is expected; an encrypted-but-unauthenticated blob is attackable

Key management is the discipline that makes crypto real:

  • Keys live in a KMS (AWS KMS, GCP KMS, Azure Key Vault, or Vault), never in code, never in the repo, never in an env file committed by accident. The KMS stores the key; the app asks it to encrypt/decrypt. The key never touches the app's memory in usable form.
  • Rotation is a schedule, not an incident. "If a key leaks" is not the only reason to rotate — old keys should expire by policy so a leaked key has a shelf life. Automate it; manual rotation is forgotten rotation.
  • Encrypt at rest for the data that needs it — PII, payment data, credentials. Encryption at rest is the last line of defense when the disk, the backup, or the database dump walks off.
  • Secrets (API keys, DB passwords) get a secrets manager and a rotation story — and the pipeline side of secret hygiene (scanning, least-privilege injection) lives in CI/CD — Secrets and configuration.

Application security: the OWASP taxonomy

OWASP's Top 10 is the shared vocabulary of application attacks — an awareness document, not an exhaustive catalog, so treat it as a checklist to start from, never a completeness proof. The point here is not the list — it is the classes: each row is a way of thinking about what the app trusts. The mechanics of each live next door; the class itself lives here.

Attack classThe trust assumption it exploitsMechanics owner
Injection (SQL, NoSQL, OS, template)"User input is data, not code." An injection feeds attacker text into a parser that executes itBackend Engineering §1e — parameterized queries; ORMs help but bypasses exist (raw queries, dynamic table names, aggregates)
Broken access control (IDOR, missing checks)"The endpoint checks ownership." The most common class — an authenticated request that fetches a record by ID without asking whose it isBackend Engineering §1d — ownership check per resource, at the handler
XSS (Cross-Site Scripting)"The browser treats my output as data." Reflected/stored attacker content executes as script in another user's sessionThe browser contract — escaping, CSP, sanitization; see API Design §8h and the frontend docs
CSRF (Cross-Site Request Forgery)"The cookie proves the browser, and the browser is the user." A malicious page rides the victim's authenticated cookies to make state-changing requestsAPI Design §8h — CSRF tokens, SameSite cookies, double-submit
SSRF (Server-Side Request Forgery)"The server only fetches things it intends to." Attacker-controlled URLs make the server reach internal addresses — including cloud metadata endpoints that mint credentialsServer-side URL validation at every fetch boundary; network egress rules (see System Design)
Security misconfiguration"The default config is safe." Default creds, verbose errors, open debug endpoints, exposed admin UIs, misconfigured storage bucketsConfiguration review in the PR gate; the checklist at the end of this doc

The unifying insight: every class is a violated trust assumption about input, output, identity, or state. The threat-modeling habit (STRIDE each endpoint) is what surfaces the class before it ships.

Infrastructure & network security

The fleet-level controls that make a breach survivable:

ControlWhat it doesWhere it breaks
mTLS between servicesEvery service proves its identity to every other — mutual certificates, not just one sideKey rotation, cert sprawl, a mesh that adds latency (see System Design §5d)
WAF / API gatewayThe edge validates traffic before the app sees it: rate limits, blocking patterns, header inspectionIt is a filter, not a security model — the app must still validate everything (defense in depth)
Network segmentationCompromised segment ≠ compromised fleet: the DB subnet unreachable from the public one, the admin plane separateFlat networks where a single pod/VM grants lateral movement; over-segmentation that makes operations impossible
Secrets management in the fleetDynamic, short-lived credentials injected at runtime, not baked into imagesHardcoded creds in images/CI; long-lived keys with no rotation story
Monitoring & responseDetect the breach early and contain it — anomaly detection, alerting, and an incident response runbookDetection with no response plan; alerts nobody is on-call for (see System Design §6f)

Rule: the network is no longer a trust boundary (zero trust) — but it is still a containment tool. Assume any single service can be compromised, and design so that compromise doesn't become the whole company.

The supply chain as an attack surface

Your dependency graph is a fleet of code you didn't write and don't fully control — the threat-model view (the mechanics — SBOMs, SLSA, secret scanning — are CI/CD's job):

Attack vectorWhat it targetsControls
Malicious packageDeveloper installs a typosquatted or hijacked package (same name, one typo off)Lockfiles, package verification, dependency review before adoption
Compromised dependencyA legitimate dependency is hijacked — Log4Shell (CVE-2021-44228) made every unpatched Java server an attack surfaceSBOM, vulnerability scanning in CI, automated patching, the patch SLA from the risk register
Build-system compromiseAttacker injects code during the build — the artifacts themselves are alteredSLSA levels, signed builds, reproducible builds, protected build environments
CI/CD pipeline compromiseAttacker modifies the pipeline to inject a backdoor into every future releasePipeline-as-code review, least-privilege CI, secret scanning, protected branches
Update-mechanism compromiseAttacker hijacks the auto-update path — SolarWinds shipped a signed backdoor to thousands of customersCode signing, update verification, staged/canary rollouts

Same shape as the rest of this doc: assume the trusted thing can be hostile, verify at the boundary, and keep the blast radius small enough that one bad dependency is an incident, not a company-ending event.

The AI-era attack surface

LLMs and agents changed the attack surface in two ways: they added new vulnerability classes, and they made existing ones easier. This is the youngest domain — treat its "best practices" as provisional and keep the threat-modeling habit on top of them.

AttackWhat it isFirst-line defense
Prompt injectionInstructions smuggled into untrusted content (a web page the model reads, an email it summarizes, a user's document) that hijack the model's behaviorTreat model input as untrusted data: separate instruction from content, sandbox the model's tools, and never let model output flow into privileged actions unvalidated
Data exfiltration via the modelThe model as a side channel — private context leaking through responses, embeddings, or the model's tools (a malicious prompt that gets the agent to fetch and return a secret)Least privilege on the model's tools and context; no secrets in the prompt; output validation before anything leaves the trust boundary
Model/data poisoningTraining or RAG data corrupted so the model behaves maliciously for chosen inputsValidate the provenance of training and retrieval data; treat retrieval sources as untrusted
Agent tool abuseAn agent with tools (read files, run commands, send email) is an attack surface — a hijacked prompt becomes a hijacked accountTool-scoped authorization, human-in-the-loop for privileged actions, audit logs of every tool call (repudiation, remember STRIDE)
Generated code as supply-chain riskAI-generated patches are new dependencies and new code — the same supply-chain risk as any dependency, minus the review habitNo "review" checkbox — human review applies to AI code like any other; scanners run on it the same way (see CI/CD — Pipeline security)

Where the AI-agent lifecycle itself — design, tools, evaluation, failure modes — is owned: Software Development Process §9d (the Agent Development Lifecycle). This doc owns what an adversary does to it.

Compliance — when security becomes auditable

Compliance is what happens when security requirements are written into law, contracts, or industry rules. The mindset content is simple — the rest is your organization's compliance program — but a security reference must know the vocabulary, because clients and employers will use it as a requirement:

StandardWhat it coversWhen it applies
SOC 2 Type IIControls over security, availability, processing integrity, confidentiality, privacy (the TSC)SaaS companies selling to enterprises — the audit buyers ask for
ISO 27001An information security management system (ISMS) — governance, policy, processOrganizations wanting formal, auditable security governance
PCI DSSCard data protection — 12 requirements, scoped by how you touch card dataAny system handling card numbers; the mechanics and the scope design live in Payments & Commerce
HIPAAProtected health information (PHI)US healthcare systems and their vendors
GDPRPersonal data of EU residents — consent, rights, breach notificationAny system processing EU personal data, wherever it runs
NIST CSFThe five functions: Identify, Protect, Detect, Respond, RecoverUS federal and critical infrastructure — and a useful self-assessment structure for everyone
FedRAMPSecurity authorization for cloud servicesCloud providers serving US government

The principle: compliance is not security. Compliance is the minimum bar a regulator or contract requires; security is protecting assets beyond that bar. A system can be fully compliant and still vulnerable (the standards are checklists of controls, not proofs of safety) — and a system can be secure and non-compliant (an unpatchable legacy box behind a firewall). Treat compliance as a floor the business chooses for market reasons, then do the threat modeling on top of it. For the freelancer tier this matters once: the moment a client asks about PCI or GDPR, the question "what are we actually required to do, and where is the seam?" is answered by Payments & Commerce and by this doc's checklist — not by fear.

Log security eventsAuth failures, authorization denials, validation failures — the repudiation (R) threat, handledSystem Design §6f (observability), this doc's checklist
Keep dependencies updatedKnown CVEs in dependencies are the most common attack vectorCI/CD — Pipeline security (SCA, SBOM)

Worked example — threat-modeling a file-upload endpoint

A classic feature with a surprisingly large attack surface. The discipline: draw the data flow, mark the boundaries, then run STRIDE against each arrow.

Step 1 — the data-flow diagram with trust boundaries:

       [Browser: untrusted]                     [Internet: untrusted]
              |  POST /uploads (multipart)              |
              ▼                                        ▼
        ┌─────────────┐   validated file  ┌────────────────────┐
        │  API server │ ─────────────────► │  Object storage    │
        └─────────────┘      upload to     └────────────────────┘
              │  metadata row                          │
              ▼                                        │
        ┌─────────────┐        thumbnail worker ◄──────┘ (fetches + reprocesses)
        │  Database   │
        └─────────────┘

   Boundaries: ① browser→API  ② API→storage  ③ storage→worker  ④ worker→DB

Step 2 — STRIDE on each boundary, with the decision:

Threat (per boundary)Realistic?Control (defense in depth)
Spoofing ①: an attacker uploads as another userYes — the obvious oneAuthenticate the request; authorize ownership of the target resource before the bytes land
Tampering ①: the file is not what it claimsYes — the classicValidate server-side (never trust the client's MIME type): magic bytes, size limit, extension policy; store with a server-generated name; antivirus scan if the type demands it
Tampering ③→④: an executable that the worker runsYes — the sneaky oneThumbnail worker runs in a sandbox with no network egress (SSRF-free), timeouts, and a memory limit; never execute or eval the payload
Information disclosure ①: another user's file readable by IDYes — IDOR againOpaque object keys, ownership check on read too — not just on write (see Backend Engineering §1d)
Denial of service ①: 10GB uploads, concurrent floods, zip bombsYes — cheap for the attackerSize limits, quotas, rate limits, decompression limits (zip bombs expand past their size), queue the worker work
Elevation of privilege ②: upload storage key with full bucket accessYes — a config mistakeLeast privilege on the storage credentials: scoped, short-lived, write-only-to-one-prefix; rotation story (KMS section)
Repudiation: "I never uploaded that"Partial — cheap to coverAudit log: who uploaded what, when, from where — the R in STRIDE is a database row, not a wish

Step 3 — the decisions that cost nothing: read-side authorization, server-side validation, opaque keys, quota limits, audit logging. The decisions that cost something: sandboxing the worker, malware scanning, signed URLs for direct-to-storage uploads (see API Design for the presigned-URL pattern). Threat modeling is what makes the second list explicit — before the incident makes it urgent.

The security checklist — the gate

Run this at design time and at PR review. If a row can't be answered, the change isn't ready — this is the shift-left inversion in practice:

CheckIf you can't answer…
Have we drawn the trust boundaries and validated data at every crossing?Draw the data-flow diagram first — no diagram, no threat model, no merge
What does STRIDE say about each boundary?Run the six threats per arrow; a boundary with no threats is a boundary you haven't looked at
Is every state-changing endpoint protected against CSRF, and does it honor idempotency keys?See API Design §8h for the browser contract
Is PII/PHI encrypted at rest and masked in logs?Name the PII fields, the KMS keys, and the log-redaction rule — explicitly
Does least privilege apply to the DB user, the IAM role, and the tool grants?Write the exact grant set the change needs; anything wider is the breach's scope
Is input validated at the boundary — including types we didn't think of as input?Enumerate every source: query params, headers, body, files, URLs, webhooks, model output
If a dependency is compromised tomorrow, what is our blast radius?Pin the dependency versions, run the scanner, write the response step in the runbook
What does the audit log record, and who can tamper with it?The R in STRIDE — log to something the app can't rewrite
What do we say no to, and who approved the no?Security is risk management — the residual risk needs an owner, not silence

FailureSymptomFix

Secrets in gitThe classic .env commit that lives in the .git history forever — rotating doesn't erase itSecrets manager + rotation from day one; secret scanning in CI (see CI/CD — Secrets and configuration); assume any history-committed secret is burned

The future — where security is going

SignalWhat it changes
Passkeys / WebAuthnPasswords (and their breach-and-reuse economy) finally have a replacement that is easier and safer — phishing-resistant by construction
OAuth 2.1 and token hygieneImplicit and password grants die; short-lived tokens, refresh rotation, and a JWT without footguns (PASETO) become the defaults (still a draft — treat it as the direction, not the final text; see API Design §10)
Workload identity (SPIFFE/SPIRE)Service-to-service auth stops being bespoke — every workload gets a machine identity (a SPIFFE ID, provisioned and rotated automatically by SPIRE)
AI security as a disciplinePrompt injection, agent tool abuse, and model poisoning get frameworks, scanners, and audit standards — the youngest domain on this shelf growing up fast
Supply-chain hardening (SLSA, SBOMs)After Log4Shell, provenance becomes a requirement: builds attest who built what from what, and deployments check it (see CI/CD — Pipeline security)
Post-quantum cryptographyLong-lived data encrypted today may be decrypted tomorrow — migration to the NIST-selected post-quantum algorithms (CRYSTALS-Kyber for encryption, CRYSTALS-Dilithium for signatures) is on every KMS roadmap

The direction is not "more controls" — it is fewer trust assumptions, proven at more points, earlier in the process, with the residual risk owned by a human who can say no.

Summary — the complete mental checklist

Before you merge anything, run this. If you can answer each row, the change has a threat model; if not, sketch until it does.

QuestionIf you can't answer…
Where are the trust boundaries, and what crosses them?Draw the data-flow diagram — every arrow is an attack surface
What did STRIDE say about each boundary?Run the six threats per arrow until each has a decision: control, accept, or documented no
Which CIA leg is this feature betting on?State it explicitly — confidentiality, integrity, or availability, and what was traded
Who can do what, and who checks it?Authn and authz separated; per-request scope + ownership checks
What is encrypted, hashed, signed — and with what, and who holds the keys?Argon2/AES-GCM via audited libraries; KMS; rotation on a schedule
What happens to garbage input?Fail-safe: deny, log, close — with the log somewhere the app can't rewrite
What is the blast radius if the worst realistic thing happens?Least privilege plus containment; and the incident response step is written down (see System Design §6f)
What are we saying no to — and who owns the risk?Residual risk needs a named owner; unowned risk is where breaches live

Print this table. Put it on your wall. Run it before every design and every merge. The first rows are "know what the adversary can touch"; the last row is "know what you decided to risk." That's the entire method.
