System Design — How Architecture Handles What Code Alone Cannot

The discipline of deciding how the solution fits together at scale — from services and data flows down to component boundaries and API contracts. Sibling docs: Design Thinking (the product layer upstream), How Developers Think (the implementation loop downstream), API Design (the contract layer that makes boundaries callable), UI/UX & Web Design (the rendering layer that makes state legible), HTML & CSS (the platform substrate the rendering strategy runs on), JavaScript Across Stacks (language-level consequences).

Language: English · العربية

Why this doc exists separately

"The real programming is in system design." This doc captures what that means. System Design is neither the product discovery of Design Thinking nor the component loop of the developer. It is the architectural layer that translates a validated problem into a structured solution — defining services, data ownership, consistency boundaries, failure modes, and the seams where components meet. It operates at two scales simultaneously: architectural (macro: services, events, scaling) and component (micro: bounded contexts, API contracts, trust boundaries). Both are system design; neither is complete without the other.

1. Definition — what system design is and what it is not

What it is

System Design is the disciplined activity of structuring a software solution across trust, consistency, and scaling boundaries. It produces decisions — not code — that determine:

  • Decomposition — what are the independently deployable, scalable, failure-isolated units? (services, functions, modules)
  • Data ownership — which unit is the source of truth for each piece of state?
  • Communication contracts — how do units exchange information? (sync RPC, async events, message schemas)
  • Consistency models — what guarantees does the system make about reads and writes? (strong, eventual, causal, read-your-writes)
  • Failure domains — what fails independently? How does the system degrade? (circuit breakers, retries, fallbacks, sagas)
  • Capacity & scaling — what are the load shapes? Where are the bottlenecks? How do we add capacity?

These decisions are expensive to change later. That is the defining characteristic: system design decisions have high reversal cost. Component-loop decisions (variable names, function extraction) are cheap to change. System design decisions (service boundaries, data ownership) are not.

What it is not

Confused withWhat that isDifference
Enterprise ArchitecturePortfolio-level: standards, governance, roadmap alignment across orgEA sets policy; System Design makes technical decisions within (or against) policy.
Solution ArchitectureA specific engagement: "design this integration for this client"Solution Architecture is a role/deliverable; System Design is the discipline behind it.
Cloud ArchitectureCloud-provider-specific: VPC, IAM, managed services selectionCloud Architecture is a specialization of System Design for one platform.
SRE / DevOpsOperations, reliability, deployment pipelines, observabilitySRE operates what System Design structures. The boundary is porous (SLOs inform design).
Database AdministrationIndex tuning, vacuum, replication lag, backup windowsDBA tunes within a chosen data model; System Design chooses the data model and ownership.
System Design InterviewA 45-minute whiteboard exercise (URL shortener, rate limiter, etc.)The interview samples the discipline; it is not the discipline. Real system design takes weeks.

3. Evolution — paradigms through one lens

Each era's primary constraint produced its system design. When the constraint inverted, the design bets inverted with it — the same pattern documented in JavaScript Across Stacks.

EraPrimary constraintSystem design it producedWhy it was challenged
Monolith (1970s–90s) Hardware cost, deployment simplicity Single process, shared DB, modular code Team scaling: merge conflicts, deploy coordination, single failure domain
Layered / N-tier (1990s–2000s) Separation of concerns, reuse Presentation / Business / Data layers Layers became leaky; changes crossed all tiers; DB became the bottleneck
Client/Server (1990s) Fat client vs thin client tradeoff Smart client (VB, PowerBuilder) or smart server (web 1.0) Web won: zero-install, universal delivery. Client became the browser.
SOA (2000s) Enterprise integration, reuse Coarse services, ESB, WS-*, canonical data model ESB became a bottleneck; contracts too heavy; central governance slowed teams
Microservices (2010s–) Team autonomy, independent deploy, scaling granularity Fine-grained services, decentralized data, API gateway, observability Distributed system complexity: debugging, consistency, operational burden
Serverless / Functions (2015–) Operational overhead, cold start latency, cost at idle Function = unit, managed runtime, pay-per-invocation Vendor lock-in, debugging distributed traces, stateful workloads awkward
Event-driven / CQRS (2017–) Write/read scaling asymmetry, auditability, temporal queries Event log = source of truth, projections = read models Eventual consistency mental model; event schema evolution; replay complexity
Edge / Stateful Functions (2022–) Latency, data gravity, personalization at scale Compute moves to data (Durable Objects, Cloudflare KV, Vercel KV) Consistency across edges; new mental model (not region, not origin)

The arc: constraint changes → old design bet conflicts → new design bet inverts. Monolith inverted to microservices (deployment autonomy > hardware cost). SOA inverted to microservices (team autonomy > reuse). Microservices are inverting to edge/stateful-functions (latency > operational simplicity). Each inversion leaves a legacy layer that still works for its constraint.

5. Underlying theory — what makes a system designed not assembled

System Design rests on a handful of proven results. Each one forces a decision; you cannot "work around" them.

Theory / ResultOriginWhat it forces in system design
CAP Theorem Brewer (2000 conjecture), Gilbert & Lynch (2002 proof) In a network partition, you must choose Consistency or Availability. You cannot have both. Every distributed data system makes this choice explicitly or implicitly.
PACELC Abadi (2010) Refines CAP: even without partitions, there's a Latency/Consistency tradeoff (ELC). "If partitioned → A or C; Else → L or C."
Little's Law Little (1961) L = λW (avg items in system = arrival rate × avg time in system). Forces capacity planning: if λ doubles, either W halves (impossible) or L doubles (queue grows).
Amdahl's Law Amdahl (1967) Speedup ≤ 1 / (serial fraction + parallel fraction / N). Forces parallelization strategy: the serial part always bounds scaling.
Consistency models Lamport (1979), Adya (1999), Bailis et al. (2013) Strong / Sequential / Causal / Eventual / Read-your-writes / Monotonic reads. Every API contract implicitly or explicitly promises one.
Information Hiding Parnas (1972) Module boundaries should hide design decisions likely to change. Not "hide data" — hide the reason for the data structure.
Conway's Law Melvin Conway (1968) "Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations." Service boundaries must align with team boundaries, or the org will fight the architecture.
Erasure Coding / Reed-Solomon Reed & Solomon (1960) Durable storage = k data + m parity shards, survive any m failures. The math behind every cloud storage tier (S3, GCS, Azure Blob).

5b. Mental models — how architects actually reason

The theories above are the guardrails. The mental models are how you navigate inside them. Each model is a compression of the theories for a specific decision context:

Mental modelWhen you use itWhat it compressesFailure mode if misapplied
Bounded Context Map (DDD) Drawing service boundaries; deciding what lives together Conway's Law + Information Hiding. "Team = context" is the heuristic; explicit context map (shared kernel, customer-supplier, anticorruption layer) is the artifact. Contexts too small (chatty services) or too large (modulith with hidden coupling)
Consistency Budget Choosing data model per feature; explaining tradeoffs to product PACELC + CAP. Every feature "spends" consistency budget. Strong = low latency budget; Eventual = high latency budget but high availability. Defaulting to strong everywhere (latency spikes) or eventual everywhere (user-visible anomalies)
Failure Domain Isolation Sizing blast radius; deciding redundancy Little's Law + Erasure Coding. If one thing fails, what else goes down? Zone, region, dependency, deployment unit. Shared fate: single DB for all services; single queue; single deploy pipeline
Latency-Throughput Curve Capacity planning; SLO setting; autoscaling thresholds Little's Law + Amdahl's Law. Latency grows non-linearly past ~70% utilization. The knee is where queueing starts. Scaling at 90% utilization (too late); over-provisioning at 30% (waste)
Decision Reversibility Choosing between options; documenting architecture decisions (ADRs) Information Hiding + Conway's Law. One-way doors (data model, service boundary) vs two-way doors (library, config). Only one-way doors need ADRs. Treating two-way doors as one-way (analysis paralysis); treating one-way doors as two-way (painful migration)
Trust Boundary Map Security review; compliance; multi-tenant design Conway's Law applied to trust. Where does data cross a trust boundary? (User→App, App→DB, Service→Service, Tenant→Tenant). Each crossing needs validation, encryption, audit. Missing boundaries (internal service trusts all callers); over-boundarying (mTLS everywhere with no key rotation)

These models are not checklists — they are lenses. An architect switches lenses per decision: Context Map for boundaries, Consistency Budget for data, Failure Domain for resilience, Latency Curve for capacity, Reversibility for commitments, Trust Boundary for security.

Failure patterns — design for degradation

  • Circuit Breaker — stop calling a failing dependency, fail fast, retry after timeout (Hystrix, Resilience4j, Go-breaker).
  • Bulkhead — isolate resources (thread pools, connections) per dependency so one saturated downstream doesn't starve others.
  • Timeout + Retry + Backoff — every external call has a budget. Exponential backoff with jitter prevents thundering herd.
  • Fallback / Degraded Mode — return stale cache, empty list, static default instead of error.
  • Saga — distributed transaction via compensating actions (order placed → reserve inventory → charge payment → if any fails, run compensations in reverse).
  • Idempotency Keys — every mutating request carries a client-generated key; server deduplicates. Enables safe retries.

6b. Capacity planning — how to estimate load, storage, and latency

Capacity planning is not perfect prediction. It is choosing an architecture that survives uncertainty — the discipline that turns §9's back-of-envelope numbers into a repeatable process.

Capacity planning process

  1. Identify the primary operations (the handful of requests that carry 90% of traffic).
  2. Estimate daily volume per operation from business reality, not hope.
  3. Convert to average QPS/TPS (divide by 86,400 seconds).
  4. Apply a peak multiplier (typically 5–10× average; more for retail/social).
  5. Estimate payload sizes for requests and responses.
  6. Project storage growth: rows/day × row size × retention period.
  7. Estimate hot data that must live in memory for acceptable latency.
  8. Estimate bandwidth (requests × payload size) for egress cost and CDN placement.
  9. Capture the read/write ratio — it decides cache vs primary DB architecture.
  10. State latency requirements (p50, p95, p99) per journey.
  11. Add seasonality and burst behavior (Black Friday, end-of-month, marketing pushes).
  12. Add headroom — plan around ~70% utilization for stateful systems; the latency curve goes vertical before 100%.

Formulas

MetricFormula
Average QPSrequests per day / 86,400
Peak QPSaverage QPS × peak multiplier
Storage growthrows per day × row size × retention period
Bandwidthrequests per second × payload size
Cache memoryhot keys × average value size × overhead (~1.3–1.5×)
Queue deptharrival rate × average processing time (Little's Law: L = λW)

Latency guidance

  • Use percentiles, not averages — a mean hides the 1% of requests that take 10× longer.
  • p50 is the typical experience; p95/p99 are the tail pain that produces user complaints and SLO burn.
  • Latency grows non-linearly near saturation (queueing kicks in past ~70% utilization).
  • Load test before assuming linear scaling — the throughput ceiling is discovered, not assumed.

The rule: if the capacity model can't fit on one page, the architecture is too complex to reason about under load. The model is a decision-support artifact, not a spreadsheet for its own sake.

6c. Data architecture — storage, partitioning, replication, and evolution

Data ownership (§7) says who writes; data architecture says how it is stored, partitioned, replicated, and evolved. Choose storage by access pattern, not by popularity.

Storage decision matrix

NeedGood defaultWhy
Strong consistency, relational integrityPostgreSQL / MySQLACID, joins, constraints

Flexible, semi-structured recordsMongoDB, DynamoDBDocument-oriented schemas
Massive write scaleCassandra, ScyllaDB, BigtableWide-column partitioned writes
Time-series dataInfluxDB, TimescaleDB, PrometheusAppend-heavy, downsampling
Search / full-textElasticsearch, OpenSearch, MeilisearchInverted indexes
Analytics / OLAPClickHouse, BigQuery, SnowflakeColumnar scans over wide tables
Large immutable filesS3, GCS, Azure BlobObject storage, cheap egress options

The worst choice is a database selected because it is familiar, then forced into an access pattern it does not fit.

Partitioning / sharding

StrategyUse whenRisk
Hash partitioningEven distribution by keyRange queries become cross-shard
Range partitioningNatural time or sequential rangesHotspots at the tail (today's data)
Tenant partitioningMulti-tenant isolationNoisy neighbor, uneven tenant sizes
Geo partitioningData residency or latencyCross-region consistency
Composite keysAccess by multiple dimensionsSecondary index complexity

Replication

  • Leader/follower — one writer, many readers; simplest, read scaling with lag.
  • Multi-leader — writers in multiple locations; needed for geo-write, costs conflict resolution.
  • Leaderless / quorum — N replicas, W+R consistency; latency trade-offs via PACELC.
  • Every replication strategy introduces lag — decide what read-your-writes and monotonic reads mean for your API before users hit the gap.
  • Failover risks: split-brain (two leaders accepting writes) is the failure mode that corrupts state — it's why quorum and fencing exist.

Schema evolution

  • Expand-and-contract — add the new column/table while old code still runs; migrate readers; drop the old field. Never mutate in place.
  • Prefer backward-compatible changes (additive fields, nullable defaults) — old consumers keep working.
  • Dual writing for migrations — write to both old and new representations until the switchover.
  • Backfills run as background jobs with checkpoints; they fail mid-way and must resume.
  • Online migrations (pgroll, gh-ost) beat downtime migrations for any always-on system.
  • Define retention up front — storage growth is a capacity and cost decision (§6b, cost row).
  • Treat irreversible data changes (deletes, rewrites) as one-way doors needing an ADR.

6d. Caching architecture — where to cache, what to cache, and how to invalidate

Caching is a scaling lever in §6; here it becomes a design discipline. Every cache is a copy of data with a staleness contract — the question is always "how stale is acceptable?"

Cache levels

LevelExampleUse for
Browser cacheHTML, JS, CSS, imagesStatic assets; zero network cost
CDN cacheCloudFront, Fastly, CloudflareGlobal read-heavy static (and edge-dynamic) content
Edge cacheVercel Edge, Workers KVPersonalized fragments, feature flags, low-latency reads
Application cacheIn-process memoryRepeated computation, request-scoped data
Distributed cacheRedis, MemcachedShared hot data across instances
Database cacheBuffer pool, query cacheStorage-layer reads
Client data cacheReact Query / SWR, ApolloServer-state reuse in the UI (link: Developer Loop)

Write policies

PolicyMeaningTrade-off
Cache-asideApp reads/writes cache explicitlySimple, but cache and DB can drift
Write-throughWrite to cache and storage togetherStronger freshness, higher write latency
Write-behindWrite cache first, persist asynchronouslyFast writes, risk of loss on crash
Refresh-aheadRefresh before expiryFewer misses, extra load on hot keys
Stale-while-revalidateServe stale while refreshingGood UX, temporary staleness

Cache failure patterns

  • Cache stampede / thundering herd — expiry hits, every request recomputes against the DB. Fix: jittered TTLs, request coalescing, refresh-ahead.
  • Hot keys — one key absorbs a disproportionate share. Fix: replication or local caching of the hot key.
  • Oversized values — megabytes in a single key degrade every read. Fix: shrink or store metadata only.
  • Unbounded TTLs — memory grows forever. Fix: TTL, eviction policy (LRU/LFU), size limits.
  • Inconsistent invalidation — cache not invalidated on write → stale data served. Fix: version keys or write-through.
  • Caching unauthorized or personalized data — the most serious: data leaks across tenants/users. Never cache at a layer that skips authorization (see Developer Loop §13c for the same warning).

6e. Event and queue reliability — the operational layer under async

§10's event-driven example is the happy path. Event systems earn their complexity in these details — without them, async delivery is silent data loss.

ConcernPattern
At-least-once deliveryIdempotent consumers (dedupe on event_id)
OrderingPartition key per aggregate — all events for one entity go to one partition
Duplicate eventsEvent ID deduplication at the consumer
Poison messagesDead-letter queue (DLQ) + alerting
Failed processingRetry with exponential backoff, jitter, and a max-attempt cap
Schema evolutionSchema registry (Confluent Schema Registry, JSON/Protobuf)
Event versioningVersion field; upcast old events or run versioned consumers
Transactional emitOutbox pattern (below)
Database-to-stream syncChange Data Capture (Debezium)
ReplayDurable event log; replay is the ultimate recovery tool
Consumer lagMonitor lag; autoscale consumers before lag becomes stale data

The outbox pattern. When a service writes to its database and must emit an event, do both atomically: write the event row into an outbox table in the same transaction as the business write. A relay publishes outbox rows to the broker. It prevents the classic failure — "database updated, event never sent" — the exact scenario that silently breaks the inventory/order consistency in §10.

The rule: an event system is production-ready only when every message can be accounted for — consumed, dead-lettered, or replayable. If an event can vanish silently, the architecture is incomplete.

6f. Reliability and disaster recovery — SLOs, degradation, and recovery

A reliable system is not one that never fails. It is one that fails in controlled, observable, recoverable ways.

The vocabulary

ConceptMeaning
SLIThe measured indicator — latency, error rate, availability
SLOInternal reliability objective ("99.9% of reads < 200ms p99")
SLAExternal contractual commitment (usually looser than the SLO)
Error budgetAllowed unreliability — when it's spent, reliability work outranks features
RPORecovery Point Objective — maximum acceptable data loss
RTORecovery Time Objective — maximum acceptable downtime
Blast radiusWhat fails when one part fails (§5b failure domains)
Graceful degradationWhat still works during partial failure

Disaster recovery patterns

PatternRTO/RPOUse when
Backup and restoreHours / hours-to-a-dayDefault for most systems; cheapest
Point-in-time recoveryMinutes / minutesData corruption is the feared failure
Warm standbyMinutes / near-zeroAvailability matters, cost is secondary
Pilot lightMinutes / near-zeroCost-efficient standby: minimal replicas, scale on failover
Active-passive failoverSeconds–minutes / near-zeroRegion-level resilience
Active-active multi-regionSeconds / near-zeroGlobal read + local write; costs consistency complexity

Drill everything. A backup that has never been restored is a hope, not a plan. Restore drills and failover drills are scheduled work, not incident-time work.

Database backup — the concrete layer

For the database specifically, the recovery story has three concrete levels (schema-design side in Data Modeling & Databases):

StrategyRPO / RTOUse when
pg_dump / logical dumpsHours / hoursSmall databases, cross-version or cross-engine migration — not a production recovery story
WAL archiving (continuous)Minutes / minutesProduction default: full backups + archived write-ahead log enable point-in-time recovery
Physical backups (pgBackRest, WAL-G)Minutes / minutesLarge databases; compressed, parallel, incremental; PITR out of the box
Streaming replicationSeconds / secondsHigh availability — a standby is not a backup, but it buys the fastest RTO

The rules that matter: back up the WAL continuously, not just nightly dumps (PITR is what turns "we lost the last hour" into "we lost nothing since last commit"); store backups off the database host; and test the restore path on a schedule — the drill is the plan's proof.

Incident response — runbooks, on-call, and the postmortem

Detection is designed (§6g); response is a process, and it must exist before the first alert fires. The loop:

PhaseWhat happensThe discipline
DetectAn alert fires (SLO burn, error rate, queue lag)Alerts page humans only when a human decision is needed; everything else is a dashboard
TriageOn-call answers, assesses severity, opens the incidentSeverity before fixing: Sev1 (users down) vs. Sev2 (degraded) vs. Sev3 (cosmetic) decides who is woken up
RespondThe runbook drives: known failure → known steps; unknown → timeboxed investigationA runbook is "if X, do Y" for every failure mode the team has seen before; write it while the memory is fresh
MitigateRestore users first — roll back, degrade, redirect — then fix root causeMitigation and diagnosis are separate jobs; one person does not do both
PostmortemTimeline, root cause, contributing factors, action items with ownersBlameless by construction — the incident is a systems failure, not a person's; every postmortem produces at least one owned, scheduled action

The rules that make it work: exactly one on-call at a time, with a written escalation path and a timebox before waking anyone else; incidents get a channel and a leader, and the leader's job is coordination, not coding; postmortems happen within days, cover the timeline of facts (logs, deploys, alerts — the observability layer provides the evidence), and the fix list is tracked like any other work — a postmortem without a scheduled action item is a diary entry, not a process.

Overload protection

  • Timeouts on every external call — a missing timeout is a hanging dependency.
  • Retry budgets — cap total retries; unbounded retries become cascading load.
  • Exponential backoff with jitter — prevents thundering-herd retry storms.
  • Circuit breakers — fail fast to a broken dependency instead of piling onto it.
  • Bulkheads — isolate thread pools/connections per dependency (§6 failure patterns).
  • Load shedding — drop low-value work (analytics, non-critical reads) before it takes down critical paths.
  • Rate limiting — per-client and per-service caps.
  • Queue backpressure — when producers outpace consumers, let the queue signal back instead of buffering forever.
  • Cancellation propagation — when a caller gives up, cancel downstream work so it doesn't keep burning resources.

6g. Observability — designing systems that can be understood in production

Observability is not "add logs later." It is an architectural requirement with a name: if a failure cannot be seen, localized, and reproduced, the architecture is not operationally complete.

The four signals

SignalPurpose
MetricsCheap aggregate health: latency, errors, saturation (USE/RED)
LogsDiscrete events with context
TracesRequest flow across service boundaries — the only way to localize
ProfilesCPU/memory hotspots when performance is the problem

Architectural requirements

  • Correlation IDs propagated through every request and event — one ID ties logs, traces, and metrics to a single journey (§10 does this for orders).
  • Structured logs (JSON), not free text — searchable, filterable, machine-parseable.
  • Trace propagation (OpenTelemetry) across every service boundary — a trace that stops at one service is a localization failure.
  • Dependency health — each service reports the state of the services it calls (the failure domain map, made visible).
  • Queue lag, cache hit ratio, saturation — the metrics that predict problems before users feel them.
  • Business metrics — checkouts, signups, payments. Technical health alone can't prove the product works.
  • Alerts tied to user impact — noisy alerts get ignored; SLO-burn alerting (§6f) ties alarms to the error budget.
  • Dashboards per service and per critical journey — a green service can still have a broken journey.

The rule: ship observability with the service, not after it. A system you cannot understand in production is not designed — it is merely deployed.

The practice side of this architecture: choosing targets, designing alerts that respect the humans on call, running incidents, and postmortems is the neighbor discipline — see Observability & Operations.

7. Component layer (micro) — where system design meets code

This layer is the direct upstream of the developer loop. Every component the developer builds lives inside a boundary defined here.

Bounded contexts (DDD strategic design)

From Eric Evans (Domain-Driven Design, 2003) and Vaughn Vernon (Implementing DDD, 2013):

  • A bounded context is a semantic boundary within which a domain model applies. "Order" means different things in Sales (quote, negotiation) vs Fulfillment (pick, pack, ship) vs Billing (invoice, revenue recognition).
  • Context Map — explicit relationships between contexts: Partnership, Shared Kernel, Customer/Supplier, Conformist, Anticorruption Layer, Open Host Service, Published Language.
  • Rule: One bounded context = one service (or one deployable module in a modular monolith). Do not share a database across contexts.

API contracts — the seam between components

AspectDecisionEnforcement
SchemaOpenAPI 3.x (REST), Protobuf (gRPC), AsyncAPI (events)CI gate: schema lint, breaking change detection
VersioningURL version (/v1/), header version, or semantic version in schemaDeprecation policy: 6-month notice, parallel run
ValidationGateway validates request/response against schema400 on invalid request; 500 on invalid response (bug)
Contract testingPact (consumer-driven), or provider schema verificationCI gate on both producer and consumer repos

Data ownership — "who mutates what?"

Every piece of mutable state has exactly one owner. The owner is the only component that writes it. All other components read via API or subscribe to events. This is the system-scale version of the per-feature "where does this belong?" decision — the Full-Stack Thinking doc carries that one.

PatternOwnerReadersExample
Single-writer DBService A (owns orders table)Service B reads via Service A's APIOrder service owns orders; Payment service calls Order API
Event-sourcedService A emits OrderCreatedService B projects into its own read modelOrder service emits; Inventory service builds local stock view
Reference dataService A owns countriesEveryone reads local cached copyCountry codes change once/year; cache with TTL

The cardinal sin: two services writing to the same table. This couples their deployment, their schema migrations, their failure domains, and their scaling. It turns two services into a distributed monolith.

Trust boundaries — where to validate

  • External boundary (API Gateway / WAF) — validate auth, rate limit, schema, size, known attack patterns. Reject early.
  • Service boundary (each service) — validate business rules, authorization, data integrity. Do not trust the gateway to have caught everything.
  • Internal boundary (module/function) — validate preconditions (Design by Contract). Fail fast inside the trust zone.

The rule: validate at every boundary. The cost of a validation check is negligible; the cost of corrupted state propagating is not.

The per-feature method for finding those boundaries — drawing the data-flow diagram and running STRIDE against each crossing — lives in Security & Threat Modeling (Threat modeling and Worked example). This section is the architecture's where; that doc is the how to enumerate.

Codebase architecture — the physical form of the boundaries

Every boundary above (bounded context, data ownership, failure domain) has a physical expression: the folder tree. If the code can't see the boundary, the boundary doesn't exist.

  • Flat vs. tree. Flat (everything in one directory) works only for scripts and tiny projects — the moment a second developer, a test suite, or a config file arrives, flat breaks. The tree is not decoration: it's namespaces (imports resolve by path), tooling scopes (lint/test/build target a subtree), and ownership (a folder = a person or team's blast radius). The question isn't "flat or tree" — it's "what is each folder for?"
  • Why src/. One code root keeps the build-visible code separated from config and tooling (package.json, tsconfig, vite.config, CI files) that lives at the root. It also gives import aliases and lint rules a single anchor ("everything under src/ is app code"). Convention > configuration, and src/ is the least controversial convention in the industry.
  • Feature folders vs. layered folders. Layered (controllers/, services/, repos/) organizes by technique; feature folders (checkout/, auth/) organize by business domain. The modern default is feature-first: each feature folder owns its UI, logic, and tests (colocated), and layering emerges inside the feature when it earns it. Layered-at-the-top spreads one feature across five folders — the physical form of a violated bounded context. Colocation is the same principle at file scale: the test, style, and story live next to the code they describe, so deleting a feature deletes everything it owns.
  • Framework-prescribed layouts are the cheapest decision: app/ (Next.js file-based routing — see Next.js), src/ + index.html (Vite SPA), src/app + NgModules (Angular). Recognizing which layout a repo uses is one of the four camp markers.
  • Monorepo layouts add one more level: apps/ (shippable products) vs. packages/ (shared libraries) — the repo-level packaging decision lives in Version Control & CI/CD.
  • The delivery bridge: each contract milestone (the freelance doc's modules) should map to a feature folder — a vertical slice that is buildable, testable, and demo-able on its own. If milestones and folders disagree, one of them is lying; usually it's the folder tree.

Failure surface — what fails independently?

Draw a box around each component. Ask:

  • If this box loses power, what else stops working?
  • If this box is deployed with a bug, what is the blast radius?
  • If this box's database is corrupted, what data is lost?

The answers define your failure domains. Good system design minimizes blast radius: a failure in the Recommendations service should not take down Checkout.

8. Why it is a method, not an algorithm

Like the developer loop and Design Thinking, System Design is not an algorithm. But the reason is different:

  • The developer loop lacks deterministic steps because the problem is discovered while building.
  • Design Thinking lacks deterministic steps because the problem is unknown until framed.
  • System Design has named constraints (CAP, Little's Law, Amdahl, Conway) that bound the option space. You cannot choose "strong consistency + high availability during partition" — CAP forbids it.

However, the decision between valid options is judgment, not derivation.

Constrained by theoryStill a judgment call
You cannot have CP + AP during partitionDo you choose CP (banking) or AP (shopping cart)?
Little's Law bounds queue sizeDo you add replicas, increase timeout, or shed load?
Conway's Law couples org and architectureDo you restructure teams, or accept the architecture the org produces?
Amdahl bounds parallel speedupDo you invest in parallelizing the serial 10%, or accept the limit?

The theories eliminate impossible options. They do not select the right option. That selection is where experience, context, and taste live — the same "rhythm" as the developer loop, but with harder guardrails.

9. Worked example — "Design a URL Shortener"

The canonical system-design interview question, walked through both layers.

Requirements (from Design Thinking output)

  • Shorten long URLs → short codes (e.g., bit.ly/abc123)
  • Redirect short → long in < 50ms p99
  • 100M URLs created / day, 10B redirects / day (100:1 read:write)
  • Custom aliases supported (user-chosen slug)
  • Analytics: clicks per link, referrer, geo
  • 99.99% availability

Architectural layer decisions

DecisionChoiceRationale
Service topologyTwo services: Shorten (write), Resolve (read)Read/write scaling asymmetry (100:1). Separate failure domains.
Storage — ShortenPostgreSQL (strong consistency for alias uniqueness)Custom aliases need ACID uniqueness check. Write volume low (100M/day = ~1150/s).
Storage — ResolveRedis Cluster (in-memory, read-optimized) + PostgreSQL async replication10B redirects = ~115k/s reads. Redis serves hot keys; PostgreSQL is source of truth.
Cache invalidationWrite-through on create; TTL 24h; background sync jobNew links must resolve immediately. Stale TTL acceptable for analytics.
Short code generationBase62 (a-zA-Z0-9), 7 chars = 3.5T space. Counter + Base62 encoding.No collision check needed (counter is monotonic). 7 chars = readable.
Custom aliasUnique index on alias column in PostgreSQLACID guarantee. Reject on conflict. Low contention.
AnalyticsAsync event: RedirectOccurred → Kafka → ClickHouse / BigQueryWrite path stays fast. Analytics is eventual.
API GatewayRate limit (1000/min per IP), schema validation, auth for custom aliasProtect Resolve from abuse. Auth only for write path.
AvailabilityMulti-AZ PostgreSQL (sync replica), Redis Cluster (3 masters), Resolve stateless (K8s HPA)99.99% = ~52.6 min/yr ≈ 4.4 min/month of downtime. Zero-downtime deploys (traffic-shifted) keep that budget intact.

Component layer decisions

Analytics Worker Link Analytics ClickHouse table (short_code, ts, referrer, country, device) Consumes RedirectOccurred from Kafka. No external API.

10. Worked example — "Design an Event-Driven Order System"

Shows when you don't pick a CRUD monolith.

Requirements

  • Place order → reserve inventory → charge payment → confirm shipping
  • Each step owned by different team (Order, Inventory, Payment, Shipping)
  • Any step can fail; must support compensation (cancel reservation, refund payment)
  • Eventual consistency acceptable; audit trail required
  • 10k orders/min peak

Architecture

┌─────────────┐     OrderPlaced      ┌──────────────┐
│   Order     │ ──────────────────►  │  Inventory   │
│  Service    │                      │  Service     │
└─────────────┘                      └──────┬───────┘
       │                                     │
       │ InventoryReserved / InventoryFailed │
       ▼                                     ▼
┌─────────────┐     PaymentCharged    ┌──────────────┐
│  Payment    │ ◄──────────────────►  │  Shipping    │
│  Service    │                       │  Service     │
└─────────────┘                       └──────────────┘
       │                                     │
       ▼                                     ▼
   OrderConfirmed / OrderFailed (compensating events flow back)

Key design decisions

DecisionChoiceRationale
CommunicationAsync events (Kafka), not sync RPCTeams deploy independently. Sync RPC couples availability.
Saga patternChoreography (events) not orchestration (central coordinator)No single point of failure. Each service owns its compensation.
IdempotencyEvery event carries event_id; consumers deduplicateAt-least-once delivery is the Kafka guarantee. Idempotency = exactly-once effect.
Out-of-order handlingEvent version + causation_id; consumers buffer or reject staleNetwork partitions reorder. Consumers must handle.
CompensationInventoryReleased, PaymentRefunded events flow backSaga rolls back by forward actions. No distributed transaction.
ObservabilityCorrelation ID (order_id) propagated through all eventsDistributed trace = filter by correlation_id in log aggregator.

Failure modes this design handles

  • Inventory service down → Order service emits OrderPlaced; Inventory processes when up. No blocking.
  • Payment fails → emits PaymentFailed; Order service emits InventoryRelease; Inventory compensates.
  • Network partition between Payment and Shipping → both continue processing local events; reconciliation job runs hourly.
  • Duplicate PaymentCharged → consumer sees same event_id, ignores second. Exactly-once effect.

ApproachWhat it gives youOrigin

12. Common failure modes

Failure modeWhat it looks likeRoot cause
Distributed Monolith 10 services, shared database, synchronous call chains, single deployment pipeline, one team owns all Did not enforce data ownership. Chose microservices for resume, not for autonomy.
Resume-Driven Architecture Kafka + Kubernetes + Istio + gRPC + Event Sourcing for a 3-person team building a CRUD app Optimized for hiring/ego, not for the problem's constraints.
Premature Sharding Sharded PostgreSQL at 50 GB because "we'll need it" Did not measure. Sharding adds cross-shard query pain, rebalancing ops, client complexity.
Ignoring Idempotency Retries cause double charges, duplicate orders, double emails Assumed exactly-once delivery. Network doesn't provide it.
Treating Eventual as Strong Read-after-write fails: user creates order, immediately queries "my orders," gets empty list Did not pick a consistency model per domain. Assumed "database = strong."
Leaky Trust Boundaries Internal service accepts raw user input because "gateway validates" Gateway misses a case; internal service trusts. Corrupted state propagates.
No Failure Domain Design Recommendations service outage takes down Checkout (shared thread pool / circuit breaker config) Did not draw failure domain boxes. Shared resources created hidden coupling.

Team Topology / Org Design Tools Team Topologies canvas, OrgWeaver, Functionly, Miro templates Conway mismatch → intentional team topology aligned to architecture Interaction mode clarity; Cognitive load per team; Handoff frequency; Dependency cycle count

Selection heuristic: Start with ADRs + Diagrams + Observability (the "minimum viable architecture toolkit"). Add Contract Management when API count >5. Add Chaos Engineering when SLOs exist but are untested. Add IaC/GitOps when infra changes >1/week. Add Formal Spec only for protocols with catastrophic failure cost (payments, consensus, auth). The tool serves the decision — not the reverse.

Signal (2024–2026)What it means for system design
Edge computing / stateful functions Cloudflare Workers, Vercel Edge, Fastly Compute, AWS Lambda@Edge. Compute moves to data. The "service" boundary becomes function + attached storage (Durable Objects, KV, D1). System design must now place state geographically.

Formal verification at the boundary TLA+ for critical protocols (AWS uses it for S3, DynamoDB). Spec the protocol, model-check it, generate code. System design for high-stakes paths becomes specification-driven.

15. Summary — the architectural checklist

Before any code is written for a new domain, verify:

QuestionIf no…
Have we estimated capacity (peak QPS, data volume, growth rate)?Stop. No capacity model = no scaling plan.
Have we drawn the failure domain boxes and verified blast radius?Stop. A single failure must not cascade.
Have we picked a consistency model per data domain?Stop. "Default" consistency is a bug.
Does every mutable state have exactly one owner?Stop. Shared-write = distributed monolith.
Are all trust boundaries validated (gateway, service, module)?Stop. Unvalidated boundary = future corruption.
Are API contracts schema-defined, versioned, and CI-gated?Stop. Implicit contracts break silently.
Is idempotency designed into every mutating endpoint?Stop. Retries will corrupt state.
Does the service topology match the team topology (Conway)?Stop. Org/arch mismatch = friction forever.
Are the architectural decisions recorded as ADRs?Stop. Oral tradition loses context in 6 months.
Does every mutating endpoint have an idempotency key and a retry budget?Stop. Retries will corrupt state (§6e).
Is there a dead-letter queue and a replay path for every event stream?Stop. Silent event loss is undetectable data corruption (§6e).
Are SLOs defined and tied to user impact, with error-budget alerting?Stop. No SLO = no agreed definition of "working" (§6f).
Is the failure visible, localizable, and reproducible (correlation IDs, traces, structured logs)?Stop. An unobservable system is not operationally complete (§6g).
Is storage chosen by access pattern, with a schema-evolution path?Stop. The familiar database that doesn't fit the pattern becomes a bottleneck (§6c).

Print this. Put it on the architecture wall. If the epic can't pass this checklist, it's not ready for the developer loop.
